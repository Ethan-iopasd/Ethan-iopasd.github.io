开场：镜像是一层层叠出来的

每一条会改动文件系统的 Dockerfile 指令都产生一个只读层。容器启动时，在镜像最上面加一个可写层。

理解这一点，缓存、体积、数据丢失的疑问都能自己推出来。

一、镜像分层

三个直接推论：

  1. 同一层被多个镜像共享 —— 10 个基于 python:3.12 的镜像，基础层在磁盘上只有一份
  2. 层是只读的，容器改文件是「写时复制」 —— 改一个文件会把整份复制到可写层，所以容器内改大文件很慢
  3. 容器删掉，可写层就没了 —— 这就是必须用数据卷的原因

二、Dockerfile 常用指令

指令 作用
FROM 指定基础镜像
WORKDIR 设置工作目录，后续指令都在此目录下执行
COPY 从构建上下文复制文件进镜像
ADD 类似 COPY，还能解压 tar、拉远程 URL（不推荐，语义不清晰）
RUN 构建时执行命令，产生新层
ENV 设置环境变量，构建时和运行时都生效
ARG 构建时参数，运行时不可见
EXPOSE 声明端口，仅是文档性质，不真的开放
CMD 容器启动的默认命令，可被 docker run 覆盖
ENTRYPOINT 容器启动的固定命令，CMD 变成它的默认参数
VOLUME 声明匿名数据卷

CMD vs ENTRYPOINT

CMD ENTRYPOINT
能否被覆盖 ✅ 完全覆盖 ❌ 只能追加参数
适合 可变的默认行为 固定的主程序

ENV vs ARG

⚠️ 不要用 ENV 存密码。ENV 会写进镜像元数据，docker history 就能看到。ARG 也会留在构建缓存里，同样不安全。

三、缓存：决定构建速度

Docker 按层顺序比对缓存。任何一层的输入变了，它和它之后的所有层全部失效。

错误写法

改一行业务代码 → COPY . . 失效 → 依赖重新安装（可能几分钟）。

正确写法：把变化频率低的放前面

原则：越稳定的指令越靠前。

还要注意 .dockerignore

没有它，COPY . . 会把 .git（可能几百 MB）也复制进去，还破坏缓存。

四、多阶段构建：把体积压下来

编译型语言（Go / Java / Rust）的构建依赖很大，但运行时不需要。

体积对比：golang:1.23 约 800MB → alpine + 二进制约 15MB。

前端项目同理：用 node 镜像构建，产物拷进 nginx 镜像。

五、几个容易踩的点

RUN 合并能减小层数

⚠️ 关键点：清理必须在同一个 RUN 里。分成两条指令时，rm 只会在新层里「删除」文件，文件仍然存在于下面的层里，镜像并不会变小。

基础镜像选型

镜像 体积 说明
python:3.12 ~1GB 完整 Debian，工具齐全
python:3.12-slim ~130MB 精简 Debian，日常推荐
python:3.12-alpine ~50MB 基于 musl libc，可能编译不过某些 wheel

⚠️ Alpine 用 musl 而不是 glibc。带 C 扩展的包（numpy、psycopg2 等）可能没有预编译 wheel，需要现场编译，反而更慢更麻烦。不确定就选 -slim。

六、常用命令对照

目的 命令
构建并打标签 docker build -t myapp:1.0 .
看镜像分层与体积 docker history myapp:1.0
看镜像总大小 docker images myapp
查看构建上下文是否过大 构建时留意 Sending build context to Docker daemon 那行
进入运行中的容器 docker exec -it <container> sh
看容器日志 docker logs -f <container>

常见坑清单

  • 先 COPY . . 再装依赖，导致每次改代码都重装依赖
  • 忘了写 .dockerignore，把 .git、node_modules 打进镜像
  • 清理缓存的 rm 和安装命令不在同一个 RUN 里（镜像不会变小）
  • 用 ENV 传密码（docker history 可见）
  • 以为 EXPOSE 会真的开放端口（它只是声明，映射靠 -p）
  • CMD 和 ENTRYPOINT 搞混，导致 docker run 传参行为不符预期
  • 无脑用 Alpine，遇到带 C 扩展的包编译失败
  • 用 ADD 拉远程 URL（下载的文件不会进构建缓存，且无法校验）
  • 把数据写在容器可写层，删容器就丢
