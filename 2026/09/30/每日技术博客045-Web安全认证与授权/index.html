开场：认证解决「你是谁」，授权解决「你能干什么」

问题 归属 典型漏洞
你是谁？ 认证（Authentication） 弱口令、会话固定、JWT 校验缺失
你能干什么？ 授权（Authorization） 越权（水平 / 垂直）、对象级授权缺失
密钥放哪？ 密钥管理 硬编码、提交进仓库、永不轮换

实际事故里授权漏洞比认证漏洞多得多 —— 认证只要用现成方案就不太会错，授权是每个接口都要自己写对的。

一、Session 与 JWT：核心差别是状态存在哪

维度 服务端 Session 无状态 JWT
状态位置 服务端（内存 / Redis / DB） 令牌自身
存储介质 HttpOnly Cookie 通常 localStorage / Authorization 头
主动失效 ✅ 删 Session 即可 ❌ 做不到（只能等过期）
水平扩展 需要共享存储（Redis） ✅ 天然无状态
携带内容 只有一个 session id 可带角色、权限等声明
大小 几十字节 几百字节到几 KB（每个请求都传）
泄露后 可立即踢下线 无法撤销，直到过期
XSS 影响 HttpOnly 下拿不到 localStorage 下可直接读走
CSRF 影响 ⚠️ 有（Cookie 自动携带） ✅ 无（手动加头）

结论：常规 Web 应用优先 Session + HttpOnly Cookie；JWT 适合服务间调用、无状态横向扩展、以及作为 OAuth 的令牌格式。

⚠️ JWT 不能主动失效 是最被低估的问题。用户改密码、管理员封号、令牌被盗，都只能等它自然过期。补救方案：短有效期（5–15 分钟）+ 刷新令牌 + 服务端黑名单 —— 但一旦引入黑名单，你就又有了服务端状态，JWT 的「无状态」优势也就没了。

⚠️ 不要把 JWT 放 localStorage。任何一处 XSS 都能直接读走。放 Cookie 则要考虑 HttpOnly（防读）和 SameSite（防 CSRF）的组合。

二、JWT 的典型误用

JWT 结构：base64url(header).base64url(payload).base64url(signature)

⚠️ payload 是 base64 编码，不是加密。 任何人复制到 base64 -d 就能看内容。绝不能放密码、身份证、内部权限细节。

误用清单

误用 后果
alg: none 攻击者把 header 改成 {"alg":"none"} 并去掉签名，服务端若信任 header 就完全绕过
算法混淆 服务端用 RS256 公钥验签，攻击者改成 HS256 并用公钥当 HMAC 密钥签名
不校验签名 直接解码 payload 就用
不校验 exp 令牌永不过期
不校验 iss / aud 别的系统的令牌能在你这儿用
kid 头部注入 kid 指向文件路径或 SQL 片段（../../../dev/null、kid' UNION SELECT ...）
敏感信息放 payload 等同于明文泄露
自己手写验签逻辑 边界条件写不对

⚠️ 永远显式指定 algorithms，绝不从 token header 里读。 这是防算法混淆的唯一要点。成熟库（PyJWT、jose、jsonwebtoken）默认就要求显式传算法，别自己绕过。

⚠️ 签名密钥必须足够强：HS256 的密钥要 ≥ 32 字节的随机值。用 secret、changeme、或者把 RSA 公钥当 HMAC 密钥，都会让签名形同虚设。

⚠️ kid 必须是服务端白名单内的标识符，不能直接当文件名或 SQL 参数用。密钥集合（JWKS）只从可信来源加载。

⚠️ JWT 不是会话的替代品，它是一份可被验证的声明。如果需要「登录后能踢下线」，就别用纯 JWT。

三、访问令牌与刷新令牌

令牌 有效期 存放 用途
访问令牌（access token） 短，5–15 分钟 内存 调业务接口
刷新令牌（refresh token） 长，几天到几周 HttpOnly Cookie（Web）或安全存储 换新的访问令牌

刷新令牌轮换 + 重用检测：

步骤 行为
每次刷新 签发新的 refresh token，旧的立即作废
检测到旧 token 被再次使用 整条令牌链全部作废，强制重新登录
为什么有效 如果旧 token 出现在攻击者手里，说明它已被泄露

⚠️ 轮换必须配合重用检测。只轮换不检测，等于换了个令牌号，攻击者照样能一直刷新。检测到重用时把该用户的所有会话全部踢掉，这是标准做法。

⚠️ 刷新令牌必须存在服务端（或至少可撤销）。纯无状态的刷新令牌等于一个长效访问令牌，一旦泄露就是长期沦陷。

⚠️ 访问令牌不要放 localStorage，尽量只放内存，页面刷新后靠刷新令牌重新获取。

四、OAuth 2.0：只用授权码 + PKCE

流程 状态 说明
授权码 + PKCE ✅ 唯一推荐 Web / SPA / 移动端全适用
授权码（无 PKCE） ❌ 不推荐 公共客户端可被截获授权码
隐式（Implicit） ❌ 已废弃 令牌直接出现在 URL fragment，会进历史记录 / Referer
密码模式（Password） ❌ 已废弃 客户端拿到用户密码，违背 OAuth 初衷
客户端凭据 ⚠️ 仅限服务间 没有用户参与，无授权概念

PKCE 解决的是授权码拦截：即使攻击者截获了 code，没有 code_verifier 也换不到令牌。

参数 要求
code_challenge_method **只用 S256**，plain 等于没保护
state 必须带，且校验，防 CSRF
redirect_uri 精确匹配注册值，不能前缀匹配
code 一次性，用完立即失效
code_verifier 43–128 字符，每次授权重新生成

⚠️ redirect_uri 前缀匹配是最常见也最致命的 OAuth 漏洞。注册了 https://app.example.com/cb 却做前缀匹配，攻击者用 https://app.example.com/cb.evil.com 或 https://app.example.com/cb?x= 就能把 code 引到自己的服务器。

⚠️ state 不能省。它防的是「攻击者用自己的账号登录后，把授权码塞给受害者」这类账号混淆攻击。

⚠️ OAuth 2.1 目前仍是 IETF 草案，但方向已经明确：PKCE 对所有客户端强制（不只公共客户端）、移除隐式流和密码模式、刷新令牌对公共客户端必须发送方约束或轮换。已发布的正式文件是 RFC 9700（OAuth 2.0 Security BCP）。

⚠️ OAuth 是授权协议，不是认证协议。要「用 Google 登录」得用 OIDC（在 OAuth 之上加 id_token 和 /userinfo），不要拿 access token 当身份凭证用。

五、密码存储

算法 推荐度 参数
Argon2id ✅ 首选 m=19456 (19 MiB), t=2, p=1（最低配置）
scrypt ✅ 次选 按内存/CPU 权衡调参
bcrypt ⚠️ 仅遗留系统 work factor ≥ 10，且密码长度限制 72 字节
PBKDF2-HMAC-SHA256 ⚠️ 需 FIPS 时 600,000 次迭代
PBKDF2-HMAC-SHA512 ⚠️ 需 FIPS 时 220,000 次迭代
MD5 / SHA-1 / SHA-256 裸哈希 ❌ 禁止 无盐、可彩虹表、GPU 每秒几十亿次

Argon2id 的其他等效配置（CPU 与内存权衡）：

内存 m 迭代 t 并行 p
47104 (46 MiB) 1 1
19456 (19 MiB) 2 1
12288 (12 MiB) 3 1
9216 (9 MiB) 4 1
7168 (7 MiB) 5 1

⚠️ 每个密码必须有独立的随机盐。盐不需要保密，但要唯一 —— 防彩虹表，防「相同密码哈希相同」被一眼看出。

⚠️ bcrypt 有 72 字节输入上限，超出部分被静默截断。所以要么强制密码长度上限，要么换 Argon2id。

⚠️ 不要给 bcrypt 做预哈希（bcrypt(sha512(pwd))）。这会导致密码脱壳（password shucking）：攻击者拿到内部 SHA-512 哈希就能直接破解，绕过 bcrypt 的成本。如果必须预哈希，用 bcrypt(base64(hmac_sha384(pwd, pepper)))，且 pepper 不存数据库。

⚠️ 哈希算法要可升级。存哈希时同时存算法标识和参数（Argon2id 的编码格式自带），登录成功时用 check_needs_rehash 判断是否需要用新参数重算。

⚠️ 绝不要用可逆加密存密码。密码只需要「验证」，不需要「还原」。

六、越权：水平与垂直

类型 含义 例子
水平越权（IDOR / BOLA） 同权限用户之间互相访问数据 A 改 URL 里的订单 id，看到 B 的订单
垂直越权 低权限用户执行高权限操作 普通用户调 /admin/deleteUser

⚠️ 每个涉及具体对象的接口都必须校验归属。这是 OWASP API Security Top 10 里长期排第一的 BOLA（Broken Object Level Authorization）。认证中间件管不到这个 —— 它只知道「你登录了」，不知道「这个订单是不是你的」。

⚠️ **返回 404 而不是 403**。403 等于告诉攻击者「这个 id 存在，只是不属于你」，可以据此枚举有效 id。

⚠️ 权限校验必须在服务端做。前端隐藏按钮、路由守卫只是体验优化，改个请求就绕过了。

⚠️ **不要用客户端传来的 user_id / role / tenant_id**。一律从服务端会话 / 令牌里取。这是水平越权最常见的入口。

⚠️ 批量接口也要逐个校验。DELETE /orders?ids=1,2,3 里混进一个别人的 id，不能整个放行。

⚠️ 权限校验要在数据访问层统一实现（ORM 全局 scope、Repository 层强制过滤），不要指望每个开发者在每个 handler 里手写一遍。

七、密钥与配置管理

反模式 风险
密钥硬编码在源码里 提交进 git，历史记录永远留着
.env 提交进仓库 同上，且常被 .gitignore 漏掉
密钥写进 Docker 镜像层 docker history 能翻出来
密钥进 CI 日志 构建日志被谁都能看
同一个密钥用三年 泄露后影响面无法界定
前后端共用同一个密钥 前端密钥等同公开
密钥放前端代码 / 环境变量前缀 VITE_ / NEXT_PUBLIC_ 会打进 bundle，等同公开

⚠️ 一旦密钥进了 git 历史，改掉文件是不够的 —— 必须轮换密钥。因为历史提交、fork、CI 缓存里都还有。git filter-repo 只能清理你自己的仓库，清不掉别人的 clone。

⚠️ 任何带 PUBLIC_ / VITE_ / NEXT_PUBLIC_ 前缀的变量都会被打进前端产物，用户 F12 就能看到。API 密钥、私钥绝对不能放这里。

轮换策略：

密钥类型 建议周期 轮换方式
数据库密码 90 天 双密码期，滚动切换
JWT 签名密钥 90 天 JWKS 多密钥并存，旧密钥只验不签
第三方 API Key 180 天 双 Key 并行，观察流量归零后停用
加密密钥（KMS） 按合规要求 保留旧版本用于解密历史数据
会话密钥 随会话 ——

⚠️ 轮换必须支持「新旧并存」的过渡期。直接换 JWT 密钥会让所有在线用户瞬间掉线。正确做法是 JWKS 里同时发布新旧公钥，新令牌用新密钥签，旧令牌用旧密钥验，等最大有效期过了再摘掉旧密钥。

⚠️ 优先用短时效凭据：云上给 Pod 挂 IAM Role 而不是发 AK/SK；数据库用 IAM 认证而不是静态密码。没有长期密钥，就没有轮换问题。

推荐做法：

方案 适用
云厂商密钥管理服务（KMS / Secrets Manager） 云环境首选
HashiCorp Vault 自建 / 多云
K8s Secret + External Secrets Operator 容器环境
环境变量注入（不落盘、不进镜像） 通用
密封文件（SOPS / sealed-secrets） GitOps

⚠️ 开启密钥扫描（GitHub Secret Scanning、gitleaks、trufflehog），在 CI 里跑 pre-commit 钩子。发现泄露的窗口期越短，损失越小。

⚠️ 加密密钥和密文要分开存（信封加密）。密钥放在 KMS，数据里只存密文和密钥版本号。这样轮换只需换密钥，不用重写全部数据。

八、登录防护

防护 做法 说明
失败限流 按 IP + 账号 双维度 只按 IP 挡不住分布式撞库
递增延迟 失败次数越多延迟越长 比硬锁定温和
账号锁定 N 次失败后临时锁定 按账号锁定可被用来 DoS 他人
验证码 达到阈值后出现 别一上来就要求
通用错误信息 「用户名或密码错误」 不区分「用户不存在」和「密码错」
时序安全比较 secrets.compare_digest / crypto.timingSafeEqual 防通过响应时间枚举用户
用户不存在也走一次哈希 保持响应时间一致 同上
MFA TOTP / WebAuthn 管理员账号强制
登录日志 记录 IP、UA、时间、结果 异常登录告警
密码强度 长度优先（≥ 12），不做复杂字符要求 复杂度要求反而导致弱密码复用

⚠️ 密码比较必须用常量时间函数。== 会在第一个不同字节处返回，攻击者可以逐字节爆破。

⚠️ 按账号锁定是双刃剑：攻击者可以故意用错误密码锁定别人的账号。用递增延迟 + IP 限流 + 验证码组合，而不是硬锁定。

⚠️ 密码重置流程比登录更容易被攻破：重置令牌要一次性、短有效期（15–30 分钟）、存哈希不存明文，且不能通过「回答密保问题」来重置。

⚠️ MFA 要防绕过：验证通过后必须换发新会话（会话固定），且 MFA 校验状态不能靠客户端传的字段。

⚠️ HttpOnly + Secure + SameSite 是会话 Cookie 的底线，会话 id 必须登录成功后重新生成（防会话固定）。

常见坑清单

  • 把 JWT 放 localStorage，一处 XSS 就全丢
  • 用 JWT 又需要「踢下线」，靠等过期糊弄
  • JWT payload 里放敏感信息（base64 不是加密）
  • 接受 alg: none，或从 token header 里读算法
  • 服务端用 RS256 验签却不固定算法，被算法混淆攻击
  • HMAC 密钥用了弱口令 / 复用 RSA 公钥
  • 不校验 exp / iss / aud
  • kid 直接当文件名或 SQL 参数
  • 自己手写 JWT 验签逻辑
  • 刷新令牌不做轮换，或轮换但无重用检测
  • 刷新令牌不可撤销（纯无状态）
  • 用隐式流 / 密码模式
  • PKCE 用 code_challenge_method=plain
  • 不带 state 或不校验 state
  • redirect_uri 用前缀匹配而不是精确匹配
  • 拿 OAuth access token 当身份凭证（该用 OIDC 的 id_token）
  • 用 MD5 / SHA-1 / 裸 SHA-256 存密码
  • 所有用户共用盐，或不加盐
  • bcrypt 密码超过 72 字节被静默截断
  • 给 bcrypt 做预哈希导致密码脱壳
  • 哈希参数写死，算法升级后无法平滑迁移
  • 查询对象时不校验归属（BOLA / IDOR）
  • 越权时返回 403 而不是 404，可被枚举
  • 信任客户端传来的 user_id / role / tenant_id
  • 只在前端做权限控制
  • 批量接口不逐个校验对象归属
  • 密钥硬编码 / .env 提交进仓库
  • 密钥进了 git 历史，只删文件不轮换
  • 密钥放在 VITE_ / NEXT_PUBLIC_ 前缀的环境变量里
  • 轮换 JWT 密钥不做双密钥过渡，全员掉线
  • 登录失败提示区分「用户不存在」和「密码错误」
  • 密码用 == 比较，存在时序侧信道
  • 靠账号锁定防爆破，被用来 DoS 他人
  • 密码重置令牌可重复使用或有效期过长
  • 登录成功后不重新生成会话 id（会话固定）
  • 会话 Cookie 缺 HttpOnly / Secure / SameSite
  • 管理员账号不强制 MFA
