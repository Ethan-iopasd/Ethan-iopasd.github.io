开场：一次请求有三个独立的缓存层，出问题时先定位是哪一层

浏览器 DNS 缓存 → 本地 DNS / 运营商 DNS → 权威 DNS，再往上是 CDN 边缘节点 → 回源到源站。绝大多数「改了配置没生效」都是某一层缓存没到 TTL。

一、DNS 解析链路

阶段 类型 说明
递归查询 Recursive 客户端只问一次，本地 DNS 负责跑完全程
迭代查询 Iterative 本地 DNS 逐级问根 / TLD / 权威，每级只给下一跳

⚠️ dig 的 ANSWER SECTION 里的 TTL 是「剩余时间」，不是配置值。 第一次查到可能是 300，几秒后再查变成 297。想看配置值就用 dig +noall +answer 连续观察，或者去权威 NS 上查（dig @ns1.example.com example.com 拿到的才是原值）。

⚠️ nslookup 会读 /etc/hosts 和系统解析器，dig 默认直接走 DNS。 两者结果不一致时，先怀疑 hosts 文件或 resolv.conf。排查线上问题用 dig，更接近真实。

二、记录类型与 TTL

类型 用途 注意
A 域名 → IPv4 最常用
AAAA 域名 → IPv6 客户端双栈时会优先 AAAA，配错会连不上
CNAME 域名 → 另一个域名 CNAME 不能和其他记录共存（MX、TXT 也不行）
MX 邮件路由 必须指向 A 记录，不能指向 CNAME
TXT 任意文本 SPF、DKIM、域名验证
NS 权威服务器 委派关系
SOA 区域元信息 含 minimum 字段，旧式实现里会影响负缓存 TTL
CAA 允许哪些 CA 签发证书 不配就任何 CA 都能签

TTL 怎么设

场景 TTL 建议 理由
常规域名 300–600 秒 兼顾切换速度和查询量
切换前（迁移 IP / 换 CDN） 提前改成 60 秒，等旧 TTL 过期再切 否则切换后旧记录还会被缓存几小时
CDN 接入的 CNAME 600 秒以上 CDN 内部靠自己的调度，不需要频繁变
极少变动的记录 3600 秒以上 减少查询

⚠️ 改 DNS 一定要「先降 TTL，再改记录」。 直接改记录的话，旧 TTL 还没过期，部分用户仍会解析到旧 IP，这段时间是双份流量。这是最常见的线上切换事故。

⚠️ TTL 只是「最大缓存时间」不是保证。 运营商 DNS 可能无视 TTL 强制缓存（俗称 DNS 劫持式缓存），也可能对 NXDOMAIN 做负缓存（时长由 SOA 的 minimum 决定，常见 300–3600 秒）。新加的域名「查不到」不一定是没配，可能只是负缓存没到期。

三、DNS 污染与加密

方案 RFC 端口 特点
明文 DNS RFC 1035 53/UDP、53/TCP 可被中间人篡改、可被投毒
DoT（DNS over TLS） RFC 7858 853/TCP 全程加密，端口特征明显，易被阻断
DoH（DNS over HTTPS） RFC 8484 443/TCP 混在 HTTPS 流量里，难识别；缺点是绕过了本地 DNS 策略

⚠️ DNS 污染的特征是「返回了 IP，但明显不对」（比如返回 0.0.0.0、127.0.0.1，或境外某 IP）。这时 dig @8.8.8.8 和本地 DNS 结果不一致就是证据。注意：DoH/DoT 只加密最后一跳，运营商仍能看到 SNI（除非用 ECH）。

⚠️ curl 解析失败但 ping 通 —— 常见原因是 ping 走的是系统解析器（可能读了 /etc/hosts），而 curl 用了不同的解析路径或代理。排查时统一用 getent hosts <域名> 看系统真实解析结果。

四、CDN：回源与缓存命中

响应头 含义
X-Cache: HIT / MISS 非标准，各家 CDN 自己定义。HIT = 边缘命中，MISS = 回源了
Age: 1200 该响应在 CDN 缓存里已存在 1200 秒（RFC 9111）
Via: 1.1 varnish 经过的代理链（RFC 9110），能看出经过了哪些中间层
X-Cache-Lookup 腾讯云 CDN 特有，区分多级缓存的命中层级
Cache-Control 决定能不能缓存、能缓多久 —— CDN 听它的
X-Served-By / X-Cache-Hits Fastly / Varnish 系，HIT 次数

⚠️ Age 是判断「到底缓存了多久」最可靠的指标。 Age: 0 或没有 Age 基本可以认定是 MISS（刚回源）。Age 接近 max-age 说明即将过期，下一波请求会集中回源 —— 这是缓存雪崩的预警信号。

刷新与预热

操作 作用 代价
刷新（Purge） 主动删除边缘缓存，下次请求回源 大量刷新会造成回源洪峰
预热（Prefetch） 主动把内容拉到边缘，不等用户请求 需要提前知道 URL 列表
URL 刷新 vs 目录刷新 目录刷新范围大、更慢、更贵 通常有配额限制
版本化 URL app.a1b2c3.js，发版换文件名 最推荐，无需刷新

⚠️ 别用「刷新」当发版手段。 刷新有延迟、有配额、可能失败，而且边缘节点众多时不是所有节点都立刻生效。正确做法是 HTML 用 no-cache + 静态资源带内容哈希，靠 URL 变化自然生效，永远不需要刷 CDN。

⚠️ CDN 缓存的是「响应」，不只是「文件」。 如果源站对不同请求头（Accept-Encoding、Cookie、Origin）返回不同内容，而没配 Vary，CDN 会把一份响应发给所有人 —— 典型症状是有人看到了别人的内容，或者 CORS 时好时坏。

五、抓包与排查工具选型

工具 层次 适用 不适用
curl -v 应用层 看请求头、响应头、TLS 握手、重定向链路 看包级别的时序
curl --resolve —— 绕过 DNS 直连指定 IP，验证是不是解析问题 ——
curl -w 应用层 分阶段耗时（DNS / TCP / TLS / TTFB） ——
traceroute 网络层 逐跳路径，看在哪一跳断 中间设备不响应 ICMP 时会显示 *
mtr 网络层 traceroute + 持续统计丢包率，判断是路径问题还是单点抖动 需要 root（或用 ICMP 模式）
tcpdump 链路/网络层 服务端侧抓包，没有 GUI 也能用 需要 root；解读门槛高
Wireshark 链路层 本地抓包 + 图形化协议解析，看 TLS/HTTP2 细节 生产服务器上不合适
ss 内核 连接状态、队列、cwnd 看不到内容

⚠️ traceroute 显示 * 不代表丢包 —— 很多路由器默认不回 ICMP TTL 超时。只有连续多跳都是 * 才说明真的断了，而且要用 mtr 看丢包率是否持续，单次抖动没意义。

⚠️ tcpdump 抓不到包的最常见原因是抓错了网卡（容器环境尤其）。用 -i any 先确认流量走哪，再换具体网卡。K8s 里要抓 Pod 的包，得进 Pod 的 network namespace。

六、「本地能访问，线上不行」的排查顺序

按这个顺序走，每一步都能排除一整类原因：

# 步骤 命令 结论
1 域名解析到哪 dig +short <域名> / getent hosts <域名> 解析对不对、是不是打到了内网 IP
2 端口通不通 nc -zv <ip> <port> / telnet TCP 层是否可达
3 TLS 握没握上 curl -v 看证书链 证书域名/有效期/中间证书是否缺
4 响应头对不对 curl -sI 是不是 CDN 返回的（X-Cache、Via）
5 绕过 DNS 直连源站 curl --resolve 区分 CDN 问题还是源站问题
6 绕过 CDN 直连源站 IP curl -H 'Host: x' http://<源站IP>/ 源站本身是否正常
7 从服务端侧抓包 tcpdump 请求到没到服务端
8 看应用日志 —— 请求到了应用但报错了

⚠️ 第 5 步和第 6 步是最关键的分水岭。 「本地能访问」通常是因为本地命中了不同的 CDN 节点、或本地有 hosts、或本地走了不同的出口 IP（被 WAF 放行）。直连源站 IP 一试，立刻知道是 CDN 的问题还是应用的问题。

⚠️ WAF 和 CDN 是按客户端 IP 判断的。 「本地能访问」很可能是因为你的 IP 在白名单里。让用户提供 curl -v 的完整输出，比自己猜快十倍。

常见坑清单

  • 改 DNS 记录前没先把 TTL 降下来，切换期间部分用户解析到旧 IP
  • 把 dig 显示的 TTL 当成配置值（那是剩余时间）
  • 新域名「解析不出来」就去改配置（可能只是负缓存没到期）
  • CNAME 和 MX / TXT 配在同一条记录上（规范不允许共存）
  • 只配了 A 没配 AAAA，或反过来，双栈客户端行为异常
  • 把 CDN 刷新当发版手段，边缘节点没全生效就以为发布失败
  • 源站按请求头返回不同内容却不写 Vary，CDN 串内容
  • 只看 X-Cache: HIT 就以为没问题（它是非标准头，各家定义不同，Age 更可靠）
  • traceroute 出现 * 就断定网络断了（多数是路由器不回 ICMP）
  • tcpdump 抓不到包却怀疑没流量（多半抓错了网卡）
  • 在容器里抓包没进 network namespace，看到的全是宿主机流量
  • 「本地能访问」就以为线上也没问题（本地 IP 可能在白名单 / 命中了不同节点）
  • 排查时不在 curl 里加 --resolve，无法区分 CDN 与源站问题
  • 用 nslookup 排查线上问题（它会读 hosts，结果不可信）
