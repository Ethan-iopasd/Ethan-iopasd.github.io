三 镜像瘦身与构建优化 本篇

开场：瘦身只有三招

  1. 少装东西 —— 换基础镜像、只拷产物（多阶段构建）
  2. 删干净 —— 同一层里删掉包管理器缓存
  3. 别重复构建 —— BuildKit 缓存挂载 + 外部缓存导出

体积和构建速度是两件事，但都归到同一个根因：层里留下了什么。

一、先量，再砍

docker history 输出的 SIZE 是每一层的增量，CREATED BY 是那一层的指令：

现象 含义
SIZE 为 0B 纯元数据层（ENV / CMD / LABEL / WORKDIR），不占体积
某层几百 MB 且 CREATED BY 是 apt-get install 装完没清缓存，或者没在同一个 RUN 里清
最后一层特别大且是 COPY 把构建产物以外的东西（源码、node_modules、.git）也拷进去了

dive 的价值在于它会同时列出每一层新增/删除了哪些文件。一个常见结论是：某层删掉的 500MB，因为写在下一层，实际上仍然占体积。

⚠️ 层的删除不是真的删除。 RUN apt-get install x && rm -rf /var/lib/apt/lists/* 写在同一个 RUN 里才算删掉；分成两条 RUN，前一条的数据会固化在那一层，永远带着走。

二、基础镜像选型

基础镜像 体积量级 适用场景 代价
scratch 0 静态编译的 Go / Rust 二进制 无 shell、无 libc、无 CA 证书，docker exec 进不去
distroless 几 MB ~ 几十 MB 需要 glibc / CA 证书但不需要 shell 不能 sh，调试靠临时换镜像
alpine 几 MB 需要 shell 和包管理 musl libc，glibc 预编译产物跑不了
debian:*-slim 几十 MB 需要 apt、需要 glibc 比 alpine 大
ubuntu 几十 MB 需要 glibc 且依赖 ubuntu 生态 同上

⚠️ alpine 不是万能瘦身药。 它是 musl libc，很多预编译 wheel / Node 原生扩展（glibc 构建的）在上面直接报 not found 或 symbol not found。Python 场景换 alpine 常常要从源码编译，构建时间和镜像体积反而都涨。

⚠️ scratch 镜像没有 /etc/ssl/certs。 里面发起 HTTPS 请求会报证书错误。需要从 builder 阶段把 ca-certificates.crt 一起拷进去。

三、多阶段构建：只拷产物

关键点：

写法 作用
FROM ... AS build 命名阶段，最终镜像不会包含它
COPY --from=build /out/app /app 只拷产物，源码、SDK、模块缓存全部留在 build 阶段
--target build 构建时只跑到某个阶段，用来调试
-ldflags="-s -w"（Go） 去掉符号表和调试信息，二进制小一截

对比一下「多阶段」和「单阶段」的差别：

单阶段 多阶段
最终镜像包含 源码 + SDK + 依赖缓存 + 产物 只有产物（+ 显式 COPY 的文件）
典型体积 800MB ~ 1.5GB 10MB ~ 50MB
构建缓存 和产物混在一起 构建阶段的缓存独立，可长期保留

⚠️ COPY . . 放在 RUN go mod download 之后。反过来写，改一行源码就会让依赖下载那层缓存失效，每次构建都重新拉依赖。

四、层缓存 vs 缓存挂载

这是两个不同的东西，经常被混为一谈：

层缓存（layer cache） RUN --mount=type=cache
匹配方式 指令文本 + 输入文件精确匹配 按 id 挂载持久目录，内容不参与层哈希
缓存失效 指令变一个字就整层重跑 目录内容变化不影响该层缓存
存哪 构建缓存里，跟着镜像层走 BuildKit 管理的独立缓存卷
典型用途 COPY + RUN npm ci 分层 包管理器下载目录（pip / npm / go mod / apt）

⚠️ 缓存挂载里的内容不会进镜像。 它只在构建期间可见。所以别指望 --mount=type=cache,target=/app/node_modules 之后 node_modules 能出现在运行镜像里 —— 需要用 npm ci 的正常安装再落到层里，或者构建完 cp 出来。

⚠️ 多个构建并行写同一个 apt 缓存会冲突，加 sharing=locked 串行化。

五、BuildKit：并行与缓存导出

BuildKit 是现在 docker build 的默认后端（docker buildx 是其 CLI）。和旧构建器比：

旧构建器 BuildKit
多阶段执行 基本串行 无依赖的阶段并行跑
未使用的阶段 仍然执行 自动跳过
缓存挂载 不支持 RUN --mount=type=cache
缓存导出 不支持 --cache-to / --cache-from
构建密钥 只能 build-arg --mount=type=secret
输出格式 只能进 docker images -o type=local/docker/registry/oci

CI 上最有用的是把构建缓存导出到外部，下次构建直接拉回来：

mode 含义
min（默认） 只导出最终镜像用到的层的缓存
max 导出所有中间阶段的缓存，多阶段构建提速明显，体积也大
缓存后端 说明
registry 推到镜像仓库，跨机器共享
local 落到本地目录
gha GitHub Actions 的缓存服务，CI 里最省事
s3 / azblob 对象存储
inline 只支持 --cache-to，把缓存元数据塞进镜像本身，适合无法配置外部缓存时

⚠️ inline 缓存的 mode 只能是 min，多阶段构建的中间层缓存它带不走。

⚠️ --cache-from 指向的缓存镜像必须已经存在，第一次构建会直接忽略（不报错）。CI 里第一次跑必然是冷构建。

六、--squash 的取舍

--squash 会把所有层压成一层。它的现状需要说清楚：

事实 说明
它属于旧版构建器的实验性开关 需要 daemon 开 experimental: true
docker buildx build 没有这个参数 官方 buildx 参考里不存在
BuildKit 下没有等价物 没有「压成一层」的官方开关

所以现在想达到「少几层」，正确路径是多阶段构建 + scratch/distroless，而不是找 squash。

即使真能压成一层，也不建议：

压层的收益 压层的代价
少几层，镜像略小（省的是层元数据，不是内容） 层缓存全废，每次构建从头来
隐藏历史指令（曾被当成”安全”手段） 拉取镜像时无法复用已下载的层，只能整块下
— 用 docker history 排查体积构成的能力也没了

⚠️ 「压成一层能减小体积」是个误解。真正的体积是文件内容本身，层只是索引。压层省下的通常是个位数 MB，换来的是构建和拉取双双变慢。

七、把包管理器缓存清干净

不清理时，缓存和依赖一起被固化进层。

包管理器 缓存位置 处理方式
apt /var/lib/apt/lists 同一 RUN 内 rm -rf，或 cache 挂载
pip ~/.cache/pip --no-cache-dir，或 cache 挂载
npm ~/.npm cache 挂载（比 --no-cache-dir 更快）
yarn ~/.cache/yarn cache 挂载
go $GOPATH/pkg/mod cache 挂载
dnf/yum /var/cache/dnf 同一 RUN 内 clean all

⚠️ apt-get update 和 apt-get install 也要在同一条 RUN 里。分开写会让 update 的索引层被缓存，过几周构建时用的还是旧索引，装到过期版本甚至装不上。

八、.dockerignore 的实测影响

.dockerignore 的作用是在把构建上下文发给 daemon 之前就排除掉文件。它同时影响两件事：

  1. 构建上下文传输量（每次构建都要传）
  2. COPY . . 拷进去的东西（直接影响镜像体积）
不加 .dockerignore 加了之后
.git 全量传给 daemon（大仓库几百 MB） 上下文只有几 MB
COPY . . 把 node_modules 拷进镜像 只拷源码，依赖在镜像里重新装
.env 里的密钥被拷进镜像，永久留在层里 不进去
改一次 .git 里的文件就可能让 COPY 层缓存失效 无影响

常见坑清单

  • apt-get update 和 apt-get install 分成两条 RUN，索引层被缓存成过期数据
  • rm -rf /var/lib/apt/lists/* 写在 install 的下一层，体积一点没省
  • 用 alpine 换掉 glibc 镜像，结果预编译依赖跑不起来，改成从源码编译
  • scratch 镜像里没有 CA 证书，HTTPS 请求全部失败
  • COPY . . 放在依赖安装之前，改一行代码就重装全部依赖
  • 没有 .dockerignore，.git / node_modules / .env 全进镜像
  • 以为 --mount=type=cache 挂的目录会留在镜像里（它不会）
  • --cache-from 指向的缓存镜像还不存在，第一次 CI 构建以为配置写错了
  • --cache-to 用 inline 却期待多阶段中间层被缓存
  • 用 --squash 压层，体积没降多少，层缓存全废
