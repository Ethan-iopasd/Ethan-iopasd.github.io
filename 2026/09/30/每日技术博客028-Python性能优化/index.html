五 性能剖析与优化 本篇

开场：没有 profile 的优化都是猜

性能优化的顺序是固定的：测 → 找热点 → 改一处 → 再测。跳过第一步的优化，十有八九改在了不重要的地方。

现象 大概率原因
单请求慢，且随数据量线性变差 算法复杂度选错了（list 做查找 / 队列）
单请求慢，数据量无关 循环里的重复计算、属性查找、未预编译正则
内存持续上涨不回落 无界缓存、全局注册表、异常对象持有 traceback
多请求下整体吞吐上不去 GIL / 连接池 / 线程池上限

一、工具选型：谁测什么

工具 粒度 适合 侵入性
timeit 代码片段 微基准，比两种写法谁快 要写代码
cProfile 函数调用 定位热点函数 低，-m 即可
pstats 函数调用 读 cProfile 的结果 无
py-spy 函数（采样） 线上进程，不改代码、可 attach 无
line_profiler 代码行 函数内部哪一行慢 要加装饰器
tracemalloc 分配点 内存是谁分配的 低
objgraph 对象引用 谁在引用这些对象 低
perf / pyperf 系统 + 解释器 含 C 扩展、系统调用的完整画像 无

⚠️ 别用 time.time() 包一圈就下结论。 单次测量的噪声通常比你要测的差异还大。要重复、要取最小值、要控制变量。

二、cProfile：最常用的第一步

输出各列的含义：

列 含义
ncalls 调用次数，A/B 形式表示 A 次调用里 B 次是递归
tottime 函数自身耗时，不含子函数
percall tottime / ncalls
cumtime 含子函数的累计耗时
cumtime percall cumtime / ncalls

⚠️ tottime 高 = 这个函数本身慢；cumtime 高但 tottime 低 = 它只是调用了很多慢东西。 找优化点看 tottime，看调用链看 cumtime。
⚠️ cProfile 对每次函数调用都插桩，开销很大。它用来找热点，不用来测绝对耗时 —— 关掉 profile 后实际可能快好几倍。
⚠️ cProfile 看不到 C 扩展内部的耗时归属（比如 numpy 的 dot 只算一次调用），也不会记录行号。那种场景用 py-spy。

三、py-spy：线上不改代码

采样式剖析器的特点：

维度 cProfile py-spy
原理 逐调用插桩（确定性） 定时采样（统计性）
开销 高 低
需要改代码 / 重启 是 否
能 attach 生产进程 否 ✅
能看到 C 扩展内部 否 部分（采样在 C 栈上）
可能漏掉调用次数极少的函数 不会 会

⚠️ 采样频率有限，只跑几十毫秒的函数可能一次都采不到。排查「偶发慢」要么拉长采样时间，要么回到 cProfile。

四、微基准：timeit

⚠️ 用 repeat() 取 min 而不是取平均。平均会被 GC、调度抖动拉高；最小值更接近真实下界。
⚠️ timeit 默认用 number 次循环的总时间，不是单次。对比两种写法时 number 必须一致。
⚠️ 别在 setup 里做昂贵的一次性工作（那样会稀释掉被测代码的差异），也别让被测代码产生副作用累积（比如往同一个 list 里无限 append）。

五、常见慢点

慢点 症状 改法
循环里重复属性查找 result.append(x) 在百万次循环里 提到循环外：append = result.append
循环里重复计算 len(s) / s.upper() 写在循环条件里 提到循环外
字符串 += 拼接 拼接次数越多越慢 收集进 list，最后 ''.join()
正则未预编译 每轮都 re.match(pattern, s) 模块级 RE = re.compile(...)，用 RE.match(s)
用 list 做成员判断 x in big_list 换 set / dict
用 list 做队列 pop(0) 头删 collections.deque.popleft()
用 list 找 top-K 每次 sorted() 全量排序 heapq.nlargest(k, it)
循环里累加字符串 / 多次 dict 查键 反复 hash 同一 key 局部变量缓存 d.get，或 defaultdict
手写计数 / 分组 for + if 手工累加 collections.Counter / defaultdict(list)
逐行读写文件 百万行 批量读 + 生成器，见第六节

数据结构的时间复杂度（平均情况）：

操作 list dict / set deque heapq
按下标访问 O(1) — O(n) —
按 key / 成员查找 O(n) O(1) O(n) O(n)
尾部追加 O(1) 摊还 O(1) 摊还 O(1) O(log n)
头部插入 / 删除 O(n) — O(1) —
中间插入 / 删除 O(n) — O(n) —
取最小 / 最大 O(n) O(n) O(n) O(1)

⚠️ 最常见的复杂度事故：在一个大 list 里做成员判断，或在循环里 pop(0)。 前者 O(n²)，后者 O(n²)。数据量小的时候完全看不出来。

六、生成器与惰性求值

itertools 里常用的几个：

工具 用途
islice(it, n) 只取前 n 个，不物化全部
chain(a, b) 顺序拼接多个可迭代对象
groupby(it, key) 分组（要求输入已按 key 排序）
batched(it, n) 按 n 个一批切分（3.12+）
count() / cycle() / repeat() 无限序列

⚠️ 生成器只能遍历一次。 遍历完再 list(gen) 得到空列表 —— 这个 bug 很常见。
⚠️ 生成器不是万能加速器。如果最终还是要全部物化，或者数据量本来就小，生成器的额外开销反而更慢。它的价值在内存，不在速度。
⚠️ 生成器里的异常只在迭代到那一步时才抛出，堆栈信息会变得难读。调试时先 list() 出来。

七、缓存

选择 场景
@cache 参数空间有限且可枚举（枚举值、固定配置、小整数）
@lru_cache(maxsize=N) 参数空间大或不可控，长驻服务默认选这个
自己写 dict 缓存 需要按 key 主动失效，或需要 TTL
Redis / Memcached 跨进程、跨实例共享

⚠️ @cache 在长驻服务里就是内存泄漏。 参数是用户 ID、URL、时间戳这类高基数时，缓存会无限增长。用 lru_cache(maxsize=...)。
⚠️ 被缓存的函数参数必须可哈希，且不能依赖会变的外部状态（文件内容、数据库、时间、随机数）。改了外部状态必须 cache_clear()。
⚠️ 缓存装饰器加在方法上时，self 会成为 key 的一部分，导致实例无法被回收。要缓存实例方法，把逻辑抽成模块级函数，或自己维护 WeakKeyDictionary。

八、向量化与 C 扩展

手段 加速量级 代价
numpy / pandas 向量化 数十倍 要重写成数组思维，注意内存放大
标准库 C 实现的函数（sum、min、sorted、str.join） 数倍 无
bisect / heapq / array / memoryview 数倍 数据结构受限
cython / mypyc 数倍到数十倍 加构建步骤，类型要标注
cffi / pybind11 / C 扩展 数十倍以上 要写 C/C++，维护成本高

⚠️ 向量化的瓶颈会转移到内存。 data * data 会新分配一个同尺寸数组。对超大数组要分批处理，或用 out= 参数复用缓冲区。
⚠️ 写 C 扩展前先确认瓶颈真在 Python 层。如果热点其实是 I/O 或某个库调用，写 C 扩展毫无意义。

九、内存排查

工具 回答的问题
tracemalloc 内存是哪一行分配的、增长了多少
sys.getsizeof 单个对象占多少字节（浅层）
objgraph 这类对象有多少个、被谁引用
gc.get_objects() / gc.get_referrers() 底层引用关系
resource.getrusage / psutil 进程整体 RSS，判断是否真在涨

常见的内存泄漏来源：

来源 说明
无界缓存 / 全局 dict 注册表 见第七节
异常对象持有 traceback traceback 会链住整条调用栈的帧和局部变量。存 exc_info 到全局前先 traceback.clear_frames()
logging handler 重复添加 每次初始化都 addHandler，handler 累积
闭包捕获大对象 回调注册后不注销，闭包一直持有
循环引用 + 有 __del__ 现代 Python 的 GC 能处理，但对象存活时间会变长
未 close() 的文件 / 连接 / 会话 走 with 或显式关闭

⚠️ 不要用 sys.getsizeof 判断一个复杂对象的真实内存占用。 它不含容器里引用的其他对象（getsizeof(list_of_1000_dicts) 只返回 list 本身的大小）。
⚠️ 内存涨不等于泄漏。先看稳态：跑完多轮 GC 后是否回落。持续单调上涨才是泄漏。

常见坑清单

  • 不 profile 直接凭感觉改代码
  • 用 time.time() 单次测量下结论
  • timeit 对比时两边 number 不一致
  • 把 cProfile 的耗时当成生产环境的真实耗时
  • 只看 cumtime 找热点，不看 tottime
  • 大 list 里做 in 判断，或在循环里 pop(0)
  • 循环里 str += 拼接
  • 正则写在循环里没预编译
  • 长驻服务上用无界的 @cache
  • 缓存函数依赖了会变的外部状态，却不 cache_clear()
  • 生成器被遍历两次（第二次是空的）
  • 用 sys.getsizeof 估算容器真实内存
