开场：TCP 的复杂度全在「连接」这两个字上

IP 层只负责把包丢出去，不保证到达、不保证顺序、不保证不重复。TCP 在这之上补了序号、确认、重传、窗口、拥塞控制五件事，把不可靠的通道伪装成一条可靠的字节流。连接状态机、TIME_WAIT、CLOSE_WAIT、粘包，都是这五件事的副作用。

一、分层与职责

层 数据单位 寻址依据 典型协议 典型设备
应用层 消息 —— HTTP / DNS / SSH / gRPC ——
传输层 段 Segment 端口 TCP / UDP / QUIC 四层负载均衡
网络层 包 Packet IP IP / ICMP / ARP 路由器、三层交换机
链路层 帧 Frame MAC Ethernet / Wi-Fi 交换机、网卡

⚠️ ARP 严格说工作在链路层与网络层之间（它把 IP 解析成 MAC，但不封装 IP 头）。面试里说「ARP 是网络层」或「是链路层」都能自圆其说，说「它跨两层」最稳。

⚠️ 四层负载均衡只看 IP + 端口，不改内容（LVS、云 SLB 的 TCP 模式）；七层负载均衡要解析 HTTP（Nginx、ALB），能按 Host / Path / Header 路由，也能改 header。选型看是否需要按路径分流。

二、三次握手

三次握手的核心作用有三个：

  1. 双方各自确认对方的收发能力正常（两个方向各需要一次 SYN 和一次 ACK，合并成三步）。
  2. 交换初始序号 ISN（RFC 9293 要求 ISN 与时间相关，不能固定，防旧连接报文串入）。
  3. 协商选项：MSS、窗口缩放因子（Window Scale）、SACK permitted、时间戳 —— 这些只能在 SYN 里协商，连接建立后无法追加。

为什么不是两次

视角 两次握手的问题
服务端 收到一个历史延迟的旧 SYN 就立刻分配资源并进入 ESTABLISHED，但这个「连接」客户端根本不认，资源白占（半开连接 / half-open）
客户端 无法区分服务端回的 SYN-ACK 是针对本次 SYN，还是针对上一个早已超时重发的旧 SYN
序号 客户端没机会告诉服务端「我确认了你的 ISN」，服务端无法确认自己的发送方向可用

⚠️ 教科书上说的「历史重复连接」就是第一种：网络里滞留的旧 SYN 到达服务端，两次握手时服务端会直接建立连接并等待永远不会来的数据，这类半开连接可以堆到耗尽服务端的连接表（配合伪造源 IP 就是 SYN Flood）。

⚠️ 防御 SYN Flood 的常见手段是 SYN Cookies：服务端不立刻分配资源，把连接信息编码进自己的 ISN，等客户端 ACK 回来再真正建连。net.ipv4.tcp_syncookies 默认开启。

抓包识别

现象 含义
只有 SYN 没有 SYN-ACK 服务端没监听 / 被防火墙 DROP / 端口不对
SYN 后立刻 RST 服务端有进程但没人监听该端口，或防火墙 REJECT
SYN 重传 3 次后失败 对端不可达或丢包，connect() 超时
握手成功但立刻 FIN 应用层主动拒绝（如 Nginx 的 deny、TLS 证书不匹配）

三、四次挥手与 TIME_WAIT

TCP 是全双工，两个方向要各自关闭，所以是四次。

TIME_WAIT 为什么必须存在

目的 说明
保证最后一个 ACK 能到达 若该 ACK 丢了，对方会重传 FIN；此时本方若已 CLOSED，会回 RST，对方认为连接异常关闭。留在 TIME_WAIT 才能重发 ACK。
让旧报文在网络中消亡 同一个四元组（源 IP、源端口、目的 IP、目的端口）如果立刻复用，上一连接的延迟报文可能被新连接误收。等 2MSL 保证旧包已全部超时。

MSL（Maximum Segment Lifetime）：报文在网络中的最大生存时间。RFC 1122 建议 MSL = 2 分钟，因此 2MSL = 4 分钟。

⚠️ Linux 并不按 RFC 建议值实现。内核里是硬编码的 TCP_TIMEWAIT_LEN = 60 秒（见 include/net/tcp.h），和 MSL 无关。所以「Linux 的 TIME_WAIT 是 4 分钟」是错的。

⚠️ 只有主动关闭方进入 TIME_WAIT。 所以 TIME_WAIT 堆积要先问：是谁在主动关连接？ 短连接客户端、Nginx 反向代理（proxy_http_version 1.1 没配时默认每请求一连接）都是典型的 TIME_WAIT 制造者。

TIME_WAIT 数量怎么看

参数 作用 备注
net.ipv4.tcp_tw_reuse 允许主动发起连接时复用 TIME_WAIT 端口 只影响出向连接；需要 tcp_timestamps=1
net.ipv4.tcp_max_tw_buckets TIME_WAIT 数量上限，超过直接销毁并打日志 治标，日志里会有 TCP: time wait bucket table overflow
net.ipv4.tcp_fin_timeout 只影响 FIN_WAIT_2，不影响 TIME_WAIT 最常见的误配

⚠️ net.ipv4.tcp_tw_recycle 已在 Linux 4.12 被移除（它靠时间戳判断，在 NAT 后面会把正常客户端全判成无效包）。看到旧教程让你开它，直接跳过。Debian 10 / CentOS 8 及以后的 sysctl 写这个键会报错。

四、CLOSE_WAIT 堆积说明什么

状态 谁在 含义
CLOSE_WAIT 被动关闭方 收到了对方的 FIN 并回了 ACK，但应用层还没调用 close()
FIN_WAIT_2 主动关闭方 已发 FIN 并收到 ACK，等对方发 FIN
TIME_WAIT 主动关闭方 正常状态，60 秒后自动消失

⚠️ CLOSE_WAIT 堆积是代码 bug，不是内核参数问题。 它意味着连接已经在应用层「死了」，但代码没走到关闭逻辑。改任何 sysctl 都无效。常见根因：

  • 连接池只借不还（异常路径没 finally 里归还）
  • HTTP 客户端没设超时，线程卡在读响应上，连接永远不关
  • 请求处理中抛异常，跳过了 close()
  • 线程池满，任务排队，连接在队列里等到超时

⚠️ CLOSE_WAIT 不占端口，占的是文件描述符。 堆积到 ulimit -n 上限后，新的 accept 会失败，日志里是 Too many open files —— 这时才有人发现。

五、可靠传输靠什么

机制 作用
序号 seq 按字节编号，接收方据此重排、去重
确认 ack 累积确认：ack=N 表示 N 之前全部收到
超时重传 RTO 由 SRTT / RTTVAR 动态算出（RFC 6298），不是固定值
快速重传 收到 3 个重复 ACK 立刻重传，不等超时
SACK（RFC 2018） 选择性确认，只重传真正丢的那段，避免整段重传
滑动窗口 流量控制，接收方用 rwnd 告诉对方自己还能收多少
  • rwnd 是接收方的能力（流量控制，防止把接收方缓冲区冲爆）。
  • cwnd 是网络的能力（拥塞控制，防止把链路冲爆）。

⚠️ 窗口缩放（Window Scale）：TCP 头里窗口字段只有 16 位，最大 65535 字节。高带宽高延迟链路（BDP 很大）必须靠 SYN 里协商的缩放因子放大窗口。如果中间设备不转发该选项，吞吐会被限制在 64KB 窗口对应的水平 —— 这是「带宽够但就是慢」的经典原因。

六、拥塞控制四个阶段

RFC 5681 定义四个算法：慢启动、拥塞避免、快速重传、快速恢复。

阶段 触发 cwnd 变化
慢启动 Slow Start 连接开始 / 重传超时后 每收到一个 ACK 加 1 MSS，每 RTT 翻倍（指数）
拥塞避免 Congestion Avoidance cwnd ≥ ssthresh 每 RTT 加约 1 MSS（线性）
快速重传 Fast Retransmit 3 个重复 ACK 立即重传，不等 RTO
快速恢复 Fast Recovery 快速重传之后 ssthresh = cwnd/2，cwnd = ssthresh + 3，进入拥塞避免

⚠️ 「慢启动」不慢 —— 它是指数增长的。名字来自它从 1 MSS 起步，而不是增长速度慢。

事件 反应
3 个重复 ACK（快速重传） ssthresh = cwnd/2，走快速恢复，不回慢启动
RTO 超时 ssthresh = cwnd/2，cwnd = 1，重回慢启动（这是最严重的信号）

⚠️ Linux 默认拥塞算法是 CUBIC（内核 2.6.19 起成为默认），它在长肥管道上比 Reno 激进。BBR 则是基于带宽和 RTT 建模，丢包不等于拥塞，在高丢包链路上优势明显。切换算法对已建立连接无效，只影响新连接。

七、粘包与拆包

TCP 是字节流，没有「消息」这个概念。 一次 send() 的内容可能被拆成多个包，多次 send() 也可能被合并成一个包 —— 这两个现象合称「粘包」，但本质是应用层没有做消息边界，不是 TCP 的 bug。

方案 适用 缺陷
定长消息 字段长度固定的协议 灵活性差
分隔符（\r\n） 文本协议（HTTP/Redis RESP） 内容里不能出现分隔符，需转义
长度字段（TLV） 二进制协议，最通用 需要处理半包状态
每次短连接 简单但代价高 延迟高、TIME_WAIT 多

⚠️ recv(n) 返回的字节数 ≤ n，绝不等于 n。 「一次 recv 拿到一条完整消息」是错的假设，任何依赖它的代码在压力下必然出问题。这就是为什么必须用长度字段 + 循环读。

⚠️ UDP 没有粘包问题（有边界，一个包一次 recvfrom），但会丢包、乱序、重复，且单包受 MTU 限制。「要不要用 UDP」的答案是：除非你能自己实现可靠性（或直接用 QUIC），否则用 TCP。

八、端口耗尽与 SO_REUSEADDR

一条 TCP 连接由四元组唯一确定：(源IP, 源端口, 目的IP, 目的端口)。

限制 说明
客户端连同一个目标 可用源端口只有约 2.8 万个（受 ip_local_port_range 限制）
客户端连多个目标 四元组更多组合，容量成倍增加
服务端 监听端口只有一个，但连接由四元组区分，容量受 fd 和内存限制

⚠️ 服务端「端口耗尽」是个常见误解 —— 服务端不会耗尽端口，它耗尽的是文件描述符（ulimit -n）和连接跟踪表（nf_conntrack）。真正的端口耗尽是客户端侧：短连接 + 高 QPS 时，TIME_WAIT 占满 2.8 万个源端口，connect() 报 Cannot assign requested address。

选项 作用 场景
SO_REUSEADDR 允许 bind() 一个处于 TIME_WAIT 的端口 服务端重启必须开，否则 Address already in use
SO_REUSEPORT 允许多个进程/线程 bind() 同一端口（Linux 3.9+） 多进程共享监听，内核做负载均衡

⚠️ TIME_WAIT 阻挡的是 bind()，不是 connect()。 客户端发起新连接时，内核会自动跳过仍在 TIME_WAIT 的本地端口（除非开了 tcp_tw_reuse）。「服务端起不来，报 Address already in use」才是 SO_REUSEADDR 要解决的问题。

⚠️ SO_REUSEADDR 在 Windows 上语义不同：Windows 默认就允许 bind 已占用端口（除非另一 socket 开了 SO_EXCLUSIVEADDRUSE），这会导致两个进程同时监听一个端口却不报错，请求随机分给其中一个。跨平台代码要显式设 SO_EXCLUSIVEADDRUSE。

常见坑清单

  • 认为「三次握手多余，两次就够」——忽略了历史重复 SYN 造成的半开连接
  • 把 TIME_WAIT 当成故障去清 —— 它是正常状态，堆到几万才需要关注
  • 用 tcp_fin_timeout 去调 TIME_WAIT（它只影响 FIN_WAIT_2）
  • 开 tcp_tw_recycle（Linux 4.12 已移除，且会误杀 NAT 后的客户端）
  • 看到 CLOSE_WAIT 堆积去改内核参数（应改代码里的连接关闭逻辑）
  • 以为服务端会端口耗尽（耗尽的是 fd / conntrack，客户端才是端口耗尽）
  • 服务端没设 SO_REUSEADDR，重启就报 Address already in use
  • 假设一次 recv() 能拿到一条完整消息，不处理半包
  • 应用层自己拼消息却不定义边界，出了问题怪「TCP 粘包」
  • 只调大 ssthresh 相关的内核参数，却不知道 cwnd 是动态的、改参数对新连接才生效
  • 没开窗口缩放或中间设备丢弃了该选项，导致高延迟链路吞吐被卡在 64KB 窗口
  • 长肥管道上看到丢包就以为网络故障（BBR 场景下丢包不等于拥塞）
