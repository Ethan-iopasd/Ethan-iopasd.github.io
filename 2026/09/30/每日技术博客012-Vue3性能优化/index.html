开场：先量再优化

Vue 3 本身已经很快。绝大多数「卡」不是框架问题，是数据量、渲染次数或打包体积的问题。

优化顺序永远是：测量 → 定位 → 改 → 再测量。凭感觉改是浪费。

一、响应式层面的陷阱

1. 大对象用深层响应式

API 代理深度 适合
ref / reactive 深层 需要改内部属性
shallowRef 只跟踪 .value 替换 整体替换的只读大对象
shallowReactive 只代理顶层 顶层会变、内部不变

⚠️ shallowRef 的坑：改 .value 内部属性不会触发更新，必须整体替换。

2. computed 里做重计算

computed 有缓存，但依赖一变就失效。如果 keyword 输入时每敲一个字符都触发重算：

3. watch 监视了不需要的东西

deep: true 在深层大对象上是递归遍历，开销随数据量线性增长。

4. 副作用没清理

未清理的定时器和事件监听会持续运行，组件卸载后还在跑。

二、组件渲染优化

v-for 的 key 必须是稳定唯一值

为什么 index 有问题？ 列表中间插入一条时，后面所有元素的 index 都变了，Vue 会认为「所有元素都变了」，于是全部重新渲染。

⚠️ 如果列表是纯静态、不会增删排序，用 index 才没问题。

v-if 和 v-show 的选择

v-if v-show
机制 销毁 / 重建 DOM 只切 display
初始开销 条件为假时更省 无论真假都要渲染
切换开销 大 小
适合 很少切换 频繁切换

拆分组件，缩小更新范围

把行拆成子组件后，Vue 的更新粒度更细，只需重渲染变化的行。

v-once 与 v-memo

v-memo 适合大列表里「大部分行不变、少数行变」的场景。用错地方反而更慢，别乱加。

六、优化的优先级

按投入产出比排序：

  1. 长列表虚拟滚动 —— 数量级提升
  2. 路由懒加载 + 代码分割 —— 直接减少首屏体积
  3. 依赖体积治理（lodash / moment / 全量 UI 库）—— 几百 KB 起步
  4. v-for 的 key、v-show 选择 —— 低成本
  5. 响应式粒度（shallowRef / Object.freeze）—— 大对象时有效
  6. 微优化（v-memo、v-once）—— 收益有限，别优先做

先做前三条，通常已经能解决 90% 的问题。

常见坑清单

  • 上万行的表格用 reactive，深层代理开销巨大
  • 用 shallowRef 后改 .value 内部属性，以为会更新
  • v-for 用 index 当 key，列表插入时整块重渲染
  • 频繁切换的场景用了 v-if
  • 长列表不虚拟滚动，硬渲染上万行 DOM
  • 路由组件全部静态引入，主包体积爆炸
  • import _ from 'lodash' 把整个 lodash 打进产物
  • 用 moment 处理日期（换 dayjs）
  • 组件卸载时没清理定时器 / 事件监听
  • console.log 留在生产代码里（Vite 不会自动删）
  • 只看 Lighthouse 本地分数，不看真实用户指标
  • 一上来就做 v-memo 微优化，却没做代码分割
