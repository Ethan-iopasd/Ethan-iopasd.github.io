开场：Service 是一层稳定的虚拟 IP

Pod 重建后 IP 会变，Service 提供固定的 ClusterIP + DNS 名，靠 label selector 动态跟踪后端 Pod。它不转发流量本身，真正干活的是每个节点上的 kube-proxy。

一、Service 四种类型

type 暴露范围 说明
ClusterIP 集群内 默认。只有一个虚拟 IP，集群内可达
NodePort 集群外（每节点同端口） 在 ClusterIP 之上，每个节点开一个 30000–32767 的端口
LoadBalancer 集群外（云 LB） 在 NodePort 之上，向云厂商申请一个外部 LB
ExternalName 只做 DNS CNAME 不代理，直接把服务名解析到外部域名
端口字段 指谁
port Service 的端口，其他服务连 web:80
targetPort 容器监听的端口，不写则默认等于 port
nodePort 节点上暴露的端口（仅 NodePort/LoadBalancer）

⚠️ port 和 targetPort 搞混是最高频错误。 应用在容器里监听 8080，Service port: 80、targetPort: 8080，其他服务连的是 web:80。

⚠️ NodePort 不是只开在某个节点上，是每个节点都开同一个端口。防火墙只放通一个节点，其他节点进来的流量会断。

⚠️ **LoadBalancer 在裸机集群上会永远 Pending**，因为没有 cloud-controller-manager 去申请 LB。裸机要用 MetalLB 之类的方案。

二、Service 怎么找到 Pod

靠 label selector 匹配 Pod 的 metadata.labels，匹配结果写进 EndpointSlice（老版本是 Endpoints）。

现象 原因
kubectl get endpoints web 显示 <none> selector 没匹配到任何 Pod
匹配到了 Pod，但访问不通 Pod 没 Ready，EndpointSlice 里被标记为 not ready
只有部分 Pod 被选中 label 写错了几个（比如 app: web vs app: Web）

⚠️ Pod 不 Ready 就不在 Service 后端里。 这是 readiness 探针的直接作用。readiness 一直失败 → EndpointSlice 空 → 请求 503。看到 503 先查 readiness，不要先怀疑 Service。

⚠️ Service 的 selector 是「弱绑定」。 写错了不会报错，只会得到一个空后端。改完 label 记得回头 describe svc 确认。

三、kube-proxy：iptables 还是 IPVS

kube-proxy 监听 Service / EndpointSlice 变化，在节点上生成转发规则。

模式 实现 特点
iptables 一串 iptables 规则链 默认。规则线性匹配，Service 数量上千后退化明显
ipvs 内核 IPVS 哈希表 规则是 O(1) 查找，支持 rr / wrr / lc 等调度算法，大规模集群更稳
nftables nftables 规则 较新，逐步替代 iptables

⚠️ 改 kube-proxy 模式要改 ConfigMap 并重启 DaemonSet，且需要节点内核加载 ip_vs 模块。不是改完立即生效。

四、Ingress 与 Ingress Controller

角色 是什么 谁提供
Ingress 一份路由规则声明（域名 + 路径 → Service） 你写 YAML
Ingress Controller 真正读规则、配反向代理的进程 需要自己装（nginx-ingress / Traefik / Envoy Gateway）

Ingress 资源本身不干活。 集群里没装 Controller，Ingress 就是一堆没人读的 YAML。

pathType 匹配方式
Prefix 按路径段前缀匹配（/api 匹配 /api 和 /api/v1，不匹配 /apix）
Exact 完全相等
ImplementationSpecific 交给 Controller 自己解释（各实现不同，尽量别用）

⚠️ ingressClassName 不写，多个 Controller 共存时会互相抢规则，表现是路由时灵时不灵。

⚠️ TLS 证书是 Secret，且必须在 Ingress 所在命名空间。 跨命名空间引用不被支持。

五、ConfigMap

坑 说明
数字没加引号 LOG_LEVEL: 1 会被 YAML 解析成 int，kubectl apply 报类型错误
大小限制 单个 ConfigMap 上限 1MiB（etcd 限制）
挂载成卷后修改 卷里的文件会自动更新（有延迟），环境变量不会
subPath 挂载 用 subPath 挂的 ConfigMap 不会自动更新

⚠️ 改 ConfigMap 不会重启 Pod。 挂成卷的最终会更新文件，应用得自己 watch 或收到信号重载；挂成环境变量的永远不变，必须 kubectl rollout restart。

六、Secret：stringData 与 base64

Secret 的 data 字段必须是 base64，stringData 是写明文、由 API Server 帮你编码的便利字段。

⚠️ base64 不是加密。 kubectl get secret -o jsonpath='{.data.DB_PASSWORD}' | base64 -d 一条命令就能还原。Secret 只是「不放进镜像、单独管理」的机制。

⚠️ echo 不带 -n 会多一个换行符，base64 出来多几个字符，解码后密码末尾带 \n，登录失败且极难排查。

⚠️ type: kubernetes.io/tls 的 Secret 必须包含 tls.crt 和 tls.key 两个键，键名写错 Controller 不认。

⚠️ Secret 默认不加密落盘。 etcd 里是明文 base64。生产要开 EncryptionConfiguration，并配合 RBAC 限制 get secret 权限。

七、注入的两种方式

环境变量 挂载卷
更新后生效 不会，必须重建 Pod 会（subPath 除外），有延迟
适合 少量标量配置 配置文件、证书、需要热加载的内容
排查 kubectl exec -- env kubectl exec -- cat /etc/app/...
泄漏面 进程环境里可见（/proc/<pid>/environ） 文件权限可控（defaultMode）

⚠️ 挂载 ConfigMap 会覆盖整个目录，不是「往目录里加文件」。mountPath: /etc/app 会让 /etc/app 下的原有内容全部不可见。

⚠️ 用 subPath 挂单个文件，更新不会同步。 想要热更新就别用 subPath，改用整个目录挂载。

八、HPA 自动扩缩

要点 说明
利用率基准 是 requests 的百分比，不是 limits
必须设 requests 没设 requests 的容器，CPU 利用率算不出来，HPA 报 unknown
生效前提 集群装了 metrics-server
抖动 默认有扩缩容稳定窗口，避免来回横跳

⚠️ HPA 依赖 requests。 忘了设 resources.requests.cpu 是 HPA 不动的最常见原因，kubectl describe hpa 会写 <unknown>/70%。

⚠️ HPA 扩容有延迟（采集指标 + 决策 + 调度 + 启动 + readiness）。突发流量靠 HPA 兜不住，前面还得有缓冲。

九、PVC 与 StorageClass

对象 谁创建 作用
PersistentVolume（PV） 管理员或 provisioner 实际的存储卷
PersistentVolumeClaim（PVC） 你 申请「我要 10Gi、可读写的存储」
StorageClass 管理员 描述「用哪套存储、怎么动态创建 PV」
accessModes 含义
ReadWriteOnce（RWO） 只能被单个节点读写挂载
ReadOnlyMany（ROX） 多节点只读
ReadWriteMany（RWX） 多节点读写（需要 NFS / CephFS 等支持）
ReadWriteOncePod（RWOP） 只能被单个 Pod 读写
volumeBindingMode 行为
Immediate PVC 一创建就分配 PV
WaitForFirstConsumer 等有 Pod 要用时才分配，避免跨可用区调度失败

⚠️ ReadWriteOnce 是「单节点」不是「单 Pod」。 同节点上两个 Pod 可以同时挂同一个 RWO 卷，跨节点就不行。

⚠️ 默认 StorageClass 的 volumeBindingMode 是 Immediate 时，多可用区集群容易出问题：PV 建在 A 区，Pod 被调度到 B 区，卡在 Pending。用 WaitForFirstConsumer。

⚠️ 删 PVC 会连带删 PV（取决于 reclaimPolicy，动态供应的默认是 Delete）。kubectl delete pvc 之前想清楚数据还要不要。

常见坑清单

  • Service 的 port 和 targetPort 写反，容器端口对不上
  • Service selector 写错，endpoints 是 <none>，但不报任何错
  • Pod 一直不 Ready，Service 后端为空，请求 503 却去查 Service
  • 裸机集群用 type: LoadBalancer，EXTERNAL-IP 永远 Pending
  • NodePort 只在防火墙放通一个节点，其他节点访问不通
  • 装了 Ingress 资源但没装 Ingress Controller，规则没人读
  • 多个 Controller 共存时不写 ingressClassName，路由互相抢
  • Secret 手写 base64 时用 echo 没加 -n，密码尾部多一个换行
  • 以为 Secret 是加密的（base64 一条命令就能还原）
  • 改 ConfigMap 后挂成环境变量的 Pod 没重启，还以为是配置没生效
  • 用 subPath 挂 ConfigMap，改了文件却一直不更新
  • 配了 HPA 但没设 resources.requests.cpu，HPA 显示 <unknown>
  • 多可用区集群用 Immediate 绑定，Pod 卡在 Pending
