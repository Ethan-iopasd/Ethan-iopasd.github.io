开场：值得动的参数只有几个

调参之前先确认问题不在 SQL 和容量上。绝大多数「数据库慢」的根因是慢查询和索引，不是参数。

在 InnoDB 上真正值得反复权衡的参数：

参数 影响
innodb_buffer_pool_size 命中率，唯一必须调的内存参数
innodb_flush_log_at_trx_commit 崩溃时的数据安全 vs 写入吞吐
sync_binlog binlog 落盘时机，同上
innodb_redo_log_capacity 写入突发时的缓冲能力
max_connections 连接数上限，不是越大越好
sql_mode 严格模式，决定脏数据能不能写进来

⚠️ 参数改完要观察至少一个完整业务周期（含日终批处理）再下结论。单次压测的结果往往不可迁移。

一、InnoDB vs MyISAM

维度 InnoDB MyISAM
事务 ✅ ACID ❌ 不支持
锁粒度 行锁（默认），间隙锁防幻读 表锁
MVCC ✅ ❌
崩溃恢复 ✅ redo log 自动恢复 ⚠️ 需 myisamchk 手工修
外键 ✅ ❌
全文索引 ✅ 5.6 起支持 ✅
COUNT(*) 无 WHERE 需扫描（MVCC 导致） 直接读计数器，极快
存储文件 .ibd 表空间 .MYD + .MYI

结论：新表一律 InnoDB。MySQL 8.0 起系统表已全部改为 InnoDB，MyISAM 只剩历史包袱 —— 唯一值得留意的是它在 COUNT(*) 上的优势，用计数表或缓存就能替代。

⚠️ 迁移老库里的 MyISAM 表时注意三点：AUTO_INCREMENT 语义差异、表锁下的并发写、以及没有崩溃恢复能力。

二、Buffer Pool：唯一必须调的内存参数

innodb_buffer_pool_size 默认 134217728 字节（128MB），官方建议专用数据库服务器上设为物理内存的 **80%**。

它缓存的是表和索引的数据页，命中率直接决定查询是否读盘。

配套参数：

参数 默认值 说明
innodb_buffer_pool_size 134217728（128MB） 必须是 chunk_size × instances 的整数倍
innodb_buffer_pool_instances buffer pool ≥ 1GB 时为 8，否则 1 拆成多个实例，减少互斥锁争用
innodb_buffer_pool_chunk_size 134217728（128MB） 在线调整的粒度

⚠️ innodb_buffer_pool_size 支持在线调整，但扩容时按 chunk 逐个分配，期间可能有性能抖动。生产环境尽量在低峰期改，且必须按 chunk 对齐，否则实例起不来。

三、redo log / undo log / binlog

三者的职责完全不同，混在一起记是常见误区。

日志 层次 作用 写入时机
redo log InnoDB 引擎层 崩溃恢复：保证已提交事务不丢 事务执行中持续写
undo log InnoDB 引擎层 MVCC + 回滚：保留旧版本 事务执行中持续写
binlog Server 层 复制 + 时间点恢复 事务提交时写

刷盘参数：性能与安全的分界线

innodb_flush_log_at_trx_commit（默认 1）：

值 行为 崩溃丢失 性能
1 每次提交都刷 redo log 并 fsync 不丢 最低
2 每次提交写 OS 缓存，每秒 fsync 丢约 1 秒（OS 崩溃时） 中
0 每秒写 + 刷一次 丢约 1 秒（MySQL 崩溃也丢） 最高

sync_binlog（默认 1）：

值 行为 崩溃丢失
1 每次提交都 fsync binlog 不丢
0 交给 OS 决定 可能丢
N 每 N 次提交 fsync 一次 最多丢 N 个事务

常见组合：

组合 场景 说明
1 + 1 默认，金融级 两边都不丢，吞吐最低
1 + N（如 1000） 一般业务 redo 不丢，binlog 可能丢，主从可能不一致
2 + 1000 高吞吐、可容忍秒级丢失 常见于日志类写入
0 + 0 只用于压测 / 可重建数据 崩溃会丢数据

⚠️ innodb_flush_log_at_trx_commit = 1 配 sync_binlog = 0 是最危险的组合：崩溃后 redo 里的数据和 binlog 对不上，主从直接不一致。要么两个都是 1，要么明确接受丢失窗口。

redo log 容量

innodb_log_file_size 和 innodb_log_files_in_group 在 MySQL 8.4 已弃用，由 innodb_redo_log_capacity 取代（8.0.30 引入，支持在线调整）。

容量太小时，写突发会频繁触发 checkpoint，出现周期性的写入抖动。

⚠️ 如果同时配置了 innodb_redo_log_capacity 和旧的 innodb_log_file_size，以前者为准；旧参数只在 innodb_redo_log_capacity 未定义时才参与容量计算。

四、连接与包大小

参数 默认值 说明
max_connections 151 最大并发连接数
max_allowed_packet 64M（8.0 起） 单个网络包上限，影响大字段和大批量导入
wait_timeout 28800（8 小时） 非交互连接空闲超时
interactive_timeout 28800 交互式连接空闲超时
thread_cache_size 8.0 起按 max_connections 自动推算 线程复用

⚠️ max_connections 不是越大越好。每个连接都有独立的内存开销（排序缓冲、连接缓冲等），拉满会导致内存耗尽和上下文切换开销。用连接池控制并发，而不是靠调大上限。

max_allowed_packet 的坑：客户端和服务端各有一份，取两者的较小值。导入大 SQL 文件报 Packet too large 时，两边都要调。

五、字符集与排序规则

MySQL 8.0 起默认 utf8mb4 + utf8mb4_0900_ai_ci。

字符集 说明
utf8mb4 ✅ 真 UTF-8，支持 emoji 和 4 字节字符
utf8mb3（别名 utf8） ⚠️ 最多 3 字节，别再用
latin1 只适用于纯 ASCII 遗留库

⚠️ 排序规则不同的列之间无法走索引 JOIN。老库从 utf8mb3 迁到 utf8mb4 时，如果只改了部分表，关联查询会突然变慢 —— 因为比较时发生了隐式转换。

六、sql_mode 的严格模式

MySQL 8.4 默认 sql_mode 包含 6 个模式：

模式 作用 关掉的风险
ONLY_FULL_GROUP_BY SELECT 里的非聚合列必须在 GROUP BY 中 查询结果不确定，最常被关掉的一个
STRICT_TRANS_TABLES 非法值直接报错而非截断 超长字符串被静默截断、数值溢出变边界值
NO_ZERO_IN_DATE / NO_ZERO_DATE 禁止 '0000-00-00' 类日期 写入无效日期，后续查询报错
ERROR_FOR_DIVISION_BY_ZERO 除零报错 静默得到 NULL
NO_ENGINE_SUBSTITUTION 引擎不可用时报错而非替换 建表悄悄变成别的引擎

⚠️ 为了兼容老代码把 sql_mode 清空，是在把错误推迟到生产。另外 NO_ZERO_IN_DATE、NO_ZERO_DATE、ERROR_FOR_DIVISION_BY_ZERO 已被标记弃用，未来会并入严格模式 —— 依赖非严格行为的代码迟早要改。

七、参数组合的取舍

场景 innodb_flush_log_at_trx_commit sync_binlog 说明
交易 / 支付 1 1 不允许丢
常规业务 1 1 默认即可，先把 SQL 优化好
日志 / 埋点 2 1000 可容忍秒级丢失
只读从库 1 — 写入少，重点在 Buffer Pool
压测 / 临时库 0 0 绝不上生产

⚠️ 用 2 或 0 换来的吞吐提升通常只有百分之几十，而一次崩溃丢数据是不可逆的。除非业务明确说「丢了可以重建」，否则保持默认。

常见坑清单

  • 还没排查慢查询就先动参数
  • innodb_buffer_pool_size 保持默认 128MB 跑生产
  • innodb_buffer_pool_size 改完没按 chunk 对齐，实例起不来
  • innodb_flush_log_at_trx_commit = 1 配 sync_binlog = 0
  • 还在用已弃用的 innodb_log_file_size
  • 为了「提升并发」盲目调大 max_connections
  • max_allowed_packet 只调了服务端，客户端没调
  • 新表还用 utf8（即 utf8mb3）
  • 字符集 / 排序规则不一致导致 JOIN 不走索引
  • 为了兼容老代码把 sql_mode 清空
  • 改了参数没观察完整业务周期就下结论
