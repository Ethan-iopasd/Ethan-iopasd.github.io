开场：错误是值，panic 只留给「程序写错了」

情况 处理方式
可预期的失败（文件不存在、网络超时、校验不通过） 返回 error，用 %w 包装
不可预期的失败（数组越界、nil 解引用、断言失败） panic，由运行时终止
初始化阶段的致命错误（配置缺失、端口被占） panic 或 log.Fatal，在 main 里
库代码里遇到「不该发生」的状态 返回 error，不要 panic

库（package）不应该 panic。 调用方无法预期，也无法优雅恢复。

一、error 是一个接口

只有这一个方法。因此任何类型都能是错误 —— 这是 Go 错误处理灵活性的全部来源，也是混乱的来源。

形态 写法 判定方式
哨兵错误 var ErrNotFound = errors.New("not found") errors.Is(err, ErrNotFound)
包装错误 fmt.Errorf("load user: %w", err) errors.Is / errors.As 沿链查找
自定义类型 type ValidationError struct { Field string } errors.As(err, &target)
聚合错误 errors.Join(err1, err2) errors.Is 会遍历所有分支

⚠️ 哨兵错误用 errors.New，不要用 fmt.Errorf。 后者每次调用都返回新值，== 比较永远不相等。

二、包装与判定：%w / Is / As / Unwrap

三个函数的职责：

函数 作用 注意
errors.Is(err, target) 沿链找是否有等于 target 的错误 target 可以是哨兵错误
errors.As(err, &target) 沿链找第一个能赋值给 target 类型的错误 第二个参数必须是指针
errors.Unwrap(err) 剥掉一层包装 只剥一层，自己写循环容易漏

⚠️ %v 包装会断链。 fmt.Errorf("load: %v", err) 之后 errors.Is(err, ErrNotFound) 返回 false，而且没有任何编译期或运行期提示。想保留链就必须用 %w。
⚠️ errors.As 的第二个参数传值而不是指针会 panic。 而且必须是「指向实现了 error 的类型」的指针。
⚠️ 永远不要用 err.Error() 的字符串做判断。 文案一改就崩，而且是静默的。
⚠️ %w 在 Go 1.20 起可以有多个（fmt.Errorf("a: %w; b: %w", e1, e2)），也可以直接 errors.Join。多个 %w 会构成一个分支错误树，errors.Is 会遍历所有分支。

三、自定义错误类型

选哨兵还是选类型 场景
哨兵错误 只需要判断「是不是这一类」，不需要额外信息
自定义类型 需要携带字段（哪个字段、哪个 ID、重试次数）
两者都用 哨兵作为 Unwrap 的终点，类型携带细节

⚠️ 自定义错误类型的方法接收者用指针（*ValidationError）。用值接收者时，errors.As(err, &target) 的类型匹配会因为装箱差异对不上。

四、panic / recover 的边界

recover() 只有一个有效位置：在 defer 的函数里，且必须是直接调用。

HTTP 中间件里的兜底：

应该 panic 不应该 panic
init() 里配置不合法 任何业务逻辑分支
编程错误：违反函数前置条件 输入校验失败
生成代码 / 反射遇到不可能的状态 外部依赖失败（DB、HTTP）
测试里标记「不可达」 库代码里的「我不支持这个」

⚠️ recover 之后不要静默吞掉。 至少要记日志 + 打 debug.Stack()，否则线上会变成「请求返回 500，日志里什么都没有」。
⚠️ recover 不能跨 goroutine。 子 goroutine 里 panic 且没自己 recover，会直接终止整个进程。每个 go func() 里如果需要兜底，得自己写 defer。
⚠️ Go 1.21 起，panic(nil) 不再产生 nil 的 recover 值 —— 它会变成 *runtime.PanicNilError。老代码里靠 recover() == nil 判断「没 panic」的逻辑会失效。
⚠️ recover 只能阻止 panic 向上传播，不能回滚已产生的副作用（已写入的数据、已发送的消息）。

五、defer 的执行顺序与陷阱

规则 说明
执行顺序 LIFO，后 defer 的先执行
参数求值时机 在 defer 语句处求值，不是在函数返回时
能否改返回值 只有命名返回值能被改
os.Exit() 不执行任何 defer
runtime.Goexit() 会执行 defer
执行时机 函数返回时，不是「块」结束时

⚠️ 写文件时 defer f.Close() 的错误不能忽略。 Close 可能因为 flush 失败而返回错误，而这时你的数据其实没落盘。defer 里要么显式处理，要么用命名返回值合并。
⚠️ 读文件时 Close 的错误可以忽略，写文件时不行。区别在于 Close 是否承担 flush 职责。

六、项目布局

目录 放什么 约束
cmd/<binary>/main.go 入口，只做装配 尽量薄，业务逻辑不要写在这
internal/ 私有代码 internal 是编译器强制的可见性，外部模块无法 import
pkg/ 想被别人 import 的代码 用不上就别建
api/ 接口契约（proto、OpenAPI）
testdata/ 测试夹具 Go 工具链自动忽略该目录

⚠️ 流传很广的 golang-standards/project-layout 不是 Go 官方标准，是社区总结。小项目硬套 pkg/、internal/、third_party/ 只会增加噪音。
⚠️ main.go 里写业务逻辑是后期最难拆的债。它应该只做「读配置 → 构造依赖 → 调 Run(ctx) → 处理信号」。
⚠️ 多模块协作时用 go.work 本地联调，但 go.work 不要提交到仓库（它绑定了本机路径）。

七、依赖注入：不用框架的做法

核心两点：构造函数注入、接口定义在消费方。

做法 什么时候值得
手工构造（上面这种） 依赖数量在几十个以内，绝大多数服务够用
google/wire 构造链很深，想要编译期校验的代码生成
uber/fx 依赖生命周期复杂（启动顺序、优雅关闭），团队熟悉 DI 容器

⚠️ 接口定义在消费方，不是实现方。 在 postgres 包里定义 Store 接口，然后让 user 包依赖它，会形成反向依赖。
⚠️ 不要为每个 struct 都抽接口。接口的价值在于「有第二个实现」或「需要在测试里替换」，否则只是增加跳转层。

八、测试

表驱动测试是 Go 的默认写法：

常用能力：

能力 写法
子测试 + 并发 t.Run(name, func(t *testing.T){ t.Parallel() })
标记辅助函数（报错行号指向调用方） t.Helper()
临时目录（自动清理） t.TempDir()
临时环境变量（自动还原） t.Setenv("K", "V")
临时文件夹具 testdata/ 目录
测 HTTP handler net/http/httptest
测并发代码的虚拟时间 testing/synctest（Go 1.25 新增）
检测 goroutine 泄漏 go.uber.org/goleak

⚠️ go test 默认会缓存结果。 CI 上必须加 -count=1，否则改了外部依赖（环境变量、文件）它可能直接返回上次的「通过」。
⚠️ 表驱动测试里 tt 的捕获问题：Go 1.22 起循环变量每次迭代独立，t.Parallel() 不再需要 tt := tt。但 go.mod 里 language version 低于 1.22 时仍需手动拷贝。
⚠️ 覆盖率是语句覆盖，跑满 100% 不代表逻辑正确。别把它当质量指标。

九、golangci-lint

检查 抓什么
errcheck f.Close()、json.Encode() 的返回值被丢弃
errorlint err == ErrX（应该用 errors.Is）、fmt.Errorf("%v", err)
govet 的 lostcancel WithCancel 的 cancel 没被调用
govet 的 copylocks 复制了含 Mutex 的 struct
staticcheck 冗余代码、可疑逻辑、已废弃 API
bodyclose http.Get 后没关 resp.Body

⚠️ go vet 是标准库自带的，先跑 go vet ./...，再上 golangci-lint。CI 里两个都跑，成本极低。
⚠️ 别一次开满所有 linter。CI 上突然冒出上千条告警，团队的第一反应是关掉它。从 5~8 个核心 linter 起步，逐条消化。

十、编译期注入版本信息

手段 优点 限制
-ldflags -X 完全可控，可注入 CI 流水线号 变量必须是未初始化的字符串变量（var Version string）
runtime/debug.ReadBuildInfo() 无需构建参数 依赖 go build 时在 git 仓库里；-trimpath / GOFLAGS 会影响
go:embed 一个版本文件 简单直接 要额外生成文件

⚠️ -X 的目标必须是字符串变量，且必须是 var（不能用 const，也不能是有初始值的表达式形式）。路径要写完整 import path，不是包名。
⚠️ 用 -X 注入时不要忘了 -s -w 之外还要保留符号表 —— 顺序和引号在 Makefile 里很容易写错，构建后打一次 /version 验证。

常见坑清单

  • 用 %v 包装错误，导致 errors.Is / errors.As 失效
  • 用 err.Error() 字符串比较判断错误类型
  • errors.As 的第二个参数传值而不是指针
  • 哨兵错误用 fmt.Errorf 创建，== 比较永远不相等
  • 库代码里 panic
  • 子 goroutine 里 panic 没自己 recover，直接杀掉整个进程
  • recover 之后不记日志、不打 debug.Stack()
  • 靠 recover() == nil 判断没发生 panic（Go 1.21 起 panic(nil) 不再返回 nil）
  • 循环里 defer，文件句柄 / 连接累积到函数返回才释放
  • 写文件时忽略 Close() 返回的错误
  • 依赖 os.Exit() 会执行 defer（它不会）
  • 用 err == ErrX 而不是 errors.Is(err, ErrX)
  • CI 上跑 go test 不加 -count=1，拿到缓存的假通过
  • 在实现方的包里定义接口，造成反向依赖
