开场：复制的核心矛盾

所有复制问题最后都归结为两件事：主库写多快 和 从库追多快。一致性、延迟、切换风险都是这个矛盾的派生问题。

排查复制问题前先确定自己站在哪一侧：

现象 大概率原因
从库延迟持续增长且不回落 从库回放能力不足（大事务 / 并行度低）
延迟周期性抖动 主库有大事务或 DDL
延迟很小但数据对不上 binlog 格式或 sql_mode 不一致
复制中断并报错停止 数据冲突 / 主键重复 / 表不存在

一、binlog 格式

格式 记录内容 优点 缺点
STATEMENT SQL 原文 日志小 ⚠️ 非确定性函数导致主从不一致
ROW 每行的前后镜像 ✅ 确定，最安全 日志量大，批量操作尤其明显
MIXED 自动在两者间切换 折中 不确定性又回来了，难预测

MySQL 8.0 起 默认 ROW，且 binlog_format 在 8.4 中已弃用（未来只保留基于行的复制）。

STATEMENT 下的经典踩坑：

binlog_row_image（**默认 full**）：

值 记录内容 影响
full 所有列 最安全，日志最大
minimal 只记变更列 + 定位行所需列 日志小，但依赖前镜像的工具会失效
noblob 所有列，但不记不需要的 BLOB/TEXT 折中

⚠️ 用 minimal 之前先确认下游工具（CDC、闪回、审计）能不能接受。很多工具依赖完整的前镜像。

二、复制流程

线程 位置 职责 常见卡点
Binlog Dump 主库 按位点 / GTID 推送 binlog 网络、从库拉取慢
Replica I/O 从库 拉取 binlog 写 relay log 网络抖动、主库限流
Replica SQL 从库 重放 relay log 回放能力，延迟的主要来源

MySQL 8.0.27 起并行回放默认开启，replica_parallel_workers 默认 4。

SHOW REPLICA STATUS 里最该看的几列：

列 关注点
Replica_IO_Running / Replica_SQL_Running 都必须是 Yes
Seconds_Behind_Master ⚠️ 不可靠，见第四节
Last_IO_Error / Last_SQL_Error 中断的直接原因
Retrieved_Gtid_Set / Executed_Gtid_Set 两者差距 = 未回放的事务数
Relay_Log_Space relay log 占用，持续增长说明回放跟不上

⚠️ Seconds_Behind_Master 是从库当前时间减去正在回放事件的原始时间戳。从库没有新事件时它显示 NULL（看起来「正常」），实际可能已经落后很久。不要拿它做告警主指标。

三、位点复制 vs GTID

维度 位点复制 GTID 复制
定位方式 file + position 全局事务 ID
切换主库 要手工找位点，易错 SOURCE_AUTO_POSITION=1 自动定位
跳过单个事务 SET GLOBAL sql_slave_skip_counter 需构造空事务
幂等性 无 事务可被识别为已执行，天然幂等
配置 简单 需 gtid_mode=ON + enforce_gtid_consistency=ON

四、主从延迟的成因与监控

成因 表现 缓解
大事务（一次改几十万行） 延迟突然飙升，久久不回落 拆成小批次提交
从库回放并发度低 延迟稳定增长 提高 replica_parallel_workers
从库承担大量读 延迟随读 QPS 波动 从库只读、加读池
主库 DDL 期间延迟飙升 用 gh-ost / pt-online-schema-change
网络带宽 / 延迟 I/O 线程跟不上 看 Relay_Log_Space
从库硬件弱于主库 长期小延迟 补齐配置

Seconds_Behind_Master 的三个盲区：

  1. 从库没有新事件时返回 NULL，无法区分「同步完了」和「网络断了」
  2. 大事务执行中只有提交后才更新时间戳，事务跑了 10 分钟它可能仍显示 0
  3. 主库时钟与从库时钟不一致时，结果无意义

外部方案是心跳表：主库周期性写时间戳，从库读出来算差值。Percona Toolkit 的 pt-heartbeat 就是这个思路，它能正确反映大事务期间的延迟。

⚠️ 拿 Seconds_Behind_Master 做告警，最常见的误报是「从库空闲时显示 NULL 或 0，实际复制已经断了」。必须同时监控 Replica_IO_Running 和 Replica_SQL_Running。

五、半同步复制

默认的异步复制下，主库提交成功不代表从库收到了 —— 主库崩溃会丢数据。半同步要求至少一个从库确认收到 binlog 才返回。

模式 行为 数据安全
异步 不等从库 主库崩溃可能丢
AFTER_SYNC 从库写 relay log 后主库再提交 ✅ 默认，推荐
AFTER_COMMIT 主库先提交，再从库确认 主库崩溃后切换可能丢

⚠️ 半同步会超时退化成异步。rpl_semi_sync_source_timeout 到点后主库不再等待从库确认，此时安全性等于异步。要监控 Rpl_semi_sync_source_status 是否仍为 ON。

六、组复制、MHA、Orchestrator

方案 定位 自动切换 一致性
半同步 + MHA 老牌主从高可用 ✅ 由 MHA 负责 依赖半同步
半同步 + Orchestrator 更现代的拓扑管理 ✅ 依赖半同步
Group Replication 基于 Paxos 的多副本 ✅ 内建 ✅ 多数派提交
InnoDB Cluster Shell + Group Replication + Router ✅ ✅ 官方全栈

Group Replication 的关键差异：事务需要多数派确认才算提交，因此不存在「主库提交了但从库没收到」的问题。代价是写入延迟更高，且对网络分区敏感（少数派会被踢出）。

⚠️ MHA / Orchestrator 这类外部方案，切换动作依赖外部脚本，脚本出错就是事故。上线前必须演练切换，并确认 VIP 漂移 / 代理改写逻辑正确。

七、主从切换与脑裂

两种典型场景：

防护手段 说明
Fencing / STONITH 切换前先确认旧主已停止写入（关服务、断网、踢出集群）
read_only / super_read_only 旧主降级后立刻置只读
代理层统一入口 客户端只连 Proxy，不暴露真实地址
GTID 校验 切换前确认新主的 Executed_Gtid_Set 是旧主的超集
多数派仲裁 Group Replication 天然避免，少数派无法提交

⚠️ 「旧主没死透」是脑裂的首要原因。切换脚本必须先执行 fencing，再提升新主 —— 顺序反了，脑裂几乎必然发生。

八、读写分离下的延迟读

复制延迟会直接变成业务问题（分片与读写分离的完整讨论见 SQL 系列第四篇）：

场景 解法
提交后跳转详情页 强制走主库
列表页 / 搜索 可容忍延迟，走从库
支付回调校验 走主库或位点校验
从库延迟超阈值 自动摘除该从库

⚠️ 从库上的统计查询和报表是最隐蔽的延迟源：它占满从库 I/O，让回放线程排队。报表要么走独立的从库，要么走 OLAP 库。

常见坑清单

  • 用 STATEMENT 格式，语句含 NOW() / UUID() / 无 ORDER BY 的 LIMIT
  • 用 binlog_row_image = minimal 但下游工具依赖完整前镜像
  • 只监控 Seconds_Behind_Master，不监控两个线程状态
  • 从库空闲时 Seconds_Behind_Master 为 NULL，被误判为正常
  • 用大事务批量更新，从库延迟长时间不回落
  • 从库承担报表查询，拖慢回放线程
  • GTID 复制下用 sql_slave_skip_counter 跳过事务
  • 迁移到 GTID 前没扫 CREATE TABLE ... SELECT 等不兼容写法
  • 半同步超时退化成异步却没监控
  • 切换脚本没有 fencing，旧主恢复后脑裂
  • 从库没设 super_read_only，被误写
  • 主库与从库的 sql_mode / 字符集不一致
