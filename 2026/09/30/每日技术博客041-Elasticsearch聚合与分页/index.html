开场：三个数字先记住

参数 默认值 作用
index.max_result_window 10000 from + size 的硬上限，超过直接报错
search.max_buckets 65536 单次响应允许创建的聚合桶总数
index.refresh_interval 1s 写入多久后对搜索可见

性能问题几乎都落在这三条线附近：分页越过了 10000、聚合桶数爆了 max_buckets、或者 refresh 太频繁导致写入吞吐上不去。

一、from + size 为什么越翻越慢

查询是分片级执行 + 协调节点归并。每个分片都要取出 from + size 条命中，把前 from 条全部丢弃，只把剩下的 size 条连同排序值交给协调节点。

代价不在返回多少，而在每个分片都要在内存里维护 from + size 大小的优先队列。

分页深度 每分片实际加载 5 分片总量
from=0, size=10 10 50
from=1000, size=10 1010 5050
from=10000, size=10 10010 50050
from=100000, size=10 100010 500050

⚠️ 翻到第 10000 页不会变慢，是直接报错：Result window is too large, from + size must be less than or equal to: [10000]。调大 max_result_window 只是把报错推迟，内存开销线性增长，不是解法。

二、search_after 与 scroll：选型对比

维度 from + size search_after scroll
状态 无 无状态 有状态（_scroll_id + search context）
能否跳页 ✅ 任意页 ❌ 只能顺序往后 ❌ 只能顺序
数据快照 ❌ 实时 ❌ 实时（除非配 PIT） ✅ 创建时的快照
资源占用 每请求内存高 低 持有上下文，阻止旧 segment 删除
官方定位 浅分页 深分页首选 数据导出 / reindex
实时性 实时 实时 快照，不反映后续变更

scroll 的写法：

scroll 细节 说明
排序用 _doc 最快，因为不需要全局排序
聚合结果 只有首次响应带 aggregations，后续没有
scroll_id 每轮返回新的，只用最新的那个

不推荐 官方已明确不再推荐用 scroll 做深分页，改用 PIT + search_after

⚠️ scroll 持有搜索上下文会阻止旧 segment 被合并删除，磁盘和文件句柄都会涨。用完立刻 DELETE /_search/scroll，别等它自然过期。

track_total_hits 是另一个常被忽略的开销：只需要总数时算一次即可，翻页时关掉。

三、cardinality：去重计数是估算值

cardinality 基于 HyperLogLog++，返回的是近似值，不是精确去重。

参数 值
默认 precision_threshold 3000
最大值 40000（超过按 40000 处理）
内存开销 约 precision_threshold * 8 字节
低于阈值的计数 期望接近精确（不保证）

⚠️ precision_threshold 是每分片每聚合的内存开销，不是全局。5 个分片 + 40000 阈值 ≈ 1.6MB，一般可接受；但聚合项一多就会乘起来。不要无脑调到 40000。

⚠️ 精度低不等于不能用。官方实测：即使阈值只有 100，在计数百万级数据时误差也在 1%–6%。要精确去重就别用 cardinality —— 改用 composite + 客户端去重，或换用别的手段。

高基数 string 字段上，预存 hash 会更快（mapper-murmur3 插件或客户端算好），因为省掉每次聚合的哈希计算。

四、terms 聚合：截断与误差

terms 是分片级局部采样再归并，不是全局 GROUP BY。这是所有误差的根源。

参数 默认值 含义
size 10 返回的桶数量上限
shard_size size * 1.5 + 10 每个分片取回的候选桶数
show_term_doc_count_error false 开启后才返回 doc_count_error_upper_bound

响应里两个字段必须看懂：

字段 含义
doc_count_error_upper_bound 各分片上未能进入 shard_size 的最大桶大小之和，即桶计数的误差上界
sum_other_doc_count 没进入 top size 的文档总数

⚠️ doc_count_error_upper_bound 只在按 _count 降序排序时才有意义。按词项值排序时没有误差；按子聚合排序或按 _count 升序排序时**无法计算，返回 -1**。

排序方式 是否安全
_count 降序（默认） ✅ 误差有界且可报告
_key 升序 / 降序 ✅ 完全准确
子聚合 max 降序 ✅
子聚合 min 升序 ✅
子聚合其它指标 / 方向 ❌ 排序可能错
_count 升序 ❌ 无界误差，官方强烈不建议，找稀有词项用 rare_terms

⚠️ 加大 shard_size 比加大 size 便宜得多，且更能修正各分片分布不均导致的 top 项错位。约束：shard_size 不能小于 size，小于时会被**自动重置为 size**。

⚠️ 唯一值非常多、又要全量取桶时，不要靠无限加大 size —— 会撞 search.max_buckets（默认 65536）。用 composite 聚合分页拉取：

五、分片数怎么影响聚合

协调节点要把每个分片的聚合结果收上来归并。分片越多：

影响 方向
分片级聚合并行度 先升后降
协调节点归并开销 单调上升
terms 误差 上升（局部 top 更不完整）
每分片内存/句柄 上升

⚠️ 经验法则：分片数尽量少，单分片几十 GB 量级通常没问题。分片过多（几百上千）会让聚合的归并阶段成为瓶颈，且 doc_count_error_upper_bound 明显变大。

⚠️ 查询时可以用 preference 或路由把请求固定到少量分片，减少归并规模。日志类场景用 _routing 按天/租户分区，比无脑加分片有效。

六、mapping 优化：三个开关

开关 关掉后失去 适用场景
index: false 不能检索（倒排索引不建） 只用于展示、排序、聚合的字段
doc_values: false 不能排序 / 聚合 / 脚本取值 只用于检索的字段
norms: false 失去字段长度归一化（评分变粗） 不参与相关性打分的字段
字段类型 norms 默认
text true
keyword false

⚠️ norms 每个文档每个字段约占 1 字节。几亿文档 × 十几个不需要评分的 text 字段，就是几十 GB。不需要评分的 text 字段关掉 norms。

⚠️ index_options: "docs" 只存文档号，不存词频和位置 —— 省磁盘，但失去短语查询能力（match_phrase 会失效）。别在需要短语匹配的字段上开。

⚠️ 完全不需要检索的结构化字段，用 "enabled": false 整个跳过解析和索引，比逐个设 index: false 更彻底。

七、写入吞吐：refresh_interval 与 _bulk

refresh 会把内存缓冲区的数据生成新的 Lucene segment 并打开以供搜索。每 refresh 一次就多一个小 segment，频繁 refresh 是写入吞吐的头号杀手。

值 行为
1s Elastic Stack 默认
-1 禁用自动 refresh
30s / 60s 批量导入常用
写入 API 的 refresh 参数 含义
refresh=false 默认，写完即返回，不等可见
refresh=wait_for 等到下次 refresh 完成再返回
refresh=true 立即 refresh 再返回（最慢，别在批量里用）

⚠️ 有隐式优化：如果没有显式设置 refresh_interval，分片在 index.search.idle.after（默认 30s）内没有收到搜索请求时不接收后台 refresh，只在被搜索时才刷。但一旦你显式写了这个设置（哪怕写的就是 1s），这个优化就失效。

_bulk 的批大小没有官方默认值，是客户端定的。经验区间：

维度 经验值
单批条数 1000 – 5000
单批体积 5 – 15 MB
并发写入线程 单节点 2 – 4 个足够，再多只会排队

⚠️ _bulk 的 body 必须以换行符结尾，否则最后一条会被丢弃（很多客户端库已经帮你处理了，手拼 JSON 时要小心）。

⚠️ _bulk 的 HTTP 状态码是 200，即使里面有文档失败。必须逐条检查响应体的 errors 字段和每条的 status，否则会静默丢数据。

八、查询缓存：两个独立的缓存

缓存 作用范围 命中条件 默认大小
Node query cache 整个节点 filter context 的子句 堆的 10%，最多 10000 条
Shard request cache 分片级 请求 size=0 的聚合 / 计数，且无 now 等非确定性条件 堆的 1%

⚠️ 只有 filter 上下文的子句进 query cache，must / should 不算分不算缓存。这就是「不做相关性判断的条件全放 filter」的第二个收益。

⚠️ request cache 只对 size: 0 的请求生效。一旦带上 size: >0 或者用了 now、Math.random() 这类非确定性条件，缓存直接不命中。

看缓存命中情况：

指标 含义
query_cache.hit_count / miss_count 命中率
query_cache.evictions 被挤出，说明缓存太小或查询太多样
request_cache.memory_size_in_bytes 占用

⚠️ 段合并（merge）会使该段相关的缓存全部失效。写入量大的索引上 query cache 命中率天然偏低，别把它当救命稻草。

常见坑清单

  • 用 from + size 翻深页，撞上 max_result_window（默认 10000）
  • 靠调大 max_result_window 解决深分页，内存开销随之线性上升
  • search_after 的 sort 里没加全局唯一的 tiebreaker，跨页漏数据或重复
  • 翻页期间发生 refresh，结果顺序变化却不配 PIT
  • 用 scroll 做用户侧实时分页
  • scroll 用完不清理，搜索上下文堆积、旧 segment 无法删除
  • 以为 cardinality 是精确去重
  • 无脑把 precision_threshold 调到 40000，忽略按分片 × 聚合项相乘的内存开销
  • 以为 terms 聚合是全局精确的 GROUP BY
  • terms 里只加大 size 不加大 shard_size，还奇怪 top 项不对
  • 把 shard_size 设得比 size 小，被静默重置为 size
  • 用 _count 升序排序找稀有项（误差无界），该用 rare_terms
  • 唯一值很多却不断加大 size，撞 search.max_buckets（默认 65536）
  • 分片数开得过多，聚合归并阶段成瓶颈
  • 给不参与评分的 text 字段保留 norms
  • 在需要 match_phrase 的字段上设 index_options: "docs"
  • 批量导入时保持默认 refresh_interval，甚至用 refresh=true
  • 显式设置了 refresh_interval 却抱怨失去了 search idle 优化
  • _bulk 只看 HTTP 200，不检查响应体里的 errors
  • 把该进 filter 的条件写进 must，白丢 query cache 命中
