开场：容器只有三个需要关心的问题

  1. 怎么跑起来 —— docker run 参数太长就用 Compose
  2. 怎么互相通信 —— 网络与 DNS
  3. 数据放哪 —— 数据卷，别放容器里

一、docker run 的参数长什么样

参数一多就该换 Compose 了 —— 把命令行参数写成声明式文件。

二、Compose

compose.yaml

文件名现在推荐 compose.yaml（旧版是 docker-compose.yml，仍然兼容）。

常用命令

命令 作用
docker compose up -d 后台启动全部服务
docker compose up -d --build 重新构建镜像再启动
docker compose ps 看服务状态
docker compose logs -f web 跟踪某个服务日志
docker compose exec web sh 进某个服务的容器
docker compose down 停止并删除容器、网络
docker compose down -v 连数据卷一起删（危险）
docker compose config 校验并展开配置（排查变量替换问题很好用）

⚠️ docker compose down -v 会删掉命名卷，数据库数据一起没。确认清楚再敲。

ports 与 expose

只给需要被外部访问的服务写 ports。 数据库不需要 ports，同一网络里的应用用服务名就能连。

环境变量与 secrets

⚠️ 不要把密码写在 compose.yaml 里提交到仓库。 用 env_file 或 secrets，并把对应文件写进 .gitignore。

三、网络

默认行为

Compose 会为项目创建一个默认网络，所有服务都接进去。服务名就是主机名，可以直接 ping 通：

这就是为什么连接串写 postgres://db:5432/mydb 而不是 localhost。

四种网络驱动

驱动 用途
bridge 默认，单机内容器互通
host 直接用宿主机网络栈，无隔离（Linux 有效）
none 无网络
overlay 跨多台宿主机（Swarm / 集群）

一个高频困惑

从哪访问 连什么地址
宿主机上的进程 → 容器 localhost:8080（映射后的端口）
容器 A → 容器 B db:5432（服务名 + 容器内端口）
容器 → 宿主机 host.docker.internal（Docker Desktop）

⚠️ 容器里写 localhost 指的是容器自己，不是宿主机。这是新手最常见的连接失败原因。

四、数据卷

三种挂载方式

类型 写法 说明
命名卷 pgdata:/var/lib/postgresql/data Docker 管理，存数据推荐
绑定挂载 ./src:/app/src 挂宿主机目录，开发时同步代码用
匿名卷 /var/lib/postgresql/data 不推荐，名字随机难管理

命名卷 vs 绑定挂载

命名卷 绑定挂载
存储位置 Docker 管理（Linux 在 /var/lib/docker/volumes） 你指定的宿主机路径
性能 好 在 macOS / Windows 上较慢（要走文件同步）
适合 数据库数据、需要持久化的业务数据 开发时挂源码、配置文件
备份 docker run --rm -v pgdata:/data alpine tar czf - /data 直接复制目录

⚠️ macOS / Windows 上不要用绑定挂载跑数据库，I/O 性能会差很多倍。用命名卷。

五、几个实战建议

restart 策略

值 行为
no 不重启（默认）
on-failure 非 0 退出码才重启
always 总是重启（包括手动停掉后重启宿主机）
unless-stopped 总是重启，但你手动 stop 的不会（推荐）

资源限制

健康检查写进 Compose

start_period 很关键。没有它，应用启动慢的容器会被反复判定为不健康。

常见坑清单

  • 容器里用 localhost 连另一个容器（应该用服务名）
  • 只写 depends_on 就以为依赖已就绪（它不管健康状态）
  • 数据库不用数据卷，docker compose down 后数据全丢
  • 在 macOS / Windows 上用绑定挂载跑数据库，I/O 慢到怀疑人生
  • 密码写在 compose.yaml 里提交进仓库
  • 给数据库也写 ports，把端口暴露到公网
  • 用 docker compose down -v 顺手清环境，把数据卷一起删了
  • 健康检查没配 start_period，启动慢的服务被反复重启
  • 容器里以 root 运行应用，出问题影响面更大
  • 忘了 restart 策略，宿主机重启后服务不会自动起来
