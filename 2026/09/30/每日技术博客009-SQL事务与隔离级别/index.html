开场：事务解决的是「一半成功」

转账要扣 A 加 B，中间挂了就会丢钱。事务就是把这组操作绑成一个原子单元。

一、ACID 各自靠什么实现

特性 含义 实现手段
A 原子性 要么全成，要么全不成 undo log（回滚日志）
C 一致性 约束不被破坏 由 A、I、D 共同保证
I 隔离性 并发事务互不干扰 锁 + MVCC
D 持久性 提交后不丢 redo log（重做日志）+ WAL

一致性是目的，A、I、D 是手段。 这条常被混淆。

WAL：为什么先写日志再写数据

直接改数据页的话，一次事务要随机写多个磁盘位置。WAL（Write-Ahead Logging）的做法是：

崩溃恢复时，用 redo log 重放已提交的事务，用 undo log 回滚未提交的。这是数据库能既快又可靠的核心机制。

二、四种隔离级别

隔离级别 脏读 不可重复读 幻读
READ UNCOMMITTED ❌ 会 ❌ 会 ❌ 会
READ COMMITTED ✅ 防住 ❌ 会 ❌ 会
REPEATABLE READ ✅ ✅ 防住 ⚠️ 视实现
SERIALIZABLE ✅ ✅ ✅ 防住

三个问题的定义

问题 现象
脏读 读到了另一个事务未提交的修改，对方回滚后你读到的是假数据
不可重复读 同一事务内两次读同一行，值不一样（别人改了/删了）
幻读 同一事务内两次执行同样的范围查询，行数不一样（别人插入了）

不可重复读 vs 幻读：前者是「同一行的值变了」，后者是「多出或少了几行」。要防幻读，光锁行不够，得锁范围（间隙锁）。

各数据库的默认级别

数据库 默认级别
MySQL（InnoDB） REPEATABLE READ
PostgreSQL READ COMMITTED
Oracle READ COMMITTED
SQL Server READ COMMITTED

⚠️ MySQL 和 PostgreSQL 默认级别不同，同一套代码迁库时行为可能不一样。

三、MVCC：读不加锁的关键

MVCC（多版本并发控制）让读操作不需要加锁，靠的是保存数据的多个版本。

实现要点

每行记录带上隐藏字段：

字段 含义
DB_TRX_ID 最后一次修改该行的事务 id
DB_ROLL_PTR 指向 undo log 中该行的上一个版本

读取时，数据库根据当前事务能看到的版本范围，顺着版本链找到该看的那个版本。

快照读 vs 当前读

语句 行为
快照读 普通 SELECT 读 MVCC 版本，不加锁
当前读 SELECT ... FOR UPDATE、UPDATE、DELETE、INSERT 读最新版本，加锁

⚠️ 在 REPEATABLE READ 下，SELECT ... FOR UPDATE 是当前读，能看到别的事务已提交的最新值。 所以「先 SELECT 判断再 UPDATE」在并发下不安全，应该直接 UPDATE 或加锁读。

四、锁

按粒度

锁 粒度 说明
表锁 整张表 开销小，并发差
行锁 单行 开销大，并发好
间隙锁（Gap Lock） 索引区间 InnoDB 在 RR 下用它防幻读
临键锁（Next-Key Lock） 行 + 前面的间隙 InnoDB 行锁的默认形式

按模式

锁 含义 兼容性
共享锁（S） 读锁 多个 S 可共存
排他锁（X） 写锁 与任何锁互斥

死锁不是 bug，是并发系统的正常现象。应用层要能处理这个错误。

减少死锁的做法

做法 说明
统一加锁顺序 所有事务都按同一顺序访问资源（如按 id 升序）
缩短事务 事务里不要做网络请求、不要等用户输入
给条件列加索引 避免锁范围扩大
降低隔离级别 RC 下没有间隙锁，死锁概率更低
用 SELECT ... FOR UPDATE 显式加锁 在事务开头就锁定所需行，避免中途升级

六、应用层要注意的

事务里不要做慢操作

事务应该只包含必要的数据库操作，外部调用放到事务外。

乐观锁 vs 悲观锁

悲观锁 乐观锁
做法 SELECT ... FOR UPDATE 先锁住 更新时校验版本号
适合 冲突频繁、写多 冲突少、读多
代价 锁等待、可能死锁 失败要重试

用「条件更新」避免竞态

常见坑清单

  • 以为 MySQL 和 PostgreSQL 默认隔离级别一样
  • 用「先 SELECT 判断、再 UPDATE」处理库存 / 余额，并发下超卖
  • UPDATE 的 WHERE 列没有索引，锁范围扩大到整表
  • 事务里发 HTTP 请求 / 等用户输入，长时间持锁
  • 把死锁当成 bug，应用层没有重试逻辑
  • 以为 SELECT 一定不加锁（FOR UPDATE 是当前读且加锁）
  • 在 REPEATABLE READ 下依赖快照读做「检查再写入」
  • 大事务一次性更新几十万行，产生大量 undo log 且阻塞并发
  • 用 SERIALIZABLE 解决所有并发问题，性能急剧下降
  • 生产环境不监控锁等待，出问题只能靠猜
