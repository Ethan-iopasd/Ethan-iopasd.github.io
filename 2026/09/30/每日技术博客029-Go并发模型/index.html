开场：Go 并发的三条路

不要通过共享内存来通信，而要通过通信来共享内存。

需求 用什么
传数据 / 交接所有权 channel
保护一小段临界区（计数器、map） sync.Mutex / atomic
等待一批任务结束 sync.WaitGroup
取消、超时、跨层传递请求域数据 context

这四样是互补的，不是替代关系。 只有 channel 的代码和只有锁的代码一样难维护。

一、goroutine 与 GMP 调度器

go f() 启动一个 goroutine。它不是 OS 线程，初始栈只有几 KB，按需增长。

字母 名字 是什么
G goroutine 用户态协程，有栈、有状态，由运行时调度
M machine OS 线程，真正执行代码的载体
P processor 逻辑处理器，持有可运行 G 的本地队列，数量 = GOMAXPROCS

同时执行 Go 代码的 M 数量上限 = P 的数量。 所以 GOMAXPROCS 决定的是并行度，不是并发度。

⚠️ Go 1.25 起，Linux 上 GOMAXPROCS 默认会考虑 cgroup CPU 限额。 在此之前（Go 1.5 到 1.24）它一直等于宿主机逻辑核数。跑在 K8s 里、给容器设了 cpu limit 的服务，升级后并行度会自动变小 —— 这是行为变化，不是 bug。
⚠️ goroutine 被阻塞在系统调用上时会占住一个 M。运行时会另起一个 M 来继续跑其他 G，所以大量阻塞 syscall 会让线程数上涨，不是无限可用的。

二、channel 的语义

操作 nil channel 已关闭 channel 正常 channel
发送 ch <- v 永久阻塞 panic 阻塞或成功
接收 <-ch 永久阻塞 立即返回零值，ok == false 阻塞或成功
close(ch) panic panic（重复关闭） 关闭成功
len(ch) / cap(ch) 0 / 0 剩余元素数 / 容量 同左

⚠️ 只由发送方 close，永远不要在接收方 close。 接收方不知道还有没有别的发送者，close 会导致发送方 panic。
⚠️ close 的语义是「不会再有新数据了」的广播，不是释放资源。channel 是 GC 管理的，不 close 也不会泄漏内存 —— 泄漏的是卡在它上面的 goroutine。
⚠️ 有缓冲 channel 也不能代替「确认处理完成」。ch <- v 返回只说明数据进了缓冲，不代表被处理。
⚠️ len(ch) 只能用于观测和调试。拿它当「还有多少任务」的同步手段必然有竞态。

三、select

规则：

情况 行为
多个分支同时就绪 随机选一个（不是按书写顺序）
没有任何分支就绪且有 default 立即执行 default
没有任何分支就绪且没有 default 阻塞等待
所有 channel 都是 nil 永久阻塞（select {} 可用来永久挂起 main）

⚠️ for { select { ... } } 里如果有 default 分支，会变成忙循环烧满一个核。要空转就加 time.Sleep，或者干脆不要 default。
⚠️ select 里放 nil channel 分支是有意为之的技巧：把某个分支「关掉」而不重写整个 select。

四、context：取消的传播

构造函数 触发取消的条件
context.WithCancel(parent) 显式调用 cancel() 或 parent 被取消
context.WithTimeout(parent, d) 超过 d 或 parent 被取消
context.WithDeadline(parent, t) 到达时刻 t 或 parent 被取消
context.WithValue(parent, k, v) 不产生取消，只携带数据

用法上的硬规矩：

规则 原因
ctx 作为函数第一个参数，命名 ctx 全生态约定
不要把 ctx 存进 struct 字段 生命周期不匹配，取消时机不可控
不要传 nil ctx 用 context.TODO() 占位
WithCancel / WithTimeout 返回的 cancel 必须 defer 调用 否则父 ctx 会一直持有子 ctx，泄漏
ctx.Err() 区分 context.Canceled 和 context.DeadlineExceeded 决定是重试还是放弃

⚠️ WithValue 只放请求域的元数据（trace id、认证主体），不要拿它当「可选参数」通道。它的 key 必须是非导出类型，否则会跨包撞车。
⚠️ 忘记 cancel() 是最常见的 context 泄漏。 子 ctx 会被父 ctx 的 children 集合引用，直到父 ctx 被取消才释放。go vet 的 lostcancel 检查能抓一部分。

五、sync 原语

原语 用途 备注
WaitGroup 等一组 goroutine 结束 Add 要在 go 之前
Mutex 互斥 不可复制，go vet 会报
RWMutex 读多写少 读锁之间不互斥，但会拖慢写
Once 只执行一次 单例初始化、懒加载
Map 并发安全 map 只在特定场景比 map + Mutex 快
Pool 对象复用，减 GC 压力 存放的对象必须「归还前清零」
Cond 等待条件成立 需要配合 Mutex，容易写错
atomic.Int64 等 无锁计数 Go 1.19+ 的类型化原子操作

⚠️ 循环变量捕获问题：Go 1.22 起 for 循环变量每次迭代都是新的，go func(){ use(v) }() 不再共享变量。但仍然推荐显式传参 —— 代码意图更清楚，也不受 go.mod 里 language version 影响。
⚠️ sync.Map 不是「并发版 map」的通用答案。 官方文档明确说它只适合两类场景：key 写入后基本不再改（读多写少），或多个 goroutine 读写不相交的 key 集合。其他情况 map + RWMutex 更快也更清楚。
⚠️ sync.Pool 里的对象可能被 GC 在任何时刻回收，不能用来保存有状态的连接（要连接池请用 database/sql 或专门的池库）。

goroutine 泄漏的四种典型 —— 这类问题运行时不报错，进程看起来正常，但内存和 goroutine 数会持续上涨：

泄漏形态 代码 修法

忘记 cancel 导致子 goroutine 永等 go worker(ctx) 但从不 cancel defer cancel()

检测手段：

⚠️ time.Sleep 之后断言是脆的。 生产项目用 goleak，它会在测试结束时扫描所有 goroutine 的栈，把泄漏点直接打出来。
⚠️ HTTP handler 里起的 goroutine **必须绑定 r.Context()**。客户端断开后 r.Context() 会被取消，这是免费的退出信号。

七、-race 检测数据竞争

-race 的边界：

能做到 做不到
报告实际发生的读写竞争，附两条完整调用栈 报告潜在竞争（没被执行到的路径不会报）
报告 channel / mutex 的 happens-before 违例 替代正确的并发设计
在 CI 里当门禁 直接用于生产（内存和 CPU 开销都很大）

⚠️ -race 只在竞争真的发生时报错。 你的测试没覆盖到并发路径，它就一句话都不说 —— 这经常被误解为「没有数据竞争」。
⚠️ 默认不开启 -race 构建时，//go:build race 标签的代码不会参与编译，别用它做业务逻辑分支。
⚠️ 开了 -race 的程序内存占用通常是数倍增长。CI 上跑并发测试给足内存，否则会 OOM 而不是报错。

常见坑清单

  • 在接收方 close(ch)，导致发送方 panic
  • 重复 close 同一个 channel
  • nil channel 上做收发，永久阻塞
  • WaitGroup.Add 写在 go 里面（可能在 Wait 之后才执行）
  • 忘记 wg.Done()，Wait 永久阻塞
  • context.WithCancel 的 cancel 没有 defer 调用
  • 把 context.Context 存进 struct 字段
  • 用 context.WithValue 传业务参数
  • 向无人接收的 channel 发送，goroutine 永久泄漏
  • for { select { ... default: } } 变成忙循环烧 CPU
  • 认为 sync.Map 在所有场景都比 map + Mutex 快
  • 测试没覆盖并发路径，就认为 -race 通过等于没有数据竞争
