开场：排查顺序比工具重要

慢查询排查是三步固定动作，顺序错了就是白干：

  1. 确认是不是数据库慢 —— 网络、应用序列化、N+1 查询都会伪装成「SQL 慢」
  2. 看扫描行数，不看执行时间 —— rows_examined 远大于 rows_sent 才是 SQL 本身的问题
  3. 最后才看执行计划 —— 定位到具体语句之后，再 EXPLAIN

⚠️ 直接对线上语句跑 EXPLAIN 然后猜优化方案，是效率最低的做法。绝大多数结论在第二步就已经出来了。

一、先把慢查询日志打开

MySQL 的慢查询日志默认关闭，long_query_time 默认 10 秒 —— 生产环境这个阈值几乎抓不到任何东西。

参数 默认值 说明
slow_query_log OFF 总开关，默认禁用
long_query_time 10 单位秒，微秒精度，最小 0
slow_query_log_file <host_name>-slow.log 默认在数据目录
log_queries_not_using_indexes OFF 未走索引的查询也记录
log_slow_admin_statements OFF 记录慢的 ALTER / OPTIMIZE 等管理语句
log_slow_extra OFF 输出额外字段（线程 id、字节数等），仅对 FILE 输出生效
min_examined_row_limit 0 检查行数低于该值不记录
log_throttle_queries_not_using_indexes 0 对上面那个参数限流，0 表示不限
log_output FILE 必须含 FILE 才写文件，为 NONE 时什么都不写

⚠️ 两个坑：

  1. long_query_time 是 session 变量，已存在的连接不会立刻生效，新连接才用新值。
  2. 开了 log_queries_not_using_indexes 之后日志量可能爆炸（连只有两行的小表也会被记），必须配 log_throttle_queries_not_using_indexes。

锁获取时间不计入执行时间。语句执行完毕、锁释放后才写日志，所以日志顺序 ≠ 执行顺序。

二、把日志汇总成排名

单条日志没有意义，要看的是「哪一类语句反复出现」。

-s 的取值：

值 含义
t / at 按总耗时 / 平均耗时（**默认 at**）
l / al 按总锁时间 / 平均锁时间
r / ar 按总返回行数 / 平均返回行数
c 按出现次数

其他常用：-a 不做数字抽象（默认会把数字抽象成 N、字符串抽象成 'S'）、-l 不扣除锁时间、-r 反向排序。

维度 mysqldumpslow pt-query-digest
依赖 MySQL 自带 Percona Toolkit，需另装
输出 纯文本 报表式，含响应时间分布、EXPLAIN 采样
排序维度 时间 / 锁 / 行数 / 次数 同上，另加方差、95 分位
适用 快速看一眼 决定「先改哪一类语句」

重点看 State 列，它直接说明语句卡在哪：

State 含义
Sending data 正在读数据并回传，扫描行数过多的最常见外在表现
Sorting result 正在排序，通常对应 Using filesort
Copying to tmp table 建临时表，常见于 GROUP BY / DISTINCT / 大 JOIN
Waiting for table metadata lock 等 MDL，多半被长事务或未完成的 ALTER 堵住
Waiting for ... lock 等行锁，需要找阻塞源
update / statistics 正在更新数据 / 收集统计信息

四、performance_schema 与 sys 库

performance_schema 按语句指纹（digest）聚合统计，不依赖慢查询日志，默认开启。

sys 库把这些包装成可直接读的视图：

视图 用途
sys.statement_analysis 全局语句排行，默认按总延迟排
sys.statements_with_full_table_scans 全表扫描的语句排行
sys.statements_with_sorting 有文件排序的语句
sys.statements_with_temp_tables 用了临时表的语句
sys.statements_with_runtimes_in_95th_percentile 长尾语句
sys.schema_table_statistics 按表看 I/O、锁等待、扫描行数
sys.schema_tables_with_full_table_scans 哪些表被全表扫得最多
sys.schema_unused_indexes 从未被用过的索引
sys.schema_redundant_indexes 冗余索引
sys.innodb_lock_waits 当前锁等待关系，直接给出阻塞者

⚠️ performance_schema 的统计重启即清零，且受 performance_schema_digests_size 限制，超出上限后新 digest 不再被记录。要看趋势必须定期落库。

五、PostgreSQL：pg_stat_statements

PostgreSQL 没有内置慢查询日志，靠 log_min_duration_statement 打日志；但**统计聚合的标准答案是 pg_stat_statements**。

关键列：

列 含义
queryid 规范化语句的哈希，比文本更稳定
query 代表性语句文本，常量已归一化成 $1
calls 执行次数
total_exec_time / mean_exec_time 总 / 平均执行时间（毫秒）
rows 返回或影响的总行数
shared_blks_hit / shared_blks_read 命中 / 读盘块数，比值低说明 Buffer 不够或语句本身扫太多

参数：

参数 默认值 说明
pg_stat_statements.max 5000 跟踪的语句数上限，超出丢弃执行最少的
pg_stat_statements.track top top 只记顶层语句，all 连函数内嵌套语句一起记
pg_stat_statements.track_planning off 是否统计规划耗时，开启有显著开销
pg_stat_statements.track_utility on 是否跟踪非 DML 的工具命令

六、排查顺序：先看扫描行数，再看执行计划

观察到的现象 结论 改法
rows_examined >> rows_sent，type = ALL 没走索引，或索引选择性差 建联合索引 / 改查询条件
rows_examined ≈ rows_sent，但耗时长 不是扫描问题，是锁等待或 I/O 看 Lock_time、sys.innodb_lock_waits
Lock_time 高 等行锁 / MDL 缩短事务、找长事务、拆大批量 UPDATE
Extra 含 Using filesort 排序没走索引 把排序列并入联合索引
Extra 含 Using temporary 用了临时表 优化 GROUP BY，避免大 DISTINCT
type = index 且 rows 很大 扫了整个索引 补更精确的索引
预估行数与实际差几个数量级 统计信息过期 ANALYZE TABLE

EXPLAIN ANALYZE 怎么读

  • 会真的执行语句，输出里同时有 actual time / rows（实际）和 cost / rows（预估）
  • 只看两个数字：预估行数 vs 实际行数、实际耗时集中在哪一层
  • 嵌套节点的 actual time 里，first row 的值包含子节点耗时，要一层层看增量

⚠️ 对写操作跑 EXPLAIN ANALYZE 会改数据。放进事务里执行再回滚：

常见坑清单

  • 慢查询日志默认关闭，生产环境从没开过
  • long_query_time 保持默认 10 秒，什么都抓不到
  • 改完 long_query_time 发现老连接没生效（session 变量）
  • 开了 log_queries_not_using_indexes 没配限流，日志把磁盘写满
  • log_output = NONE 时开了慢查询日志却没有输出
  • 只看单条日志，不做 mysqldumpslow / pt-query-digest 聚合
  • 只按平均耗时排序，漏掉「单条不慢但调用百万次」的语句
  • 用 SHOW FULL PROCESSLIST 试图找已经结束的慢查询
  • 用 SHOW PROCESSLIST 而不是 SHOW FULL PROCESSLIST，看不到完整 SQL
  • 拿 Seconds_Behind_Master 式的时间指标判断慢，忽略扫描行数
  • 对写操作直接跑 EXPLAIN ANALYZE，把数据改了
  • 看到 Using filesort 就加索引，没先确认返回行数
