四 分库分表与读写分离 本篇

开场：分片是最后手段，不是起点

扩容的优先级从上到下，能停在上面一层就不要往下走：

水平分片一旦落地，跨片 JOIN、分布式事务、全局 ID、扩容迁移会同时变成长期成本。先确认前面几层都做完了。

手段 解决什么 代价
索引优化 单表查询慢 几乎为零，先做
冷数据归档 单表行数膨胀 需要业务定义「冷」的边界
垂直拆分 单库表太多 / 单表列太多 跨库 JOIN 消失，要拆事务
读写分离 读 QPS 压力 主从延迟导致读不一致
水平分片 单表写入 / 存储到顶 跨片查询、全局 ID、迁移

⚠️ 「单表多少行必须分」没有标准答案。取决于单行大小、索引命中率、Buffer Pool 能否装下热数据。500 万行的高频小表，可能比 5000 万行的归档表更值得分片。

一、垂直拆分

两个方向，建议先拆表再拆库。

方向 做什么 典型信号
拆表（拆列） 把大字段 / 低频字段挪到扩展表 单行超过几 KB，SELECT * 拖慢一切
拆库（业务域） 按限界上下文拆成独立库 单库连接数打满、DDL 互相影响

⚠️ 拆库之后就没有跨库 JOIN 了。要么在应用层拼装，要么冗余字段。这一步想不清楚，后面会反复返工。

二、水平分片：分片键怎么选

分片键（sharding key）决定数据落在哪个分片，选错等于每次查询都打全部分片。

候选分片键 优点 缺点
用户 ID 同一用户数据全在一个分片，天然隔离 大客户造成数据倾斜
订单 ID 分布均匀 查「某用户的所有订单」要跨片
时间 范围查询友好、归档简单 最新数据全在一个分片 → 写热点
商户 ID 同商户数据聚合 头部商户倾斜严重
组合键（用户 ID + 时间） 兼顾均匀与聚合 查询必须同时带上两个维度

三条判断原则：

  1. 高频查询条件 —— 最常出现在 WHERE 里的维度优先
  2. 分布均匀 —— 避开 status、type 这类低基数列
  3. 尽量单分片命中 —— 一个请求只打一个分片，这是最重要的目标

⚠️ 分片键一旦选定基本改不动（要全量重分布）。上线前用真实数据分布跑一遍倾斜度。

三、范围分片 vs 哈希分片

维度 范围分片 哈希分片
分布均匀度 差，易倾斜 好
范围查询 ✅ 单分片 ❌ 打全部分片
写热点 容易出现（最新区间） 无
扩容 只需拆一个分片 通常要重分布
归档 简单，直接删旧分片 困难
典型场景 时序数据、日志、账单 用户中心、订单

哈希分片的关键技巧是预分片：一开始就切成远超当前需要的逻辑分片，再把这些逻辑分片映射到少量物理库上。

⚠️ hash(key) % N 这种取模分片，N 一变所有数据都要迁移。要么用预分片，要么用一致性哈希。

四、跨片查询与聚合的代价

分片之后，「按非分片键查询」和「聚合统计」都会变贵。

操作 分片后
按分片键等值查 ✅ 单分片，和单库一样快
按分片键范围查 范围分片 ✅ / 哈希分片 ❌ 全片扫描
按非分片键查 ❌ 广播到所有分片，再内存归并
COUNT / SUM / AVG ❌ 各分片算一遍，再二次聚合
ORDER BY + LIMIT ❌ 各分片各取前 N，再归并
深翻页 ❌❌ 每片都要扫到 offset + limit
跨片 JOIN ❌ 基本放弃

⚠️ 深翻页在分片下会放大 N 倍。要么改成游标分页（WHERE created_at < ?），要么把列表数据同步到 ES 里查。

五、全局唯一 ID

分片之后自增主键不再全局唯一，需要一个独立的发号方案。

方案 有序性 性能 缺点
UUID ❌ 随机 本地生成，无网络 占空间、索引页分裂严重
数据库自增 + 步长 ✅ 简单 扩容要改步长，单点
号段模式 ✅ 一次取一批，吞吐高 服务重启会浪费号段
雪花算法（Snowflake） ✅ 趋势递增 本地生成，无依赖 依赖机器时钟

雪花算法的经典位布局（64 位）：

字段 位数 容量
时间戳 41 约 69 年
机器 ID 10 最多 1024 个节点
序列号 12 同一毫秒最多 4096 个 ID

⚠️ 雪花算法的唯一死穴是时钟回拨。回拨几毫秒就可能生成重复 ID。生成器里必须检测：回拨小则等待，回拨大则直接拒绝服务，绝不能硬生成。

六、读写分离与主从延迟

读写分离把读流量分给从库，代价是从库可能落后于主库。「写后读」不一致是最高频的线上问题：

解法 做法 适用
强制走主库 写后一段时间内的读打到主库 单条记录详情页
会话粘滞 同一会话内写后读都走主库 交互式流程
位点校验 记录写入的 binlog 位点，从库追上才读 强一致要求
半同步复制 至少一个从库确认收到才返回 降低延迟概率，不消除
延迟感知路由 监控从库延迟，超阈值自动摘除 兜底

⚠️ 主从延迟不是「配置问题」，是物理限制。大事务、DDL、从库单线程回放都会放大它。延迟超阈值时，正确做法是把从库摘出读池，不是等它追上。

七、中间件 vs 应用层

方案 定位 优点 缺点
ShardingSphere-JDBC 客户端 SDK，跑在应用进程内 无额外网络跳数 和语言/框架绑定，升级要改依赖
ShardingSphere-Proxy 独立代理进程，兼容 MySQL/PG 协议 应用零改动，语言无关 多一跳网络，代理是瓶颈点
Vitess 面向 MySQL 的集群方案 支持在线 resharding 部署运维复杂度高
应用层自研 自己写路由和归并 完全可控 工作量最大，最容易写错

⚠️ 中间件能解决路由和归并，但解决不了「分片键选错」和「跨片事务」。这两个必须在设计阶段定下来。

八、扩容时的数据迁移

标准流程是双写 + 增量同步 + 校验 + 切换，不要指望一次停机搞定。

步骤 做什么 关键点
1. 双写 新写入同时写旧分片和新分片 写入路径要幂等
2. 存量迁移 把旧数据按新规则搬到新分片 分批 + 限速，别打满 I/O
3. 增量追平 消费 binlog 补齐迁移期间的变更 用位点校验是否追平
4. 数据校验 对比新旧分片的行数与校验和 按分片键抽样全量比对
5. 读切换 灰度切读流量到新分片 出问题能立刻切回
6. 停双写 确认稳定后只写新分片 旧数据保留一段时间

⚠️ 迁移期间新旧分片的一致性由业务代码保证，数据库不会帮你。双写的任一侧失败必须有补偿，否则迁移完才发现数据对不上。

常见坑清单

  • 单表刚过千万就急着分片，索引还没优化
  • 分片键选了低基数列（status、type），数据严重倾斜
  • 用 hash(key) % N 取模，扩容时全量迁移
  • 分片键选完才发现最频繁的查询用不上它
  • 按时间分片，最新分片成为写热点
  • 分片后仍按非分片键查询，每次广播全部分片
  • 深翻页在分片下放大 N 倍
  • 用 UUID 做主键，索引页分裂、写入放大
  • 雪花算法没处理时钟回拨
  • 读写分离后没处理「写后读」，用户看不到自己刚提交的数据
  • 从库延迟很高还留在读池里
  • 迁移只做存量同步，没做增量追平和数据校验
