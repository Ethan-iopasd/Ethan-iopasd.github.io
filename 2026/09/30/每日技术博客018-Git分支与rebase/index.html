开场：merge 保留历史，rebase 重写历史

一句话区分：

  • **merge**：新建一个合并提交，两边的历史都保留
  • rebase：把你的提交「摘下来」重新贴在目标分支后面，历史变成一条直线

关键差别：rebase 会改变提交的 SHA。 所以有一条铁律：

⚠️ 不要 rebase 已经推送到共享分支的提交。 别人基于旧提交做的工作会全部对不上。

一、Git 的三个区域

命令 影响范围
git add 工作区 → 暂存区
git commit 暂存区 → 本地仓库
git push 本地 → 远程
git fetch 远程 → 本地（不动工作区）
git pull fetch + merge（或 rebase）
git restore 撤销工作区 / 暂存区的改动

二、分支模型

常见的几种

模型 分支 适合
主干开发 只有 main + 短命特性分支 持续交付、团队成熟
Git Flow main / develop / feature / release / hotfix 有明确版本发布节奏
GitHub Flow main + PR 分支 大多数 Web 项目

现在主流是「主干开发 + 短命分支」：特性分支存活不超过一两天，频繁合并回主干。

强制保留合并提交

--no-ff 的价值：让每个特性在历史里都有一个明确的合并点，方便日后回滚整个特性。

选项 效果
默认 能快进就快进
--no-ff 总是产生合并提交
--ff-only 不能快进就报错（保证线性历史）
--squash 把分支上所有提交压成一个，需要再手动 commit

⚠️ **--squash 之后必须再 git commit**，否则改动只在暂存区。
而且 squash 后原来的提交历史丢失，git branch --merged 不会认为该分支已合并。

四、rebase 的正确用法

场景一：把主分支的最新改动同步到自己的分支

效果：把自己的提交重新贴在 origin/main 最新提交之后，历史是一条直线。

场景二：整理自己的提交历史

打开编辑器：

指令 作用
pick 保留
reword 保留但改提交信息
edit 停下来修改内容
squash 合并到上一个提交，保留两条信息
fixup 合并到上一个提交，丢弃本条信息
drop 删除该提交
调整顺序 直接移动行

⚠️ rebase -i 只应该用在「还没推送」或「只有你自己在用」的分支上。

冲突怎么处理

⚠️ rebase 冲突可能反复出现同一个地方 —— 因为每个提交都要重新应用一次。
如果同一个冲突反复出现很多次，考虑改用 merge。

rerere：记住冲突解决方案

开启后，Git 会记住你解决过的冲突，下次遇到同样的冲突自动解决。反复 rebase 时非常省事。

五、merge 还是 rebase

merge rebase
历史形态 有分叉，有合并提交 一条直线
是否改 SHA ❌ ✅
冲突处理 一次解决全部 每个提交都可能冲突
适合 共享分支、多人协作 个人分支整理、同步主干
危险点 历史较乱 改写已推送的历史

实践建议

场景 用什么
把 main 同步到自己的特性分支 rebase（保持线性）
把特性分支合回 main merge --no-ff（保留特性边界）
提交前整理自己的提交 rebase -i（squash 掉「修笔误」）
已经推送且别人在用 只用 merge

配置 pull 的默认行为

⚠️ 团队里统一 pull 策略很重要，否则历史形态会混乱。这个配置要写进团队规范。

六、几个实用配置

最后一条很实用：默认情况下 Git 会把中文路径显示成 "2025/\345\255\246..."，
设成 false 后正常显示中文。脚本里解析 git diff 输出时更要注意这个
（或者用 git diff -z）。

常见坑清单

  • rebase 了已经推送到共享分支的提交，别人的工作全乱
  • git merge --squash 后忘了再 git commit
  • git pull 默认行为在团队里不统一，历史形态混乱
  • rebase 冲突时慌了直接 --abort，其实只需要 git add + --continue
  • 同一个冲突在 rebase 里反复出现很多次（该改用 merge）
  • 用 git checkout 既切分支又还原文件，误操作丢改动
  • 特性分支存活太久，合并时冲突成灾
  • --no-ff 和默认快进混用，历史形态不一致
  • 脚本解析 git diff 输出时没处理中文路径的八进制转义
  • 没开 rerere，反复解决同一处冲突
