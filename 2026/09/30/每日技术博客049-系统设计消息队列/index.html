开场：MQ 换来的三个能力，都要用一致性去还

能力 说明
解耦 生产者不关心谁消费、有几个消费者
削峰 突发流量先落到队列，下游按自己的速率消费
异步 主流程不等慢操作，缩短响应时间

代价：系统从「强一致」变成「最终一致」，从「同步失败可回滚」变成「必须自己处理重试、幂等、补偿」。引入 MQ 的那一刻，就要开始设计对账。

一、投递语义：现实里只有「至少一次」可用

语义 含义 现实
至多一次 At-most-once 可能丢，不重复 发完不管，性能最好，可靠性最差
至少一次 At-least-once 不丢，可能重复 绝大多数系统的实际语义
恰好一次 Exactly-once 不丢不重 只在特定范围内可做到（见下）

⚠️ 「恰好一次」在跨系统、跨网络的通用场景下不可能实现（需要分布式事务或两阶段提交，代价远超收益）。Kafka 的 EOS 是「Kafka 内部」的恰好一次（消费 + 生产 + 位点提交在同一事务里），一旦你消费后调用了外部 HTTP 接口、写了另一个数据库，语义立刻退化为至少一次。

结论：把「至少一次 + 消费端幂等」当成默认设计，而不是追求恰好一次。

二、消息可能丢在三个地方

环节 丢失原因 防护
生产 网络抖动、Broker 未落盘就 ack、异步发送没处理回调 同步发送 / 检查回调；acks=all；重试
存储 Broker 宕机、单副本、刷盘策略为异步 副本数 ≥ 3、min.insync.replicas ≥ 2、unclean.leader.election=false
消费 先提交位点后处理、处理抛异常被吞掉、位点自动提交 先处理业务，再提交位点；关掉自动提交

⚠️ enable.auto.commit=true（默认值）是丢消息的头号原因。 它按时间间隔自动提交位点，和业务处理进度完全无关 —— 消息还在处理中，位点已经被提交了，进程一崩就永久丢。所有要求不丢的场景都必须关掉自动提交。

⚠️ unclean.leader.election.enable=true 会丢数据。 它允许非 ISR 副本当 leader（为了可用性），代价是那些「没同步到」的消息直接消失。金融类场景必须设为 false（宁可不可用也不丢数据）。

⚠️ acks=1 只等 leader 落盘，leader 挂了、副本还没同步，消息就丢了。 要保证不丢必须 acks=all 且 min.insync.replicas >= 2 且 副本数 ≥ 3。只配 acks=all 而副本数是 1，等于没配。

三、重复消费与幂等

至少一次语义下，重复消费是必然的，触发场景：

  • 消费者处理完，提交位点前进程挂了 → 重启后重新消费
  • 消费超时，Rebalance 把分区转给别人，原消费者其实处理成功了
  • 生产端重试，消息被重复写入
  • Broker 内部重投
幂等方案 实现 适用
唯一索引 业务表加 UNIQUE(业务单号)，重复插入报错并忽略 最简单可靠，首选
去重表 独立表记录已处理的消息 ID 无天然唯一键时用
Redis SETNX SET msgId 1 NX EX 86400 快，但要考虑 Redis 挂了怎么办
状态机 只允许 待支付 → 已支付，重复的 已支付 直接忽略 有状态流转的业务
乐观锁 / 版本号 UPDATE ... WHERE version = ? 更新类操作

⚠️ 去重键要选「业务唯一标识」，不是消息 ID。 生产者重试时消息 ID 会变（新消息），但业务单号不变。用消息 ID 去重挡不住生产端重试造成的重复，这是最常见的幂等设计错误。

⚠️ 幂等键的存储和业务操作必须在同一个事务里。 如果先去重表插一条、再写业务表，中间崩了，就会出现「去重记录在、业务数据没写」的情况 —— 之后重投的消息会被当成重复永久丢弃。要么同一个本地事务，要么用 INSERT ... ON CONFLICT DO NOTHING 把去重和写入合并成一条语句。

⚠️ Redis 去重有个窗口期问题。 EX 86400 意味着 24 小时后的重复消息挡不住。如果消息延迟可能超过这个窗口（如延迟消息、积压重投），去重就失效了。要求强幂等的场景用数据库唯一索引，Redis 只做前置快速过滤。

四、顺序消息

顺序只在一个分区 / 一个队列内成立，全局顺序等于放弃并行。

需求 做法
局部顺序（同一订单） 按 orderId 哈希到固定分区，同一 key 落同一分区
全局顺序 单分区（吞吐直接掉到单机水平）
消费端顺序 单线程消费该分区（或按 key 分发到固定线程）

⚠️ 顺序消息的三个破坏点：① 生产端重试导致乱序（max.in.flight > 1 时后发的消息可能先成功）→ 开 enable.idempotence=true 让 Broker 端排序；② 分区数变化或 Rebalance 导致重新分配；③ 消费端用了线程池并行处理，顺序立刻丢失。第三条最常被忽略。

⚠️ 顺序消息和「不丢」是互斥的优先级选择。 严格顺序要求前一条处理失败时阻塞整个分区（不能跳过），这会带来严重的队头阻塞。大多数业务其实不需要严格顺序 —— 用「状态机 + 幂等」让乱序消息也能正确处理，比强行保序更稳。

五、积压的排查与处理

指标 含义 判断
Consumer Lag 未消费消息数 持续上涨 = 消费能力 < 生产速率
消费 TPS 每秒处理条数 对比生产 TPS
Rebalance 次数 分区重新分配次数 频繁 = 消费者不稳定 / 处理超时
分区消费延迟 单分区落后程度 是否有个别分区特别慢（热点 key）
处理手段 说明
加消费者 上限是分区数，超过分区数的消费者会空闲
加分区 可提升并行度，但会破坏 key 到分区的映射（历史消息和新消息可能落到不同分区）
提高单批处理量 max.poll.records 调大，减少往返
优化消费逻辑 通常瓶颈在消费逻辑里的同步调用（该批量 / 该异步）
临时跳过 用另一个 consumer group 消费到新位置（会丢消息，需业务确认）
降级丢弃 只对非核心消息可用，且必须有日志和补偿

⚠️ 加消费者之前先看分区数。 6 个分区、加到 12 个消费者，多出来的 6 个一直空闲 —— 这个坑每年都有人踩。扩容前先确认分区数够。

⚠️ max.poll.interval.ms 太小会引发 Rebalance 死循环。 如果单批处理耗时超过这个值（默认 5 分钟），消费者会被踢出组，分区转给别人，别人也处理不完又被踢 —— lag 永远追不上，且日志里全是 Rebalance。调大 max.poll.interval.ms 或调小 max.poll.records。

六、延迟消息

实现方式 精度 优缺点
RocketMQ 延迟级别 固定档位 4.x 只有 18 个固定级别（1s 5s 10s 30s 1m 2m 3m 4m 5m 6m 7m 8m 9m 10m 20m 30m 1h 2h），不支持任意时间
RocketMQ 5.0 定时消息 任意时间戳 5.0 起支持指定时间戳，需 Broker 配置
RabbitMQ TTL + DLX 秒级 队列 TTL / 消息 TTL + 死信交换机；同一队列里不同 TTL 会导致队头阻塞
时间轮 / 定时任务扫表 取决于扫描间隔 实现简单，扫表有 DB 压力
Redis ZSET + 轮询 毫秒级 ZADD score=到期时间戳，轮询 ZRANGEBYSCORE 取到期任务

⚠️ RocketMQ 4.x 的 18 个延迟级别是硬编码的，delayLevel 从 1 开始（1 = 1s）。 传 0 或超出 18 会直接报错。需要「30 分钟后」这种非标准间隔时，得取最接近的档位（16 = 30m），或者改用 5.0 的定时消息。

⚠️ RabbitMQ 的「队列 TTL + 死信」有队头阻塞问题：同一队列里，如果先入队的消息 TTL 更长，后面的短 TTL 消息即使到期也不会被投递（队列是 FIFO 的，必须等前面的出队）。解法是每个 TTL 一个队列，或者用 rabbitmq_delayed_message_exchange 插件。

⚠️ 延迟消息的「延迟」不是精确的。 时间轮和扫表都有轮询间隔，实际触发时间会晚于预期。不要用延迟消息做「精确到秒」的业务（如定时开奖），那需要专门的调度系统。

七、事务消息与本地消息表

问题

方案一：RocketMQ 事务消息（半消息 + 回查）

要点 说明
半消息 存在 RMQ_SYS_TRANS_HALF_TOPIC，消费者看不到
回查 Broker 定期回调生产者实现的 checkLocalTransaction
回查次数 超过上限（默认 15 次）后回滚
生产者要求 本地事务必须能被查询（不能只靠内存状态）

方案二：本地消息表（更通用）

方案 优点 缺点
事务消息 框架内建，回查自动化 绑定 RocketMQ；回查有窗口
本地消息表 不依赖 MQ 特性，任何 MQ 都能用 需要自己实现投递线程 + 清理

⚠️ 本地消息表的投递是「至少一次」，下游仍然必须幂等。 别以为用了本地消息表就不用做幂等了 —— 投递成功后标记 SENT 这一步失败，消息就会重发。

⚠️ 事务消息只能保证「本地事务和消息发送」的一致性，不能保证下游处理成功。 下游处理失败依然要靠重试和补偿。事务消息解决的是「消息发不发得出去」，不是「业务最终一致」。

八、最终一致性的兜底：补偿与对账

机制 说明 周期
重试队列 消费失败进重试 topic，指数退避 秒~分钟
死信队列 DLQ 重试 N 次仍失败，人工介入 小时级
定时补偿任务 扫描「中间状态」的记录主动修正 分钟~小时
对账 和第三方/上游系统逐笔比对 T+1 日切
人工工单 兜底 天级

⚠️ 对账必须做，且必须做「差异处理」而不只是「差异告警」。 只有告警没有自动修正，对账就只是把问题延后。对账的输出应该是：差异列表 + 自动补偿动作 + 无法自动处理的进人工队列。

⚠️ 补偿任务必须幂等且可重入。 它会在任何时刻被触发多次，包括并发触发。补偿逻辑不幂等的话，故障会被补偿放大成更大的故障。

⚠️ 状态机的「中间态」必须能超时自愈。 有 PAYING 这种中间态的业务，一定要有「超时未回调就主动查询」的机制。没有自愈的中间态，就是永久卡死的数据。

常见坑清单

  • 追求「恰好一次」，实际上跨系统根本做不到
  • 保留 Kafka 默认的 enable.auto.commit=true，进程崩溃丢消息
  • 配了 acks=all 但副本数是 1（等于没配）
  • 开了 unclean.leader.election，leader 切换时丢数据
  • 先提交位点再处理业务
  • 用消息 ID 做幂等键（生产端重试时 ID 会变）
  • 幂等记录和业务写入不在同一个事务里
  • 只用 Redis 做去重，没考虑 TTL 过期后的重复消息
  • 生产端 max.in.flight > 1 却要求顺序
  • 消费端用线程池并行处理，顺序消息直接失效
  • lag 上涨就加消费者，没看分区数够不够
  • 随意加分区的数量，破坏了 key 到分区的映射
  • max.poll.interval.ms 小于单批处理耗时，导致 Rebalance 死循环
  • RocketMQ 4.x 传了不存在的 delayLevel（只有 1~18）
  • RabbitMQ 同一队列混用不同 TTL，队头阻塞导致延迟不生效
  • 以为用了事务消息就不用做下游幂等和补偿
  • 有中间态但没有超时自愈机制，数据永久卡住
  • 对账只告警不自动处理
