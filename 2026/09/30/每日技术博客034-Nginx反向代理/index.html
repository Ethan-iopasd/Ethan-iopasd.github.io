开场：proxy_pass 的斜杠决定一切

location 匹配到的那段路径，是被替换掉还是原样透传，只取决于 proxy_pass 里有没有写 URI。这就是那个被反复问的「斜杠问题」的答案。

一、正向代理 vs 反向代理

正向代理 反向代理
代表谁 客户端 服务端
客户端知道目标吗 知道，但连不上，让代理去连 不知道，以为代理就是服务端
典型场景 科学上网、公司出口代理 Nginx 暴露后端服务
配置方 客户端 服务端

二、proxy_pass 的 URI 规则

判定依据只有一个：**proxy_pass 后面有没有写路径**。

写法 传递到上游的 URI
proxy_pass http://host;（无 URI） 客户端原始 URI 原样透传
proxy_pass http://host/;（有 URI，是 /） location 匹配的部分被替换成 /
proxy_pass http://host/remote/; location 匹配的部分被替换成 /remote/
proxy_pass http://host$request_uri;（用变量） 按变量展开后的值原样传给上游，替换原始 URI
正则 / 命名 location 里 必须不带 URI

看具体例子：

坑 现象
location /api + proxy_pass http://b/ 拼出 //users，部分后端会把双斜杠当不同路由，404
location /api/ + proxy_pass http://b 原样透传，上游收到 /api/...，如果上游没有 /api 前缀就 404
正则 location 里写了 URI 配置能加载，但 URI 处理行为不符合预期

⚠️ 规则不是「斜杠」，而是「有没有 URI」。 proxy_pass http://backend/ 里的 / 就是一个 URI（根路径），所以触发替换逻辑。

⚠️ **rewrite ... break 之后再 proxy_pass**，proxy_pass 里写的 URI 会被忽略，传的是 rewrite 之后的完整 URI。

⚠️ 用变量的 proxy_pass 不走 upstream 块，也不会在启动时解析域名，需要显式配 resolver，否则报 no resolver defined。

三、必须透传的头

默认情况下，Nginx 转发时会把 Host 改成 proxy_pass 里的主机名，客户端真实 IP 也丢了。后端拿到的全是 127.0.0.1。

头 作用 不透传的后果
Host 后端做虚拟主机 / 生成绝对 URL 后端以为请求来自 backend，重定向跳错域名
X-Real-IP 单个客户端 IP 日志里全是 Nginx 的 IP，限流按 IP 全打到一起
X-Forwarded-For 代理链，逗号分隔 多级代理后拿不到真实来源
X-Forwarded-Proto 原始是 http 还是 https 后端生成 http:// 链接，浏览器报混合内容
X-Forwarded-Host / -Port 原始 Host 和端口 拼出的回调地址不对

X-Forwarded-For 的累加过程：

⚠️ X-Forwarded-For 的第一个值才是客户端 IP，但它可伪造。 只有在你信任的那一层代理之后取，才是可信的。取值用「从右往左数第 N 个」而不是「第一个」。

⚠️ $host 与 $http_host 的区别：$host 是规范化后的小写主机名（不含端口），$http_host 是客户端原样发来的（含端口）。后端要按 Host 分流时用 $host，需要保留端口时用 $http_host。

四、upstream 负载均衡

算法 指令 特点
轮询 默认 依次分发，weight 加权
最少连接 least_conn 给当前连接数最少的节点，长连接场景更均衡
IP 哈希 ip_hash 同一客户端固定落到同一后端（会话粘性）
通用哈希 hash $key [consistent] 自定义键；加 consistent 用一致性哈希，扩缩容时迁移少
随机 random [two] 随机；two 表示随机挑两个再按 least_conn 选一个
server 参数 含义
weight=n 权重，默认 1
max_conns=n 该后端最大并发连接数，超出则不再分发
max_fails=n fail_timeout 内失败多少次算不可用，默认 1
fail_timeout=10s 失败统计窗口 + 标记不可用后的冷却时长，默认 10s
backup 备用节点
down 永久下线（配合 ip_hash 做灰度时有用）
resolve 动态解析域名（配合 resolver）

⚠️ max_fails=0 表示关闭失败统计，即该节点永远不会被标记为不可用。别误以为是「不重试」。

⚠️ ip_hash 与 weight 不能混用出你期望的效果，且节点增减时大量客户端会被重新映射，会话大面积失效。

⚠️ backup 节点平时不接流量，只在所有主节点都不可用时才启用。所以它的代码版本可能很旧。

五、健康检查与 max_fails

Nginx 开源版的「健康检查」是被动的：只有请求失败才会标记节点。

概念 默认值 说明
max_fails 1 窗口内失败次数达到就标记不可用
fail_timeout 10s 既做失败统计窗口，也做不可用冷却时间
proxy_next_upstream error timeout 默认只对连接错误和超时重试
proxy_next_upstream_tries 0 0 表示不限制尝试次数

proxy_next_upstream 的取值：

值 是否默认生效
error / timeout / invalid_header 始终算失败，不写也生效
http_500 / http_502 / http_503 / http_504 / http_429 只有显式写了才重试
http_403 / http_404 永远不会被当成失败
non_idempotent 允许重试 POST 等非幂等请求，谨慎开
off 禁止转发到下一台

⚠️ 重试会放大写入风险。 默认不重试 POST 是有原因的：请求可能已经在后端执行成功了，只是响应超时，重试会写两次。要重试必须保证接口幂等。

⚠️ 开源版没有主动健康检查（health_check 指令属于 Nginx Plus）。想主动探测要么上 Plus，要么用 nginx_upstream_check_module 之类的第三方模块。

六、try_files 与 SPA 兜底

try_files 按顺序尝试，最后一个参数是兜底（不再检查存在性，直接内部重定向或返回）。

⚠️ try_files ... /index.html 会让所有 404 都变成 200。 API 路径不要走这条 location，否则前端拿到一个 HTML 当 JSON 解析。

⚠️ try_files $uri $uri/ /index.html 里的 $uri/ 会尝试目录，如果目录存在但没有 index 文件，会返回 403 而不是兜底。SPA 通常只需要 $uri /index.html。

⚠️ index.html 别配长缓存，否则发版后用户拿到的还是旧 HTML，引用的旧 JS 哈希文件已经被删了。HTML 用 no-cache，带哈希的静态资源才用 immutable。

七、WebSocket 升级

WebSocket 靠 Upgrade / Connection 头做协议升级，必须显式透传：

头 值 为什么
Upgrade $http_upgrade 透传客户端的 websocket
Connection "upgrade" 固定字符串，不能用 $http_connection
proxy_http_version 1.1 HTTP/1.0 没有 Upgrade 机制
proxy_read_timeout 调大 空闲连接会被默认 60s 掐断

⚠️ Connection 必须硬编码成 "upgrade"。 用 $http_connection 会得到 keep-alive, Upgrade 之类的不规范值，部分后端直接拒绝升级。

⚠️ WebSocket 断线往往是 proxy_read_timeout 到期。 表现是「连上后正好 60 秒断一次」。

八、超时参数

指令 默认值 管哪一段
proxy_connect_timeout 60s 与上游建立连接的时间
proxy_send_timeout 60s 向上游发送请求（两次写操作之间）
proxy_read_timeout 60s 从上游读响应（两次读操作之间）
send_timeout 60s 向客户端发送响应
client_body_timeout 60s 读取客户端请求体
keepalive_timeout 75s 客户端长连接空闲时间

⚠️ 超时不能大于前端（比如负载均衡、网关）的超时，否则前一层先断开，Nginx 还在傻等上游，日志上看到的是一堆无意义的 499。

⚠️ proxy_read_timeout 是「两次读之间的间隔」，不是整个响应的总时长。 流式接口持续有数据返回就不会超时；反而是「处理后一次性返回」的慢接口容易被打断。

常见坑清单

  • 以为规则是「加不加斜杠」，其实判定依据是「有没有写 URI」
  • location /api 配 proxy_pass http://b/，拼出双斜杠导致 404
  • 正则 location 里给 proxy_pass 带了 URI
  • 没透传 Host，后端重定向跳到了内网域名
  • 没透传 X-Forwarded-Proto，HTTPS 站点里后端生成 http 链接
  • 直接把 X-Forwarded-For 的第一个值当真实 IP 用（可伪造）
  • 用 ip_hash 做会话粘性，扩缩容时会话大面积失效
  • 以为 max_fails=0 是「不重试」，其实是关闭失败统计
  • 开了 proxy_next_upstream http_500 又没保证幂等，POST 被写两次
  • WebSocket 的 Connection 用了 $http_connection 而不是硬编码 "upgrade"
  • WebSocket 每 60 秒断一次，没改 proxy_read_timeout
  • SPA 兜底规则把 API 的 404 也变成了 200 HTML
  • index.html 配了长缓存，发版后用户拿到旧 HTML 引用已删除的资源
