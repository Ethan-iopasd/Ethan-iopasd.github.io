开场：稳定性三件套的分工

手段 解决的问题 生效位置
限流 别让请求进来太多 入口 / 网关 / 单接口
熔断 下游挂了别陪着一起挂 调用方
降级 挂了也要返回点东西 调用方 / 业务层

顺序是：限流挡在门口 → 熔断断开坏依赖 → 降级给出兜底响应。

一、四种限流算法

算法 原理 优点 缺陷
固定窗口 按时间窗口计数，窗口切换清零 实现最简单（一个计数器） 窗口边界双倍突发：0.9s 打满 100，1.1s 又打满 100
滑动窗口 用多个小窗口（或 Redis ZSET）算最近 N 秒 边界平滑，可调精度 内存 / 计算开销大，精度与格子数成正比
漏桶 Leaky Bucket 请求进桶，以恒定速率流出 输出速率绝对平滑 无法应对突发（有容量时也只能匀速出）
令牌桶 Token Bucket 以固定速率发令牌，请求取令牌 允许突发（桶里有存量令牌就能一次放行） 需要处理桶容量与速率的配合

⚠️ 固定窗口的边界双倍突发是它的硬伤，不是「可以忽略的误差」。 只要流量是脉冲式的（秒杀、定时任务触发），它就一定会漏。要么用滑动窗口，要么在固定窗口里额外加一个「上一窗口的尾部计数」（Redis 的 INCR + EXPIRE 做不了，得用 ZSET）。

⚠️ RateLimiter.create(100) 得到的桶容量默认是 100（1 秒的存量），也就是允许一次性放行 100 个请求。要限制突发就显式指定 warmupPeriod，或者用 SmoothBursty 的容量控制。很多人以为设了 100 QPS 就永远不会超过 100，其实瞬间能过 100。

限流维度

维度 实现 注意
IP 网关按 X-Forwarded-For 第一段计数 NAT 后面一整个公司共享 IP，容易误伤
用户 按 userId / token 计数 未登录用户怎么算（按 IP + UA 兜底）
接口 每个 path 独立配额 同一 path 不同参数要不要拆（如按商品 ID）
租户 多租户 SaaS 必做 防止单个租户吃光全局配额
全局 集群总配额 需要中心化存储，见下

⚠️ X-Forwarded-For 可以伪造。 只信任最后一跳可信代理写入的值，取倒数第一个（或按已知代理层数从右往左数），绝不能直接取最左边那个。取错等于限流形同虚设。

单机 vs 分布式限流

方案 精度 适用
单机内存（Guava / Sentinel 单机模式） 集群QPS / 节点数 近似 节点数固定、要求不严
Redis + Lua 全局精确 需要严格全局配额
网关层限流（Nginx limit_req / APISIX / Sentinel 集群流控） 全局精确 推荐，把限流推到最外层

⚠️ 必须用 Lua 保证「读计数 + 判断 + 写入」的原子性。 分两条命令做的话，并发下会超发。另外 ZSET 的 member 要带随机后缀，否则同一毫秒的请求会互相覆盖（ZADD 同 member 是更新 score）。

⚠️ Redis 限流本身会成为瓶颈和单点。 每次请求一次 Redis 往返，高 QPS 下 Redis 先被打满。工程上的做法是「本地令牌桶 + 定期向 Redis 批量领令牌」 —— 精度略降，但把 Redis 压力降到 1/N。

限流后的响应

⚠️ 限流必须返回 429 + Retry-After，不要返回 403 或 200。 客户端和 SDK 靠 429 决定退避重试；返回 403 会让客户端认为「永久无权限」直接放弃，或者更糟 —— 一直重试。

二、熔断

三个状态

状态 行为 切换条件
CLOSED 正常放行，统计失败率 窗口内失败率 ≥ 阈值 → OPEN
OPEN 直接失败，不发起调用（这是熔断的核心价值） 等待 waitDurationInOpenState → HALF_OPEN
HALF_OPEN 放行少量探测请求 达到阈值成功率 → CLOSED；否则 → OPEN

⚠️ minimumNumberOfCalls 是最容易被忽略的参数。 如果它等于窗口大小（默认 100），那么在只有 3 个请求时永远不会熔断。低流量接口必须显式调小这个值，否则熔断器形同虚设。

⚠️ OPEN 状态必须「快速失败」，不能「等待超时」。 熔断的意义是立刻返回错误，省掉连接建立、等待超时的开销。如果 OPEN 后还去发起调用等 3 秒超时，那和没熔断一样 —— 线程照样被占满。

阈值怎么设

参数 设太小的后果 设太大的后果
failureRateThreshold 偶发抖动就熔断，误伤 下游已经挂了才熔断，保护太晚
slidingWindowSize 样本太少，统计噪声大 反应迟钝，滞后
waitDurationInOpenState 下游还没恢复就放流量，反复打挂 恢复后长时间不恢复流量
慢调用阈值 正常慢请求被判为失败 慢到拖垮线程池也不熔断

⚠️ 熔断要按「依赖」而不是按「接口」配置。 同一个下游服务的所有接口共用一个熔断器（否则一个接口的故障不会触发保护）；反过来，不同下游必须用不同熔断器，否则 A 挂了会连累对 B 的调用被一起断掉。

⚠️ 超时（Timeout）必须在熔断之前生效。 没有超时，请求会一直挂在连接上，熔断器根本统计不到「失败」。超时是熔断的前置条件，先设 connectTimeout / readTimeout，再谈熔断。

隔离

方式 机制 特点
线程池隔离 每个依赖一个独立线程池 强隔离，支持超时中断；线程切换开销大
信号量隔离 计数器限并发 无额外线程，开销小；无法中断阻塞调用

⚠️ 信号量隔离对「阻塞式 IO 超时」无能为力 —— 信号量只能限制并发数，线程还是卡在那里等。要能主动中断，必须用线程池隔离。Hystrix 默认线程池隔离，Sentinel 默认信号量，这个差别决定了它们对慢调用的处理能力。

三、降级

策略 做法 示例
兜底数据 返回缓存 / 默认值 / 空集合 推荐位挂了返回热门榜
功能降级 关掉非核心功能 关闭实时库存，只显示「有货/无货」
读降级 降级到只读 写入口关掉，读走缓存
异步化 同步改异步，先返回「处理中」 下单先返回，异步扣库存
开关 配置中心热开关 一键关掉某功能

⚠️ 降级路径必须比主路径更可靠。 兜底数据来自同一个挂掉的依赖，或者降级逻辑本身还会抛异常，那降级就是灾难放大器。降级分支里的代码要尽可能简单：内存缓存 + 静态默认值，不要有远程调用。

⚠️ 降级要能观测。 每次降级都打点（metric + 日志），否则「接口一直返回空列表」会持续几周没人发现 —— 因为从监控上看**成功率是 100%**。

四、重试的正确姿势

要点 说明
只重试幂等操作 GET / PUT / DELETE 可以，POST 要谨慎（需幂等键）
只重试可重试错误 5xx、超时、连接失败可以；4xx 绝不重试（重试也不会成功）
指数退避 间隔 base * 2^n，避免持续施压
加抖动 所有客户端同时重试 = 重试风暴，会把下游彻底打挂
限制次数和总时长 重试预算不能超过上游超时
限制重试放大倍数 3 层调用各重试 3 次 = 27 倍流量

⚠️ 不加抖动的指数退避和没退避差不多。 下游刚恢复，所有客户端在同一时刻（第 1s、第 2s、第 4s）一起重试，形成周期性的脉冲洪峰，直接把下游再打挂一次 —— 这叫重试风暴 / 惊群。**full jitter（random(0, ceiling)）是最简单有效的解法。**

⚠️ 重试必须在最外层做，不能在每一层都做。 网关重试 + 服务重试 + SDK 重试，一次用户请求可能变成 27 次下游调用。约定「只在调用方的最外层重试一次」，或者用 Retry-After / 请求头传递重试预算。

超时预算

原则 说明
总超时 < 上游超时 每层都要比调用自己的那一层短
留出预算 别把 3s 全给下游，自己还要序列化、写日志
超时必须可配 硬编码的超时在故障时会成为新的故障点
超时要小于上游的容忍度 用户能等 3 秒，你就不能设 10 秒

⚠️ 「每层设 3 秒」是最常见的错误。 网关 3s、服务 3s、DB 3s，那么最坏情况下一个请求要 9 秒才返回，而用户早就走了 —— 但线程还被占着，连接池被耗尽，雪崩就是这么来的。超时必须逐层递减。

⚠️ 重试次数 × 单次超时 ≤ 上层超时。 上游给你 1 秒，你设「超时 800ms + 重试 2 次」，最坏要 2.4 秒，上层早就超时了 —— 你还在重试，白烧资源，还可能触发上层的熔断。

常见坑清单

  • 用固定窗口限流，秒杀场景下边界处放行双倍流量
  • 以为设了 RateLimiter.create(100) 就不会有突发（桶里默认有 1 秒存量）
  • 直接取 X-Forwarded-For 最左边的 IP 做限流（可伪造）
  • 分布式限流不用 Lua，并发下超发
  • 每次请求都打 Redis 做限流，把 Redis 变成瓶颈
  • 限流返回 403 而不是 429，客户端不知道要退避
  • 熔断器 minimumNumberOfCalls 没调小，低流量接口永远不熔断
  • 熔断后还去发起调用等超时（应该立即失败）
  • 所有下游共用一个熔断器，一个挂了全断
  • 没设超时就想靠熔断保护（熔断统计不到没有超时的失败）
  • 用信号量隔离却期望能中断阻塞的 IO 调用
  • 降级兜底数据来自同一个挂掉的依赖，降级也失败
  • 降级不打点，接口一直返回空值却没人发现
  • 对 4xx 也做重试
  • 指数退避不加抖动，形成重试风暴把下游二次打挂
  • 每层都重试，放大成 N 倍流量
  • 各层超时都设成同一个值，最坏耗时叠加导致线程池耗尽
