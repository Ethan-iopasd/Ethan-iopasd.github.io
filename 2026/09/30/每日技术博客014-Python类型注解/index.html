开场：注解不影响运行，但影响你半夜是否被叫醒

Python 的类型注解运行时不做检查（除非用 pydantic 这类库主动校验）。它的价值在于：

  1. IDE 补全和跳转 —— 写 user. 时能列出字段
  2. 静态检查工具 —— mypy / pyright 能在提交前发现类型错误
  3. 可读性 —— 函数签名自带文档

最大收益来自第 1 条。 即使不做静态检查，注解也值得写。

一、基础写法

内置泛型（3.9+ 不用再 import）

旧写法（3.8 及以前） 新写法（3.9+）
List[str] list[str]
Dict[str, int] dict[str, int]
Tuple[int, str] tuple[int, str]
Set[int] set[int]

⚠️ 用 list[str] 这种写法时，运行时也会求值。如果目标版本低于 3.9 会报错，需要加
from __future__ import annotations 把注解变成字符串延迟求值。

二、Optional 与 | None

写法 最低版本 推荐度
Optional[str] 3.5+ 兼容老版本时用
str | None 3.10+ 新项目推荐

⚠️ Optional[X] 的意思不是「可选参数」，是「可能是 None」。

三、容器与泛型

可变参数与多返回值

Sequence vs list

注解 含义 该用哪个
list[int] 必须是 list 需要 .append() 时
Sequence[int] 任何有序可迭代 只读遍历时（更宽松）
Iterable[int] 任何可迭代 只遍历一次
Mapping[str, int] 只读字典 只读查询时

原则：参数类型尽量宽，返回类型尽量窄。 参数写 Sequence[int] 能接受 list 和 tuple；返回写 list[int] 让调用方明确知道拿到什么。

TypedDict：给字典加结构

适合「接口返回的 JSON 结构」——比 dict[str, Any] 有信息量得多。

Literal：限定取值

Protocol：结构化子类型（鸭子类型的静态版）

不用改现有类的继承关系，这是 Protocol 相比抽象基类的最大优势。

几个开关的作用

配置 作用
strict = true 一次打开下面大部分严格选项
disallow_untyped_defs 所有函数必须有注解
check_untyped_defs 连没注解的函数内部也检查
no_implicit_optional x: int = None 报错（必须写 int | None）
warn_unused_ignores # type: ignore 没用到时报警，防止滥用
show_error_codes 显示错误码，方便按码屏蔽

⚠️ 不要一上来就开 strict = true 跑老项目，会报几千个错，然后你就把 mypy 关掉了。
正确做法：先只对新增代码开启，或按模块逐步放开。

六、# type: ignore 的正确姿势

配合 warn_unused_ignores = true，用不到的 ignore 会被标记出来，避免残留。

七、运行时校验：注解不够用时

注解不校验运行时数据。 接口传进来一个字符串，注解写 int 也不会拦。

场景 用什么
内部函数之间 注解 + mypy
外部输入（API、配置、文件） pydantic 等运行时校验
两者都要 pydantic 的模型本身就是类型

常见坑清单

  • 以为注解会在运行时校验（它不会）
  • 把 Optional[X] 理解成「可选参数」
  • 用 x: int = None 而不是 x: int | None = None
  • 参数类型写得太窄（该用 Sequence 却写 list）
  • 返回类型写 dict 而不给结构（用 TypedDict 或 pydantic 模型）
  • 老项目一上来就 strict = true，被几千个错误劝退
  • 到处 # type: ignore 且不带错误码
  • 目标版本低于 3.9 却用了 list[str] 内置泛型
  • 用 list[str] 时忘了 from __future__ import annotations 的兼容作用
  • 在 __init__ 之外初始化实例属性，mypy 推断不出来
