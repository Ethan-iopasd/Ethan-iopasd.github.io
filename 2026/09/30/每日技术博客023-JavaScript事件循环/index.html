开场：事件循环只有两层队列

JavaScript 单线程，但有两套队列：任务队列（macrotask） 和 微任务队列（microtask）。

执行模型一句话：

类型 成员
宏任务 setTimeout、setInterval、setImmediate（Node）、I/O、UI 事件、MessageChannel
微任务 Promise.then/catch/finally、await 之后的代码、queueMicrotask、MutationObserver、process.nextTick（Node）

⚠️ 微任务队列是「清空」，不是「取一个」。 微任务里再产生微任务，会在同一轮里继续跑完 —— 这是死循环卡死页面的根源。

一、同步 → 微任务 → 宏任务

推演：同步跑完 1、4 → 微任务队列有 3 → 输出 3 → 微任务空 → 下一轮宏任务 2。

链式 then 全部在同一轮跑完

then1 执行完才把 then2 推进微任务队列，但它仍是微任务，同一轮被清空，跑不到宏任务。

宏任务之间的先后

同延迟的定时器按注册顺序执行（同一时间源内）。C 是微任务，永远插在 A、B 前面。

二、await 之后的代码是微任务

await x 等价于「把后面所有代码包进 x.then(...)」，所以 await 之后的语句一定让出当前同步执行流。

原生 Promise 只占 1 个微任务，thenable 要多跳

现代 V8（V8 7.2 / Node 12 起，「faster async functions」优化）对 await 原生 Promise 做了特化：只占 1 个微任务 tick。但 await 一个 thenable（非原生 Promise 对象） 会先被 Promise.resolve() 包装，多出跳数。

native 的恢复微任务排在 then 之前，thenable 被挤到后面。数跳数时先判断被 await 的是不是原生 Promise。

⚠️ 这个结论跟引擎版本强相关。旧版 V8 里 await Promise.resolve(1) 要 3 跳。面试题答案随运行时变化，遇到争议直接跑一遍 node -e 验证。

经典综合题

关键点：async2() 是同步调用的（await 只挂起 async1，不阻止 async2 的同步体先跑完）；async1 end 和 promise2 都是微任务，async1 的挂起点更早，所以先输出。

三、queueMicrotask

显式把一个函数推进微任务队列，等价于 Promise.resolve().then(fn)，但没有 Promise 对象开销、也不会吞异常。

方案 异常处理 开销
queueMicrotask(fn) 抛出即成为全局未捕获错误 低
Promise.resolve().then(fn) 变成 rejected promise，不报错，容易静默失败 略高
setTimeout(fn, 0) 宏任务，慢一轮，且会被钳制 高

⚠️ 微任务里抛出的异常不会冒泡到调用方。要统一兜底，加 window.addEventListener('unhandledrejection', ...) 和 window.onerror。

四、setTimeout 的最小延迟与嵌套钳制

HTML 规范里定时器的初始化步骤有两条硬规则：

条件 处理 规范原文
timeout < 0 设为 0 “If timeout is less than 0, then set timeout to 0.”
nestingLevel > 5 且 timeout < 4 设为 4 “If nestingLevel is greater than 5, and timeout is less than 4, then set timeout to 4.”

也就是说：嵌套调用超过 5 层之后，最小间隔被强制为 4 毫秒（浏览器实现通常还有额外对齐）。

⚠️ 规范明确写了「不保证定时器按计划运行」（”This API does not guarantee that timers will run exactly on schedule”）。setTimeout(fn, 0) 不是 0 毫秒，别拿它做精确计时；要精确用 performance.now() 校准，或改用 requestAnimationFrame。

nestingLevel 统计的是对该算法本身的嵌套调用，setTimeout 和 setInterval 混用也会累加。

五、微任务饿死与渲染

一轮宏任务结束后，浏览器才有机会渲染。只要微任务队列一直有东西，渲染就被推迟。

需求 正确工具
尽快执行、不关心渲染 queueMicrotask
让出主线程、允许渲染 setTimeout(fn, 0) / MessageChannel
下一帧前执行 requestAnimationFrame
长任务切片 requestIdleCallback / scheduler.postTask

⚠️ requestAnimationFrame 回调在渲染之前执行，但它不是微任务也不是宏任务队列的普通成员 —— 它属于「渲染步骤」。在 rAF 里改 DOM，同一帧就能看到。

六、Node.js 的差异

Node 的事件循环有多个阶段，比浏览器多两条队列：

队列 相对顺序
process.nextTick 队列 优先级最高，每个阶段切换时先清空它
Promise 微任务队列 在 nextTick 之后清空
定时器阶段 setTimeout / setInterval
check 阶段 setImmediate

⚠️ nextTick 优先级高于 Promise，这跟浏览器里「微任务先于一切」的直觉不一样。而 queueMicrotask 在 Node 里排在 Promise 微任务队列，不在 nextTick 队列。

setTimeout(fn, 0) 与 setImmediate 在主模块里顺序不确定（取决于进程启动耗时是否已超过 1ms）；但在 I/O 回调内部，setImmediate 总是先于 setTimeout。

常见坑清单

  • 以为微任务队列每轮只取一个，实际是清空整个队列
  • 在微任务里递归，页面完全无法渲染
  • 以为 setTimeout(fn, 0) 是立即执行，忽略了最小延迟与 4ms 钳制
  • 依赖 setTimeout 做精确计时，不校准 performance.now()
  • 在 async 函数里忘了 await，异常变成 rejected promise 静默消失
  • 用 Promise.resolve().then(fn) 代替 queueMicrotask，异常被吞掉
  • 以为 await 普通值和 await 已 resolve 的 Promise 跳数一样
  • 在 Node 里以为 Promise 微任务优先于 process.nextTick
  • 在主模块里依赖 setTimeout 与 setImmediate 的固定先后
  • 用 setInterval 做轮询却不考虑回调堆积（上一次没跑完下一次已入队）
  • 把 MutationObserver 的回调当成同步执行
  • 用 setTimeout(fn, 0) 等 DOM 更新，应该用 await nextTick() / queueMicrotask
