开场：同源策略是浏览器的，不是服务器的

跨域报错时，请求往往已经发出去了、服务器也处理了，只是浏览器不把响应交给 JS。

所以：CORS 是浏览器行为，用 curl / Postman 测永远测不出跨域问题。

一、什么是「同源」

协议 + 域名 + 端口，三者完全相同才算同源。

页面地址 请求地址 同源？ 原因
https://a.com https://a.com/api ✅
https://a.com http://a.com/api ❌ 协议不同
https://a.com https://api.a.com/x ❌ 域名不同（子域也算）
https://a.com https://a.com:8443/x ❌ 端口不同
https://a.com https://a.com/api（页面在 443） ✅ 默认端口相同

二、CORS 的两种请求

简单请求

同时满足以下条件才算简单请求：

  • 方法是 GET / HEAD / POST
  • 请求头只用了安全列表内的（Accept、Accept-Language、Content-Language、Content-Type 等）
  • Content-Type 只能是 text/plain、multipart/form-data、application/x-www-form-urlencoded

简单请求直接发，浏览器检查响应里有没有 Access-Control-Allow-Origin。

预检请求（Preflight）

只要「不简单」——比如 PUT、DELETE、Content-Type: application/json、带自定义头——浏览器会先发一个 OPTIONS 请求问服务器。

⚠️ **带 Cookie 时 Access-Control-Allow-Origin 不能写 ***，必须回显具体源。这是最高频的跨域配置错误。

各响应头汇总

响应头 作用
Access-Control-Allow-Origin 允许的源（* 或具体源）
Access-Control-Allow-Methods 允许的方法
Access-Control-Allow-Headers 允许的请求头
Access-Control-Allow-Credentials 是否允许带凭据
Access-Control-Expose-Headers 允许 JS 读取的额外响应头
Access-Control-Max-Age 预检结果缓存秒数

⚠️ 默认 JS 只能读到简单响应头（Cache-Control、Content-Type、Expires 等）。要读 X-Total-Count 这类自定义头，必须写 Access-Control-Expose-Headers。

三、Cookie 的属性

一个 Cookie 长什么样

属性 作用
Domain 生效的域（含子域）
Path 生效的路径
Expires / Max-Age 过期时间。都不写就是会话 Cookie，关浏览器就没了
Secure 只在 HTTPS 下发送
HttpOnly JS 读不到（防 XSS 窃取）
SameSite 控制跨站请求是否携带（防 CSRF）

SameSite 三档

值 行为
Strict 任何跨站请求都不带。从外站点链接过来会显示未登录
Lax 默认值。跨站的 GET 顶级导航带，POST / iframe / fetch 不带
None 总是带。**必须同时加 Secure**，否则被拒

⚠️ **SameSite=None 必须搭配 Secure**，且只在 HTTPS 下生效。前后端分离、跨站携带 Cookie 的场景常踩这个。

⚠️ 这是设计如此，不是 bug。HttpOnly 就是为了防 XSS。需要给前端传信息，用响应体或非 HttpOnly 的 Cookie。

四、几个低成本的安全响应头

头 防什么
Strict-Transport-Security（HSTS） 强制 HTTPS，防降级攻击
X-Content-Type-Options: nosniff 阻止浏览器猜测 MIME 类型
X-Frame-Options 防点击劫持（iframe 嵌套）
Referrer-Policy 控制跳转时泄漏多少来源信息
Content-Security-Policy（CSP） 防 XSS，最有效也最容易配错

⚠️ HSTS 一旦生效，浏览器在 max-age 内会强制 HTTPS，期间 HTTP 直接拒绝。测试时先用小 max-age。

五、一张表看清 CSRF 与 XSS

XSS CSRF
攻击点 页面（注入脚本） 请求（借用户身份发请求）
靠什么生效 浏览器信任页面内容 浏览器自动携带 Cookie
主要防御 CSP、输出转义、HttpOnly SameSite、CSRF Token、校验 Origin
HttpOnly 有用吗 ✅ 防 Cookie 被偷 ❌ 无用

记住这条：CSRF 之所以成立，是因为浏览器会自动带上 Cookie。所以防御的核心是「确认这个请求是用户主动发的」。

常见坑清单

  • 以为跨域是服务器拦的（其实是浏览器，curl 测不出来）
  • 带 Cookie 时 Access-Control-Allow-Origin 写了 *
  • 没设 Access-Control-Max-Age，每个请求都多一次 OPTIONS
  • 想读自定义响应头却没配 Access-Control-Expose-Headers
  • 把子域名当成同源
  • SameSite=None 忘了配 Secure
  • Cookie 用 JS 读不到就以为是 bug（那是 HttpOnly 生效）
  • 清除 Cookie 时 Path / Domain 不匹配，导致删不掉
  • 敏感 Cookie 没加 Secure，在 HTTP 下明文传输
  • HSTS 直接上大 max-age，配错后无法回退
  • CSP 一次写很严，把内联脚本和 CDN 全拦了导致页面白屏
