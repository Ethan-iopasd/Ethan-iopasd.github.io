开场：Redis 不是「一个会过期的字典」

只用 SET/GET 的话，你只用到 Redis 的一成。每种数据结构都对应一类问题的解法，选对了能让代码量少一个数量级。

截至 2026-09，Redis 最新稳定版为 8.10.2。Redis 8 把原先 Redis Stack 的模块
（JSON、Search、TimeSeries、概率型结构等）并入了核心发行版，不再需要单独装。

一、九种数据结构

结构 底层 一句话用途
String SDS 缓存、计数、分布式锁
Hash listpack / hashtable 存对象、部分更新
List quicklist 队列、时间线
Set intset / hashtable 去重、交并集
Sorted Set listpack / skiplist 排行榜、延时队列
Bitmap String 签到、布隆过滤器
HyperLogLog 稀疏/稠密 基数统计（UV）
Geo Sorted Set 附近的人
Stream radix tree 消息队列、事件溯源

二、String：不只是缓存

原子计数

INCR 是原子的，天然适合计数，不需要加锁。

分布式锁

参数 作用
NX 只有 key 不存在时才设置（互斥）
PX 30000 30 秒后自动过期（防死锁）

⚠️ 释放锁必须用 Lua 脚本校验 value，否则可能删掉别人的锁：

「先 GET 判断再 DEL」两条命令之间不是原子的，中间锁可能已过期并被别人获取。

⚠️ 单实例 Redis 锁在故障转移时会失效（主从切换，锁可能丢失）。
要求强一致的场景用 Redlock 或基于共识的组件（etcd / ZooKeeper）。

存对象 vs 用 Hash

String + JSON Hash
改单个字段 全量读写 ✅ 只改该字段
取整个对象 ✅ 一次搞定 需要 HGETALL
内存（字段少时） 略小 略大
嵌套结构 ✅ ❌ 只能一层

经验：字段少（< 10）、每次都是整体读写 → String + JSON；字段多、常改个别字段 → Hash。

三、Hash

⚠️ **不要在生产环境对大 Hash 用 HGETALL**，它会一次返回所有字段，阻塞单线程。
用 HSCAN 分批。

四、List：队列与时间线

用法 命令组合
队列（FIFO） LPUSH + RPOP
栈（LIFO） LPUSH + LPOP
时间线 LPUSH + LRANGE + LTRIM
阻塞队列 LPUSH + BRPOP

⚠️ BRPOP 的「阻塞」会占用连接。大量消费者时考虑用 Stream。

五、Set：去重与集合运算

典型场景：标签、共同好友、抽奖去重、黑名单。

六、Sorted Set：排行榜与延时队列

延时队列

否则多消费者会抢到同一条。

排行榜的细节

需求 做法
分数相同按时间先后排 分数 = 实际分数 × 10^10 + (上限 − 时间戳)
分页 ZREVRANGE key start stop
取某人附近的排名 ZREVRANGEBYSCORE 或 ZRANK + 偏移

七、Bitmap、HyperLogLog、Geo、Stream

Bitmap：签到

1 亿用户的日活，用 Bitmap 只要约 12MB。 这是它最大的价值。

HyperLogLog：UV 统计

HyperLogLog Set
内存 固定约 12KB 随基数线性增长
误差 约 0.81% 精确
能否取元素 ❌ 只能计数 ✅

适合「只要数量、不需要具体是谁」的场景（UV、去重计数）。

Geo：附近的人

底层就是 Sorted Set，所以不要对 Geo key 用普通的 ZADD 乱写，会破坏地理编码。

Stream：正经的消息队列

特性 说明
消费者组 一条消息只被组内一个消费者处理
XACK 显式确认，未确认的留在 PEL 里
XAUTOCLAIM 认领超时未确认的消息
消息持久化 可设 MAXLEN 自动裁剪

比 List 做队列强在：有消费确认、支持多消费者组、可以回溯历史。
需要「至少一次投递」语义时用 Stream。

八、怎么选（速查）

需求 结构
缓存对象、页面 String
计数、限流 String（INCR）
分布式锁 String（SET NX PX）
存对象、常改单字段 Hash
队列 List 或 Stream
最新 N 条 List（LPUSH + LTRIM）
去重、标签、交并集 Set
排行榜 Sorted Set
延时队列 Sorted Set（时间戳当分数）
签到、布尔位图 Bitmap
UV 统计 HyperLogLog
地理位置 Geo
消息队列（要确认） Stream

九、通用操作与陷阱

⚠️ 生产环境禁用 KEYS。 它会遍历整个 keyspace，阻塞单线程 Redis，
数据量大时直接卡住所有请求。用 SCAN 分批。

⚠️ SCAN 不保证返回所有元素（遍历过程中有增删时可能漏）。需要完整遍历就多轮，
或改用其他结构。

⚠️ Redis 执行命令是单线程的（6.0+ 的网络 I/O 是多线程，命令执行仍是单线程）。
一条慢命令会阻塞所有人。避免 KEYS、大 HGETALL、SMEMBERS、大 ZRANGE。

常见坑清单

  • 只用 String 存 JSON，改一个字段要全量读写
  • 释放分布式锁时「先 GET 再 DEL」，非原子
  • 分布式锁没设过期时间，进程崩了锁永远不释放
  • 生产环境用 KEYS 遍历（阻塞整个实例）
  • 对大 Hash / Set 用 HGETALL / SMEMBERS
  • 把 HyperLogLog 当精确计数用
  • 用 Set 统计 UV，内存随用户数线性增长
  • 延时队列取出任务忘了删除，重复执行
  • 对 Geo key 用普通 ZADD，破坏地理编码
  • 用 List 做队列却需要消息确认（该用 Stream）
  • 对 key 做 SCAN 时以为能拿到全部元素
  • 大 key 没拆（一个 Hash 存几十万字段）
