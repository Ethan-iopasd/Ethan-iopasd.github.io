开场：调优是「让配置不超过系统上限」

Nginx 的性能问题基本只有两类：配置的上限超过了系统给的上限（跑不到那么高），或者某个超时配得不匹配（前后端互相等）。前者看 worker_* 和 ulimit，后者看日志里的时间字段。

一、worker 进程数

值 说明
auto 等于 CPU 核数，绝大多数场景的正确选择
具体数字 手动指定；I/O 极重的场景有人配到 2 倍核数
1 只在开发机或需要单进程调试时用

⚠️ worker 数不是越大越好。 超过核数只会增加上下文切换和锁竞争，吞吐反而下降。

二、worker_connections 与文件描述符

概念 层级 含义
系统 ulimit -n 操作系统 进程能打开的文件描述符硬上限
worker_rlimit_nofile Nginx main Nginx 主动把 worker 的 RLIMIT_NOFILE 调高，不用重启主进程
worker_connections Nginx events 单个 worker 能同时打开的最大连接数

关键约束：**worker_connections 统计的是所有连接，包括客户端连接和**到上游的连接。所以反向代理场景下，一个客户端请求最多占 2 个 fd。

理论上限：

三者要对齐：

配置 建议
系统 ulimit -n ≥ worker_rlimit_nofile
worker_rlimit_nofile ≥ worker_connections（代理场景再留余量，比如 ×2）
worker_connections 按目标并发倒推

⚠️ worker_rlimit_nofile 只能往上提到系统允许的范围。 系统 ulimit -n 或 systemd 的 LimitNOFILE 太小，Nginx 调不上去，日志里会出现 too many open files。

⚠️ systemd 启动的 Nginx 读的是 LimitNOFILE，不是 shell 的 ulimit。 要在 unit 里改，或者 /etc/systemd/system/nginx.service.d/ 里覆盖。

⚠️ 反向代理时把 worker_connections 当并发请求数算会高估一倍，因为每个请求还占一个到上游的连接。

三、sendfile / tcp_nopush / tcp_nodelay

指令 默认值 作用
sendfile off 用内核 sendfile() 把文件直接从页缓存送到 socket，绕过用户态拷贝
tcp_nopush off 配合 sendfile，用 TCP_CORK 把响应头和起始数据凑成一个包发出去
tcp_nodelay on 关闭 Nagle 算法，小包立即发送，降低延迟

三个一起开是静态文件服务的常规配法：

  • sendfile on —— 减少数据拷贝
  • tcp_nopush on —— 减少小包数量（先攒够一个 MSS 再发）
  • tcp_nodelay on —— 长连接上最后一个不足 MSS 的包立即发，不被 Nagle 卡住

⚠️ tcp_nopush 只在 sendfile on 时生效。 单独开没有任何作用。

⚠️ sendfile 对动态内容（代理转发的响应）没有帮助，它只处理「从文件发送」的路径。反向代理的性能瓶颈在别处。

四、keepalive 与 upstream 连接池

客户端侧

到上游的连接池

三件事必须同时做，少一个长连接就不生效：

必须项 位置 不做的后果
keepalive N upstream 块 没有连接池，连接用完就关
proxy_http_version 1.1 location 默认 1.0，1.0 默认 Connection: close
proxy_set_header Connection "" location 传了 Connection: close，连接不被复用

⚠️ keepalive 只限制「每个 worker 缓存的空闲连接数」，不是上游连接总数上限。真正并发时还会临时新建连接，上限由 max_conns 或系统 fd 决定。

⚠️ keepalive 值太小是常见问题。 只有 32 个空闲连接，而 QPS 很高时，池子不够用，长连接复用率上不去，效果约等于没配。

⚠️ 上游是 HTTP/2 或 gRPC 时，Connection 头本来就不该出现，配置要另写（grpc_pass）。

五、gzip 与 brotli

gzip brotli
是否内置 是（ngx_http_gzip_module） 否，需要第三方模块或官方 Plus
压缩率 一般 通常比 gzip 高 15%–25%
CPU 开销 低 同压缩率下更低
浏览器支持 全支持 现代浏览器都支持（HTTPS 场景）
常见做法 兜底 优先，不支持时回落 gzip

⚠️ 图片、视频、woff2 不要开 gzip。 它们已经是压缩格式，再压基本不减小，纯浪费 CPU。

⚠️ 忘了 gzip_vary on 会出问题。 中间 CDN 可能把压缩版响应缓存下来发给不支持 gzip 的客户端。

⚠️ gzip_static on 只发 .gz 文件，不会帮你生成。 构建时没有预压缩产物的话它什么也不做，静默失败。

六、client_max_body_size 与 413

现象 原因
上传超过 1MB 就 413 client_max_body_size 默认 1m
只在某个 location 上传失败 该 location 覆盖了 http 层的配置
前面有 LB / 网关时 413 那一层也有自己的 body 限制，要一起改
前端是 K8s Ingress 还要加注解，比如 nginx.ingress.kubernetes.io/proxy-body-size: "20m"

⚠️ **请求体超过 client_body_buffer_size 会先落盘到 client_body_temp_path**，磁盘慢或满会表现为上传卡住。

⚠️ 413 的报错可能来自 Nginx 前面的任何一层。 排查时先看响应头的 Server 字段，确认是谁返回的。

七、502 / 504 成因对照

状态码 含义 常见成因
502 Bad Gateway 上游返回了无法解析的响应 上游进程挂了 / 端口没监听；上游崩在响应中途；上游返回的响应头不合法；上游是 HTTPS 但用了 http://；DNS 解析失败
504 Gateway Timeout 等上游响应超时 proxy_read_timeout 到期；上游真的慢（慢 SQL、锁等待）；上游被限流排队；上游连不上但没拒绝（防火墙丢包）
499 客户端在 Nginx 返回前断开了 前端超时设得比 Nginx 短；用户手动取消
413 请求体过大 见上一节
502 + no live upstreams 所有后端都被标记不可用 max_fails / fail_timeout 触发，或健康检查全挂

快速定位：

error.log 里几种典型行：

日志内容 含义
connect() failed (111: Connection refused) 后端没监听 → 502
upstream timed out (110: Connection timed out) while reading response header 读超时 → 504
no live upstreams while connecting to upstream 所有节点都被标记不可用
upstream prematurely closed connection 后端中途断开 → 502
client intended to send too large body 413
worker_connections are not enough 连接数不够，调 worker_connections
Too many open files fd 上限不够，调 worker_rlimit_nofile / systemd LimitNOFILE

⚠️ 502 里一大半是后端问题，不是 Nginx 问题。 先 curl 直连后端确认。

⚠️ 504 不要一味调大超时。 调大只是把失败往后拖，真正该看的是上游为什么慢。

⚠️ 499 是客户端断开，别当成 Nginx 故障。 但如果 499 大量出现，说明上游响应时间超过了前端的耐心值。

八、日志里加时间字段

默认的 combined 格式看不出时间花在哪。加上这两个字段就能拆开：

变量 含义
$request_time 从收到第一个字节到发完响应的总耗时（秒，毫秒精度）
$upstream_response_time 从连上上游到收完响应体的时间
$upstream_header_time 从连上上游到收到响应头的时间
$upstream_connect_time 与上游建立连接的时间
$upstream_addr 这次请求打到了哪个后端（重试时会用逗号列出多个）

判断逻辑：

观察 结论
request_time 大，upstream_response_time 小 慢在 Nginx 与客户端之间（带宽、客户端慢、大文件传输）
request_time ≈ upstream_response_time 慢在后端
upstream_connect_time 大 与上游建连慢（网络、上游 backlog 满）
upstream_header_time 远小于 upstream_response_time 后端吐得慢（流式接口、大响应体）
upstream_addr 有多个值 发生了重试，前一个节点有问题

⚠️ $upstream_response_time 可能有多个值（重试过），也可能有 -（没走到上游，比如命中本地文件）。统计脚本要处理这两种情况。

⚠️ 开启带时间的日志格式会增加少量 CPU 开销，高 QPS 场景建议用 buffer：access_log ... buffer=64k flush=5s;。

九、nginx -t 与平滑 reload

平滑 reload 的机制：

命令 会不会中断请求
nginx -s reload 不会，旧 worker 处理完再退
nginx -s stop / kill -9 会，正在处理的请求直接断
systemctl reload nginx 不会（等价于 -s reload）
systemctl restart nginx 会，整进程重启，有短暂不可用

发版标准流程：

⚠️ 先 -t 再 reload。 配置写错时 -t 会拦住，reload 遇到错误配置会保留旧 worker 继续跑（不中断服务），但你的改动也没生效 —— 容易误以为”改了没效果”。

⚠️ nginx -s reload 不校验上游是否可用。 新配置里后端地址写错了照样 reload 成功，故障要到第一个请求才暴露。

⚠️ reload 会同时存在新旧两批 worker，如果 upstream 连接池里还有旧连接，短时间内容量会短暂波动。

⚠️ nginx -T 会输出配置里的敏感信息（上游地址、密钥路径），别直接贴到公开的地方。

常见坑清单

  • worker_connections 按并发请求数配，忽略反向代理每个请求占 2 个 fd
  • 只调了 worker_rlimit_nofile，systemd 的 LimitNOFILE 没改，调不上去
  • tcp_nopush on 但 sendfile 是 off，配置完全没生效
  • upstream 配了 keepalive，却漏了 proxy_http_version 1.1 和 Connection ""
  • keepalive 32 在高 QPS 下池子太小，长连接复用率上不去
  • 对图片、woff2 开 gzip，白烧 CPU 没收益
  • gzip_vary on 没开，CDN 缓存串味
  • 上传报 413，只改了 Nginx，没查前面 LB / Ingress 的限制
  • 504 就调大 proxy_read_timeout，不看后端为什么慢
  • 把 499 当故障排查（它其实是客户端先断开）
  • 日志没加 $request_time / $upstream_response_time，慢在哪全靠猜
  • 直接 nginx -s reload 不先 -t，配置写错后误以为改动已生效
  • 用 systemctl restart 代替 reload，造成不必要的请求中断
