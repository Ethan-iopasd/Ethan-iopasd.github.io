一 依赖管理与虚拟环境 本篇

开场：依赖管理只有三件事

任何语言的依赖管理，本质都在解决这三个问题：

  1. 隔离 —— 这个项目的依赖不要污染别的项目
  2. 声明 —— 我直接用了哪些库（直接依赖）
  3. 锁定 —— 每个库具体装哪个版本（含传递依赖），保证换台机器装出来一模一样

Python 的工具链乱，就是因为这三件事被不同工具各管一段。想清楚你要哪一段，选型就不纠结了。

一、为什么必须用虚拟环境

不隔离的后果很具体：

所有包装进同一个全局 site-packages，装 B 就会顶掉 A 的版本。两个项目没法同时跑。

更麻烦的是系统自带的 Python：很多 Linux 发行版用系统 Python 跑系统工具，你 sudo pip install 装崩了依赖，可能连包管理器都用不了。

结论：一个项目一个虚拟环境。没有例外。

二、venv：标准库自带，够用

激活后 python 和 pip 都指向环境内部：

⚠️ 用 python -m pip 而不是 pip
在没激活环境、或 PATH 里有多个 Python 时，pip 可能指向另一个解释器的 pip，装到别处去了。
python -m pip 保证「用哪个 python，就装到哪个 python 里」。

⚠️ Windows PowerShell 激活报错「无法加载文件，因为在此系统上禁止运行脚本」

或者直接用 CMD / Git Bash。

venv 的边界：它只解决「隔离」，不管依赖声明和锁定。那部分要另想办法。

三、requirements.txt 的四个坑

最常见的做法是：

pip freeze 看着能用，但有四个坑：

坑一：它记录的是「环境里有什么」，不是「你需要什么」

一堆你从没 import 过的库。想升级 Django 时，你分不清哪些能删、哪些是传递依赖。

坑二：开发依赖和运行依赖混在一起

pytest、black、mypy 这些只在开发时用的，也被写进去了。生产环境装一堆用不上的东西。

坑三：平台相关的包会污染

在 Windows 上 freeze，可能写进 pywin32、pywinpty 这种 Windows 专有包。拿到 Linux 服务器上直接装不上。

坑四：== 锁得太死，也不够死

锁死了直接依赖的版本，但传递依赖的版本是你 freeze 那一刻恰好装到的，换台机器重新解析可能得到不同结果 —— 这就是「本地能跑，服务器上炸」的经典来源。

正确的分工应该是：

文件 内容 谁维护
requirements.in 只写直接依赖，可以放宽版本 人手工写
requirements.txt 编译出的完整锁定，含传递依赖 pip-compile 生成

四、pyproject.toml：新的标准位置

以前 Python 项目的元数据散在 setup.py / setup.cfg / requirements.txt 里。现在标准是 **pyproject.toml**（PEP 621）：

装依赖：

-e（editable）的意义：装完之后 import myapp 直接指向你的源码目录，改了代码立刻生效，不用重装。

五、工具对比

工具 隔离 声明 锁定 速度 一句话评价
venv + pip ✅ ❌ ❌ 慢 标准库自带，最小可用
venv + pip-tools ✅ ✅ ✅ 慢 保守派首选，纯 pip 生态
uv ✅ ✅ ✅ 极快 目前最推荐，Rust 写的
poetry ✅ ✅ ✅ 中 生态成熟，功能全
pipenv ✅ ✅ ✅ 慢 曾经的官方推荐，现在不推荐了

当前版本参考：uv 0.12.21 · poetry 2.5.1 · pip-tools 7.6.1 · pipenv 2026.8.0

uv：目前我最推荐

Rust 实现，速度比 pip 快一个数量级（解析依赖时尤其明显）。

uv run 这个设计很舒服 —— 不用先 activate 再执行，它自己找环境。写脚本和 CI 里特别省事。

poetry

功能最全（打包、发布、多环境依赖分组），生态成熟。缺点是依赖解析比 uv 慢不少。

六、怎么选

你的情况 选择
只想快速隔离一下 python -m venv .venv
团队已有 pip 流程，不想换 venv + pip-tools
新项目，没有历史包袱 uv
需要打包发布到 PyPI poetry 或 uv（uv build）
维护老项目 保持现状，别为了换工具而换

换工具的成本主要在迁移锁文件和改 CI 脚本。老项目只要还能跑，没有非换不可的理由。

七、常见坑清单

  • 不用虚拟环境，所有包装进全局 site-packages
  • 用 sudo pip install 装包（污染系统 Python，可能弄坏包管理器）
  • 用 pip 而不是 python -m pip（可能装到另一个解释器里）
  • 用 pip freeze 当依赖声明（把传递依赖和开发依赖全写进去了）
  • 把 .venv/ 提交进 Git（应该写进 .gitignore）
  • 提交了 requirements.txt 但没提交锁文件（uv.lock / poetry.lock）
  • Windows 上 freeze 出的 pywin32 拿到 Linux 装
  • 手动 pip install 之后忘了同步到声明文件，下次别人装不起来
  • CI 里缓存了虚拟环境但没按锁文件 hash 做 key，导致缓存了错误版本
  • 生产环境用 pip install -r requirements.txt 而不锁传递依赖，构建不可复现
