开场：线程在等，还是在算

任务性质 正确的模型 理由
等网络 / 等磁盘 / 等数据库 threading 或 asyncio 等待期间主动释放 GIL
纯 CPU 计算（解析、压缩、加密、数值） multiprocessing 绕过 GIL，吃满多核
两者混合 进程池，每进程内再用线程 / asyncio 两类瓶颈分开处理

GIL 不是「Python 慢」的原因，它是「Python 的线程不能并行执行字节码」的原因。 这两件事经常被混为一谈。

一、GIL 是什么

CPython 解释器里的一把全局互斥锁：同一进程内，同一时刻只有一个线程在执行 Python 字节码。

它保护的是解释器自身的状态，不是你的业务逻辑：

被 GIL 保护的东西 说明
引用计数 ob_refcnt += 1 不是原子的，两个线程同时改会丢计数
对象分配 / 内存池 pymalloc 的 freelist 是全局结构
字节码求值循环状态 求值栈、异常状态、帧对象
未声明线程安全的 C 扩展 大量老扩展靠它兜底

⚠️ GIL 保护解释器，不保护你的代码。 counter += 1 编译成多条字节码，线程可能在任意一条之间被切走。

切换也不是「只在 I/O 时发生」。CPython 在字节码之间检查 sys.getswitchinterval()，默认 0.005 秒。CPU 密集的多线程会不停被切，切完还只能有一个跑 —— 净亏。

二、为什么 I/O 密集有效、CPU 密集无效

关键只有一句：执行阻塞式系统调用时会主动释放 GIL。

操作 是否释放 GIL
socket.recv / send / accept ✅ 阻塞期间释放
文件 read / write / open ✅ 阻塞期间释放
time.sleep() ✅ 全程释放
等待子进程（subprocess） ✅
list.sort()、sum()、正则匹配、json.loads ❌ 全程持锁
纯 Python 循环 / 算术 ❌ 只在切换间隔让步

⚠️ 上面的 cpu_work 在无 GIL 的自由线程构建下结论完全相反 —— 4 线程接近 4 倍加速。前提是你的依赖都声明了自由线程安全，见第七节。

三、threading / multiprocessing / concurrent.futures

维度 threading multiprocessing concurrent.futures
执行单元 线程 进程 两者都能包
并行执行 Python 代码 ❌（GIL 构建下） ✅ 取决于用哪个 Executor
共享内存 ✅ 直接共享 ❌ 要 pickle 或 shared_memory 同左
启动开销 极低 高（fork / forkserver / spawn） 同左
适合 I/O 密集 CPU 密集 两种都用它写

concurrent.futures 是门面，日常直接用它，不用手搓 Thread / Process：

不传 max_workers 时的默认值：

Executor 默认值 备注
ThreadPoolExecutor min(32, os.cpu_count() + 4) 3.8 起
ProcessPoolExecutor os.process_cpu_count() 3.13 起由 os.cpu_count() 改为该值

⚠️ 容器里一定要显式传 max_workers。按宿主机核数起进程会瞬间打满内存。

几个必须知道的细节：

  • ex.map() 按传入顺序返回，且是惰性的 —— 取结果时才推进任务
  • ex.submit() 返回 Future，用 as_completed() 按完成顺序收
  • 异常在取结果时（future.result() / 迭代 map）才抛出，不是提交时
  • 想知道哪个任务炸了，用 submit + future.result() 包 try

四、进程间通信的代价

进程池不是「线程池换个词」。开销在三处：序列化、启动、传数据。

通信方式 适用 代价
Executor / Pool 的返回值 任务结果 一次 pickle 往返
multiprocessing.Queue 流式传小对象 pickle + 管道 + 锁
multiprocessing.Pipe 两个进程之间 比 Queue 轻
shared_memory 大数组（numpy） 无拷贝，但要自己管生命周期
Manager() 共享 dict / list 最慢，所有操作走代理进程

启动方式（start method）：

方式 平台 特点
spawn Windows 默认、macOS 默认 全新解释器，最慢，最安全
fork Linux 3.13 及以前的默认 最快，但多线程进程里 fork 不安全
forkserver Linux 3.14 起的默认 折中：先起干净的服务进程，再由它 fork

⚠️ Python 3.14 起，POSIX 平台默认 start method 从 fork 改为 forkserver。 依赖 fork 继承父进程状态的代码会失效 —— 模块级变量、已打开的连接、父进程配置好的 logging。
⚠️ 多线程程序里调 os.fork() 自 3.12 起会发 DeprecationWarning：子进程只保留调用线程，其他线程持有的锁可能永远不释放。

⚠️ 进程不共享全局状态。 子进程改了全局变量，父进程看不到；multiprocessing 的全局变量在每个 worker 里是各自独立的副本。

五、asyncio 与多线程的边界

asyncio 是单线程的事件循环。它解决的是「海量并发 I/O 下线程太重」，不是「多核利用」。

需求 用什么
上万个并发连接、每连接少量数据 asyncio
少量并发、每个任务内部有同步阻塞调用 线程池
两者都要 asyncio 主循环 + asyncio.to_thread() 兜住阻塞调用
CPU 密集 进程池（asyncio 里用 run_in_executor 调 ProcessPoolExecutor）

⚠️ 在协程里直接调 time.sleep() / requests.get() 会卡死整个事件循环，不是卡死一个任务。这是 asyncio 最贵的错误。

⚠️ asyncio.to_thread() 用的是默认线程池（上限 min(32, cpu+4)）。大量阻塞调用会把它占满，后续 await 排队。必要时自建 ThreadPoolExecutor 并显式传入。

六、共享状态与锁

多线程改共享数据就必须加锁 —— GIL 不替你解决这个。

原语 用途
Lock 最常用，保护临界区
RLock 同一线程可重复获取（递归场景）
Semaphore 限制并发数（如最多 5 个连接）
Event 一个线程通知多个线程
Condition 等待某个条件成立
queue.Queue 线程安全队列，优先用它代替「加锁的 list」

七、free-threading：GIL 的现状

版本 状态 说明
3.13 实验性 首次提供 --disable-gil 构建（PEP 703），bug 优先级低，库支持不全
3.14 正式支持 PEP 779 定义了「受支持」标准，无 GIL 构建作为官方产物随版本发布（python3.14t）

⚠️ 导入一个未声明自由线程安全的 C 扩展，会让 GIL 被静默重新打开，不报错、不抛异常。要确认并行真的生效，必须在所有 import 之后检查 sys._is_gil_enabled()。
⚠️ 自由线程构建有单线程性能代价。官方 pyperformance 基准给出的平均开销范围约 1%（macOS aarch64）到 8%（x86-64 Linux），具体随负载和硬件变化。
⚠️ 即使没有 GIL，多线程的竞态问题依然存在，甚至更容易暴露。free-threading 不是「打开就变快」的开关。

常见坑清单

  • 用多线程跑 CPU 密集任务，以为能加速
  • 认为 counter += 1 是原子的
  • 在协程里调同步阻塞函数（time.sleep / requests），卡死整个事件循环
  • 多线程改共享 dict / list 却不加锁
  • 多把锁的获取顺序不一致，造成死锁
  • 持锁做网络 / 磁盘 I/O
  • 以为 multiprocessing 的子进程能改到父进程的全局变量
  • 往进程池传大对象，序列化开销吃掉并行收益
  • 容器里不设 ProcessPoolExecutor(max_workers=...)，按宿主机核数起进程
  • 在 3.14 上依赖 fork 继承父进程状态（默认已改为 forkserver）
  • 只看 sys.version 就断言并行生效，不在 import 之后查 sys._is_gil_enabled()
