一 复杂度与常用数据结构 本篇

开场：复杂度是「增长趋势」，不是「快慢」

O(n log n) 的算法在小数据量下完全可能比 O(n²) 的慢 —— 大 O 忽略常数和低阶项，只在 n 足够大时才有意义。 选数据结构时，先看操作模式（随机读还是频繁插入），再看数据规模，最后才看复杂度。

一、大 O 的定义与常见量级

定义：f(n) = O(g(n)) 表示存在常数 c > 0 和 n₀，使得所有 n ≥ n₀ 都有 f(n) ≤ c · g(n)。它描述的是上界，不是紧界。

量级 名称 n=1e3 n=1e6 典型场景
O(1) 常数 1 1 哈希查找、数组按下标访问
O(log n) 对数 ~10 ~20 二分查找、平衡树
O(n) 线性 1e3 1e6 遍历、单层循环
O(n log n) 线性对数 ~1e4 ~2e7 排序下界、堆操作 n 次
O(n²) 平方 1e6 1e12 ❌ 双层循环、朴素字符串匹配
O(2ⁿ) 指数 天文数字 —— 子集枚举、朴素斐波那契递归
O(n!) 阶乘 天文数字 —— 全排列

⚠️ O(log n) 的底数不重要（log₂n 和 log₁₀n 只差常数倍），所以写 O(log n) 不写底数。同理 O(2n + 5) 要写成 O(n)。

⚠️ O(n²) 在 1e6 规模下是 1e12 次操作，按每秒 1e8 次算要 3 小时。「n 只有一百万，应该没问题」是性能事故的常见起点。 遇到嵌套循环先想清楚数据量级。

⚠️ 均摊（amortized）≠ 平均（average）。

  • 均摊是对最坏情况的保证：n 次操作总共 O(n)，那么每一次均摊下来是 O(1)，这是确定性的。
  • 平均是对输入分布的假设：哈希表平均 O(1) 依赖哈希均匀分布，**恶意输入下会退化成 O(n)**。

动态数组 push 是均摊 O(1)（扩容时 O(n)，但被 n 次操作摊薄）；哈希表查找是平均 O(1)（最坏 O(n)）。这两个说法不能混用。

空间换时间

手段 时间收益 空间代价
哈希表缓存 查找 O(n) → O(1) 额外 O(n) 空间
前缀和数组 区间求和 O(n) → O(1) 额外 O(n)
记忆化 / DP 表 指数 → 多项式 O(n) 或 O(n²)
位图 Bitmap 判断存在 O(n) → O(1) n/8 字节（极省）
布隆过滤器 判断「一定不存在」 位图 + 少量误判率
排序预处理 多次查询 O(n) → O(log n) O(n)，且排序本身 O(n log n)

⚠️ 布隆过滤器只能回答「一定不存在」或「可能存在」。 它没有假阴性，但有假阳性 —— 说「存在」时可能是误判。用来挡缓存穿透很合适（误判只是多查一次 DB），用来做权限判断是灾难。

二、各语言的真实实现

语言 动态数组 哈希表 有序映射 备注
Java ArrayList HashMap TreeMap（红黑树） HashMap 桶内链表 ≥ 8 且容量 ≥ 64 才树化
Python list dict 无内建（用 sortedcontainers） dict 用开放寻址，3.7 起保证插入序
Go slice map 无内建 Go 1.24 起 map 改用 Swiss Table（原为 bucket + 溢出链）
C++ std::vector std::unordered_map std::map（红黑树） unordered_map 标准不要求开放寻址
JS Array Map 无内建 Map 保证插入序；Object 的数字键会重排
Rust Vec HashMap BTreeMap（B 树） HashMap 默认用 SipHash
Redis —— hash（小对象 listpack） zset（跳表 + 哈希表） zset 小对象也用 listpack（Redis 7.0 起）

⚠️ Java 的 ArrayList 扩容是 1.5 倍，CPython 的 list 约 1.125 倍，HashMap 是 2 倍。 扩容倍数影响内存浪费和扩容频率的权衡：倍数大 → 扩容少但浪费多；倍数小则相反。这就是为什么 HashMap 能预估大小时一定要传初始容量（避免多次 rehash）。

⚠️ HashMap 的初始容量必须传「期望元素数 / 0.75」再向上取整到 2 的幂，否则照样会扩容。放 1000 个元素应传 new HashMap<>(2048)（1000/0.75 ≈ 1334，向上取 2 的幂是 2048）。

⚠️ Go 的 map 在 Go 1.24 换成了 Swiss Table，性能提升明显，但遍历顺序仍然随机（语言规范不保证，且故意加了随机起点）。任何时候都不能依赖 Go map 的遍历顺序，需要有序就显式排序或用 slice。

哈希冲突处理

方案 原理 代表实现 特点
链地址法 冲突元素挂成链表 Java HashMap、Go 旧版 map 实现简单；负载因子可 > 1；缓存不友好
开放寻址 冲突后按探测序列找下一个空槽 Python dict、Go 1.24 Swiss Table、Rust 缓存友好、内存紧凑；负载因子必须 < 1
线性探测 逐个往后找 —— 简单，但容易聚集（clustering）
二次探测 / 双重哈希 按平方或第二个哈希跳 —— 缓解聚集
Robin Hood 探测距离长的「抢」短的槽位 Rust hashbrown 降低最坏探测长度

⚠️ 开放寻址在负载因子高时性能断崖式下跌（探测长度急剧上升），所以 Python/Go 的哈希表在负载因子达到约 2/3 时就扩容，而不是等到满。链地址法可以容忍更高的负载因子，但代价是指针跳转和内存碎片。

⚠️ 哈希表的「最坏 O(n)」不是理论洁癖。 如果 key 是用户可控的（如 HTTP 参数名），攻击者可以构造大量哈希碰撞的 key，把 O(1) 打成 O(n) —— 这就是 HashDoS。防御手段是给哈希函数加随机种子（Java 的 String.hashCode 不加，但 HashMap 会扰动；Python 的 PYTHONHASHSEED 默认随机化）。

三、操作复杂度对照

结构 随机访问 头部插入 尾部插入 中间插入 查找 删除
动态数组 O(1) O(n) 均摊 O(1) O(n) O(n) O(n)
链表（单向） O(n) O(1) O(1)* O(1)** O(n) O(1)**
哈希表 —— —— 平均 O(1) —— 平均 O(1) 平均 O(1)
栈 / 队列 —— —— O(1) —— —— O(1)
二叉堆 —— —— O(log n) —— O(n)（找最小 O(1)） O(log n)
平衡 BST —— —— O(log n) O(log n) O(log n) O(log n)
跳表 —— —— O(log n) O(log n) 平均 O(log n) 平均 O(log n)
B 树 / B+ 树 —— —— O(log n) O(log n) O(log n) O(log n)

* 需维护尾指针 ** 需已持有前驱节点引用

⚠️ 「链表插入是 O(1)」有个前提：你已经拿到了插入位置的节点。 如果只知道下标，定位本身是 O(n)。所以链表在「已知节点、频繁插删」的场景才有优势，做「按下标访问 + 插入」时它全面劣于数组。

⚠️ 数组的「尾部插入均摊 O(1)」不代表每次都快。 扩容那一次是 O(n)，如果业务对尾延迟（p99）敏感，扩容抖动会直接体现在监控上。能预估容量就预先分配（Java new ArrayList<>(n)、Go make([]T, 0, n)、Python 用列表推导而不是循环 append）。

⚠️ 「哈希表删除」在开放寻址实现里不是真的删。 直接置空会切断探测链，导致后面的元素查不到。Python/Go 用的是墓碑标记（tombstone），这也是为什么开放寻址的哈希表在大量删除后需要 rehash 才能恢复性能。

四、跳表与平衡树

维度 跳表 Skip List 平衡 BST（红黑树 / AVL）
查找/插入/删除 平均 O(log n)（概率保证） 最坏 O(log n)（确定性）
实现难度 低（几十行） 高（旋转、着色，易写错）
范围查询 天然有序，遍历友好 需要中序遍历
并发 容易做成无锁（局部修改，无全局旋转） 旋转影响范围大，并发难
内存 期望 2 倍指针（层数分布） 每个节点 2~3 个指针 + 颜色位
排名查询（第 k 大） 可以在节点存跨度 span，O(log n) 需要额外维护子树大小
代表实现 **Redis zset**、Java ConcurrentSkipListMap、LevelDB memtable Java TreeMap、C++ std::map、Linux CFS

⚠️ Redis 用跳表而不是红黑树，主要理由是「范围查询 + 排名 + 并发简单 + 实现简单」 —— 不是性能。ZRANGE / ZRANK 这类操作在跳表上非常自然，在红黑树上要么加额外字段，要么退化。选型时「哪种实现更贴合访问模式」比「哪种理论更快」重要得多。

⚠️ 跳表的 O(log n) 是期望值，不是最坏值。 层数是随机生成的，理论上可能出现极差的分布（概率极低）。要求严格最坏界的场景（如实时系统）用红黑树，工程上跳表足够。

五、选型决策表

需求 选 不要选
按下标随机访问 数组 / slice 链表
频繁在已知位置插删 链表（或直接用 LinkedList / list） 数组
键值查找 哈希表 有序结构
需要有序遍历 平衡树 / 跳表 / BTreeMap 哈希表
需要范围查询 B+ 树（数据库）/ 跳表 哈希表
反复取最大/最小 堆 每次排序
Top-K（k 很小） 大小为 k 的最小堆 全量排序
滑动窗口最值 单调队列（双端队列） 每个窗口扫一遍
FIFO 任务队列 环形缓冲区 / ArrayDeque 链表（缓存不友好）
LIFO 栈 / 数组尾部 ——
去重且量极大 位图 / 布隆过滤器 HashSet（内存爆）
前缀匹配（自动补全） Trie / 有序数组 + 二分 哈希表（前缀不是完整 key）
大量字符串判存在 布隆过滤器前置 + 哈希表兜底 只用哈希表
区间查询（数据库索引） B+ 树 红黑树（磁盘 IO 次数多）

⚠️ ArrayDeque 优于 LinkedList 做队列 —— 即使两者都是 O(1)。LinkedList 每个节点一次内存分配 + 指针跳转，缓存局部性极差，实测吞吐常差 3~10 倍。「复杂度一样」不代表「性能一样」。

⚠️ 数据库索引用 B+ 树而不是红黑树，是因为磁盘 IO 的粒度是「页」而不是「元素」。 B+ 树的节点大小对齐页（通常 4KB/16KB），一次 IO 能载入几百个 key，树高通常只有 3~4 层；红黑树是二叉的，树高 log₂n，1e8 数据要 27 次 IO。复杂度相同，常数差一个数量级。

六、递归的栈开销

每次递归调用都会在栈上压入一个栈帧（返回地址、参数、局部变量）。栈深度就是空间复杂度。

语言 / 场景 尾递归优化 TCO 说明
C / C++ 支持（-O2 及以上） 编译器把尾调用转成跳转
Java / JVM 不支持 语言层面刻意不做（栈追踪会断）
Python 不支持 默认递归上限 1000（sys.setrecursionlimit）
JavaScript (V8) 不支持 规范里有 PTC，但主流引擎未实现
Scala 支持（@tailrec） 编译期校验
Kotlin 支持（tailrec） 编译期转成循环
Go 不支持 TCO，但栈会自动增长 goroutine 初始栈很小，可增长到上限
Erlang / Elixir 支持 语言核心特性

⚠️ Java / Python / JS 都不要指望尾递归优化，把「递归深度 n」当成 O(n) 的额外空间来评估。深度可能达到 1e5 的场景（链表、深树、大图 DFS）必须写成迭代或显式栈，否则必崩。

⚠️ sys.setrecursionlimit 调大不是解法。 CPython 的递归还受C 栈限制，调太高会直接段错误（Segmentation fault）而不是抛异常 —— 崩溃比报错难排查得多。 调大上限只适合「深度确实需要、且能保证不爆 C 栈」的少数场景。

⚠️ 递归的空间复杂度要算「最大栈深度」而不是「调用总次数」。 二叉树 DFS 是 O(h)（h 为树高）而不是 O(n)；但退化成链的树 h = n，所以平衡性直接决定递归是否安全。这也是为什么要用平衡树。

常见坑清单

  • 用大 O 比较小数据量下的性能（常数项被忽略了）
  • 把「均摊 O(1)」当成「每次都快」，忽略扩容抖动对 p99 的影响
  • 把「平均 O(1)」当成最坏保证，不防 HashDoS
  • 拿链表做「按下标访问 + 插入」的场景
  • 用 LinkedList 做队列（比 ArrayDeque 慢数倍）
  • HashMap 不预估容量，放几千个元素触发多次 rehash
  • HashMap 初始容量传期望元素数而不是 元素数 / 0.75
  • 依赖 Go map 的遍历顺序（规范不保证）
  • 用哈希表做范围查询或有序遍历
  • 用红黑树做磁盘索引（应该用 B+ 树）
  • 需要有序集合时用 HashSet + 每次 sort()
  • 只用一个布隆过滤器做权限判断（假阳性会放行）
  • 深度可能上万的场景写递归，指望尾递归优化（JVM / Python / V8 都不支持）
  • 调大 sys.setrecursionlimit 来「修」递归爆栈（可能变成段错误）
  • 用递归总调用次数估算空间复杂度（应该算最大栈深度）
  • Top-K 直接全量排序（k 远小于 n 时用堆）
