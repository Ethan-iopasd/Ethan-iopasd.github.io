开场：索引就是「排好序的目录」

没有索引时，查询只能全表扫描（逐行比对）。有索引时，数据库先在有序结构里定位，再回表取数据。

代价：每个索引都要额外占空间，且每次写入都要维护。索引不是越多越好。

一、B+ 树为什么是默认选择

结构 范围查询 磁盘友好度
哈希表 ❌ 只能等值 一般
二叉搜索树 ✅ 差，树太高
B 树 ✅ 一般
B+ 树 ✅ 好

B+ 树的两个关键设计：

  1. 只有叶子节点存数据，内部节点只存键 —— 同样大小的节点能放更多键，树更矮，磁盘 I/O 更少
  2. 叶子节点用链表相连 —— 范围查询（BETWEEN、>、ORDER BY）可以顺序扫描

一张千万行的表，B+ 树通常 34 层，也就是 34 次磁盘 I/O 就能定位。

二、索引类型

类型 说明 示例
主键索引 聚簇索引，叶子节点存整行数据 PRIMARY KEY (id)
唯一索引 值唯一，允许多个 NULL UNIQUE KEY uk_email (email)
普通索引 无约束 KEY idx_name (name)
联合索引 多列组合，遵循最左前缀 KEY idx_ab (a, b)
覆盖索引 查询列全在索引里，不需要回表 KEY idx_ab (a, b) 满足 SELECT a, b
前缀索引 只索引字符串前 N 位 KEY idx_url (url(20))

聚簇索引 vs 二级索引

所以二级索引查询通常要走两次 B+ 树。 覆盖索引能省掉第二次 —— 这就是它快的原因。

三、联合索引与最左前缀

这个索引相当于建立了 (a)、(a,b)、(a,b,c) 三个索引。

查询条件 能用上索引吗
WHERE a = 1 ✅
WHERE a = 1 AND b = 2 ✅
WHERE a = 1 AND b = 2 AND c = 3 ✅
WHERE b = 2 ❌ 跳过最左列
WHERE b = 2 AND c = 3 ❌
WHERE a = 1 AND c = 3 ⚠️ 只用到 a，c 用不上
WHERE a = 1 AND b > 2 AND c = 3 ⚠️ b 用了范围，c 用不上

⚠️ 范围查询会截断后续列。a = 1 AND b > 2 AND c = 3 里，c 无法走索引。
把等值条件放前面、范围条件放后面，是建联合索引的基本顺序原则。

索引列顺序怎么定

  1. 等值查询的列放前面
  2. 区分度高的列放前面（user_id 比 status 好）
  3. 范围查询的列放最后
  4. 有 ORDER BY 时，让排序列跟在等值列后面可以避免额外排序

四、索引失效的常见场景

1. 在索引列上做运算或函数

2. 隐式类型转换

⚠️ 这个坑很隐蔽。字符串列一定要用字符串查。

3. 前导模糊匹配

4. OR 连接非索引列

5. NOT IN / != / IS NOT NULL（视情况）

优化器判断「走索引再回表」比「全表扫描」更贵时，会主动放弃索引。这不是失效，是优化器的选择 —— 数据量大时才明显。

五、用执行计划自己判断

MySQL

EXPLAIN 输出里重点看这几列：

列 关注点
type 访问类型，性能从好到差：system > const > eq_ref > ref > range > index > ALL
key 实际用了哪个索引，NULL 表示没用
rows 预估扫描行数，越小越好
filtered 过滤后剩余行的百分比
Extra 关键信息，见下表

Extra 里最该注意的：

Extra 值 含义
Using index ✅ 覆盖索引，不用回表
Using where 在存储引擎返回后再过滤
Using filesort ⚠️ 额外排序，没走索引排序
Using temporary ⚠️ 用了临时表，常见于 GROUP BY / DISTINCT
Using index condition 索引下推，一般是好事

type = ALL 或 key = NULL 出现在大表上，就是慢查询的头号嫌疑。

PostgreSQL

重点看：

节点 含义
Seq Scan 全表扫描
Index Scan 走索引 + 回表
Index Only Scan 覆盖索引，最好
Bitmap Heap Scan 索引先建位图再批量回表，适合返回行数中等的情况

EXPLAIN ANALYZE 会真的执行语句。在写操作上要放进事务里再回滚，否则数据就被改了。

六、建索引的实操原则

场景 建议
高频 WHERE 条件 建索引
高频 ORDER BY / GROUP BY 列 考虑建索引，或并入联合索引
区分度极低的列（如性别） 单独建索引意义不大
频繁写入的列 谨慎，索引会拖慢写入
长字符串 用前缀索引 col(20)
大表加索引 生产环境注意锁表风险，用在线 DDL

组合索引 vs 多个单列索引

一个联合索引通常比多个单列索引更有效，因为数据库在一次查询里一般只能用上一个索引（除索引合并外）。

怎么找该建的索引

常见坑清单

  • 在索引列上用函数或运算（WHERE YEAR(created_at) = 2026）
  • 字符串列用数字查，触发隐式类型转换
  • LIKE '%xx' 前导模糊，索引失效
  • 联合索引查询跳过最左列
  • 范围查询后面的列以为还能用索引
  • 用 SELECT * 导致无法走覆盖索引
  • 每个列都单独建索引，实际只用得上一个
  • 给区分度极低的列（性别、状态）单独建索引
  • 只看 EXPLAIN 的 type，忽略 Extra 里的 Using filesort / Using temporary
  • 在大表上直接 ALTER TABLE ADD INDEX，业务高峰期锁表
