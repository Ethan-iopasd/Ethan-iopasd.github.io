开场：K8s 是个「对账」系统

你写的 YAML 是期望状态（desired state）。K8s 里每个控制器都在跑一个循环：

所以你不执行操作，只描述结果。扩容不是「执行扩容」，是把 replicas: 3 改成 5。这也是为什么 kubectl edit 之后 Pod 会自己冒出来 —— 不是你让它起的。

一、控制平面与工作节点

组件 在哪 干什么
kube-apiserver 控制平面 唯一的入口。所有读写都走它，其余组件只跟它对话
etcd 控制平面 存全量集群状态。挂了等于集群失忆
kube-scheduler 控制平面 决定 Pod 落到哪个节点（只决策，不动手）
kube-controller-manager 控制平面 各种控制器循环：Deployment、ReplicaSet、Node 等
cloud-controller-manager 控制平面 对接云厂商（LB、磁盘）
kubelet 每个节点 节点上的执行者。按 PodSpec 起容器、跑探针、上报状态
kube-proxy 每个节点 维护 Service 的转发规则（iptables / IPVS）
容器运行时 每个节点 containerd / CRI-O，真正起容器

⚠️ kube-scheduler 只负责挑节点，实际起容器的是目标节点上的 kubelet。Pod 长时间 Pending 是调度问题，一直 ContainerCreating 是 kubelet / 运行时问题 —— 排查方向完全不同。

二、Pod：为什么不直接跑容器

Pod 是一个或多个容器的集合，共享网络命名空间和存储卷，也是调度的最小单位。

问题 答案
为什么不直接调度容器？ 因为存在「必须同机、共享 localhost」的容器组合（sidecar），需要有个东西把它们绑在一起调度
Pod 里容器共享什么？ 网络命名空间（同一 IP、同一端口空间）、IPC、volumes
不共享什么？ 文件系统、进程命名空间（默认各自独立）
能改 Pod 的镜像吗？ 不能。Pod 的容器镜像、资源等字段不可变，只能重建

同 Pod 内两个容器不能监听同一端口，因为共享网络栈。

⚠️ 别裸用 Pod。 单独创建的 Pod 挂了不会重建，也不会滚动更新。生产上用 Deployment / StatefulSet / DaemonSet 管。

三、Deployment → ReplicaSet → Pod

三层，各管各的：

层 职责 变更时
Deployment 描述「我要 N 个什么版本的 Pod」，管理发布历史 改镜像 → 建一个新 ReplicaSet
ReplicaSet 保证「当前有 N 个 Pod 在跑」 Pod 挂了就补一个
Pod 真正跑的东西 不可变，重建

⚠️ ReplicaSet 不要手改。 手动改 rs 的副本数，下一轮 Deployment 的对账会把你改回来。要改改 Deployment。

⚠️ 不要直接 kubectl edit 线上 Deployment 的镜像。 这会在 revisionHistory 里留一条无意义的记录，且没有对应的代码提交。用 CI 改 YAML 再 apply。

四、滚动更新与回滚

参数 作用 常见配法
maxSurge 更新期间最多多出几个 Pod 1 或 25%
maxUnavailable 更新期间最多几个 Pod 不可用 要零中断就设 0
minReadySeconds Ready 之后还要稳多久才算可用 配合慢启动应用调大
progressDeadlineSeconds 多久没进展就判定失败 默认 600s

⚠️ maxUnavailable: 0 + maxSurge: 0 是死锁组合，两个都为 0 时无法腾出位置，更新会卡住。

⚠️ 回滚只回滚 Pod 模板。 如果新版本同时改了 ConfigMap / Secret / 数据库 schema，rollout undo 不会把那些一起回退。

五、探针三兄弟

探针 失败后果 检查什么
livenessProbe 重启容器 进程是否还活着（死锁、卡死）
readinessProbe 摘掉流量，容器继续跑 现在能不能接请求（依赖就绪、预热完成）
startupProbe 重启容器 是否启动完成；成功前 liveness/readiness 都不执行

默认值（三种探针共用）：

字段 默认值 最小值
initialDelaySeconds 0 0
periodSeconds 10 1
timeoutSeconds 1 1
successThreshold 1 1（liveness/startup 必须是 1）
failureThreshold 3 1

配错的典型后果：

配法 后果
liveness 探依赖的接口（/health 里查数据库） 数据库抖一下 → 全部 Pod 同时重启 → 雪崩
没有 startupProbe，慢启动应用 启动期间被 liveness 反复杀掉，永远起不来
readiness 探得太勤（periodSeconds: 1） 频繁摘挂流量，请求时好时坏
timeoutSeconds 默认 1s，但接口 P99 是 1.5s 随机判定失败，偶发重启
只配 liveness 不配 readiness 滚动更新期间流量打到没起来的 Pod 上

⚠️ liveness 只检查「我还能不能自己恢复」，不要把外部依赖放进去。外部依赖挂了应该走 readiness 摘流量，而不是把容器重启一遍。

⚠️ HTTP 探针 2xx 和 3xx 都算成功（>=200 && <400），返回 302 到登录页的接口会被判为健康。

⚠️ exec 探针每次执行都会 fork 进程。 Pod 密度高、periodSeconds 小时会给节点 CPU 加明显负担，能用 httpGet 就别用 exec。

六、requests / limits 与 QoS

字段 含义 谁用
requests 调度依据，也是 cgroup 的 cpu.shares / 内存软保障 kube-scheduler 挑节点
limits 硬上限 运行时执行

超限的后果不一样：

资源 超过 limits 时
CPU 被限流（throttle），变慢但不会被杀
内存 OOMKilled，容器被杀并重启

QoS 等级（决定节点资源紧张时谁先被驱逐）：

QoS 判定条件 驱逐顺序
Guaranteed 每个容器都有 CPU 和内存的 request 和 limit，且两者相等、都大于 0 最后驱逐
Burstable 不满足 Guaranteed，但至少一个容器设了 request 或 limit 中间
BestEffort 所有容器都没设任何 CPU/内存的 request 和 limit 最先驱逐

⚠️ **不设 requests 就设 limits 会被判为 Burstable**，调度器按 0 来算，节点会超卖，容易整片被驱逐。

⚠️ limits 设得和 requests 一样（Guaranteed）会导致 CPU 被硬限流。CPU 密集服务通常留出弹性，比如 requests: 500m / limits: 2。

⚠️ QoS 在 Pod 创建时确定，之后不可改。 想改 QoS 必须重建 Pod。

七、kubectl 高频命令

目的 命令
看列表（带标签筛选） kubectl get pods -l app=web -o wide
看全量 YAML kubectl get deploy web -o yaml
看事件（排查首选） kubectl describe pod <pod>
看日志 kubectl logs -f <pod> -c <container> --tail=200
看上一次崩溃的日志 kubectl logs <pod> --previous
进容器 kubectl exec -it <pod> -- sh
临时调试容器 kubectl debug -it <pod> --image=busybox --target=<container>
端口转发 kubectl port-forward svc/web 8080:80
应用配置 kubectl apply -f app.yaml
看差异（不提交） kubectl diff -f app.yaml
删除 kubectl delete -f app.yaml
看资源占用 kubectl top pod / kubectl top node
看事件流 kubectl get events --sort-by=.lastTimestamp -w
切命名空间 kubectl config set-context --current --namespace=dev

⚠️ kubectl apply 会保留上次 apply 的 last-applied-configuration 注解。 如果之前有人 kubectl edit 改过某个字段，apply 之后可能又变回去 —— 排查「配置莫名回滚」先看这个注解。

常见坑清单

  • 裸用 Pod，节点重启后不会自动重建
  • 手改 ReplicaSet 的副本数，被 Deployment 对账改回去
  • liveness 探针里查数据库，外部抖动导致全线重启
  • 没配 startupProbe，慢启动应用被 liveness 反复杀掉
  • maxSurge: 0 且 maxUnavailable: 0，滚动更新直接卡住
  • 只设 limits 不设 requests，调度按 0 算，节点严重超卖
  • CPU 的 requests 等于 limits，QoS 是 Guaranteed 但被硬限流
  • 以为 Guaranteed 就不会被 OOMKilled（超 limit 照样杀）
  • 改了 ConfigMap 以为 Pod 会重启（挂成环境变量的不会）
  • 用 kubectl logs 看崩溃前的日志（应该加 --previous）
