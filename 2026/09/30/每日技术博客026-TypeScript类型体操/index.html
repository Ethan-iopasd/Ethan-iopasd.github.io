开场：类型体操只有三个工具

工具 语法 解决什么
条件类型 T extends U ? X : Y 分支判断
infer T extends F<infer U> ? U : never 从结构里提取类型
映射类型 { [K in keyof T]: ... } 批量改写属性

标准库里的工具类型全是用这三样拼的。

标准库工具类型的真实实现

工具类型 实现
Partial<T> { [P in keyof T]?: T[P] }
Required<T> { [P in keyof T]-?: T[P] }
Readonly<T> { readonly [P in keyof T]: T[P] }
Pick<T, K> { [P in K]: T[P] }（K extends keyof T）
Record<K, T> { [P in K]: T }（K extends keyof any）
Omit<T, K> Pick<T, Exclude<keyof T, K>>
Exclude<T, U> T extends U ? never : T
Extract<T, U> T extends U ? T : never
NonNullable<T> T & {}
ReturnType<T> T extends (...args: any) => infer R ? R : any
Parameters<T> T extends (...args: infer P) => any ? P : never

⚠️ Omit 是不是 Pick 的反操作那么简单：它先 Exclude<keyof T, K> 再 Pick，所以 K 可以是 T 上不存在的键（因为 K extends keyof any 而不是 keyof T）。这意味着 Omit<User, 'typo'> 不会报错 —— 打错字编译器不会救你。

TypeScript 对递归类型实例化有深度上限，超了报：

上限取决于递归形态，实测（TypeScript 7.0.2）差异极大：

形态 实测上限
非尾递归 约 50 层

尾递归消除（TypeScript 4.5+）

关键是把「累积结果」放进额外的类型参数，让递归调用出现在条件类型的尾位置。编译器就能把它优化成循环。

输入收缩型同理，天然是尾递归：

⚠️ 尾递归消除不适用于「模板字面量累加器」。像 Repeat<S, N, \${A}${S}`>这种每轮都产生**新字符串字面量类型**的写法，实测连N = 2都直接报 TS2589 —— 每次迭代都在制造新类型，编译器无法把它折叠成循环。要重复字符串就换成元组累加器 + 最后Join`。

⚠️ 触发 TS2589 的常见场景是递归遍历深层 JSON / 嵌套对象类型。修法优先级：改成尾递归 → 给递归加深度计数上限参数 → 降低类型精度（用 unknown 截断）。别硬堆递归深度，编译时间会成倍上涨，而且阈值是编译器实现细节，跨版本会变。

五、tsconfig 的 strict 家族

strict 是一个总开关，开启后同时打开下面全部子选项：

子选项 作用
strictNullChecks null / undefined 独立成类型，不再被忽略
strictFunctionTypes 函数参数逆变检查（只对 function 语法生效，方法语法不受影响）
strictBindCallApply 检查 call / bind / apply 的参数类型
strictPropertyInitialization 类属性必须在构造函数里初始化
noImplicitAny 推断为 any 的地方报错
noImplicitThis 隐式 any 的 this 报错
alwaysStrict 按严格模式解析并输出 "use strict"
useUnknownInCatchVariables catch (e) 的 e 变成 unknown（4.4+）
strictBuiltinIteratorReturn 内置迭代器 return 类型为 undefined

⚠️ noUncheckedIndexedAccess 打开后 Record<string, T> 和数组索引全部变成 T | undefined，存量代码会炸出一大片错误。建议新项目一开始就开，老项目评估成本后再开。

⚠️ exactOptionalPropertyTypes 打开后 { a?: string } 不能写 { a: undefined }。给可选属性传 undefined 是常见写法，会直接编译失败。

六、skipLibCheck 的取舍

skipLibCheck 默认关闭，需要显式开启。它跳过所有 .d.ts 文件的类型检查。

维度 开启 关闭
编译速度 明显更快（大项目差距可观） 慢
三方库 .d.ts 冲突 忽略，不报错 可能报出一堆无关错误
自己写的 .d.ts 也会被跳过 会被检查
风险 库之间的类型不兼容被掩盖 无

⚠️ skipLibCheck: true 不会跳过你的业务 .ts 代码检查，只跳 .d.ts。真正危险的是自己手写的声明文件（declare module、全局类型扩展）也一起被跳过 —— 这类文件建议单独放一个 tsconfig 用 skipLibCheck: false 校验。

七、项目引用与构建

大仓库用 references 把代码拆成独立编译单元。**references 是 extends 唯一不继承的顶层属性**。

配置 作用 默认
composite 允许被 references 引用，隐含 declaration + incremental 关闭
incremental 写 .tsbuildinfo，只重编变更部分 关闭
tsBuildInfoFile 指定 .tsbuildinfo 位置 由 outDir 推导
references 声明依赖的项目 关闭

⚠️ composite 要求 include 里的文件全部被显式覆盖，并且不允许 outDir 和源文件混在一起。报 Referenced project must have setting "composite": true 基本都是漏了这个开关。

⚠️ 根 tsconfig.json 里加 "files": [] 是为了让根项目不编译任何文件，只当引用入口。不加的话根项目会把所有子项目源码再编一遍。

与打包器配合的两个开关

⚠️ isolatedModules 下 export { SomeType } 会报错 —— 单文件转译器分不清类型和值，必须写 export type { SomeType }。verbatimModuleSyntax 把这个规则变成了硬约束。

常见坑清单

  • 条件类型分发到联合成员上，结果类型比预期多了一堆分支
  • 以为 ToArray<string \| number> 是 (string \| number)[]，实际是 string[] \| number[]
  • 想关掉分发却忘了用 [T] extends [U] 包元组
  • 在非条件类型的 extends 子句里写 infer，语法直接报错
  • 键重映射里写 Capitalize<K>，漏了 string &
  • Omit<T, K> 传了不存在的键，以为编译器会拦住
  • 用 Omit 处理联合类型，得到的结果不是预期的联合
  • 递归类型不写累加器参数，几十层就触发 TS2589
  • 硬堆递归深度换取类型精度，编译时间暴涨
  • 以为 noUncheckedIndexedAccess 属于 strict 家族，实际要单独开
  • 以为 exactOptionalPropertyTypes 属于 strict 家族，可选属性赋 undefined 报错
  • 开 skipLibCheck 后忘了自己手写的 .d.ts 也不再被检查
  • 项目引用漏了 composite: true，报 “Referenced project must have…”
  • 根 tsconfig 没写 "files": []，子项目源码被重复编译
  • isolatedModules 下 export { SomeType } 报错，忘了改 export type
