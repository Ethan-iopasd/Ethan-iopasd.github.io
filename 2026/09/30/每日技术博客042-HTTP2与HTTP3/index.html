开场：三代协议解决的是同一个问题的三层

版本 多路复用在哪一层 剩下的瓶颈
HTTP/1.1 ❌ 没有，靠开多条 TCP 连接凑 应用层队头阻塞 + 连接数限制
HTTP/2 TCP 连接内的 stream（二进制分帧） TCP 层队头阻塞（丢包就全停）
HTTP/3 QUIC 连接内的 stream（跑在 UDP 上） 各 stream 独立，丢包只影响自己

一句话：HTTP/2 把并发从「多条连接」搬到了「一条连接里的多个流」，但底下还是 TCP；HTTP/3 干脆换掉 TCP。

一、HTTP/1.1 到底卡在哪

两个限制叠加：

限制 数值 / 表现
浏览器同域名并发 TCP 连接数 约 6 条（不同浏览器略有差异）
一条连接上同一时刻 只能处理一个请求

所以第 7 个请求必须排队等前面的连接空出来。

再叠加 HTTP/1.1 的响应必须按请求顺序返回：如果第 1 个请求的响应很慢，后面已经准备好的响应也发不出去 —— 这就是应用层队头阻塞（HOL blocking）。

历史上的规避手段（现在大多是负担）：

手段 原理 副作用
域名分片 用 a.example.com、b.example.com 突破 6 连接限制 多份 DNS / TCP / TLS 握手
雪碧图 / 资源合并 减少请求数 缓存粒度变粗，改一个文件全失效
内联小资源 减少请求数 无法单独缓存，HTML 变大

⚠️ 这三条在 HTTP/2 下是负优化，见第五节。

二、HTTP/2：二进制分帧与多路复用

HTTP/1.1 是纯文本、按行解析、边界靠 \r\n。HTTP/2 全部改成二进制帧（frame），帧头固定 9 字节：

概念 含义
Frame 最小传输单位，带类型和 stream id
Stream 一条逻辑上的双向通道，对应一次请求/响应
Message 一次完整的请求或响应，由若干帧组成
Connection 一条 TCP 连接，承载所有 stream

关键点：帧可以乱序发送，接收端按 stream id 重新组装。所以同一条 TCP 连接上可以同时跑几十上百个请求，不用再排队。

HPACK 头部压缩

HTTP/1.1 每个请求都重发一遍 User-Agent、Cookie、Accept-*，动辄几百字节到几 KB。HTTP/2 用 HPACK（RFC 7541）压缩：

机制 说明
静态表 61 个预定义的高频头部（:method: GET、:status: 200 等）
动态表 连接内逐条累积的表，重复出现的头部只发索引
Huffman 编码 对字面量再做一次熵编码

索引编码后，一个重复的 user-agent 可能只占 1–2 字节。

⚠️ 动态表是连接级状态，不是请求级。这也带来 HPACK 的压缩侧信道问题（CRIME/BREACH 类攻击的变种）。这也是 HTTP/3 换用 QPACK 的原因之一 —— 见第四节。

服务端推送：已经废弃

HTTP/2 的 PUSH_PROMISE 让服务端主动推送资源，理论上省掉一次往返。实践中没做出来收益，反而经常推送客户端已经缓存的资源，浪费带宽。

时间线 事件
2022 年 8 月 Chrome 宣布移除 HTTP/2 Server Push 支持
Chrome 106 起 默认停用，PUSH_PROMISE 被忽略

替代方案是 103 Early Hints 和 <link rel="preload">。

⚠️ 新项目不要再实现服务端推送。103 Early Hints 是当前推荐的做法。

优先级：也被移除了

HTTP/2 最初的流优先级（priority tree / PRIORITY 帧）实现复杂、各家实现不一致，实际收益有限。RFC 9113 移除了优先级方案，改为可选的 PRIORITY_UPDATE 帧和 priority 头字段（Extensible Prioritization Scheme，RFC 9218）。

HTTP/2 里被禁用的东西

头部 / 机制 HTTP/2 下的状态
Connection ❌ 禁止出现
Keep-Alive ❌ 禁止
Proxy-Connection ❌ 禁止
Upgrade ❌ 禁止（版本切换走 ALPN）
Transfer-Encoding ❌ 禁止（HTTP/2 自带帧长）
TE ⚠️ 只允许 TE: trailers
Host ⚠️ 被 :authority 取代

⚠️ 这些是连接专属头部，在 HTTP/2 里连接是共享的、不能按请求协商，所以协议直接禁掉。手写代理或老网关转发时如果原样透传 Connection，会被判定为协议错误（PROTOCOL_ERROR）直接断连。

三、HTTP/2 没解决的问题：TCP 层队头阻塞

多路复用只解决了应用层的排队。底下还是一条 TCP 连接，而 TCP 保证字节流的严格顺序。

结果：一个 TCP 段丢失，这条连接上所有 stream 全部暂停，包括那些数据完整的。

丢包率 HTTP/2 相对 HTTP/1.1
0% HTTP/2 明显更快
低（<1%） 大致持平
高（>2%） HTTP/2 可能更慢 —— 单连接把所有鸡蛋放在一个篮子里

⚠️ 这就是 HTTP/2 在移动网络 / 弱网下表现不如预期的根本原因。也是 HTTP/3 存在的全部理由。

四、HTTP/3：把传输层换成 QUIC

维度 HTTP/2 HTTP/3
传输层 TCP QUIC（基于 UDP）
标准 RFC 9113 RFC 9114（QUIC 本体 RFC 9000）
队头阻塞 TCP 层仍存在 消除，stream 独立
头部压缩 HPACK（RFC 7541） QPACK（RFC 9204）
加密 TLS 1.2 / 1.3 独立握手 TLS 1.3 内建（RFC 9001），无法明文
建连 TCP 握手 + TLS 握手（2 RTT） 首次 1 RTT
会话恢复 需要 TCP + TLS 各自恢复 0-RTT
连接标识 四元组（IP + 端口） Connection ID

为什么 HTTP/3 没有 TCP 队头阻塞

QUIC 的 stream 是传输层原生概念，每个 stream 有自己的序号和重传逻辑。丢包只影响丢失的那个 stream。

⚠️ QPACK 就是为了配合这一点：HPACK 的动态表要求严格顺序，而 QUIC 的 stream 是乱序的。QPACK 把动态表更新拆成独立的单向 stream，允许解码器等待但不阻塞其它 stream。

0-RTT 的代价

0-RTT 让恢复连接时可以在第一个包里就带应用数据，省掉一次往返。代价是重放攻击：

⚠️ 0-RTT 数据可以被攻击者录制后原样重放。 所以：

  • 只允许幂等请求走 0-RTT（GET、HEAD）
  • POST、支付、下单这类有副作用的请求必须禁用 0-RTT
  • 服务端侧要有独立的防重放机制（ticket 一次性、时间窗）

连接迁移

TCP 连接由四元组 (源 IP, 源端口, 目的 IP, 目的端口) 标识，手机从 Wi-Fi 切到 4G 就断。QUIC 用 Connection ID 标识连接，IP 变了连接还在。

五、域名分片为什么在 HTTP/2 下有害

维度 HTTP/1.1 HTTP/2 / HTTP/3
连接数 越多越好（突破 6 条限制） 1 条就够
域名分片 有效 负优化
每个新域名的代价 一次 TCP + TLS 握手 同样要握手，但无法复用已建立的连接
多路复用 不适用 被切碎到多条连接，每条都在等 TCP 窗口
HPACK / QPACK 动态表 不适用 每个域名各一份，压缩率下降

⚠️ 具体损失：每个额外域名都要重新握手（几十到几百毫秒），HPACK 动态表要重新累积（前几十个请求的头部压缩率接近无效），TCP 慢启动要重新爬一遍拥塞窗口。HTTP/2 站点应该把资源收敛到同一个域名下。

其他 HTTP/1.1 时代的优化在 HTTP/2 下的结论：

手段 HTTP/2 下
域名分片 ❌ 有害
雪碧图 ❌ 收益消失，缓存粒度变差
大量内联 ⚠️ 谨慎，优先用多路复用拉小文件
资源合并 ⚠️ 收益下降
减少请求数 ❌ 不再是目标，减少字节数和关键路径才是

六、TLS 握手与会话复用

HTTP/2 在 TLS 上通过 ALPN 协商（h2），HTTP/3 也是（h3）。明文 HTTP/2（h2c）浏览器基本不用。

复用机制 省掉 说明
Session ID 一次完整握手 老方案，TLS 1.2
Session Ticket 一次完整握手 TLS 1.2/1.3，服务端无状态
PSK（TLS 1.3） 一次往返 TLS 1.3 恢复为 1-RTT
0-RTT（TLS 1.3 / QUIC） 两次往返 有重放风险

⚠️ TLS 1.3 的会话恢复票据（session ticket）默认可能只发 1–2 张，或者不发送（取决于服务端配置和 num_tickets）。高并发短连接场景下票据不够用会导致大量完整握手，直接推高延迟。

七、怎么确认线上跑的是哪个版本

方法 命令 / 位置
浏览器 DevTools Network 面板加 Protocol 列，显示 h2 / h3 / http/1.1
curl curl --http2 -I https://example.com，看状态行是 HTTP/2 200
curl 强制 HTTP/3 curl --http3 -I https://example.com（需要 curl 编译时带 HTTP/3 支持）
openssl openssl s_client -alpn h2 -connect ... 看协商结果
响应头 Alt-Svc: h3=":443"; ma=86400 表示服务端宣告支持 HTTP/3

DevTools 里 Protocol 列默认隐藏，右键表头勾选即可。

⚠️ Alt-Svc 是 HTTP/3 生效的前提。服务端不发这个头，浏览器根本不知道可以用 HTTP/3，会一直走 HTTP/2。而且它是跨连接生效的 —— 首次访问走 HTTP/2，下次才可能升级到 HTTP/3。

⚠️ 看到 http/1.1 时先查 ALPN 是否协商成功（证书、SNI、TLS 版本都可能导致降级），再查中间是否有设备在解密或降级。

常见坑清单

  • 以为 HTTP/2 解决了所有队头阻塞，忽略 TCP 层那一段
  • 弱网场景盲目上 HTTP/2，丢包时反而比 HTTP/1.1 慢
  • 继续在 HTTP/2 站点上做域名分片
  • 继续用雪碧图 / 资源合并来「减少请求数」
  • 网关原样透传 Connection / Keep-Alive / Transfer-Encoding，触发 PROTOCOL_ERROR
  • 在 HTTP/2 里手动发 Host 头，而不是让客户端生成 :authority
  • 还在实现 HTTP/2 服务端推送
  • 还在依赖 HTTP/2 的流优先级（RFC 9113 已移除该方案）
  • 允许有副作用的 POST 走 0-RTT，留下重放漏洞
  • 服务端不发 Alt-Svc，却以为 HTTP/3 已经生效
  • 看到 http/1.1 只怀疑 CDN，不去查 ALPN 协商
  • 只把 HTTP/3 开在 CDN 边缘，回源仍是 HTTP/1.1 且没做连接池
  • 以为 HTTP/3 一定比 HTTP/2 快，忽略 QUIC 在部分网络被 UDP 限速的情况
  • 压测只测 0% 丢包，没测 1%–3% 丢包下的表现
