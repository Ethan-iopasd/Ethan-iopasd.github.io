四 REST 与 API 设计 本篇

开场：REST 的约束只有一条是硬的

REST 常被当成「URL 好看点」，实际真正能省事的是统一接口带来的两件事：

  1. 方法语义固定 → 网关、缓存、重试库能自己判断哪些请求可以安全重试
  2. 状态码语义固定 → 监控、熔断、告警不用为每个业务定制

其余的风格问题（复数、连字符）怎么选都行，但整个 API 必须自洽。

一、资源命名

规则 好 差
用名词，不用动词 POST /orders POST /createOrder
集合用复数 /orders/{id} /order/{id}
层级表达从属 /orders/{id}/items /orderItems?orderId=
多词用连字符 /audit-logs /auditLogs、/audit_logs
全小写 /users /Users
不用文件扩展名 /users + Accept /users.json

动作类操作是唯一该出现动词的地方，两种处理方式：

方式 写法 适用
子资源 + 控制器 POST /orders/{id}/cancel 通用，可读性好
状态字段变更 PATCH /orders/{id} {"status":"cancelled"} 状态机简单时

⚠️ 别把 ID 放进查询串：/orders?id=123 和 /orders/123 是两套缓存键，CDN 会各存一份。资源标识放路径，筛选条件放查询串。

⚠️ 层级不要超过两层。/a/{id}/b/{id}/c/{id}/d 这种，客户端拼 URL 时容易错，且换个关联路径就要改代码。深关联用查询参数。

二、方法与幂等性

方法 安全（Safe） 幂等（Idempotent） 请求体 典型用途
GET ✅ ✅ ❌ 读取
HEAD ✅ ✅ ❌ 只取响应头
OPTIONS ✅ ✅ ❌ 能力探测 / CORS 预检
PUT ❌ ✅ ✅ 整体替换
DELETE ❌ ✅ ⚠️ 通常无 删除
PATCH ❌ ❌ ✅ 部分更新
POST ❌ ❌ ✅ 创建 / 非幂等动作
  • 安全 = 不改变服务端状态，可以随便重试、可以预取
  • 幂等 = 执行一次和执行 N 次，最终状态相同

连发 3 次，结果都是「42 号用户是 Ethan」—— 幂等。

连发 3 次，会建出 3 个用户 —— 不幂等。

⚠️ PATCH 不幂等，这点常被忽略。PATCH {"balance": {"$inc": 100}} 连发两次就加了两百。幂等的部分更新应该用 PUT 语义，或干脆上幂等键。

⚠️ PUT 是整体替换：没在 body 里出现的字段会被置空 / 重置为默认值。想做部分更新用 PATCH，别用 PUT 假装。

⚠️ DELETE 的幂等性：第一次返回 204，第二次应该返回 404 或 204，但不能报 500。实现上要能容忍「已不存在」。

⚠️ GET 绝不能有副作用。爬虫、预取、CDN 预热都会主动打 GET，如果 GET /orders/{id}/cancel 能取消订单，你的订单会被随机取消。

三、状态码与业务错误的边界

情况 用 不用
参数格式 / 类型错 400 200 + {code:400}
参数格式对但语义非法（邮箱已被占用） 409 / 422 400 一把梭
未登录 / token 无效 401 403
已登录但无权限 403 401
资源不存在 404 200 + 空对象
方法不支持 405 + Allow 头 404
业务规则冲突（余额不足、状态不允许） 409 / 422 500
限流 429 + Retry-After 403
服务端未预期错误 500 200 + msg:"系统繁忙"

判定标准很简单：

问题 结论
同样的请求重试一次会不会成功？ 会 → 5xx；不会 → 4xx
这个错误是调用方写错了，还是运行时状态不对？ 调用方 → 400/422；状态 → 409
中间层（缓存、重试、监控）需要知道这是错误吗？ 需要 → 必须用 4xx/5xx

⚠️ 业务错误也要用 HTTP 状态码。用 200 + 自定义 code 会让缓存把失败响应缓存住、重试库不重试、监控统计不到错误率。业务错误码可以作为补充，不能替代状态码。

四、分页：offset 与 cursor

维度 offset / page cursor（游标）
参数 ?page=3&size=20 ?cursor=eyJ...&size=20
能否跳页 ✅ ❌ 只能顺序
深度性能 随偏移线性变差 稳定
数据变动时的稳定性 差（插入/删除会串页、漏项） 好
能否返回总数 ✅ 容易 ⚠️ 需要额外计数（可缓存）
适用 后台管理、数据量小 Feed、导出、大数据集

⚠️ offset 分页在数据变动时会漏项和重复。用户翻到第 2 页时如果有人往前面插了一条，第 2 页的第一条就会重复出现。cursor 分页不会 —— 它的锚点是一条具体记录。

⚠️ cursor 必须是不透明字符串（服务端 base64 编码的内部游标），不要让客户端拼装 ?after_id=123。否则客户端会开始依赖你的内部字段，改动就是破坏性变更。

⚠️ total 在大数据集上很贵。按需返回：管理后台要，Feed 不要。或者加 ?with_total=true 显式请求。

size 必须有上限：

建议 值
默认 size 20
size 上限 100（列表）/ 1000（导出接口，走异步）

五、版本演进

方案 写法 优点 缺点
URL 路径 /v1/users 直观、好调试、CDN/网关好路由 URL 会变，违反「URI 标识资源」
自定义 Header API-Version: 1 URL 稳定 浏览器直接访问难调试
Accept 内容协商 Accept: application/vnd.api.v2+json 最 RESTful 工具链支持差、易写错
查询参数 ?version=1 简单 与缓存键耦合

实践结论：用 URL 路径版本号，原因不是它最规范，而是它最容易在网关、日志、监控、CDN 里被正确处理。

⚠️ 大版本才进 URL，小改动不要。/v1/users → /v2/users，中间的所有兼容性演进都靠「只增不改不删」完成：

变更类型 是否破坏性
新增可选请求字段 ❌ 不破坏
新增响应字段 ❌ 不破坏（客户端应忽略未知字段）
新增枚举值 ⚠️ 可能破坏（客户端 switch 没 default 就崩）
修改字段类型（string → int） ✅ 破坏
重命名字段 ✅ 破坏
删除字段 ✅ 破坏
收紧校验规则 ✅ 破坏
改变默认排序 ✅ 破坏

⚠️ 新增枚举值是隐性破坏性变更。所以枚举要么明确文档化「客户端必须容忍未知值」，要么新增时走新字段。

⚠️ 别维护超过 2 个大版本。同时维护 v1/v2/v3 的测试矩阵和维护成本会指数上升。发 v2 时就给 v1 定下线日期，并在响应头里提前告知。

六、过滤、排序、字段选择的规范化

需求 约定 示例
精确筛选 ?field=value ?status=active
多值 逗号分隔 ?status=active,pending
范围 field[gte] / field[lte] ?created_at[gte]=2026-01-01
排序 sort=field / -field 表降序 ?sort=-created_at,name
字段裁剪 fields=a,b,c ?fields=id,name
全文搜索 固定参数名 q ?q=elasticsearch

⚠️ 排序字段必须白名单。直接把 sort 参数透传给 ORM 或数据库就是注入漏洞（?sort=id; DROP TABLE users）。白名单外一律 400。

⚠️ 范围查询用 [gte] 这种方括号形式要 URL 编码成 %5Bgte%5D，很多客户端库不会自动编码。嫌麻烦就用 created_at_gte 下划线形式，统一即可。

七、幂等键：解决重复提交

网络超时、用户连点、网关重试都会导致同一个逻辑请求被发多次。POST 不幂等，所以要靠 Idempotency-Key（IETF 草案，非正式 RFC）补上。

服务端流程：

要点 说明
保存原始响应（含状态码） 重放要返回一样的结果
校验请求体指纹 防止 key 被误用在不同请求上
设置 TTL 24 小时是常见选择，别永久存
客户端生成 key 用 UUID，同一次业务操作复用同一个 key
幂等键 ≠ 去重 它只保证「同 key 同结果」，不解决业务层重复

⚠️ 幂等键必须和写入在同一个事务/原子操作里。先写 key 再写业务数据，中间崩了会留下「key 存在但业务没执行」的脏状态，后续重试直接返回缓存结果，业务永远不执行。

⚠️ 并发同 key 请求要加锁或走唯一索引，不能靠「先查再写」。两个请求同时查不到，就会同时执行。

八、批量操作

方案 写法 返回
批量创建 POST /users/batch 207 或多状态列表
批量删除 DELETE /users?ids=1,2,3 204 或结果列表
批量部分更新 PATCH /users/batch 逐项结果

⚠️ 批量接口必须逐项返回结果，不能只有一个总状态码。部分成功是常态，客户端需要知道哪几条失败了。

⚠️ 让客户端为每项传一个 client_id（临时标识），服务端回传。否则客户端只能靠数组下标对应结果，一旦服务端重排或过滤顺序就全错。

⚠️ 批量接口要有条数上限（比如 100/500），超过返回 413 Payload Too Large 或 400。无限批量等于给自己留一个 DoS 入口。

九、统一错误响应体

用 RFC 9457 Problem Details（取代 RFC 7807）：

字段 含义 是否必填
type 错误类型的稳定 URI 建议
title 人类可读的简短摘要 建议
status HTTP 状态码，与响应行一致 建议
detail 本次错误的具体说明 可选
instance 本次出错的资源路径 可选
扩展字段 errors[]、trace_id 等 自定义

⚠️ type 是给机器看的稳定标识，一旦发布就不能改。detail 是给人看的，可以随便改。把错误信息塞进 title 并让客户端做字符串匹配，是典型的错误设计。

⚠️ trace_id 必须返回。否则线上报错时，用户截图给你，你只能靠时间戳去日志里大海捞针。

十、限流响应头

RateLimit-* 系列目前是 IETF 草案（draft-ietf-httpapi-ratelimit-headers），不是正式 RFC；Retry-After 则是 RFC 9110 里的正式字段。

头 含义
RateLimit-Policy 配额定义（100;w=60 = 每 60 秒 100 次）
RateLimit-Limit 当前窗口的配额上限
RateLimit-Remaining 剩余次数
RateLimit-Reset 距窗口重置的秒数

被限流时：

⚠️ **429 必须带 Retry-After**，否则客户端只能盲目重试，反而加剧拥堵。

⚠️ 限流成功响应也要带剩余配额头。只在被限流时才告知，客户端无法提前退避，只能撞墙后才知道。

⚠️ 限流维度要明确：按 IP、按 用户、还是按 API Key？写在文档里。不写清楚，客户端会以为「按用户」，实际被 NAT 后的共享 IP 拖累。

常见坑清单

  • URL 里用动词（/getUsers、/createOrder）
  • 集合和单体命名不一致（/orders 但 /order/123）
  • 层级嵌套超过两层
  • GET 带副作用，被预取 / 爬虫触发
  • 用 PUT 做部分更新，未传的字段被清空
  • 忽略 PATCH 不幂等，$inc 类更新被重试放大
  • DELETE 第二次返回 500 而不是 404/204
  • 用 200 + 自定义 code 表达业务错误
  • 401 / 403 混用
  • 限流返回 403 而不是 429，且不带 Retry-After
  • 深分页用 offset，数据变动时串页漏项
  • cursor 用明文自增 ID，客户端开始依赖内部字段
  • size 无上限，被一个请求拉爆数据库
  • 每次小改动就发一个新 URL 版本号
  • 新增枚举值当成了非破坏性变更
  • 老版本不给下线时间，无限期维护
  • sort / filter 字段不做白名单，直接透传给数据库
  • POST 无幂等键，用户连点造成重复下单
  • 幂等键的写入和业务写入不在同一事务里
  • 并发同 key 请求靠「先查再写」，没加锁或唯一索引
  • 批量接口只返回一个总状态码，不返回逐项结果
  • 批量接口用数组下标对应结果
  • 批量接口没有条数上限
  • 错误响应体格式各接口不统一
  • 错误响应里没有 trace_id
