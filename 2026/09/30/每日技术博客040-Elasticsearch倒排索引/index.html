开场：ES 同时维护两套索引

理解 ES 的查询行为，只需要记住它有两条独立的数据通路：

结构 形态 用途
倒排索引（inverted index） 词 → 文档 id 列表 全文检索（match）
正排索引（doc values） 文档 id → 值 排序、聚合、脚本取值

检索快，是因为倒排索引直接按词定位文档，不需要扫描全部文档。排序和聚合快，是因为 doc values 按列存储，可以顺序读。

⚠️ 这两套结构分开维护。所以「能搜到」不代表「能聚合」，反之亦然。后面所有的坑都能追到这个根源上。

一、倒排索引 vs 正排索引

维度 倒排索引 正排索引（doc values）
映射方向 词 → 文档 文档 → 值
存储 磁盘，segment 内 磁盘，列式
擅长 检索、相关性打分 排序、聚合、脚本
是否分词产物 ✅ 分词后建立 ❌ 按原值
text 字段 ✅ 有 ❌ 没有
keyword 字段 ✅ 有（整个值当一个词） ✅ 有

⚠️ text 字段没有 doc values —— text 和 annotated_text 是明确不支持的例外。所以在 text 字段上排序或聚合会直接报错。这就是动态映射会给字符串自动补一个 keyword 子字段的原因。

二、分词器（analyzer）三件套

一个 analyzer 由三部分组成，按顺序执行：

组件 作用 示例
Character filter 处理原始字符 html_strip 去 HTML 标签
Tokenizer 切分成词 standard、ik_smart、whitespace
Token filter 改写词 lowercase、stop、stemmer

标准分词器 standard 对中文是逐字切分，这是「中文搜不到」最常见的原因。

三、text 与 keyword 的取舍

维度 text keyword
是否分词 ✅ ❌ 整个值作为一个词
用途 全文检索 精确匹配、排序、聚合、过滤
doc values ❌ 没有 ✅ 有
排序 / 聚合 ❌ 报错 ✅
典型查询 match term、terms、prefix
大小写 由 analyzer 决定 原样保留

title 因此同时具备两种能力：title 走全文检索，title.keyword 走排序和聚合。

⚠️ 动态映射给字符串生成的 keyword 子字段带 ignore_above: 256 —— **超过 256 字符的值不会被索引进 keyword**，聚合时会「丢数据」。长文本要么显式加大 ignore_above，要么别聚合它。

四、match 与 term：为什么 term 查 text 查不到

这是 ES 最高频的困惑。

查询 是否分析查询词 适用字段
match ✅ 用字段的 search analyzer 处理 text
term ❌ 原样拿去查倒排索引 keyword、数值、日期、布尔
terms ❌ 原样，多个值 同上

原因很直接：倒排索引里存的是分词后的 mysql、索、引、优、化，从来没有存过「MySQL 索引」这个完整字符串。term 不分词，拿原文去查，自然查不到。

⚠️ 三条速记：

  1. term 查 text 字段 → 基本查不到
  2. term 查 keyword → 必须大小写、空格完全一致（除非配了 normalizer）
  3. 该用 term 还是 match，取决于字段类型，不取决于「想不想精确匹配」

五、bool 查询：must / should / must_not / filter

子句 逻辑 参与算分 可缓存
must AND ✅ ❌
should OR ✅ ❌
filter AND ❌ 分数恒为 0 ✅ 可被缓存
must_not NOT ❌ ✅

把**不做相关性判断的条件全部放进 filter**，有两个直接收益：

  1. 不计算分数，省 CPU
  2. filter context 下的子句会被缓存，重复查询直接复用

⚠️ minimum_should_match 的默认值取决于上下文：如果 bool 里没有 must 也没有 filter，默认是 1；否则默认是 0。后者意味着 should 只影响排序、不参与筛选 —— 很多人以为加了 should 就是「必须满足」，实际不是。

六、mapping 不能改字段类型

字段类型一旦建好就不能修改，改类型必须重建索引。

想做的事 能不能直接做
改字段类型（text → keyword） ❌
改 analyzer ⚠️ 对已有数据不生效，需重建索引
新增字段 ✅
给已有字段加 fields 子字段 ⚠️ 可以，但对已有数据不生效
删除字段 ❌ 只能重建

七、_source 与 doc_values

项目 _source doc_values
存什么 写入时的原始 JSON 每个字段的列式值
用途 返回文档内容、_reindex、update 排序、聚合、脚本
能否关闭 ✅（但失去 update / _reindex 能力） ✅（该字段将无法排序 / 聚合）
是否分词 ❌ 原样 ❌ 原样

⚠️ "_source": false 是常见的「省空间」操作，代价是**无法 update、无法 _reindex**。除非数据完全可以从外部重建，否则不要关。

常见坑清单

  • 中文用 standard 分词器，逐字切分导致搜不到
  • 索引和查询用了不同的 analyzer
  • 在 text 字段上做排序或聚合，直接报错
  • 用 term 查 text 字段，怎么都查不到
  • 用 term 查 keyword 时大小写不一致
  • 动态映射的 keyword 子字段 ignore_above 默认 256，长值聚合丢数据
  • 该进 filter 的条件写进 must，白白算分且不缓存
  • 以为 should 是「必须满足」，忽略了 minimum_should_match 的默认值
  • 想改字段类型，试图直接改 mapping
  • 应用直接访问物理索引名，改 mapping 就要发版
  • 关掉 _source 后才发现无法 update / _reindex
  • 全量返回 _source，网络开销大
