七 内存管理、GC 与内存泄漏排查 本篇

开场：一句话结论

内存泄漏不是「忘了 free」——JS 里根本没有 free。泄漏的唯一形态是：有一条从 GC Root 出发、你以为是断的、其实还连着的强引用链。所以排查泄漏从来不是找「谁占了内存」，而是找 retainer（保留者）：谁还指着它。

一、V8 的堆不是一个堆

V8 按分代假说（大多数对象死得早）把堆切开，不同区域用不同回收器：

区域 装什么 回收器
New Space（新生代） 新分配的小对象 Scavenger（默认）/ Minor MS
Old Space（老生代） 熬过若干轮回收的对象 Mark-Sweep-Compact
Large Object Space 超过阈值的大对象（大数组、大 Buffer） 直接归老生代逻辑，不参与复制
Code Space JIT 后的机器码 单独回收
Read-Only Space 内建对象、字面量 从不回收

新生代：Scavenger 是复制式的

默认回收器 Scavenger 用半空间（semi-space）设计：

  1. 新生代切成 To-Space 和 From-Space 两半，新对象只往 To-Space 里放
  2. To-Space 满了 → 互换角色，原来的 To 变成 From
  3. 从 From-Space 追踪存活对象，复制到 To-Space；熬过上一轮的直接晋升（promote）到老生代
  4. 复制是压缩式的，新生代内部没有碎片

⚠️ 代价是「总有一半空间是空的」。所以新生代很小 —— 默认几 MB 到几十 MB 级别。

V8 还有一个非默认的替代方案：--minor-ms 开启的 Minor Mark-Sweep。它不复制对象（非移动式），改为标记 + 清扫，存活率高的整页直接晋升到老生代。--minor-ms 是实验性开关，不是默认值 —— 别在生产里想当然地以为 V8 已经不用 Scavenger 了。

老生代：Mark-Sweep-Compact 三阶段

阶段 做什么 能否并发
Marking 从 root set 出发标记可达对象 ✅ 增量 + 并发标记
Sweeping 把死对象空间挂进 free-list ✅ 并发清扫
Compaction 选高度碎片化的页做搬移压缩 部分并行

关键点：Compaction 是启发式的，只压缩碎片严重的页。老生代里大量长寿命对象不会每次都被搬来搬去。

并行 / 增量 / 并发，三个词别混

术语 主线程在干什么 是否 STW
Parallel 和 worker 一起做 GC ✅ 是（只是摊薄了）
Incremental 间隙性地做一小段 GC ✅ 是（切成很多小段）
Concurrent 继续跑 JS，worker 后台回收 ❌ 基本不是

这三个是 V8 把停顿压下去的全部手段。剩下的停顿点只有两处：标记收尾（finalization） 和 并行压缩/指针更新。你能感知到的卡顿，基本都出在这。

写屏障：分代回收能成立的前提

老生代对象指向新生代对象时，新生代回收必须知道这个引用存在 —— 否则会把活对象当垃圾。V8 用写屏障（write barrier）在赋值时把这类引用记进 Remembered Set（OLD_TO_NEW）：

三种屏障，各管一件事：

屏障 作用
Generational（Old-to-New） 记进 Remembered Set，供 Scavenger 找活的新生代对象。始终开启
Marking 防止增量标记期间出现「黑对象指向白对象」漏标
Evacuation（Old-to-Old） 压缩时记录需要改写的指针

⚠️ 所以往老对象上频繁挂新对象（比如长命 Map 里不停塞新 value）不是零成本的 —— 每次赋值都有屏障开销。

二、什么才叫「泄漏」

GC 只认可达性。一个对象只要从 GC Root 能走到，它就活着，哪怕你永远不会再用它。

GC Root 有哪些

Root 说明
执行栈上的局部变量 函数返回后自动消失
全局对象 / 模块顶层作用域 模块作用域是常驻的，比 window 更隐蔽
闭包捕获的变量 只要闭包活着，捕获的整个环境都活着
正在运行的定时器 / 回调注册表 回调引用的对象全部被保活
已注册的事件监听器 同上
DOM 树的文档引用 节点在树上就活着

强引用 vs 弱引用

引用方式 能否阻止回收 可枚举 典型用途
普通属性 / Map key ✅ 阻止 ✅ 需要确定性的缓存
WeakMap / WeakSet ❌ 不阻止 ❌ 给对象挂元数据、DOM 节点缓存
WeakRef ❌ 不阻止 — 弱缓存、大对象池
FinalizationRegistry — — 回收后做清理（时机不确定）

WeakRef / FinalizationRegistry 是 ES2021 引入的。两个坑：

⚠️ WeakRef.deref() 的结果可能在任何时候变成 undefined，甚至同一次 GC 前后两次调用结果不同。必须每次都判空，不能缓存 deref 结果。

⚠️ FinalizationRegistry 的回调时机完全由引擎决定，可能在页面关闭前都不触发。不要拿它做业务逻辑的清理（比如关闭数据库连接），只能做「尽力而为」的兜底。

DevTools 里可以直接验证：Memory 面板的 Summary 视图搜 Detached，或者看底部状态栏的 DOM Nodes / JS event listeners 计数 —— 反复打开关闭弹窗，这两个数只涨不跌就是泄漏。

6. Node.js 特有：监听器无上限

Node.js 默认在同一个 emitter 上超过 10 个监听器时打印 MaxListenersExceededWarning。这个警告本身就是泄漏信号，不要用 setMaxListeners(0) 把它关掉。

四、浏览器侧：DevTools 三件套

Memory 面板的三种 profile 用途完全不同：

Profile 抓什么 适合回答
Heap snapshot 某一刻的完整对象图 + retainer 链 谁还引用着它
Allocation instrumentation on timeline 每段时间内分配且未被回收的对象 哪个操作在漏
Allocation sampling 采样版，开销低 长时间跑、性能敏感

三快照法（官方推荐的两快照法 + 一步基线）

Node.js 官方文档给的两快照流程，搬到浏览器一样成立：

  1. 等页面加载完、bootstrap 结束（几秒内）
  2. 先操作一次你要怀疑的功能 —— 这一步的分配是预热，不算泄漏
  3. 取快照 A
  4. 再重复操作若干次，中间别做别的
  5. 取快照 B
  6. Memory 面板先加载 A、再加载 B，选中 B，把顶部下拉从 Summary 切到 Comparison
  7. 找大的正 delta，点开底部 retainer 面板看引用链

⚠️ 顺序不能反 —— 必须先加载旧快照，DevTools 才会把新快照标为「较新」，Comparison 的 delta 方向才是对的。

⚠️ 取快照会全停顿，堆大的话可能卡几秒到几十秒，且快照本身占内存。

控制台里的两个小工具

queryObjects 是判断「有没有泄漏」最快的办法：反复创建销毁组件，然后数实例。数字不回落就是漏了。

performance.memory：能用但别依赖

属性 含义
jsHeapSizeLimit 该上下文可用堆上限（字节）
totalJSHeapSize 已分配堆总量
usedJSHeapSize 当前活跃段

⚠️ MDN 明确标注：非标准 + legacy，仅 Chromium 系可用，且数值不可靠 —— 页面共享堆时会高估，用 worker / 跨站 iframe 时会低估。为了隐私，Chrome 默认还对返回值做分桶/量化（想要精确值要启动 --enable-precise-memory-info）。

替代方向是 performance.measureUserAgentSpecificMemory()，需要跨源隔离（COOP/COEP）才可用。别把 performance.memory 写进生产监控的告警阈值。

五、Node.js 侧：先量，再抓

第一步：process.memoryUsage()

字段 含义 排查价值
rss 进程占用的物理内存（含堆外） 涨得比 heapUsed 快 → 问题不在 JS 堆
heapTotal V8 堆已申请总量 只涨不跌说明堆在扩张
heapUsed V8 堆实际使用 泄漏的核心指标
external 绑到 C++ 对象的内存 原生插件、Buffer 相关
arrayBuffers Buffer / ArrayBuffer 占用 二进制处理泄漏看这个

⚠️ rss 和 heapUsed 分属两个世界。**Buffer 分配在堆外**，heapUsed 完全看不见它 —— 只盯 heapUsed 会漏掉一整类泄漏。

第二步：看 GC 到底有没有在回收

判断标准：如果 GC 频率越来越高、每次回收后 heapUsed 的谷底还在抬升，那就是真泄漏，不是「GC 还没跑」。

第三步：抓堆快照

方式 版本要求 适用场景
--inspect + DevTools Memory 面板 所有维护中版本 本地、可交互
--heapsnapshot-signal=SIGUSR2 v12.0.0+ 生产容器里按信号触发
v8.writeHeapSnapshot() v11.13.0+ 代码里主动触发（HTTP handler / 信号）
Inspector Protocol — 从进程外远程触发

⚠️ 官方明确警告：取快照时主线程全停，堆大时可能超过一分钟；而且快照在内存里构建，可能让堆占用翻倍，直接把进程撑爆。

在生产上取快照，前提是这个实例崩了不影响可用性（多副本、可摘流）。

另外别把 writeHeapSnapshot() 挂在公开路由上 —— 那等于给外部一个 DoS 入口。

第四步：对比快照

拿 Chrome DevTools 打开 .heapsnapshot，按上面「三快照法」的步骤切 Comparison 视图找正 delta，再顺着 retainer 链往上走到 GC Root。

第五步：调堆参数

⚠️ 两个高频误解：

  1. --max-old-space-size 只是把上限抬高，不解决泄漏。 它把 OOM 时间往后推，代价是每次 Major GC 停顿更长。
  2. 它管不了容器 cgroup 限制。 Docker / K8s 里堆上限和容器内存 limit 是两套东西，--max-old-space-size 调大反而更容易被 cgroup OOMKilled。堆上限应该略低于容器 limit。

--max-semi-space-size 调大能减少 Minor GC 次数，但新生代越大，单次 Scavenge 停顿越长，是拿延迟换吞吐。

六、Vue 3 / 前端实战清单

Ethan 的 Django + Vue3 栈里，泄漏基本出在这几个地方：

场景 泄漏点 修法
onMounted 里挂 window 监听 卸载时没解绑 onUnmounted 里 ac.abort()
watch 外部数据源 watch 返回的 stop 没调用 组件内 watch 会自动停；在 setup 外建的 effect 必须手动 stop
自建响应式订阅 副作用跑在组件外 用 effectScope() 包起来，卸载时 scope.stop()
<keep-alive> 缓存所有页面 每个页面实例都常驻 配 :max="10"，或按需 include
超长列表全量渲染 几万个 vnode + 组件实例 虚拟滚动，只渲染视口内
全局事件总线 订阅没退订 卸载时 off，或改用 props / pinia
大对象塞进 reactive 深层代理 + 常驻 用 shallowRef / markRaw 包大而不可变的数据

⚠️ markRaw / shallowRef 能省掉深层代理开销，但代理没了，响应式也没了。只对「只读的大数据」用，比如图表数据、静态配置。

常见坑清单

  • 用 Map 给 DOM 节点 / 短命对象做缓存，而不是 WeakMap
  • 模块级数组 / 对象当缓存，没有容量上限和淘汰策略
  • setInterval / 递归 setTimeout 的句柄没保存、没清理
  • window / document / 全局 emitter 上的监听器没解绑
  • 闭包为了一个字段，把整个大对象保活
  • 移除 DOM 节点时，忘了清掉持有它的数组 / 回调列表
  • Node.js 里往全局 emitter 上反复 on，无视 MaxListenersExceededWarning
  • 用 setMaxListeners(0) 把监听器警告关掉，而不是修泄漏
  • 缓存 WeakRef.deref() 的返回值，不做判空
  • 用 FinalizationRegistry 做业务清理（关闭连接、写盘）
  • 只看 heapUsed，忽略 rss / external / arrayBuffers（Buffer 在堆外）
  • 拿 performance.memory 当生产监控指标（非标准、Chromium only、数值被量化）
  • 在生产环境随手取堆快照，没考虑全停顿 + 堆翻倍的风险
  • 把 writeHeapSnapshot() 挂在公开路由上
  • 以为 --max-old-space-size 能修泄漏（它只是推迟 OOM）
  • Docker 里堆上限设得比容器 limit 还大，结果被 cgroup OOMKilled
  • 对比快照时先加载了新快照，Comparison 的 delta 方向反了
  • 用 --minor-ms 以外的理由，以为 V8 默认已经不是 Scavenger 了
