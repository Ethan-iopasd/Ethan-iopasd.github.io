六 浏览器渲染、DOM 与性能优化 本篇

开场：一句话结论

页面卡不卡只取决于三件事：关键渲染路径有多长、每帧主线程剩多少预算、以及你让浏览器重排了几次。前两件是设计问题，第三件基本全是自己写出来的。

一、渲染流水线：Style → Layout → Paint → Composite

一次「把页面画出来」要走完四步，改动不同属性会从不同的步骤重新开始：

你改的属性 从哪一步重跑 代价 例子
几何属性 Layout 最高（重排） width height margin padding top left font-size display
绘制属性 Paint 中（重绘） color background box-shadow border-radius outline
合成属性 Composite 最低 transform opacity filter

帧预算：主线程要在每帧里完成「执行 JS → Style → Layout → Paint」，超出就是掉帧。

刷新率 单帧预算 长任务判定线
60 Hz 16.7 ms > 50 ms
120 Hz 8.3 ms > 50 ms

⚠️ transform / opacity 走合成是有前提的：浏览器要为它单独提升一个合成层。滥用 will-change、translateZ(0) 会让层数暴涨，显存和合成开销反而更大 —— 只在动画开始前加，动画结束后移除。
⚠️ will-change: transform 是性能提示不是性能修复。加在几十个元素上，等于让浏览器给几十个层各留一份内存。
⚠️ filter / backdrop-filter / mix-blend-mode 也会提升层，且 backdrop-filter 的代价远高于普通合成。

二、强制同步布局（Layout Thrashing）

浏览器本来会把写操作攒起来，在下一帧统一算一次布局。但只要你读一个几何属性，它就必须立刻把之前所有写操作 flush 掉，才能给你准确值 —— 这就是强制同步布局。

读操作（触发 flush） 写操作（使布局失效）
offsetTop / offsetLeft / offsetWidth / offsetHeight style.width = ...
clientWidth / clientHeight classList.add/remove
scrollTop / scrollLeft / scrollWidth appendChild / removeChild
getBoundingClientRect() innerText / innerHTML / textContent
getComputedStyle() style.setProperty
offsetParent / scrollIntoView() focus()

⚠️ getComputedStyle() 也是读操作，而且它返回的是 CSSStyleDeclaration 活对象 —— 循环里反复调、每次再取属性，等于每轮都强制一次布局。
⚠️ el.style.width = el.offsetWidth + 'px' 这种写法看着无害，循环里就是 O(n) 次重排。
⚠️ 用 DevTools 的 Performance 面板录一段，紫色 Layout 块密集且窄就是典型读写交替；一整块很宽则是 DOM 太大或样式选择器太复杂。

三、批量 DOM 操作

做法 重排次数 事件监听 适用
循环 appendChild 攒到一帧，但每次插入都触发 mutation 记录 保留 少量节点
DocumentFragment 1 次 保留 批量插入（推荐）
replaceChildren(...nodes) 1 次 全部重建 整体替换
innerHTML = html 1 次 全部丢失 静态内容、且必须转义
insertAdjacentHTML 1 次 保留已有 局部追加
赋值方式 是否解析 HTML XSS 风险 速度
textContent 否 无 最快
innerHTML 是 有（用户输入直接拼 = XSS） 慢
insertAdjacentHTML 是 有 中

⚠️ innerHTML 会重建整棵子树 —— 输入框里已经输入的内容、滚动位置、手动挂的事件监听全部丢失。表单区域永远不要用 innerHTML 重绘。
⚠️ textContent 不是 innerText：innerText 会触发重排（它需要真实渲染结果），textContent 不会。
⚠️ replaceChildren 与 innerHTML = '' 都会清掉子元素上的监听器，Safari 14 之前不支持 replaceChildren。

四、事件：委托、passive 与节流

方案 监听器数量 内存 动态新增节点
每个子元素各绑一个 N 高 要重新绑
委托到父元素 1 低 自动生效
框架的 onClick 冒泡 1（挂在根） 低 自动生效

⚠️ 非 passive 的 touchmove 会阻塞滚动：浏览器必须等你的 handler 跑完，才知道你会不会 preventDefault()。这一等就是肉眼可见的滚动延迟。
⚠️ Chrome 56+ 只对 window / document / body 上的 touchstart / touchmove / wheel / mousewheel 默认设为 passive；绑在其他元素上不是默认，必须显式写 { passive: true }。
⚠️ 用了 { passive: true } 之后再调 preventDefault() 不报错，只是静默失效 —— 需要阻止默认行为就别加 passive。

滚动场景 老写法 现代写法
元素进入视口 scroll + getBoundingClientRect() IntersectionObserver
元素尺寸变化 resize + 轮询 ResizeObserver
滚动方向/进度 scroll + rAF 节流 scroll + { passive: true } + rAF
视差动画 scroll 里直接改样式 IntersectionObserver 标记 + transform

⚠️ IntersectionObserver 的回调里不要同步改被观察元素的尺寸 —— 会触发 ResizeObserver 的 ResizeObserver loop completed with undelivered notifications 错误。
⚠️ 滚动里做 requestAnimationFrame 节流时，回调里必须再读一次滚动位置，不要用事件对象里的缓存值（它是触发时刻的值，不是绘制时刻的）。

五、让浏览器跳过屏幕外的活：contain 与 content-visibility

contain 值 隔离了什么 典型场景
layout 子元素不影响外部布局 独立组件、动画块
paint 子元素不画到边框外 有 overflow 的容器
style 计数器/变量不外泄 少用
size 元素尺寸与子元素无关 需自己写死宽高
content = layout paint style 通用推荐
strict = layout paint style size 固定尺寸的第三方嵌入

浏览器支持（Baseline 2024）：content-visibility Chrome 85+ / Firefox 125+ / Safari 18+；contain-intrinsic-size 的 auto 关键字 Chrome 117+ / Firefox 117+ / Safari 17+。不支持的浏览器静默忽略，页面照常渲染。

⚠️ 不写 contain-intrinsic-size 会直接制造 CLS —— 屏幕外元素被当成 0 高，滚动到时突然撑开。
⚠️ contain: size 如果不给固定尺寸，元素会塌成 0。
⚠️ 屏幕外且被跳过的内容不会出现在 Ctrl+F 查找结果里，部分读屏软件也可能不播报。长文/信息流没问题，正文关键的锚点章节别用。
⚠️ content-visibility: hidden 保留 DOM 状态和滚动位置，display: none 不保留 —— SPA 里切 Tab 用前者，性能更好且不丢状态。

六、LCP 的两大来源：图片与字体

手段 影响 LCP 影响 CLS
首屏图 fetchpriority="high" + preload 明显改善 无
首屏图 loading="lazy" 明显恶化 无
图片写 width/height 或 aspect-ratio 无 明显改善
字体 font-display: swap 无 会引入一次换字偏移
size-adjust / 匹配回退字体度量 无 明显改善
广告位/iframe 预留固定高度 无 明显改善

⚠️ 首屏大图千万不要 loading="lazy" —— 浏览器会等布局算完才发起请求，LCP 直接推迟一个 RTT 以上。
⚠️ preload 加错 as（比如字体写成 as="font" 但没带 crossorigin）会导致下载两次，比不 preload 更慢。
⚠️ 图片没有 width/height 是 CLS 的头号来源；现代浏览器会用它算 aspect-ratio 占位，比 CSS 手写更可靠。

七、Core Web Vitals：三个指标与阈值

指标 衡量 Good Needs Improvement Poor
LCP 加载（最大内容元素绘制） ≤ 2.5 s 2.5 ~ 4.0 s > 4.0 s
INP 交互响应（所有点击/点按/按键） ≤ 200 ms 200 ~ 500 ms > 500 ms
CLS 视觉稳定性（累积布局偏移） ≤ 0.1 0.1 ~ 0.25 > 0.25

判定口径：取第 75 百分位的页面加载，且移动端与桌面端分开统计；三项全部达标才算通过。

INP 在 2024 年成为稳定的 Core Web Vital，取代了 FID。

维度 FID INP
观测范围 只测第一次交互的输入延迟 观测整段会话的所有交互
时间跨度 输入延迟 输入延迟 → 事件处理 → 绘制下一帧
取值 首次输入延迟 最长的一次交互延迟（忽略离群值）
状态 已淘汰 稳定
症状 对应指标 首要手段
首屏白很久才出现大图/大标题 LCP 图片压缩 + fetchpriority + 减少阻塞渲染的 CSS/JS
点了没反应、输入卡顿 INP 拆长任务、scheduler.yield() / setTimeout 让出主线程、减少同步布局
页面自己跳动、点错按钮 CLS 图片写尺寸、广告位预留、字体度量对齐

⚠️ 实验室数据 ≠ 真实用户数据：Lighthouse 是模拟的单一环境，CrUX / RUM 才是第 75 百分位真值。两者不一致时以 RUM 为准。
⚠️ INP 不观测 hover / scroll / zoom，只算点击、点按、按键。页面没有这三种交互就不会有 INP 值。
⚠️ hadRecentInput 为 true 的布局偏移（用户交互后 500ms 内）不计入 CLS —— 别用它来掩盖问题，用户仍然看得见跳动。

八、用 DevTools 定位，而不是猜

面板 看什么 结论
Performance 主线程长任务（> 50ms，红角标） JS 执行阻塞了绘制
Performance 紫色 Layout 块窄而密集 读写交替 → 强制同步布局
Performance 紫色 Layout 一整块很宽 DOM 过大 / 选择器过复杂
Performance 绿色 Paint 反复出现 改的是绘制属性而非合成属性
Rendering Paint flashing 哪些区域被重绘
Rendering Layer borders 合成层数量是否失控
Coverage 未使用的 CSS/JS 字节 首屏加载了多少用不到的东西

⚠️ 用无痕模式 + CPU 4x/6x 降速录制，否则本机跑得太快，什么都看不出来。
⚠️ 「Layout 很宽」不等于重排次数多 —— 先看 Layout 块数量，再看宽度。

常见坑清单

  • 用 left / top / width 做动画，而不是 transform / opacity
  • 给几十个元素都加 will-change，导致合成层爆炸
  • 动画结束后忘了移除 will-change
  • 循环里读写交替（el.style.width = el.offsetWidth + ...）
  • 循环里反复调 getComputedStyle()
  • 用 innerText 读文本（会触发重排），该用 textContent
  • 用 innerHTML 重绘表单区域，丢掉输入内容和事件监听
  • 拼用户输入进 innerHTML，制造 XSS
  • 逐个 appendChild 插入上百个节点，不用 DocumentFragment
  • 给每个列表项单独绑事件，而不是事件委托
  • 滚动/触摸监听不加 { passive: true }
  • 加了 passive: true 还指望 preventDefault() 生效
  • 用 scroll + getBoundingClientRect() 做曝光埋点，不用 IntersectionObserver
  • 用 ResizeObserver 回调里改被观察元素尺寸，触发 loop 错误
  • 首屏 LCP 大图加了 loading="lazy"
  • preload 字体时漏了 crossorigin，导致下载两次
  • 图片不写 width/height，CLS 全靠运气
  • 用 content-visibility: auto 却不写 contain-intrinsic-size
  • 对固定尺寸元素写 contain: size 却没给宽高，元素塌成 0
  • 在正文锚点章节用 content-visibility: auto，Ctrl+F 找不到内容
  • 拿 Lighthouse 分数当真实用户指标
  • 以为 INP 会把 hover / 滚动算进去
