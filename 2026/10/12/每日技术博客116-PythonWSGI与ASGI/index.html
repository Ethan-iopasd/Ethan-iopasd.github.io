九 WSGI、ASGI 与 Web 服务请求生命周期 本篇

开场：一句话结论

WSGI 是同步协议，一个 worker 一次只能处理一个请求；ASGI 是异步协议，一个 worker 一个事件循环可以同时挂着成千上万个连接。 选错协议、或选错 Gunicorn 的 worker class，同一份代码的吞吐能差一个数量级 —— 而这一切都不报错，只是慢。

真正决定上限的不是框架，是三样东西：协议（WSGI/ASGI）× worker class（sync/gthread/gevent/asgi）× 视图里有没有阻塞调用。

ASGI 的入口是一个异步可调用对象，通过 receive / send 流式收发事件：

维度 WSGI ASGI
规范 PEP 3333（v1.0.1） ASGI 3.0（2019-03-04）
入口形态 app(environ, start_response) 同步 async app(scope, receive, send) 单可调用
输入 environ dict，一次性给全 scope dict + receive() 事件流
输出 返回 bytes 可迭代对象 send() 事件流，可分块

连接类型 只有 HTTP（一次请求） HTTP / WebSocket / Lifespan 统一抽象
并发模型 线程 / 进程 / 协程补丁（gevent） 原生 asyncio 事件循环
长连接 靠 worker 或补丁支持 协议层原生（SSE、WebSocket、长轮询）
HTTP/2、HTTP/3 不支持（只能靠前置代理） 支持，但取决于具体服务器实现

⚠️ ASGI 2.0 和 3.0 的应用形态不一样：2.0 是「同步第一层调用返回一个可 await 的实例」，3.0 才是现在的单可调用。写中间件时如果按 2.0 写，会出现「明明实现了却报 500」的诡异现象。asgiref.compatibility 里有检测并转换旧风格的工具。

⚠️ WSGI 里 start_response 返回的 write 可调用对象几乎没人用，也别用 —— 它会绕过中间件对响应头的处理，且与延迟发送冲突。老老实实 return [body]。

二、ASGI 的 scope / receive / send 长什么样

这三个东西不是黑盒，搞清楚字段之后，写中间件、做鉴权、做链路追踪都不用猜。

HTTP 连接的 scope：

键 必需 说明
type ✅ "http" / "websocket" / "lifespan"
asgi.version ✅ ASGI 版本，缺省视为 "2.0"
asgi.spec_version ❌ 子规范版本，HTTP 子规范当前为 2.5
http_version ✅ "1.0" / "1.1" / "2" / "3"
method ✅ 大写的 HTTP 方法
path ✅ 已 percent-decode 的路径，不含查询串
query_string ✅ ? 之后的原始字节，未解码
headers ✅ [(b"name", b"value"), ...]，全是 bytes
scheme ❌ "http" / "https"，缺省 "http"
raw_path ❌ 未解码的原始路径字节
root_path ❌ 子路径挂载点，等价 WSGI 的 SCRIPT_NAME
client ❌ [host, port]
server ❌ [host, port]，unix socket 时是 [path, None]
state ❌ lifespan 命名空间的副本，用于跨中间件传值

事件（receive 收 / send 发）：

事件 方向 关键字段
http.request 收 body（bytes，缺省 b""）、more_body（bool）
http.disconnect 收 客户端断开后触发，用于长轮询清理
http.response.start 发 status（int）、headers（必须小写）
http.response.body 发 body、more_body
lifespan.startup / shutdown 收 应用初始化 / 清理

⚠️ scope 里的 headers 是 bytes，不是 str。 用 dict(scope["headers"]) 拿到的 key 是 b"host" 这种。要么自己 decode，要么用框架提供的 Headers 包装类（Starlette 的 Headers(scope=scope)、Django 的 HttpRequest.headers）。

⚠️ http.response.start 一旦发出，响应头和状态码就锁死了。 之后再想改状态码（比如视图中途发现权限不足）只能靠框架的异常处理在 start 之前拦截。这也是为什么中间件要在 send 外面包一层 hook。

⚠️ Lifespan 不是可选项而是必需项：数据库连接池、Redis 客户端、后台任务都该在 lifespan 里建和关。Uvicorn 的 --lifespan auto（默认）会探测应用是否支持；Django 3.0 那代的 ASGI 应用不支持 lifespan，启动时会看到 “ASGI lifespan unsupported” 之类的提示。

三、请求生命周期：从 nginx 到视图

每一层都会改变并发上限，也都会吃掉一点信息：

层 会丢什么 怎么补
nginx X-Forwarded-Proto 之外的真实协议信息 设 proxy_set_header X-Forwarded-*
ASGI server 真实客户端 IP 被代理 IP 覆盖 --proxy-headers + --forwarded-allow-ips
框架 scope 里的 bytes headers 被包装成对象 用框架的 headers 属性，别回头读 scope
中间件 同步中间件会引入线程切换 写成 async def，或接受开销

Django 在 ASGI 下的中间件适配规则（官方文档原文语义）：

情况 Django 的行为
异步视图 + 全异步中间件 全链路同一个事件循环，无额外线程
异步视图 + 夹了同步中间件 该中间件被丢到独立线程里跑，跑完再切回异步
同步视图 + ASGI server 视图在适配出的线程里跑（thread_sensitive 语义）
全是同步中间件和视图 进入中间件栈前只切换一次
异步视图跑在 WSGI 下 每个请求新建一个一次性事件循环，长请求吃不到任何异步好处

四、Gunicorn worker class 怎么选

Gunicorn 是 pre-fork 模型：一个 arbiter 管一群 worker，arbiter 自己不碰客户端 socket。worker 类型决定并发模型。

worker class -k 取值 并发模型 keep-alive 适用
sync sync（默认） 每 worker 同时 1 个请求 ❌ CPU 密集型，且前面有 nginx 缓冲
gthread gthread 每 worker 一个线程池 ✅ 混合负载、中等并发
gevent gevent greenlet，--worker-connections 控并发 ✅ I/O 密集、WebSocket、流式
ASGI asgi 原生 asyncio 事件循环 ✅ FastAPI / Starlette / Quart 等 ASGI 框架
uvicorn worker uvicorn.workers.UvicornWorker 原生 asyncio（第三方实现） ✅ 同上，用 Uvicorn 当引擎
tornado tornado Tornado IOLoop ✅ 原生 Tornado 应用

worker 数量公式（Gunicorn 官方）：

官方同时强调：不要过度扩 worker —— 通常 4~12 个 worker 就足够扛重流量，worker 开太多反而浪费资源、降低吞吐（进程切换 + 每个进程独立的连接池和内存）。运行中可以发信号动态调：

信号 作用
TTIN worker +1
TTOU worker −1
HUP 重新加载配置、优雅重启 worker
CHLD 子进程异常退出时由 arbiter 补位
TERM / QUIT 优雅 / 快速关闭

⚠️ --threads 对 ASGI worker 完全无效。 Gunicorn 官方明确：ASGI worker 的并发由 --worker-connections 控制（默认 1000），--threads 不生效。给 ASGI worker 配 --threads 4 是最常见的无效调优。

⚠️ sync worker 不支持 keep-alive，且必须有缓冲代理。 官方原话：sync 是「一次一个请求」，连接在响应后关闭，生产环境需要 nginx / HAProxy 这类缓冲代理挡在前面，否则慢客户端会把 worker 占满。

⚠️ gevent 需要给 C 扩展打补丁。 例如 PostgreSQL 的 psycopg 需要 psycogreen，否则驱动内部仍是阻塞的，greenlet 调度不起来。且任何依赖阻塞语义的代码在 gevent 下行为会变。

Gunicorn 的 ASGI worker 还带这些参数（Uvicorn worker 没有）：

进程管理 内置 外部（自己起 --workers 或配 systemd） 内置
HTTP/2 ✅（需 SSL + h2） ❌ ✅
WebSocket ✅ ✅ ✅
Lifespan ✅ ✅ ✅
uvloop ✅ ✅ ✅

五、Uvicorn 的生产参数（含默认值）

Uvicorn 的默认值几乎全是「开发友好、生产不友好」，部署时必须显式覆盖。

参数 默认值 生产建议
--host 127.0.0.1 容器内 0.0.0.0，裸机保持回环 + nginx
--port 8000 显式指定
--workers $WEB_CONCURRENCY 或 1 按 (2×CPU)+1 或容器 CPU limit 定
--reload False 生产禁用，且与 --workers 互斥
--limit-concurrency 无限制 设成能承受的上限，超了立刻 503
--backlog 2048 高流量入口按需调大（OS accept 队列）
--timeout-keep-alive 5（秒） 反代后建议 ≥ 反代的 keepalive
--timeout-graceful-shutdown — 配合 K8s 的 terminationGracePeriodSeconds
--limit-max-requests 无限制 防内存泄漏，配合 --limit-max-requests-jitter（默认 0）
--proxy-headers 启用 启用，但必须收紧 --forwarded-allow-ips
--forwarded-allow-ips 127.0.0.1、::1 写清反代 IP，绝不写 *
--lifespan auto 保持 auto
--interface auto ASGI 应用保持 auto
--loop auto auto（有 uvloop 就用）
--http auto auto（有 httptools 就用）
--http2 False 需配合 --http zttp
--root-path "" 子路径部署时必填

--limit-concurrency 和 --backlog 不是一回事，别搞混：

--limit-concurrency --backlog
层级 应用层 OS 层（listen() 的 accept 队列）
超限行为 立刻返回 503，不入队 连接排队等待 accept
用途 保证内存占用可预测 扛瞬时流量尖峰
典型误用 设太小 → 正常流量被打 503 设太大 → 排队连接全超时

⚠️ --reload 与 --workers 互斥，同时用会直接报错。--reload 依赖文件监听，是开发特性，生产上还会因为 watchfiles 轮询额外吃 CPU。

⚠️ --proxy-headers 默认是开着的，但只信任 --forwarded-allow-ips 里的来源（默认 127.0.0.1 / ::1）。如果 Uvicorn 跑在容器里、nginx 在另一个容器，默认值会导致 request.client.host 拿到的是代理 IP。把它写成网段，不要写 * —— 写了 * 意味着任何人伪造 X-Forwarded-For 都能冒充任意 IP。

⚠️ Uvicorn 自带的 WSGI 适配模式已废弃，要跑 WSGI 应用请用 a2wsgi。别用 --interface wsgi。

六、异步视图里最容易踩的：同步调用

事件循环里任何一次阻塞，都会让该 worker 上所有并发请求一起卡住。这不是「慢一点」，是「并发归零」。

常见阻塞源，按出现频率排：

阻塞调用 为什么阻塞 替代
requests.get() 纯同步 socket httpx.AsyncClient
time.sleep() 线程休眠 asyncio.sleep()
同步 DB 驱动 / 同步 ORM 阻塞 IO 异步驱动，或 sync_to_async
open() 读大文件 阻塞 IO asyncio.to_thread
subprocess.run() 等子进程 asyncio.create_subprocess_exec
CPU 密集计算 占着 GIL 不撒手 进程池 run_in_executor(ProcessPoolExecutor)
threading.Lock.acquire() 阻塞等待 asyncio.Lock

Django 的异步安全保护：同步 ORM API 被标记为 async-unsafe，在有活跃事件循环的线程里直接调用会抛 SynchronousOnlyOperation。正确写法是包一层：

sync_to_async 参数 行为
thread_sensitive=True（默认） 与同一上下文里其他 thread-sensitive 调用共用同一个线程，单请求内串行
thread_sensitive=False 每次调用新开线程，调用完销毁

为什么默认是 True：数据库适配器通常要求「在创建它的同一个线程里访问」，而大量既有 Django 代码假设「所有代码在同一个线程」。代价是单请求内的多个同步调用会串行化 —— 但这只影响同一个请求，不同请求各有自己的 per-context worker 线程，互不阻塞。

想提并发，**应该加大连接池，而不是关掉 thread_sensitive**。

sync_to_async 的开销量级（Django 官方）：请求内路径约几十微秒，冷启动路径约几百微秒。相对毫秒级请求不明显，但在 GIL 争用下会随活跃线程数放大。

⚠️ 异步模式下事务不可用。 Django 官方文档明确：需要事务的代码应写成一个同步函数，再用 sync_to_async() 调用。别在 async def 视图里指望 atomic()。

⚠️ 异步模式下要关掉持久连接。 CONN_MAX_AGE 那套在异步下不适用，改用数据库后端的内置连接池，池大小按「在途查询并发量」设 —— 也就是 workers × (threads 或 worker-connections) 量级。

⚠️ DJANGO_ALLOW_ASYNC_UNSAFE 是逃生舱，不是解决方案。 官方警告：启用后若有并发访问 async-unsafe 部分，可能导致数据丢失或损坏，不要在生产使用。另外 Jupyter / IPython 会自动提供活跃事件循环，所以在 notebook 里调 ORM 也可能触发同一个异常，用 %autoawait off 临时关掉。

⚠️ 客户端断开会抛 asyncio.CancelledError。 长连接请求（SSE、长轮询）里必须在视图内捕获并清理，然后重新抛出，否则清理逻辑不会执行。

七、参数联动：三个数字要一起算

上线前必须让这三个数字自洽，否则会出现「压测过了但线上连接池爆了」。

场景 workers 并发模型 并发上限 连接池下限
Django 同步视图 + gthread 4 --threads 4 16 ≥ 16
Django ASGI + 异步视图 4 事件循环 看 worker-connections（如 1000） 按实际在途查询量，不是 4000
FastAPI + Uvicorn 单进程 1（容器内） 事件循环 受 --limit-concurrency 限制 按 QPS × 平均查询数
K8s 里 8 个 Pod × 1 进程 8（跨 Pod） 事件循环 8 × limit-concurrency 池大小 × 8 ≤ DB max_connections

⚠️ ASGI 下别把「连接上限」直接当成「DB 连接池大小」。 一个 worker 能挂 1000 个连接，但绝大多数时间它们在 await 上游 I/O，真正同时打 DB 的可能只有几十个。按 worker-connections 配池子会瞬间打爆数据库 max_connections。

⚠️ K8s 里通常不用 --workers。 官方建议是「每个容器跑一个 Uvicorn 进程」，副本数交给 Deployment 管 —— 这样探针、优雅退出、资源 limit 都由编排层统一处理，不会出现「一个 Pod 里 4 个 worker 只有一个收到 SIGTERM」的混乱。

常见坑清单

  • 异步视图里用了 requests / time.sleep / 同步 DB 驱动，把整个 worker 的事件循环堵死
  • 给 ASGI worker 配 --threads（无效参数，并发由 --worker-connections 控制）
  • 同时用 --reload 和 --workers（互斥，直接报错）
  • 生产环境开着 --reload
  • --forwarded-allow-ips '*' —— 任何人伪造 X-Forwarded-For 都能冒充 IP
  • 以为 --limit-concurrency 是队列（它是立刻 503，不入队）
  • sync worker 前面没挂 nginx 缓冲代理，慢客户端占满 worker
  • gevent worker 没给 psycopg 打 psycogreen 补丁，greenlet 根本调度不起来
  • 异步视图跑在 WSGI 下 —— 每请求一个一次性事件循环，长请求白跑
  • async def 视图里用 atomic() 想开事务（异步模式下事务不可用）
  • 异步模式仍用 CONN_MAX_AGE 持久连接，没换连接池
  • 在紧循环里逐行 sync_to_async，线程切换开销被放大几十倍
  • 靠 DJANGO_ALLOW_ASYNC_UNSAFE 绕过 SynchronousOnlyOperation
  • 长连接视图没捕获 asyncio.CancelledError，客户端断开后资源不回收
  • 以为 http.response.start 之后还能改状态码
  • scope["headers"] 当 str 用（它是 bytes）
  • lifespan 里没建/关连接池，靠模块级全局变量硬撑
  • ASGI 部署按 worker-connections 配 DB 连接池，打爆数据库 max_connections
  • 子路径部署没设 --root-path / root_path，路由全 404
  • 容器里 --host 127.0.0.1，探针和外部都连不上
