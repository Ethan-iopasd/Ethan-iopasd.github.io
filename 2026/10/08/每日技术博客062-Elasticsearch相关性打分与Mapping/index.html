三 相关性打分与 Mapping 设计 本篇

开场：一句话结论

_score 由 BM25 算，但能不能被搜到完全由 mapping 决定 —— term 查 text、keyword 没配 normalizer、object 数组丢关联，这三个是线上 90% 的「搜不到 / 搜错」根因。

一、BM25 与打分诊断

BM25 自 ES 5.0 起取代 TF-IDF 成为默认相似度。

维度 TF-IDF BM25
TF 增长 线性（词频越高分越高） 饱和（k1 控制上限）
文档长度 不归一化 归一化（b 控制）
参数 无 k1=1.2、b=0.75
默认 5.0 之前 5.0 起

打分核心：score = IDF × (tf × (k1+1)) / (tf + k1 × (1 - b + b × dl/avgdl))

参数 作用 调大 调小
k1（0~3） 控制 TF 饱和速度 词频影响更大 更快饱和
b（0~1） 控制长度归一化 更惩罚长文档 b=0 完全不归一化

explain 输出逐层拆解：

层级 含义
value 该节点的贡献分
description 用的公式（如 score(freq=2.0), computed as boost * idf * tf）
details 逐层拆解：boost / idf / tf / fieldLength

⚠️ k1 / b 只能在建索引时定义，不能对已有字段动态修改。想调参得 reindex 重建。别指望线上 PUT _settings 改完立刻生效。

⚠️ b=0.75 是通用默认，但**短文本（标题、标签）通常该调低 b**，否则长度差异被过度惩罚；长正文可保持或调高。

⚠️ 字段长度归一化用的是该字段的平均长度（avgdl）。索引里文档构成一变，同一文档的分数也会变 —— 相关性分数不是跨索引 / 跨时间可比的绝对值。

⚠️ explain: true 会给每个命中文档都算一遍解释，开销极大。只在调试单条时开，别在线上大查询里用。

⚠️ 查询里有 filter（如 term 过滤）时，filter 部分不参与打分，_score 只反映 must / should。所以「加了 filter 分数没变」是正常的。

二、boost / function_score / script_score

方式 用途 代价
boost（query 级） 调整某个子查询权重 低
function_score 按字段值 / 衰减函数改分 中
script_score 任意脚本算分 高（painless 逐文档执行）

⚠️ script_score 在每个候选文档上跑一次脚本，_score 无法被索引优化。几万候选就能把查询拖到超时。能用 function_score 的衰减 / 权重解决就别上脚本。

⚠️ function_score 的 score_mode / boost_mode 组合直接决定最终分。boost_mode: replace 会丢掉原始 BM25 分，文本相关性完全失效。

⚠️ boost 值是乘数不是加法。给某字段 boost: 2 不等于「多加 2 分」，而是把该子查询得分翻倍，效果随原始分缩放。

三、multi_match 三策略与 dis_max

type 行为 适用
best_fields（默认） 取得分最高的单字段 一个词主要出现在某字段
most_fields 累加所有字段的得分 同一词在多个字段重复出现
cross_fields 把多字段当一个字段处理 词分散在不同字段（如 first_name + last_name）

⚠️ most_fields 会让多字段重复出现同一个词的文档分数虚高（同一个词被算多次），和 best_fields 语义相反。选错会让「到处都提到关键词的文档」排在真正精准匹配前面。

⚠️ cross_fields 只在所有字段用同一个 analyzer 时才有意义，且 operator=and 下才能保证「所有词都出现」。字段分词器不同时结果不可预期。

⚠️ dis_max 是 best_fields 的底层结构（best_fields 内部就是 dis_max + tie_breaker）。想微调「最佳字段之外其他字段也贡献一点分」，用 tie_breaker。

四、match / term / match_phrase 与 keyword vs text

查询 是否分析 作用
match ✅ 对 query 分词 全文检索
match_phrase ✅ 分词 + 保持顺序 短语匹配（slop 控制词间距）
term ❌ 不分词 精确值（keyword、数值）
terms ❌ 不分词 多值精确匹配
维度 text keyword
分词 ✅ ❌
排序 / 聚合 ❌（需 fielddata） ✅（doc_values）
term 查询 ❌ ✅
典型用途 正文、标题 状态、标签、ID

⚠️ term 不分析：text 字段默认用 standard analyzer 把 Elasticsearch 转成小写 elasticsearch，但 term 直接拿原始大小写去查，匹配不上。**term 只该用在 keyword 或数值字段上。**

⚠️ keyword 字段用 match 会先被当作一个整体（不分词），等价于 term；但不做 lowercase，"Published" 查不到 "published" —— 要么用 term 精确值，要么给字段配 normalizer。

⚠️ 一个字段**不能既是 text 又是 keyword**，标准做法是 text + fields.keyword 子字段（多字段），同时支持全文检索和精确聚合 / 排序。

⚠️ 对 text 字段直接做聚合 / 排序，ES 会要求开 fielddata，而 fielddata 默认关闭且会把字段值全量加载进堆内存，是 OOM 的头号元凶。

机制 存储 场景
doc_values 磁盘列存（默认开） 排序、聚合、脚本
fielddata 堆内存 text 字段的排序 / 聚合

⚠️ doc_values: false 能省磁盘，但会让该字段无法排序和聚合，且不能对已有字段动态修改（需 reindex）。关之前想清楚。

五、Mapping 设计：dynamic、analyzer 与字段限制

dynamic 行为
true（默认） 自动新增字段映射
false 忽略新字段，不索引也不报错
strict 遇到未定义字段直接报错拒绝写入
分词器 粒度 用途
ik_max_word 最细 索引（召回多）
ik_smart 粗 查询（精度高）
standard 按空格 / 标点 英文默认，中文会被切成单字

⚠️ dynamic: true 是字段爆炸的元凶：JSON 里一个动态 key（如 attr_20261008）就新增一个映射，映射表膨胀后集群直接拒绝写入（超 index.mapping.total_fields.limit，默认 1000）。

⚠️ ignore_above: 256 只影响索引（超过长度的值不索引），原值仍在 _source 里。所以「设了 ignore_above 却还能在 _source 看到长值」是正常的，但聚合会漏掉这些长值。

⚠️ index: false 的字段不能用于查询，但可排序 / 聚合（若有 doc_values）且保留在 _source。适合「只展示不检索」的字段。

⚠️ 用 standard 处理中文，会把「每日技术博客」切成一个个单字，召回高但相关性极差。中文必须装 analysis-ik 并显式指定 analyzer。

⚠️ 索引时和查询时用了不同 analyzer 会导致查不到。标准做法是索引用细粒度（ik_max_word）、查询用粗粒度（ik_smart），但分析器产出的 token 必须能对上，否则 term 无法匹配。

⚠️ 改 analyzer 对已有数据不生效，必须 reindex。只改 mapping 不重建索引，老数据仍按老分词器建的倒排。

_source / stored_fields / copy_to

概念 作用
_source 原始 JSON，默认全存，可取回任意字段
stored_fields 只对显式 store: true 的字段有效
copy_to 把多个字段拼进一个「大字段」供检索

⚠️ copy_to 只是把值复制进目标字段的倒排，目标字段的 _source 不会包含这些值，也不能直接用于 term 精确匹配（它仍是 text）。

⚠️ 关闭 _source 能省磁盘，但会失去 reindex / update 的能力；stored_fields 与 _source 是两套机制，同时开等于存两份。

六、字段爆炸、flattened、nested 与 join

类型 动态 key 能否单独查询某 key
object（默认） 每个 key 都建映射 ✅
flattened 不建独立映射 ⚠️ 只能整体查
方式 特点
nested 同文档内父子，查询快，写放大
join 跨文档父子，必须在同一 shard，查询用 has_child / has_parent

⚠️ flattened 把整个对象当成一个字段，labels.color: red 这种针对单个 key 的精确查询能力变弱（用 term 查 labels 整个字段）。这是「字段数爆炸」与「查询能力」之间的取舍。

⚠️ 超过 index.mapping.total_fields.limit（默认 1000）后，索引拒绝任何新增字段的写入，报 Limit of total fields [1000] has been exceeded。要么调大阈值（治标），要么改 flattened / dynamic: false（治本）。

⚠️ object 数组会把子字段拍平成独立数组，丢失「哪个值和哪个值属于同一个对象」的关联。name=alice AND age=30 会匹配到 {alice,20} + {bob,30} 的文档 —— ES 最经典的误命中。

⚠️ nested 查询必须用 nested query 包住，直接写 user.name: alice 会查不到（nested 字段不在根倒排里）。

⚠️ nested 每个子文档是独立的 Lucene 文档，文档数会成倍膨胀，写入与查询都更贵。能用 flattened 或 copy_to 拼字段解决就别上 nested。

⚠️ join 字段要求父子文档路由到同一个 shard（相同 routing），否则查不到。这让 join 在多分片下扩展性很差，能用反范式冗余就别用。

七、写入调优：refresh_interval 与 _bulk

⚠️ refresh_interval 默认 1s，意味着每秒生成一个 segment，写入压力大时产生大量小 segment。批量导入时临时调大（如 30s 或 -1），导完再调回。

⚠️ _bulk 的响应要逐条检查：整体 HTTP 200 不代表全部成功，每条带自己的 status。字段冲突、解析失败都在 items 里，不看就丢数据。

⚠️ 单次 _bulk 体积建议控制在几 MB ~ 十几 MB，不是越大越好。过大会打爆协调节点内存，也会撞上 HTTP 请求体限制（http.max_content_length 默认 100MB）。

⚠️ refresh_interval: -1 会关闭自动刷新，此时写入的数据不可被搜索，直到手动 POST /idx/_refresh。别在生产查询索引上这么设。

常见坑清单

  • term 查 text 字段，因分词 / 大小写导致查不到
  • keyword 字段用 match 查，期望自动小写匹配
  • 对 text 字段开 fielddata 做聚合，堆内存被打爆
  • 一个字段既想全文检索又想聚合，却没配 fields.keyword
  • 用 most_fields 当 best_fields，重复词文档分数虚高
  • cross_fields 用在分词器不同的字段上
  • boost_mode: replace 丢掉 BM25 分，相关性全无
  • 在线上大查询里开 explain: true，开销爆炸
  • 以为 filter 参与打分（实际不参与）
  • dynamic: true 遇到动态 key，字段数超 1000 被拒写
  • ignore_above 设了却以为长值被丢弃（其实还在 _source）
  • 改了 analyzer 不 reindex，老数据仍按老分词
  • 中文索引用 standard 分词器，切成单字相关性极差
  • object 数组当 nested 用，关联关系丢失导致误命中
  • nested 查询没用 nested query 包住，查不到
  • join 字段父子文档 routing 不一致，跨 shard 查不到
  • 批量导入不调 refresh_interval，segment 碎成一片
  • _bulk 只看 HTTP 200，不看 items 里的失败项
  • 关闭 _source 后想 _update / reindex，发现没数据
  • 调 k1 / b 时想动态改已有字段，实际必须 reindex
