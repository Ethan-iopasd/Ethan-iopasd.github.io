开场：一句话结论

只要服务端不需要主动接收消息，就优先用 SSE（协议简单、自动重连、天然过 HTTP 中间件）；需要双向且高频，才上 WebSocket。轮询是兜底，不是方案。

一、四种方案对比

维度 短轮询 长轮询 SSE WebSocket
方向 客户端拉 客户端拉 服务端单向推 双向
底层协议 HTTP HTTP HTTP 独立协议（TCP）
握手成本 每轮一次 每轮一次 一次 一次（HTTP Upgrade）
断线重连 天然 天然 浏览器自动 需自己实现
消息格式 任意 任意 UTF-8 文本 文本 / 二进制
同源 6 连接限制 受影响 受影响 ⚠️ 受影响 通常不受
代理友好度 高 高 高 ⚠️ 需配置透传
服务端状态 无 无 无 有（每连接一份）
适合 低频可容忍延迟 中低频需即时 通知流、日志、AI 流式 聊天、协同、游戏

⚠️ HTTP/1.1 下同源最多 6 个并发连接。开 6 个 SSE 标签页就会占满整个域名的连接池，其余请求全部排队 —— 这是 SSE 最经典的线上事故。WebSocket 不占用 HTTP 请求队列，因此不受这条限制，但服务端要为每条连接维持一个长生命周期对象。

二、WebSocket 握手

客户端发起的是标准 HTTP/1.1 请求，方法必须为 GET，版本至少 1.1：

头 必需 值要求
Upgrade ✅ 必须包含 websocket
Connection ✅ 必须包含 Upgrade token
Sec-WebSocket-Key ✅ 16 字节随机数 base64 编码
Sec-WebSocket-Version ✅ 必须为 13
Sec-WebSocket-Protocol 可选 子协议列表，逗号分隔
Origin 浏览器必带 用于服务端校验来源

服务端接受时返回 101，并带上 Sec-WebSocket-Accept，其值为 base64(SHA1(Key + "258EAFA5-E914-47DA-95CA-C5AB0DC85B11"))。那个 GUID 是固定常量，作用只是证明服务端真的读了这次握手（防缓存 / 误连接）。

⚠️ 握手返回非 101 时 HTTP 语义依然生效，浏览器 onerror 里拿不到状态码。要靠 onclose 的 code，或者先发一个 HTTP 预检接口拿 token。

⚠️ Sec-WebSocket-Protocol 若服务端返回了客户端没请求的子协议，客户端必须判定握手失败。子协议不是「随便协商」的。另外 WebSocket 是独立协议，与 HTTP 的唯一关系是握手被解释为 Upgrade 请求 —— 缓存、重定向这些 HTTP 语义都不适用。

默认端口 ws:// → 80、wss:// → 443。RFC 明确指出 443 上的连接成功率显著更高（能穿过大多数企业代理），生产环境一律用 wss。

三、帧与心跳

帧类型 Opcode 说明
Continuation 0x0 分片消息的后续帧
Text / Binary 0x1 / 0x2 UTF-8 文本 / 二进制
Close 0x8 关闭连接
Ping / Pong 0x9 / 0xA 探活 / 响应，payload ≤ 125 字节

常用关闭码：1000 正常 · 1001 端点离开（服务重启、页面导航）· 1002 协议错误 · 1006 异常关闭 · 1007 payload 非法（如非 UTF-8）· 1008 违反策略（常见于鉴权失败）· 1011 服务端内部错误。

⚠️ 1006 是本地合成的，永远不会由对端发来。收到 1006 意味着连接异常断开（网络断、进程被杀），此时必须重连。

⚠️ 浏览器原生 WebSocket API 不暴露 Ping/Pong，想用心跳只能在应用层自己发文本消息。另外控制帧 payload 不能超过 125 字节且不可分片，用它传业务数据会直接被协议层拒绝。

心跳的必要性：中间的 Nginx、SLB、云防火墙普遍有 60s 空闲超时，会静默切断无流量的长连接。心跳间隔取 30s 左右比较安全。

⚠️ 心跳要双向：客户端发 ping 服务端回 pong，同时服务端也要检测「多久没收到任何帧」并主动关闭僵尸连接。只做单向心跳会留下大量假活连接。

四、断线重连与指数退避

要素 作用
指数退避 2^n 避免服务端刚重启就被打爆
上限（如 30s） 防止退避到几小时
抖动 jitter 避免所有客户端同时重连（惊群）
成功即重置计数 否则正常波动也会累积到上限

⚠️ 没有抖动的指数退避 = 惊群。服务端重启后所有客户端会在同一毫秒重连，加 Math.random() 抖动是最低要求。同时重连期间要缓存待发送消息并补齐，否则用户在网络抖动时输入的内容会静默丢失。

⚠️ 重连成功后必须重新鉴权。token 可能已过期，服务端会立刻用 1008 关闭，形成「连上就断」的死循环。要在 onopen 里重发认证消息。

五、SSE

服务端响应 Content-Type: text/event-stream，事件流格式（WHATWG HTML Standard）：

字段 作用
data: 数据内容，多行会以 \n 拼接
event: 事件类型名，默认 message
id: 设置 lastEventId，重连时通过 Last-Event-ID 发回
retry: 指定重连间隔（毫秒）
: 开头 注释，常用来做心跳保活
规则 说明
编码 必须 UTF-8，无法指定其他编码
行分隔 CRLF / LF / CR 均可
事件分隔 空行触发派发，流末尾不算
冒号后空格 若存在会被忽略（data: x 与 data:x 等价）
重定向 / 停止重连 支持 301 / 307；服务端返回 204 可让客户端停止重连

readyState：CONNECTING(0) 未建立或正在重连 · OPEN(1) 已连接 · CLOSED(2) 已关闭且不再重连。

⚠️ 断线重连时浏览器会带上 Last-Event-ID 请求头（值为最后收到的 id）。服务端必须据此续传，否则重连后会丢消息或重复推送。不实现这个，自动重连就是「看起来能用」的假象。

⚠️ EventSource 只能发 GET，不能带自定义请求头，也不能设 body。要 POST 或加 Authorization 头，只能用 fetch + ReadableStream 自己解析事件流。

⚠️ retry 字段控制重连间隔，未指定时用 UA 默认值（主流浏览器约 3 秒）。这个默认值偏激进，服务端故障时会造成重连风暴，建议显式下发 retry:。

⚠️ SSE 的 6 连接限制在 HTTP/2 下被消除；但若 Nginx 到上游仍是 HTTP/1.1，瓶颈只是从浏览器挪到了 Nginx。规范还提醒中间层 chunked 传输可能破坏 SSE 时序，代理层要关掉 text/event-stream 的缓冲。

六、Nginx 反代配置

指令 作用 漏掉的后果
proxy_http_version 1.1 启用 Upgrade 机制 ⚠️ 默认 1.0，握手直接失败
proxy_set_header Upgrade 透传升级头 ⚠️ 服务端收不到 Upgrade
proxy_set_header Connection 透传连接头 ⚠️ 握手 400 / 连接被复用
proxy_read_timeout 延长读超时 ⚠️ 默认 60s 后静默断开
proxy_buffering off 关缓冲（SSE） ⚠️ 消息被攒着不发
X-Accel-Buffering: no 应用层关 Nginx 缓冲 ⚠️ 同上

⚠️ Nginx 默认 proxy_read_timeout 60s。心跳间隔必须小于这个值，否则连接会在两次心跳之间被掐掉，表现为「每分钟断一次」。

⚠️ 多实例部署时，WebSocket 需要会话保持（sticky）或共享的发布订阅（Redis Pub/Sub）。否则 A 实例上的用户发的消息，B 实例上的用户收不到。

七、鉴权

WebSocket 不能携带自定义请求头（浏览器 WebSocket 构造函数只有 URL 和子协议两个参数），Authorization: Bearer xxx 这条路走不通。

方案 做法 风险
URL 查询参数 wss://x/ws?token=xxx ⚠️ token 进访问日志、Referer
Cookie 依赖同源 Cookie 自动携带 ✅ 简单，但需防 CSRF
子协议传 token new WebSocket(url, ['bearer', token]) 非标准用法，易被中间件拦
首帧认证 连上后立刻发一条 auth 消息 ⚠️ 认证前连接已建立
一次性 ticket 先用 HTTP 换短时 ticket 再连 ✅ 推荐

⚠️ URL 里的 token 会进入 Nginx access log、浏览器历史、Referer 头，还可能被 CDN 缓存。要用就必须是一次性、短过期（秒级）的 ticket。

⚠️ 用 Cookie 鉴权时，WebSocket 握手不受同源策略保护（没有 CORS 预检）。服务端必须校验 Origin 头，否则存在跨站 WebSocket 劫持（CSWSH）。认证也应尽量在握手阶段完成（用 101 与 401 区分），否则攻击者可先占连接资源做耗尽攻击。

八、消息顺序与幂等

问题 原因 对策
乱序 分片、多路复用、多实例 带单调递增序号，前端按序缓冲
丢失 断线期间的消息 Last-Event-ID / 重连后拉增量
重复 重连重放、重试 消息带唯一 id，消费端去重
积压 消费慢 背压控制，超阈值丢弃或降级

⚠️ TCP 保证单连接内有序，但不保证跨连接。重连后是新连接，多实例又是不同连接 —— 序号必须由业务层给出，不能依赖 TCP。

⚠️ 客户端发送也要带 clientMsgId 作幂等键，否则重连重发会让服务端收到两条相同的业务消息。生产级场景推荐 at-least-once + 去重，而不是追求 exactly-once。

九、Socket.IO 与选型边界

Socket.IO 在 WebSocket 之上加了一层协议，提供自动重连、房间、广播、ack 回调，以及降级到 HTTP 长轮询的能力。

能力 原生 WebSocket Socket.IO
自动重连 / 房间 / ack 自己写 ✅ 内置
降级到长轮询 ❌ ✅
包体积 0（浏览器原生） ~40KB+
协议 标准 RFC 6455 ⚠️ 私有（非标准 WS 客户端连不上）
场景 更优选择 理由
只要服务端推（通知、日志、AI 流式） SSE 自动重连、无私有协议、curl -N 就能调试
更新频率 < 1 次/分钟 短轮询 长连接成本 > 收益
需要 CDN / 多层代理 SSE WebSocket 需逐层配置 Upgrade
不想引入 Pub/Sub 还要水平扩展 轮询 / SSE 有状态连接会绑死实例
双向高频（聊天、协同、游戏） WebSocket 唯一合适的选择

⚠️ Socket.IO 不是 WebSocket 的封装，而是一套私有协议。标准 WebSocket 客户端（wscat、Go 的 gorilla/websocket）连不上 Socket.IO 服务端，反之亦然。降级到长轮询也会让每台客户端占更多连接、延迟显著上升 —— 它是保险，不是常态。

⚠️ 长连接最大的隐性成本是有状态：滚动发布、扩缩容、负载均衡都必须处理「连接该断在哪、消息怎么补」。轮询天然无状态，运维复杂度低一个量级。

⚠️ 移动端切后台、网络切换（4G ↔ WiFi）会导致连接静默失效。必须有 visibilitychange 与 online / offline 事件驱动的重连逻辑，不能只靠 onclose。

常见坑清单

  • 用短轮询做「实时」，靠缩短间隔硬撑，打爆后端
  • 开多个 SSE 标签页，占满同源 6 连接导致其他请求排队
  • Nginx 没配 proxy_http_version 1.1，WebSocket 握手直接失败
  • 只透传 Upgrade 忘了 Connection，或没配 map $http_upgrade
  • proxy_read_timeout 保持默认 60s，连接每分钟被掐一次
  • 心跳间隔大于 Nginx 空闲超时
  • 只做单向心跳，服务端留下大量僵尸连接
  • 重连没加抖动，服务端重启引发惊群
  • 重连后没重新鉴权，陷入「连上就被 1008 关闭」的死循环
  • 重连期间不缓存待发消息，用户输入静默丢失
  • 把 1006 当成服务端发来的关闭码
  • SSE 服务端不处理 Last-Event-ID，重连后丢消息或重复推
  • 用 EventSource 发 POST 或加自定义请求头
  • SSE 响应没关 Nginx 缓冲，消息攒着不发
  • WebSocket token 放 URL 且长期有效，进了 access log
  • 用 Cookie 鉴权但不校验 Origin，存在跨站 WebSocket 劫持
  • 多实例部署没有 sticky session 或 Redis Pub/Sub，消息投递不全
  • 客户端重发不带幂等键，服务端收到重复业务消息
  • 以为标准 WebSocket 客户端能连 Socket.IO 服务端
  • 移动端只监听 onclose，忽略 visibilitychange 与 online 事件
