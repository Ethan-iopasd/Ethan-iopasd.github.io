每日技术博客 076 · 设计模式（二）：结构型与行为型模式

每日技术博客 · 2026-10-08 · 第 076 篇

设计模式系列第二篇。结构型怎么组装对象、行为型怎么组织协作，重点讲清「适配器 / 装饰器 / 代理」和「策略 / 状态 / 命令」这两组最常被混淆的模式。

二 结构型与行为型模式 本篇

开场：一句话结论

结构型解决「对象怎么拼」，行为型解决「对象怎么分工」；判断标准永远只有一个 —— 变化点在哪，就在哪加一层抽象。

一、结构型总览

模式 一句话 典型例子
适配器 Adapter 转换接口，让不兼容的能一起工作 InputStreamReader（字节流转字符流）
装饰器 Decorator 同接口包装，动态叠加功能 BufferedInputStream(new FileInputStream(...))
代理 Proxy 同接口包装，控制访问 Spring AOP、懒加载、远程代理
外观 Facade 给子系统一个统一入口 slf4j 门面、Service 门面
组合 Composite 树形结构，叶子与容器一致对待 文件/目录、UI 组件树
桥接 Bridge 抽象与实现分离，各自独立变化 JDBC Driver / Connection
享元 Flyweight 共享细粒度对象省内存 字符串常量池、Integer 缓存

二、适配器 vs 装饰器 vs 代理（最常混的一组）

三者都「包一层」，区别在意图：

维度 适配器 Adapter 装饰器 Decorator 代理 Proxy
目的 转换接口 增强功能 控制访问
对外接口 变成另一个接口 与被包对象相同 与被包对象相同
包装对象 已知的旧接口 任意同接口实现 被代理的真实对象
是否改变行为 语义映射 叠加/增强 拦截/转发（可改变）
典型 读卡器、InputStreamReader Java IO、Collections.unmodifiableList Spring AOP、动态代理、缓存代理

⚠️ 装饰器可以嵌套任意层（A(B(C(x)))），代理通常一对一。看到「多层包装」多半是装饰器。
⚠️ 装饰器和代理结构相同、意图不同。命名/文档写清楚，否则维护者永远分不清。

三、外观、组合、桥接、享元

外观 Facade：给复杂子系统一个简单入口，不禁止直接访问底层。

组合 Composite：叶子与容器实现同一接口，递归处理树。

桥接 Bridge：抽象维度与实现维度各自独立扩展，避免子类爆炸（M × N 变 M + N）。

享元 Flyweight：把可共享的内部状态抽出来复用，只保留不可共享的外部状态。

场景 共享的是 效果
字符串常量池 相同字面量 同一份 String 实例
Integer 缓存 -128 ~ 127 的装箱对象 Integer.valueOf 直接返回缓存
字符/图标/样式 重复的小对象 大幅降低内存占用

⚠️ Integer 缓存范围默认 -128~127，可用 -XX:AutoBoxCacheMax 调大上界（下界固定）。
⚠️ 包装类型一律用 equals 比较，== 在缓存边界内外行为不一致，是最隐蔽的坑之一。

四、策略 Strategy 与观察者 Observer

策略：把可互换的算法抽成接口，运行期替换。

观察者：主题状态变化时通知所有订阅者。

观察者 vs 发布订阅（Pub/Sub）：解耦程度不同。

观察者 Observer 发布订阅 Pub/Sub
耦合 主题直接持有观察者引用 双方只认识事件总线/Broker
中间层 无 有（EventBus / MQ）
通信 同步调用为主 可异步、跨进程
典型 DOM addEventListener、PropertyChangeListener Kafka、Redis Pub/Sub、Node EventEmitter 解耦版

⚠️ 观察者里同步调用所有订阅者时，一个订阅者抛异常会中断后续通知 —— 要 try/catch 隔离，或改用事件总线。
⚠️ 订阅后忘记取消订阅是内存泄漏的头号来源（尤其是长生命周期主题 + 短生命周期观察者）。

五、模板方法与责任链

模板方法：父类定义骨架，把可变步骤留给子类覆写（好莱坞原则的典型）。

责任链：请求沿链传递，每个处理者决定「处理 / 放行 / 拦截」。中间件、过滤器链的本质。

框架 形态 特点
Servlet Filter doFilter(req, res, chain) + chain.doFilter() 线性，调用前后都可插手
Spring Interceptor preHandle / postHandle / afterCompletion 三段式，返回 false 即中断
Express (req, res, next)，next() 放行 线性，不调 next() 即终止
Koa async (ctx, next) => { ... await next(); ... } 洋葱模型，await next() 前后各执行一段，回溯时逆序

⚠️ Koa 的洋葱模型里，**await next() 之后的代码是「响应阶段」，顺序与请求阶段相反 —— 这是很多中间件写错的原因。
⚠️ 责任链忘写终止条件（不调 next() 也不响应）会挂起请求**，直到超时。

六、命令、状态、迭代器、中介者、访问者、备忘录

模式 意图 关键点
命令 Command 把请求封装成对象 支持撤销/重做、排队、事务日志
状态 State 状态决定行为 替代「一堆 if-else / switch」的状态机
迭代器 Iterator 顺序访问聚合元素 不暴露内部结构；现代语言多为语法糖
中介者 Mediator 用中间人协调多对象 把网状 N×N 耦合降为星形 N×1
访问者 Visitor 在不改元素类的前提下加操作 依赖双重分派，新增元素类型代价高
备忘录 Memento 保存/恢复对象状态 快照、撤销；注意内存与深拷贝

⚠️ 访问者模式新增一个元素类型要改所有 Visitor，违反 OCP；元素类型稳定、操作频繁变化时才用。
⚠️ 备忘录默认是浅拷贝，恢复后原对象可能已被后续操作污染 —— 与原型模式同款深拷贝陷阱。

七、策略 vs 状态 vs 命令（第二组常混）

维度 策略 Strategy 状态 State 命令 Command
解决什么 算法可替换 行为随状态变 请求对象化
谁决定切换 调用方显式选择 对象自身按状态转移 调用方创建并触发
是否感知彼此 策略之间互不知 状态之间互相转移 命令互不知，可入栈
典型 排序/计费/压缩算法 订单状态机、TCP 状态 撤销重做、任务队列

⚠️ 策略与状态结构几乎一样，区别在「谁驱动切换」：外部驱动是策略，内部转移是状态。

八、怎么判断「该用模式了」

代码坏味道清单 —— 出现以下信号再考虑模式，别反过来：

坏味道 可能对应
长 if-else / switch 分支爆炸 策略、状态
一个类里成片的 type 判断 状态、多态
参数列表过长（> 4~5 个） 建造者
散弹式修改（改一处要动很多类） 责任链、观察者解耦
想给一批对象统一加功能 装饰器、代理
树形/递归结构 组合
两个维度各自扩展 桥接
重复创建同类小对象 享元、对象池

九、现代语言里被语法糖替代的模式

模式 替代
策略 一等函数 / 函数值 / lambda
命令 闭包 / 可调用对象
迭代器 生成器 / yield / 内建 for-of
访问者 模式匹配 / sealed class / switch 表达式
模板方法 高阶函数（传入步骤函数）
观察者 语言/框架自带的事件系统、响应式流（RxJS / Reactor）

十、何时不该用模式

  • 只有一个实现，且短期内不会变 → 别抽接口
  • 分支不会继续增长 → 用 switch 更直观
  • 语言已有等价能力（函数值、生成器、模式匹配）→ 用语言特性
  • 抽象只为「以后可能扩展」→ YAGNI
  • 加模式后调用链变长、跳转变多但收益不明显 → 退回直接实现

⚠️ 模式是对变化的投资，不是代码规范。没有变化点的地方加模式，只有成本。
⚠️ 一次重构只引入一个模式，多个模式同时上会让 review 无法定位问题。

常见坑清单

  • 把适配器写成装饰器（改变了对外接口）
  • 把代理当装饰器用，混用「增强」与「访问控制」两种职责
  • 装饰器嵌套过深，调试时栈看不清真实调用者
  • 外观被当成「唯一入口」强制封装，禁止直接访问底层
  • 组合模式里叶子与容器语义不一致（如容器 size() 返回子节点数）
  • 桥接误用成「多一层转发」，维度没有真正独立变化
  • 用 == 比较 Integer，在缓存边界（-128~127）内外行为不一致
  • 以为 Integer 缓存范围无限大（实际可调上界，下界固定 -128）
  • 观察者同步通知时一个异常中断全部订阅者
  • 订阅后忘记取消，长生命周期主题持有短生命周期观察者导致泄漏
  • 把观察者当发布订阅用，误以为已经解耦（实际主题仍直接持有引用）
  • Koa 洋葱模型里 await next() 之后的代码顺序写反
  • 责任链不调 next() 也不响应，请求挂起直到超时
  • 用状态模式但状态之间不做转移，退化成策略
  • 访问者模式里频繁新增元素类型，导致所有 Visitor 都要改
  • 备忘录/原型浅拷贝，恢复后状态被后续操作污染
  • 只有一种实现也抽策略接口，抽象噪声
  • 分支不会增长也用策略替代 switch
  • 一次重构同时引入多个模式，无法定位问题
  • 为「以后可能扩展」提前引入模式（YAGNI 违规）
