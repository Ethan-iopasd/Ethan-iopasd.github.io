开场：一句话结论

日志和指标都答不出「一个请求慢在哪一跳」，只有 Trace 能把跨服务的调用串成一条链 —— 而它的前提是上下文能跨进程、跨线程正确传播。

一、为什么需要追踪

问题 指标能答 日志能答 Trace 能答
整体 QPS 掉了 ✅ ⚠️ ❌
某接口 p99 飙高 ✅ ❌ ❌
慢在哪个下游服务 ❌ ⚠️ 要拼 ✅
这条请求经过了哪些服务 ❌ ⚠️ 要拼 ✅
一次调用各段耗时占比 ❌ ❌ ✅

⚠️ 微服务里「一个请求慢」在单服务视角下是「我这没慢」。只有把链路拼起来，才能看到瓶颈在第三跳的数据库。

二、Trace / Span / SpanContext

概念 含义
Trace 一次分布式调用的整体，TraceID 全局唯一
Span 一个工作单元，有开始/结束时间和操作名
SpanContext TraceID + SpanID + 采样标志，跨进程传播的载体
Parent-Child Span 的父子关系，构成调用树
Root Span 链路起点，没有父 Span

⚠️ Span 的 End() 必须成对调用。忘记 End() 的 Span 不会被导出，长任务里还会持续占内存。

⚠️ 父 Span 必须随 ctx 传下去。手工创建 Span 时不带父 ctx，链路就会断成两棵独立的树。

三、TraceID / SpanID 与传播

标识 长度 说明
TraceID 16 字节（32 位十六进制） 全局唯一，全链路相同
SpanID 8 字节（16 位十六进制） 单个 Span 唯一
TraceFlags 1 字节 最低位是采样标志（01 采样）

⚠️ TraceID 必须在链路起点生成。如果每个服务各生成一个，链路就永远拼不起来。

⚠️ TraceID 不应包含业务信息（如时间戳、用户 ID）。它是随机数，编码信息会破坏匿名性并可能被推断。

四、上下文传播

标准 Header 说明
W3C Trace Context traceparent / tracestate 官方推荐，跨厂商通用
B3 X-B3-TraceId 等 Zipkin 生态
Jaeger uber-trace-id Jaeger 原生

⚠️ 跨进程传播必须显式注入与提取。用了自动埋点才免手工；手动埋点时漏掉任一步，链路就断。

⚠️ traceparent 的 parent-id 是「调用方的 SpanID」，不是接收方自己的。接收方要新建 Span，父 ID 指向它。

⚠️ 消息队列、定时任务、异步回调不会自动传播。HTTP 头传不过去，必须把上下文序列化进消息体，消费端再提取。

五、采样策略

策略 决策时机 特点
头部采样（head-based） 链路起点 简单、低成本，但看不到全貌
尾部采样（tail-based） 链路结束后 可保留慢/错请求，成本高
固定比例 —— 1% / 10%，简单
自适应 动态 按流量自动调整

⚠️ 全量采样在生产不可行。Trace 数据量与 QPS 成正比，100% 采样会打爆存储和带宽。

⚠️ 采样决策必须全链路一致。上游采样、下游不采样（或反之），链路就会断裂。头部采样的标志位就是为此存在。

⚠️ 尾部采样需要先把整条链路缓存在内存。decision_wait 越长内存压力越大，必须配合 Collector 的水平扩展。

六、OpenTelemetry 架构

层 作用
API 定义埋点接口，与实现无关
SDK 具体实现，负责采样、导出
Collector 接收 / 处理 / 导出，可做采样与批处理
OTLP 语言无关的传输协议（gRPC / HTTP）

⚠️ API 与 SDK 分离是为了「库不绑定后端」。第三方库只依赖 API，应用在启动时选 SDK 和导出目标。

⚠️ OTLP 是标准协议，不是某个后端。同一套埋点可以导出到 Jaeger、Tempo、厂商 APM，切换后端不用改代码。

⚠️ 自动埋点覆盖面有限。它能自动埋 HTTP/gRPC/DB 客户端，但业务逻辑内部的耗时还得手动加 Span。

七、Collector 的作用

能力 说明
接收 多种协议（OTLP / Jaeger / Zipkin）
处理 批处理、属性裁剪、尾部采样
导出 多个后端、重试与队列
缓冲 后端抖动时不丢数据

⚠️ 别让应用直连后端。中间隔一层 Collector，才能统一做采样、裁剪和后端切换。

⚠️ Collector 的队列要有上限并配丢弃策略。后端挂了而队列无限增长，会把 Collector 自己 OOM。

八、Span 的语义约定

约定 示例属性
HTTP http.request.method / url.path / http.response.status_code
DB db.system / db.statement
RPC rpc.system / rpc.method
Messaging messaging.system / messaging.destination

⚠️ Span 属性同样要防高基数。把 user_id、完整 SQL、完整 URL 塞进属性，和指标基数爆炸是同一个病。

⚠️ db.statement 要参数化。SELECT * FROM t WHERE id = 12345 每条都不一样，应写成 SELECT * FROM t WHERE id = ?。

⚠️ 语义约定有版本，属性名会变（如 http.method → http.request.method）。升级时后端查询要对齐，否则仪表盘全空。

九、把 trace 与 log / metric 关联

关联方式 做法
log ↔ trace 日志里带 trace_id / span_id
metric ↔ trace Exemplars：直方图桶里挂具体 TraceID
统一 ID 用同一套 ID 贯穿

⚠️ 日志带 trace_id 是性价比最高的关联手段。有了它，从指标告警跳到日志、再跳到 trace，只需一次点击。

⚠️ Exemplar 让「p99 高」可以直接点进具体 trace。没有它，你只能凭时间去猜是哪条请求。

十、常见坑

坑 后果 解法
Span 忘记 End() 不导出、内存泄漏 defer span.End()
goroutine 里丢了 ctx 断链、新起 root span 显式传 ctx
线程池 / 消息消费丢上下文 链路断裂 手动注入提取
采样率不一致 链路不完整 统一采样决策
时钟偏移 子 Span 时间早于父 用同一时钟源、NTP
过度埋点 性能下降、成本上升 只埋关键路径

⚠️ go func(){ ... }() 里直接 tracer.Start(context.Background(), ...) 是新起一条链，父 ctx 必须显式传进闭包。

⚠️ 时钟偏移会让调用树「时间倒流」。分布式系统里各机器时钟不齐，Span 的相对时间可能看起来不合理，排查时要留余地。

⚠️ 埋点是有成本的。每个 Span 都要分配、序列化、传输，高频循环里加 Span 会显著拖慢业务。

十一、追踪数据的成本控制

手段 效果
采样（头部 + 尾部） 砍量最直接
保留期分级 近期全存、远期聚合
只存关键 Span 丢弃无信息量的中间 Span
属性裁剪 去掉大字段

⚠️ 成本控制的核心是「只留有用的」。正常请求留 1%，慢和错请求全留，既省成本又不丢关键信息。

十二、实战排查套路

⚠️ 排查要自上而下，不要一上来就 grep 日志。先缩小范围（哪个服务、哪个接口、哪段时间），再下钻，效率差几十倍。

⚠️ 每个服务都打 trace_id 才有这套流程。只要有一环不打，链路就断在这里，前功尽弃。

常见坑清单

  • Span 忘记调用 End()，数据不导出还占内存
  • 异步任务里用 context.Background() 新起链路
  • goroutine / 线程池 / 消息消费没手动传播上下文
  • 只注入不提取（或反之），跨进程传播断链
  • 采样决策不统一，导致链路只有半截
  • 生产环境开 100% 采样，打爆存储
  • 尾部采样 decision_wait 过长，Collector 内存爆掉
  • 把 user_id / 完整 SQL / 完整 URL 塞进 Span 属性
  • db.statement 没参数化，每条都是新属性值
  • 日志不带 trace_id，无法与链路关联
  • 应用直连追踪后端，没有 Collector 做缓冲与裁剪
  • 机器时钟未同步，Span 时间出现「倒流」
  • 高频循环里加 Span，埋点成本超过业务本身
  • 依赖旧语义约定属性名，升级后查询全空
  • 只靠日志排查，不先用指标缩小范围
  • Collector 队列无上限，后端故障时自身 OOM
