开场：一句话结论

分布式锁只有两种写法：SET key val NX PX ttl 一条命令搞定，或者用 Redisson；其余写法都是错的。限流别自己发明算法，INCR + EXPIRE 能覆盖 80% 场景，剩下的用 ZSET 滑动窗口或 Lua 令牌桶。

一、加锁：为什么不能 SETNX + EXPIRE

写法 原子性 后果
SETNX + EXPIRE ❌ 两步 中间崩溃 → 死锁
SET ... NX EX ✅ 秒级过期
SET ... NX PX ✅ 毫秒级过期，推荐
SETEX ❌ 无条件覆盖 会抢别人的锁

⚠️ SETNX 是 SET ... NX 的旧别名，它没有过期参数，必须配 EXPIRE，这就是两步非原子的根源。用 SET 一条命令。

⚠️ EX / PX 的区别是单位：EX 秒、PX 毫秒。业务 TTL 通常按毫秒估，写 PX。

二、value 必须存「持有者标识」

value 不能随便写个 1。必须写能唯一标识当前线程/进程的值，解锁时才能校验「锁还是不是我的」。

⚠️ 直接 DEL 是致命 bug：A 的锁因 TTL 到期自动释放，B 拿到锁，此时 A 执行完 DEL，删掉的是 B 的锁。后续 C 又能拿锁 → 同一临界区两个执行者。

⚠️ GET 和 DEL 分开写同样有竞态窗口：GET 校验通过后、DEL 之前锁到期被别人拿走，删的仍是别人的。校验和删除必须在 Lua 里原子完成。

三、锁续期与看门狗

TTL 是双刃剑：太短，业务没跑完锁就没了；太长，进程崩了别人要等很久。

方案 做法 问题
固定 TTL 估一个「够长」的值 估不准，业务变慢就失效
手动续期 业务里定时 PEXPIRE 续期逻辑和业务耦合，容易漏
看门狗 后台线程自动续期 依赖客户端存活

Redisson 的 RLock：不显式传 leaseTime 时启用看门狗，默认 lockWatchdogTimeout = 30s，每 10s（1/3 周期）续一次，续到业务显式 unlock 为止。

⚠️ 显式传了 leaseTime，看门狗就不再续期。业务执行超过 leaseTime 时锁会提前释放，两个线程同时进临界区。要么不传靠看门狗，要么传一个确信够大的值。

⚠️ 看门狗靠 JVM 存活续期。进程被 kill -9 或 STW 卡死时，续期线程一起停，锁到期自动释放 —— 这是设计上的安全兜底，不是 bug。

四、Redlock 与它的争议

单实例 Redis 锁有个硬伤：主从异步复制。客户端在 master 加锁成功、master 还没同步到 slave 就宕机，slave 升主后锁丢失，另一个客户端能重新加锁。

Redlock 的思路：用 N（通常 5）个独立 master，客户端依次加锁，超过半数成功且总耗时小于锁 TTL 才算拿到锁。

争议方 核心论点
Martin Kleppmann 锁不解决「时钟漂移 / GC 停顿」；没有 fencing token 时，锁失效后旧持有者仍能写共享资源
antirez（Redis 作者） 引入 fencing token 需要存储层配合；Redlock 的目标是「多数派、无单点」，是合理权衡

Kleppmann 的替代主张：别用分布式锁保证正确性，用带单调递增 token 的存储层做乐观并发控制（如 etcd 的 revision、数据库的行版本号）。

⚠️ Redlock 不是「更安全的单机锁」，它换的是故障模型：容忍单节点宕机，代价是 5 个独立实例的运维成本 + 对时钟的假设。

⚠️ 如果你要的是「防重复执行」这种性能优化，单机 SET NX PX + 幂等就够了；如果你要的是正确性，锁本身就不够，得上 fencing token 或数据库唯一约束。

五、限流：四种算法与 Redis 落地

算法 优点 缺点 Redis 实现
固定窗口 最简单 窗口边界双倍流量 INCR + EXPIRE
滑动窗口 平滑、精确 占内存（存时间戳） ZSET
令牌桶 允许突发 实现稍复杂 Lua
漏桶 输出恒定 不允许突发 Lua

5.1 固定窗口：INCR + EXPIRE

⚠️ INCR 和 EXPIRE 分开写有坑：INCR 之后进程崩溃，key 没有 TTL → 计数永远累加，接口被永久限流。放进 Lua 或保证 INCR 返回 1 时才 EXPIRE。

⚠️ 固定窗口在窗口切换点可放行 2 倍流量：第 59 秒打满 100 次，第 61 秒又打满 100 次。

5.2 滑动窗口：ZSET

结构 存什么 内存
固定窗口 一个计数 O(1)
ZSET 滑动窗口 每条请求一个 member O(阈值)

⚠️ ZSET member 必须唯一，用时间戳做 member 时同毫秒并发会互相覆盖，要拼随机后缀或自增序号。

⚠️ 滑动窗口内存随 QPS 线性增长。阈值 10 万时，一个 key 存 10 万个 member，本身就成大 key 了 —— 高 QPS 场景优先令牌桶。

5.3 令牌桶：Lua

令牌桶只存「上次补充时间 + 当前令牌数」，内存 O(1)，且允许突发。

⚠️ 时间必须由调用方传入（ARGV[3]），不要在脚本里调 redis.call("TIME")。虽然 Redis 5.0 起默认按效果复制脚本（不再把 TIME 当致命错误），但多实例/主从对时仍然要求脚本行为可复现 —— 时间戳统一从外部传入最稳。

六、Lua 脚本的硬约束

约束 说明
原子性 脚本执行期间不处理其他命令，但不是事务，中途报错不回滚
同 slot Cluster 下所有 KEYS 必须落同一个 slot，否则报 CROSSSLOT
无阻塞 脚本里不能有长循环 / 大范围 KEYS，会卡住整个实例
可缓存 SCRIPT LOAD 后可用 EVALSHA 按 SHA1 调用

⚠️ 脚本缓存不持久化、不跨重启，也不随主从同步。EVALSHA 报 NOSCRIPT 时必须降级 EVAL 重新加载 —— 客户端库一般内置这个回退，自己裸写要处理。

⚠️ Cluster 下想跨 key，必须用 hash tag：{user:1}:lock 和 {user:1}:quota 会落同一 slot（只取 {} 内内容算哈希）。

七、SCAN 替代 KEYS、大 key / 热 key

命令 阻塞 保证
KEYS 全量遍历，O(N) 精确
SCAN 每批 O(COUNT) 可能重复、期间新增可能漏

⚠️ SCAN 的 COUNT 是提示不是上限，一次可能返回更多或更少。且遍历期间新增的 key 不保证被返回、已返回的可能重复 —— 做全量迁移时要能容忍。

排查工具：

⚠️ --hotkeys 有硬性前提：maxmemory-policy 必须是 allkeys-lfu 或 volatile-lfu（Redis 4.0+ 才有 LFU）。策略是 LRU 时它直接报错或无意义。

⚠️ 大 key 的删除也要注意：DEL 一个大 ZSET / HASH 是 O(N)，会阻塞。用 UNLINK（4.0+）异步回收，或 HSCAN 分批删。

八、pipeline 与事务 MULTI 的边界

特性 pipeline MULTI/EXEC
目的 省网络 RTT 原子执行
原子性 ❌ 只是批量发送 ✅ 中间不插其他命令
回滚 ❌ ❌ 运行期错误不回滚，只是全部执行
读取中间结果 ❌ 发完才读 ❌ 命令入队时拿不到值

⚠️ MULTI 没有回滚。第 2 条命令报错（如类型不匹配），第 1、3 条照常生效。要「按读到的值决定写」必须用 Lua，不是事务。

⚠️ 用 WATCH 做乐观锁时，EXEC 返回 nil 表示期间 key 被改过，必须重试整个读-改-写流程，不能当成失败直接放弃。

常见坑清单

  • 用 SETNX + EXPIRE 两步加锁，中间崩溃导致死锁
  • SETNX 不带过期，锁永久占用
  • 加锁 value 写死 1，无法校验持有者
  • 解锁直接 DEL，删掉别人的锁
  • 解锁时 GET 和 DEL 分开写，中间有竞态
  • EX / PX 单位写错，TTL 差 1000 倍
  • 显式传 leaseTime 后以为看门狗还在续期
  • 看门狗依赖 JVM，进程被 kill -9 后锁靠 TTL 兜底，误以为「锁不会丢」
  • 把 Redlock 当成正确性保证，没有 fencing token
  • 主从架构下忽略「主宕机丢锁」的窗口
  • INCR 和 EXPIRE 分开写，计数没有 TTL 被永久限流
  • 固定窗口在边界放行 2 倍流量
  • ZSET 滑动窗口用时间戳做 member，同毫秒并发互相覆盖
  • 滑动窗口阈值开太大，key 变成大 key
  • Lua 里调 TIME / RANDOMKEY，多实例行为不一致
  • Cluster 下脚本跨 slot，报 CROSSSLOT
  • EVALSHA 报 NOSCRIPT 没有降级到 EVAL
  • 生产用 KEYS 扫全库
  • --hotkeys 在 LRU 策略下运行
  • 用 MULTI 当回滚事务，以为出错会撤销
  • 用 DEL 删大 key 阻塞主线程
