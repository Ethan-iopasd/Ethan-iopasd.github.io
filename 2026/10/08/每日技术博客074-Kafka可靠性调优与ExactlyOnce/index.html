开场：一句话结论

幂等生产者只保证单分区、单会话去重；事务把范围扩到跨分区；但两者一旦跨出 Kafka（调外部 DB / HTTP），EOS 立刻退化为 at-least-once。

一、幂等生产者：约束与去重机制

开启幂等后，这三个配置会被强制约束：

配置 要求 不满足时
acks 必须 all 抛 ConfigException
retries 必须 > 0 抛 ConfigException
max.in.flight.requests.per.connection 必须 ≤ 5 抛 ConfigException

去重机制：

保证范围 边界
✅ 单分区内去重 序列号按分区独立维护
✅ 单个 Producer 会话内 PID 随会话生成
❌ 跨分区 不做跨分区去重
❌ 跨会话 Producer 重启 → 新 PID → 老序列号信息失效

⚠️ 幂等不是「业务幂等」，只解决 Kafka 内部因重试导致的重复写入。
⚠️ max.in.flight 从 5 改成 1 会严重降吞吐，且幂等本身已处理乱序重试，没必要改。
⚠️ 消费端用 enable.auto.commit=true 时，处理成功但提交失败仍会重复消费 —— 幂等生产者管不到这一步。

二、事务：把范围扩到跨分区

API 作用
initTransactions() 注册 transactional.id，获取 PID，终止未完成事务
beginTransaction() 开启事务
sendOffsetsToTransaction() 把消费位移提交纳入同一事务（Exactly-Once 消费-处理-生产）
commitTransaction() 提交
abortTransaction() 回滚

消费端要读到「已提交」的数据：

概念 含义
LSO（Last Stable Offset） 第一个未提交事务的起始 offset；read_committed 下消费者只能读到 LSO 之前
HW 之前讲过，ISR 最小 LEO
关系 read_committed 下可读上界 = min(HW, LSO)

⚠️ transactional.id 必须每个 Producer 实例唯一，重复会导致 fencing —— 老实例被踢下线。
⚠️ transaction.max.timeout.ms 默认 900000（15 分钟）；transaction.timeout.ms 超过它，事务会被 Broker 主动 abort。
⚠️ read_committed 下未提交事务的消息会被跳过，消费者看到的 offset 会出现空洞，不要以为是丢数据。
⚠️ 事务会引入额外开销（写入 marker、控制 batch），高吞吐场景要权衡是否真的需要。

三、EOS 的边界

场景 语义
Kafka → Kafka（读-处理-写） ✅ 真正 Exactly-Once
Kafka → 外部 DB（非事务） ❌ 退化为 at-least-once
Kafka → 外部 HTTP 调用 ❌ 无法保证
消费端写 DB + 提交 offset 非原子 ❌ 重复消费不可避免

要让「Kafka + 外部系统」也 EOS，只能：

  1. 外部系统支持幂等写（唯一键 + upsert）；
  2. 或把位移和业务数据写在同一个事务里（如 DB 事务 + outbox 表）；
  3. 或外部系统支持两阶段提交（极少见）。

⚠️ 事务 + 外部 DB 是最常见的误用：生产者事务提交成功，但 DB 写入失败，Kafka 无法感知。
⚠️ 别为了「EOS」引入两阶段提交，大多数业务用「幂等写 + 至少一次」更简单可靠。

四、顺序保证的三个破坏点

破坏点 原因 解法
重试乱序 max.in.flight>1 且未开幂等 开幂等（max.in.flight≤5 也保序）
分区变更 加分区后 hash % N 变化 分区数一次性规划好，别事后加
消费端并行 多线程处理同一分区 同 key 路由到同一线程，或按分区单线程

⚠️ 「Kafka 保证顺序」这句话只在单分区内成立。跨分区没有任何顺序保证。
⚠️ 消费端开线程池并行处理，即使单分区也会乱序 —— 这是业务代码引入的，不是 Kafka 的锅。

五、吞吐调优参数表

Producer

参数 默认值 调大/调小的影响
batch.size 16384 调大 → 更高压缩比、更高吞吐，但单条延迟上升
linger.ms 0 调大 → 攒批更充分，吞吐升、延迟升
buffer.memory 33554432（32 MB） 总缓冲，满了 send() 阻塞或抛异常
compression.type none 见下节
max.request.size 1048576（1 MB） 单请求上限，调大才能发大消息
acks all（3.0+ 幂等开启后） 见第一篇

Consumer

参数 默认值 作用
fetch.min.bytes 1 攒够这么多字节才返回，调大降空转
fetch.max.wait.ms 500 最多等这么久就返回
max.partition.fetch.bytes 1048576 单分区单次拉取上限
max.poll.records 500 单次 poll() 返回的记录数
max.poll.interval.ms 300000 处理超时会被踢出组

⚠️ linger.ms 与延迟是直接冲突的：设 20ms 意味着每条消息最多等 20ms 才发。低延迟场景保持 0。
⚠️ buffer.memory 满了默认阻塞 send()（max.block.ms 默认 60s），之后抛 TimeoutException；用 send(callback) 别用同步 get()。
⚠️ max.partition.fetch.bytes 必须 ≥ 生产者单条消息大小，否则会出现「能写进去但读不出来」的诡异现象。
⚠️ max.poll.records 调大不一定更快：单次处理时间变长，可能触发 max.poll.interval.ms 超时。

六、压缩算法对比

算法 压缩比 CPU 开销 适用
none 1× 无 已压缩数据（图片/视频）
gzip 高 高 网络带宽极紧张
snappy 中 低 通用，兼容性好
lz4 中 最低 低延迟优先
zstd 最高 中 推荐默认（Kafka 2.1+）

压缩是批量级的：整个 record batch 压一次，Broker 存压缩态，只有 Consumer 解压。

⚠️ 换压缩算法会导致混合压缩格式的日志段，旧客户端可能不支持新算法，滚动升级要注意顺序。
⚠️ 压缩比再高也救不了「消息本身太小」的场景 —— 小消息攒批（linger.ms）比换算法更有效。

七、分区数规划与副本同步

分区不是越多越好：

成本项 说明
文件句柄 每个分区每个 segment 至少 2~3 个文件
Rebalance 时间 分区越多，分配计算与元数据传播越慢
端到端延迟 多分区 = 更多批、更多网络往返
故障恢复 Leader 切换要处理更多分区
元数据 Controller 维护的分区状态线性增长
场景 建议分区数
低吞吐、强顺序 1（或按 key 分布）
常规业务 6~12
高吞吐 按目标吞吐 / 单分区吞吐估算，再留 2× 余量

副本同步：

参数 默认值 作用
num.replica.fetchers 1 每个 Broker 拉取副本的线程数，调大可加速同步
replica.fetch.max.bytes 1048576 单次副本拉取上限
replica.lag.time.max.ms 30000 ISR 踢出阈值

⚠️ num.replica.fetchers 从 1 调到 2~4 常能显著降低 ISR 抖动，但会占用更多磁盘/网络。
⚠️ 分区数加到几百后，__consumer_offsets 的 50 个分区可能成为瓶颈，且 Controller 元数据变更会明显变慢。

八、监控指标与故障排查

必须盯的指标

指标 含义 危险信号
UnderReplicatedPartitions 副本数不足的分区数 持续 > 0
OfflinePartitionsCount 无 Leader 的分区数 > 0 立即告警
IsrShrinksPerSec / IsrExpandsPerSec ISR 收缩/扩张速率 持续收缩 = 同步跟不上
RequestHandlerAvgIdlePercent 请求处理线程空闲率 < 0.3 说明过载
Consumer Lag 消费滞后条数 持续增长
ActiveControllerCount 集群里应为 1 > 1 或 = 0 都是脑裂/无主

常见异常码

异常 原因 处理
NotLeaderForPartitionException 请求发给了非 Leader（通常是选举中） 客户端会自动刷新元数据重试
OffsetOutOfRangeException 提交的 offset 超出范围（数据已被清理） 检查 auto.offset.reset 与保留策略
UnknownTopicOrPartitionException Topic 不存在或元数据未同步 检查是否真的建了 Topic、auto.create.topics.enable
RecordTooLargeException 消息超过 max.request.size / message.max.bytes 调大或拆分消息
TimeoutException（send） buffer.memory 满或 Broker 无响应 看 max.block.ms、网络、Broker 负载
RebalanceInProgressException 消费组正在再平衡 重试；排查 Rebalance 风暴根因

⚠️ RecordTooLargeException 有三处限制：Producer max.request.size、Broker message.max.bytes、Consumer fetch.max.bytes，三处都要放开。
⚠️ OffsetOutOfRangeException 多半是「消费停太久 + 保留期到了」，根治靠监控 lag，而不是调大保留期。
⚠️ Rebalance 风暴的典型链路：处理慢 → max.poll.interval.ms 超时 → 退组 → 再平衡 → 处理更慢，必须从业务耗时下手。

常见坑清单

  • 以为开了幂等就万事大吉，忘了它只覆盖单分区单会话
  • enable.idempotence=true 同时手动设 acks=1，启动直接报错
  • 把 max.in.flight 改成 1 求顺序，白白牺牲吞吐
  • 事务里调外部 DB，以为还是 Exactly-Once
  • transactional.id 多实例共用，触发 fencing 互相踢下线
  • 消费端 read_committed 看到 offset 空洞，误判为丢数据
  • 事后给 Topic 加分区，同 key 顺序被破坏
  • 消费端多线程处理同一分区，自己把顺序搞乱
  • linger.ms 为了吞吐调到很大，P99 延迟爆炸
  • max.partition.fetch.bytes 小于消息体，写进去读不出来
  • max.poll.records 调大后触发 max.poll.interval.ms 超时
  • 用同步 send().get()，吞吐降到单条级别
  • 换压缩算法时没考虑滚动升级期间新旧客户端兼容
  • 盲目加分区，忽略了文件句柄与 Rebalance 成本
  • 只看 UnderReplicatedPartitions，漏掉 OfflinePartitionsCount
  • RequestHandlerAvgIdlePercent 长期接近 0 却还在加压
  • RecordTooLargeException 只改了 Producer 没改 Broker
  • 用调大保留期来掩盖 lag 增长，磁盘最终写满
