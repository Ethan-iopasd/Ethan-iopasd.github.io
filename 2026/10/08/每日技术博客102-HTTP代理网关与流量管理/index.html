七 代理、网关与流量管理 本篇

开场：一句话结论

正向代理代表客户端，反向代理代表服务端 —— 这一个区别决定了后面所有配置的默认值；而网关出问题，八成是「真实 IP 取错」或「超时错配」。

一、代理与网关的角色划分

角色 代表谁 位置 典型实现
正向代理 客户端 客户端侧 公司出口代理、抓包工具、VPN
反向代理 服务端 服务端入口 Nginx、Envoy
负载均衡器 服务端 入口 / 四层 LVS、ELB、Envoy
API 网关 服务端 应用入口 Kong、APISIX、Spring Cloud Gateway
BFF 服务端 面向某类客户端 自研 Node / Java 服务
CDN 服务端 边缘 各家 CDN
层 决策依据 例子
四层（L4） IP + 端口 TCP 转发，不解 HTTP
七层（L7） 路径 / Host / Header 路由到不同服务、改头、鉴权

⚠️ 正向代理与反向代理的区分点只有一个：它替谁出面。 客户端配置了它 → 正向；服务端部署了它 → 反向。同一个软件（Nginx）两边都能当。

⚠️ BFF 与 API 网关不是一回事：网关做通用横切（鉴权 / 限流 / 日志），BFF 做面向特定客户端的聚合与裁剪。把 BFF 逻辑塞进网关，网关就会变成变更瓶颈。

二、真实客户端 IP 怎么取

经过代理后，TCP 层的 remote_addr 是上一跳代理的地址，不是真实客户端。

头 标准 内容
X-Forwarded-For 事实标准 逗号分隔的 IP 列表，客户端在前
X-Real-IP Nginx 约定 单个 IP，通常取最后一个可信值
Forwarded RFC 7239 结构化，含 for / by / proto / host
True-Client-IP Cloudflare 等 厂商专用
取法 结果 是否安全
取最左（第一个） 原始客户端 ❌ 可伪造
取最右（最后一个） 最近一跳代理 ❌ 不是客户端
从右往左数第 N 个可信跳 真实客户端 ✅ 需配可信代理白名单

⚠️ X-Forwarded-For 完全可伪造：客户端可以自己带一个 X-Forwarded-For: 1.2.3.4，代理只会在后面追加。直接取最左值等于把 IP 白名单交给攻击者。

⚠️ 正确做法是维护可信代理链：从右往左跳过已知代理的 IP，取第一个不可信的值。Nginx 用 set_real_ip_from + real_ip_header + real_ip_recursive on 实现。

⚠️ 忘了配 set_real_ip_from，日志里全是代理 IP，限流会把所有用户当成同一个人。

三、协议、连接与 hop-by-hop 头

X-Forwarded-Proto 与重定向死循环

TLS 在代理层卸载后，应用看到的是 http，于是把「HTTP 跳 HTTPS」的重定向又发一遍 —— 无限重定向。

应用侧判断 正确写法
原始协议 读 X-Forwarded-Proto，不是 req.protocol
原始 Host 读 Host / X-Forwarded-Host
生成绝对 URL 用上面两个拼，不要用 socket 信息

⚠️ 这是重定向死循环的头号成因：代理卸载了 TLS，应用却按 http 判断，于是不停 301 到 https，代理再卸载一次。改配置时优先怀疑这里。

⚠️ X-Forwarded-Proto 同样是客户端可伪造的。只有紧邻应用的代理写的那个值才可信。

hop-by-hop 头

这些头是逐跳的，代理不应原样转发：

逐跳头 说明
Connection 列出本次连接的所有逐跳头
Keep-Alive 连接保活参数
Transfer-Encoding 分块编码
TE 允许的传输编码
Upgrade 协议升级（如 WebSocket）
Proxy-Authenticate / Proxy-Authorization 代理认证
Trailer trailer 字段名

⚠️ Connection: Upgrade + Upgrade: websocket 必须被显式转发，否则 WebSocket 握手会在代理处失败。多数现代代理有专门配置项，别只改 Connection。

代理超时与应用超时错配

超时 位置 典型默认
keepalive_timeout 客户端 ↔ 代理 65s（Nginx）
proxy_connect_timeout 代理 → 上游建连 60s
proxy_read_timeout 代理 ← 上游两次读之间 60s
proxy_send_timeout 代理 → 上游两次写之间 60s
应用侧 DB / RPC 超时 应用内部 视实现

⚠️ 代理超时必须大于应用超时。 否则应用还在处理，代理已经断开返回 504，应用白干一场 —— 还会继续消耗资源。

⚠️ proxy_read_timeout 是两次连续读操作之间的间隔，不是整个请求的总时长。长轮询 / SSE / 流式接口必须单独放宽，否则会被误杀。

100-continue 与 chunked

特性 代理下的行为
Expect: 100-continue 部分代理不支持，会直接转发 body，失去「先拒绝再传」的省流效果
Transfer-Encoding: chunked 代理通常需要缓冲后才能转发；Content-Length 未知会影响某些鉴权逻辑

⚠️ 依赖 Expect: 100-continue 做「先鉴权再上传」的服务，在链路上多一层不支持它的代理后会先收到完整 body，鉴权形同虚设。

四、网关的核心能力与限流

能力 说明 该不该放网关
路由 按路径 / Host / Header 转发 ✅
鉴权 校验 token、注入用户身份 ✅（粗粒度）
限流 按 IP / 用户 / 路由 ✅
熔断 上游连续失败则快速失败 ✅
重试 对失败请求重发 ⚠️ 谨慎
灰度 按规则切分流量 ✅
请求改写 改头、改路径 ✅
协议转换 HTTP ↔ gRPC ✅
响应缓存 缓存可缓存的响应 ✅
访问日志 统一入口日志 ✅
业务逻辑 订单校验、价格计算 ❌

限流四种算法

算法 原理 突发流量 实现要点
固定窗口 每分钟计数 边界处可双倍 最简单，有临界问题
滑动窗口日志 记录每次请求时间戳 精确 内存开销大
滑动窗口计数 相邻两窗口加权 近似精确 常用折中
令牌桶 匀速发令牌，桶内可积累 允许突发 网关最常用
漏桶 匀速流出 不允许突发 适合整形

⚠️ 限流键用 $remote_addr 而不是 $binary_remote_addr 会浪费大量共享内存。**$binary_remote_addr 是压缩后的二进制形式。**

⚠️ 多实例网关时，本地限流是每实例的：10 个实例各限 20r/s，全局就是 200r/s。要全局精确限流必须用共享存储（Redis）。

五、在网关重试与灰度

重试的风险

风险 说明
放大后端压力 后端慢时重试会让它更慢，雪崩
重复副作用 非幂等操作被重放
重试风暴 多层（客户端 / 网关 / 服务）叠加重试

⚠️ 只对幂等方法重试（GET / HEAD / PUT / DELETE / OPTIONS）。Nginx 里 non_idempotent 参数默认不启用，别为了「提高成功率」打开它 —— 那是在允许重放 POST。

⚠️ 重试要配退避 + 上限，并且要和熔断配合。没有熔断的重试，就是在后端已经挂了的时候继续砸它。

灰度 / 金丝雀切分

方式 实现 特点
按权重 split_clients / upstream 权重 简单，同一用户可能来回切
按 Header 匹配 X-Canary: 1 精准，便于内部验证
按用户 ID 哈希 hash $arg_uid consistent 同一用户粘性
按 Cookie 匹配灰度 Cookie 可随时收放

⚠️ 按权重切分时，同一用户的请求可能落到不同版本。需要用户级一致性就必须用哈希或 Cookie，否则会出现「刷新一次界面变一次」。

六、网关不该做的事与选型

反模式 后果
在网关写业务逻辑 所有变更都要改网关，成为瓶颈
网关做数据聚合 引入业务耦合，回滚困难
网关存状态 无法水平扩容
只有一个人能改网关配置 变更风险集中
网关做鉴权的全部逻辑 权限模型变化要动基础设施
网关 定位 特点
Nginx 通用反向代理 性能好，动态能力靠 Lua / njs
Envoy 服务网格数据面 xDS 动态配置，gRPC / 双向流支持好
Kong API 网关 插件生态，基于 Nginx
APISIX API 网关 动态路由，etcd 配置，Lua 扩展
Spring Cloud Gateway Java 生态 与 Spring 深度集成，Reactor 模型

⚠️ 网关的配置必须进版本库 + 可自动化发布。手动改配置、无灰度、无回滚的网关，是线上事故的高发地。

七、可观测性与常见故障

在网关打点

内容 说明
Access log 包含真实客户端 IP、上游地址、耗时、状态码
Trace 注入 生成 / 透传 traceparent（W3C Trace Context）
上游耗时 区分「网关处理」与「上游处理」

⚠️ $request_time 包含网关自身耗时，$upstream_response_time 只有上游耗时。两者差值大 = 问题在网关（如缓冲区、限流排队、Lua 阻塞）。

502 / 504 的区分与排查

状态码 含义 常见原因
502 Bad Gateway 上游返回了无效响应或拒绝连接 上游进程挂了、端口错、协议不匹配
504 Gateway Timeout 上游在超时内没响应 上游慢、超时配太短、死锁

排查顺序：

  1. 看 upstream_addr 是否为 - → 根本没连上（502）
  2. 看 upstream_status → 上游自己的状态码
  3. 看 upstream_response_time 是否为 - 或超时值
  4. 对比应用日志同一时刻有没有收到请求
其他故障 原因
400 请求头过大 large_client_header_buffers 太小
413 body 过大 client_max_body_size 太小
超时级联 代理超时 > 应用超时 > DB 超时，逐层放大
请求被截断 缓冲区不足，上游响应未完整转发

⚠️ 超时配置必须自内向外递增：DB 超时 < 应用超时 < 代理超时 < 客户端超时。反过来配会导致「内层还在跑，外层已放弃」。

⚠️ 502 出现时先看 upstream_addr 是不是 -。是 → 连不上（网络 / 端口 / 上游未启动）；不是 → 连上了但响应非法（协议错、上游中途崩溃）。这一步能省掉大量排查时间。

常见坑清单

  • 直接取 X-Forwarded-For 最左值当真实 IP
  • 没配 set_real_ip_from，日志里全是代理 IP
  • 限流按代理 IP 做，把所有用户当成一个人
  • TLS 卸载后应用仍按 http 判断，造成重定向死循环
  • 忘记转发 X-Forwarded-Proto / Host
  • 只改 Connection 头却漏了 Upgrade，WebSocket 握手失败
  • 代理超时小于应用超时，上游白干活
  • 把 proxy_read_timeout 当成总时长，误杀流式接口
  • 对非幂等方法开 non_idempotent 重试
  • 重试不带退避与熔断，制造重试风暴
  • 限流键用 $remote_addr 而非 $binary_remote_addr
  • 多实例网关只用本地限流，以为是全局精确
  • 按权重灰度导致同一用户来回切换
  • 在网关里写业务逻辑与数据聚合
  • 网关配置手工改、无版本、无回滚
  • 超时配置自外向内递减，出现级联超时
  • 502 / 504 不分，排查方向一开始就错
  • 忘了 client_max_body_size，大请求被 413 拦掉
