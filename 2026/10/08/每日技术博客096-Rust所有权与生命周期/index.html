一 所有权、借用与生命周期 本篇

开场：一句话结论

Rust 不靠 GC，也不靠程序员自觉 —— 它把「谁负责释放内存」「谁能同时改这块内存」变成类型系统的一部分，编译不过就是真的会出事。

一、它到底在跟谁抢活

语言 内存回收 数据竞争 空指针 / 悬垂 运行时成本
C / C++ 手动 / RAII + 智能指针 无保证，UB 无保证，UB 接近零
Go GC 运行时 -race 才检测 nil panic GC 停顿
Java GC 靠 synchronized / volatile NullPointerException GC 停顿
Rust 编译期所有权 + Drop 编译期 Send / Sync 拒绝 Option 显式建模 接近零

⚠️ Rust 的安全不是「不会崩」，而是「不会未定义行为」。越界访问照样 panic，只是 panic 是定义良好的行为，不是 UB。

二、所有权三原则

作用域结束时，Drop::drop 会按声明的逆序依次调用；结构体内部则按字段声明顺序 drop。

三、移动（move）vs 拷贝（Copy）

类型 赋值 / 传参行为
实现了 Copy 的类型 按位复制，原变量仍可用
未实现 Copy 的类型 移动，原变量失效

实现 Copy 的常见类型：

类别 例子
整数 / 浮点 i32 u64 usize f64
bool / char bool char
共享引用 &T
由 Copy 组成的复合 (i32, bool)、[u8; 4]、Option<i32>
裸指针 / 函数指针 *const T fn(i32) -> i32

⚠️ &mut T 不是 Copy。 可变借用一旦被移动（比如传进函数），原来的借用就失效了 —— 这是为了独占性。
⚠️ 为什么 String 不是 Copy？ 它持有堆指针。若允许按位复制，两个变量会指向同一块堆内存，出作用域时双重释放（double free）。这正是 Rust 拒绝隐式复制的理由。

四、Clone：显式深拷贝，代价自己扛

方式 是否分配 是否显式 原变量
Copy 隐式 栈上按位 否 可用
.clone() 视类型（String 会分配） 是 可用
move 否 否 失效

⚠️ .clone() 是性能可见的操作。在大循环里无脑 .clone() 是新手最典型的性能坑 —— 编译器不会替你优化掉它。
⚠️ #[derive(Clone)] 只是自动实现，不改变语义：字段是 Vec 就真的深拷贝整个 Vec。

五、借用：&T 与 &mut T

借用规则（编译期强制）：

同一作用域内，对同一数据：要么任意多个 &T，要么唯一一个 &mut T，二者不可兼得。

借用 别名数 可否写 跨线程共享（若 T: Sync）
&T 多个 否 可以
&mut T 唯一 是 可以（T: Send）

⚠️ 这条规则就是 Rust 不需要读-写锁就能静态排除数据竞争的根基：有别名就不能写，能写就没有别名。
⚠️ 借用是非词法（NLL）的：生命周期到最后一次使用为止，不是到作用域结束 —— 老代码里那些「明明没冲突」的报错，现在很多已经不报了。

六、借用检查器常见报错与修法

报错 触发场景 修法
cannot borrow as mutable 已有共享借用还活着 缩短共享借用作用域，或改用 RefCell / Mutex
cannot borrow as immutable ... as mutable 可变借用还活着时读 把读挪到写之后，或先 drop(m)
does not live long enough 返回了局部变量的引用 返回拥有所有权的值，或让调用方传 &mut 输出参数
cannot move out of borrowed content 从 &T 里 move 字段 .clone()、mem::take / mem::replace，或 Option::take
use of moved value move 后又用原变量 改传引用，或 .clone()
borrowed here after move 闭包捕获后又被使用 用 move 闭包 / Rc 共享

⚠️ mem::take 对 &mut T 生效（要求 T: Default），mem::replace 可以塞回一个替换值。这两个是「从借用里拿出所有权」的标准手法。

七、生命周期标注 'a

生命周期标注不改变任何值的存活时间，它只告诉编译器「这些引用之间的约束关系」。

生命周期省略（elision）三条规则 —— 满足就不用手写：

# 规则
1 每个引用参数各自分配一个独立生命周期
2 只有一个输入生命周期时，它被赋给所有输出生命周期
3 有 &self / &mut self 时，self 的生命周期赋给所有输出

'static 的真实含义：

写法 含义
&'static T 该引用可以活到程序结束（字符串字面量就是）
T: 'static T 内部不含任何非 'static 引用 —— 不是说值活到永远
Box<dyn Trait + 'static> 默认约束，Box 里的东西不能借用外部短命数据

⚠️ T: 'static 经常被误读成「活得久」。String、Vec<u8> 都满足 T: 'static，它们照样会在作用域结束时被 drop。
⚠️ 把 &'static 当成「万能解」硬塞进结构体，是新手最常见的逃逸手段 —— 它通常意味着设计错了。

八、&str / String / Cow 与 &[T] / Vec<T>

类型 拥有所有权 可增长 典型用途
str 否（DST） 否 只能以 &str / Box<str> 出现
&str 否 否 函数入参、切片
String 是 是 需要拥有 / 修改的字符串
Cow<'a, str> 视情况 视情况 多数只读、偶尔要改
场景 选型
只读入参 &str / &[T]
需要返回新值 String / Vec<T>
绝大多数只读、偶尔改 Cow<'a, T>
跨线程传递且要改 Arc<Mutex<Vec<T>>>

⚠️ &String / &Vec<T> 作为参数几乎总是错的 —— 用 &str / &[T]，它们能接受更多调用方（&String 能自动 Deref 成 &str，反过来不行）。

九、Drop 与 RAII

机制 触发时机
Drop::drop 所有者离开作用域 / 被 drop(x) 显式释放
提前释放 drop(value) 移动进 drop 函数后立即释放
不可提前 实现了 Drop 的类型不能做字段级部分移动

⚠️ Rust 没有 finally 的等价需求：文件、锁、连接都在 Drop 里释放，? 提前返回也不会漏 —— 这正是 RAII 的价值。

十、Box / Rc / RefCell / Arc / Mutex 选型

类型 解决什么 线程安全 运行时代价
Box<T> 堆分配 / 递归类型 / dyn Trait 继承 T 一次分配
Rc<T> 多所有者（单线程） 否（非 Send/Sync） 非原子计数
Arc<T> 多所有者（多线程） 是 原子计数
Cell<T> 内部可变性（T: Copy，无引用） 否 零检查
RefCell<T> 内部可变性（任意 T） 否 运行时借用检查，违反则 panic
Mutex<T> 跨线程可变共享 是 加锁，可能死锁
RwLock<T> 读多写少的跨线程共享 是 读写锁开销

⚠️ Rc 不是线程安全的 —— 计数不是原子的，Rc<T> 不实现 Send/Sync，跨线程会被编译器直接拒绝。
⚠️ RefCell 把借用检查推迟到运行时 —— 同时两个 borrow_mut() 会在运行时 panic，不是编译错误。滥用 RefCell = 把编译期保证换成崩溃。
⚠️ Arc<Mutex<T>> 里 Mutex 保护的是数据本身，不是「临界区代码」，锁的粒度由包住的范围决定。
⚠️ Mutex 中毒（poisoning）：持锁线程 panic 后，后续 lock() 返回 Err，可用 .unwrap_or_else(|e| e.into_inner()) 忽略。

内部可变性模式：外部看是 &self，内部却能改 —— Cell / RefCell / Mutex / RwLock 都是这个模式的不同取舍（检查时机从编译期移到运行时）。

十一、impl Trait vs 泛型

写法 位置 语义
fn f(x: impl Trait) 参数 等价于泛型 fn f<T: Trait>(x: T)，单态化
fn f() -> impl Trait 返回值 不透明类型，调用方只知道实现了 Trait
fn f<T: Trait>(x: T) 参数 显式泛型，可被 turbofish 指定 f::<T>
dyn Trait 字段 / 集合 动态分发，运行时查虚表，不能单态化

⚠️ impl Trait 参数不能同时指定 turbofish；需要显式类型参数时用泛型写法。
⚠️ 泛型是单态化：每个具体类型生成一份代码，二进制会变大；dyn Trait 只有一份代码但每次调用有虚表开销。

十二、什么时候真的需要 unsafe

unsafe 不关闭借用检查，它只解锁五件事：

能力 说明
解引用裸指针 *const T / *mut T
调用 unsafe fn 包括 FFI
访问 union 字段 ——
实现 unsafe trait 如 Send / Sync
修改 static mut 全局可变状态（edition 2024 收紧了规则）

⚠️ unsafe 的语义是「这段代码的正确性由你保证」，不是「关掉检查」。用它时要写清 // SAFETY: 注释说明前提。
⚠️ 安全抽象的意义：Vec、HashMap、Rc 内部全是 unsafe，但它们把不变量封在 pub API 后面。用户拿到的是无需 unsafe 就能安全使用的类型 —— 这才是 unsafe 的正确用法：集中封装，而不是四处开花。

常见坑清单

  • 以为 String 是 Copy，let b = a 之后继续用 a
  • 无脑 .clone() 绕过借用检查，把零拷贝代码写成 O(n²)
  • 同时持有 &T 和 &mut T，以为「只读一下没事」
  • 返回局部变量的引用（does not live long enough）
  • 从 &T 里直接 move 字段，忘了 clone / mem::take
  • 把 &'static 当万能解硬塞进结构体
  • 误读 T: 'static 为「值活到程序结束」
  • 参数写成 &String / &Vec<T>，白白限制调用方
  • 单线程用 Arc / Mutex（应该用 Rc / RefCell）
  • 多线程用 Rc / RefCell（编译不过，或改错成 Arc 忘了 Mutex）
  • 同时两个 RefCell::borrow_mut()，运行时 panic
  • 忘了 Mutex 中毒，.lock().unwrap() 在别人 panic 后连锁崩溃
  • 以为 unsafe 会关掉借用检查
  • 用 unsafe 却写不出 // SAFETY: 前提
  • 结构体字段顺序影响 drop 顺序，却没意识到
  • 在 Drop 类型上做字段级部分移动
