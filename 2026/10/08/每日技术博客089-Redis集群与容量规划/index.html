开场：一句话结论

主从解决读扩展与备份，Sentinel 解决单主自动切换，Cluster 解决分片与水平扩展 —— 三者不是替代关系，而 Cluster 的核心代价是多 key 操作不再自由。

一、主从复制：全量 / 部分重同步

配置 默认值 作用
repl-backlog-size 1mb 环形缓冲区，决定部分重同步能容忍多久断线
repl-diskless-sync yes（6.0+） 不落盘，直接经 socket 传 RDB
repl-diskless-sync-delay 5 等待更多 replica 一起做无盘同步
repl-timeout 60 复制超时
client-output-buffer-limit replica 256mb 64mb 60 从库缓冲上限，超了断开

复制风暴的两种形态：

形态 场景 缓解
单 master 多 replica 同时重连，master 反复 BGSAVE repl-diskless-sync-delay 聚合
级联（master → replica → replica） 副本数量多 中间层分担，减少 master 直接下游

⚠️ repl-backlog-size 默认只有 1MB，高写入场景几秒写满，断线必然触发全量同步。
⚠️ repl-diskless-sync-delay=5 会延迟 5 秒才开始同步，对快速切主有影响。
⚠️ 复制是异步的：master 返回 OK 时数据可能还没到 replica，min-replicas-to-write 是唯一兜底。
⚠️ WAIT 只等「当前时刻的复制进度」，不是持久化保证；且会阻塞当前连接，别放热路径。

二、Sentinel：quorum 与 majority 不是一回事

概念 含义
SDOWN 主观下线：单个 Sentinel 自己认为 master 挂了
ODOWN 客观下线：达到 quorum 个 Sentinel 都认为挂了
quorum 判定 ODOWN 所需的票数
majority 真正发起故障转移所需的多数派（> 总数 / 2）
Sentinel 总数 quorum=2 时 能否 failover
3 2 票 ODOWN ✅ 需 2 票 > 1.5
5 2 票 ODOWN ✅ 需 3 票（majority）
2 2 票 ODOWN ❌ 无容错，脑裂时无多数派

⚠️ quorum 只决定「是否标记 ODOWN」，majority 才决定「能否真正切换」，quorum 设小只让判定更快。
⚠️ Sentinel 必须奇数且 ≥ 3，否则脑裂时无法形成多数派。
⚠️ 客户端必须支持 Sentinel 协议（先连 Sentinel 拿 master 地址），直连 IP 的话切换后仍打旧主。
⚠️ min-replicas-to-write 是防脑裂丢数据的关键，代价是副本全挂时拒绝写入（刻意取舍）。

三、Cluster：16384 个 slot 与重定向

项 值
slot 总数 16384
分片算法 CRC16(key) mod 16384
最小节点数 3 主（多数派要求）
集群总线端口 port + 10000
返回 含义 客户端动作
MOVED <slot> <ip:port> slot 已永久归属别的节点 更新本地 slot 映射并重发
ASK <slot> <ip:port> slot 正在迁移中，该 key 已在目标节点 只重发这一次，不更新映射
TRYAGAIN 多 key 命令涉及正在迁移的 slot 稍后重试

⚠️ MOVED 要更新映射，ASK 不能更新映射 —— 搞反会导致后续请求持续打错节点。
⚠️ resharding 期间对正在迁移的 slot 做多 key 操作，可能拿到 TRYAGAIN，业务必须能重试。
⚠️ Cluster 模式下 SELECT 不可用（只有 db 0），FLUSHALL 也只作用于当前节点。

四、多 key 与 Lua 的跨 slot 限制

操作 单机 Cluster
MGET / MSET ✅ ⚠️ 同 slot 才行
SUNIONSTORE / RENAME ✅ ⚠️ 同 slot 才行
EVAL（Lua） ✅ ⚠️ 所有 key 必须同 slot
事务 MULTI/EXEC ✅ ⚠️ 同 slot 才行

强制同 slot 用 hash tag：

⚠️ hash tag 是双刃剑：所有 {1001} 的 key 挤在同一个 slot / 同一个节点，容易造成热点。
⚠️ 别用 {user} 这种常量 tag 把整个业务塞进一个 slot —— 那等于放弃分片。
⚠️ Cluster 下没有跨节点原子操作；要跨 key 原子性只能靠 Lua + 同 slot，或换回单机。

五、持久化与主从的结合

方式 说明 恢复速度 数据安全
RDB 定时快照，文件紧凑 快 可能丢最后一次快照后的数据
AOF 追加写命令日志 慢 取决于 appendfsync
RDB + AOF 同时开启，重启优先用 AOF 中 最好
appendfsync 行为 丢数据窗口
always 每条命令都 fsync 几乎不丢，性能最差
everysec（默认） 每秒 fsync 一次 最多丢 1 秒
no 交给操作系统 可能丢几十秒

⚠️ 正确组合是主库开 AOF、从库开 RDB，避免主库在 BGSAVE fork 时抖动。
⚠️ AOF 重写也会 fork，aof-rewrite-incremental-fsync yes 能缓解尖峰。
⚠️ 别把持久化当备份：FLUSHALL、误删都会同步写进 AOF，必须有异地快照。

六、内存管理与淘汰策略

八种淘汰策略：

策略 淘汰范围 算法
noeviction（默认） 不淘汰 写命令直接报错
allkeys-lru 所有 key 近似 LRU
allkeys-lfu 所有 key 近似 LFU
allkeys-random 所有 key 随机
volatile-lru 仅设了 TTL 的 key 近似 LRU
volatile-lfu 仅设了 TTL 的 key 近似 LFU
volatile-random 仅设了 TTL 的 key 随机
volatile-ttl 仅设了 TTL 的 key 优先淘汰 TTL 短的
场景 推荐
纯缓存，所有 key 都可丢 allkeys-lru 或 allkeys-lfu
缓存 + 持久数据混用 volatile-lru（务必给缓存设 TTL）
不允许丢数据 noeviction + 容量告警
mem_fragmentation_ratio 含义
≈ 1.0 正常
> 1.5 碎片严重，考虑 activedefrag
< 1 ⚠️ 已发生 swap，性能急剧下降

⚠️ noeviction 下内存满了写命令报 OOM command not allowed，读命令仍可用 —— 常被误判为 Redis 挂了。
⚠️ volatile-* 系列在没有 key 设 TTL 时等同 noeviction，会直接报错。
⚠️ mem_fragmentation_ratio < 1 说明用了 swap，单线程模型下会拖垮全部请求。
⚠️ 淘汰策略只对设了 maxmemory 生效；不设就一直吃到物理内存耗尽被 OOM Killer 杀掉。

七、大 key / 热 key 与阻塞排查

命令 问题 替代
KEYS * 全量扫描 SCAN 游标迭代
FLUSHALL / FLUSHDB 清空全部 FLUSHALL ASYNC
DEL 大 key 同步释放，阻塞 UNLINK（4.0+，后台释放）
HGETALL / SMEMBERS 大对象 一次性返回全部 HSCAN / SSCAN
LRANGE key 0 -1 全量返回大 list 分段 LRANGE
SORT 复杂度高 数据量小才用

⚠️ KEYS * 在生产上是事故级命令，数据量大时能阻塞几秒到几十秒。
⚠️ --bigkeys 内部用 SCAN，但会对每个 key 做 TYPE 与大小统计，仍有开销，别在高峰期跑。
⚠️ UNLINK 只是把释放动作丢给后台线程，内存不会立刻下降。
⚠️ slowlog 只记录命令执行耗时，不含网络往返，客户端看到的慢不一定在慢日志里。
⚠️ slowlog-log-slower-than 0 会记录所有命令，生产上会迅速吃满内存。
⚠️ latency monitor 抓的是事件级延迟（fork、过期键、淘汰等），和 slowlog 互补。

常见坑清单

  • 用默认 repl-backlog-size=1mb，高写入下断线必然全量同步
  • 把 WAIT 当成持久化保证
  • 混淆 Sentinel 的 quorum 与 majority，以为 quorum 设小就更容易切换
  • Sentinel 部署偶数个或只有 2 个，脑裂时无法形成多数派
  • 客户端不支持 Sentinel 协议，切主后仍打旧主
  • 没开 min-replicas-to-write，脑裂后丢失隔离期的写入
  • 把 MOVED 和 ASK 处理逻辑写反，ASK 时更新了本地映射
  • Cluster 下直接 MGET 跨 slot 的 key，报 CROSSSLOT
  • 用常量 hash tag 把整个业务塞进一个 slot，热点集中
  • 主库同时开 RDB + AOF，BGSAVE fork 时抖动
  • 把持久化当备份，误删后无法恢复
  • 内存满了却用 noeviction，误判为 Redis 宕机
  • 用 volatile-lru 但缓存 key 忘了设 TTL，等价于不淘汰
  • 不设 maxmemory，被系统 OOM Killer 杀掉
  • 忽略 mem_fragmentation_ratio < 1，已 swap 却继续加压
  • 生产上执行 KEYS * 或同步版 FLUSHALL
  • 用 DEL 删大 key，阻塞主线程
  • 高峰期跑 --bigkeys，把 Redis 拖慢
  • 只盯 slowlog 不看 LATENCY，漏掉 fork / 淘汰类延迟
  • slowlog-log-slower-than 0 上线，日志把内存吃满
