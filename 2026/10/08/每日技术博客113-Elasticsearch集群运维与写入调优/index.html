四 集群运维与写入调优 本篇

开场：一句话结论

ES 写入慢和集群不健康，八成出在两处：分片设计不合理（太多或太大），以及堆内存与磁盘水位没留余量。

一、节点角色：master 与 data 必须分离

角色 职责 是否存数据
master 维护集群状态、分片分配、索引元数据 否（专用 master 不存数据）
data 存分片、执行查询与写入 是
ingest 写入前预处理（pipeline） 否
coordinating 只做请求分发与结果合并 否
ml 机器学习任务 否

⚠️ 生产必须分离 master 与 data 角色。混布时数据节点的 GC 停顿会拖慢 master 选举与集群状态更新，极端情况下整个集群失去响应。

⚠️ master 选举需要「半数以上有投票权节点」存活。3 个专用 master 只能容忍 1 台故障；2 个 master 是危险配置（无法形成多数）。要么 3，要么 5，不要 2。

⚠️ cluster.initial_master_nodes 只在「全新集群第一次启动」时用。集群成形后必须移除，否则重启时可能触发脑裂式的重新选举。7.x 起 minimum_master_nodes 已被自动仲裁取代，不要再手动配。

二、分片设计：不是越多越好

规则 说明
主分片数创建后不可改 只能 reindex 或 _split / _shrink
副本数可动态改 PUT index/_settings 随时调
单分片大小 经验 10~50GB
每个分片都是独立 Lucene 索引 有文件句柄 / 堆内存 / 集群状态开销

⚠️ 分片过多是 ES 最常见的架构错误。每个分片都要占用堆内存、文件句柄，并写进集群状态。几千个小分片会让 master 更新集群状态变慢，最终拖垮整个集群。

⚠️ 「20 分片/GB 堆」是旧经验，已在 ES 8.3 废弃。不要再拿它当硬指标。当前做法是按分片大小（10~50GB）和数据量反推分片数，而不是按堆内存反推。

⚠️ number_of_shards 写错就没法改。上线前一定要算准；事后只能 reindex（成本极高）或用 _split（分片翻倍）/ _shrink（分片减半）。建索引前先估算数据量与增长。

分片分配与再平衡

分配失败常见原因 排查
磁盘水位超限 见第三节
节点属性不匹配 index.routing.allocation.*
版本 / 插件不一致 节点日志
分片数超过节点上限 total_shards_per_node

⚠️ 分片卡在 UNASSIGNED 时，先看 _cluster/allocation/explain，别急着 _cluster/reroute 强制分配。强制分配一个没有副本的分片（allow_primary）可能造成数据丢失。

三、磁盘水位线：写入失败的经典原因

水位 默认值 行为
low 85% 停止向该节点分配副本分片
high 90% 开始把分片迁移离开该节点
flood_stage 95% 把该节点上的所有索引设为只读

⚠️ flood_stage 触发后写入直接报错，错误形如 disk usage exceeded flood-stage watermark, index has read-only-allow-delete block（HTTP 429）。这是线上「突然写不进去」的头号原因。

⚠️ 解除只读只是临时止血。磁盘没腾出来，几分钟后又会触发。根因是容量不足，必须扩盘或删索引 / 缩短 ILM 保留期。

⚠️ 副本会成倍占用磁盘。1 副本 = 双倍存储。设副本前先算清磁盘预算，别让副本把水位线顶穿。

四、写入调优

手段 效果 注意
refresh_interval: 30s 或 -1 批量导入首选，减少 segment 生成 导入完改回 1s
_bulk 批量 5~15MB 摊薄网络与开销 太大反而增加失败重试成本
多线程并发 bulk 提升吞吐 别超过节点处理能力
副本设为 0，导入后改回 减少写入放大 导入期间无冗余
translog.durability: async 减少 fsync 有丢数据风险

⚠️ refresh_interval 默认 1s，每次 refresh 都生成一个新 segment。批量导入时高频 refresh 会制造大量小 segment，拖慢写入并加重后续合并。导入期间设 -1（关闭自动 refresh），导入后再 _forcemerge + 改回。

⚠️ translog.durability: async 会丢数据。异步刷 translog 时，节点崩溃可能丢失最近未刷盘的操作。只在可重建的导入场景用，不要在生产写入路径常开。

⚠️ index.translog.flush_threshold_size 控制 translog 何时触发 flush（默认 512MB）。调大能减少 flush 次数，但崩溃后恢复要重放的 translog 更多，恢复更慢。

⚠️ 导入时把副本设为 0 是标准操作，但别忘了改回来。忘了改，集群就没有冗余，一台节点挂了就可能丢分片。

五、refresh / flush / forcemerge：三者别混

操作 作用 代价
_refresh 把内存 buffer 写入新 segment，使其可被搜索 频繁 refresh 产生大量小 segment
_flush 把 translog 落盘并清空 触发 Lucene commit
_forcemerge 把多个 segment 合并成更少、更大的 消耗大量 IO 和 CPU

⚠️ _forcemerge 只对「只读索引」做。对仍在写入的索引 forcemerge 会不断重新合并，浪费 IO 且永远合不完。典型场景：冷数据 / 已关闭的历史索引。

⚠️ _forcemerge 会打满磁盘 IO。在大索引上执行可能导致查询变慢、写入受阻。低峰期执行，且一次只处理一个索引。

六、查询性能

手段 说明
filter context 结果可缓存，比 query context 快
_routing 自定义路由 减少分片扇出（查询只打相关分片）
preference 指定分片 / 节点偏好
track_total_hits 默认不再精确统计总数，精确统计代价高
batched_reduce_size 协调节点分批归并，降低内存峰值

⚠️ track_total_hits: true 在大结果集上开销显著。只需要「有没有结果」或近似总数时，别开精确统计。

⚠️ 自定义 _routing 能减少扇出，但会带来数据倾斜。路由值分布不均时，某些分片会明显偏大。用之前先确认路由键的分布。

七、_cat 排查清单与堆内存

API 看什么
_cat/health?v 集群状态、节点数、分片数、unassigned
_cat/indices?v 索引大小、文档数、健康色、分片数
_cat/shards?v 分片分布、UNASSIGNED 原因
_cat/allocation?v 各节点磁盘使用与分片数
_cat/thread_pool?v queue / rejected（过载信号）
_cat/nodes?v CPU / 堆 / 负载

⚠️ rejected 上升就是过载。线程池队列满了会直接拒绝请求，客户端拿到 es_rejected_execution_exception。这是写入 / 查询过载最直接的证据，比 CPU 指标更早。

⚠️ 堆不要超过 31GB。超过后 JVM 关闭压缩指针（compressed oops），对象引用从 4 字节变 8 字节，实际可用内存反而下降。宁可多开节点，不要开 64GB 堆的单节点。

⚠️ Xms 必须等于 Xmx。堆动态扩缩会引起 GC 停顿。固定堆大小是 ES 的基本要求。

⚠️ 必须禁用 swap。堆被换到磁盘会让 GC 停顿从毫秒级飙到秒级。**bootstrap.memory_lock: true + 系统层面关 swap，两个都要做。**

⚠️ indices.memory.index_buffer_size 默认占堆的 10%，是所有分片共享的索引缓冲区。堆太小 → 索引 buffer 太小 → 写入更容易触发 refresh。

八、监控、快照、滚动重启与 ILM

监控项 预警信号
JVM GC 时间 老年代 GC 频繁 / 停顿长
thread_pool.rejected 持续 > 0 = 过载
segment 数量 持续增长 = 合并跟不上
search / indexing 延迟 突增
磁盘水位 接近 high
unassigned_shards 持续 > 0

⚠️ 快照是增量的。第一次全量，后续只备份新增 segment，所以便宜且快，别省着不做。没有快照 = 没有后悔药。

滚动重启：禁用分片分配 → 重启一个节点 → 等分片恢复 → 再重启下一个。

⚠️ 滚动重启前必须禁用分片分配，否则每次重启都会触发大规模分片迁移，产生巨量 IO。重启完再恢复分配。

ILM（索引生命周期）：

阶段 动作
hot 活跃写入，rollover 滚动新索引
warm 只读，forcemerge、减少副本
cold 极少访问，迁移到廉价节点
delete 到期删除

⚠️ 不用 ILM 的日志集群，磁盘一定会爆。靠人工删索引不可持续。ILM 是日志类场景的必备配置，不是可选优化。

常见坑清单

  • master 与 data 混布，数据节点 GC 拖垮集群状态更新
  • 只配 2 个专用 master，无法形成多数派
  • 集群成形后没移除 cluster.initial_master_nodes
  • 主分片数设错，事后只能 reindex
  • 分片数量过多（几千个小分片），拖慢 master
  • 还拿已废弃的「20 分片/GB 堆」当硬指标
  • 磁盘顶到 flood_stage（95%），索引被设为只读写入失败
  • 解除只读后不腾磁盘，几分钟后再次触发
  • 批量导入时没把 refresh_interval 设为 -1
  • 导入时把副本设 0 却忘了改回来
  • 生产写入路径常开 translog.durability: async
  • 对仍在写入的索引执行 _forcemerge
  • 高峰时段对超大索引 _forcemerge，打满 IO
  • track_total_hits: true 用于大结果集，开销失控
  • 用 _routing 后路由键分布不均，造成分片倾斜
  • 忽略 thread_pool.rejected，直到客户端大量报错
  • 堆开到 31GB 以上，压缩指针失效
  • Xms 与 Xmx 不等，堆动态扩缩引起停顿
  • 没禁用 swap，堆被换出导致 GC 停顿暴涨
  • 不配快照，误删索引后无法恢复
  • 滚动重启前不禁用分片分配，触发大规模迁移
  • 日志集群不用 ILM，靠人工删索引直到磁盘爆
