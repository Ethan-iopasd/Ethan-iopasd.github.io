开场：一句话结论

CI 只负责产出不可变制品，CD 只负责把同一个制品送进不同环境 —— 环境里绝不重新构建。

一、CI 与 CD 的边界

阶段 输入 输出 职责
CI 源码 镜像 + digest 编译、测试、构建、扫描、推送
CD 镜像 digest 环境中的运行实例 拉取、配置注入、编排、发布

⚠️ 「构建一次，到处部署」是铁律：测试用的镜像和生产运行的必须是同一个 digest，否则测试结论不成立。
⚠️ 在环境里 docker build 或 npm install 再打包，等于每个环境一个制品 —— 必然出现「测试过了、线上不同」。

二、镜像标签策略

标签 可变性 评价
latest 可变 ❌ 无法回滚定位，禁止在生产使用
git sha 不可变 ✅ 与提交一一对应，推荐
语义版本 v1.2.3 不可变 ✅ 可读，适合对外发布
branch / env 可变 ⚠️ 覆盖写，回滚困难

⚠️ latest 的危险在于同一个标签指向不同内容，kubectl rollout undo 也回不到确定的版本。
⚠️ tag 可以被覆盖，digest 不能。生产部署优先固定 digest。
⚠️ 用分支名当标签，一旦分支重跑就把旧镜像覆盖了，回滚时找不到原物。

三、环境配置注入

方式 适用 注意
环境变量 简单配置、开关 数量多时难管理
ConfigMap 非敏感配置 改后需重启或触发 reload
Secret 敏感信息 默认 base64 不是加密
启动参数 命令行覆盖 便于临时调试

⚠️ 不要把配置打进镜像：同一镜像要能跑在 dev/staging/prod，配置靠外部注入。
⚠️ K8s Secret 只是 base64 编码，没有加密；etcd 未加密时明文可读，必须配 RBAC 与静态加密。
⚠️ 改 ConfigMap 后很多应用不会自动重载，需要 rollout restart 或挂 reloader。

四、GitOps 核心思想

原则 含义
Git 是唯一真相源 期望状态全部声明在 Git
声明式 描述「要什么」，不是「怎么改」
持续协调 Reconciliation 控制器不断把实际状态对齐到期望状态
拉模式 Pull 集群内 agent 主动拉取，而非外部推送
推模式 拉模式（GitOps）
凭证 CI 持有集群凭证（高风险） 集群内 agent 持有 Git 只读凭证
漂移检测 无（只能靠人比） ✅ 自动比对并告警/自愈
回滚 重跑流水线 git revert / 回退 commit

⚠️ 拉模式的关键收益是集群凭证不外泄，CI 不需要能直接操作生产集群。
⚠️ GitOps 的「自愈」会把手工修改自动抹掉 —— 这是特性不是 bug，但要提前告知运维。

五、Argo CD 与 Flux

维度 Argo CD Flux
形态 有 Web UI + CLI，Application CRD 纯 CLI/CRD，控制器集合
抽象 Application / ApplicationSet Kustomization / HelmRelease
同步策略 手动 / 自动（syncPolicy） 自动协调为主
漂移检测 UI 直观展示 OutOfSync 控制器 reconcile + 告警
多集群 中心化控制面管理多集群 每集群各装一套

⚠️ prune: true 会删除 Git 里已移除的资源，误删一个目录可能连带清掉生产对象 —— 生产建议先观察再开。
⚠️ selfHeal: true 会撤销手工改动，与「紧急热修」流程冲突，要约定好逃生通道。
⚠️ Argo CD 默认同步周期较长（约 3 分钟），需要 webhook 触发即时同步。

六、GitOps 里的 Secrets

方案 原理 取舍
Sealed Secrets 用集群公钥加密，只有集群内私钥能解 简单；密钥与集群绑定，迁移麻烦
SOPS 对 YAML 字段级加密，密钥放 KMS/Vault 灵活；需管理 age/KMS 密钥
External Secrets Git 只存引用，运行时从 Vault/云 Secret 拉 最安全；依赖外部系统可用性
Vault 独立密钥管理系统 功能全；运维成本高

⚠️ 永远不要把明文 Secret 提交进 Git，即使仓库私有 —— 历史记录会一直留着。
⚠️ Sealed Secrets 的解密私钥只在集群里，集群重建后旧密文无法解，必须备份私钥。
⚠️ External Secrets 依赖 Vault 可用；Vault 挂了新 Pod 可能起不来，要做本地缓存。

七、部署策略

策略 做法 优点 代价
滚动 Rolling 逐个替换旧 Pod 简单、资源省 新旧版本短时共存
蓝绿 Blue-Green 两套环境整体切换 秒级回滚 双倍资源
金丝雀 Canary 先导小比例流量 风险可控、可自动判定 需要流量切分与指标判定

⚠️ 滚动更新期间新旧版本同时在线，接口必须向后兼容，否则调用方随机报错。
⚠️ 蓝绿切换前要确认数据库兼容两个版本，否则切过去就炸。
⚠️ 金丝雀没有自动判定指标（错误率、延迟）就是「手动放量」，风险依旧。

八、回滚：三种手段的优先级

手段 速度 适用
特性开关 Feature Flag 秒级 代码已部署、仅需关功能
镜像版本回退 分钟级 需换回旧版本
git revert + 同步 分钟级 配置/清单回滚

⚠️ 优先用特性开关：不改镜像、不动部署，关闭开关即可止血，回滚成本最低。
⚠️ 镜像回退要求数据库向后兼容，否则旧代码读不懂新表结构。
⚠️ git revert 之后要等控制器同步，不是立刻生效，紧急时直接改镜像更快。

九、数据库迁移与部署时序

扩展-迁移-收缩（Expand → Migrate → Contract） 三段式：

时序 做法 原因
❌ 先发码后迁移 新代码读不存在的列 立刻报错
✅ 先迁移后发码 旧代码容忍新结构 新旧版本共存安全

⚠️ 迁移必须向后兼容：滚动更新期间新旧代码同时运行，删列/改类型会直接打挂旧版本。
⚠️ 大表 ALTER TABLE 可能锁表，生产要用在线 DDL 或分步执行。
⚠️ 迁移脚本要幂等，失败重跑不能报错。

十、健康检查与部署门禁

探针 作用 失败后果
liveness 进程是否活着 重启容器
readiness 是否能接流量 从 Service 摘除
startup 启动是否完成 保护慢启动应用

⚠️ liveness 探针配太激进（如 1s 超时）会把启动慢的应用反复杀死，形成重启循环。
⚠️ readiness 未就绪就接流量，滚动更新时用户会收到 502。
⚠️ 探针只测 /health 返回 200，却不检查依赖（DB/缓存），照样会放出坏实例。

十一、多环境结构与漂移

组织方式 结构 特点
分支隔离 env/dev、env/prod 分支 易漂移，合并痛苦
目录隔离（推荐） base/ + overlays/dev、overlays/prod 共享基线，仅覆盖差异

⚠️ 多分支管理环境会导致同一个修复要 merge 多次，长期必然漂移。
⚠️ 禁止手工改生产：手改的下一刻就被 GitOps 自愈抹掉，还会造成「配置只改一次」的幻觉。
⚠️ 环境差异只应存在于 overlay 的覆盖项里，base 必须完全共享。

十二、部署可观测性与 DORA 指标

把变更事件（部署/回滚）叠加到指标面板上，故障时一眼看出「是哪次发布引起的」。

DORA 指标 含义 方向
部署频率 Deployment Frequency 多久发一次 越高越好
前置时间 Lead Time for Changes 提交到上线耗时 越短越好
变更失败率 Change Failure Rate 需修复/回滚的发布占比 越低越好
恢复时间 Time to Restore 故障到恢复耗时 越短越好

⚠️ 只追求部署频率而不看变更失败率，是在制造事故。
⚠️ 没有变更事件打点，故障复盘只能靠人回忆「刚才是不是发了版」。
⚠️ 四个指标要一起看，单看任何一个都能被刷。

常见坑清单

  • 在每个环境里重新构建，导致测试与生产的镜像不是同一个
  • 生产用 latest 标签，回滚时定位不到版本
  • 用分支名当镜像标签，重跑覆盖旧镜像
  • 部署不用 digest 固定，tag 被覆盖后行为漂移
  • 把配置打进镜像，同一镜像无法跨环境
  • 以为 K8s Secret 是加密的（实际只是 base64）
  • 改 ConfigMap 后不重启，以为配置已生效
  • CI 持有生产集群凭证（推模式），凭证泄露风险高
  • 开 prune: true 误删 Git 里已移除的生产资源
  • 开 selfHeal 但没约定紧急热修流程
  • 把明文 Secret 提交进 Git
  • Sealed Secrets 私钥不备份，集群重建后无法解密
  • 滚动更新期间新旧版本接口不兼容
  • 金丝雀没有自动指标判定，实为手动放量
  • 回滚优先改镜像而非关特性开关，止血慢
  • 数据库先发码后迁移，新代码读不存在的列
  • 迁移不向后兼容，滚动期间打挂旧版本
  • liveness 探针过激，把慢启动应用反复杀死
  • 探针不检查依赖，放出坏实例
  • 手工改生产配置，造成环境漂移
