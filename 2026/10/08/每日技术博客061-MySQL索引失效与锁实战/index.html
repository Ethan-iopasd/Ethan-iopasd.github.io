开场：一句话结论

索引失效不是「索引坏了」，而是优化器算出来走索引更贵；锁问题的本质是「加锁范围由索引决定」—— 没走索引的更新，加锁范围等同全表。

一、索引失效清单

写法 是否失效 说明
WHERE name LIKE '%张%' ❌ 左模糊，无法定位起点
WHERE name LIKE '张%' ✅ 前缀可用
WHERE phone = 13800138000（phone 为 varchar） ❌ 隐式转换，列被当成数字
WHERE DATE(created_at) = '2026-10-08' ❌ 函数包裹列
WHERE id + 1 = 100 ❌ 列参与运算
WHERE a = 1 OR b = 2（b 无索引） ❌ 整体退化为全表
WHERE status != 1 ⚠️ 区分度低时优化器放弃
WHERE id NOT IN (1,2,3) ⚠️ 同上
WHERE idx_col IS NULL ✅ 索引里存 NULL，可用
WHERE a = 1 AND b > 2 AND c = 3 ⚠️ c 用不上（范围后截断）
ORDER BY 顺序与索引不一致 ⚠️ 触发 Using filesort

⚠️ 隐式转换的方向决定后果：字符串列传数字会让索引失效（列被转成数字）；反过来数字列传字符串通常仍能走索引（常量被转成数字）。只有前者是坑。

⚠️ WHERE a = 1 AND b > 2 AND c = 3 里，c 无法用于定位，但仍可用于索引下推（Using index condition）在引擎层过滤。别一看 Extra 有 Using where 就断定没用上索引。

⚠️ ORDER BY 想避免 filesort，排序列必须和索引顺序一致，且方向也要一致（ORDER BY a ASC, b DESC 用不了 (a, b) 的升序索引，除非建降序索引）。

⚠️ WHERE idx_col IS NULL 可以走索引（InnoDB 索引里存 NULL）。IS NOT NULL 能否走取决于 NULL 比例与优化器估算。

⚠️ 统计信息过期会让优化器选错索引。ANALYZE TABLE t;，或调 innodb_stats_auto_recalc / innodb_stats_persistent。大批量写入后不更新统计信息，执行计划可能突然劣化。

二、EXPLAIN 关键列与 EXPLAIN ANALYZE

列 关注点
type 访问类型，从好到差：system > const > eq_ref > ref > range > index > ALL
key 实际用的索引；NULL = 没用索引
key_len 实际用到的索引字节数，可反推用了几列
rows 预估扫描行数，越小越好
filtered 过滤后剩余百分比；rows × filtered% ≈ 实际参与 join 的行
Extra Using index / Using filesort / Using temporary / Using index condition

key_len 反推（以 utf8mb4 为例）：

列定义 索引中占用的 key_len
int NOT NULL / 允许 NULL 4 / 5（+1 存 NULL 标志）
bigint NOT NULL 8
varchar(20) NOT NULL utf8mb4 20×4 + 2 = 82
varchar(20) 允许 NULL 82 + 1 = 83
datetime（8.0） 5

EXPLAIN ANALYZE 输出是树形的，每个节点带 (actual time=... rows=... loops=...)：

字段 含义
actual time=A..B 该节点首行 / 末行耗时（ms）
rows=N 该节点实际返回行数（对比 EXPLAIN 的预估）
loops=N 该节点被执行的次数

⚠️ key_len 是反推用了联合索引前几列的关键：KEY idx(a,b,c) 全用上时 key_len = 三者之和，只用 a 时等于 a 的长度。这是判断「范围查询截断了后面列」最直接的手段。

⚠️ type = ALL 或大表上 key = NULL 是慢查询的头号嫌疑，但小表上 ALL 反而可能更快 —— 优化器是对的，别硬加 FORCE INDEX。

⚠️ Using filesort 不等于「用了磁盘排序」，它只是说「没走索引排序」。数据量小时在内存里排，一样叫 filesort。

⚠️ EXPLAIN ANALYZE 会真的执行语句。在 UPDATE / DELETE / INSERT 上用要包在事务里再 ROLLBACK，否则数据被改。

⚠️ 预估 rows 与实际差几个数量级，说明统计信息不准或谓词相关性被忽略 —— 这才是执行计划跑偏的根因，光看 type 看不出来。

三、行锁、间隙锁、临键锁与显式加锁

锁类型 加锁对象 何时出现
Record Lock 单条索引记录 等值命中唯一索引
Gap Lock 索引记录之间的间隙 RR 隔离级别下
Next-Key Lock 记录 + 前面的间隙 RR 下范围查询 / 普通索引等值
语句 锁类型 兼容性
SELECT ... FOR UPDATE 排他锁（X） 阻塞其他 X 和 S
SELECT ... FOR SHARE 共享锁（S） 与 S 兼容，与 X 互斥
LOCK IN SHARE MODE 同 FOR SHARE（旧语法） 8.0 起推荐 FOR SHARE

⚠️ 加锁范围由索引决定：走唯一索引等值命中 → 只锁一行；走普通索引 → 锁记录 + 间隙；没走索引 → 锁全表所有记录（InnoDB 逐行加锁，但效果等同表锁）。

⚠️ RR 下的 Gap Lock 是「防幻读」的代价，也是死锁高发区：两个事务分别锁住相邻间隙、再互相插入，就会形成死锁。很多高并发写入场景把隔离级别降到 RC，就是为了去掉间隙锁。

⚠️ SELECT ... FOR UPDATE 在 autocommit=1 且不在显式事务里时，锁立即释放，等于没加锁。必须在 BEGIN / START TRANSACTION 之后才有效。

⚠️ FOR SHARE 与 FOR UPDATE 互斥，但两个 FOR SHARE 兼容。多个事务同时 FOR SHARE 后再各自 UPDATE，就是典型死锁来源。

⚠️ INSERT ... ON DUPLICATE KEY UPDATE 在高并发下死锁率显著高于「先 UPDATE 再 INSERT」：它同时持有插入意向锁与冲突记录的锁，加锁顺序不确定。

⚠️ REPLACE INTO 不是「更新」，是先 DELETE 再 INSERT：自增主键会跳、ON DELETE 触发器会触发、外键级联会连锁。能用 INSERT ... ON DUPLICATE KEY UPDATE 就别用 REPLACE。

四、死锁排查

⚠️ MySQL 8.0.1 起 INFORMATION_SCHEMA.INNODB_LOCKS / INNODB_LOCK_WAITS 已被 performance_schema.data_locks / data_lock_waits 取代。旧脚本查锁会直接报「表不存在」。

⚠️ SHOW ENGINE INNODB STATUS 只保留最近一次死锁。要历史记录必须开 innodb_print_all_deadlocks，把每次死锁都打到 error log。

⚠️ InnoDB 检测到死锁后会主动回滚代价小的事务，不会自动重试。应用层必须捕获 1213 Deadlock found 并重试整个事务。

⚠️ innodb_lock_wait_timeout（默认 50s）只影响等待锁超时（报 1205），跟死锁检测无关。死锁是检测后立即回滚，不是等到超时。

五、MDL 元数据锁与长事务阻塞 DDL

场景 后果
长事务持有 MDL 读锁 ALTER TABLE 拿不到写锁，DDL 阻塞
DDL 排队之后 后续所有查询也排在 DDL 后面，整表不可用

⚠️ 这就是「一个 ALTER TABLE 卡住，整个表跟着挂」的经典事故：DDL 等待 MDL 时会插队到等待队列前面，之后所有新的 DML 都要排在它后面。先 KILL 长事务，再执行 DDL。

⚠️ SELECT 也会持有 MDL 读锁。一个跑了几分钟的 SELECT 就足以让线上 ALTER TABLE 卡死。DDL 前务必先查 INNODB_TRX。

⚠️ 大表加索引用 ALTER TABLE ... , ALGORITHM=INPLACE, LOCK=NONE;，或 pt-online-schema-change / gh-ost。8.0 的部分 DDL 已支持 instant（ALGORITHM=INSTANT），但仍要确认版本与操作类型。

六、隔离级别：RR vs RC 的取舍

维度 RR（默认） RC
幻读 靠 Gap Lock 防住 允许（需自行处理）
间隙锁 有 几乎没有
死锁概率 高 低
主从一致性 相对安全 需要 row 格式 binlog
典型场景 强一致账务 高并发互联网业务

⚠️ RC 下 binlog 必须用 ROW 格式（binlog_format=ROW），否则主从不一致。8.0 默认已是 ROW，但改隔离级别时仍要确认。

⚠️ RC 下每次 SELECT 都读最新快照，同一事务内两次读可能不同。依赖「读到的值不变」的业务逻辑（如扣减前先查余额）必须显式加锁，不能靠隔离级别。

⚠️ 从 RR 切到 RC 会去掉间隙锁，不会自动修复已有死锁逻辑。加锁顺序不一致导致的死锁，换隔离级别只是降低概率。

常见坑清单

  • 字符串列用数字查，触发隐式转换导致索引失效
  • 在索引列上套函数（DATE() / YEAR()），改写成范围条件
  • LIKE '%x%' 前导模糊
  • 联合索引查询跳过最左列
  • 范围查询之后的列以为还能用于定位
  • ORDER BY 列顺序或方向与索引不一致，触发 filesort
  • 用 SELECT * 放弃覆盖索引
  • 大批量写入后不 ANALYZE TABLE，统计信息过期
  • 只看 type，不看 key_len / rows / filtered
  • 在写操作上直接跑 EXPLAIN ANALYZE，数据被真实修改
  • 以为 FOR UPDATE 一定只锁一行，忽略无索引时锁全表
  • 在 autocommit 的隐式事务里用 FOR UPDATE，锁立即释放
  • RR 下范围更新触发大范围 Next-Key Lock，阻塞并发插入
  • 高并发用 INSERT ... ON DUPLICATE KEY UPDATE，死锁频发
  • 用 REPLACE INTO 当更新用，自增跳号 / 触发器误触发
  • 查锁还在用 INNODB_LOCKS 旧表（8.0 已移除）
  • 长事务不清理，阻塞 ALTER TABLE 并连带拖垮整表
  • 死锁回滚后应用不重试，直接把错误抛给用户
  • 把 innodb_lock_wait_timeout 当成死锁超时
  • 改 RC 却没确认 binlog_format=ROW，主从不一致
