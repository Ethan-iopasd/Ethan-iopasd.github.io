开场：一句话结论

容量不是「数据库能扛多少」，而是「在 p99 延迟目标下能扛多少并发」—— 先定延迟目标，再谈 QPS，最后用压测验证，永远留 2~3 倍余量。

一、容量评估的输入项

没有输入就没法算容量。先把这些量出来：

输入 说明 怎么拿
QPS / TPS 每秒查询 / 事务数 业务预估 + 历史峰值
读写比 SELECT 与写操作比例 慢查询日志 / Com_select vs Com_insert 等
数据量与增长速率 当前大小 + 每日增量 information_schema.tables
峰值倍数 峰值 / 均值 大促常见 3~10 倍
延迟目标 p95 / p99（不是平均值） 业务 SLA
热点分布 80% 请求打在哪 20% 数据 慢查询 + 业务分析

⚠️ 用平均值做容量规划一定会翻车。均值 1000 QPS 的系统，峰值可能是 8000 QPS。容量要按峰值 × 安全系数算。

二、连接数与连接池：不是越大越好

指标 含义
max_connections 服务器允许的最大连接数（硬上限）
Threads_connected 当前已建立的连接数
Threads_running 当前正在执行（非 Sleep）的线程数 ← 真正的并发

关键判据：

⚠️ Threads_connected 高不代表压力大，很多是空闲（Sleep）连接。真正要看的是 Threads_running。把 Threads_connected 当并发用是常见误判。

⚠️ 连接池不是越大越好。每个连接一个线程 + 栈 + 会话内存，几百个连接会加剧上下文切换和锁竞争。经验起点是 **CPU 核数 × 2 + 磁盘数**，再靠压测微调，而不是拍脑袋设 1000。

连接池关键参数（以 HikariCP 为例）：

参数 建议 说明
maximumPoolSize 从核数公式起步，压测调 不是越大越好
minimumIdle 与 max 接近，避免频繁建连 —
connectionTimeout 秒级（如 3s） 获取连接超时
idleTimeout 分钟级 空闲回收
maxLifetime 小于 MySQL wait_timeout 否则拿到被服务端关掉的死连接
validationTimeout 秒级 连接有效性检测

⚠️ 应用侧超时必须小于数据库侧超时，否则数据库先杀连接，应用还在傻等。典型：maxLifetime 要小于 wait_timeout，connectionTimeout 要小于 lock_wait_timeout。

三、innodb_buffer_pool_size：热数据必须装得下

参数 建议 说明
innodb_buffer_pool_size 专用机器 50%~75% 物理内存 缓存数据页 + 索引页
innodb_buffer_pool_instances 大池子设 8 或更多 减少内部锁争用
innodb_buffer_pool_dump_at_shutdown ON 关机时把热页列表落盘
innodb_buffer_pool_load_at_startup ON 启动时预热，避免冷启动打满 IO

⚠️ 命中率下降 → 磁盘 IO 成瓶颈 → 延迟整体上升。这是 buffer pool 不够（或热数据突增）最早的信号。命中率比 QPS 更早反映容量问题。

⚠️ 冷启动预热：dump_at_shutdown / load_at_startup 默认行为各版本不同，重启后 buffer pool 是空的，前几分钟会疯狂读磁盘。大实例务必显式开启，否则每次重启都是一次小型故障。

四、磁盘 IO 能力评估

列 含义 判读
%util 设备繁忙度 接近 100% 说明盘是瓶颈
await 平均 I/O 等待（ms） 超过 SSD 正常值（<1ms）很多就要警觉
aqu-sz 平均队列长度 持续 > 1 说明在排队
r/s w/s 每秒读写次数（IOPS） 对照盘的能力上限
存储 典型 IOPS 说明
机械盘 100~200 随机 IO 极差
本地 SSD 数万~数十万 —
云盘（ESSD 等） 随规格变化 IOPS 有配额上限，超了会限流

⚠️ 云盘 IOPS 是有配额的，不是想用多少用多少。规格买小了，业务量上来直接被限流，表现为 await 飙升。选云盘要同时看容量、IOPS、吞吐三个维度。

redo log 刷盘：innodb_flush_log_at_trx_commit

取值 行为 持久性 性能
1（默认） 每次提交都刷盘 最强，不丢已提交事务 最慢
2 写 OS 缓存，每秒刷盘 实例崩溃不丢，宕机可能丢 较快
0 交给后台每秒刷 可能丢 1 秒 最快

⚠️ 0 / 2 是拿持久性换性能。金融 / 订单类必须 1；能容忍极端情况丢 1 秒的数据（如日志、统计）才考虑放宽。别为了压测数字好看把生产改成 0。

五、写入瓶颈定位

参数 作用 调优方向
innodb_log_file_size redo log 文件大小 太小会频繁 checkpoint，写抖动
innodb_io_capacity 后台刷脏页的 IO 能力基线 SSD 可上调（如 2000~4000）
innodb_io_capacity_max 紧急刷脏上限 一般是 capacity 的 2 倍
innodb_flush_neighbors 是否连带刷相邻页 SSD 建议 0（随机 IO 快，连带无益）
innodb_page_cleaners 刷脏页线程数 大实例可增加

⚠️ 写瓶颈往往不是「写太慢」，而是「刷脏页刷不过来」。脏页堆积 → checkpoint 追不上 → 写入被限速。调 innodb_io_capacity / innodb_log_file_size 比加内存更直接。

⚠️ innodb_flush_neighbors=1 在 SSD 上是负优化。机械盘时代连刷相邻页能省寻道，SSD 没有寻道，连带刷只会放大写入量。

六、sysbench 压测：怎么测才有意义

sysbench 1.x 用 Lua 脚本名（oltp_read_write / oltp_point_select / oltp_write_only 等）指定场景；--table-size 是每张表行数，总数据量 = --tables × --table-size。

场景 用途
oltp_point_select 主键点查，测读上限
oltp_read_only / write_only 分离读 / 写能力
oltp_read_write 混合负载，最接近真实
--threads 梯度 找出吞吐拐点（QPS 不再涨、延迟开始涨）

⚠️ 不要在线上库压测。压测会打满 IO、产生大量 binlog、拖垮从库，甚至写脏业务数据。用与生产同配置的独立实例。

⚠️ 压测数据量必须与生产同量级。10 万行全在 buffer pool 里，测出来的是内存速度；1 亿行才会触发真实磁盘 IO。数据量不对，结论全废。

⚠️ 只看 QPS 不看延迟会被骗。加大并发 QPS 可能还在涨，但 p99 已经从 5ms 涨到 500ms —— 这叫「吞吐饱和但延迟崩溃」。找的是延迟拐点，不是最大 QPS。

七、压测必须看的指标

指标 来源 关注点
QPS / TPS sysbench / 监控 吞吐是否随并发线性增长
p95 / p99 sysbench 拐点出现在哪
错误率 sysbench 非 0 说明触到瓶颈
Threads_running MySQL 持续 > 核数 = 排队
主从延迟 SHOW REPLICA STATUS 写入压测必然放大
CPU / IO top / iostat 谁先饱和
buffer pool 命中率 MySQL 是否掉到 99% 以下

⚠️ 主从延迟是写入容量的隐藏上限。主库写得再快，从库重放跟不上，读业务就拿到旧数据。写入容量必须按「从库能重放多快」来算。

八、容量规划：公式与冗余

触发扩容的信号 阈值参考
QPS 达到单机上限 70%~80%
Threads_running 持续高 > CPU 核数
buffer pool 命中率 < 99%
磁盘使用率 > 70%~80%
主从延迟 持续 > 1s
p99 延迟 超过 SLA 的 50%

⚠️ 峰值不是平均值，扩容要提前。扩容（尤其分库分表）是重操作，需要迁移数据、改代码。等 QPS 打到 90% 才想扩容，已经来不及了。

⚠️ 冗余是 2~3 倍，不是 1.2 倍。要考虑：单节点故障后流量集中、大促峰值、数据增长、慢查询突发。1.2 倍余量等于没有余量。

九、单表行数、分库分表阈值与慢查询

单表没有硬性行数上限，取决于访问模式与索引。但下面这些会先变成问题：

现象 原因
B+ 树变高 树每高一层多一次磁盘 IO
DDL 时长剧增 重建表时间随行数线性增长
备份 / 恢复变慢 mysqldump / 物理备份都随数据量增长
统计信息不准 优化器选错执行计划
信号 常见阈值（经验，非绝对）
单表行数 千万~亿级开始警惕
单表大小 数十 GB 以上考虑拆分
单库 QPS 超过单机能力 70%
单库写入 从库重放跟不上

⚠️ 慢查询是容量杀手。一条没走索引的全表扫描，能耗掉几十个正常查询的容量。先优化慢查询，再考虑扩容 —— 扩容只是把问题放大。

⚠️ 分库分表是不可逆的架构决策。它带来分布式事务、跨库 JOIN、全局 ID、扩容再平衡等一连串问题。能用索引 + 读写分离 + 缓存解决的，别急着分库分表。

十、容量监控与预警

指标 预警线
连接数使用率 > 80%
buffer pool 命中率 < 99%
磁盘使用率 > 70%
主从延迟 > 1s（或业务可容忍值）
慢查询数 环比突增
Threads_running 持续 > 核数

⚠️ 预警要留出反应时间。磁盘 90% 才告警，可能来不及清理；连接数 95% 才告警，下一次流量高峰就是雪崩。阈值要按「处理问题所需的时间」倒推。

常见坑清单

  • 用平均 QPS 做容量规划，忽略峰值倍数
  • 把 Threads_connected 当并发，忽略 Threads_running
  • 连接池 maximumPoolSize 拍脑袋设成 1000
  • maxLifetime 大于 MySQL wait_timeout，拿到死连接
  • 应用超时大于数据库超时，数据库先杀连接应用还在等
  • innodb_buffer_pool_size 太小，热数据装不下
  • 没开 buffer pool 预热，每次重启都冷启动打满 IO
  • 只看 QPS 不看 p99，忽略延迟拐点
  • 云盘只买容量不看 IOPS 配额，被限流
  • 为了压测数字把 innodb_flush_log_at_trx_commit 改成 0
  • SSD 上仍开着 innodb_flush_neighbors=1
  • 在线上库跑 sysbench 压测
  • 压测数据量远小于生产，结论无意义
  • 忽略主从延迟这个写入容量的隐藏上限
  • 扩容只留 1.2 倍余量
  • 慢查询没优化就急着扩容
  • 单表几千万行还没评估 DDL 与备份代价
  • 把分库分表当成第一选择
  • 磁盘 / 连接数告警阈值定得太晚，来不及处理
