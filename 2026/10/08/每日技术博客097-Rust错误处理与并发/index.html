开场：一句话结论

Rust 里没有异常：**能恢复的错误走 Result，不可恢复的走 panic!**；并发能不能编译过，由 Send/Sync 在编译期裁定。

一、Option / Result 与 ? 运算符

需求 用哪个
找不到 / 空 Option<T>
会失败且需要知道原因 Result<T, E>

? 等价于在 Err 分支上做 return Err(From::from(e)) —— 所以错误类型不同也能传播，只要实现了 From。

场景 ? 的行为
Result<T, E> → 函数返回 Result<U, E> 直接传播
E 与返回错误类型不同，但 E: Into<F> 自动 From 转换后传播
Option<T> → 函数返回 Option<U> 同样可用
函数返回 () / 非 Result ✗ 编译错误

⚠️ Option<T> 不是 null：Option<i32> 和 i32 是不同类型，必须显式 match / ? / unwrap 才能拿到内部值。
⚠️ ? 在返回 Option 的函数里不能传播 Result，反之亦然 —— 类型必须对齐。

二、unwrap / expect / unwrap_or / ok_or

方法 失败时 适用
.unwrap() panic! 原型 / 测试 / 逻辑上不可能失败
.expect("msg") panic! + 信息 同上，但要留上下文
.unwrap_or(x) / .unwrap_or_else(f) 返回默认值 有合理默认值（或需要计算）
.unwrap_or_default() 返回 T::default() T: Default
.ok_or(e) / .ok_or_else(f) Option → Result 需要补上错误值
.map_err(f) / .and_then(f) 转换错误 / 链式成功路径 错误映射、连续失败操作

⚠️ 生产代码里 unwrap 的边界：只在「失败即 bug」处用（如已 contains_key 后的 get），并优先 .expect("说明为什么不会失败")。
⚠️ 把 unwrap 当错误处理 = 把可恢复错误变成进程崩溃。库代码尤其不能这么干。

三、panic! vs 可恢复错误

情况 选择
输入非法、文件缺失、网络失败 Result
逻辑不变量被破坏、越界、unwrap 空 panic!
库的公开 API **一律 Result**，别替调用方决定崩不崩
测试 / 示例 / 快速原型 panic! 可接受
配置 行为
panic = "unwind"（默认） 逐层展开栈，Drop 会执行，可被 catch_unwind 捕获
panic = "abort" 直接终止进程，体积更小、无展开开销，不可捕获

⚠️ catch_unwind 只捕获 unwind 模式下的 panic；panic = "abort"（[profile.release]）下根本没得捕。
⚠️ 跨 catch_unwind 边界的值需要 UnwindSafe；AssertUnwindSafe 是你在担保，别用来掩盖 &mut 的破坏性。
⚠️ 不要把 catch_unwind 当异常机制做流程控制 —— 那是反模式。

四、自定义错误与 thiserror / anyhow

分工：库用 thiserror（结构化、可实现 Error）、应用用 anyhow（省事、带上下文）。

维度 thiserror anyhow
错误类型 具名 enum，可 match anyhow::Error（类型擦除）
适合 库（调用方要按类型处理） 应用 / main / 二进制
上下文 需手写 .context() / .with_context()
下游 match ✅ ❌

错误链用 Error::source() 逐层取：let mut src = Some(&err as &dyn Error); while let Some(e) = src { println!("{e}"); src = e.source(); }

⚠️ Box<dyn Error> 的局限：类型被擦除，调用方无法 match 具体变体，也无法要求 Send + Sync（除非写 Box<dyn Error + Send + Sync>）。
⚠️ anyhow::Error 同样不能在库的公开 API 里出现 —— 那等于把「不可判别」传染给下游。
⚠️ main 返回 Result 时，Err 会以 Debug 格式打印 —— 想更友好要自己 match + eprintln! + std::process::exit(1)。

五、并发：thread / Send / Sync

trait 含义 例子
Send 所有权可跨线程转移 大多数类型；Rc<T> 不是
Sync &T 可跨线程共享 Mutex<T>（当 T: Send）是；RefCell<T> 不是

⚠️ Send / Sync 是自动 trait：由字段自动推导，编译器据此在编译期挡住数据竞争 —— 这是 Rust 并发安全的全部底气。
⚠️ Rc / RefCell 不是 Send，跨线程直接被拒；换 Arc / Mutex 即可。
⚠️ 锁的作用域越短越好：别把 MutexGuard 跨 await 持有（异步里会死锁）。

六、channel：std::sync::mpsc

项 说明
Sender<T> 可 clone → 多生产者
Receiver<T> 不可 clone → 单消费者
send / recv 接收端全丢时 send 返 Err；所有 Sender drop 后 recv 结束
sync_channel(n) 有界缓冲，n=0 为会合（rendezvous）

⚠️ 忘了 drop(tx) 会导致 for v in rx 永久阻塞 —— 因为还有存活的 Sender。这是 channel 最经典的死锁。

七、异步：async / await 与 tokio

维度 线程 async 任务
调度 OS 抢占式 运行时协作式（.await 处让出）
栈 每线程独立栈（MB 级） 无栈，状态机（KB 级）
切换成本 高（内核态） 低（用户态）
数量级 / 适合 数千 / CPU 密集 数十万 / I/O 密集

Pin 为什么存在（简要）：async 会被编译成自引用状态机，跨 await 保存的局部变量在内存里的地址不能变。Pin<P> 就是「保证不再移动」的类型级承诺 —— 所以你看到 Box::pin / Pin<Box<dyn Future>>。用 async/await 时编译器替你处理，手写 unsafe 的 poll 才需要操心。

⚠️ async 函数在被 .await / spawn 之前不会执行任何代码 —— 它返回的是一个惰性 future。
⚠️ tokio::spawn 要求 future 是 Send + 'static：跨 await 持有非 Send 值（如 Rc）会让它编译不过。
⚠️ 在 async 里调 std::fs、std::net、同步锁、reqwest::blocking 等会卡住整个运行时线程，其他任务全部饿死。用 tokio::fs / tokio::net 或 spawn_blocking。
⚠️ **不要跨 .await 持有 std::sync::Mutex 的 MutexGuard**（它不是 Send，会编译不过）—— 换 tokio::sync::Mutex。

八、工程实践：cargo 工作区、feature 与工具链

命令 用途
cargo build --features json / --no-default-features 打开 / 关闭 feature
cargo tree -e features 看 feature 从哪来
cargo fmt 统一格式（rustfmt）
cargo clippy -- -D warnings lint，CI 里当错误跑
cargo test / cargo doc --open 测试 / 生成 API 文档
cargo audit 扫依赖的已知漏洞（RustSec）
cargo deny / cargo udeps 许可与来源约束 / 找未使用依赖
serde 属性 作用
rename_all = "camelCase" 字段名批量转换命名风格
skip_serializing_if = "Option::is_none" 为 None 时不输出该字段
default 反序列化缺失时用 Default
flatten / tag = "type" 内联嵌套结构 / 枚举内部标签

⚠️ feature 是可加的（additive）：Cargo 会把同一依赖被所有使用者打开的 feature 做并集，所以 feature 不能用来做「二选一」的破坏性开关 —— 那会在多 crate 依赖里失效。
⚠️ 工作区里每个成员共享一份 Cargo.lock，但 [patch] / [profile] 只在工作区根生效。
⚠️ 文档测试默认会被 cargo test 编译并执行 —— 文档里的示例一旦过时就构建失败，这是好事。
⚠️ tracing 是结构化日志：字段以键值对携带，可跨 async 任务传播 span，比 log + env_logger 更适合异步。subscriber 只能 init 一次，重复 .init() 会 panic；库代码不要自己 init。
⚠️ serde 是零拷贝优先的：&str / &[u8] 字段可借用输入缓冲，但要求输入活得更久；生命周期不够时用 String。

九、与 C / Python 互操作（简介）

方向 工具 备注
Rust → C extern "C" + #[no_mangle] 注意 ABI、unsafe
C → Rust bindgen 生成绑定 头文件转 extern
Rust ↔ Python PyO3 + maturin 最成熟的方案
Rust ↔ Node napi-rs ——
类型自动桥接 cbindgen / cxx 减少手写胶水

⚠️ FFI 边界**全是 unsafe**：跨语言传的指针、生命周期、字符串编码（CString vs &str）都要自己保证。边界越窄越好。

常见坑清单

  • 生产代码里到处 unwrap，把可恢复错误变成进程崩溃
  • 库的公开 API 返回 panic! 而不是 Result
  • 忘了 ? 会做 From 转换，手写一堆 map_err
  • Box<dyn Error> 用在库 API，类型被擦除，调用方没法 match
  • thiserror / anyhow 用反（库用 anyhow、应用用 thiserror）
  • catch_unwind 配 panic = "abort"，根本捕不到
  • panic = "abort" 后才发现需要 Drop 展开清理
  • mpsc 忘了 drop(tx)，for v in rx 永久阻塞
  • 跨线程用 Rc / RefCell，或该用 Mutex 却只用了 Arc
  • 在 async 里调同步阻塞 API（std::fs / reqwest::blocking）
  • 跨 .await 持有 std::sync::MutexGuard（非 Send，编译不过）
  • 跨 .await 持有非 Send 类型，导致 spawn 编译失败
  • 以为 async fn 会立即执行（其实要 .await / spawn）
  • feature 拿来做二选一的破坏性开关（Cargo feature 是可加并集）
  • tracing_subscriber 多次 .init() panic
  • 库代码里自己 init 全局 subscriber
  • 忘了文档测试会被 cargo test 真的跑，示例写死过时 API
