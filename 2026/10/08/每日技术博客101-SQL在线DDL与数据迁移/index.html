七 在线 DDL 与数据迁移 本篇

开场：一句话结论

DDL 的危险不在 DDL 本身，而在它要抢的那把 MDL 排他锁 —— 一个未提交的长事务就能让 DDL 排队，进而堵死后面所有查询。

一、DDL 为什么会锁表：MDL 才是主角

MySQL 8.0 的 ALTER TABLE 执行分三段：准备阶段（拿 MDL 排他锁）→ 执行阶段（按 ALGORITHM 干活）→ 提交阶段（改元数据 + 再拿一次 MDL 排他锁）。

关键在于：准备和提交阶段都需要短暂的 MDL 排他锁。这个锁必须等所有持有 MDL 共享锁的事务结束。

⚠️ 这就是最经典的线上事故链：长事务 → DDL 等锁 → DDL 之后的查询全部排队。哪怕 DDL 本身是 ALGORITHM=INSTANT 也躲不过，因为卡的是 MDL，不是数据重建。

先杀掉长事务，再执行 DDL

给 DDL 加锁等待超时，避免无限排队

⚠️ lock_wait_timeout 是会话级的，DDL 默认值是 31536000 秒（一年）。不改它，DDL 会一直排队，把后面的查询全堵死。

二、ALGORITHM 三档：INSTANT / INPLACE / COPY

ALGORITHM 是否重建表 是否复制数据 并发 DML 代价
INSTANT 否 否 ✅ 只改元数据，毫秒级
INPLACE 多数否（部分原位重建） 视操作 ✅（部分需 LOCK=SHARED） 需记录 DDL 期间的并发变更
COPY 是 是 ❌ 阻塞写 最重，等于重建整张表

哪些操作能走 INSTANT（MySQL 8.0 官方 Online DDL 表）：

操作 INSTANT 支持 起始版本
ADD COLUMN ✅ 8.0.12 起默认 INSTANT
DROP COLUMN ✅ 8.0.29 起默认 INSTANT
RENAME COLUMN ✅ 8.0.28 起（需同类型、同 NULL 属性）
设置 / 删除列默认值 ✅ 仅改数据字典
末尾追加 ENUM / SET 成员 ✅ 仅当存储大小不变
加 / 删 VIRTUAL 生成列 ✅ 非分区表
重命名表 ✅ 仅重命名文件
修改索引类型（USING BTREE） ✅ —

哪些操作必须重建表（COPY 或 INPLACE 原位重建）：

操作 实际算法 说明
修改列数据类型 COPY 几乎一定重建，代价最大
缩小 VARCHAR COPY —
VARCHAR 从 <256 字节扩到 ≥256 字节 COPY 长度字节从 1 变 2
删除主键（不加新主键） COPY 只有 COPY 支持
添加主键（单加） INPLACE 原位重建，需 SQL_MODE 严格
加 / 删 STORED 生成列 COPY / INPLACE 添加与改序仅 COPY
PARTITION BY / REMOVE PARTITIONING COPY 重建整表

⚠️ 改列类型几乎一定是 COPY。所以「把 VARCHAR(20) 改成 VARCHAR(64)」这种扩长通常可以 INPLACE，但「INT 改 BIGINT」就是全表重建 —— 千万行表在高峰期执行等于自杀。

⚠️ INSTANT 有行版本上限 64：每次 INSTANT 加 / 删列都会产生一个新行版本，由 INFORMATION_SCHEMA.INNODB_TABLES.TOTAL_ROW_VERSIONS 跟踪（SELECT NAME, TOTAL_ROW_VERSIONS FROM INFORMATION_SCHEMA.INNODB_TABLES WHERE NAME LIKE '%/t'），超过 64 后 INSTANT 会被拒绝，必须退回 INPLACE / COPY 重建。

三、LOCK 级别与降级行为

LOCK 允许并发读 允许并发写 适用
LOCK=NONE ✅ ✅ 在线首选
LOCK=SHARED ✅ ❌ 如加 SPATIAL 索引
LOCK=EXCLUSIVE ❌ ❌ 最差，尽量避免
LOCK=DEFAULT 由操作决定 由操作决定 不显式指定时的行为

降级规则（ALGORITHM / LOCK 都是「向上申请、向下兼容」）：

⚠️ 不显式指定 ALGORITHM / LOCK 时，MySQL 会自己挑一个。挑到 COPY 你也不知道 —— 生产环境 DDL 永远显式写死 ALGORITHM 和 LOCK。比如 ALTER TABLE t MODIFY COLUMN c VARCHAR(64), ALGORITHM=INPLACE, LOCK=NONE; —— 若只能 COPY，它会直接失败，而不是默默重建。

四、innodb_online_alter_log_max_size 与「DDL 跑到一半失败」

INPLACE 期间，并发 DML 的变更会写进一块 online alter log（临时日志），等 DDL 完成后重放到新结构上。这块日志的大小上限由 innodb_online_alter_log_max_size 控制。

参数 默认值 含义
innodb_online_alter_log_max_size 128 MB 在线 DDL 期间并发 DML 日志上限

超上限的后果：DDL 直接失败并回滚，前面几小时的重建全部作废：

⚠️ 大表 + 高写入的 INPLACE DDL 一定要先调大这个值（比如 1G），并且在低峰期执行。写入越猛，日志涨得越快，失败得越早。

⚠️ 另一种失败是 Lock wait timeout exceeded —— 说明 DDL 在等 MDL，前面有长事务。先清长事务，再重试，不要盲目加大 lock_wait_timeout。

五、大表变更：pt-online-schema-change 与 gh-ost

ALGORITHM=INSTANT 覆盖不了所有场景（改类型、删主键、重建分区），大表这时要用外部工具。两者都是影子表思路，区别在怎么同步增量。

维度 pt-online-schema-change gh-ost
增量同步方式 在源表上建触发器（INSERT/UPDATE/DELETE） 读取 binlog（伪装成 replica）
对源表的影响 触发器增加写入开销 无触发器，源表几乎零额外负载
需要权限 建触发器权限 REPLICATION SLAVE + REPLICATION CLIENT
外键 支持（受限） 不支持外键
暂停 / 限速 支持 支持，且可动态调整
切换（cut-over） 短暂锁（RENAME 原子切换） 同样短暂锁，需 RENAME
适用 通用、成熟 高写入大表、不想加触发器

⚠️ 两者切换瞬间都会短暂锁表（RENAME TABLE 需要 MDL），只是窗口从「小时级」压到「秒级」。这不是零锁，是「极小锁」。

⚠️ 对主从延迟的影响是双刃剑：影子表重建会产生大量 binlog，从库重放跟不上 → 主从延迟飙升。所以工具都要限速（--max-load / --critical-load / --chunk-time），宁可慢，不要打爆从库。

六、迁移工具：版本表与 checksum

工具 语言 版本表 校验机制 回滚
Flyway Java flyway_schema_history 记录每个版本的 checksum 社区版无自动 undo（需 undo 脚本，Teams 版）
Liquibase Java DATABASECHANGELOG changeset 级 checksum 支持 rollback（需写 rollback 段）
Alembic Python alembic_version 链式 revision downgrade
golang-migrate Go schema_migrations up / down 成对文件 down 脚本

核心规则：已执行的迁移文件不能改。

⚠️ 改已执行迁移 = 改了历史。线上环境会 checksum 失败启动不了；就算强制忽略，各环境结构已经分叉。要改就新增一个版本，不要动老的。

⚠️ 回滚脚本要不要写？ 看场景：结构变更（加列）用「向后兼容 + 新增修复版本」比 down 更安全 —— down 在生产常常没法真正回滚（数据已经写进去了）。数据变更的 down 基本是骗自己。

七、向后兼容的三段式迁移（expand → migrate → contract）

目标：每一步都可以独立回滚，且任意时刻新旧代码都能跑。

阶段 动作 兼容性 回滚
① Expand（扩展） 加新列 / 新表（可空、带默认值） 新旧代码都能跑 删列（无数据损失）
② Migrate（双写迁移） 应用同时写新旧结构，回填历史数据 新旧都能跑 停双写，回到单写
③ Contract（收缩） 确认无读旧结构后，删旧列 / 旧表 只跑新代码 需从备份恢复（不可逆）

⚠️ 改列名不要直接 RENAME COLUMN 就上线。老代码还在读旧名，会立刻报 Unknown column。正确姿势是加新列 + 双写 + 回填 + 切读 + 删旧列。

⚠️ 加列带 NOT NULL 且无默认值在 COPY 算法下会重建表；即使 INSTANT 也要求默认值语义明确。能可空就先用可空。

⚠️ Contract 阶段是不可逆的。删列前必须确认：代码里没有任何 SQL 引用该列（含 ORM、视图、存储过程、BI 报表）。删列前的搜索范围往往被低估。

八、大表数据回填：分批 + 限速 + 断点续传

⚠️ 断点续传靠的是「条件可重入」：WHERE phone_new IS NULL 这种幂等条件，中断后重跑不会重复处理。别用「第 N 页」这种游标，中间插入 / 删除就错位。

⚠️ 每批之间要 sleep（如 50~200ms），否则等于对数据库做持续压测。观察 Threads_running 和主从延迟，超阈值就停。

九、主从延迟、校验与演练

关注点 现象 对策
从库延迟 重建 / 回填产生海量 binlog，从库重放慢 限速、低峰执行、临时提高 replica_parallel_workers
读写分离读旧结构 从库还没应用 DDL，读到旧表结构报错 DDL 后等从库追平再切流量；或短暂关闭读从库
校验 迁移后行数 / 内容对不上 行数比对 + checksum + 抽样
演练 生产执行时长无法预估 先在影子库跑一遍全流程，量出耗时

⚠️ 双写期间的一致性校验只能抽样 + 对账，全量校验成本极高。生产做法通常是按天对账 + 差异修复，而不是实时全量比对。

⚠️ 迁移演练不是可选项。同一张表在测试库（10 万行）和生产（1 亿行）的执行时间差几个数量级。用生产数据量的影子库跑一遍，才能估出窗口。

跨库迁移的三条路

方式 原理 适用 注意
导出导入 mysqldump / SELECT INTO OUTFILE 一次性、可停机 大表慢，需分批
binlog 同步 主从复制 / mysqlbinlog 回放 增量、近实时 需处理 DDL 与 GTID
CDC（Debezium） 解析 binlog → Kafka 不停机、可多下游 需维护位点、处理 schema 变更

⚠️ CDC 的位点（offset）管理是命门：位点丢了要么丢数据、要么重复。必须有幂等消费 + 位点持久化，不能只靠「重启从上次位置继续」。

常见坑清单

  • 生产 DDL 不显式指定 ALGORITHM / LOCK，被 MySQL 默默降级成 COPY 重建
  • 执行 DDL 前不检查长事务，MDL 排队把后续所有查询堵死
  • lock_wait_timeout 用默认值（一年），DDL 无限排队
  • 忘记 INSTANT 行版本上限 64，反复加 / 删列后突然无法 INSTANT
  • 高峰期在大表上 MODIFY COLUMN 改类型（COPY 重建）
  • innodb_online_alter_log_max_size 太小，INPLACE 跑到一半失败回滚
  • 大表直接用 ALTER TABLE 而不是 gh-ost / pt-osc
  • 用 pt-osc 却忽略触发器带来的源表写入开销
  • 大表变更不限速，从库延迟飙升拖垮读业务
  • 修改已经执行过的迁移文件，导致 checksum 校验失败
  • 生产环境指望 down / rollback 脚本真正回滚数据变更
  • 改列名直接 RENAME COLUMN，老代码立刻 Unknown column
  • 加列时带 NOT NULL 且无默认值，触发重建
  • 回填脚本不幂等，中断后重跑重复处理或错位
  • 回填不限速、无 sleep，等于对库持续压测
  • DDL 后不等从库追平就切读流量，读到旧结构
  • 迁移不做影子库演练，上线才发现耗时远超窗口
  • Contract 阶段删列前没有全量搜索引用（视图 / 存储过程 / BI）
