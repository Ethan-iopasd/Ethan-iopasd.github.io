开场：一句话结论

GraphQL 的性能问题九成来自 N+1，安全问题九成来自「字段级授权比端点级复杂」；这两个坑不解决，别上生产。

一、N+1：GraphQL 的头号性能杀手

GraphQL 的执行模型是「每个字段独立调用自己的 resolver」。父级返回一个列表，列表里每个元素再去查一次关联数据 —— 就是 N+1。

层数 每层 N 查询数
1 层关联 100 101
2 层关联 100 × 50 5001
3 层关联 100 × 50 × 20 100001

⚠️ N+1 的可怕之处在于它随查询嵌套深度指数放大。客户端多写一层嵌套，数据库压力就翻一个数量级 —— 而且客户端完全不知道自己做了什么。

二、DataLoader：批处理 + 缓存

DataLoader 把同一「执行帧」内对同一 loader 的 load() 调用收集起来，合并成一次批量查询。

选项 默认值 作用
batchLoadFn — 入参 key 数组，返回等长 value 数组的 Promise
maxBatchSize Infinity 单批最大条数，防 IN (...) 过长
cache true 是否启用 memoization 缓存
cacheKeyFn key => key 对象作 key 时的等价判定
cacheMap new Map() 自定义缓存（长生命周期时换 LRU）
batchScheduleFn 微任务调度 决定「同一帧」的边界
方法 语义
load(key) 返回单个值的 Promise
loadMany(keys) 总是 resolve，失败项以 Error 实例混在结果里
clear(key) / clearAll() 清缓存（mutation 后必须）
prime(key, value) 预填缓存

⚠️ 必须每个请求新建一个 DataLoader 实例。 实例自带缓存，跨请求复用会把 A 用户的数据喂给 B 用户 —— 这是越权，不是性能问题。用 context 承载实例即可。

⚠️ batchLoadFn 返回的数组必须与入参 key 数组顺序、长度完全一致。漏一个或错位，DataLoader 会把结果安到错误的 key 上。

⚠️ loadMany 与 Promise.all 语义不同：Promise.all 一个失败全 reject，loadMany 永远 resolve，得自己检查结果里哪些是 Error。

⚠️ 同一请求内发生 mutation 后，缓存里的旧值必须 clear，否则读到的还是变更前的数据。

三、resolver 四参数与 context

参数 典型用途
parent 从父对象取外键，避免重复查主表
args 分页、过滤条件
context 认证信息、DataLoader 实例、数据库连接、request id
info 按需裁剪 SQL 字段（配合 info.fieldNodes）、鉴权钩子、埋点

context 里该放什么：

放 不放
已解析的当前用户 / 租户 全局单例的 DataLoader
本请求的 DataLoader 集合 跨请求复用的可变状态
请求 id / trace 上下文 大对象（每个字段都会读到）
数据库连接或事务句柄 业务计算结果

⚠️ info 能拿到客户端实际选择的字段，这是 GraphQL 相对 REST 独有的优化点（只 SELECT 需要的列）。但解析 info 很啰嗦，别在每个 resolver 里手写 —— 用 graphql-parse-resolve-info 之类的工具。

四、错误处理与 null 冒泡

GraphQL 允许部分成功：能解析的字段照常返回，失败的进 errors 数组。

null 冒泡规则

非空字段出错时，null 会向上冒泡到最近的可空字段：

字段声明 出错后果
email: String 该字段变 null，兄弟字段不受影响
email: String! 冒泡到父对象，父对象变 null
user: User! 继续冒泡到 Query，data 整体变 null

⚠️ 这就是「一个非空字段出错导致整个响应 data: null」的原因。非空声明是在给错误传播划定爆炸半径，不是单纯的类型约束。

⚠️ 永远不要把内部堆栈写进 message。 用 extensions.code 给客户端可编程的错误码，细节写日志。

⚠️ 区分两类错误：请求错误（语法 / 校验失败，整个查询不执行）与字段错误（部分成功）。前者该回 4xx，后者是 200 + errors。

五、鉴权、限流与安全

字段级授权

层次 粒度 复杂度
端点级（网关 / HTTP 中间件） 整个请求 低
操作级（按 operationName） 一个 query / mutation 中
字段级 单个字段 高

⚠️ 字段级授权是 GraphQL 特有的复杂度来源：每个字段都要独立判定，且要考虑父对象的归属关系。salary 能不能看取决于「被查的人是不是我」，这个信息在 parent 里，不在 token 里。

⚠️ 别只在 resolver 里加判断。字段的存在性本身也是信息泄漏 —— 用 schema 裁剪（按角色生成不同 schema）比运行时判空更安全。

深度与复杂度限制

⚠️ 恶意客户端可以构造极深嵌套查询（friends { friends { friends ... } }）在单次请求里打垮服务。深度限制与复杂度限制是必须项，不是可选项。

⚠️ 复杂度限制要能读参数。first: 10000 和 first: 10 的成本差三个数量级，只数字段个数会低估。

其他安全项

措施 作用
关闭内省（生产） 不暴露完整数据模型
查询白名单 / 持久化查询 只允许预先登记过的查询
按复杂度限流 而不是按请求数
禁用 GET 写操作 避免被预取或缓存
超时中断 长查询强制结束，释放资源

⚠️ 按请求数限流对 GraphQL 基本无效。 一个请求可以合法地消耗掉一千个请求的资源，必须按复杂度或字段数计费。

六、GraphQL 没有 HTTP 语义

问题 后果
全部 POST 到同一 URL CDN / 浏览器缓存无法按 URL 复用
执行错误也返回 200 监控、告警、客户端重试逻辑全部失灵
无法按端点限流 只能按复杂度
无 GET 语义 无法用 ETag / Last-Modified 做条件请求

持久化查询与 APQ

把查询文本换成 hash，请求体从几 KB 降到几十字节：

收益 说明
请求体变小 移动端收益明显
白名单化 未登记的 hash 直接拒绝，天然防注入
可缓存 hash 稳定的查询可走 CDN（配合 GET）

⚠️ 用 @cacheControl 之类的指令给字段打缓存提示，是 GraphQL 里唯一能抢救 CDN 缓存的路径。别指望它能像 REST 那样天然可缓存。

⚠️ 统一返回 200 会让 APM 与告警把「服务出错」看成「正常」。必须在服务端按 errors 内容额外打点，否则线上故障是静默的。

七、订阅、上传、工具链与可观测性

subscription

传输 协议 / 库 特点
WebSocket graphql-ws 主流，双向
WebSocket（旧） subscriptions-transport-ws 已停止维护，协议与 graphql-ws 不兼容
SSE graphql-sse 单向，走普通 HTTP，代理友好

⚠️ 订阅的扩展性难题是「每个连接都占资源」。 一万个客户端就是一万条长连接，横向扩容时要处理跨实例的消息分发（通常靠 Redis Pub/Sub）。它和普通 HTTP 请求的扩容模型完全不同。

⚠️ subscriptions-transport-ws 与 graphql-ws 子协议不同，客户端和服务端混用会连不上。选一个，别两套并存。

工具链定位

服务端 语言 定位
Apollo Server JS / TS 生态最全，功能最重
GraphQL Yoga JS / TS 轻量、贴近规范、支持 SSE
gqlgen Go 强类型代码生成，性能好

可观测性

打点维度 说明
operationName 必须要求客户端提供，否则指标里全是匿名查询
完整查询文本 慢查询记录时一起存，否则无法复现
复杂度得分 与耗时一起看，找异常查询
resolver 级耗时 定位到具体字段

⚠️ 客户端不传 operationName 时，线上所有查询在监控里长得一模一样。**在网关层强制要求 operationName**，是 GraphQL 可观测性的第一前提。

常见坑清单

  • 关联字段直接查库，产生 N+1
  • 把 DataLoader 实例挂在全局，跨请求串数据
  • batchLoadFn 返回数组与入参 key 顺序不一致
  • 误以为 loadMany 会像 Promise.all 一样 reject
  • mutation 后不清 DataLoader 缓存，读到旧值
  • 用 [T!]! 却不接受「一个坏数据让整个字段失败」
  • 把内部堆栈写进 errors[].message
  • 请求错误与字段错误混用同一个状态码
  • 只在 resolver 里做字段级鉴权，忽略字段存在性泄漏
  • 不做深度限制，被深嵌套查询打垮
  • 复杂度限制不读参数，first: 10000 被当成普通查询
  • 按请求数限流，对 GraphQL 基本无效
  • 生产开着内省，暴露完整数据模型
  • 依赖 HTTP 状态码告警，忽略 GraphQL 永远返回 200
  • 指望 CDN 按 URL 缓存 GraphQL 响应
  • subscriptions-transport-ws 与 graphql-ws 混用，连不上
  • 用 GraphQL 传大文件，撑爆服务端内存
  • 不要求 operationName，监控里全是匿名查询
