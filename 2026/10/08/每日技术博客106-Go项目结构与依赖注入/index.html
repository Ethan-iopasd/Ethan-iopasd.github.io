开场：一句话结论

Go 的工程化就三句话：布局没有官方标准、依赖在 main 里显式组装、能生成的代码就别手写。

一、项目布局

官方没有强制的项目布局（只有 Organizing a Go module 的建议）。

目录 用途 说明
cmd/<app>/main.go 可执行入口 每个二进制一个子目录
internal/ 私有代码 编译期可见性保护
pkg/ 可被外部导入的库 有争议，慎用
api/ API 定义（proto / OpenAPI） 契约
configs/ / test/ 配置模板 / 集成测试

⚠️ internal/ 的可见性是编译期强制的：myapp/internal/x 只能被 myapp/... 子树导入，外部模块一律编译失败。
⚠️ pkg/ 不是官方约定，没带来任何编译器保证；**没有外部使用者时不要建 pkg/**。
⚠️ 不要过早分层。初期就铺 controller/service/repository/dto/entity 六层，改一个字段要动五个文件 —— 先按领域分，需要时再拆。
⚠️ main 包要尽量薄：只做「读配置 → 建依赖 → 启动 → 等信号关闭」，业务逻辑一律不进 main，否则无法测试。

二、包设计

原则 说明
包名是 API 的一部分 调用处写 user.New() 而不是 user.NewUserService()
小接口优先 io.Reader 只有 Read 一个方法
接口在使用方定义 Go 的隐式接口让这条成立
接受接口、返回结构体 入参用接口更灵活，返回值用具体类型更好用
避免循环 import Go 不允许循环依赖，编译直接报错

⚠️ Go 的接口是隐式的：实现方不需要（也不应该）声明 implements，因此接口应由使用方定义 —— 与 Java 显式接口最大的差异。
⚠️ util / common 是包设计的坏味道：它们会吸引所有无关代码，最终变成循环依赖的温床；按用途拆成 strutil / retry / httpx。
⚠️ 循环 import 无法用任何技巧绕过（Go 没有前向声明），只能抽公共依赖到第三个包，或把接口下沉。用 go list -deps ./... 看依赖图。

三、依赖注入与选项模式

Go 推崇「显式优于隐式」，所以推荐手工构造：所有依赖在 main 里组装。

方案 时机 开销
手工构造 编译期 零
google/wire 编译期代码生成 零运行时开销
uber/dig / fx 运行时反射 有反射与调试成本

参数膨胀时用 functional options：

⚠️ 优先手工构造。依赖数量超过几十个再考虑 wire；一上来就上 fx 属于过度设计，排查「这个依赖哪来的」会非常痛苦。
⚠️ 不要用全局变量 / 包级单例做「隐式 DI」，它让测试无法替换依赖，也让初始化顺序变成玄学。
⚠️ 选项模式解决的是「可选参数爆炸」，参数固定且少时直接传参更清晰；Option 里也别做建连接这类副作用。

四、wire / dig / fx

google/wire：编译期生成 DI 代码，无反射、无运行时开销。

维度 wire dig / fx
注入时机 编译期 运行时反射
运行时开销 无 有
调试 生成代码可读 需理解容器
生命周期钩子 需手写 fx 内建

⚠️ wire_gen.go 是生成产物，不要手改 —— 下次 wire 会覆盖，要改就改 provider 或 injector。
⚠️ wire 的报错依赖 provider 链，provider 多时拆成多个 wire.NewSet(...) 组合，否则一处缺失满屏报错。
⚠️ fx 的生命周期钩子（OnStart / OnStop）有隐式顺序，出问题先看 fx 的日志事件，别盲猜启动顺序。

五、代码生成

工具 生成什么
stringer 枚举 → 字符串
mockgen / moq 接口 → mock 实现
sqlc SQL → 类型安全的查询函数
protoc-gen-go proto → Go 结构体 / gRPC
ent schema → ORM 代码

生成代码提交进仓库还是 CI 生成？

做法 优点 缺点
提交进仓库 clone 即可编译、diff 可见 仓库变大、易忘更新
CI 生成 仓库干净、保证最新 本地需装工具、IDE 跳转差

⚠️ 生成代码必须与源同步：CI 里跑 go generate ./... && git diff --exit-code，能拦住「改了接口忘了重生成」。
⚠️ sqlc 与 gorm 取舍：sqlc 写 SQL、生成类型安全代码（可控、无隐式查询）；gorm 是运行时 ORM（开发快、易出 N+1）。
⚠️ //go:embed 的注释与变量声明之间不能有空行，也不能写在函数内；路径不能用 .. 越出包目录。

六、构建与发布

参数 作用
-X main.version=v1.2.3 编译期注入变量
-s -w 去掉符号表与调试信息（体积更小）
CGO_ENABLED=0 静态链接，便于放进 scratch 镜像
-trimpath 去掉构建机绝对路径（可复现构建）
GOOS / GOARCH 交叉编译目标平台

⚠️ -X 的变量必须是 string 类型，且写完整路径（如 main.version）；写成未导出包里的变量会静默不生效。
⚠️ -s -w 会让 panic 栈丢失部分信息，排查线上崩溃时可能不便；生产可只在最终镜像里加。
⚠️ CGO_ENABLED=0 时依赖 cgo 的库（如某些 sqlite 驱动）会编译失败，需换纯 Go 实现或保留 cgo。

七、配置、日志与优雅关闭

方案 说明
viper 多来源、多格式，但依赖重、全局状态
标准库 + 环境变量 12-factor，简单可控
envconfig / caarlos0/env 结构体标签解析

⚠️ 配置结构体要校验（Validate() 或加载后检查必填项），否则 Addr 为空会在启动时以奇怪的方式失败。
⚠️ srv.Shutdown 不会等后台 goroutine，它只等在途 HTTP 请求；业务后台任务要自己用 WaitGroup 或 errgroup 收尾。
⚠️ **日志用 log/slog 并带上 trace_id**，跨服务串联才有依据；纯文本日志在分布式下无法关联。

八、API 层与并发编排

框架 定位
net/http（1.22+） 标准库已够用，无依赖
chi 轻量，兼容 http.Handler，中间件生态好
gin / echo 功能全、上手快，自带绑定与校验

⚠️ Go 1.22 的 ServeMux 改变了路径匹配语义（方法前缀 + 通配符），升级后旧的注册写法可能冲突，注意 /path 与 /path/ 的区别。
⚠️ errgroup 默认只保留第一个返回的错误，其余 goroutine 被 ctx 取消；要收集所有错误需自行聚合。
⚠️ singleflight 只合并并发调用、不缓存结果，且返回的 v 是共享的，不要就地修改它。

九、lint 与 CI

⚠️ CI 里的 lint 版本 / 配置必须与本地一致（用同一镜像或固定版本），否则「本地过、CI 挂」。
⚠️ errcheck 会报大量历史问题，接入时先排除测试文件与生成代码，别一次性全量阻塞 CI。

常见坑清单

  • 项目初期就铺六层分层，改一个字段动五个文件
  • 建 pkg/ 但根本没有外部使用者
  • main 包里塞业务逻辑，无法测试
  • 用 util / common 当垃圾桶包名
  • 在实现方定义接口，而不是使用方
  • 想用技巧绕过循环 import（Go 不允许）
  • 用全局变量 / 包级单例做隐式依赖注入
  • 手改 wire_gen.go，被下次生成覆盖
  • 改了接口忘记重新 go generate，CI 不校验
  • //go:embed 注释与变量之间加了空行，嵌入失效
  • -X 注入的变量不是 string 或路径写错，静默不生效
  • 依赖 cgo 的库却设 CGO_ENABLED=0，编译失败
  • 配置结构体不校验，空值在启动时才暴露
  • 只调 srv.Shutdown，忘了等后台 goroutine
  • 升级到 Go 1.22 后没检查旧的路由注册写法
