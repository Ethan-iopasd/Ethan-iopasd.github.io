六 数据库设计与范式 本篇

开场：一句话结论

范式解决的是更新异常，不是「好看」；主键选型决定 B+ 树的写入局部性；金额绝不用浮点、时间统一存 UTC——这三条没有例外。

一、三范式与 BCNF

范式 要求 消除的问题
1NF 每列原子，不可再分 一行里塞数组 / 逗号串
2NF 非主键列完全依赖整个主键 联合主键下的部分依赖
3NF 非主键列不传递依赖其他非主键列 传递依赖
BCNF 每个决定因素都是候选键 主属性之间的依赖

⚠️ 范式只针对「非主键列」。主键列之间的依赖（BCNF 处理的那部分）在实际建模里极少遇到，别为了凑 BCNF 把表拆得七零八落。

拆表的收益与成本

项目 规范化的表 反范式的表
存储冗余 少 多
更新一致性 天然一致 靠应用维护
查询 需要 join 单表直出
写入 多表写 单表写

二、反范式的时机

什么时候该反：

场景 做法 一致性责任
读多写少 + 报表 预聚合 / 宽表 定时任务重算
列表页要展示作者名 冗余 author_name 作者改名时同步更新
计数类字段 冗余 comment_count 写评论时 +1（事务内）
避免多表 join 的深分页 冗余排序字段 由写入方维护

⚠️ 反范式等于把一致性责任从数据库搬到应用层。搬之前先问：这段代码以后会有人维护吗？有没有定时对账任务兜底？

⚠️ 冗余字段必须有明确的更新入口。常见事故：author_name 冗余了三张表，改名接口只更新了一张。

三、主键选型

类型 有序性 索引局部性 分布式友好 可猜测 大小
自增 BIGINT ✅ 严格递增 ✅ 最好 ❌ 需中心发号 ✅ 可枚举 8B
UUIDv4 ❌ 完全随机 ❌ 最差 ✅ ❌ 16B / 36B
雪花 ID（Snowflake） ✅ 趋势递增 ✅ 好 ✅ ⚠️ 可推算 8B
ULID ✅ 时间前缀有序 ✅ 好 ✅ ⚠️ 可推算 16B / 26B
UUIDv7 ✅ 时间前缀有序 ✅ 好 ✅ ⚠️ 16B

随机 UUID 做主键为什么伤 B+ 树：

⚠️ InnoDB 的聚簇索引按主键物理排序。随机主键导致插入位置分散，innodb_buffer_pool 里的热点页被频繁换出，写入吞吐能掉几倍。

⚠️ 自增主键可被外部枚举（/orders/1001 → /orders/1002），暴露业务量且易被爬。对外接口应另发不可猜的业务 ID，不要直接把自增主键暴露给前端。

⚠️ 用 UUID 又想要局部性，选 UUIDv7 或 ULID（时间戳在前），不要用 UUIDv4。

四、外键与字段类型

外键该不该用

维度 用外键 不用外键
数据一致性 数据库强制 应用层保证
写入性能 每次写要检查父表 无额外开销
级联删除 ON DELETE CASCADE 方便 手动删
分库分表 ❌ 跨库无法建 ✅ 不受限
在线 DDL ❌ 改父表常锁子表 ✅
高并发 父表行锁可能成热点 ✅

⚠️ 互联网场景常禁用外键，理由是：锁竞争、级联删除不可控、分库分表后根本建不了、DDL 变更被拖住。代价是一致性完全靠应用层——那就必须有定期对账任务。

⚠️ 禁用外键 ≠ 不建索引。order.user_id 这类关联列必须建普通索引，否则删父表记录时要全表扫子表。

字段类型

类型 用 不用
主键 BIGINT UNSIGNED INT（21 亿就溢出）
金额 DECIMAL(18,2) / BIGINT 存分 ❌ FLOAT / DOUBLE
定长码 CHAR(6) ——
变长 VARCHAR(n) 一律 VARCHAR(255)
大文本 TEXT，单独拆表 塞进主表导致行溢出
枚举 字典表 / TINYINT + 代码 ⚠️ ENUM（改值要 DDL）
布尔 TINYINT(1) ——

⚠️ 绝不用浮点存钱。 0.1 + 0.2 != 0.3 在 IEEE 754 下必然成立，对账差一分钱就是事故。用 DECIMAL 或整数存最小单位（分）。

⚠️ ENUM 增删值需要 ALTER TABLE，且顺序敏感（ENUM('a','b') 里 'a' 的存储值是 1，调整顺序会静默改数据）。用字典表或 TINYINT + 代码常量更稳。

⚠️ VARCHAR(255) 不是「万能长度」。MySQL 索引有 3072 字节上限（utf8mb4 下约 768 字符），超长列参与索引会被截断或建不上。

DATETIME vs TIMESTAMP

维度 DATETIME TIMESTAMP
存储范围 1000-01-01 ~ 9999-12-31 1970-01-01 ~ 2038-01-19
时区 不带，原样存 存 UTC，按会话时区转换
大小 5B（+fsp） 4B
2038 问题 ✅ 无 ❌ 有

⚠️ 2038 问题真实存在：TIMESTAMP 用 32 位存秒，2038-01-19 03:14:07 之后溢出。新表一律用 DATETIME。

⚠️ TIMESTAMP 的时区转换行为依赖 time_zone 会话变量。同一行数据，在不同时区的连接里读出来不一样——这是排查「时间差了 8 小时」的常见根因。

五、NULL、时间与软删除

NULL 的语义与陷阱

表达式 结果
NULL = NULL NULL（不是 TRUE）
NULL != NULL NULL
NULL + 1 NULL
NOT (NULL) NULL
COUNT(*) 计所有行
COUNT(col) 只计非 NULL

⚠️ 唯一索引允许多个 NULL（MySQL / PostgreSQL 都是）。想「软删除后手机号仍唯一」不能靠唯一索引加 NULL 绕过——UNIQUE(phone) 下两条 phone IS NULL 不冲突，但两条相同手机号仍冲突。

⚠️ WHERE col NOT IN (1, NULL) 返回空集，因为 x NOT IN (1, NULL) 展开成 x<>1 AND x<>NULL，后者是 NULL。NOT IN 的子查询一定要过滤 NULL。

时间与时区

做法 建议
存储 统一 UTC，列类型用 DATETIME
应用层 按用户时区展示时转换
列名 带 _at 后缀（created_at）
默认值 用应用写入，别依赖 DEFAULT CURRENT_TIMESTAMP 的服务器时区

⚠️ 混用「本地时间存 DATETIME」+「UTC 存 TIMESTAMP」是灾难。一个库里只能有一种时间口径，写进设计规范。

软删除

方案 唯一索引冲突解法
is_deleted 唯一键改成 UNIQUE(phone, is_deleted)（只能删一次）
deleted_at UNIQUE(phone, deleted_at)，NULL 不冲突，可反复删
独立归档表 删除时把行搬到 users_deleted，主表唯一键不受影响

⚠️ 软删除后**所有查询都要带 deleted_at IS NULL**，漏一处就是脏数据。用视图或 ORM 全局作用域统一过滤，别靠每个 WHERE 手写。

⚠️ 软删除的表会越来越大，唯一索引和查询都会退化。数据量大时应该真的搬到归档表，而不是无限堆在主表里。

审计字段与乐观锁

⚠️ 乐观锁用 version 自增列，不要用 updated_at 当版本号：同一秒内的两次更新时间戳相同，检测不出冲突。

六、JSON 列与建模流程

场景 用 JSON 列 该拆表
结构不定的扩展属性 ✅ ——
需要按字段查询 / 排序 ⚠️ 需生成列 + 索引 ✅
需要外键约束 ❌ ✅
数组元素要单独统计 ❌ ✅
字段会频繁整体替换 ✅ ——

⚠️ JSON 列不能直接建索引（MySQL），必须通过生成列。PostgreSQL 有 GIN 索引可以直接索引 jsonb，但语义和代价不同。

⚠️ 一旦某个 JSON 字段开始被 WHERE / ORDER BY 高频使用，它就是该拆出来的列。JSON 是给「不确定的扩展」用的，不是用来逃避建模。

逻辑模型 → 物理模型

步骤 产出
1. 梳理实体 名词 → 表
2. 梳理关系 1:1 / 1:N / M:N → 外键或中间表
3. 定属性 属性 → 列，标出必填 / 唯一
4. 定主键 自增 / 雪花 / 业务键
5. 规范化 过 1NF → 2NF → 3NF
6. 反规范化 按查询模式加冗余
7. 物理化 类型、长度、索引、分区

七、常见建模错误

错误 症状 修法
把多对多写成一对多 一个订单只能有一个商品 加中间表 order_items
把属性当实体 user 表里塞 dept_name 部门独立成表
把实体当属性 一列存 "1,2,3" 拆关联表（违反 1NF）
循环依赖 A 引用 B，B 又引用 A，插不进数据 拆出第三方表，或允许一方为 NULL
用业务键当主键 手机号变更导致级联改 用代理主键 + 业务唯一索引
一张表塞所有业务 200 列、含义混杂 按聚合根拆
无审计字段 出问题查不到谁改的 加 created_at / updated_at / updated_by
状态列用中文 status = '已完成' 用 TINYINT + 字典表

命名规范

对象 规范 例
表名 小写下划线，单数 user_order
字段名 小写下划线 created_at
布尔列 is_ / has_ 前缀 is_deleted
时间列 _at 后缀 paid_at
索引 idx_表_列 idx_order_user_id
唯一键 uk_表_列 uk_user_phone
外键 fk_表_引用表 fk_order_user

⚠️ 表名单复数、下划线还是驼峰全公司统一一种即可，怕的是同一库里混着 UserOrder 和 user_order，跨库迁移时全要改。

⚠️ 大字段（TEXT / BLOB）与热数据同表会让每行变大，InnoDB 页里能放的行数变少，扫描成本上升。冷热分离到扩展表是标准做法。

常见坑清单

  • 一列存 "1,2,3" 这种多值，违反 1NF
  • 联合主键下存在部分依赖，非主键列只依赖其中一列
  • 存在传递依赖（zip_code → city），没拆表
  • 反范式加了冗余字段，却没有明确的更新入口
  • 用随机 UUIDv4 做主键，B+ 树随机写、页分裂严重
  • 把自增主键直接暴露给前端，业务量可被枚举
  • 禁用外键后，关联列忘了建普通索引
  • 用 FLOAT / DOUBLE 存金额，对账差一分钱
  • 主键用 INT，业务量涨到 21 亿后溢出
  • VARCHAR(255) 参与索引，超出 3072 字节上限
  • 用 TIMESTAMP 存远期时间，撞 2038 问题
  • 库里混用本地时间与 UTC，时区口径不统一
  • WHERE col = NULL，永远查不到数据
  • NOT IN 子查询里带 NULL，结果恒为空集
  • 唯一索引想靠多个 NULL 绕过软删除冲突，理解错了语义
  • 软删除后查询漏写 deleted_at IS NULL
  • 乐观锁用 updated_at 当版本号，同秒更新检测不出冲突
  • JSON 列高频用于查询却不加生成列索引
  • 把多对多关系写成一对多，一个订单只能挂一个商品
  • 大字段与热数据同表，行溢出拖慢扫描
