一 Schema、类型系统与查询 本篇

开场：一句话结论

GraphQL 把「返回哪些字段」的决定权从服务端交给客户端，代价是 HTTP 缓存、错误语义、限流这些 REST 里免费的东西，全部要自己补回来。

一、GraphQL 与 REST 的本质差异

维度 REST GraphQL
端点 每个资源一个 URL 通常单一端点 POST /graphql
返回形状 服务端决定 客户端在查询里声明字段
类型 OpenAPI 可选、易漂移 schema 是运行时可校验的契约
取多个资源 多次请求或专门写聚合接口 一次请求，一张图遍历
过取 / 欠取 常见 由客户端字段集决定
HTTP 缓存 天然可用（GET + URL） 难，全是 POST 到同一 URL
错误表达 HTTP 状态码 200 + errors 数组（允许部分成功）
文件上传 multipart/form-data 核心规范不含，靠社区扩展
限流 按端点 / 请求数 要按查询复杂度
版本管理 URL 版本 /v2 无版本，靠字段演进

⚠️ 「一次请求拿多资源」是把网络往返换成了服务端的一次图遍历。解析成本上升是必然的，别把它当免费优化。

什么时候不该用 GraphQL

场景 为什么不合适
简单 CRUD 后端 schema / resolver / 工具链的引入成本换不回收益
文件上传下载 核心规范不含 multipart，扩展生态不统一
强依赖 CDN 缓存 单 URL + POST，CDN 无法按 URL 缓存
固定报表接口 客户端不控制字段集，灵活性用不上
纯内部服务间调用 gRPC 的契约与性能更合适

GraphQL 的价值只在三件事同时成立时出现：多客户端、字段需求差异大、数据是图状的。

⚠️ 反过来说，只有一个前端、接口形状固定，上 GraphQL 是纯负债。

二、类型系统：六种定义方式

关键字 用途 能否作为参数 / 输入
scalar 叶子值 可以（内置 5 个 + 自定义）
enum 枚举值 可以
type 对象，字段可有 resolver 不可以
interface 抽象，一组共享字段 不可以
union 抽象，一组对象类型的并集 不可以
input 输入对象 只能作输入

内置标量只有五个：Int、Float、String、Boolean、ID。

为什么 type 与 input 必须分开

原因 说明
语义不同 输出可带 resolver、可循环引用；输入必须是可序列化的纯数据
能力不同 输出字段可以有参数、可以返回 interface / union；输入不行
命名空间独立 允许 User（输出）与 UserInput（输入）同名共存
校验方向不同 输入需要「必填 / 默认值 / 未知字段拒绝」，输出不需要

⚠️ 试图复用同一个类型既当输出又当输入，遇到「输出字段带参数」时会立刻崩掉 —— 规范层面就不允许。

! 与列表的组合语义

写法 含义
String 可为 null
String! 不可为 null，返回 null 即触发错误
[String] 列表本身可为 null，元素可为 null
[String!] 列表可为 null，元素不可为 null
[String]! 列表不可为 null，元素可为 null
[String!]! 列表与元素都不可为 null

⚠️ [T!]! 最常用也最危险：任何一个元素为 null 都会让整个字段报错。分页接口里一个坏数据就能让整页失败。

⚠️ 自定义标量只声明「形状」，不会自动序列化。必须在代码里实现 serialize / parseValue / parseLiteral，否则它等价于 JSON —— 客户端拿不到任何类型保证。

三、三种操作与 SDL

操作 语义 字段执行顺序
query 读 可并行
mutation 写 串行（同层字段按出现顺序执行）
subscription 长连接推送 每次事件触发一次执行

⚠️ mutation 的串行保证只作用于顶层字段。嵌套层级仍可并行 —— 别以为整个 mutation 是事务。

SDL 与 code-first 是两种流派：

流派 写法 优点 缺点
SDL first 先写 .graphql，再挂 resolver schema 是纯文本，可 review、可生成客户端 与代码双份定义，易漂移
Code first 用语言构造 schema 单一来源，复用类型系统 schema 需生成才能看

四、字段参数、变量与别名

变量：生产环境唯一正确的传参方式

方式 注入风险 能否复用查询缓存 能否用 APQ
字符串拼接 高（同 SQL 注入） 否，每次文本都不同 否
变量 低，值不参与解析 是 是

⚠️ 变量声明类型必须与用法精确匹配。$id: ID! 传 null 是请求错误；$id: ID 传给 ID! 参数是校验错误 —— 两者报错位置不同，排查时别混。

别名：同一字段取多次

⚠️ 没有别名时，同一字段用不同参数取多次会在响应里互相覆盖，只保留最后一个。需要多份就必须起别名。

五、片段与指令

内联片段用在 interface / union 上，靠 __typename 区分具体类型：

指令 作用 位置
@include(if: Boolean!) false 时不包含该字段 字段 / 片段展开
@skip(if: Boolean!) true 时跳过该字段 字段 / 片段展开
@deprecated(reason:) 标记废弃，自省可见 字段定义 / 枚举值

⚠️ @include / @skip 的 if 必须是变量或字面量，不能依赖其他字段的结果 —— 条件在查询执行前就已求值。

六、分页：offset 与 cursor

方案 参数 优点 缺点
offset / limit skip / take 实现简单，可跳页 数据变动时错位、深翻页慢
cursor after / first 稳定、可无限滚动 不能跳页、需要有序唯一键

⚠️ 规范明确不建议同时使用 first 与 last，也不建议 after 与 before 混用 —— 语义冲突时行为未定义，各实现可能不同。

⚠️ cursor 必须编码「稳定排序键」，通常是 (created_at, id) 这类组合。只用 id 排序会在时间相近的数据上出现跳过或重复。

七、自省、调试与 schema 演进

工具 用途
GraphiQL 内置文档浏览器，随 schema 实时更新
Apollo Sandbox 在线 IDE，支持变量、header、历史
schema.graphql 从代码导出，作为契约进版本库

⚠️ 生产环境通常关闭内省（introspection: false），否则等于把完整数据模型送给攻击者。但注意：关掉内省也会让部分客户端代码生成器失效，需要走 CI 导出 schema 的流程。

向后兼容规则

变更 安全性
新增字段 ✅ 安全（对旧客户端不可见）
新增可空参数 ✅ 安全
新增必填参数 ❌ 破坏旧客户端
把字段改成非空 ❌ 破坏（可能返回 null）
把字段改成可空 ⚠️ 对客户端类型生成有破坏
改字段类型 ❌ 破坏
删字段 / 删枚举值 ❌ 破坏，必须先进 @deprecated
改枚举值拼写 ❌ 破坏

⚠️ 演进顺序固定：先加 @deprecated → 观察调用量归零 → 再删。直接删字段在 GraphQL 里没有版本号兜底，客户端会当场报校验错误。

与 OpenAPI 对照

维度 OpenAPI GraphQL SDL
描述对象 端点 + 方法 类型 + 字段
强制程度 文档，运行时通常不校验 运行时强制
客户端生成 生成 SDK 生成类型 / hook
演进 URL 版本 字段级 deprecated
内省 无标准机制 __schema 内建

常见坑清单

  • 把 GraphQL 用在单一客户端、固定接口形状的项目上
  • 以为「一次请求多资源」没有成本，忽略服务端解析开销
  • 用字符串拼接生成查询文本，埋下注入风险
  • 复用 type 当输入类型，遇到带参数字段直接崩
  • 到处用 [T!]!，一个 null 元素让整个字段报错
  • 自定义 scalar 只声明不实现 serialize / parseValue / parseLiteral
  • 以为 mutation 整体是事务，其实只有顶层字段串行
  • 变量声明类型与用法不匹配（ID 传给 ID!）
  • 同一字段取多份却不起别名，响应互相覆盖
  • 把 @include / @skip 的条件写成依赖字段结果
  • 分页同时用 first 与 last，行为未定义
  • cursor 只编码 id，时间相近的数据出现跳过或重复
  • 生产环境开着内省，把完整数据模型暴露出去
  • 直接删字段或枚举值，旧客户端立刻校验失败
  • 把字段改成非空却不检查历史数据里的 null
  • 以为 GraphQL 自带 HTTP 缓存，忽略全是 POST 的事实
