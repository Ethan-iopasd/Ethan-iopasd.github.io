开场：一句话结论

多级缓存的价值是用「本地内存换一次网络往返」，代价是「多实例各存一份」—— 所以架构的核心不是加缓存，而是控制不一致窗口。

一、分层的意义：为什么要本地缓存

层级 延迟量级 容量 一致性 成本
本地缓存 微秒级 小（受进程内存限制） 弱（各实例独立） 无网络开销
Redis 毫秒级 大 强（集中一份） 一次网络往返
数据库 毫秒~百毫秒 最大 权威 磁盘 IO

⚠️ 本地缓存省的是「一次网络往返 + 序列化」。对单次请求，微秒 vs 毫秒差 10~100 倍；在高 QPS 下，这直接决定 Redis 是否会成为瓶颈。但它的代价是多实例数据不一致，见第三节。

二、本地缓存选型与淘汰算法

方案 语言 淘汰算法 特点
Caffeine Java W-TinyLFU 高命中率 + 高并发，事实标准
Guava Cache Java LRU 老牌，性能不如 Caffeine
sync.Map Go 无（手动） 只提供并发安全，不淘汰
Ristretto Go TinyLFU Go 生态的高命中率选择
淘汰算法 思路 短板
LRU 淘汰最久未使用 突发冷数据会挤掉热数据
LFU 淘汰访问频率最低 历史高频数据「霸占」位置，难适应变化
W-TinyLFU 窗口缓存 + 频率准入 实现复杂

W-TinyLFU 为什么命中率更高：它把缓存分成 Window Cache（窗口区，吸收新数据） 和 Main Cache（主区，用 SLRU 维护热数据），并用一个频率草图（Count-Min Sketch）做准入判断 —— 新数据要进主区，必须访问频率高于被淘汰的候选，否则直接拒之门外。

⚠️ LRU 的痛点是「扫描型突发流量」：一次全表扫描会把缓存里的热数据全部冲掉。W-TinyLFU 用频率准入挡住这类一次性访问，这是它命中率高的根本原因。

⚠️ 本地缓存必须设上限 + 过期。无上限的 map 就是内存泄漏。容量（maximumSize / maximumWeight）+ TTL 双保险。

三、本地缓存的头号问题：多实例不一致

解法 机制 一致性 代价
短 TTL 靠过期自愈 弱（窗口 = TTL） 简单，但 TTL 内可能读到旧值
广播失效 Redis Pub/Sub / MQ 通知各实例删除 较好 需处理消息丢失
版本号 缓存值带版本，读时比对 较好 需额外查询版本
集中式开关 关键数据只用 Redis 强 放弃本地缓存收益

⚠️ Redis Pub/Sub 不可靠：无持久化、断连即丢消息、没有 ACK。订阅端在重启 / 网络抖动期间的消息会永久丢失，本地缓存就再也删不掉了。要可靠就用 Redis Stream（可 ACK + 消费组）或 MQ。

⚠️ 广播失效不能保证「一定删掉」。最坏情况仍需 TTL 兜底。生产做法：短 TTL（如 5~30s）+ 广播失效，双保险。

四、缓存更新模式对照

模式 读路径 写路径 一致性 复杂度 适用
Cache-Aside 先查缓存，miss 查 DB 回填 更新 DB，删除缓存 最终一致 低 绝大多数场景
Read-Through 缓存层代理读 由缓存层负责加载 最终一致 中 需要统一封装
Write-Through 同上 写缓存 + 写 DB（同步） 较强 中 写少、要求较高
Write-Behind 同上 只写缓存，异步刷 DB 弱（可能丢） 高 写多、可容忍丢

⚠️ 「先更新 DB 再删缓存」也不是绝对安全，只是把出错窗口压得更小（需要读请求恰好慢于写请求且回填发生在删缓存之后）。缓存与 DB 本质无法做到强一致，只能把不一致窗口压到极小。

延迟双删：更新 DB 前后各删一次缓存（第二次延迟几百毫秒），进一步缩小窗口。

⚠️ 延迟双删只是降低概率，不是消除。延迟多久取决于主从同步 + 读请求耗时，没有普适值。它换来的是「简单」，不是「正确」。

五、穿透 / 击穿 / 雪崩的架构级解法

问题 现象 架构解法
穿透 查不存在的 key，每次都打 DB 布隆过滤器前置；空值缓存（短 TTL）
击穿 单个热 key 过期，瞬间全打到 DB 互斥锁重建；逻辑过期
雪崩 大量 key 同时过期，DB 被压垮 TTL 加随机抖动；多级缓存；降级兜底

逻辑过期（解决击穿且不阻塞读）：缓存永不过期，值里额外存一个「逻辑过期时间」。

方案 是否阻塞读 复杂度 一致性
互斥锁重建 阻塞（拿锁的请求等） 中 高
逻辑过期 不阻塞（返回旧值） 高 短暂旧值

⚠️ 逻辑过期换来的是「永远不阻塞读」，代价是刷新窗口内读到旧值，且实现复杂（需异步线程 / 任务队列）。对延迟极敏感的热点数据值得用它。

⚠️ TTL 必须加随机抖动。统一设 3600s 会让大批 key 在同一秒集中过期 → 自造雪崩。**TTL = 基础值 + random(0, 基础值 × 10%)。**

⚠️ 多级缓存天然抗雪崩：Redis 挂了，本地缓存还能扛一段时间。这是分层架构除了降延迟之外的第二个价值 —— 隔离故障。

⚠️ 降级要有兜底数据。缓存全挂时，返回旧值 / 默认值 / 限流，都比直接把请求全放给 DB 强。降级的目的是「保住 DB」，不是「保住功能」。

六、热点数据：本地缓存是最优解

手段 说明 局限
本地缓存 热 key 留在进程内，不打 Redis 多实例一致性弱
key 分片打散 hot_key:{0..N} 分散到多节点 读要聚合 N 份
读写分离 热 key 走多个副本 需客户端支持

⚠️ CLUSTER 模式下热 key 无法靠分片解决。同一个 key 只能落在一个分片（hash slot 固定），分片再多也没用。要扛热 key，靠本地缓存或读副本，不是加节点。

⚠️ 热 key 打散成 hot_key:0..N 后，读要合并 N 份结果。这增加了客户端复杂度和网络往返，只在单 key 确实打爆单分片时才用。

七、缓存一致性：能接受多大窗口

场景 可接受的不一致 方案
商品列表、推荐 秒~分钟级 短 TTL + 异步刷新
用户资料 秒级 Cache-Aside + 删缓存
账户余额、库存 不允许 别用缓存，或强一致存储

⚠️ 强一致场景就别加缓存。加缓存本质是「用一致性换性能」。如果业务不能容忍任何旧值，缓存不是解法，是负债。

⚠️ 最终一致必须配「对账」。缓存与 DB 的偏差不会自己消失，要靠定时对账 + 差异修复。没有对账的最终一致，等于放任脏数据。

八、缓存与事务：别把缓存操作塞进事务

⚠️ 事务未提交就读缓存有风险：事务里更新了 DB，还没 commit，缓存已经被删/更新，其他请求读到的是「未提交的中间态」。

⚠️ 缓存操作不该放在事务里。正确顺序是：先提交 DB 事务，再删缓存。放在事务内，一旦事务回滚，缓存已经被改，直接不一致。

⚠️ 删缓存失败要有补偿。删除抛异常 / 网络超时 → 缓存长期是旧值。用重试 + 短 TTL 兜底。

九、预热、可观测性与容量规划

缓存预热：发布 / 扩容后缓存是空的，冷启动会把请求全打到 DB。

手段 说明
提前预热 发布前把热点数据刷进缓存
分批放量 新实例逐步接入流量，边服务边回填
本地缓存持久化 进程重启后恢复本地缓存（部分库支持）
指标 含义 预警
keyspace_hits / (hits+misses) 命中率 下降 = 最早的故障信号
evicted_keys 被淘汰 key 数 持续增长 = 内存不够
大 key / 热 key 单 key 过大 / 单 key 过热 阻塞、倾斜
内存使用率 used_memory / maxmemory > 70%~80%

⚠️ 命中率下降是最早的故障信号。它往往先于延迟上升、DB 压力上升出现。盯住命中率，比盯 QPS 更早发现问题。

⚠️ maxmemory 要留 20%~30% 余量。Redis 除了数据还有：复制缓冲区、客户端缓冲区、AOF/RDB 重写时的额外内存、碎片。打满 maxmemory 会导致频繁淘汰甚至 OOM。

⚠️ 容量按「热数据量」估算，不是按全量数据。全量 1TB 但热数据 50GB，缓存 50~100GB 就够。按全量买内存是最大的浪费。

十、什么时候不该加缓存

场景 原因
写多读少 缓存收益低，失效成本高
数据量小 DB 直接扛得住，加缓存纯增复杂度
强一致要求 缓存本质是弱一致，加了就是负债
访问分布均匀、无热点 缓存命中率低，性价比差
缓存本身成了故障源 每次事故都因缓存，考虑去掉

⚠️ 缓存会引入新的故障模式：穿透、击穿、雪崩、数据不一致、热 key、大 key、缓存与 DB 双写。加缓存前先问：不加会怎样？答案往往是「加个索引就够了」。

⚠️ 如果每次故障都因缓存而起，那就该考虑去掉它。缓存是性能工具，不是架构必需品。复杂度本身也是成本。

常见坑清单

  • 本地缓存无上限、无 TTL，等于内存泄漏
  • 用 Redis Pub/Sub 做失效广播，断连消息永久丢失
  • 多实例本地缓存更新后不通知其他实例，读到随机旧值
  • 采用「先删缓存再更新 DB」，并发下产生长期脏数据
  • 以为「先更新 DB 再删缓存」就是强一致
  • 盲目上延迟双删，延迟时间没有依据
  • TTL 不设随机抖动，大批 key 同时过期自造雪崩
  • 击穿场景用互斥锁，读请求被阻塞拖慢整体延迟
  • 降级没有兜底数据，缓存挂了直接打爆 DB
  • CLUSTER 下想靠加节点解决单个热 key
  • 把缓存操作放进 DB 事务里，事务回滚后缓存已脏
  • 事务未提交就读缓存，读到中间态
  • 删缓存失败没有补偿，缓存长期是旧值
  • 发布后不预热，冷启动把请求全打到 DB
  • 不监控命中率，错过最早的故障信号
  • maxmemory 打满，没有留复制 / 客户端缓冲余量
  • 按全量数据量而不是热数据量规划缓存容量
  • 强一致场景硬加缓存，用一致性换性能却无法承受
  • 写多读少的场景也加缓存，收益低复杂度高
