四 monorepo 与大仓库管理 本篇

开场：一句话结论

monorepo 的价值是「原子提交 + 统一依赖」，代价是「仓库膨胀 + CI 全量构建 + 没有目录级权限」。 前者靠 sparse-checkout / partial clone / 受影响分析抵消，后者（Git 没有目录级权限）无解，只能靠流程和 CODEOWNERS 兜。

一、monorepo vs polyrepo

维度 monorepo polyrepo（多仓）
依赖管理 统一版本，改一处全仓可见 各自锁版本，跨仓升级难
原子提交 ✅ 跨包改动一次提交 ❌ 要发多个 PR 协调
权限粒度 ❌ Git 没有目录级权限 ✅ 按仓授权
CI 复杂度 高，需受影响分析 低，但配置重复
构建缓存 可跨包共享 难共享
版本发布 集中管理（changesets 等） 各仓独立
团队自治 弱，规范要统一 强
仓库体积 持续膨胀 分散

⚠️ Git 没有目录级读权限。把 A 团队和 B 团队的代码放进同一仓，A 就能 clone 到 B 的全部历史 —— 这一点在 monorepo 立项时必须先说清楚，靠 CODEOWNERS 只能管「谁能改」，管不了「谁能看」。

⚠️ monorepo 的原子提交是优势也是陷阱：一次提交动 5 个包，回滚时要么全回、要么手动挑，无法「只回滚 A 包」。

二、大仓库的性能问题

症状 原因 缓解
git status 慢 每次扫描全部文件 core.fsmonitor / core.untrackedCache
git log 慢 提交历史巨大 --filter 部分克隆、浅克隆
clone 慢 对象库巨大（blob 全量下载） partial clone
磁盘占用大 历史里的 blob 永不消失 仓库瘦身 / LFS

部分克隆与浅克隆

方式 省什么 代价
--filter=blob:none 全部历史文件内容 部分操作触发按需下载
--filter=tree:0 tree 也不下载 更激进，操作更慢
--depth 1 历史提交 不能正常 fetch 历史、bisect 受限

⚠️ 浅克隆（--depth）的历史是残缺的：git log 到不了更早的提交，git bisect 无法在缺失区间工作，后续 fetch 要 --unshallow 才能补全。CI 里图快用它可以，本地开发别用。

⚠️ partial clone 需要服务端支持 uploadpack.allowFilter。GitHub / GitLab 支持；自建 Git 服务器没开这个配置时 --filter 会被忽略（静默退化为全量克隆）。

三、sparse-checkout 与 LFS

模式 说明
--cone 只按目录（含父目录）匹配，性能好、规则直观
非 cone 用 gitignore 风格 pattern，灵活但易错、慢

⚠️ sparse-checkout 只是不把文件写进工作区，对象仍在本地对象库里。想真正减小 clone 体积必须配合 --filter=blob:none，两者是互补不是替代。

⚠️ sparse-checkout 下被排除的目录里的文件仍存在于索引/历史中，git grep（默认只搜工作区）搜不到它们。要搜历史用 git grep <pat> <rev>。

Git LFS

⚠️ LFS 的代价：需要服务端支持（GitHub 有配额，自建要装 git-lfs）、clone 时默认拉取全部 LFS 对象（可以 GIT_LFS_SKIP_SMUDGE=1 跳过）、不是所有平台都支持。已经提交进历史的大文件，再 git lfs track 不会自动搬走 —— 必须重写历史。

四、历史重写与仓库瘦身

工具 状态 特点
git filter-branch ⚠️ 官方不推荐 极慢，易出错
git filter-repo ✅ 推荐 快、安全，需单独安装
BFG Repo-Cleaner 可用 Java 工具，删大文件直观

⚠️ 重写历史会改变所有后续提交的 SHA，所有人必须重新 clone（git pull 会冲突）。所有基于旧 SHA 的 PR / 分支 / CI 记录全部失效。必须提前通知全团队，选在无人在推代码的窗口执行。

⚠️ 删除文件不会让历史里的 blob 消失。git rm big.iso 后仓库体积不变，因为旧提交仍引用它。必须重写历史 + git gc 才能释放。

⚠️ git gc --prune=now 会删掉所有 reflog 指向的对象，误删提交无法再靠 reflog 找回。执行前确认没有需要保留的悬空提交。

五、构建工具与受影响分析

工具 定位 语言生态
Turborepo JS/TS monorepo，任务编排 + 远程缓存 Node
Nx 全功能，依赖图 + affected + 插件 多语言
Bazel 大厂级，强 hermetic 构建 多语言
Pants Python 优先，增量构建 多语言

核心思想：构建工具维护一张任务图 / 依赖图，只跑「受改动影响的包」（affected），并把结果推到远程缓存供 CI 和同事复用。

⚠️ affected 分析依赖正确的依赖图。package.json 里漏声明依赖（用了但没写）会让工具误判「不受影响」，从而跳过该构建 —— 表现为「本地能过、CI 跳过导致线上缺文件」。

⚠️ 远程缓存要求缓存 key 稳定（输入文件、环境变量、依赖版本都参与 hash）。把随机数、时间戳塞进构建输入会让缓存永不命中。

六、CI 优化与版本管理

优化手段 作用
paths / paths-ignore 只在对改动路径相关时触发
并行分片（matrix） 把测试拆到多个 job
缓存 node_modules / 构建产物 省去重复安装 / 编译
远程构建缓存 跨机器复用任务结果
affected 过滤 避免全量构建

⚠️ paths 过滤配合「必须通过的检查」时，可能出现「PR 没触发 CI 但分支保护要求检查通过 → 卡住」。要么给过滤条件配一个总是运行的占位 job，要么接受这种边界。

⚠️ 缓存 node_modules 要按 lockfile 的 hash 做 key，否则依赖更新后命中旧缓存，装出过时依赖。

发布与版本

模式 说明 工具思路
固定版本（fixed） 所有包同一版本号 Lerna fixed 模式
独立版本（independent） 每个包各自版本 changesets / Lerna independent
变更日志 从提交 / changeset 自动生成 changesets、semantic-release
依赖升级 机器人提 PR Renovate / Dependabot

⚠️ 独立版本下，一个包升到 2.0 而依赖它的包没跟着升，可能出现「依赖范围允许但行为不兼容」。跨包依赖建议用 workspace:* 协议由工具统一改写。

七、子模块、子树与 worktree

方案 适用 经典坑
git submodule 引用外部仓、需固定 commit **clone 后忘 --recursive**、detached HEAD
git subtree 把外部仓并进主仓 历史膨胀，push 回上游要额外操作
git worktree 同一仓多分支并行检出 同一分支不能在两处同时检出

⚠️ 子模块最经典的坑是「clone 后忘了 --recursive」，目录是空的，npm install 或构建直接失败。另一个是子模块默认处于 detached HEAD，在里面提交的改动不属于任何分支，容易丢。

⚠️ git worktree 里同一个分支不能在两个工作区同时检出（fatal: 'x' is already checked out）。共享的是同一个 .git 对象库，删除工作区记得 git worktree remove。

目录级评审与分支策略

⚠️ CODEOWNERS 只影响「评审人」，不影响读写权限。Git 层面任何人都能 clone 全仓。真要目录级权限只能拆仓或用支持路径级 ACL 的平台能力。

⚠️ monorepo 下长期存在的 feature 分支会持续与主干冲突（全仓都在动）。trunk-based + 特性开关更适合：短分支频繁合入主干，未完成功能靠开关关闭。

⚠️ pre-commit 钩子在 monorepo 里对全仓文件跑 lint 会非常慢（几十万文件）。配置成只对暂存 / 改动文件跑（lint-staged 的思路），否则每次提交等几十秒，最后所有人加 --no-verify 绕过。

常见坑清单

  • 以为 monorepo 能按目录限制访问权限（Git 不支持）
  • git rm 大文件后仓库体积不变，以为清掉了
  • 用 git filter-branch 重写历史（应改用 filter-repo）
  • 重写历史前没通知团队，导致所有人的 PR 失效
  • git gc --prune=now 前没确认，丢掉了靠 reflog 找回的提交
  • 本地开发用浅克隆，git bisect / git log 受限
  • 部分克隆用在没开 uploadpack.allowFilter 的服务器上，静默退化
  • 用 sparse-checkout 却没配 partial clone，clone 体积没减小
  • 已提交进历史的大文件只 lfs track，没重写历史
  • LFS 依赖服务端支持，换了平台才发现不支持
  • package.json 漏声明依赖，affected 误判导致 CI 跳过构建
  • 构建输入含时间戳 / 随机数，远程缓存永不命中
  • 缓存 node_modules 没用 lockfile hash 做 key
  • paths 过滤与分支保护必需检查冲突，PR 卡住
  • 子模块 clone 忘了 --recursive，目录是空的
  • 在子模块的 detached HEAD 上提交，改动丢失
  • 同一分支在两个 worktree 同时检出
  • pre-commit 对全仓跑 lint，慢到所有人 --no-verify
