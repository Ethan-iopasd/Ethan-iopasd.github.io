一 Protocol Buffers 与 gRPC 基础 本篇

开场：一句话结论

gRPC = HTTP/2 + Protocol Buffers + 代码生成，用 .proto 定义契约，protoc 生成强类型 stub，二进制编码比 JSON 小 3~10 倍，但浏览器不能直接调。

一、gRPC vs REST vs GraphQL

维度 gRPC REST/JSON GraphQL
传输协议 HTTP/2（必须） HTTP/1.1 或 2 HTTP/1.1 或 2
序列化 Protobuf（二进制） JSON（文本） JSON（文本）
IDL .proto（强制） OpenAPI（可选） SDL（强制）
流式 双向流原生支持 一般靠 SSE/WebSocket Subscription
浏览器支持 ❌ 需 grpc-web + 代理 ✅ 原生 ✅ 原生
可读性 ❌ 需工具解码 ✅ 肉眼可读 ✅
性能 最高（体积小、多路复用） 中 中
代码生成 一等公民 靠工具 靠工具
典型场景 内部微服务、移动端 SDK 对外 API 前端灵活取数

⚠️ gRPC 不是「更好的 REST」。它面向服务间调用：契约先行、强类型、高性能。对外给第三方或浏览器的公开 API，REST 往往更省事。

二、HTTP/2 是 gRPC 的底座

gRPC 依赖 HTTP/2 的三个特性，缺一不可：

特性 作用
多路复用（multiplexing） 一条 TCP 连接上并发跑多个请求，无队头阻塞
头部压缩（HPACK） 头部表 + 哈夫曼编码，重复的 header 只发索引
流控（flow control） 基于 WINDOW_UPDATE 的窗口，防止接收方被压垮

⚠️ HPACK 有动态表状态。长连接上大量随机 header（比如每个请求塞唯一 trace id）会撑爆动态表，反而降低压缩率。

三、Protocol Buffers 基础语法

语法 语义 注意
repeated 有序列表 proto3 默认打包（packed）编码
map<K,V> 无序字典 不能 repeated，不能做 map 的 value
oneof 联合类型，互斥 设置新字段会清空旧字段
optional 显式存在性 3.15+ 回归，底层是 synthetic oneof
reserved 保留号/名 防止旧数据被新字段误解析

⚠️ 字段编号 1~15 用一个字节编码（tag 只占 1 字节），16~2047 用两个字节。高频字段用小编号，能省字节。

⚠️ **proto3 移除了 required**。官方理由：required 破坏向前/向后兼容 —— 你永远不能安全地增删一个 required 字段。

四、默认值不序列化：proto3 的存在性陷阱

proto3（无 optional）无法区分「未设置」和「零值」：

需求 解法
区分「未设置」和 0 / "" / false 加 optional 关键字（3.15+）
用官方 wrapper google.protobuf.Int32Value 等
老代码里判断 服务端按业务约定处理，别依赖 hasField

⚠️ optional 和 wrapper 会让 hasXxx() 生效，但代价是每个字段多一次存在性判断。别给所有字段无脑加 optional。

五、well-known types

类型 用途 对应
google.protobuf.Timestamp 时间点 秒 + 纳秒，UTC
google.protobuf.Duration 时间段 秒 + 纳秒
google.protobuf.Any 任意消息 带 type_url，需手动 unpack
google.protobuf.Struct 动态 JSON 对象 键值树
google.protobuf.Empty 空消息 无参/无返回

⚠️ Any 是兼容性逃逸口。它把类型检查推到运行时，滥用等于放弃 Protobuf 的强类型优势。

六、向后 / 向前兼容规则

操作 是否安全 说明
新增字段 ✅ 旧代码忽略未知字段
删除字段 ⚠️ 要 reserved 否则新代码可能复用旧号
改字段编号 ❌ 破坏 wire 兼容
改字段类型（不兼容的） ❌ 如 int32 → string
int32 → int64 ⚠️ 变长整数编码兼容，但小心负数
新增枚举值 ✅ 旧代码落到 default
把单字段改成 repeated ❌ 不兼容

⚠️ 永远不要复用已经删除的字段号。旧数据里的 9 号字段会被新定义按新类型解析，产生静默数据损坏。

⚠️ 枚举的第一个值必须是 0，且建议命名为 XXX_UNSPECIFIED，因为 proto3 的默认值就是 0。

七、编码原理：为什么比 JSON 小

Protobuf 用 TLV（Tag-Length-Value）结构，tag = (字段号 << 3) | wire_type。

wire_type 含义 用于
0 Varint int32/int64/bool/enum
1 64-bit fixed64/double
2 Length-delimited string/bytes/嵌套消息
5 32-bit fixed32/float

Varint：每字节最高位是续位标志，7 位存数据。小数字占 1 字节，大数字占多字节。

Zigzag：负数直接 varint 会占 10 字节（补码全是 1），sint32/sint64 用 zigzag 把负数映射成小正整数：

⚠️ 负数用 int32 会膨胀到 10 字节。确定会传负数就用 sint32 / sint64。

八、四种 RPC 类型

类型 客户端发 服务端回 典型场景
Unary 1 1 普通查询
Server streaming 1 N 大结果集、订阅、进度推送
Client streaming N 1 批量上传、聚合计算
Bidirectional N N 实时聊天、双向同步

⚠️ 流式不等于「实时」。它是 HTTP/2 的 DATA 帧序列，服务端推完就结束；要做长连接推送得靠双向流自己维持。

九、代码生成流程

工具 优势
protoc 官方，最小依赖
buf lint / 破坏性检测 / 依赖管理 / 插件配置
protoc-gen-go Go 消息代码
protoc-gen-go-grpc Go 服务 stub

⚠️ buf breaking 是 CI 里最值钱的一步。它能自动拦住「改字段号」「删字段不 reserved」这类破坏兼容的提交。

十、命名规范与包名

对象 规范 示例
包名 小写 + 点分层 + 版本 user.v1
消息 PascalCase GetUserRequest
字段 snake_case user_id
枚举值 大写下划线 + 前缀 STATUS_ACTIVE
服务 PascalCase UserService
方法 PascalCase GetUser

⚠️ 包名带版本号（user.v1）是官方推荐，它让不兼容的新版本可以并存，是 API 演进的关键手段。

十一、状态码与错误详情

gRPC 状态码有 17 个（0~16），与 HTTP 没有一一对应，只有约定俗成的映射：

gRPC 码 近似 HTTP 语义
OK 0 200 成功
CANCELLED 1 499 调用方取消
UNKNOWN 2 500 未知错误
INVALID_ARGUMENT 3 400 参数非法
DEADLINE_EXCEEDED 4 504 超时
NOT_FOUND 5 404 不存在
ALREADY_EXISTS 6 409 已存在
PERMISSION_DENIED 7 403 无权限
RESOURCE_EXHAUSTED 8 429 配额/资源耗尽
FAILED_PRECONDITION 9 400 状态不符
ABORTED 10 409 并发冲突
OUT_OF_RANGE 11 400 越界
UNIMPLEMENTED 12 501 未实现
INTERNAL 13 500 内部错误
UNAVAILABLE 14 503 暂时不可用，可重试
DATA_LOSS 15 500 数据损坏
UNAUTHENTICATED 16 401 未认证

其中这 7 个只由业务代码产生，库不会自动生成：INVALID_ARGUMENT / NOT_FOUND / ALREADY_EXISTS / FAILED_PRECONDITION / ABORTED / OUT_OF_RANGE / DATA_LOSS。

带详情的错误用 google.rpc.Status：

⚠️ 别把业务错误码塞进 message 字符串。用 ErrorInfo.reason 这类结构化字段，客户端才能编程式判断。

⚠️ UNAVAILABLE 与 DEADLINE_EXCEEDED 才是该重试的。INVALID_ARGUMENT 重试一万次也是同样结果，只会放大故障。

⚠️ 错误详情走的是 trailer，不是 message。自定义错误详情需要 HTTP/2 的 trailer 支持，某些代理会把它吃掉。

常见坑清单

  • 在 proto3 里用「值为 0 / 空串」判断字段是否被设置
  • 删除字段后没写 reserved，字段号被新字段复用
  • 修改已有字段的编号或类型
  • 给负数字段用 int32 而不是 sint32，编码膨胀到 10 字节
  • 高频字段用了 16 以上的编号，白白多占一个字节
  • 枚举第一个值不是 0，或没命名为 XXX_UNSPECIFIED
  • 滥用 google.protobuf.Any，把类型检查推迟到运行时
  • 包名不带版本号（user 而不是 user.v1），无法平滑演进
  • 用 repeated 表达本应是集合的语义，客户端不得不手动去重
  • 以为流式 RPC 等于 WebSocket 式的长连接推送
  • 把业务错误码拼进 message 字符串，客户端无法结构化解析
  • 对 INVALID_ARGUMENT 这类错误做自动重试
  • CI 里没跑 buf breaking，破坏兼容的改动直接进主干
  • 浏览器直接调 gRPC 接口（必须走 grpc-web + 代理）
  • 用 gRPC 对外提供公开 API，却要求调用方装 protoc 工具链
