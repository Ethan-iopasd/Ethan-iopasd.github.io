开场：一句话结论

grpc_pass 只差一个 http2 on 和一个 grpc:// scheme 就能跑通，但流式调用的超时、metadata 大小写、以及 Nginx 对双向流的限制，才是真正会踩的点。

一、grpc_pass 代理 gRPC

ngx_http_grpc_module（1.13.10+）依赖 ngx_http_v2_module，必须走 HTTP/2。

项 值
明文 gRPC grpc_pass grpc://host:port
TLS gRPC grpc_pass grpcs://host:port
Unix socket grpc_pass unix:/tmp/grpc.socket
上游组 支持 upstream 块，默认轮询
变量 1.17.8 起地址可含变量
trailer 从上游收到的 trailer 原样透传，不解释

⚠️ 不写 scheme 时按明文处理，接 TLS 上游必须显式 grpcs://，否则握手直接失败。

⚠️ 自 1.25.1 起 listen 443 ssl http2; 里的 http2 参数已废弃，要改成独立的 http2 on;。

⚠️ ngx_http_grpc_module 不解析 trailer，只转发。链路中任何一环缓冲了 trailer，grpc-status 就会丢失。

metadata 与 grpc_set_header

指令 默认值
grpc_set_header Content-Length $content_length
grpc_hide_header 默认隐藏 Date、Server、X-Accel-*

⚠️ HTTP/2 要求 header 名全小写，gRPC metadata 的 key 也必须小写，自定义 key 混用大小写时最容易出现对不上。

⚠️ grpc_set_header 是层级继承的：只要当前层级写了任意一条，上一层的全部不继承。

二、超时、缓冲与重试

指令 默认 语义
grpc_read_timeout 60s 读上游响应的两次连续读之间的超时
grpc_send_timeout 60s 写上游请求的两次连续写之间的超时
grpc_buffer_size 4k|8k 读响应的缓冲区大小
grpc_socket_keepalive off 对上游连接开 SO_KEEPALIVE

⚠️ grpc_read_timeout 不是整个请求的总时长，而是「两次读之间」的间隔。流式接口只要持续有数据就不会超时。

⚠️ 反过来：服务端流 / 双向流在两次消息之间超过该值就会被断开。流式接口必须单独放宽到业务最大空闲时间。

重试

参数 默认是否算失败
error / timeout / denied / invalid_header 始终算（即使没写）
http_500 / http_502 / http_503 / http_504 / http_429 只在显式写上时算
http_403 / http_404 永不算失败
non_idempotent 允许重试非幂等方法，默认关闭

⚠️ 只有在尚未向客户端发送任何内容时才能切到下一台上游。流式响应一旦开始推送，重试就不可能了。

⚠️ non_idempotent 默认是关的，别随手打开。gRPC 的 POST 语义上非幂等，重试等于重放副作用。

三、gRPC-Web、HTTP/2 与 SNI 分流

浏览器无法直接发 HTTP/2 gRPC（不能设置自定义帧、不能读 trailer），只能走 gRPC-Web。

⚠️ Nginx 官方没有 gRPC-Web 模块。 grpc_pass 代理的是原生 gRPC，不能直接给浏览器用。要在 Nginx 上做 gRPC-Web，必须引入第三方模块（需自行编译）或直接换 Envoy。

同一端口按 SNI / ALPN 分流

ssl_preread（stream 模块，1.11.5+）可以不解密就读出 SNI 与 ALPN：

变量 内容
$ssl_preread_server_name SNI 主机名
$ssl_preread_alpn_protocols 客户端 ALPN 列表，逗号分隔

⚠️ ALPN 值是逗号分隔列表，匹配要用正则边界（\bh2\b）；用 = h2 等值比较会漏掉 h2,http/1.1。

⚠️ ssl_preread 只在 stream（四层） 可用，写在 http 块里会直接启动失败。

⚠️ 用 ssl_preread 分流后 TLS 在后端终止，四层这一跳看不到任何 HTTP 信息，无法做基于路径的路由。

四、Lua：执行阶段与顺序

OpenResty 把 LuaJIT 嵌进 Nginx，按 Nginx 的处理阶段挂载。

指令 阶段 典型用途 cosocket
init_by_lua* master 启动 加载配置、预热 ❌
init_worker_by_lua* 每个 worker 启动 定时器、健康检查 ❌
set_by_lua* rewrite 前 计算变量 ❌
rewrite_by_lua* rewrite URL 改写 ✅
access_by_lua* access 鉴权、限流 ✅
content_by_lua* content 直接生成响应 ✅
balancer_by_lua* 选上游 动态负载均衡 受限
header_filter_by_lua* 响应头 改响应头 ❌
body_filter_by_lua* 响应体 改 / 截断响应体 ❌
log_by_lua* 日志 异步上报 ❌

⚠️ ngx.exit 是终止请求，不是「返回一个值」。 阶段写错会导致后面的阶段继续执行。

⚠️ cosocket 在 set_by_lua / init_by_lua / init_worker_by_lua / header_filter_by_lua / body_filter_by_lua / log_by_lua 被禁用，在这些阶段发起网络请求直接报错。

⚠️ 虽然 rewrite_by_lua 里 cosocket 可用，但任何真正的阻塞调用（同步文件 IO、外部命令）都会卡住整个 worker 的事件循环，把所有并发请求一起拖死。

⚠️ Lua 里未捕获的错误会返回 500。 所有可能失败的外部调用（Redis、HTTP、JSON 解析）都必须 pcall 兜底。

五、Lua 做鉴权、限流与动态路由

要点 说明
lua_shared_dict 所有 worker 共享的内存区，声明在 http 块
incr 的 init / init_ttl 一次调用完成「不存在则初始化为 0」并设过期
resty.lock 需要「读-改-写」原子性时加锁，避免并发丢更新
ngx.shared.DICT:get/set/incr 单个操作原子，多条组合起来不是

⚠️ lua_shared_dict 是单机共享的。多台 Nginx 之间不共享，全局精确限流仍要靠 Redis。

⚠️ incr 的 init_ttl 只在 key 首次创建时生效。不要用 set + expire 两步，中间崩溃会让 key 永不过期，把用户永久限死。

动态负载均衡

⚠️ balancer_by_lua 里不能用 cosocket 做同步服务发现调用，节点列表要在 init_worker_by_lua 里预热好放进共享内存。

⚠️ balancer_by_lua 每次重试都会执行一次，里面的副作用（写日志、计数）会被重复执行，必须做幂等。

灰度与条件路由

⚠️ split_clients 按哈希切分，同一客户端稳定命中同一组，但它不知道「用户」是谁 —— 换 IP 或换 UA 就会换版本。

⚠️ map 与 split_clients 都在 http 块求值，不能访问 $upstream_* 这类上游变量。

六、Lua 性能、生命周期与 njs 取舍

注意点 说明
避免热路径建大 table 每次请求都建大 table 会推高 GC 压力
table.new(narr, nrec) LuaJIT 扩展，预分配避免 rehash
复用模块级常量 把不变的 table 提到 init_by_lua
生命周期 执行次数 适合做什么
init_by_lua master 启动 1 次 加载配置、require 模块
init_worker_by_lua 每个 worker 1 次 启动定时器、预热共享内存

⚠️ init_by_lua 里不能做 cosocket，也不能依赖 ngx.var —— 它执行时还没有任何请求。

⚠️ init_by_lua 里 require 的模块在 reload 时不会重新加载（package.loaded 缓存），改代码后必须重启而非 reload。

维度 Lua（OpenResty） njs（官方）
来源 第三方发行版 Nginx 官方模块
生态 极丰富（lua-resty-*） 少，标准库受限
共享内存 lua_shared_dict js_shared_dict_zone
适用 复杂网关逻辑 轻量头处理、简单路由

⚠️ njs 是 JavaScript 子集，没有 Promise、没有 async、没有 npm 生态。想用它替代 Lua 做网关，会很快撞到能力边界。

七、动态上游与配置调试

写法 DNS 解析时机 是否受 resolver 影响
proxy_pass http://api.internal; 启动时解析一次并缓存 ❌ 不生效
proxy_pass $target; 每次请求按 TTL 解析 ✅ 生效

⚠️ 用变量做 proxy_pass 会失去静态解析的缓存，每个请求都要走一次 DNS（受 valid= 控制）。QPS 高时 DNS 会成为瓶颈。

⚠️ 用了变量式 proxy_pass 却**没配 resolver**，会直接报 no resolver defined to resolve ...。

⚠️ nginx -t 只校验语法，不校验语义。配置能通过检查，仍可能因 upstream 不存在、证书过期、resolver 缺失而在运行时出错。

⚠️ nginx -T 输出的是合并后的配置（含所有 include）。排查「配置到底生效没有」时必须看 -T，不能看源文件。

常见坑清单

  • listen ... http2 在 1.25.1+ 已废弃，未改用 http2 on
  • 接 TLS 上游却写 grpc:// 而非 grpcs://
  • gRPC metadata key 大小写不统一，出现对不上
  • 把 grpc_read_timeout 当成总时长，误判流式接口超时
  • grpc_buffer_size 设得过小，响应头被判 invalid
  • 打开 non_idempotent 允许重放非幂等 gRPC 调用
  • 以为 Nginx 官方能直接代理 gRPC-Web
  • $ssl_preread_alpn_protocols 用等值比较，漏掉多值情况
  • 在 log_by_lua / header_filter_by_lua 里用 cosocket
  • 在热路径做阻塞 IO，卡死整个 worker
  • Lua 外部调用不 pcall，一次抖动产生一片 500
  • lua_shared_dict 用 set + expire 两步，key 永不过期
  • 以为 lua_shared_dict 跨实例共享，做全局精确限流
  • balancer_by_lua 里写副作用，重试时重复执行
  • 变量式 proxy_pass 没配 resolver
  • 只跑 nginx -t 就发布，忽略语义错误
  • 改 Lua 代码后用 reload 而非 restart，require 缓存没更新
