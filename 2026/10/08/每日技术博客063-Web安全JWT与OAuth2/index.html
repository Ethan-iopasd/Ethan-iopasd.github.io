开场：一句话结论

JWT 是一份「可被验证、但不可被撤销」的声明；OAuth 2.0 是授权协议不是认证协议；要「用 Google 登录」必须上 OIDC。

概念 规范 解决什么 不解决什么
JWT RFC 7519 令牌怎么编码、怎么验签 谁发的、发给谁、能不能撤销
OAuth 2.0 RFC 6749 第三方怎么拿到受限访问权 用户是谁
OIDC OpenID Connect Core 1.0 用户是谁（认证） 授权
OAuth 2.0 安全 BCP RFC 9700 上面这些怎么用才不出事 ——

一、JWT 结构：三段 base64url，签名 ≠ 加密

段 内容 是否可读
Header {"alg":"RS256","typ":"JWT","kid":"key-1"} ✅ 明文
Payload sub / exp / iss / aud / 自定义 claim ✅ 明文
Signature 对 header.payload 的签名 只能验，不能改

⚠️ base64url 是编码不是加密。 payload 放密码、身份证 = 明文泄露；签名只保证「没被篡改」，不保证「看不到」。而且签名**只覆盖 header + payload**，不覆盖任何外部上下文 —— 令牌里的 role: admin 不能证明服务端现在真认为你是 admin，得看签名密钥在谁手里、有没有撤销机制。JWT 用的是 base64url（标准 base64 的 + / 换成 - _，去掉 = 填充）。

二、三种经典算法攻击

alg: none —— 把 alg 改成 none，删掉第三段签名，服务端若信 header 就无条件通过。

算法混淆 RS256 → HS256 —— 服务端用 RSA 公钥验签（RS256），攻击者改成 HS256，拿那个公钥当 HMAC 密钥重新签名。公钥是公开的，攻击者拿得到。

kid 注入 —— kid（key id）是给服务端选密钥用的，直接拿去拼路径 / SQL / URL：

攻击载荷 目标
"kid": "../../../../dev/null" 读到空文件当密钥
"kid": "key1' UNION SELECT 'attacker_secret'--" SQL 注入替换密钥
"kid": "http://evil.com/key" 服务端去攻击者服务器取密钥（SSRF + 自签）

⚠️ algorithms 参数永远写死，绝不从 token header 里读 —— 这是防 alg:none 和算法混淆的唯一要点。kid 必须先在服务端 JWKS 白名单里查，绝不当文件名 / URL / SQL 参数用；jku / x5u 头部让服务端去取远程密钥，是最直接的伪造入口，默认应禁用。另外 HS256 密钥要 ≥ 32 字节随机值（RFC 7518 最低要求），用 secret / changeme / RSA 公钥当 HMAC 密钥，签名形同虚设。

三、必须校验的声明（claim）

claim 含义 不校验的后果
exp 过期时间 令牌永不过期
nbf 生效时间 未生效的令牌被接受
iss 签发者 别的系统的令牌能在你这儿用
aud 接收方 给 A 服务的令牌拿去调 B 服务
sub 主体（用户 id） 无法定位到具体用户
jti 令牌唯一 id 无法做黑名单 / 防重放
azp 授权方（OIDC） 无法校验令牌发给哪个客户端

⚠️ aud 不校验是跨服务重放的头号成因。 同一个 IdP 给所有服务签令牌时，给「只读服务」的令牌能直接调「支付服务」—— 只要不校验 aud。同理不要用「解码成功」当「验签成功」（decode(..., verify_signature=False) 只解码不验签），写一个「篡改 payload 后必须被拒」的测试用例；时钟偏移要留容差（通常 leeway=60 秒），否则多机时间不同步时，刚签发的令牌会被判为「未生效」。

四、JWT 无法主动失效 —— 三个解法

JWT 无状态、服务端不存它，所以用户改密码、封号、令牌被盗，都只能等 exp 到点。

解法 机制 代价
短有效期 access token 5–15 分钟 只能缩小窗口，不能撤销
黑名单 存 jti 到 Redis，验签后查 引入服务端状态
令牌版本号 用户表存 token_version，令牌带上；改密码时 +1 每次请求查一次用户（可缓存）

⚠️ 黑名单必须设 TTL = 令牌剩余有效期，永不过期的黑名单会无限膨胀，且令牌本身早失效了。更重要的是：一旦上了黑名单或版本号，JWT 就退回成「有状态令牌」 —— 这时要问「那我为什么不用 Session」。JWT 的价值在服务间无状态调用和跨域传递，不是「比 Session 高级」。

⚠️ 不要给 access token 设几天有效期来「省刷新」。 有效期越长，撤销窗口越大。正确做法是短 access token + 长 refresh token。

五、Refresh Token：轮换 + 重放检测

机制 行为
轮换（rotation） 每次刷新签发新的 refresh token，旧的立即失效
重放检测（reuse detection） 已用过的 refresh token 再次出现 → 整条链作废
令牌族（token family） 一个 refresh 链共用一个 family id，重放时按 family 全清
发送方约束 DPoP / mTLS 绑定，令牌只能被持有密钥的那一方用

⚠️ 只轮换不检测 = 没做。 攻击者拿着旧令牌照样能一直刷新。检测到重放时，必须把该用户 / 该 family 的所有会话全部踢掉，因为无法分辨谁是攻击者。RFC 9700 明确要求：公共客户端（SPA / 移动端）的 refresh token 必须轮换 + 发送方约束，且必须存在服务端可撤销 —— 纯无状态的 refresh token 等于一个长效 access token。

六、令牌存哪：localStorage vs httpOnly Cookie

维度 localStorage httpOnly Cookie
XSS 能否读走 ❌ 能 ✅ 读不到
CSRF 风险 ✅ 无（要手动加头） ⚠️ 有（浏览器自动携带）
跨域调用 ✅ 方便 ⚠️ 需要 CORS + credentials
服务端注销 做不到 ✅ 删 Cookie
Cookie 属性 作用
HttpOnly JS 读不到（防 XSS 窃取）
Secure 只在 HTTPS 发送
SameSite=Lax 顶级导航带 Cookie，跨站 POST 不带（防 CSRF）
Path=/auth/refresh 限制只在刷新接口发送，缩小暴露面
__Host- 前缀 强制 Secure + 无 Domain + Path=/

⚠️ 推荐组合：access token 放内存（不落盘），refresh token 放 HttpOnly Cookie。 页面刷新时用 refresh 换新的 access token，XSS 也拿不到长效凭据。BFF（Backend for Frontend）模式更稳：浏览器只跟同源后端会话（Cookie），令牌全留在后端，前端完全接触不到令牌。

⚠️ SameSite=Lax 不是万能的，它只拦跨站 POST，不拦顶级 GET 导航。若刷新接口是 GET，仍会被利用 —— 刷新 / 写操作一律用 POST。

七、签名算法怎么选

算法 类型 密钥 适用
HS256 对称 HMAC 共享密钥 单一服务自签自验、内部服务
RS256 非对称 RSA 私钥签 / 公钥验 多服务验签、第三方 IdP（首选）
ES256 非对称 ECDSA 同上 令牌体积小、移动端友好
none —— —— ❌ 永远不要接受

⚠️ 只要验签方和签名方不是同一进程，就用非对称算法。 HS256 要求验签方持有同一把密钥 —— 每个下游服务都拿到「能签发」的密钥，等于每个下游都能伪造令牌。JWKS 只从 iss 对应的可信 URL 加载（如 https://auth.example.com/.well-known/jwks.json），不要跟着令牌里的 jku 走。

⚠️ 轮换密钥靠 JWKS 多密钥并存：新旧公钥同时发布，新令牌用新私钥签，旧令牌用旧公钥验，等最大有效期过后再摘旧公钥。直接换密钥会让所有在线用户瞬间掉线。

八、OAuth 2.0 四种授权模式

模式 状态 场景 令牌在哪
授权码 + PKCE ✅ 唯一推荐 Web / SPA / 移动端 / 桌面 后端用 code 换
授权码（无 PKCE） ❌ 不推荐 仅机密客户端历史遗留 同上
隐式 Implicit ❌ 已废弃 旧 SPA URL fragment（进历史 / Referer）
密码 Password (ROPC) ❌ 已废弃 旧第一方 App 客户端直接拿密码
客户端凭证 ⚠️ 仅服务间 无用户参与的服务调用 客户端自己换

PKCE 解决的是授权码拦截：即使攻击者截获 code（自定义 URL scheme、Referer、日志、共享浏览器），没有 code_verifier 也换不到令牌。

参数 要求
code_challenge_method **只用 S256**；plain 等于没保护
code_verifier 43–128 字符，每次授权重新生成，绝不复用
state 必须带 + 必须校验，防 CSRF
nonce OIDC 才需要，防 id_token 重放
redirect_uri 精确字符串匹配注册值
code 一次性，用完立即失效
scope 最小权限，别默认要一堆

⚠️ redirect_uri 前缀匹配是最常见也最致命的 OAuth 漏洞。 注册了 https://app.example.com/cb 却做前缀匹配，攻击者用 https://app.example.com/cb.evil.com 或 https://app.example.com/cb?x= 就能把 code 引到自己服务器。必须逐字符精确匹配，注册时就拒绝通配符和片段。

⚠️ state 不能省，它防的是「攻击者用自己的账号走完授权、把 code 塞给受害者」的账号混淆攻击。PKCE 现在对机密客户端也推荐（RFC 9700 / OAuth 2.1 草案要求所有客户端）—— 别以为「我有 client_secret 就不用 PKCE」，授权码在浏览器链路里就能被拦。

⚠️ OAuth 2.1 至今仍是 IETF 草案（draft-ietf-oauth-v2-1，2026 年仍在迭代），没有成为 RFC。方向已定：PKCE 强制、移除隐式与密码模式、refresh token 必须轮换或发送方约束。已发布可引用的正式文件是 RFC 9700（2025-01）。另外客户端凭证模式没有用户，它拿到的是「这个应用能干什么」，不是「这个用户能干什么」。

九、OIDC：在 OAuth 之上加的身份层

OAuth 只解决授权（拿到 access token 去调 API），不告诉你「用户是谁」。OIDC 补了这块：

新增 作用
scope=openid 请求 OIDC，必须有它才返回 id_token
id_token 一个 JWT，声明用户身份（sub / name / email …）
nonce 请求时带上，校验 id_token.nonce 一致，防重放
/userinfo 用 access token 换用户信息端点
/.well-known/openid-configuration 发现文档：端点、支持算法、JWKS 地址
用途 用哪个令牌
调业务 API access token
判断「用户是谁」 id_token 的 sub
取更多用户信息 access token 调 /userinfo
❌ 拿 access token 当身份 错误 —— 它的格式、受众都是给资源服务器的

⚠️ id_token 只用来认证，不用来调 API；反过来 access token 不是身份凭证，别解出里面的 sub 就当真。id_token 的 aud 必须等于你的 client_id、iss 必须是你信任的 IdP、nonce 必须与请求时一致 —— 三项缺一就是「任何 IdP 的令牌都能登进你的系统」或「id_token 可被重放」。**账号关联用 (iss, sub)，不要用 email**（可能被改、被回收、被多个 IdP 共用）。

十、SSO 单点登录流程

概念 含义
IdP（Identity Provider） 统一认证中心，如 Keycloak / Okta / Auth0 / Entra ID
SP / RP（服务提供方） 各个业务应用
全局会话 / 本地会话 IdP 的会话 / 各应用自己的会话
SLO（单点登出） 登出时通知所有 SP 清会话 —— 实践中很难做全

⚠️ 登出是个坑。 OIDC 的 end_session_endpoint 只保证 IdP 会话被清，各 SP 的本地会话不一定同步清掉。要真登出，得靠后端会话中心化（共享会话存储）或缩短本地会话有效期，且 IdP 侧要能强制吊销 —— 否则员工离职后，各 SP 里还挂着登录态。

常见坑清单

  • 把 JWT payload 当加密内容，往里塞敏感信息
  • 接受 alg: none，或从 token header 读 alg 再据此验签
  • 服务端 RS256 验签却不固定算法，被 RS256→HS256 打穿
  • HS256 密钥用弱口令，或复用 RSA 公钥当 HMAC 密钥
  • kid 直接当文件名 / SQL 参数 / URL 用；允许 jku / x5u
  • 不校验 exp / iss / aud，或用「解码成功」当「验签成功」
  • 手写 JWT 验签逻辑；时钟偏移不留容差
  • 需要「踢下线」却用纯无状态 JWT，靠等过期糊弄
  • 黑名单不设 TTL；access token 有效期设成几天来「省刷新」
  • refresh token 只轮换不做重放检测，或纯无状态不可撤销
  • 公共客户端的 refresh token 不做发送方约束
  • 把令牌放 localStorage；刷新接口用 GET
  • 会话 Cookie 缺 HttpOnly / Secure / SameSite
  • 用隐式流 / 密码模式；PKCE 用 plain 或复用 code_verifier
  • 不带或不校验 state；redirect_uri 做前缀匹配
  • 授权码可被重复使用；scope 一上来就要最大权限
  • 拿 OAuth access token 当身份凭证
  • 前端解出 JWT payload 就信任里面的 role / user_id
  • id_token 不校验 aud / iss / nonce；用 email 做账号关联
  • 以为登出 IdP 就等于所有应用都登出了
