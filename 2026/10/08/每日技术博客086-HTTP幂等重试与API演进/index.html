六 幂等、重试与 API 版本演进 本篇

开场：一句话结论

重试的前提是幂等，而 HTTP 方法自带的幂等只覆盖到「语义」层面 —— 真正保证不重复下单、不重复扣款的，是服务端自己的幂等键。

一、幂等性与安全性矩阵

方法 Safe（安全） Idempotent（幂等）
GET / HEAD ✅ ✅
OPTIONS / TRACE ✅ ✅
PUT ❌ ✅
DELETE ❌ ✅
POST ❌ ❌
PATCH ❌ ❌（取决于内容）
概念 定义
Safe 不改变服务端状态（只读）
Idempotent 执行 1 次和 N 次，服务端最终状态相同

所以 DELETE 幂等但不安全 —— 它改状态，只是重复执行效果一致。

⚠️ PUT 幂等是语义约定，不是自动保证。服务端写 UPDATE balance = balance + 1 就把它变成非幂等。
⚠️ PATCH 用 JSON Merge Patch 时 {"v":1} 幂等，但 {"op":"inc"} 不是 —— 方法本身不承诺。
⚠️ DELETE 幂等的正确实现是「删不存在的资源也返回 204/404」，而不是第二次报 500。

二、幂等键（Idempotency-Key）

Stripe 的实现可作为参考基线：

项 值
请求头 Idempotency-Key，最多 255 字符，建议 UUID v4
保存时长 至少 24 小时后可被清理
命中重复 返回首次的状态码与响应体（含 500）
并发同键 返回 409 Conflict
参数不一致 idempotency_error
GET / DELETE 不要传，本身已幂等，传了无效

⚠️ 幂等键必须由客户端生成，且每个逻辑操作一个键（不是每个 HTTP 请求一个），重试时复用。
⚠️ 键被清理后复用会当成新请求处理，TTL 要覆盖客户端最长的重试窗口。
⚠️ 别把邮箱、手机号当幂等键：既泄漏隐私，熵也不够。
⚠️ 存储必须对键加唯一约束，否则并发同键会双写 —— 「先查再写」挡不住竞态。

三、重试的适用条件与退避抖动

情况 是否重试
网络错误 / 连接超时 ✅（需确认服务端未处理成功）
408 / 429 ✅（配合 Retry-After）
500 / 502 / 503 / 504 ✅（服务端瞬时故障）
400 / 401 / 403 / 404 / 422 ❌ 参数或权限问题，重试无用
409 ❌ 冲突，应交给业务逻辑处理
未带幂等键的 POST ❌ 可能重复下单

Retry-After 可以是秒数或 HTTP 日期，服务端给了就按它等，别用自己的退避。

抖动策略 公式 特点
Full Jitter random(0, delay) 分散效果最好，推荐
Equal Jitter delay/2 + random(0, delay/2) 保底一半等待
Decorrelated min(cap, random(base, prev*3)) 自适应
机制 作用
Retry Budget 限制重试占总请求的比例（如 10%）
Circuit Breaker 连续失败到阈值就快速失败，不再打后端
Bulkhead 隔离依赖资源池，防止一处拖垮全局

⚠️ 不做抖动的重试 = 定时雪崩：所有客户端同一时刻重试，把瞬时故障放大成持续故障。
⚠️ 重试要有上限（次数 + 总时长），无限重试等于把故障转嫁给上游。
⚠️ 重试次数是乘法放大：网关重试 3 次 × 客户端重试 3 次 = 后端承受 9 倍流量。
⚠️ 只在最外层重试；熔断恢复要用半开状态试探，直接全开会让刚恢复的后端被瞬间打满。

四、超时分层与连接复用错配

错配 后果
客户端超时 < 服务端超时 客户端已放弃，服务端还在跑，产生孤儿请求
客户端超时 = 服务端超时 边界竞争，偶发超时
无总超时 连接池被慢请求占满，级联失败
Keep-Alive 错配 现象
服务端 keepalive_timeout < 客户端 服务端先关，客户端复用旧连接 → Connection reset by peer
客户端空闲 < 服务端 客户端先关，服务端维持空闲连接
中间有 LB / Nginx 又多一层超时，最容易撞

⚠️ 典型故障：Nginx keepalive_timeout 60s、客户端连接池空闲 65s 复用 —— 复用瞬间被 RST。
⚠️ 客户端连接池必须配置空闲连接最大存活时间，并且小于所有中间层的 keep-alive 超时。
⚠️ 幂等请求遇到 Connection reset 可安全重试；非幂等请求要先查状态再决定。

五、API 版本演进策略与破坏性变更

方案 示例 缺点
URL 路径 /v1/users URL 会变，不严格符合「URI 标识资源」
Query 参数 /users?version=1 缓存键混乱、易漏传
自定义 Header X-API-Version: 1 不便调试、CDN/缓存难区分
Content Negotiation Accept: application/vnd.acme.v1+json 实现复杂、工具支持差

实践结论：公开 API 用 URL 路径版本（/v1/），内部 API 可用 Header。

变更 是否破坏性
新增可选字段 ❌ 兼容
新增必填字段 ✅ 破坏
删除字段 / 改字段类型 ✅ 破坏
改字段语义（单位、含义） ✅ 破坏
改错误码 / 状态码语义 ✅ 破坏
收紧校验规则 / 改排序默认顺序 ✅ 破坏
枚举新增取值 ⚠️ 视客户端实现，可能破坏
改默认值 / 改分页默认页大小 ⚠️ 可能破坏

⚠️ 「加字段」通常安全，但客户端若用严格反序列化（未知字段报错），照样炸。
⚠️ 枚举新增值是最隐蔽的破坏性变更：老客户端遇到未知值可能直接崩溃或当成默认值。
⚠️ 改字段语义（如「秒」改「毫秒」）比改类型更危险 —— 类型没变，编译期毫无提示。

六、弃用流程（Deprecation / Sunset）

头 规范 含义
Deprecation RFC 9745 资源已被弃用（时间戳）
Sunset RFC 8594 资源预计停止响应的日期
Link RFC 8288 指向替代版本或弃用说明

过渡期做法：发布 /v2 与 /v1 双写双读（/v1 内部转发到 v2 模型）→ 给 /v1 全部响应加 Deprecation + Sunset 头 → 监控调用方并主动通知 → 到期前保留降级开关，到期后返回 410 Gone。

⚠️ Sunset 描述的是「预计」时间，不是保证 —— 客户端不能把它当契约。
⚠️ 弃用公告要落到响应头 + 文档 + 邮件三处，只改文档等于没通知。
⚠️ 到期直接删接口是最常见的翻车点：先返回 410 并保留一段时间，比直接 404 更易定位。

七、PATCH、错误格式与分页

对比 JSON Merge Patch JSON Patch
规范 RFC 7386 RFC 6902
表达力 简单合并 完整（增删改移拷贝测试）
删除字段 置 null {"op":"remove"}
数组操作 ❌ 整体替换 ✅ 支持索引

RFC 9457（取代 RFC 7807）定义的五个标准成员：

成员 含义
type 问题类型的 URI，默认 about:blank
title 简短的人类可读摘要
status HTTP 状态码（应与响应行一致）
detail 本次问题的具体说明
instance 该问题实例的 URI
分页方式 示例 稳定性
Offset ?offset=100&limit=20 ⚠️ 数据增删会重复/漏读
Cursor ?cursor=eyJpZCI6MTAwfQ ✅ 稳定，不随数据变化漂移
Keyset ?after_id=100&limit=20 ✅ 稳定，且可用索引

⚠️ Merge Patch 里 null 表示删除字段，不是设为 null —— 语义容易踩坑。
⚠️ 两种 PATCH 的 Content-Type 不同，服务端必须按类型分派，否则解析出错。
⚠️ Content-Type 必须是 application/problem+json，否则客户端无法识别。
⚠️ 别把所有错误都包成 HTTP 200 + {code, message} —— 监控、网关、缓存全部失效。
⚠️ Offset 分页深翻页性能急剧下降（OFFSET 100000 要扫描并丢弃 10 万行）。
⚠️ Cursor 必须不可伪造（签名或加密），否则等于把数据库主键暴露成公共 API。
⚠️ 用 ORDER BY 分页时排序键必须唯一，否则同一页边界会重复或跳过记录。

常见坑清单

  • 把 Safe 和 Idempotent 混为一谈，以为 DELETE 安全
  • 对未带幂等键的 POST 做自动重试，造成重复下单
  • 重试 4xx（400 / 401 / 403 / 404 / 422）
  • 重试不做抖动，所有客户端同时重试造成雪崩
  • 无限重试或没有总时长上限
  • 网关和客户端两层都重试，流量被指数放大
  • 幂等键由服务端生成，重试时变成了新键
  • 幂等键 TTL 短于客户端重试窗口，键过期后重复执行
  • 幂等键存储没加唯一约束，并发同键双写
  • 客户端超时小于服务端超时，产生孤儿请求
  • 没有总超时，连接池被慢请求占满
  • 客户端连接池空闲时间大于中间层 keep-alive，复用被 RST
  • 忽略服务端返回的 Retry-After，用自己的退避
  • 新增必填字段却当成兼容变更
  • 枚举新增取值，老客户端直接崩
  • 悄悄把字段单位从秒改成毫秒
  • 只改文档做弃用通知，没有 Deprecation / Sunset 头
  • Sunset 到期直接删接口，返回 404 而不是 410
  • PATCH 用 Merge Patch 时把 null 当成「设为 null」
  • 错误响应用 200 + {code}，Content-Type 也不是 problem+json
  • 深翻页用 OFFSET，性能随页码线性下降
  • Cursor 未签名，暴露内部主键且可被伪造
  • 分页排序键不唯一，边界记录重复或丢失
