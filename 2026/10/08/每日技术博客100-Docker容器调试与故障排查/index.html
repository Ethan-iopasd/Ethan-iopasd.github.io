开场：一句话结论

排查顺序固定为：docker ps -a 看退出码 → docker logs 看输出 → docker inspect 看 State → 进容器动手。 90% 的问题在前三步就能定位；退出码本身就是线索（137 是 OOM 或被强杀，127 是命令不存在）。

一、起不来的排查顺序

docker inspect 的 State 关键字段：

字段 含义
Status exited / running / restarting / dead
ExitCode 退出码，见下表
OOMKilled true 表示被内存限制杀死
Error 启动期错误信息
RestartCount 重启次数，配合 restart 策略看

退出码对照（Linux 里 128+N = 收到信号 N）：

退出码 含义 常见原因
0 正常退出 命令跑完就结束，容器自然停止
1 应用错误 未捕获异常、配置缺失
126 无执行权限 入口文件没有 +x
127 命令不存在 ENTRYPOINT 写错 / shebang 路径不对
137 128+9 = SIGKILL OOMKilled 或被 docker stop 超时强杀
139 128+11 = SIGSEGV 段错误，原生扩展 / 底层库崩溃
143 128+15 = SIGTERM 收到 docker stop，正常终止流程

⚠️ 137 不等于一定是 OOM。docker stop 默认发 SIGTERM 等 10 秒，应用没退出就补 SIGKILL，同样是 137。要区分必须看 docker inspect 的 OOMKilled 字段。

⚠️ 127 最常见的原因是 ENTRYPOINT ["python"] 但镜像里没装 python，或 shebang 写成 #!/usr/bin/env python 而 env 路径不存在。别急着怀疑代码。

⚠️ 容器里 PID 1 必须能正确处理信号。用 CMD ["python", "app.py"] 这种 exec 形式，PID 1 就是 python，能收 SIGTERM；用 CMD python app.py（shell 形式）时 PID 1 是 /bin/sh，信号不转发给子进程，docker stop 要等满 10 秒才被强杀 → 表现为「退出慢 + 137」。

二、docker logs 与日志驱动

⚠️ docker logs 只能拿到 PID 1 的 stdout / stderr。应用把日志写进容器内文件（如 /var/log/app.log）时，docker logs 一片空白 —— 这不是没日志，是没走标准输出。要么改配置输出到 stdout，要么用 docker cp 把文件拷出来。

日志驱动 去向 特点
json-file 宿主文件，默认 docker logs 可用
local 宿主文件，二进制 更省空间，docker logs 可用
syslog syslog 集中收集
fluentd Fluentd 日志管道
none 丢弃 docker logs 无输出

⚠️ 默认 json-file 不轮转。长时间运行的容器会把日志无限写进 /var/lib/docker/containers/，直到磁盘满 —— 生产环境必须设 max-size / max-file。

⚠️ 日志驱动设为 none / syslog 后 docker logs 会失效或为空，排查时先确认驱动类型。

三、进容器：几种方式与优先级

方式 适用 风险
docker exec 绝大多数情况 需要容器内有 shell
docker attach 想接主进程 stdio 退出会杀掉容器、且共享 stdio
docker cp 只读文件 只拷不执行
nsenter 直接进 namespace 需宿主权限，绕过 Docker
docker debug distroless / scratch 需 Docker Desktop

⚠️ docker attach 按 Ctrl+C 会终止容器（信号发给 PID 1）。detach 要用 Ctrl+P Ctrl+Q。且多个 attach 会共享同一 stdio，互相干扰。

⚠️ distroless / scratch 镜像没有 shell，docker exec -it sh 报 executable file not found。这时用 docker debug（能进入任何容器或镜像的调试 shell，甚至不含 shell 的镜像），或临时挂一个 busybox sidecar。

四、docker inspect 该看什么

路径 内容
.State ExitCode / OOMKilled / Error / Health
.Config.Env 环境变量，确认是否注入成功
.NetworkSettings IP、端口映射、网关
.Mounts 卷 / 绑定挂载的源与目标
.HostConfig.RestartPolicy 重启策略
.RestartCount 重启次数

健康检查

⚠️ **没有 HEALTHCHECK 的镜像，.State.Health 是 null**，unhealthy 无从谈起。unhealthy 也不等于容器退出 —— 它只是标记，除非编排层（Compose / Swarm / K8s）依据它做动作。

⚠️ HEALTHCHECK 命令在容器内执行，镜像里没有 curl / wget 会一直判失败。用 CMD ["sh","-c","..."] 或换成镜像里确实存在的工具。

五、网络问题排查

现象 原因 排查
容器内域名解析失败 默认 bridge 无内置 DNS 用自定义网络（自带 DNS）
跨容器不通 不在同一网络 docker network inspect 比对成员
端口映射不生效 -p 绑定了 host IP / 只 EXPOSE 检查 -p 与 NetworkSettings.Ports
访问宿主服务 需 host.docker.internal 或用宿主真实 IP

⚠️ 默认 bridge 网络没有自动 DNS，容器只能靠 IP 互通；自定义网络（docker network create）才提供按容器名解析。这是「容器间用服务名连不上」的头号原因。

⚠️ EXPOSE 不发布端口，它只是元数据 / 文档。真正对外映射必须用 -p 8080:80 或 Compose 的 ports。

⚠️ -p 8080:80 默认绑 0.0.0.0（全网可达）；-p 127.0.0.1:8080:80 只绑本机回环。安全敏感场景显式指定 host IP。

六、存储、资源与时区

卷与权限

⚠️ 容器内 UID 与宿主 UID 不匹配是最常见的权限坑。宿主目录属主是 1000，容器里进程以 root（UID 0）写文件，产物在宿主上就变成 root 属主；反过来容器以非 root 跑、宿主目录只对 root 可写，就报 Permission denied。用 --user $(id -u):$(id -g) 对齐，或预先 chown 目录。

⚠️ -v /host/not/exist:/data 会自动把宿主路径创建成一个目录（而不是报错），于是你往「文件」挂载时得到的却是个目录。用 --mount 形式会明确报错，更安全。

⚠️ 具名卷（myvol:/data）与绑定挂载（./data:/data）排查方式不同：具名卷在 /var/lib/docker/volumes/ 下，看不到不代表不存在；绑定挂载则是宿主真实路径。

资源

⚠️ --memory 512m 超限会被 OOMKill，退出码 137 且 OOMKilled=true。Java / Node 这类运行时不会自动感知 cgroup 限制，堆按宿主内存估算，容易直接撞上限被杀 —— 要显式设 -Xmx / --max-old-space-size。

⚠️ --cpus 1 是限流不是报错：进程被 CFS 调度节流，表现为「慢」而非「崩」。排查慢时先看 docker stats 的 CPU 是否长期贴顶。

⚠️ docker system df 里「构建缓存」经常是最大头。磁盘满时先看这里，再决定清什么。

时区

⚠️ 容器默认 UTC，与宿主（如东八区）差 8 小时。日志时间对不上、定时任务在错误时刻触发，多半是这个。设 TZ=Asia/Shanghai 环境变量，或挂载 /etc/localtime：-v /etc/localtime:/etc/localtime:ro。注意有些精简镜像没有 tzdata，光设 TZ 不生效。

七、Compose 调试、事件与清理

⚠️ depends_on 默认只保证容器「已启动」，不保证服务「已就绪」。db 容器 Up 了但 Postgres 还在初始化时，web 照样会连不上。要等就绪必须配 condition: service_healthy（且被依赖方要有 HEALTHCHECK）。

⚠️ docker compose config 是把多个 override 文件、.env、extends 全部合并后的结果 —— 排查「为什么这个变量没生效」时以它为准，而不是看单个 yaml。

⚠️ docker system prune -a --volumes 会删掉未被任何容器使用的卷 —— 数据卷里可能是数据库。删之前先 docker volume ls 确认，别在带数据的机器上随手执行。

常见坑清单

  • 看到 137 就断定 OOM，其实可能是 docker stop 超时强杀
  • 127 却去查业务代码，实际是 ENTRYPOINT / shebang 写错
  • CMD 用 shell 形式导致 PID 1 不转发信号，退出慢
  • 应用把日志写进容器内文件，docker logs 看不到还以为是没日志
  • 日志驱动没设 max-size，日志撑爆磁盘
  • 用 docker attach 后 Ctrl+C 把容器杀了
  • distroless 镜像里 docker exec sh 报找不到可执行文件
  • 没有 HEALTHCHECK 却期望 .State.Health 有值
  • 默认 bridge 网络里用容器名互相解析，解析不到
  • 以为 EXPOSE 就等于对外发布端口
  • -p 绑了 0.0.0.0 把服务暴露到公网
  • 容器 UID 与宿主 UID 不匹配，卷里写入 Permission denied
  • -v 挂载了不存在的宿主路径，被静默创建成目录
  • Java / Node 不感知 cgroup 限制，被 OOMKill
  • 把 --cpus 限流当成崩溃排查
  • 容器默认 UTC，日志时间与宿主差 8 小时
  • 以为 depends_on 会等服务就绪，实际只等容器启动
  • 随手 docker system prune -a --volumes，删掉了数据库卷
