开场：一句话结论

国际化是消息 key 的组织问题，SSR 是两套运行时必须渲染出同一棵树，微前端是用运行时开销换团队自治——三件事都不难写，难的是知道代价在哪。

一、vue-i18n 的 Composition API

vue-i18n v9 起支持 Vue 3，当前主版本 v11（v8 已 EOL）。

参数 作用 常见误用
legacy: false 启用 Composition API 忘写 → useI18n 抛 Not available in legacy mode
globalInjection 模板里能用 $t 只在 legacy: false 下有效
useScope: 'global' 读写全局语言包 默认 local 改了不生效
fallbackLocale 缺 key 时兜底 不设 → 页面直接显示 key

⚠️ 默认 useScope 是 local，locale.value = 'en' 只改组件级作用域。要切全局必须显式传 useScope: 'global'。

三、语言包的组织、懒加载与兜底

key 命名 示例 评价
语义 key user.login.submit ✅ key 稳定，改文案不动代码
原文当 key "Submit" ⚠️ 改文案即改 key，同词不同语境无法区分

⚠️ import.meta.glob 是 Vite 编译期特性，参数必须是字面量字符串。写成 ./locales/${locale}/*.json 直接编译报错。

配置 生产建议 原因
missingWarn / fallbackWarn false 缺 key 警告会刷爆日志
fallbackLocale 必设 否则缺 key 显示原始 key
missing 回调 上报监控 把缺 key 变成可观测指标

⚠️ 别用 fallbackLocale: false 图省事，页面会出现 user.login.submit 这种字符串，比显示英文更难看。

SEO 与 hreflang

⚠️ hreflang 必须用绝对 URL，且要互相引用（A→B、B→A）。单边引用搜索引擎不认，SPA 动态注入 head 爬虫也未必执行。

四、SSR：两套运行时，一棵树

API 环境 用途
createSSRApp 两端 SSR 实例，客户端 hydration 也用它
renderToString 服务端 渲染为 HTML 字符串
renderToWebStream 服务端 流式输出
useSSRContext 服务端 组件内取 SSR context
onServerPrefetch 服务端 渲染前预取数据

数据预取与状态序列化

⚠️ 序列化必须把 < 转义成 \u003C，否则数据里出现 </script> 会提前闭合标签，直接 XSS。

SSR 下不能用的 API

客户端 API 替代方案
window / document onMounted 包裹，或 <ClientOnly>
localStorage / sessionStorage Cookie，或挂载后再读
Date.now() / Math.random() 服务端算好塞进 state

⚠️ SSR 收益是首屏与 SEO，成本是服务端 CPU。每个请求跑一次 Vue 渲染，高 QPS 下 Node 成瓶颈。绝不能把跨请求状态放模块顶层变量，会串号。

Nuxt 3 vs 手写 SSR

维度 手写 SSR Nuxt 3
起步成本 高（自己搭 Vite + Express） 低（约定式）
控制粒度 完全可控 受框架约定约束
数据预取 自己写 useAsyncData / useFetch 内置
部署形态 自己选 SSR / SSG / ISR / SPA 一键切
适合 已有 Node 服务、深度定制 新项目、内容站

SSG 是构建期生成静态 HTML，ISR 是静态页 + 后台按需再生成。二者都无运行时服务端渲染成本，适合内容不频繁变的站点。

五、hydration mismatch 的成因与排查

hydration 是客户端复用服务端 HTML 并挂载事件的过程。两边渲染结果不一致时，Vue 会丢弃服务端 DOM 重渲染并报 Hydration node mismatch。

成因 表现 修法
Math.random() / Date.now() 文本节点对不上 服务端算好，随 state 下发
时区 / Intl 数据差异 日期文本不同 固定 timeZone，两端同一 ICU
浏览器 API 分支 服务端走了另一条路 import.meta.env.SSR 或 onMounted
无效 HTML 嵌套 <p> 里塞 <div> 修模板
v-if 依赖客户端状态 树结构不同 <ClientOnly> 包起来
第三方脚本改 DOM 水合时 DOM 已变 隔离到 onMounted

⚠️ <ClientOnly> 让该区域不参与 SSR，首屏内容缺失、SEO 拿不到。能改成「服务端算好再下发」的优先那么做，别拿它当万能挡箭牌。

⚠️ 无效 HTML 嵌套最隐蔽：<p><div>x</div></p> 被浏览器重排成三段，客户端按虚拟 DOM 找节点就错位。校验服务端 HTML 合法性比对着代码猜快。

六、微前端：五种方案对比

方案 隔离级别 接入成本 依赖复用 典型场景
iframe 最强（进程级） 极低 ❌ 完全不复用 第三方页面、强隔离
Web Components Shadow DOM 样式隔离 中 ⚠️ 弱 跨团队组件级集成
Module Federation 无运行时沙箱 中高 ✅ 共享依赖 构建期共享、同技术栈
qiankun JS 沙箱 + 样式隔离 中 ⚠️ 需配置 多技术栈子应用
micro-app 类 Web Components 中 ⚠️ 需配置 同上，接入更轻
样式隔离手段 隔离范围 代价
Shadow DOM 真隔离 全局样式进不来，需 ::part / CSS 变量
scoped 组件内 子应用间不隔离
命名前缀 约定级 靠自觉，容易冲突
qiankun strictStyleIsolation 影子 DOM 包裹 UI 库弹层挂 body 会失效

⚠️ qiankun 的 strictStyleIsolation 与 experimentalStyleIsolation 二选一。前者用 Shadow DOM，很多 UI 库的弹窗挂载到 document.body，被隔离后样式全丢，这是最常踩的坑。

JS 沙箱通过 Proxy 劫持子应用的 window 读写，卸载时销毁，不污染真实全局。

⚠️ 沙箱拦不住所有场景：document.body.appendChild 的节点、setTimeout 闭包、动态插入的第三方 <script> 都可能泄漏到真实全局。

通信方式 适用 风险
Props 下发 主 → 子，一次性配置 变化需重挂载
initGlobalState 主 ↔ 子双向 强耦合，状态难追踪
事件总线 松耦合广播 事件名冲突、难调试
postMessage iframe 方案 序列化成本

⚠️ 主应用与子应用同时接管路由是冲突根源。约定「主应用只管顶层路径，子应用只在激活前缀内接管」，并让子应用 base 指向自己前缀。

⚠️ Module Federation 里 singleton: true 但版本区间不重叠时，运行时会加载两份 Vue，provide/inject 与响应式直接失效。

七、微前端不是银弹

症状 更该用的方案
一个团队、一个仓库 单体 + 目录分模块
只想复用几个组件 发 npm 包（私有 registry）
只想独立部署 独立 CI + 反向代理按路径分流
子应用间频繁共享状态 说明它们本就是一个应用
团队技术栈完全统一 Module Federation，或干脆别拆
团队独立、发布节奏不同、栈可不同 微前端才有意义

⚠️ 微前端换来的每条好处都对应一份运行时开销：多一次资源加载、多一层沙箱代理、多一份公共依赖、多一套调试路径。只有「团队边界」真实存在时它才划算。

⚠️ 常见反模式：把微前端当性能优化。它只会更慢，目标是团队自治与独立发布，不是快。

常见坑清单

  • createI18n 忘写 legacy: false，useI18n 直接报错
  • useI18n() 默认 local 作用域，改 locale 不生效
  • 用字符串拼接组装翻译文案，换语言语序全错
  • 复数只写中英两分支，忽略其他语言分支数不同
  • 自己 toFixed(2) 拼货币符号，不用 Intl.NumberFormat
  • import.meta.glob 路径用变量拼接，编译期报错
  • 生产环境 missingWarn: true，日志被缺 key 警告刷爆
  • fallbackLocale: false，页面直接显示原始 key
  • hreflang 用相对路径，或只做单向引用
  • 客户端用 createApp 而不是 createSSRApp，水合失败
  • 序列化 state 时未转义 <，数据含 </script> 触发 XSS
  • 跨请求状态放模块顶层变量，SSR 下串号
  • 用 Math.random() / Date.now() 渲染，hydration mismatch
  • 模板写出 <p><div></div></p>，DOM 结构错位
  • <ClientOnly> 包住首屏主要内容，SEO 失去意义
  • qiankun strictStyleIsolation 开完，UI 库弹窗样式全丢
  • 子应用 vue 版本区间与主应用不重叠，运行两份 Vue
  • 主应用与子应用都接管全局路由，互相抢跳转
  • 把微前端当性能方案，实际每次导航都更慢
