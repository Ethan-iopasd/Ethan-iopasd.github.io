每日技术博客 091 · Go（四）：标准库实战与测试

每日技术博客 · 2026-10-08 · 第 091 篇

标准库够用是 Go 的卖点，但 context、io、json、time 各有必须知道的语义。这一篇讲这些包的实战用法、testing 全套写法和最常见的坑。

开场：一句话结论

context 管取消与超时，io 管流式组合，testing 管表驱动 + 子测试 + 竞态检测。 这三样吃透，项目里 80% 的「标准库该用哪个」就不用查了。

一、context：取消、超时与请求域数据

构造函数 用途 取消触发
WithCancel 手动取消 调用 cancel()
WithTimeout 相对超时 到时或 cancel()
WithDeadline 绝对时间点 到点或 cancel()
WithValue 传递请求域数据 不取消

⚠️ WithValue 只放「请求域元数据」（trace id、认证信息、请求 ID）。把可选参数、配置项塞进去会让函数签名撒谎，调用方无法从签名看出依赖。

⚠️ defer cancel() 必须写。 不 cancel 会让子 context 及其定时器一直挂在父节点上，直到父节点被取消——典型的 goroutine / 内存泄漏。

⚠️ context.Background 用于 main、初始化、测试；context.TODO 只是占位符，别把 TODO 留在生产代码里。

⚠️ ctx 必须是第一个参数，命名统一 ctx；值类型 key 用未导出的自定义类型，别用 string 做 key，否则会和别的包撞车。

二、io：接口组合的教科书

只有两个方法，组合出整个生态：

函数 / 类型 作用
io.Copy(dst, src) 流式拷贝，内部 32KB 缓冲
io.ReadAll(r) 一次读完（⚠️ 注意大小）
io.TeeReader(r, w) 读的同时写一份到 w
io.Pipe() 内存管道，同步的 Reader/Writer
io.LimitReader(r, n) 限制最多读 n 字节

⚠️ bufio.Writer 不 Flush 就丢数据。 尤其在有 return err 提前返回的路径上，defer w.Flush() 是标配。io.TeeReader(r, w) 能在读的同时写一份到 w（边读边算 hash 边落盘）。

⚠️ io.ReadAll 会把整个响应读进内存。**对外部输入必须先 io.LimitReader**，否则一个超大响应就能把服务打 OOM。

⚠️ io.Pipe 是同步的：Write 会阻塞直到有 Read 消费。忘了在另一头读就是死锁。

三、encoding/json：tag、精度与流式

tag 选项 语义
json:"name" 重命名字段
json:"-" 永不序列化
json:",omitempty" 零值时省略
json:",string" 以 JSON 字符串形式编码数字

⚠️ omitempty 会把零值也省掉：Age: 0、Name: ""、Active: false 全部消失。想区分「零值」和「未设置」必须用指针 *int 或 json.RawMessage。

⚠️ float64 装大整数会丢精度。 订单号、ID 这类用 json.Number 或 json:",string"，别让 9007199254740993 变成 9007199254740992。

⚠️ **json.Marshal vs json.NewEncoder(w).Encode**：前者返回 []byte（一次性分配），后者直接写 io.Writer，适合 HTTP 响应流式输出（末尾自带换行）。

⚠️ time.Time 默认序列化成 RFC 3339（2006-01-02T15:04:05Z07:00）。要和前端约定格式就自定义 MarshalJSON。

四、time 与 errors

用 time.Duration 常量（1500 * time.Millisecond）而不是裸 int；time.Since(start) 走单调时钟，不受系统时间调整影响。

类型 用途 坑
time.Timer 一次性定时 用完 Stop()
time.Ticker 周期性触发 必须 Stop()
time.After(d) 简化版 Timer 循环里会积压

⚠️ for { select { case <-time.After(time.Second): } } 在 Go 1.22 及以前会不断创建新 Timer 且无法回收，长时间运行内存持续上涨。改用 Ticker 或复用一个 Timer。（Go 1.23 起未引用的 Timer 可被 GC 回收。）Ticker 不 Stop() 同样会泄漏，-race 能检测到残留 goroutine。

⚠️ %w 和 %v 的区别：%w 建立错误链（errors.Is/As 可用），%v 只拼字符串（链断了）。一个 %w 只能包一个错误，多个用 errors.Join。

⚠️ errors.As 的第二个参数必须是指向实现了 error 的类型的指针，写错编译能过但永远匹配不上。

五、testing：表驱动 + 子测试 + 竞态

能力 用法
子测试 / 并行 t.Run(name, fn) / t.Parallel()
清理 t.Cleanup(fn)（LIFO 执行）
临时目录 t.TempDir()（自动删除）
测试数据 testdata/ 目录（go 工具会忽略）

⚠️ -race 只报「实际发生的」竞争，不报潜在竞争。CI 里要跑，但它让程序慢 5~20 倍，别在生产开。

⚠️ Go 1.22 之前，for 循环变量在所有迭代间共享，t.Parallel() + 闭包捕获 tt 会全测最后一条。1.22 起每轮独立，但老代码要显式 tt := tt。

⚠️ mock 优先用「接口 + 手写 fake」，别急着上 mock 框架。Go 的接口是隐式实现，手写一个返回固定值的 struct 往往比生成 mock 更清楚。

六、go:embed 与 sync 回顾

⚠️ //go:embed 必须紧贴变量声明，中间不能有空行，且变量必须是包级（不能是函数局部）；嵌入的目录不含 _ 或 . 开头的文件（除非用 all: 前缀）。

sync 类型 场景 取舍
sync.Once 单例初始化 比 init 更可控
sync.WaitGroup 等一组 goroutine Add 要在 go 之前
sync.Mutex 读写都频繁的普通 map 简单直接
sync.Map 读多写少、key 集合稳定 多数场景不如 map + RWMutex

⚠️ sync.Map 不是「更快的 map」。 它是为「键只增不减、读远多于写」的场景设计的，其他场景用普通 map 加锁更快也更省内存。

⚠️ WaitGroup.Add 必须写在 go 语句之前，写在 goroutine 内部会有竞态。

七、net/http 客户端与 log/slog

⚠️ http.DefaultClient 没有超时，一个卡住的请求能永久占用 goroutine。生产环境必须用带 Timeout 的自定义 client。

⚠️ 每次 &http.Client{} 会丢掉连接池，导致大量 TIME_WAIT。Client 要复用，需要改参数就改 Transport。

⚠️ 只 Close 不读完 Body，连接不会回到连接池。要复用得先 io.Copy(io.Discard, resp.Body)。

⚠️ 结构化日志键值对个数必须成对，少一个值不会编译报错，但输出会多一个 !(MISSING)。

⚠️ slog 的 With 返回新 logger，不是原地修改。logger.With(...) 后不接收返回值，等于没加字段。

常见坑清单

  • context 不 defer cancel()，goroutine / 内存泄漏
  • 把可选参数塞进 WithValue
  • 用 string 当 context key，跨包撞车
  • context.TODO 留在生产代码
  • bufio.Writer 忘了 Flush
  • 对外部输入直接 io.ReadAll，没有 LimitReader
  • io.Pipe 只有写没有读，死锁
  • omitempty 把 0 / "" / false 一起省略
  • 用 float64 解大整数 ID，精度丢失
  • 循环里 time.After，Timer 不断积压
  • Ticker 不 Stop()
  • %v 包装错误，errors.Is 再也匹配不上
  • errors.As 第二个参数传值而不是指针
  • t.Parallel() + 闭包捕获循环变量（Go 1.22 前）
  • WaitGroup.Add 写在 goroutine 内部
  • 用 sync.Map 替换所有 map，以为更快
  • http.Client 每次 new，连接池反复重建
  • 不读完 resp.Body 就 Close，连接无法复用
  • //go:embed 和变量声明之间有空行
  • slog.With 不接收返回值
