容器共享宿主内核，隔离的是「看到什么」和「用多少」，不是安全边界。这一篇讲 Capabilities、seccomp、root 用户、镜像供应链和运行时加固。

开场：一句话结论

容器不是虚拟机。 它和宿主共享同一个 Linux 内核，namespace 只改变「进程能看见什么」，cgroups 只限制「进程能用多少」，两者都不阻止进程攻击内核。所以容器的安全 = 默认收紧 + 显式授权 + 镜像可信，缺一不可。

一、隔离的三层与它的边界

机制 管什么 不管什么
namespace 可见性：PID / NET / MNT / UTS / IPC / USER 看不到 ≠ 打不到
cgroups 资源量：CPU / 内存 / PID 数 / IO 不限制系统调用
Capabilities 特权粒度：把 root 拆成 40+ 个开关 不限制已授予的能力
seccomp 系统调用白名单 默认 profile 只挡约 44 个
LSM（AppArmor/SELinux） 强制访问控制 依赖宿主内核启用

关键差别：

⚠️ 共享内核是容器的性能来源，也是它的安全天花板。 内核里任何一个提权漏洞，都可能变成容器逃逸。

⚠️ 内核版本要跟着宿主更新。容器里跑的应用补丁再勤，宿主内核不打补丁照样被 Dirty Pipe、OverlayFS 这类漏洞打穿。

二、Capabilities：默认给了你什么

Docker 默认以 root 身份运行容器主进程，但把 root 的传统特权拆掉，只留一份白名单：

不在这个列表里的（SYS_ADMIN、SYS_PTRACE、NET_ADMIN、SYS_MODULE、SYS_TIME……）默认拿不到。

最小权限的做法

先全丢，再按需加。非 root 进程绑定 80/443 需要 NET_BIND_SERVICE（内核 4.3+ 起 net.ipv4.ip_unprivileged_port_start 可调整，低端口不一定非要它）。

能力 能干什么 危险度
SYS_ADMIN mount、setns、改 cgroup、加载 eBPF…… ⚠️ 等价半个 root，逃逸常用
SYS_PTRACE ptrace 其他进程，注入代码 ⚠️ 可读宿主进程内存
NET_ADMIN 改路由、iptables、网卡 ⚠️ 可做 MITM
SYS_MODULE 加载内核模块 ⚠️ 直接内核代码执行
DAC_READ_SEARCH 绕过文件读权限检查 ⚠️ 可读宿主敏感文件
NET_RAW 原始套接字（ping、ARP） 中，可构造欺骗包

⚠️ SYS_ADMIN 是被滥用最多的能力。 很多教程为了「让容器能挂载/调试」直接 --cap-add=SYS_ADMIN，这基本等于放弃了 Capabilities 防线。

⚠️ --cap-add 只对 root 用户生效的能力，一旦进程用 USER 切成非 root，能力会按 CapBnd/CapPrm 规则被丢弃。别指望「非 root + cap-add」还能 mount。

三、--privileged 等于放弃隔离

--privileged 一次性做了三件事：

  1. 授予全部 Capabilities（含 SYS_ADMIN、SYS_MODULE）
  2. 关闭默认 seccomp 与 AppArmor 限制
  3. 放开对宿主设备的访问（/dev 全给）

⚠️ 特权容器里 mount /dev/sda1 /mnt 就能读宿主磁盘，这是教科书级的逃逸。任何写 --privileged 的 CI 配置都要被 review 拦下。

⚠️ 需要「用 docker 跑 docker」时不要 --privileged，用 rootless 或 docker:dind 的专用方案；实在要用就只加必要的 --device + 能力。

四、seccomp / AppArmor / SELinux

机制 作用层 默认行为
seccomp 系统调用 Docker 自带默认 profile，允许列表，挡约 44 个调用
AppArmor 文件路径 / 网络 / 能力 Ubuntu/Debian 系默认 docker-default profile
SELinux 标签 / 类型强制 RHEL/CentOS 系，容器进程打 container_t 标签

seccomp 默认 profile 挡掉的高危调用（节选）：mount、umount、pivot_root、setns、unshare、ptrace、bpf、kexec_load、init_module、open_by_handle_at、io_uring_*（后者因逃逸漏洞被加进黑名单）。

⚠️ 不要为了排错直接 seccomp=unconfined 就上线。 它把内核攻击面完整暴露，比 --privileged 只差在能力上。

⚠️ AppArmor 与 SELinux 只能二选一，取决于宿主发行版。跨平台镜像别写死某一种的 profile 路径。

五、root 用户与文件系统

容器内默认 uid=0。一旦逃逸，你就是宿主的 root。

做法 说明
USER 指令 镜像层固化，推荐
--user uid:gid 运行时可覆盖，优先级更高
--read-only 根文件系统只读，防篡改
--tmpfs /tmp 只读根下给临时可写目录
--userns=host/private 用户命名空间重映射

⚠️ /etc/passwd 里的用户名不等于宿主用户。 容器内的 node 默认是 uid 1000，宿主的 1000 可能是你的登录账号。写文件到挂载卷时，权限问题十有八九出在这里。

⚠️ --read-only 会让很多程序直接崩（写日志、写 PID 文件、JIT 缓存）。先 --tmpfs 补齐需要写的路径，再开只读。

⚠️ 非 root 用户无法绑定 <1024 端口，除非给 NET_BIND_SERVICE 或调 ip_unprivileged_port_start。换端口往往比加能力更省事。

六、rootless 与 userns-remap

方案 原理 代价
rootless Docker 整个 daemon 跑在非特权用户 + user namespace 不支持部分功能（如 --net=host 受限）
userns-remap 容器内 root 映射为宿主非特权 uid 卷权限、镜像层会变复杂
直接 --user 只改进程 uid 最简单，但不隔离能力

⚠️ user namespace 让「容器内 root」映射到宿主的一个普通 uid。 逃逸出来也只是普通用户，这是纵深防御里性价比很高的一层。

⚠️ userns-remap 开启后，之前直接写宿主目录的卷会突然没权限。已有环境上线前先在小范围验证。

七、镜像供应链安全

基础镜像的取舍：

基础镜像 体积 有 shell 吗 适用
debian:bookworm-slim ~75MB ✅ 需要 apt/调试
alpine:3.20 ~7MB ✅（busybox sh） 体积敏感，注意 musl
gcr.io/distroless/* ~20MB ❌ 生产运行，无包管理器
scratch 0 ❌ 静态编译的 Go/Rust

⚠️ alpine 用 musl libc，不是 glibc。 预编译的 native 扩展（node-gyp 产物、某些 Python wheel）会直接报 not found 或段错误，需要重编译。

⚠️ distroless 没有 shell，kubectl exec 进去什么都干不了。 排查问题只能靠日志和 metrics —— 这是它安全的原因，也是它的痛点。

固定 digest 而非 tag

扫描与签名

⚠️ curl ... | sh 装东西等于把执行权交给对方 CDN。 构建镜像时尤其危险 —— 请用带校验的包管理器或固定版本的二进制 + SHA256 校验。

⚠️ 扫描器报的 CVE 里大量是「基础镜像自带的、你根本没用到的包」。先看有没有可利用路径，再决定是否阻塞发布，否则会陷入无休止的升级。

八、Dockerfile 里的密钥与层历史

ARG 的值会留在镜像历史（docker history --no-trunc）里，ENV 也会进 docker inspect。删除文件的 RUN rm 也不删层。

⚠️ docker inspect 能看到所有 ENV、CMD、挂载、网络配置。 别把密码放环境变量，用 secret 挂载或运行时注入。

⚠️ .dockerignore 忘了写，.env、.git、node_modules 会一起被 COPY . . 打进镜像。上线前 docker history 和 docker save | tar -t 自查一遍。

九、运行时：PID 1、信号与资源限制

容器里的 PID 1 和普通进程不一样：不注册 handler 的 SIGTERM 会被忽略，且 PID 1 不自动回收僵尸进程。

参数 作用 注意
--memory=512m 硬限制，超了 OOM Kill 容器内看到的总内存会变
--memory-swap 内存+交换总量 设置不当会掩盖泄漏
--cpus=1.5 CPU 配额 等价 --cpu-quota/--cpu-period
--cpu-shares=512 相对权重，不是上限 只在争抢时生效
--pids-limit=200 限制进程数 防 fork 炸弹

⚠️ --cpu-shares 不是限制，是权重。 宿主空闲时它照样能用满所有核。要硬上限用 --cpus 或 cpuset。

⚠️ JVM、Node、Python 默认按宿主内存算堆大小，容器里不设 --memory 之外的 -Xmx/--max-old-space-size，很容易被 OOM Kill。

⚠️ 被 OOM Kill 的容器退出码是 137（128+9）。看到 137 先查内存，不要先怀疑代码。

常见坑清单

  • 以为容器 = 虚拟机，把它当安全边界用
  • 生产用 --privileged，或图省事 --cap-add=SYS_ADMIN
  • 排错时 --security-opt seccomp=unconfined 之后忘了改回来
  • 镜像里默认 root，且没有任何 USER 指令
  • 密码写进 ENV / ARG / RUN，留在镜像历史里
  • 用 ARG 传 token 并在 RUN 里用，以为删除就没事
  • 忘了 .dockerignore，把 .env、.git 打进镜像
  • 用 nginx:latest 这类可变 tag，没有固定 digest
  • 构建时 curl ... | sh 装工具，没校验
  • 容器不写 --read-only，应用被篡改也没察觉
  • 挂了宿主目录，权限对不上就 chmod 777
  • CMD 用 shell 形式，SIGTERM 收不到，只能被 kill -9
  • 没开 --init，进程池里全是僵尸进程
  • 只设 --cpu-shares 当限流，以为能限死 CPU
  • 不设 --pids-limit，一个 fork 炸弹拖垮宿主
  • JVM / Node 不调堆参数，容器被 OOM Kill 报 137
  • 从不扫描镜像，基础镜像的 CVE 长期不修
  • 宿主内核长期不打补丁，容器内应用再新也没用
  • 把宿主 docker.sock 挂进容器（等于给容器宿主 root）
  • 没有审计基线，不知道容器实际跑了哪些特权配置
