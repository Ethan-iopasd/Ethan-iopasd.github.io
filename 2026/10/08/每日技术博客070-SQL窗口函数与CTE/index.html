五 窗口函数与 CTE 本篇

开场：一句话结论

窗口函数在 WHERE / GROUP BY 之后、ORDER BY 之前执行，所以它算出的列不能出现在 WHERE 里。想要「按排名过滤」只能套一层子查询或 CTE。

一、语法骨架

子句 作用
PARTITION BY 把结果集切成互不重叠的窗口；不写 = 整个结果集一个窗口
ORDER BY 窗口内排序，决定累计/排名方向
frame 当前行参与计算的「行范围」，`ROWS

⚠️ OVER() 括号不能省。SUM(x) OVER 是语法错误；SUM(x) 是聚合，语义完全不同。

⚠️ 窗口函数只能出现在 SELECT 列表和 ORDER BY 中。放 WHERE / GROUP BY / HAVING 里都报错。

二、排名函数

score ROW_NUMBER RANK DENSE_RANK NTILE(4)
100 1 1 1 1
100 2 1 1 1
90 3 3 2 2
80 4 4 3 2
70 5 5 4 3
函数 并列处理 后续序号 用途
ROW_NUMBER 任意打破 连续 去重、分页（结果唯一）
RANK 同名次 跳号（1,1,3） 竞赛排名
DENSE_RANK 同名次 不跳号（1,1,2） 分级
NTILE(n) 均分 n 桶 — 分位数、抽样

⚠️ ROW_NUMBER 在并列值上结果不确定：不加第二排序键时同分行的序号可能每次查询都不同。要稳定必须 ORDER BY score DESC, id ASC。

三、LAG / LEAD / FIRST_VALUE / LAST_VALUE

函数 默认 frame 下的行为
LAG(col, n, default) 前 n 行；越界返回 default（不写则 NULL）
LEAD(col, n, default) 后 n 行；越界同上
FIRST_VALUE 窗口第一行
LAST_VALUE ⚠️ 当前行，不是分区最后一行

⚠️ 窗口函数最著名的坑：有 ORDER BY 时默认 frame 是 RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW，右边界就是当前行，所以 LAST_VALUE 返回当前行自己。要拿分区末值必须显式写 ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING。

⚠️ LAG 默认 n=1、default=NULL。算环比时**第一行必然 NULL**，不做 COALESCE 会污染下游计算。且 LAG 不会跨 PARTITION 取值。

四、SUM() OVER 与 frame 语义

关键字 语义
ROWS 按物理行数取范围
RANGE 按 ORDER BY 值的范围取，并列值算同一组
n PRECEDING 前 n 行 / 值差 ≤ n

⚠️ ROWS 和 RANGE 在有并列值时结果不同。SUM(x) OVER (ORDER BY k)（RANGE）会把 k 相同的行一起累加；ROWS 则逐行。做累计求和时不确定就**显式写 ROWS**。

⚠️ 没有 ORDER BY 时默认 frame 是整个分区，所以 SUM(x) OVER (PARTITION BY g) 得到的是分区总和，不是累计值。RANGE 的 n PRECEDING 还要求排序列是数值或日期，字符串列直接报错。

五、窗口函数 vs GROUP BY

维度 GROUP BY 窗口函数
输出行数 每组 1 行 与输入行数相同
能否保留明细列 ❌（除非聚合） ✅
能否在结果里比较「行 vs 组」 ❌ ✅
能否用于 WHERE 用 HAVING ❌ 只能外层过滤

⚠️ 窗口函数的别名也不能在同一个 SELECT 的其他表达式里引用（SELECT ROW_NUMBER() OVER (...) AS rn, rn + 1 报错）—— SELECT 列表是同时求值的。用 CTE 包一层。

⚠️ QUALIFY 是专门解决这个问题的子句（ANSI SQL:2023，Snowflake / BigQuery / DuckDB / Teradata 支持），语义等价于外层 WHERE。PostgreSQL 与 MySQL 目前不支持。

七、CTE：物化还是内联

数据库 默认行为 强制物化 强制内联
PostgreSQL 12+ 非递归 CTE 默认内联（仅被引用一次时） WITH x AS MATERIALIZED (...) WITH x AS NOT MATERIALIZED (...)
PostgreSQL < 12 总是物化 — —
MySQL 8.0 优化器决定（可合并则合并） ... /*+ MATERIALIZE */ ... /*+ MERGE */
MySQL < 8.0 不支持 CTE — —

⚠️ PostgreSQL 12 之前 CTE 一律物化，这是「CTE 当优化栅栏」说法的来源。12+ 起非递归 CTE 默认可能被内联，旧文章的结论不能直接套用。

⚠️ CTE 被引用多次时物化通常是好事（算一次用多次）；只引用一次时物化是纯浪费。优化器判断随统计信息变化，性能敏感处显式写 MATERIALIZED / NOT MATERIALIZED 更可控。

⚠️ 递归 CTE 不能内联，一定物化。且 MySQL 8 默认 cte_max_recursion_depth = 1000，超过报错，需 SET SESSION cte_max_recursion_depth = 100000。

八、递归 CTE

结构固定三段：锚成员 + UNION [ALL] + 递归成员。

要素 说明
终止条件 递归成员返回 0 行时停止
UNION ALL vs UNION UNION 会去重，能防环但更慢
防死循环 加 WHERE lvl < N，或用 PostgreSQL 14+ 的 CYCLE 子句（CYCLE id SET is_cycle USING path）
列类型 锚成员与递归成员对应列类型必须一致

⚠️ 数据里有环（A→B→A）时 UNION ALL 会无限递归直到内存/深度耗尽。必须自己加深度上限或用 UNION。

九、实战模板

9.1 去重：每组取最新一条 / Top-N

⚠️ 排序键必须唯一（created_at 并列时加 id），否则「最新一条」不确定。这是 ROW_NUMBER 去重的唯一正确姿势。要「并列都算」就换 RANK，代价是每组可能超过 N 行。

9.2 连续登录天数（gaps-and-islands）

思路：登录日 - 行号 得到「岛编号」，同岛内该值恒定。

9.3 会话切分（同思路）

⚠️ 日期相减语法因数据库而异：PostgreSQL 用 date - INTERVAL '1 day' * rn；MySQL 用 DATE_SUB(login_date, INTERVAL rn DAY)；SQL Server 用 DATEADD(day, -rn, login_date)。别照抄。

⚠️ 必须先 DISTINCT / GROUP BY 去重，否则同一天登录两次会把行号打乱，岛编号全错。会话切分的 SUM(...) OVER (ORDER BY ts ROWS ...) 也必须带 ROWS —— 用默认 RANGE 时 ts 相同的行会一起累加，编号跳号。

十、性能注意

点 说明
排序开销 PARTITION BY + ORDER BY 基本必然触发排序，EXPLAIN 里看 WindowAgg / Using filesort
索引 (partition_col, order_col) 联合索引能帮优化器省一次排序
frame 宽度 RANGE UNBOUNDED PRECEDING 累积值需 O(N) 状态；ROWS n PRECEDING 只需 O(n)
多窗口 多个窗口定义若 PARTITION/ORDER 相同可合并；不同则各排一次
CTE 引用次数 引用 2 次以上才值得物化

⚠️ EXPLAIN 里出现 Sort Method: external merge Disk 说明排序落到磁盘了，通常是 work_mem 太小或窗口太宽 —— 加索引或调 work_mem。窗口函数不能在 WHERE 之前剪枝，对大表先用子查询滤掉无关行再开窗，比直接对全表开窗快得多。

常见坑清单

  • 窗口函数写进 WHERE / HAVING / GROUP BY
  • 在同一个 SELECT 里引用窗口函数别名
  • 以为 OVER 可以不带括号
  • ROW_NUMBER 排序键不唯一，去重结果不确定
  • 混用 RANK 和 DENSE_RANK，并列后序号跳错
  • LAST_VALUE 不加 UNBOUNDED FOLLOWING，拿到当前行
  • LAG / LEAD 结果不做 NULL 处理
  • 以为 LAG 会跨分区取值
  • 累计求和不区分 ROWS 与 RANGE，并列值被合并
  • 没有 ORDER BY 时以为 SUM() OVER 是累计（实为分区总和）
  • RANGE n PRECEDING 用在字符串排序列上
  • 以为窗口函数会像 GROUP BY 一样减少行数
  • 以为 PostgreSQL 所有版本 CTE 都物化（12 起默认内联）
  • CTE 只引用一次还强行物化
  • 递归 CTE 不设深度上限，数据有环时无限递归
  • MySQL 递归深度超 cte_max_recursion_depth（默认 1000）
  • gaps-and-islands 前不去重，行号被同日重复记录打乱
  • 日期加减语法跨库照抄
  • 大表先开窗再过滤，排序落盘
  • 以为 QUALIFY 到处都能用（PG / MySQL 不支持）
