开场：一句话结论

单元测试验证逻辑，集成测试验证接线，E2E 验证用户旅程 —— 越往上越贵越脆，所以只测关键路径。

一、集成测试测什么

集成测试的核心是真实依赖之间的交互：SQL 能不能跑、事务边界对不对、序列化是否匹配、消息能不能收发。

依赖 单元测试里 集成测试里
数据库 Mock 仓库 真实 DB（容器）
缓存 Mock client 真实 Redis
消息队列 Mock producer 真实 Kafka/RabbitMQ
外部 HTTP Mock server WireMock / 沙箱

⚠️ 集成测试最容易漏的是事务与并发：@Transactional 没生效、连接池耗尽、死锁，只在真实 DB 下才暴露。
⚠️ Mock 仓库永远「成功」，因此永远测不出 ORM 映射错误、字段类型不匹配、SQL 语法问题。

二、用 Testcontainers 起真实依赖

优点 代价
与生产同版本同引擎 需要 Docker / 容器运行时
环境一致，可复现 启动慢（首次拉镜像）
容器随测试销毁，天然隔离 CI 上需要缓存镜像、加机器资源

⚠️ Testcontainers 依赖 Docker daemon；CI 里没有容器运行时就直接失败，要提前确认 runner 支持。
⚠️ 镜像别写 latest，用固定 tag（如 postgres:16-alpine），否则某天拉到的版本变了，测试随机挂。
⚠️ 容器是静态单例（static）时复用可提速，但测试间数据要自己清理；否则测试互相污染。

三、内存替代品的取舍（H2 / SQLite ≠ PostgreSQL）

维度 真实 PostgreSQL H2 兼容模式
类型系统 jsonb、array、uuid、interval 部分缺失或语义不同
SQL 方言 ILIKE、ON CONFLICT、窗口函数 常不支持或行为不同
并发/锁 真实 MVCC 语义 完全不同
约束/触发器 完整 支持有限

⚠️ 别拿 H2 测 PostgreSQL 特有语法：测试全绿、上线全红是最典型的事故。
⚠️ 内存库跑得快，但它的价值上限就是「SQL 语法大致能过」—— 涉及类型、并发、方言就必须用真库。
⚠️ SQLite 与 PostgreSQL 的类型亲和性、事务隔离、NULL 排序都不同，跨库替代风险更高。

四、数据库测试的隔离策略

策略 做法 速度 代价
事务回滚 每个测试包在事务里，结束回滚 快 测不了跨事务提交、异步写
重建 Schema 每个测试前清库/重建 慢 最干净，适合小库
随机 Schema 名 每个测试用独立 schema 中 连接与迁移管理复杂
容器/快照复用 起一次容器 + 快照回滚 快 依赖容器能力

⚠️ @Transactional 回滚会让异步任务、消息发送、缓存写入看不到未提交数据 —— 这类测试必须用重建或随机 schema。
⚠️ 回滚方案下自增 ID 不重置，依赖固定 ID 的断言会随执行顺序变化。

五、契约测试（Consumer-Driven Contract）

微服务里用契约替代部分 E2E：消费者定义期望，提供者验证实现。

维度 E2E 契约测试
覆盖 全链路真实调用 单条接口契约
速度 分钟级 秒级
环境 需要全套服务在线 只需提供者自身
定位 集成回归 接口不兼容

⚠️ 契约测试不验证业务正确性，只验证「接口字段/格式是否满足消费者期望」。
⚠️ 契约要版本化并绑定分支，否则提供者验证的是过期的旧契约。

六、E2E / UI 测试工具对比

工具 语言/生态 特点 主要短板
Playwright 多语言（TS/Java/Python/.NET） 多浏览器、自动等待、并行、trace 回放 生态较新
Cypress JS/TS 开发者体验好、调试强 早期仅 Chromium 系，多标签/跨域受限
Selenium 多语言 最老、W3C WebDriver 标准、生态最广 需自建等待与重试，易写 flaky

选择器策略（从稳到脆）：

选择器 稳定性
data-testid ✅ 最稳，与样式/结构解耦
ARIA role / label ✅ 兼顾可访问性
文本内容 ⚠️ 文案改动即挂
CSS class / 层级路径 ⚠️ 样式重构即挂
XPath 绝对路径 ❌ 最脆

⚠️ 不要用 sleep 等元素出现。Playwright 的 auto-waiting 与 Cypress 的重试机制会在断言前自动轮询。
⚠️ 用 CSS class 当选择器，等于把测试绑死在样式实现上 —— 换皮肤就全线飘红。

七、flaky 的成因与治理

成因 表现 治理
硬编码等待 有时快有时慢 用自动等待 / 显式等待条件
共享测试数据 并行时互相踩 每个测试独立数据
测试顺序依赖 单独跑绿、一起跑红 消除共享状态
动画/过渡 元素未稳定就点 禁用动画、等待稳定
时间/时区 跨天、跨时区失败 固定时钟与时区
网络抖动 偶发超时 重试 + 合理的超时配置

⚠️ retry 是止痛药，不是解药。CI 里开 3 次重试会把真 bug 也一起吞掉。
⚠️ flaky 测试要登记并限期修复，长期挂着会让团队对红色失去敏感度。

八、Page Object 与它的反模式

正确用法 反模式
封装页面操作 封装断言（测试失去表达力）
返回下一个 Page Object 塞入业务逻辑
只暴露用户可见行为 暴露内部 DOM 细节

⚠️ Page Object 里写断言，测试就读不出「在验证什么」。
⚠️ 过度抽象成「上帝 Page Object」后，改一个选择器要动半个测试套件。

九、E2E 成本与「该测多少」

成本项 说明
时长 分钟级，串行会拖垮 CI
环境 需要完整部署 + 种子数据
维护 UI 一变就要改，脆

只测关键用户旅程：登录、下单、支付、注册 —— 这些路径挂了业务就挂了。

⚠️ 不要用 E2E 覆盖所有表单校验与边界值 —— 那是单元/集成测试的活。
⚠️ E2E 数量应以「覆盖关键旅程」为准，而不是「覆盖率」。

十、测试环境与数据

问题 做法
种子数据 版本化脚本 + 幂等，测试前重建
环境漂移 用 IaC 管理环境，禁止手改
生产数据 脱敏后再用，禁止明文导入
数据隔离 每套测试独立租户/命名空间

⚠️ 直接拿生产数据做测试，等于把 PII 泄漏到测试环境 —— 合规红线。
⚠️ 环境「手工改过一次」是漂移的源头，之后所有「本地能过、CI 不能过」都源于此。

十一、测试分层组合策略

层级 占比（参考） 关注
单元 多 逻辑、边界、算法
集成 中 DB / 缓存 / 消息 / HTTP
契约 少量 服务间接口兼容
E2E 极少 关键旅程

⚠️ 占比没有标准答案，取决于架构与业务风险，不要照抄别人的数字。
⚠️ 判定标准是「哪一层能最快发现这类 bug」，而不是「哪一层看起来更高级」。

十二、性能测试

工具 特点 脚本形态
k6 Go 实现，JS 写脚本，CI 友好 JS
JMeter 老牌，GUI + 分布式压测 XML
Locust Python 写用户行为，易扩展 Python
指标 含义
RPS / QPS 每秒请求数
p95 / p99 95% / 99% 请求的耗时上界（别只看平均值）
错误率 非 2xx / 超时占比
并发数 同时压的虚拟用户

⚠️ 平均值会掩盖长尾：p99 飙到 2s、平均仍是 50ms 是常见现象。
⚠️ 压测必须在接近生产的配置下做，否则结论没有参考价值。

十三、混沌测试与 CI 里的测试阶段

混沌测试：主动注入故障（杀进程、断网、延迟），验证系统的韧性而非正确性。

手段 验证目标
杀 Pod 自愈与重启策略
注入网络延迟/丢包 超时与重试
依赖不可用 降级与熔断

CI 组织原则：

  • 快慢分离：单元测试先跑（秒级），集成/E2E 后跑
  • 失败即停：单元挂了不必再跑 E2E
  • 并行分片：E2E 按文件/旅程分片并行
  • 重试 flaky：只对已知 flaky 用例，且登记追踪

⚠️ 混沌测试不要在未做可观测性的系统上做 —— 出了故障你也看不出原因。
⚠️ 无脑重试所有失败用例，会把真实的回归掩盖成「重试后通过」。

常见坑清单

  • 用 Mock 仓库做集成测试，永远测不出 SQL/ORM 问题
  • 集成测试忽略事务边界与连接池耗尽
  • Testcontainers 在无 Docker 的 CI runner 上直接失败
  • 容器镜像用 latest，版本漂移导致随机挂
  • 静态容器复用但不清数据，测试互相污染
  • 拿 H2 测 PostgreSQL 专有语法（ON CONFLICT、jsonb）
  • 用 SQLite 替代 PostgreSQL，忽略隔离级别与类型差异
  • @Transactional 回滚下测异步/消息，看不到未提交数据
  • 回滚方案下依赖固定自增 ID 做断言
  • 契约不版本化，提供者验证的是过期契约
  • 把契约测试当成业务正确性测试
  • E2E 用 CSS class / XPath 绝对路径当选择器
  • 用 sleep 等待元素出现
  • flaky 用例只靠 retry 掩盖，从不修复
  • Page Object 里写断言或业务逻辑
  • 用 E2E 覆盖所有表单校验与边界值
  • 测试环境手工改动，造成环境漂移
  • 生产数据不脱敏直接导入测试环境
  • 性能测试只看平均耗时，忽略 p95/p99
  • 在无观测能力的系统上做混沌测试
