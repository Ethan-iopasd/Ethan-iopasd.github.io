开场：一句话结论

滚动更新的正确性由「探针 + 优雅停机 + PDB」三者共同保证 —— 探针配错会把好 Pod 反复杀掉，terminationGracePeriodSeconds 配错会让请求打到已停止的容器，缺 PDB 会在更新时把副本打到零。

一、Deployment 关键字段

字段 默认值 作用
replicas 1 期望副本数
revisionHistoryLimit 10 保留多少个旧 ReplicaSet（回滚用）
progressDeadlineSeconds 600 更新多久没进展就标记 ProgressDeadlineExceeded
minReadySeconds 0 Pod Ready 后再等多久才算「可用」
strategy.type RollingUpdate 另一种是 Recreate
maxSurge 25% 更新期间最多超出 replicas 的 Pod 数
maxUnavailable 25% 更新期间最多不可用的 Pod 数
策略 行为 可用性 适合
RollingUpdate 逐批替换，新旧共存，峰值 replicas + maxSurge 全程有副本服务 无状态服务
Recreate 先删光所有 Pod 再建新的 更新期间完全不可用 有独占资源、不能新旧并存

⚠️ maxSurge 和 maxUnavailable 不能同时为 0，API server 会直接拒绝创建，
因为没有任何副本可以被替换，更新永远推进不了。

二、rollout 命令与回滚

命令 用途
rollout status 阻塞等待更新完成，CI 里必加
rollout history 看历史 revision（CHANGE-CAUSE 常为空）
rollout undo 回滚到上一个 revision
rollout restart 换 ConfigMap / Secret 后常用

⚠️ rollout history 的 CHANGE-CAUSE 默认是 <none>，Deployment 不会自动记录原因。
**必须 kubectl annotate ... kubernetes.io/change-cause**，否则回滚时面对一串
revision 号根本不知道哪个是哪个。

三、三种探针的职责

探针 回答的问题 失败后果 生命周期
startupProbe 应用启动完了吗 达到 failureThreshold 后杀掉容器重启 只在启动阶段
livenessProbe 应用还活着吗 重启容器 全程
readinessProbe 能接流量了吗 从 Service EndpointSlice 摘除，不重启 全程

四种检查机制（每个探针只能选一种）：

机制 成功判定 备注
httpGet 200 <= code < 400 最常用
tcpSocket 端口能连上 连接后立刻断开也算成功
exec 命令退出码为 0 每次会 fork 进程，Pod 密度高时开销大
grpc 健康检查返回 SERVING 需应用实现 gRPC Health Checking

⚠️ liveness 探针不等待 readiness 成功（官方原话：Liveness probes do not wait for
readiness probes to succeed）。启动慢的服务不配 startupProbe 时，会出现
「liveness 超时 → 重启 → 又没启动完 → 又超时」的无限重启循环。

⚠️ liveness 探针指向依赖外部组件的接口（如「能连上数据库」）是最常见的误配。
数据库抖动 30 秒 → 所有 Pod 同时被判死 → 全体重启 → 雪崩。
liveness 只检查「进程自身是否卡死」，依赖健康放 readiness。

四、探针参数与默认值

参数 默认 最小 说明
initialDelaySeconds 0 0 容器启动后等多久才开始探测
periodSeconds 10 1 探测间隔
timeoutSeconds 1 1 单次探测超时
successThreshold 1 1 连续成功几次算成功
failureThreshold 3 1 连续失败几次算失败
terminationGracePeriodSeconds 继承 Pod（默认 30） 1 探针级宽限期（v1.28+ Stable）

⚠️ liveness 和 startup 的 successThreshold 必须为 1，写成 2 会被 API server
拒绝；readiness 才允许 >1，且不能设 terminationGracePeriodSeconds。

⚠️ timeoutSeconds 默认只有 1 秒。应用在 GC 停顿或高负载下响应 1.5 秒很常见，
于是探针连续失败被误判为「死」。这个默认值是生产事故的高频来源。

五、resources、QoS 与 OOMKilled

QoS 等级 判定条件 驱逐优先级
Guaranteed 每个容器的 CPU 和内存都设了 requests == limits 最低（最后被驱逐）
Burstable 至少一个容器设了 request 或 limit，但不满足 Guaranteed 中
BestEffort 所有容器都没设 requests 和 limits 最高（最先被驱逐）
资源 超 limit 的后果
CPU（可压缩） CFS 限流，延迟升高，container_cpu_cfs_throttled 飙高，进程不死
内存（不可压缩） 直接 OOMKilled

⚠️ Exit Code 137 不等于 OOMKilled。liveness 探针失败后 kubelet 发的也是 SIGKILL，
必须看 lastState.terminated.reason 才能区分。Java 容器的 -Xmx 若没考虑堆外内存
（Metaspace、Direct Buffer、线程栈），JVM 总内存超 cgroup limit 一样会被杀，
**-Xmx 应设成 limit 的 60%~75%**。

六、HPA 与 metrics-server

⚠️ HPA 必须依赖 metrics-server。没装时 kubectl get hpa 显示
TARGETS: <unknown>/70%，副本数永远不动。

七、PodDisruptionBudget

⚠️ PDB 只管自愿中断（节点 drain、kubectl evict），不管滚动更新。
滚动更新的可用性由 maxUnavailable 控制，两者各管一段，别混淆。

八、优雅停机：preStop + 宽限期

停机顺序：Pod 标记 Terminating → EndpointSlice 标记 not ready（kube-proxy / Ingress 异步更新）→ 并行执行 preStop → 结束后 kubelet 发 SIGTERM → 超宽限期则 SIGKILL。

⚠️ Endpoint 摘除与 SIGTERM 是并行的，且传播有延迟。应用收到 SIGTERM 就立刻退出时，
那些已按旧 Endpoint 发过来的请求会全部连接失败。**preStop 里 sleep 几秒是标准解法**，
用来覆盖 Endpoint 传播窗口。

九、StatefulSet vs Deployment

维度 Deployment StatefulSet
Pod 名称 随机后缀 web-7d9f-x2k 有序固定 db-0 db-1
网络标识 无稳定域名 配合 Headless Service 有稳定 DNS
启动顺序 并行，无序 按序号串行（OrderedReady）
存储 共享 PVC 或不用 volumeClaimTemplates 每 Pod 一个独立 PVC
扩缩容 / 更新 无顺序保证 / 滚动更新 缩容从最大序号开始；默认从最大序号倒序更新
适合 无状态服务 数据库、消息队列、有状态中间件

十、Job 与 CronJob

字段 作用
concurrencyPolicy: Forbid 上次没跑完就跳过本次（默认 Allow，会并发）
startingDeadlineSeconds 错过调度窗口超过这个时间就记为 Missed
backoffLimit 失败重试次数
activeDeadlineSeconds 整个 Job 的最长运行时间，超时终止

⚠️ CronJob 的 concurrencyPolicy 默认是 Allow。任务跑超过一个周期时会同时有
多个 Job 在跑，抢同一份资源。默认值几乎从来不是你想要的。

十一、滚动更新期间 Service 断流的排查顺序

现象 最可能的原因
Running 但 READY 0/1 readiness 探针没过
Endpoint 列表为空 readiness 一直失败，或 Service selector 不匹配
Exit 137 + reason: OOMKilled 内存 limit 太小
Exit 137 + 非 OOM liveness 杀的重启
ProgressDeadlineExceeded 新 Pod 一直没 Ready，或镜像拉不下来

⚠️ 「Pod 是 Running 但 READY 0/1」是断流的第一大原因。Running 只表示容器进程起来了，
Ready 才是「可以接流量」。只看 STATUS 列会漏掉这个区别。

常见坑清单

  • maxSurge 与 maxUnavailable 同时为 0，Deployment 创建失败
  • minReadySeconds 保持默认 0，把「刚 Ready 就崩」的版本推完
  • revisionHistoryLimit: 0，rollout undo 无法使用
  • 启动慢的服务只配 liveness，不配 startupProbe，陷入无限重启
  • liveness 探针里检查数据库连通性，依赖抖动引发全体重启雪崩
  • timeoutSeconds 用默认 1 秒，GC 停顿即被误判为死
  • liveness/startup 探针设 successThreshold > 1，被 API server 拒绝
  • 只设 limits 不设 requests，调度器按 limit 挑节点
  • 认为 CPU 超 limit 会被杀（实际是限流，内存才会被杀）
  • 把 Exit Code 137 一律当成 OOMKilled
  • 没装 metrics-server，却排查 HPA 为什么不扩缩容
  • Pod 没设 requests.cpu，HPA 算不出利用率
  • PDB.minAvailable 等于 replicas，节点 drain 永久卡住
  • preStop 里不 sleep，停机瞬间请求全部连接失败
  • terminationGracePeriodSeconds 小于 preStop + 应用排空时间
  • entrypoint 用 sh -c 导致 SIGTERM 传不到应用，每次都被 SIGKILL
  • 删 StatefulSet 后没删 PVC，重装时复用脏数据卷
