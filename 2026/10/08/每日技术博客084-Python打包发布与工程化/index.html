开场：一句话结论

pyproject.toml 是唯一的配置入口（PEP 518 + PEP 621），setup.py / setup.cfg 只作为兼容保留；构建产物是 wheel 和 sdist，锁文件才是可复现的保证。

一、pyproject.toml 是唯一入口

标准 作用
PEP 518 定义 [build-system]，声明构建时依赖
PEP 517 定义构建后端接口（build_wheel / build_sdist）
PEP 621 定义 [project] 表，元数据的标准写法
文件 现状
setup.py 仍被 setuptools 支持，但只该留「构建时动态逻辑」
setup.cfg 声明式元数据可写，但新项目没理由再用
pyproject.toml ✅ 元数据 + 工具配置统一入口

⚠️ 只要目录里存在 setup.py，很多工具会优先走 legacy 流程，绕过 PEP 517。迁移时该删就删干净。

⚠️ license = { text = "MIT" } 是旧写法，PEP 639 起推荐 license = "MIT" + license-files。后端支持不一，跨后端时先用兼容写法。

二、构建后端与项目布局

后端 配置风格 适合
setuptools pyproject.toml + 少量 setup.py 老项目、需要 C 扩展
hatchling 纯 pyproject.toml，默认认 src 布局 新库，配置最少
poetry-core 跟 Poetry 生态绑定 用 Poetry 管依赖的项目
flit-core 极简，要求模块名 == 包名 单文件小库
pdm-backend 支持动态版本、多后端 PDM 生态

⚠️ build-backend 一旦发布过版本就别轻易换。不同后端对文件包含规则、动态字段的支持不同，换后端经常导致新版本 wheel 里少文件。

布局 直接 pytest 时 风险
扁平（myapp/ 在根） 导入的是工作目录里的源码 测试通过，装到环境里跑不起来
src 布局 必须 pip install -e . 才能导入 强制验证「打包后能用」

⚠️ 扁平布局的经典事故：pyproject.toml 里漏配子包，本地测试全绿，pip install 后 ImportError。src 布局就是让这个问题在测试阶段暴露。

三、版本号与依赖声明

⚠️ 用 setuptools-scm / hatch-vcs 时，从 PyPI 下载 sdist 再构建没有 git 历史，会报找不到版本。所以必须在构建时预生成 _version.py。

写法 含义 备注
>=1.2,<2.0 明确区间 最可控
~=1.2.3 >=1.2.3, ==1.2.* 兼容版本，不改次要号
==1.2.3 精确锁定 库里不该这么写
>=1.2 无上界 ⚠️ 迟早被上游破坏

⚠️ 库（library）的 dependencies 不要写 == 精确版本，会把冲突全部转嫁给使用者。应用（application）才用锁文件锁死。

锁文件的意义

锁文件 生态 内容
uv.lock uv 全量解析结果 + hash
poetry.lock Poetry 同上
requirements.txt（pip-compile 生成） pip-tools 带 hash 的固定版本
requirements.txt（手写） —— ⚠️ 通常没锁传递依赖

⚠️ 生产环境绝不装未锁定的依赖。pip install flask 今天和明天的解析结果可能不同，一个补丁版本就能把线上打挂。

四、构建 wheel 与 sdist

产物 本质 安装时
*.whl 一个 zip 包 解压即用，不执行构建
*.tar.gz 源码包（sdist） 需要本地构建，可能编译

⚠️ sdist 里漏文件是最常见的发布事故：别人从 PyPI 装就是坏的，而你本地（从源码装）永远复现不了。

⚠️ 验证方式：python -m build 后在干净的虚拟环境里从 sdist 安装再跑测试。本地直接 pip install . 走的是源码目录，查不出漏文件。

五、发布、入口点与包数据

凭据放 ~/.pypirc 的 [testpypi] / [pypi] 段，username = __token__，password 填 API token。

⚠️ PyPI 上的版本号发布后不可撤销（只能 yank，不能覆盖）。先在 TestPyPI 演练，检查 README 渲染和文件清单。

⚠️ main() 的返回值会作为进程退出码，返回 None 等价于 0，别靠异常栈当退出码。

⚠️ 用 __file__ 拼路径读数据文件在打包成 zipapp / 单文件可执行后必然失效，importlib.resources（3.9+）才可靠。

⚠️ __all__ 只影响 from myapp import *，不阻止别人导入内部模块。真正的边界靠文档与 _internal/ 命名约定。

六、单文件可执行与 Docker

方案 产物 启动速度 适用
PyInstaller 单文件 / 目录 慢（自解压） 分发给非技术用户
Nuitka 编译为 C 的二进制 快 性能 + 保护源码
shiv / pex zipapp / pex 单文件 中 有 Python 环境的内网机器
Docker 镜像 中 服务端首选

⚠️ PyInstaller 单文件模式每次启动都要解压到临时目录，冷启动可能慢几秒，且杀软常误报。别指望它是「轻量分发」。

做法 效果
多阶段构建 编译工具链留在 builder 阶段
pip install --no-cache-dir 不留 pip 缓存
uv sync --frozen 按锁文件精确安装
slim / alpine 更小，但 alpine 的 musl 会踩 C 扩展坑

⚠️ 不要把 gcc、build-essential 留在最终镜像里。多阶段构建的意义就是「装依赖需要编译器，运行不需要」。

⚠️ alpine 用 musl libc，很多预编译 wheel（numpy、psycopg2）没有对应产物，会退化成源码编译并失败。除非确定依赖链干净，否则用 slim。

七、质量工具链与 CI

工具 职责 关系
ruff lint + format + import 排序 已覆盖 flake8 / isort / 大部分 black 场景
black 格式化 可与 ruff 二选一
isort import 排序 ruff 的 I 规则已替代
mypy / pyright 类型检查 严格度可调，pyright 更快

⚠️ ruff 的 format 与 black 不要同时跑，格式规则有细微差异，会来回改。选一个。

⚠️ pre-commit 默认只在暂存文件上跑，hook 环境的依赖是独立的。mypy 必须把被检查模块的依赖写进 additional_dependencies，否则报找不到实现。

CI 阶段 内容
lint ruff check + ruff format --check
type mypy / pyright
test pytest -n auto --cov
build python -m build，检查产物内容
publish tag 触发，twine upload

⚠️ pytest 在 CI 里必须从已安装的包测试（src 布局 + pip install -e .），否则测的是工作目录源码，sdist 漏文件 CI 也发现不了。

常见坑清单

  • dependencies 里写 == 精确版本，把冲突转嫁给使用者
  • 库的依赖写 >=x 无上界，被上游破坏性更新打挂
  • 生产环境装未锁定的依赖，解析结果每天都可能变
  • 锁文件没进版本控制，CI 无法复现
  • uv sync 不加 --frozen，CI 里悄悄改了依赖
  • 保留 setup.py 导致部分工具走 legacy 流程
  • 用扁平布局，本地测试通过但装完 ImportError
  • setuptools 没配 packages.find，子包没打进 wheel
  • sdist 漏文件（MANIFEST.in / include 没配全）
  • 只在源码目录验证，从不从 sdist 装一遍
  • 用 hatch-vcs 但没生成版本文件，从 sdist 构建时找不到版本
  • 用 __file__ 读包内数据文件，打包成 zipapp 后失效
  • license = { text = "MIT" } 旧写法与新标准混用
  • PyPI 版本发布后想覆盖，只能 yank
  • 从不在 TestPyPI 演练，直接传正式仓库
  • ruff format 和 black 同时跑，来回改格式
  • pre-commit 的 mypy 没写 additional_dependencies，误报找不到实现
  • Docker 最终镜像里留着 gcc / build-essential
  • alpine 基础镜像踩 musl 缺 wheel，退化成源码编译
  • PyInstaller 单文件模式冷启动慢，被当成轻量分发
