一 流水线设计与制品管理 本篇

开场：一句话结论

CI 是「每次提交都验证」，持续交付是「随时可发但由人点」，持续部署是「自动发到生产」 —— 三者差的是最后一步是否自动。

概念 做什么 最后一步
CI（持续集成） 每次 push/PR 自动 lint + build + test ——
持续交付（Continuous Delivery） CI + 自动部署到 staging + 制品就绪 人工审批后上生产
持续部署（Continuous Deployment） 持续交付 + 自动上生产 全自动

⚠️ 「持续交付」和「持续部署」英文缩写都是 CD，必须区分。 团队说「我们做 CD」时，先问一句：生产是自动发还是点按钮发 —— 这决定了回滚、审批、灰度整套设计。

一、流水线阶段划分

阶段 内容 失败即停
lint / 静态检查 ESLint、gofmt、ruff、格式与类型检查 ✅
build 编译、打包、构建镜像 ✅
test 单测 → 集成测试 → E2E ✅
package 产出制品（镜像 / 包 / 二进制） ✅
deploy 部署到 dev → staging → prod ✅
优化手段 说明
阶段并行 无依赖的 job 同时跑（lint / unit / 类型检查）
快速失败 fail-fast: true，一个挂了取消其余
DAG 依赖 用 needs 显式声明前后关系，而不是串成一条线
拆分 E2E E2E 只在 merge 到 main 或 nightly 跑，PR 上跑子集

⚠️ 不要把 lint 放在最后。 一个拼写错误要等 20 分钟 E2E 跑完才报出来，是最浪费人时间的反模式 —— 按「成本从低到高」排。同时 PR 上的流水线要快（< 10 分钟），否则开发者会绕过它；重型测试（全量 E2E、性能压测、跨平台构建）放到 main 或 nightly。

二、缓存策略

缓存类型 缓存什么 典型 key
依赖缓存 node_modules / ~/.m2 / pip wheel / go mod hash(lockfile)
构建缓存 编译产物、Bazel/Turborepo 远程缓存 hash(源码 + 工具链版本)
Docker 层缓存 镜像层 buildx + registry cache

⚠️ 缓存 key 必须包含「会影响结果的输入」。 只按分支名做 key，会让 A 分支的依赖被 B 分支复用，产生缓存污染 —— 表现为「本地能跑、CI 报奇怪的错」。同时 restore-keys 是前缀回退，用错会把旧环境的缓存捞回来；跨 OS / 跨架构（amd64 vs arm64）的缓存不能共用，key 里必须带 runner.os 和架构。

⚠️ 缓存默认不可写回（只读），只有命中缓存的那个 job 结束后才保存；多 job 并发写同一个 key 会互相覆盖。构建缓存要区分「读缓存」和「写缓存」角色。

三、制品管理：不可变 + 按 commit sha

反模式 问题
用 latest 标签部署 不知道线上跑的是哪个 commit，无法回滚
每个环境重新构建 环境间产物不同，测过的不等于发的
标签策略 说明
app:<git-sha> 主标识，唯一且不可变
app:main / app:latest 只作「最新」提示，绝不用来部署

⚠️ 「构建一次，处处部署」（build once, deploy many）。 每个环境重新构建会让「staging 测过的制品」和「prod 部署的制品」不是同一个二进制，测试结果失去意义。另外 latest 是可变标签，push 新版本会覆盖旧版本 —— 用它部署等于「部署时才知道跑的是什么」。制品仓库要开不可变策略（ECR immutable tags、Harbor 不可变 tag），允许覆盖 tag 的话，「同一个版本」在不同时间可能是不同内容。

四、GitHub Actions 核心概念

概念 含义
workflow 一个 .github/workflows/*.yml 文件
event / trigger on: 触发条件（push / pull_request / schedule / workflow_dispatch）
job 一组 step，默认并行，跑在独立 runner 上
step 一个 run 命令或一个 uses action
runner 执行机（ubuntu-latest / 自托管）
needs 声明 job 依赖，形成 DAG
matrix 参数化组合（多 OS × 多语言版本）
secret 加密变量，日志自动打码
cache / artifact 跨 job 传缓存 / 传文件

⚠️ artifact 和 cache 用途不同：artifact 传「构建产物」给下游 job（有保留期、按 run 隔离），cache 是「加速依赖下载」。别用 cache 传构建产物 —— cache 会被 evict、key 匹配有回退语义，产物会莫名其妙变旧。另外 upload-artifact@v4 与 v3 不兼容：v4 起同一个 workflow 内 artifact 名字必须唯一，且不再支持 GHES，跨 workflow 共享要用 download-artifact@v4 或外部制品库。

⚠️ secrets 在 pull_request 事件里对 fork 不可用（这是安全设计），别在 PR 里跑需要密钥的部署；用 pull_request_target 要极其小心，它会在目标仓库上下文运行，若又 checkout 了 PR 代码就是 RCE 入口。**concurrency 也必须配**：不配的话同一分支连推 5 次就起 5 条流水线，既浪费资源又可能让部署乱序。

五、分支策略、环境分层与审批

触发 跑什么
pull_request lint + unit + build（不部署）
merge 到 main 全量测试 + 构建镜像 + 部署 dev
tag / release 部署 staging → 人工审批 → prod
schedule（nightly） 全量 E2E、依赖扫描、性能基线
环境 用途 数据
dev / staging / prod 开发自测 / 预发 / 生产 造数据 → 脱敏近似生产 → 真实数据

⚠️ staging 和 prod 的差异越大，staging 通过就越没意义（配置、依赖版本、中间件、数据规模都要对齐，否则「staging 全绿」只是幻觉）。生产部署必须有人工审批门或至少可暂停（GitHub Actions 用 environment + required reviewers），这不是形式主义，是给「回滚窗口」留决策时间。另外别用「长期存在的 develop 分支」做集成分支（GitFlow 那套）—— 分支存活越久，合并冲突越大、集成越晚，主干开发（trunk-based）+ 短命特性分支 + 特性开关才是主流。

六、密钥管理：不要明文，尽量免密钥

反模式 风险
密钥写进 workflow YAML 提交进仓库，永久留在历史里
长期 AK/SK 存 CI secret 泄露即长期沦陷，且难轮换
方案 说明
CI secret / 环境变量 基础做法，日志自动打码
OIDC 联邦身份 CI 从云厂商换短期凭据，无需长期密钥
Vault / Secrets Manager 集中管理 + 动态凭据 + 审计
短期 token（GITHUB_TOKEN） 每次 run 自动签发、自动过期

⚠️ permissions 默认可能是「读写全部」（老仓库），必须显式最小化，尤其 id-token: write 只给需要的 job —— 拿到 OIDC token 就能换云上凭据。OIDC 的信任策略要限定 sub（仓库 + 分支 + 环境），例如只允许 repo:org/app:ref:refs/heads/main，写成 repo:org/app:* 等于任何分支都能换到生产凭据。另外一旦密钥进了 git 历史，改文件没用，必须轮换（历史提交、fork、CI 缓存里都还在），同时开 Secret Scanning / gitleaks 在提交时拦截。

七、数据库迁移在流水线里的位置

顺序问题：代码先上还是迁移先上？

顺序 风险
先迁移后发代码 新代码没上，老代码遇到新 schema —— 只要向后兼容就安全
先发代码后迁移 新代码依赖新列，但列还不存在 → 直接报错

⚠️ 迁移必须向后兼容，且要能被旧代码容忍。「删列」「改列类型」「加非空无默认值的列」都是破坏性变更 —— 部署到一半时新老代码同时在线，任何一边挂都会导致事故。同时迁移和代码发布要解耦成独立阶段，迁移本身必须幂等、可重入（在 CI 里跑 migrate 前先确认「重复执行不会炸」）。大表迁移会锁表（MySQL 加索引、改列在旧版本会阻塞写入），生产上要用 pt-online-schema-change / gh-ost 或原生在线 DDL，并从流水线里分离出去单独执行。

八、发布与回滚策略

策略 做法 回滚成本 资源成本
滚动更新 逐批替换实例 中（再滚回去） 低
蓝绿 新环境全量起来 → 切流量 极低（切回旧环境） 高（双倍）
金丝雀 先给 1% 流量 → 观察 → 逐步放量 低（切断金丝雀） 低
特性开关 代码上线但功能关闭，按开关放量 最低（关开关） 低
回滚方式 说明
镜像版本回退 把部署引用换回上一个 sha —— 最快、最可靠
特性开关关闭 不重新部署，秒级生效
数据库回滚 ⚠️ 最难，所以迁移必须向前兼容，尽量不回滚 schema

⚠️ 「能部署」不等于「能回滚」。 回滚路径要和发布路径一样被测试 —— 很多团队半年不回滚一次，真出事时发现回滚脚本早就坏了。而且数据库没法「回滚」，只能「向前修复」，所以发布策略的前提是 schema 变更永远向后兼容，回滚代码时老代码仍能跑在新 schema 上。金丝雀要选对观察指标并提前定义回滚阈值，「看着不对再回滚」在事故现场等于没有策略。

九、流水线性能优化与质量门禁

优化 手段
只跑受影响的服务 monorepo 用路径过滤 / Turborepo / Bazel 依赖图
并发 matrix 并行、job 并行、分片测试（shard）
缓存 依赖缓存 + 构建缓存 + Docker 层缓存
跳过冗余 文档变更不跑全量测试（paths-ignore）
质量门禁 工具示例
测试覆盖率阈值 codecov、覆盖率低于阈值直接失败
SAST CodeQL、Semgrep、SonarQube
依赖漏洞扫描 Dependabot、Trivy、npm audit、Snyk
镜像扫描 / 许可证合规 Trivy、Grype / license-checker、FOSSA

⚠️ 覆盖率是「必要不充分」的门禁 —— 100% 不代表没 bug，但大幅下降必须拦下来；阈值用「不低于基线」而不是拍脑袋的固定数字。扫描结果要能「阻断」而不只是「报告」：只在 PR 里贴评论、不影响合并的扫描等于没做，设 severity >= high 直接 fail。门禁也不能只加不减 —— 越多流水线越慢，开发者越会找绕过方式，定期 review 每条门禁的命中率和误报率，把没用的删掉。

十、可观测性接入

构建时把 commit sha / 版本号注入镜像标签与 VERSION 文件；部署时打 deploy 事件到监控；运行时日志 / 指标 / Trace 带 version 标签；发布后自动跑冒烟测试，指标劣化自动回滚。

⚠️ 制品里必须带版本信息（--build-arg GIT_SHA）。线上出问题时，第一步是确认「跑的是哪个版本」—— 没这个信息，排查从第一步就卡住。部署事件也要打进监控，把「发布时刻」画在指标图上，否则看到错误率尖刺时，要花十几分钟才能想起来「刚才发了版」。

常见坑清单

  • 混淆持续交付与持续部署，生产自动发却没审批和回滚预案
  • lint 放在流水线最后；PR 流水线超过 10 分钟
  • 缓存 key 不含 lockfile 哈希，产生缓存污染
  • 跨 OS / 跨架构共用同一份缓存；用 cache 传构建产物
  • 用 latest 标签部署，无法追溯与回滚
  • 每个环境重新构建，测过的不等于发的；制品仓库允许覆盖 tag
  • 没配 concurrency，同分支并发跑多条流水线
  • 在 PR 里跑需要 secrets 的部署（fork 拿不到 secret）
  • 用 pull_request_target 却 checkout 并执行 PR 代码
  • 没显式最小化 permissions，尤其 id-token: write
  • 密钥明文进 workflow YAML 或 echo 到日志
  • 密钥进了 git 历史只删文件不轮换
  • OIDC 信任策略用通配 sub，任何分支都能换生产凭据
  • 破坏性数据库迁移（删列 / 改类型 / 非空无默认值）
  • 迁移与代码发布耦合在同一阶段，不可重入
  • 大表迁移直接在流水线里跑，锁表影响生产
  • staging 与 prod 差异过大，预发通过无意义
  • 长期存在的 develop 分支做集成，合并地狱
  • 只测发布路径，不测回滚路径
  • 金丝雀没提前定义回滚阈值和观察指标
  • 制品里不带版本信息；部署事件不打进监控
  • 质量门禁只报告不阻断；或门禁只加不减
