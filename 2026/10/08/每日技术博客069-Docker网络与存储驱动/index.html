开场：一句话结论

永远用自定义 bridge 网络而不是默认 bridge —— 默认 bridge 没有容器名 DNS 解析，只能靠已废弃的 --link 或手写 /etc/hosts；存储侧则是 volume 给数据、bind mount 给配置、tmpfs 给敏感临时文件，三者不要混用。

一、五种网络驱动

驱动 隔离性 性能 跨主机 典型场景
bridge 中（独立 netns + 软件网桥） 中（NAT 开销） ❌ 单机默认选择
host 无（共享宿主 netns） 最高（无 NAT） ❌ 高性能、端口固定的服务
none 最高（只有 lo） — ❌ 完全离线任务、自定义网络栈
overlay 中（VXLAN 封装） 中低（封装开销） ✅ Swarm / 多主机集群
macvlan 中（独立 MAC） 高（无 NAT） ✅（同二层） 需要真实 IP、被外部设备直连
ipvlan 中（共享 MAC） 高 ✅ 类似 macvlan，受交换机 MAC 表限制时用

⚠️ macvlan 在云主机上经常不可用 —— 虚拟网卡通常禁止混杂模式，且对单网卡的 MAC
数量有限制。AWS / 阿里云上优先考虑 ipvlan 或干脆用 host 网络。

⚠️ --network host 在 Linux 上会让 -p 完全失效（Docker 只打印一条 warning，
不报错）。容器直接占用宿主端口，多个容器想用同一端口会冲突。Docker Desktop 上
host 网络长期受限，别指望它和 Linux 行为一致。

二、默认 bridge vs 自定义 bridge（头号坑）

维度 默认 bridge 自定义 bridge
容器名 DNS 解析 ❌ 不支持 ✅ 内嵌 DNS（127.0.0.11）
容器间互访 只能用 IP，或 --link（已废弃） 直接用容器名 / 别名
隔离性 所有未指定 --network 的容器都在里面 按网络隔离
运行中挂载/卸载 ❌ 必须重建容器 ✅ docker network connect/disconnect
配置粒度 全局一份，改完要重启 daemon 每个网络独立配置（MTU、iptables 规则）
环境变量共享 --link 会注入（历史行为） 不支持（用 volume / compose 传）
能解析的名字 说明
容器名 默认生效
--network-alias 指定的别名 一个容器可挂多个别名
--hostname 在自定义网络里也会注册
Compose 的 service 名 Compose 会自动建网络并注册
container_name 只有当它在同一个自定义网络里才生效

⚠️ 这是 Docker 最高频的坑：docker run --name db postgres 之后，另一个容器
ping db 不通，不是网络坏了，是默认 bridge 不提供名字解析。养成习惯：
所有 docker run 都显式带 --network。

三、端口映射与 EXPOSE 的真实语义

概念 写法 是否真的打开端口
暴露（expose） Dockerfile EXPOSE 8080 ❌ 只是元数据 / 文档
发布（publish） docker run -p 8080:80 ✅ 建立映射
自动发布 docker run -P ✅ 随机宿主端口映射到所有 EXPOSE 端口

⚠️ EXPOSE 不会发布端口，也不能让宿主机访问容器。官方文档原话：
The EXPOSE instruction does not actually publish the port.
它只影响 docker run -P 和 docker inspect 的元数据，以及提供文档价值。

⚠️ -p 8080:80 默认绑 0.0.0.0，等于暴露到公网。只想本机访问必须写
-p 127.0.0.1:8080:80。云主机上不加 IP 前缀直接暴露数据库端口是常见事故。

⚠️ 同一自定义网络内的容器互访不需要 -p —— 网络内所有端口彼此可见。
-p 只影响「从宿主机外部能否访问」。

四、iptables 与 docker-proxy

组件 作用
DOCKER 链（nat 表） 做 DNAT，把宿主端口流量转到容器 IP:端口
DOCKER-USER 链 留给用户自定义规则的钩子，优先于 DOCKER 链
docker-proxy 用户态转发进程，处理宿主机本地回环访问等场景
userland-proxy daemon 配置，默认 true；设 false 后纯靠 iptables

⚠️ 防火墙（firewalld / ufw）规则常被 Docker 的 iptables 链绕过 —— Docker 直接往
nat 表的 DOCKER 链插规则，优先级高于 firewalld 的 INPUT 链。想限制容器端口访问，
规则要写在 DOCKER-USER 链里。

五、容器访问宿主机

平台 写法 说明
Docker Desktop（mac/Win） host.docker.internal 内置解析，开箱可用
Linux --add-host=host.docker.internal:host-gateway Docker 20.10+
任意 宿主 docker0 的 IP（默认 172.17.0.1） 硬编码，换环境就废
任意 --network host 直接用 127.0.0.1

⚠️ **Linux 上没有内置的 host.docker.internal**（Docker Desktop 才有），直接写会报
Could not resolve host，必须显式 --add-host ...:host-gateway。

⚠️ 宿主服务若只监听 127.0.0.1，容器无论用哪个地址都连不上 —— 流量到达宿主网卡后
目标地址是宿主 IP，不匹配回环监听。要让服务监听 0.0.0.0，或用 --network host。

六、跨主机 overlay 与 VXLAN

概念 说明
VXLAN 把二层帧封装进 UDP，默认端口 4789
VNI 网络标识，每个 overlay 网络一个
--attachable 允许独立容器（非 Swarm service）接入
数据存储 Swarm 模式内置；独立使用需 Consul / Etcd / ZooKeeper
--opt encrypted 在 VXLAN 之上再加一层 IPSec 加密（有 CPU 开销）

七、存储驱动与分层

驱动 分层机制 状态 说明
overlay2 OverlayFS 默认，推荐 内核 4.0+，性能好、稳定
overlay OverlayFS（旧） 已废弃 层数受限，用 overlay2
aufs AUFS 已废弃 老 Ubuntu 的历史产物
btrfs Btrfs 子卷 可用 需要 /var/lib/docker 在 Btrfs 上
zfs ZFS 数据集 可用 需要 ZFS，内存开销大
devicemapper 瘦置备 已废弃 RHEL 7 时代，不要再选
vfs 逐层完整复制 可用 无 CoW，极慢极大，只用于测试

⚠️ 容器可写层是「写时复制」的。改一个大文件（比如日志）会把整个文件复制到可写层，
容器体积和 I/O 都会暴涨。所有需要持久化或高频写的路径必须挂 volume。

八、三种挂载方式与 --mount vs -v

维度 volume bind mount tmpfs
存储位置 /var/lib/docker/volumes/（Docker 管理） 宿主任意路径 内存
可移植性 ✅ 跨平台、可被 volume driver 接管 ❌ 依赖宿主目录结构 ❌ Linux only
备份 docker volume 命令 + 临时容器 直接用宿主工具 不可备份
权限 由 Docker 初始化（可继承镜像内权限） 宿主权限说了算 由 tmpfs-mode 控制
性能 好（Linux 上走原生 fs） 好，但 macOS/Win 上经 gRPC-FUSE 很慢 最快
适合 数据库数据、上传文件 配置文件、源码热挂载、开发调试 密钥、session、临时缓存
被 docker rm -v 影响 匿名卷会删，具名卷不删 不受影响 不受影响
差异点 -v --mount
语法 冒号分隔的位置参数 key=value，可读性好
宿主路径不存在 自动创建目录（以 root 属主） 报错退出
文件名挂载 宿主文件不存在时也会创建成目录 明确报错
挂载选项 :ro :rw :z :Z :cached readonly、volume-opt=
tmpfs 参数 只能用 --tmpfs tmpfs-size / tmpfs-mode 直接写
推荐度 短、快，交互式敲命令方便 脚本 / Compose 里推荐

⚠️ macOS / Windows 上的 bind mount 性能极差（走虚拟化层文件共享），大项目
node_modules 挂进去，构建能慢十倍。数据放 volume，只有必须实时同步的源码才用
bind mount。

九、具名卷、匿名卷、备份与空间回收

类型 生命周期 命名 排查难度
具名卷 显式 docker volume rm 才删 可读的名字 低
匿名卷 docker rm -v 时删除，否则残留 64 位随机 ID 高

⚠️ 数据库的 volume 不能直接 tar 备份。运行中的 MySQL / PostgreSQL 数据文件处于
不一致状态，恢复出来可能起不来。要么 mysqldump / pg_dump，要么先停容器再打包。
打包时要 -C /data .，写成 tar czf x.tar /data 会带上 /data 这一层路径。

⚠️ docker system prune -a --volumes 是清库级操作，会删掉所有未运行容器引用的卷。
容器停着但数据还要留的场景，数据就没了。执行前先 docker system df -v 看清每一项。

⚠️ 磁盘被占满但 docker system df 显示不多时，检查 /var/lib/docker/overlay2 与
/var/log/containers（日志文件不受 prune 管理）。容器 stdout 日志由
--log-opt max-size 控制，默认无上限。

十、容器内 DNS 与 /etc/hosts

文件 来源 可否持久修改
/etc/hosts Docker 启动时生成（含容器名、--add-host） ❌ 重启即重置
/etc/resolv.conf 自定义网络为 127.0.0.11；默认 bridge 为宿主 DNS ❌ 重启即重置
/etc/hostname 容器 ID 或 --hostname ❌

⚠️ --dns 只在默认 bridge / 自定义网络下生效。用了 --network host 时容器直接读
宿主的 /etc/resolv.conf，--dns 被忽略。

⚠️ 自定义网络下 127.0.0.11 是 Docker 的内嵌 DNS，它会把解析不了的域名转发给宿主
DNS。宿主 DNS 配错时表现为「容器名能解析、外网域名不能解析」，排查时别只盯着 Docker 网络。

常见坑清单

  • 用默认 bridge 网络，容器之间无法用容器名互访
  • 还在用已废弃的 --link，容器重建后别名失效
  • 以为 EXPOSE 会发布端口，宿主机访问不到却查不出原因
  • -p 8080:80 不带 IP 前缀，服务被暴露到公网
  • --network host 下写 -p，以为端口映射生效（实际被忽略）
  • 用 firewalld/ufw 限制容器端口，被 Docker 的 DOCKER 链绕过
  • Linux 上直接用 host.docker.internal，报无法解析
  • 宿主服务只监听 127.0.0.1，容器连不上
  • 云主机上强行用 macvlan，被虚拟网卡限制卡住
  • overlay 网络的 VXLAN 封装导致大包不通（MTU 未调整）
  • macOS 上把大目录 bind mount 进容器，构建慢十倍
  • tmpfs 不设 size，吃光宿主内存
  • 空 volume 挂到代码目录，遮住镜像里已构建好的文件
  • 用匿名卷，docker rm 不带 -v，磁盘被随机 ID 占满
  • 直接 tar 备份运行中的数据库卷，恢复后起不来
  • docker system prune -a --volumes 一把梭，删掉还需要的数据卷
  • 容器日志无上限增长，占满磁盘却不被 prune 清理
  • Compose 里写 - data:/data 以为是 bind mount，实际是具名卷
