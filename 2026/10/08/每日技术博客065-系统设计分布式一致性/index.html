开场：一句话结论

CAP 说的是「网络分区发生时，只能在 C 和 A 之间二选一」，不是「三选二」；共识算法只在「多数派存活」时才能工作；微服务里分布式事务能不用就不用。

概念 一句话
CAP 分区发生时，一致性与可用性二选一
PACELC 分区时选 A/C；无分区时也要在延迟 L 和一致性 C 之间选
共识（Consensus） 让多个节点对「同一份日志的顺序」达成一致
分布式事务 让跨服务的多个写操作「全成功或全回滚」

一、CAP 的准确表述与 PACELC

CAP 常被误读成「三选二」，正确表述是：

当网络分区（P）发生时，系统只能在一致性（C）和可用性（A）之间选一个。 P 不是可选项 —— 分布式系统里分区一定会发生。

选择 行为 例子
CP 拒绝服务也不返回旧数据 etcd、ZooKeeper、HBase
AP 返回可能过期的数据也要可用 Cassandra、DynamoDB（默认）、Eureka

PACELC 补上了「没有分区时」的情况：

系统 分区时 平时
DynamoDB / Cassandra PA EL（低延迟优先）
BigTable / HBase PC EC（一致优先）
MongoDB PA EC

⚠️ CAP 里的 C 是「线性一致」，不是「ACID 的 C」。 线性一致要求「写成功后，任何后续读都能立刻看到」，这比「事务不破坏约束」严格得多。拿 CAP 的 C 去套数据库事务，是最常见的误用。

⚠️ CAP 描述的是「分区期间的取舍」，不是系统的永久属性。 一个系统可以在分区时牺牲一致性、平时给强一致 —— 把它归类成「CP 系统」或「AP 系统」本身就过于简化。

二、一致性谱系与 BASE

从强到弱：

级别 保证 代价
线性一致（Linearizable） 所有操作像在一个单机上按实时顺序执行 最高，分区时不可用
顺序一致（Sequential） 所有节点看到的操作顺序一致，但不要求与真实时间一致 高
因果一致（Causal） 有因果关系的操作有序，无关操作可乱序 中
最终一致（Eventual） 停止写入后，最终所有副本一致 低，中间有窗口

BASE 是对 ACID 的「反着来」：

缩写 含义
BA（Basically Available） 基本可用，允许降级、限流
S（Soft state） 软状态，中间状态允许存在
E（Eventually consistent） 最终一致

⚠️ 「最终一致」的「最终」没有时间上界。 它只保证「不再写入后一定会收敛」，不保证 1 秒还是 1 小时。业务上如果要求「下单后 100ms 内库存可见」，最终一致是不够的 —— 得在链路里显式等待或补偿。

⚠️ 因果一致是很多业务的实际下限。 用户「发了评论 → 立刻刷新看到自己的评论」是因果一致需求，用纯最终一致会出现「自己看不到自己刚写的东西」，体验上等同于 bug。

三、分布式事务：2PC / 3PC / TCC / SAGA

2PC（两阶段提交）

问题 说明
同步阻塞 Prepare 后参与者一直持锁等 Commit，期间资源全锁死
协调者单点 协调者挂掉，参与者永远等不到第二阶段，一直阻塞
数据不一致 部分参与者收到 Commit、部分没收到 → 副本不一致

3PC（三阶段提交）

在 2PC 前插入 CanCommit 阶段（预询问，不锁资源），并给参与者加超时。缓解阻塞，但仍无法解决分区下的不一致，且多一轮 RTT。

TCC（Try-Confirm-Cancel）

特点 说明
业务层补偿 每个服务自己实现 Try/Confirm/Cancel 三个接口
不依赖数据库锁 靠「预留」而非「长事务锁」
要求 Confirm / Cancel 必须幂等，且要能处理空回滚、悬挂

SAGA

把长事务拆成 N 个本地事务，失败时反向执行补偿：

模式 说明
编排（Orchestration） 一个中心协调器依次调各服务，逻辑集中、好排查
协同（Choreography） 各服务监听事件自行触发下一步，无中心，耦合低但难追踪

⚠️ SAGA 没有隔离性（no isolation）。 中间状态对外可见 —— T3 失败时，T2 的改动已经被人读到了。必须靠语义锁（状态字段 PENDING）、业务容忍或读隔离来兜底。

⚠️ 补偿不等于回滚。 「退款」和「没扣款」不是同一件事（可能已产生手续费、已发积分）。补偿动作本身也是业务操作，会失败、需要重试、必须幂等。

⚠️ 2PC 在微服务里几乎不用，因为跨服务的 Prepare 会把锁和连接池全占住，一个慢服务拖死整条链路。它更适合单库多数据源这种同机房、低延迟、同事务管理器的场景。

四、最终一致的三种落地方案

方案 机制 一致性 复杂度 适用
本地消息表 业务写入 + 消息记录同一个本地事务，再由投递器发送 最终一致 低 自研、无 MQ 事务能力
事务消息 MQ 支持半消息：先发半消息，本地事务成功后确认投递 最终一致 中 RocketMQ 等支持事务消息的 MQ
最大努力通知 失败后按退避策略反复通知对端，对端保证幂等 最弱 最低 通知外部系统、回调

⚠️ 本地消息表的关键是「业务写和消息写在同一事务里」。 分两次提交就会出现「业务成功但消息丢了」或「消息发了但业务回滚了」，那就不叫可靠消息。

⚠️ 投递器必须保证「至少一次」投递 + 消费端幂等。 想做到「恰好一次」是不可能的 —— 投递器在「发出去」和「标记已发」之间崩溃，就会重复投递。所以消费端必须去重。

五、共识：Paxos、Raft 与 Quorum

共识要解决的：多个节点对同一份日志的内容和顺序达成一致，且多数派存活时仍能推进。

算法 特点
Paxos 理论奠基，正确但难懂、难实现完整版（Multi-Paxos 描述不清）
Raft 把共识拆成选举 / 日志复制 / 安全性三块，可理解性优先，工业界主流
ZAB ZooKeeper 用，类似 Raft 但顺序不同

Raft 三个子问题：

子问题 机制
Leader 选举 随机超时（150–300ms）触发投票，得票过半成为 Leader
日志复制 Leader 收请求 → 追加日志 → 复制到多数派 → 提交并返回
任期（term） 单调递增的逻辑时钟，每轮选举 +1，用于拒绝过期 Leader
概念 含义
多数派 Quorum 任何决策需要 ⌊N/2⌋ + 1 个节点同意，两个多数派必然相交
容错数 容忍 f 个节点故障需 2f+1 个节点（3 节点容 1，5 节点容 2）
W + R > N 读 Quorum + 写 Quorum 之和 > 副本数，保证读写有交集

⚠️ 共识需要「多数派存活」，不是「任意节点存活」。 5 节点集群挂 3 个就彻底不可写 —— 这是 CP 的代价，不是 bug。节点数用奇数（3/5/7），偶数不增加容错却多一个可能脑裂的节点。

⚠️ W + R > N 保证的是「读能读到最新写入」，不保证事务隔离。 而且它要求副本集固定 —— 节点数变化时要重新计算，否则交集假设失效。

⚠️ Raft 的日志提交只认「当前任期的多数派」。老任期的日志即使被复制到多数派，也不能直接提交，必须由新 Leader 复制一条当前任期的日志后连带提交（Raft 论文 Figure 8 的经典坑）。

六、冲突与时间

时钟问题

不能依赖各机器的物理时间戳来给事件排序。 NTP 校时会跳变，不同机器时钟有漂移，同一毫秒内的事件无法定序。

时钟 用途
物理时钟（wall clock） 只适合记录日志时间，不能用于定序
单调时钟（monotonic） 测时长，不受 NTP 跳变影响
逻辑时钟（Lamport） 给事件一个偏序，a → b 则 L(a) < L(b)
向量时钟（Vector Clock） 能判断「因果先后」还是「并发冲突」

冲突解决

策略 说明 缺点
LWW（Last-Write-Wins） 时间戳大的赢 依赖时钟，静默丢数据
版本向量 + 应用合并 检测到并发冲突交业务处理 复杂
CRDT 数据结构本身可交换、可合并，天然收敛 只适用特定类型

⚠️ LWW 会静默丢更新。 两节点并发写同一 key，时钟快的一方赢，另一方直接被丢弃且无任何提示。只要业务不能接受丢写，就不能用 LWW。

⚠️ 物理时钟回拨是真实存在的：NTP 同步、虚拟机迁移、闰秒都会让时间倒退。任何用 timestamp 做「最新版本判断」的地方都要问一句「时钟回拨了会怎样」。

七、脑裂与 fencing token

脑裂：分区导致出现两个 Leader，两边都接受写入 → 数据分叉。

方案 说明
fencing token 存储侧校验单调递增的令牌，拒绝过期 Leader
STONITH 直接断电/隔离旧主（硬件层）
租约（Lease） Leader 持有带超时的租约，过期即失去资格

⚠️ 光靠「心跳超时判死」是不够的。 老 Leader 可能只是因为 GC 停顿被误判，恢复后仍以为自己在线。必须有存储侧的 fencing 校验，否则脑裂照样写坏数据。

⚠️ 租约依赖时钟。 时钟漂移会让租约「提前失效」或「延后失效」，所以租约时长要留足安全边界，且要能容忍一定漂移。

八、ZooKeeper / etcd 与工程取舍

系统 共识 典型用途
ZooKeeper ZAB 选主、分布式锁、配置中心、Kafka 旧版元数据
etcd Raft K8s 元数据、服务发现、配置中心、选主
Consul Raft 服务发现 + KV + 健康检查

微服务下的现实取舍：

场景 建议
能拆成「单库事务」 就拆，别上分布式事务
跨服务但可异步 本地消息表 / 事务消息 + 幂等
跨服务且必须同步强一致 重新设计边界，尽量合并成一个服务
跨服务且要补偿 SAGA / TCC
真需要强一致 2PC，但限定在同机房、少量参与者

⚠️ 幂等是分布式的基础设施，不是可选项。 只要涉及重试、消息、补偿，就必须有幂等键（业务唯一 id / 请求 id）和去重表。没有幂等，任何「至少一次」投递都会产生重复数据。

⚠️ 别把 ZooKeeper / etcd 当数据库用。 它们适合小数据量、读多写少的协调场景；大量写会打爆 Raft 日志。配置中心里存几百 KB 的大 JSON 也是常见误用。

⚠️ 「分布式事务」通常是边界划错的信号。 如果一次业务操作要跨 4 个服务写库，多半是领域边界没拆对。先怀疑设计，再考虑事务方案。

常见坑清单

  • 把 CAP 当成「三选二」，或把 CAP 的 C 当成 ACID 的 C
  • 以为「最终一致」有确定的时间上界
  • 用纯最终一致做「自己写的自己立刻能看到」的需求
  • 在微服务里上 2PC，慢服务拖死整条链路
  • 用 3PC 以为能解决分区下的一致性问题
  • TCC 的 Confirm / Cancel 不幂等，或没处理空回滚与悬挂
  • SAGA 忽略「没有隔离性」，中间状态被下游读到
  • 把补偿当成回滚，以为「退款 = 没扣款」
  • 本地消息表把业务写和消息写分成两个事务
  • 消费端不做幂等，重试就产生重复数据
  • 追求「恰好一次」投递（不可能，只能至少一次 + 幂等）
  • 共识集群用偶数节点，或以为挂一半还能写
  • 用 W + R > N 当隔离性保证，或副本数变化后不重算
  • Raft 里直接提交老任期的日志（Figure 8 坑）
  • 用各机器物理时间戳给事件排序
  • 用 LWW 解决冲突，静默丢更新
  • 忽略时钟回拨，用 timestamp 判断「最新版本」
  • 只靠心跳超时判死，没有 fencing token
  • 租约时长不留时钟漂移的安全边界
  • 把 ZooKeeper / etcd 当数据库或大对象存储用
  • 业务边界没拆对就上分布式事务
