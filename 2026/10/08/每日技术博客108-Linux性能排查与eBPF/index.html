开场：一句话结论

排查顺序永远是 先量化再猜测：先用 uptime / vmstat 定瓶颈类型，再按 CPU → 内存 → 磁盘 → 网络 → 应用逐层下钻，别一上来就重启。

一、USE 方法与黄金顺序

USE 方法：对每一种资源检查三个指标。

指标 含义 典型命令
Utilization 使用率（多忙） mpstat / iostat -x / sar -n DEV
Saturation 饱和度（排队多长） vmstat 的 r / b、iostat 的 aqu-sz
Errors 错误计数 ip -s link、dmesg、/proc/net/*

逐层下钻顺序：CPU → 内存 → 磁盘 IO → 网络 → 应用，每一层先看全局再看单进程。

⚠️ load average 高不等于 CPU 忙 —— 它统计的是「运行中 + 不可中断睡眠（D 状态）」的进程数，等 IO 的进程也算进去。CPU 空闲但 load 高，通常是磁盘或网络卡住。

⚠️ 单看 top 的第一屏会骗人。top 是采样平均，瞬时抖动看不到；要动态观察必须 top -d 1 或换 vmstat 1 看趋势。

二、CPU

top 的 CPU 行含义：

列 含义 异常信号
us 用户态 高 = 应用计算重
sy 内核态 高 = 系统调用 / 锁 / 网络重
wa IO 等待 高 = 磁盘瓶颈
si / hi 软 / 硬中断 高 = 网卡中断、中断亲和问题
st 被虚拟化抢占 高 = 宿主机超卖
成因 触发场景
自愿切换 进程主动阻塞等锁 / IO / sleep
非自愿切换 时间片用尽被抢占（CPU 争抢）

⚠️ st（steal）高是宿主机问题，不是你应用的锅 —— 虚拟机被其他租户抢了 CPU，调优应用没用，只能换规格或投诉。

⚠️ wa 高说明 CPU 在等 IO，此时把 CPU 加满没用；要去看磁盘（下一节）。**si 高**常见于高 PPS 网络或单队列网卡，检查中断亲和 irqbalance。

⚠️ 上下文切换 cs 过高（vmstat 的 cs 列）常见两类：锁竞争（自愿）与核数不足（非自愿）。用 pidstat -w 区分，别盲目扩核。

三、内存

free -h 关键列：

列 含义
free 完全空闲（低不代表不够）
buff/cache 页缓存，可回收
available 真正可用的估算值，看这个

⚠️ free 很低不等于内存不足。Linux 会把空闲内存拿去做页缓存（buff/cache），要回收时立刻释放；判断依据是 available。

⚠️ vmstat 的 si / so 非零就是换页，是性能灾难 —— 内存不足时内核把页换到 swap，磁盘延迟比内存高几个数量级。此时 available 通常也偏低。

⚠️ 别在生产随手 echo 3 > /proc/sys/vm/drop_caches —— 它会清空页缓存，之后所有读都回源磁盘，短期性能骤降；它只适合压测前制造一致环境。

⚠️ OOM Killer 杀进程的顺序由 oom_score 决定，oom_score_adj 可调（-1000 到 1000）。容器里被杀往往是 limits 太低，先看 cgroup 限制。

四、磁盘 IO

iostat -xz 关键列：

列 含义
r/s / w/s 每秒读 / 写次数（IOPS）
await 平均 IO 延迟（ms），含排队
aqu-sz 平均队列长度（饱和度的直接指标）
%util 设备有 IO 在飞的时间占比

⚠️ %util 接近 100% 不等于磁盘饱和。现代 SSD / NVMe 多队列并发，%util 只是「有过 IO 的时间比例」；**判断饱和要看 aqu-sz 和 await**。

⚠️ df 与 du 结果不一致：典型原因是文件被删了但进程还持有 fd（lsof | grep deleted 能找到）。空间要等进程关闭 fd 或重启才释放。

⚠️ df -h 显示有空间却写不进 —— 大概率是 inode 用满（df -i 看 IUse%）。海量小文件（如 session、缓存）是常见元凶。

⚠️ await 高但 %util 不高，通常是队列里的 IO 大小不均或设备限速（云盘有 IOPS/带宽上限），看云厂商的盘规格。

五、网络

工具 说明
ss netstat 已被 ss 取代（更快、信息更全）
ip -s link 看 errors / dropped，非零即链路问题
mtr 结合 ping + traceroute，逐跳看丢包
tcpdump 抓包定位重传 / RST / 握手失败

⚠️ TIME_WAIT 多不一定是坏事 —— 它是主动关闭方的正常状态（2MSL）。只有端口耗尽才是问题，可开 tcp_tw_reuse（仅对出向连接生效），别用已废弃的 tcp_tw_recycle。

⚠️ SYN 队列溢出：netstat -s 里 SYNs to LISTEN sockets dropped 非零说明握手被打满，检查 somaxconn 与 tcp_max_syn_backlog，也可能是被 SYN Flood 打了。

⚠️ ip -s link 的 dropped 非零常见于网卡缓冲区满或 txqueuelen 太小，不一定是丢包到对端；先确认计数增长的速率。

六、strace 与 perf

火焰图（Brendan Gregg 的 FlameGraph）：

⚠️ strace 会显著拖慢进程（每次系统调用都要停下通知 tracer），生产环境只做短时定位，别长期挂着。

⚠️ perf record 采样频率过高会引入可观开销（-F 99 已是常用折中）。容器里跑 perf 常因 perf_event_paranoid 受限，需要提权。

⚠️ strace -f 会跟随所有子线程，输出量巨大；不加 -e trace= 过滤时容易刷爆终端和磁盘。

七、eBPF 与 bpftrace

eBPF 让内核态可编程：挂在内核 hook 上，低开销、无需改应用、无需重启。

runqlat 调度延迟（队列等待）

⚠️ eBPF 有内核版本门槛：基础功能需 **4.x+**，bpftrace 建议 **4.9+**，CO-RE / BTF 便携编译需 5.x+ 且内核带 CONFIG_DEBUG_INFO_BTF。老内核（如 CentOS 7 的 3.10）用不了或要另装 BCC 的兼容包。

⚠️ eBPF 也要评估开销：高频 hook（如每次网络包）会累积可观 CPU；生产先在低峰试跑，观察 perf top 里 bpf 的占比。

⚠️ **bcc 与 bpftrace 需要 root 或 CAP_BPF**；容器内跑要挂载 /sys/kernel/debug 或 debugfs，权限不足会静默失败。

八、启动性能与日志

⚠️ systemd-analyze blame 里耗时长不等于在关键路径上 —— 真正拖慢启动的是 critical-chain 上的串行依赖。

⚠️ journalctl 默认只保留有限历史（受 SystemMaxUse 限制），排查前先确认日志没被轮转掉。

九、排查套路总结

⚠️ 重启会销毁现场。除非已确认是「进程僵死」且要先恢复服务，否则先留证据（perf record、ss、iostat 快照）再动手。

⚠️ 不要同时改多个参数再观察 —— 无法归因。一次只动一个变量。

常见坑清单

  • 把 load average 高直接等同于 CPU 忙（D 状态等 IO 也计入）
  • 只看 top 瞬时值，不用 vmstat 1 看趋势
  • 看到 wa 高却去加 CPU
  • 忽略 st（steal），把宿主机超卖当应用问题
  • 上下文切换高就盲目扩核，不区分自愿 / 非自愿
  • 用 free 而非 available 判断内存是否够
  • 忽略 vmstat 的 si / so，没发现正在换页
  • 生产随手 drop_caches，造成短期性能骤降
  • 只看 %util 判断磁盘饱和，忽略 aqu-sz / await
  • df 和 du 不一致时不查 lsof | grep deleted
  • 写不进数据只查 df -h，忘了 df -i 的 inode
  • 还在用 netstat（应用 ss）
  • 看到 TIME_WAIT 多就上 tcp_tw_recycle（已废弃且有害）
  • strace 长期挂生产，拖慢目标进程
  • 老内核上硬跑 eBPF 工具，不确认版本与 BTF
  • 容器里跑 bcc / bpftrace 未处理权限与 debugfs
  • 依赖 systemd-analyze blame 而不看 critical-chain
  • 排查时直接重启，销毁现场
  • 一次改多个参数，无法归因
  • 不先量化瓶颈类型就猜测原因
