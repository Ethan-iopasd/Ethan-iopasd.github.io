开场：一句话结论

分支模型的复杂度要匹配发布节奏 —— 持续部署用 Trunk-Based，有版本发布用 GitHub Flow，只有需要同时维护多个已发布版本时才上 Git Flow；cherry-pick 是补丁搬运工不是日常合并手段，bisect 把「哪次提交引入 bug」从猜测变成二分查找。

一、三种主流工作流

维度 Git Flow GitHub Flow Trunk-Based
长期分支 main + develop 只有 main 只有 main
临时分支 feature/ release/ hotfix/ feature/ 短命分支或直接提交
分支寿命 天~周 小时~天 小时级
发布方式 从 release/ 打 tag 合并 main 即部署 每次提交都可能上线
主干形状 feature/→develop；release/ 验收后合回 main 与 develop 每个 feature/ 从 main 拉出，评审后合回即上线 频繁提交到 main，每次提交过 CI 即可发布
适合 有版本号、多版本并行维护 SaaS / 持续部署 高频部署 + 完善 CI
主要代价 分支多、冲突多、develop 与 main 易漂移 无 要求测试与灰度足够强

⚠️ Git Flow 的经典痛点：**develop 上积累了大量未发布提交，main 上又打了 hotfix**，
两个分支开始分叉，之后每次 release 都在解冲突。没有「多版本并行维护」的硬需求，不要上。

二、PR 的三种合并方式

方式 结果 历史形状 适合
Merge commit 生成合并提交，保留全部原始提交 有分叉、有 merge 节点 提交粒度好、想保留
Squash 压成 1 个提交到目标分支 线性 默认推荐，一个 PR 一条记录
Rebase merge 逐个重放到目标分支顶端 线性，保留粒度 提交已 rebase -i 整理过

⚠️ Squash 之后原分支的提交在 main 上不存在。同一分支被反复 squash 合并两次，
第二次会冲突或重复应用 —— 因为找不到共同祖先。squash 合并过的分支应立刻删除。

三、cherry-pick：把单个提交搬到别处

-x 会在提交信息末尾追加 (cherry picked from commit 4a1f9c2e...) 一行。

参数 作用 何时用
-x 记录来源 SHA hotfix 回迁到 release 分支时必加
-n / --no-commit 不自动提交 要合并多个提交成一次
-e 编辑提交信息 需要改 message
-m 1 指定 merge commit 的主线父 cherry-pick 一个合并提交

⚠️ 同一补丁被 cherry-pick 到两条分支，之后这两条分支再合并时，Git 会看到
「两个不同提交改了同一处」，产生无意义的冲突。这类冲突通常两边内容一样，
但要先确认等价再选边，别盲目 --theirs。

⚠️ git cherry -v 判等靠 patch-id，只看 diff 内容。cherry-pick 时顺手改了
message 或夹带了别的改动，patch-id 就不一样，会被判为「未合并」而重复挑一次。

四、bisect：二分定位引入 bug 的提交

二分区间是 log2(N)：1000 个提交约 10 次，10000 个约 14 次。run 脚本的退出码语义：

退出码 判定 退出码 判定
0 good 125 skip（无法测试）
1 ~ 127（除 125） bad >= 128 中止 bisect

⚠️ 编译失败必须 exit 125，不能让它返回 1。否则历史中间态编译不过的提交
会被判成 bad，把 bug 定位到完全错误的位置。

⚠️ git bisect 会 checkout 到 detached HEAD 并修改工作区，未提交的改动会被
拒绝或丢失。开始前先 git stash -u 或确保工作区干净。

五、worktree：同时开多个分支

场景 传统做法 worktree
边开发边救火 stash → 切分支 → 回来 pop 两个目录并行，互不干扰
跑长 CI 同时改代码 会互相踩工作区 隔离
对比两个版本 拉两份完整 clone 共享 .git，省空间
构建产物与源码同目录 冲突 隔离目录

⚠️ 同一个分支不能在两个 worktree 里同时检出（fatal: 'x' is already checked out）。
这是保护不是 bug。给 CI 用就 add -b ci/tmp 建临时分支，或 add --detach <sha>。

六、stash：注意它挂在哪个分支上

⚠️ stash 不绑定分支，它是仓库级的栈。在 feature 上 stash，切到 main 再 pop，
改动会落到 main 的工作区 —— 这是「代码莫名其妙跑到别的分支」事故的根因。
git stash branch 从 stash 的原始提交开新分支，是最安全的恢复方式。

七、reflog：最后一道保险

场景 恢复命令
误 reset --hard git reflog 找到旧 SHA，再 reset --hard <sha>
误删分支 git reflog 或 git fsck --lost-found 找回 SHA
rebase 做砸了 git reflog 找 rebase 前的 SHA
误 commit --amend git reflog，ORIG_HEAD 也可以

⚠️ reflog 是本地的，默认保留 90 天（不可达对象 30 天），且不随 clone 传播。
换台机器就找不回来，重要操作前手动记一下 SHA。

八、找「谁改的、什么时候改的」

命令 用途
git blame -L 10,30 f 逐行作者与提交
git blame -w -C -C f 忽略空白改动 + 追踪跨文件搬移
git log -S'needle' pickaxe：找出增删了这个字符串的提交
git log -G'regex' pickaxe 的正则版
git log -L 10,20:f 追踪这几行的完整演变史
git log -L :funcName:f 按函数名追踪（支持部分语言）
git log -p --follow f 跨重命名的完整历史

⚠️ -S 找的是字符串出现次数发生变化的提交。某次提交只把它从 A 行挪到 B 行
（次数不变）时 -S 不会命中，这种情况用 -G。

九、range-diff：对比两版分支

输出形如 1: abc123 ! 1: def456 fix: 校验 token：= 完全一致，! 内容变了但意图相同，
< / > 表示只在一侧存在。

⚠️ 强推之后 review 平台上的 diff 会全部「重来」，reviewer 看不出你改了什么。
range-diff 是唯一能回答「这一轮 review 之后你改动了什么」的命令，
但 GitHub / GitLab 界面默认不展示，得本地跑。

十、--force-with-lease 为什么优于 --force

命令 行为 风险
--force 无条件覆盖远端 别人的新提交直接消失
--force-with-lease 远端等于我记录的 origin/x 时才覆盖 别人推过就拒绝
--force-with-lease=<ref>:<sha> 显式指定期望值 最精确
--force-if-includes 额外要求远端提交已在本地 reflog 里 防后台 fetch 造成的假安全

⚠️ --force-with-lease 的判定基准是本地记录的 refs/remotes/origin/feature。
后台有进程（IDE、git fetch --all、脚本）刚 fetch 过，本地记录已更新为别人的提交，
lease 就形同虚设。加 --force-if-includes 补上这个洞。

十一、tag 与语义化版本

类型 创建方式 含元数据 用途
轻量 tag git tag v1.0 否（就是个 ref） 临时标记
附注 tag git tag -a v1.0 -m 是（作者/日期/说明，可签名） 正式发布

SemVer 是 MAJOR.MINOR.PATCH：不兼容改 MAJOR，向后兼容加功能改 MINOR，向后兼容修 bug 改 PATCH。

⚠️ git push 默认不推 tag。忘了推 tag，CI 上按 tag 触发的发布流程不会跑，
而本地看起来一切正常。用 --follow-tags 或 push.followTags=true。

十二、.gitattributes 与换行符

配置 含义 建议
core.autocrlf=true 提交转 LF，检出转 CRLF Windows 单机
core.autocrlf=input 提交转 LF，检出不动 Linux / macOS
core.autocrlf=false 完全不转换 仓库已用 .gitattributes 统一管理时

⚠️ **不要同时依赖 core.autocrlf 和 .gitattributes。前者是每台机器的本地配置，
同事之间不一致，换行符会在提交间来回抖动，diff 里全是「整文件重写」。
团队协作的正确做法是仓库里放 .gitattributes，所有人 autocrlf=false**。
已经乱了用 git add --renormalize . 重新 normalize。

十三、LFS、submodule vs subtree、仓库瘦身

方案 版本记录 克隆体验 适合
Git LFS 指针进 Git，实体存 LFS 服务器 需装 LFS，否则拉到指针 大二进制（设计稿、模型、视频）
submodule 记录子仓库的某个 SHA 需 --recurse-submodules，容易忘更新 独立版本、独立权限的子项目
subtree 子项目代码真的进本仓库 普通 clone 即可 想省心、不介意仓库变大
症状 原因 处理
.git 体积远大于工作区 历史里有大文件 git filter-repo（filter-branch 已不推荐）
拉取慢 对象多、packfile 大 git gc --aggressive --prune=now，或浅克隆 --depth=1
误提交了密钥 历史里还在 立刻轮换密钥 + filter-repo 重写历史

⚠️ 重写历史（filter-repo）会改变所有相关提交的 SHA，等同于换了一个仓库，
必须通知所有人重新 clone。且先轮换泄露的密钥，重写历史不能代替轮换。

常见坑清单

  • 没有多版本并行维护需求却上 Git Flow，develop 与 main 长期漂移
  • squash 合并后的分支不删，第二次合并报冲突或重复提交
  • 已推送、被别人拉取过的分支 rebase 后直接 --force
  • cherry-pick 忘了 -x，后续无法追溯补丁来源
  • 同一补丁在两条分支各 cherry-pick 一次，合并时产生假冲突
  • git bisect run 脚本里编译失败返回 1 而不是 125，定位到错误提交
  • bisect 前不清理工作区，未提交改动丢失
  • 用 git bisect skip 大量跳过，最后结论模糊
  • 同一个分支在两个 worktree 里同时检出（其实是被禁止的）
  • 手动删 worktree 目录，残留 .git/worktrees 元数据
  • stash 后切分支再 pop，改动落到错误的分支
  • stash 不带 -u，未跟踪文件没进去，以为丢了
  • 依赖 reflog 恢复，却不知道它不随 clone 传播、90 天后过期
  • 用 git blame 找人没加 -w，被格式化提交误导
  • 用 -S 找移动过的字符串（次数没变），应该用 -G
  • 用 --force 覆盖共享分支
  • 用 --force-with-lease 但后台进程刚 fetch 过，保护失效
  • git push 后忘了推 tag，CI 的 tag 触发流程没跑
  • 同时依赖 core.autocrlf 和 .gitattributes，换行符来回抖动
  • submodule 只 clone 不 update --init，子目录是空的
  • 误提交密钥后只 rm 文件，没轮换密钥也没重写历史
