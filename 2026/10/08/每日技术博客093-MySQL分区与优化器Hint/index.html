开场：一句话结论

分区表的用途是快速归档（DROP PARTITION）而不是提速单点查询；临时表是优化器的产物而不是你建的；Hint 是统计信息不准时的补丁而不是常规手段。

一、分区类型与最硬的限制

类型 分区依据 适合
RANGE 区间（< 2026-01-01） 时间归档，最常用
LIST 离散枚举值 按地区 / 租户 ID 分组
HASH MOD(col, n) 均匀打散，无区间语义
KEY 内置哈希函数（支持字符串） 同 HASH，键类型不限

⚠️ 分区键必须包含在表的每一个唯一索引（含主键）里。 这是最硬的限制，没有绕法。上例里主键只能是 (id, created_at)，不能是 (id)。

⚠️ 表没有任何唯一索引时这条限制不适用，可以用任意列做分区键。但没主键的表在 InnoDB 里是另一堆问题。

其它限制

限制 说明
分区数上限 单表最多 8192 个分区
不支持外键 分区表不能有外键，也不能被外键引用
不支持全文索引 分区表不能建 FULLTEXT

⚠️ 「先建普通表，事后再分区」不现实：分区键必须进主键，而 ALTER TABLE 改主键在千万级表上等于重建。分区要在建表时决定。

二、分区裁剪与「分区表不等于更快」

裁剪生效的条件

EXPLAIN 的 partitions 列直接告诉你扫了哪些分区：

partitions 值 含义
p2026 ✅ 裁剪到单个分区
p2025,p2026,pmax ⚠️ 裁剪到多个，检查条件写法
NULL 表未分区
全部列出 ❌ 裁剪完全失效

为什么分区表可能更慢

原因 表现
元数据开销 分区多时打开表变慢，受 table_open_cache / open_files_limit 限制
二级索引是局部分区索引 每个分区各有一份索引，非分区键查询要扫所有分区
跨分区查询 结果要归并，比单表 B+ 树遍历更贵
分区数过多 优化器评估分区本身的成本上升

⚠️ MySQL 的分区没有全局二级索引。WHERE user_id = ? 而 user_id 不是分区键时，优化器要在每个分区里各查一次索引再归并。分区越多，这条查询越慢。

⚠️ 「分区表更快」是错觉。它只在「条件能裁剪到少数分区」时才有优势，其余场景都是纯开销。

分区的真实用途

用途 说明
快速归档 DROP PARTITION 是 DDL，比 DELETE 快几个数量级
冷热分离 冷分区放独立表空间
按时间清理 定时任务 DROP 过期分区

⚠️ DROP PARTITION 会直接丢弃数据，不可回滚。生产上先 SELECT 导出备份，或者先把分区 EXCHANGE PARTITION 成独立表再处理。

⚠️ REORGANIZE PARTITION 会重建涉及的分区并移动数据，大分区上是重操作。要在低峰期做，并预留足够的磁盘空间（会临时占用接近一倍）。

分区 vs 分库分表

维度 分区表 分库分表
范围 单机单实例内 跨机器
对应用 透明 需分片中间件 / 应用层路由
扩容 受单机容量限制 可水平扩展
事务 本地事务 分布式事务
适用 归档、冷热分离 单机容量到顶

⚠️ 两者不是一回事，别混着说。分区解决「单机内数据管理」，分库分表解决「单机装不下」。分区表无法突破单机磁盘与连接数上限。

三、临时表与派生表

内部临时表何时产生

语句特征 是否用临时表
GROUP BY 非索引列 ✅ 通常
DISTINCT ✅ 通常
UNION（非 UNION ALL） ✅ 去重需要
派生表未合并 ✅

⚠️ Using temporary 和 Using filesort 不是一回事：前者是「用了内部临时表」（可能全在内存），后者是「没走索引排序、额外排序」。一条语句可以同时出现两者，也可以只有其中一个。

参数 作用
tmp_table_size 内存临时表上限
max_heap_table_size MEMORY 引擎表上限（取两者较小值）
internal_tmp_mem_storage_engine TempTable（8.0.16+ 默认）/ MEMORY
temptable_max_ram TempTable 引擎的内存上限

⚠️ 内存临时表超过上限会转成磁盘临时表（OnDisk），性能断崖式下降。Created_tmp_disk_tables / Created_tmp_tables 这个比值高就说明配置偏小或语句写得不对。

派生表与 derived_merge

开关 版本 行为
derived_merge 5.7+ 派生表合并进外层，不物化
derived_condition_pushdown 8.0.22+ 无法合并时，把外层条件下推到派生表内

⚠️ derived_condition_pushdown 只在 MySQL 8.0.22 及以上存在（8.0.28 修复过一个相关 bug）。8.0.22 之前，派生表一旦无法合并就整表物化，外层条件只能事后过滤。

⚠️ 派生表里有 LIMIT、聚合函数、UNION 时通常无法合并，会物化。写 LIMIT 的派生表要特别看执行计划。

四、优化器 Hint

Hint 作用
/*+ INDEX(t idx) */ 强制用某个索引
/*+ NO_INDEX(t idx) */ 禁用某个索引
/*+ JOIN_ORDER(t1, t2) */ / /*+ JOIN_FIXED_ORDER() */ 建议 / 强制 join 顺序
/*+ MAX_EXECUTION_TIME(1000) */ 超时毫秒数
/*+ SET_VAR(sort_buffer_size=16M) */ 语句级改会话变量

⚠️ Hint 是最后手段。 先做这三件事：ANALYZE TABLE 刷新统计信息、检查索引是否缺失、改写 SQL。Hint 写死了执行计划，数据分布一变就变成新的事故源，而且升级 MySQL 版本后 Hint 行为可能变。

⚠️ JOIN_ORDER 只是建议，优化器可以无视；JOIN_FIXED_ORDER 才是强制。两者别混用。

五、统计信息、直方图与 trace

参数 作用
innodb_stats_auto_recalc 变更超过 10% 时自动重算

⚠️ 统计信息不准是选错执行计划的头号原因。典型场景：status 列 99% 是同一个值，但采样恰好都取到少数值，优化器以为走索引更便宜，结果扫了全表。

⚠️ 直方图对数据倾斜严重的列（status、city）效果最明显。持久化统计默认按 10% 变更触发重算，大批量导入后手动 ANALYZE TABLE 一次。

用 trace 看优化器在想什么

EXPLAIN FORMAT=JSON 里的 cost_info 值得关注：

字段 含义
query_cost 整个查询的估算成本
prefix_cost 到当前表为止的累计成本
eval_cost 条件求值成本
prefix_cost 到当前表为止的累计成本
data_read_per_join 每行读取的数据量

⚠️ EXPLAIN 的 rows 是估算值，不是真实行数。想看真实值用 EXPLAIN ANALYZE（8.0.18+，会真的执行语句，写操作要包在事务里回滚）。

⚠️ optimizer_trace 的 JSON 可能几百 KB，且只对当前会话最后一条语句有效。生产上慎开，会有额外开销。

⚠️ innodb_buffer_pool_size 直接影响「走索引 + 回表」的估算成本。buffer pool 太小，索引扫描的真实代价远高于优化器的估算，这是「本地测试很快、线上很慢」的常见原因之一。

六、查询改写

原写法 改写 原因
相关子查询 JOIN 逐行执行子查询，O(n×m)
IN (子查询) EXISTS / JOIN 视数据量与版本，IN 可能物化子查询
EXISTS JOIN 只做存在性判断时可走半连接优化
UNION UNION ALL UNION 要额外去重排序
ORDER BY RAND() 应用层随机取 ID 全表排序，大表必崩
SELECT * 列出需要的列 无法走覆盖索引

⚠️ IN vs EXISTS 没有绝对答案，取决于子查询结果集大小与外层行数：子查询小用 IN，外层小用 EXISTS。MySQL 8.0 的优化器会把两者都转成半连接（semijoin），实际差别要 EXPLAIN 看。

⚠️ SQL_CALC_FOUND_ROWS 已被废弃（8.0.17 起 deprecated）。它为了拿总数而放弃 LIMIT 优化，比单独跑一次 COUNT(*) 更慢。分页就老实查两次。

常见坑清单

  • 分区键没包含在所有唯一索引里，建表直接失败
  • 先建普通表再想分区，改主键等于重建表
  • 用 YEAR(created_at) 当条件，分区裁剪失效
  • 分区键与另一列比较（created_at > updated_at），裁剪失效
  • 以为分区表会更快，实际非分区键查询要扫全部分区
  • 分区数过多，撞 open_files_limit / table_open_cache
  • DROP PARTITION 前不备份，数据不可回滚
  • 高峰期 REORGANIZE PARTITION，磁盘空间没预留
  • 混淆 Using temporary 与 Using filesort
  • tmp_table_size 太小，临时表频繁落磁盘
  • 不看 Created_tmp_disk_tables 比值，问题长期潜伏
  • 派生表里有 LIMIT / 聚合，以为会被 derived_merge 合并
  • 在 8.0.22 以下版本指望 derived_condition_pushdown
  • 一上来就用 /*+ INDEX() */，不先 ANALYZE TABLE
  • JOIN_ORDER 当成强制生效，其实只是建议
  • 大批量导入后不手动 ANALYZE TABLE
  • 直接信 EXPLAIN 的 rows，以为是真实行数
  • buffer_pool 太小，本地快线上慢却归因于 SQL
  • 用 UNION 代替 UNION ALL，白付去重排序成本
  • 继续使用已废弃的 SQL_CALC_FOUND_ROWS
