一 架构、Topic / Partition 与消费者组 本篇

开场：一句话结论

Kafka 的并行度、顺序性、可靠性三件事，全部由 Partition 一个概念决定 —— 并行度上限 = 分区数，顺序性只在分区内成立，副本同步也以分区为单位。

一、组件全景与元数据层演进

组件 职责
Broker 单个 Kafka 进程，存消息、服务生产/消费请求
Topic 逻辑消息流，只是逻辑概念，不落盘
Partition Topic 的物理分片，存储与并行度的最小单位
Replica 分区的副本，1 Leader + N Follower
Controller 由某个 Broker 兼任，负责 Leader 选举、副本分配、元数据变更
Group Coordinator 负责消费组成员管理与 offset 提交的那个 Broker
ZooKeeper / KRaft 存集群元数据（Topic 列表、分区分布、配置）

元数据层（Controller 的选主依赖）的演进：

版本 状态
≤ 2.8 仅 ZooKeeper
2.8 KRaft 引入（预览，KIP-500）
3.3 KRaft 生产可用（KIP-833 标记 GA）
3.5 ZooKeeper 模式标记 deprecated
4.0（2025-03-18 发布） ZooKeeper 模式彻底移除，只剩 KRaft

⚠️ 3.3 之前 KRaft 只能测试，别把 3.0 / 3.1 的 KRaft 上生产。
⚠️ 4.0 起 zookeeper.connect、--zookeeper 这类配置和参数全部失效，老迁移脚本会直接报错。
⚠️ 生产环境建议 controller 与 broker 角色分离部署；combined 模式下 Controller 数量一般是 3，且必须是奇数。

二、Partition 是并行度的唯一单位

结论 说明
消费并行度上限 = 分区数 同一消费组内，一个分区只能被一个消费者消费
消费者数 > 分区数 多出来的消费者空转，分不到分区
生产者并行度 = 分区数 写入分散到各分区，单分区仍是顺序追加

分区数不能事后随便加：加分区会破坏基于 key 的分区映射（hash(key) % N 的 N 变了）。

⚠️ 加了分区后，同一个 key 的历史消息可能落在旧分区、新消息落到新分区，同 key 的顺序保证直接失效。
⚠️ 分区数减少在 Kafka 里不支持（只能重建 Topic）。

三、offset 语义：分区内单调，不是全局唯一

概念 含义
offset 消息在某个分区内的顺序编号，从 0 递增
唯一性 (topic, partition, offset) 三元组才唯一，offset 本身不唯一
提交位置 __consumer_offsets 里存的是「下一条要读的 offset」
auto.offset.reset 无提交记录时的起始位置：earliest / latest / none

⚠️ offset 不连续 —— 日志清理（compact）会删掉中间的消息，你会看到 offset 跳跃。
⚠️ auto.offset.reset 只在没有有效提交位点时生效；有提交位点时它什么都不做。
⚠️ 提交的 offset 是「下一条」，不是「已消费的最后一条」，写监控时别错位一格。

四、副本模型：Leader / Follower / ISR / AR / LEO / HW

缩写 全称 含义
AR Assigned Replicas 分区的全部副本（含 Leader）
ISR In-Sync Replicas 与 Leader 保持同步的副本（含 Leader）
OSR Out-of-Sync Replicas 落后太多、被踢出 ISR 的副本，AR = ISR + OSR
LEO Log End Offset 每个副本下一条要写的 offset
HW High Watermark ISR 中最小 LEO，消费者只能读到 HW 之前的消息
  • Follower 持续向 Leader 发 fetch 请求同步数据；不是 Leader push。
  • 判定「跟不上」用的是时间不是条数：replica.lag.time.max.ms 默认 30000（30s）。
  • 只要 Follower 在 30s 内发过一次 fetch 并追到 Leader 的 LEO，就算同步。

⚠️ 老版本还有个 replica.lag.max.messages，已废弃，别再按条数调它。
⚠️ HW 只在 ISR 变化时推进，所以 acks=all 也不等于「立刻对消费者可见」。
⚠️ 消费者默认只能读到 HW 之前的消息（isolation.level=read_uncommitted 也不越过 HW，只影响事务未提交消息的可见性）。

五、消费者组与 Rebalance

一个消费组内，分区在成员间重新分配的过程叫 Rebalance。三种触发条件：

触发条件 说明
成员加入 新消费者启动，触发分配
成员离开 消费者主动关闭，或 session.timeout.ms 超时被判定死亡
分区数变化 Topic 增加了分区

关键参数：

参数 默认值 作用
session.timeout.ms 45000 心跳超时，超时判死
heartbeat.interval.ms 3000 心跳间隔
max.poll.interval.ms 300000 两次 poll() 的最大间隔，超了主动退组
group.instance.id 无 设置后成为静态成员，短暂重启不触发 Rebalance

Eager vs Cooperative

模式 行为 影响
Eager（老） 所有成员先放弃全部分区，再重新分配 Stop-The-World，全组暂停消费
Cooperative（增量） 只回收需要转移的分区，其余不动 只影响变动的那部分分区

⚠️ Rebalance 期间全组停止消费（Eager 模式尤其明显），是消费 lag 突增的常见原因。
⚠️ max.poll.interval.ms 超时是「Rebalance 风暴」的头号来源 —— 业务处理太慢就会被反复踢出。
⚠️ 静态成员 group.instance.id 只对计划内重启有效，进程崩溃后仍要等 session.timeout.ms 才判死。

六、分区分配策略

partition.assignment.strategy 可选值：

策略 特点 问题
RangeAssignor 按 Topic 逐个分配，分区数/消费者数 取整 + 余数 多 Topic 时前面的消费者多分，倾斜
RoundRobinAssignor 所有 Topic 的分区打平轮询 订阅不同 Topic 时分配不优
StickyAssignor 尽量均衡 + 尽量保留上次分配 仍是 Eager，会全停
CooperativeStickyAssignor Sticky 的增量版本 需要客户端 2.4+，且不能与 Eager 策略混用

Kafka 2.4 起默认是 [RangeAssignor, CooperativeStickyAssignor] 这个列表（前者为兼容回退）。

⚠️ 迁移到 Cooperative 必须分两步：先把 partition.assignment.strategy 改成只含 Cooperative 策略，再滚动重启，否则会因协议不兼容无限 Rebalance。
⚠️ Range 策略在多 Topic 场景下倾斜很明显：10 分区 3 消费者会分成 4/3/3，多个 Topic 叠加后第一个消费者压力最大。

七、日志存储结构与清理

  • 文件名前缀 = 该 segment 的起始 offset。
  • .index / .timeindex 是稀疏索引：不是每条消息都记，而是每隔 log.index.interval.bytes（默认 4096 字节）记一条，靠二分 + 顺序扫描定位。
配置 默认值 作用
log.segment.bytes 1073741824（1 GiB） 单个 segment 上限，超过就滚动新文件
log.retention.hours 168（7 天） 基于时间的保留
log.retention.bytes -1 基于大小的保留，-1 表示不限
log.retention.check.interval.ms 300000 检查周期
log.cleanup.policy delete delete 或 compact

两种清理方式：

策略 语义 典型场景
delete 按时间/大小整段删除 普通事件流
compact 按 key 保留每个 key 的最新值 changelog、状态同步、CDC

⚠️ log.retention.bytes 是按分区算的，不是按 Topic；Topic 总占用 = 分区数 × 该值。
⚠️ compact 只保证最终保留最新值，删除是后台异步的，短期仍可能读到旧值。
⚠️ 时间保留以 segment 为粒度：一个 segment 只要还有未过期的消息就整体保留，实际保留时长可能远超 7 天。

消息格式 v2

  • 批量（record batch）+ 批量级压缩：整个 batch 压一次，比逐条压缩省 CPU 且压缩比更高。
  • 压缩后 Producer 发送、Broker 存储都是压缩态，只有 Consumer 解压。
  • v2 起 create time 与 append time 分离，时间戳语义更清晰。

八、写入可靠性的三个开关

配置 含义
acks 0 不等确认 / 1 Leader 落盘即回 / all(= -1) ISR 全部落盘才回
min.insync.replicas 写成功至少需要多少个 ISR 副本确认（Broker 端配置）
unclean.leader.election.enable 是否允许非 ISR 副本当选 Leader，默认 false

acks=all 只有在 min.insync.replicas > 1 时才有实际容错意义：

acks min.insync.replicas 副本数 结果
all 1 3 只保证 Leader 落盘，丢数据风险仍在
all 2 3 至少 2 份确认，容忍挂 1 台
all 2 3 ISR 只剩 1 个时写入直接失败（这是保护，不是 bug）

⚠️ acks=all + min.insync.replicas=1 是常见的「以为很安全其实不安全」组合。
⚠️ min.insync.replicas 是 Broker 级配置，Topic 级可覆盖，别只改 Broker 忘了 Topic 覆盖。
⚠️ unclean.leader.election.enable=true 换来可用性，代价是可能丢数据，金融类场景一律 false。

常见坑清单

  • 把 acks=all 当成不丢数据，min.insync.replicas 还是默认的 1
  • 在 3.3 之前把 KRaft 用上生产
  • 4.0 之后仍用 zookeeper.connect 启动，直接启动失败
  • 事后给已有 Topic 加分区，导致同 key 顺序失效
  • 消费者数超过分区数，多出来的消费者空转
  • 以为 offset 全局唯一，或以为 offset 连续
  • 混淆「已提交 offset」与「最后消费的 offset」，差一格
  • 调 replica.lag.max.messages（已废弃），应该调 replica.lag.time.max.ms
  • 业务处理慢导致 max.poll.interval.ms 超时，引发 Rebalance 风暴
  • Eager 再平衡期间 lag 突增被误判为消费能力不足
  • 从 Range 直接切 CooperativeSticky 而不分步滚动重启
  • 认为 compact 会立刻删除旧 key 的消息
  • 用 log.retention.bytes 时按 Topic 总量算，忘了它是按分区
  • 把 auto.offset.reset=latest 当成「总会从最新开始」
  • 开了 unclean.leader.election.enable=true 却没意识到会丢数据
  • 单分区写入量远超其他分区，造成热点（key 分布不均）
  • 用 SELECT * 式思维读 Kafka：以为能跨分区按时间全局有序
