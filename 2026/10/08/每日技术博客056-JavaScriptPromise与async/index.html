三 Promise 与 async/await 本篇

开场：一句话结论

async 函数是「生成器 + 自动执行器」的语法糖，await 只在微任务队列里让出一次；Promise 一旦 settled 就永久锁定。这两条决定了后面所有坑的形态。

一、三态与不可逆

状态 说明 能否再变
pending 初始态，未决 ✅ 可变
fulfilled 成功，携带 value ❌ 锁定
rejected 失败，携带 reason ❌ 锁定

fulfilled 与 rejected 合称 settled。一旦 settled，后续 resolve / reject 全部静默无效，不报错。

⚠️ resolve 收到 thenable 时会「跟随」它（resolve with a thenable），最终状态由那个 thenable 决定 —— 你后续的 reject 会被覆盖掉。

二、微任务队列与执行顺序

Promise 回调属于 microtask，在当前宏任务结束后、下一个宏任务开始前被一次性清空。

队列 成员 执行时机
宏任务 macrotask setTimeout / setInterval / I/O / 渲染 每轮事件循环取一个
微任务 microtask .then/.catch/.finally、queueMicrotask、MutationObserver 宏任务后全部清空

⚠️ 微任务会插队到所有宏任务之前。setTimeout(fn, 0) 永远排在已经入队的 .then 之后，与「0 毫秒」无关。

await 之后的代码等价于 .then 回调：

写法 等价语义
await x; 之后的语句 Promise.resolve(x).then(() => { ... })
连续 await 连续嵌套 .then，每次让出一个微任务
await 一个非 Promise 值 仍然让出一次微任务

⚠️ 每个 await 都是一次调度开销。循环里 await N 次就是 N 次微任务往返 —— 热路径上是实打实的损耗。

三、async 函数的本质

async 编译产物 = 生成器函数 + 自动执行器：

事实 含义
async 函数总是返回 Promise return 1 得到的是 Promise<1>
函数体内同步抛错 不会同步冒泡，而是返回 rejected promise
return await x vs return x 前者多包一层、多一次微任务
没有 await 的 async 函数 返回值依然被包装成 Promise

⚠️ return await promise 在 try/catch 内部是必需的 —— 只有 await 才能把 rejection 交给本层的 catch。在 try 块外面则是多余的一层。

四、错误处理

场景 正确做法
async 函数内部 try/catch
裸 Promise 链 .catch() 放链尾
多个独立任务 每个任务各自 .catch，别指望外层
全局兜底 unhandledrejection / process.on('unhandledRejection')

⚠️ unhandledrejection 的触发有延迟：要等一个 rejection 走完整个微任务检查点仍无 handler 才触发。在同一轮微任务里补挂 .catch 有效，跨轮就晚了。

⚠️ Promise.all 中只要一个 reject，其余任务不会被取消。它们后续的 rejection 若无人处理，就变成 unhandled rejection。

五、四个并发方法

方法 何时 fulfill 何时 reject 返回值 规范
Promise.all 全部 fulfill 任一 reject（取首个原因） 值数组（保序） ES2015
Promise.allSettled 全部 settle 永不 reject {status, value|reason} 数组 ES2020
Promise.race 任一 settle 且为 fulfilled 任一 settle 且为 rejected 首个 settle 的值/原因 ES2015
Promise.any 任一 fulfill 全部 reject 首个 fulfillment 值 / AggregateError ES2021

⚠️ race 的名字具有误导性：它只看谁先 settle，不看成功。用 race 做超时，超时 Promise 必须 reject，否则超时会被当成正常结果返回。

⚠️ any 全部失败时抛的是 AggregateError，原因在 e.errors 数组里，**不在 e.message**。

需求 选哪个
全都要成功，任一失败即整体失败 all
要每个结果（含失败明细） allSettled
只要最快 settle 的那个 race
只要最快成功的那个 any

六、串行 vs 并行

⚠️ 关键在于**先创建 Promise 再 await**。await f1(); await f2(); 永远是串行 —— await 会阻塞到 f1 结束，才轮到 f2() 被创建。

⚠️ forEach 里的 await 不会被等待。Array.prototype.forEach 丢弃回调返回值，回调自己挂起、外层循环立刻继续。

for await...of 用于异步可迭代对象（Symbol.asyncIterator），按迭代器串行消费：

写法 并发度 顺序
for...of + await 1 严格顺序
for await...of 1 严格顺序（按迭代器）
map + Promise.all 无限 结果保序，执行无序
信号量池 自定义 严格顺序

七、并发控制与取消

Promise.all 并发无上限，容易打爆下游。手写信号量：

成熟实现是 p-limit：const limit = pLimit(5); await Promise.all(urls.map(u => limit(() => fetch(u))));

⚠️ 手写池时 worker 数量必须取 min(limit, 任务数)。写死 limit 会在任务少时空转；不取 min 又会在任务多时并发失控。

Promise 本身不可取消。取消要靠 AbortController 去取消底层操作（fetch、流、定时器）。

⚠️ ac.abort() 只对支持 signal 的 API 生效。对普通 new Promise 毫无作用 —— 必须自己在 Promise 内监听 signal。

⚠️ 取消后必须清理监听器（{ once: true } 或手动 removeEventListener），否则长生命周期 signal 会累积 listener 造成泄漏。

常见坑清单

  • 以为 settled 的 Promise 还能被再次 resolve / reject 改变
  • resolve(thenable) 时忽略「跟随」语义，状态被 thenable 覆盖
  • 混淆宏任务与微任务，以为 setTimeout(fn, 0) 先于 .then
  • 循环里直接 await，把可并行的任务写成串行
  • forEach 里 await，误以为循环会等待
  • 用 race 做超时，超时 Promise 没有 reject
  • any 全失败时读 e.message 而不是 e.errors
  • Promise.all 一个失败，误以为其余任务会被取消
  • all 内部没有各自 catch，产生 unhandled rejection
  • try 块外写 return await，白白多一层微任务
  • try 块内写 return promise（无 await），catch 抓不到 rejection
  • 无上限 Promise.all，把下游打爆
  • 以为 Promise 可取消，或对不支持 signal 的 API 调 abort()
  • 监听 abort 后不清理 listener，长期累积泄漏
  • 未注册 unhandledrejection，线上静默丢错误
