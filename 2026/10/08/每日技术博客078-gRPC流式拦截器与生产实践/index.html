开场：一句话结论

流式调用省的是「往返次数」不是「数据量」，生产上真正让 gRPC 稳定的，是 deadline、拦截器、客户端负载均衡和 keepalive 这四件事。

一、四种流式调用的适用场景

类型 语义 适合 不适合
Unary 1 请求 1 响应 绝大多数 CRUD ——
Server streaming 1 请求 N 响应 大结果集、进度、订阅 需要客户端应答
Client streaming N 请求 1 响应 批量上传、聚合 需要中途返回
Bidirectional N 请求 N 响应 实时聊天、双向同步 简单请求响应

⚠️ Send 是阻塞的。当 HTTP/2 窗口用尽，Send 会挂住直到对端 WINDOW_UPDATE。这就是背压 —— 但如果你在持锁时 Send，锁会被一直占住。

二、背压与流控

参数 位置 含义
连接级窗口 HTTP/2 层 整条连接的收发额度
流级窗口 每条 stream 单个流的收发额度
initial_window_size 连接配置 初始窗口，默认 64KB
max_concurrent_streams HTTP/2 SETTINGS 单连接最大并发流

⚠️ 窗口默认 64KB，大消息会「走走停停」。高带宽场景调大 initial_window_size（如 1MB）能显著提升吞吐，但会增加内存占用。

⚠️ max_concurrent_streams 默认 100。流式连接数多的服务要主动调大，否则新流会被排队而不是立刻处理。

三、流式调用的常见坑

坑 后果 解法
忘记 CloseSend client streaming 永不结束 用 defer CloseSend()
中途错误直接 return 错误丢给客户端成 UNKNOWN 返回 status.Error(...)
服务端不检查 ctx.Done() 客户端断了还在算 长任务里定期检查
服务端 Send 到已断的流 首次报错后持续报错 立即退出循环
双向流用共享变量 数据竞争 每方向独立 goroutine

⚠️ **Send 返回 error 后不要继续 Send**。对端已经没了，后续调用只会不断报错。

⚠️ 流中途的错误只能通过返回 error 传递。已经 Send 出去的消息不会撤回，客户端必须自己处理「收到部分数据后失败」的情况。

四、deadline 与超时传播

概念 说明
deadline 绝对时间点，跨服务传播时会被换算
timeout 客户端本地概念，WithTimeout 会转成 deadline
传播 gRPC 把剩余时间放进 grpc-timeout header 传给下游
超时错误 DEADLINE_EXCEEDED（码 4）

⚠️ deadline 会逐跳递减。上游给的 3s 到了第三跳可能只剩 0.5s，下游必须尊重传入的 deadline，而不是自己重新设一个更大的。

⚠️ 服务端也要主动检查 deadline。ctx.Err() 返回 context.DeadlineExceeded 时就该放弃，继续算只是浪费 CPU。

⚠️ 超时不是「失败」的同义词。服务端可能已经执行成功，只是响应晚了 —— 所以写操作超时后不能盲目重试。

五、拦截器

用途 Unary Stream
日志 UnaryInterceptor StreamInterceptor
鉴权 / 指标 / 限流 ✅ ✅
panic recovery ✅ ✅

⚠️ 拦截器链是有顺序的。ChainUnaryInterceptor(a, b, c) 里 a 最先进入、最后返回（洋葱模型）。recovery 要放在最外层，否则内层 panic 逃不出去。

⚠️ Stream 拦截器只能包一层。要拦截每条消息得包装 grpc.ServerStream 重写 SendMsg / RecvMsg，或者用 stats.Handler。

⚠️ 客户端也有拦截器，且必须成对注册。客户端加了鉴权拦截器、服务端没配对应校验，等于没鉴权。

六、metadata 与自定义头

规则 说明
键必须小写 HTTP/2 头部规范，大写会被规范化或拒绝
-bin 后缀 二进制值，自动 base64 编码
大小限制 默认约 8KB，超了报错
保留键 grpc- 前缀由库使用，别占用

⚠️ metadata 键一律小写。Go 里 metadata.Pairs 会自动转小写，但手工构造 map 时容易踩。

⚠️ 别把大对象塞进 metadata。它走 HTTP/2 头部，受 HPACK 表大小和 MAX_HEADER_LIST_SIZE 限制，塞几 KB 的 JSON 会直接失败。

⚠️ metadata 是逐跳的，不是端到端的。服务端调下游时不会自动转发，要显式传递。

七、负载均衡与服务发现

方案 位置 优点 缺点
代理侧 LB 客户端前面放 Envoy/LB 客户端简单 多一跳、代理成瓶颈
客户端侧 LB gRPC 内建 少一跳、性能高 每个客户端都要解析服务列表
Service Mesh Sidecar 对应用透明 运维复杂
策略 行为
pick_first 默认，连第一个可用地址
round_robin 轮询所有地址

⚠️ **默认策略是 pick_first，不是 round_robin**。不显式配置的话，客户端只会用一个后端实例，扩缩容基本无效。

⚠️ DNS 解析需要 dns:/// 前缀。直接写 user-svc:50051 走默认 resolver，某些环境下不重解析，后端 IP 变了连不上。

⚠️ round_robin 需要能拿到多个地址。如果服务名解析成 ClusterIP 单地址，轮询无从谈起 —— 要用 Headless Service 或 xDS。

八、keepalive 与 ENHANCE_YOUR_CALM

⚠️ Time 设太小会被服务端用 GOAWAY + ENHANCE_YOUR_CALM 拒绝。服务端默认有最小间隔限制（常见 5 分钟），客户端 ping 太频繁会被当成攻击。

⚠️ PermitWithoutStream=true 尤其危险。空闲连接上疯狂发 ping 很容易触发限流，要用就得同时调服务端的 enforcement policy。

九、连接复用与 WithBlock 的坑

选项 行为 建议
grpc.NewClient 惰性连接，调用时才建 ✅ 默认用这个
grpc.Dial（旧） 语义含糊，已弃用 别用
WithBlock 阻塞到连接就绪 ⚠️ 慎用

⚠️ WithBlock 会把「服务暂时不可用」变成「启动直接失败」。它在网络抖动时会卡住整个启动流程。新代码用 grpc.NewClient 的惰性语义。

十、重试与对冲

概念 说明
retry 失败后重试同一请求
hedging 同时发多个副本，取最快响应
maxAttempts 总尝试次数上限
可重试状态码 通常只列 UNAVAILABLE / DEADLINE_EXCEEDED

⚠️ 只对幂等方法开重试。CreateOrder 重试可能创建两笔订单 —— 除非有幂等键。

⚠️ 对冲会成倍放大流量。hedging 同时发 N 份请求，后端负载瞬间 ×N，只适合低 QPS 的读接口。

⚠️ 重试受 deadline 约束。maxAttempts=4 但 deadline 只有 100ms 时，可能只来得及重试 1 次。

十一、暴露成 REST：grpc-gateway

组件 作用
protoc-gen-grpc-gateway 生成反向代理 handler
protoc-gen-openapiv2 生成 OpenAPI/Swagger
反向代理 把 REST/JSON 翻译成 gRPC 调内部服务

⚠️ grpc-gateway 是「翻译层」不是「转换器」。它把 HTTP/JSON 转成 gRPC 调用，浏览器仍不直接说 gRPC。

⚠️ grpc-web 不支持客户端流和双向流（部分实现只支持 unary + server streaming）。浏览器实时通信，WebSocket 往往更省事。

十二、反射与调试

⚠️ 反射默认关闭，生产环境要谨慎开。它会把所有服务和方法暴露给任何能连上的人，等于接口文档公开。

十三、可观测性与 HTTP/2 调优

指标 含义
grpc_server_handled_total 按方法 + 状态码计数的请求数
grpc_server_handling_seconds 处理耗时直方图
grpc_client_attempt_duration_seconds 客户端每次尝试耗时

⚠️ 状态码要进指标 label，但方法名不要拆太细。按 service/method/status_code 打标是常规做法；再叠加 user_id 之类就是基数爆炸。

⚠️ max_concurrent_streams 和 initial_window_size 要一起调。只调窗口不调并发流，瓶颈会从流控转移到并发上限。

常见坑清单

  • 流式调用忘记 CloseSend，client streaming 永不结束
  • 服务端长任务里不检查 ctx.Done()，客户端断了还在算
  • 流中途失败直接 return err，错误被吞成 UNKNOWN
  • 在持锁状态下 Send，窗口用尽时把锁也一起挂住
  • 客户端不设 deadline，慢下游把上游连接池耗尽
  • 服务端忽略传入 deadline，自己重设一个更大的
  • 写操作超时后盲目重试，产生重复数据
  • 用 WithBlock 让启动强依赖下游可用
  • 每个请求新建 ClientConn，丢掉连接复用和负载均衡
  • 不配置负载均衡，默认 pick_first 只用一个实例
  • DNS 目标没写 dns:/// 前缀，后端变更后不重解析
  • keepalive Time 设得太小，被服务端 ENHANCE_YOUR_CALM 拒绝
  • metadata 键用了大写，或被当成普通 header 丢掉
  • 非幂等接口开启重试或对冲，放大流量与副作用
  • 只注册了 Stream 拦截器，漏了 Unary（或反之）
  • 生产环境开启 gRPC 反射，接口全暴露
  • 用 grpc-web 做双向流，发现浏览器根本不支持
  • 调大 initial_window_size 却不调 max_concurrent_streams
