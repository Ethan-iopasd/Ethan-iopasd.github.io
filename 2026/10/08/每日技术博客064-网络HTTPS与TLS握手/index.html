开场：一句话结论

HTTPS = 用非对称加密安全地交换出一个对称密钥，之后用对称加密传数据；TLS 1.3 把握手压到 1-RTT，并删掉了所有不提供前向保密的密钥交换。几乎所有「证书报错」都出在证书链和 SAN。

一、为什么混合加密

加密 特点 在 TLS 里的角色
对称（AES / ChaCha20） 快，但密钥分发难 传输数据
非对称（RSA / ECDSA） 慢，可公开公钥 签名 / 身份验证
密钥交换（ECDHE / DHE） 双方各自算出同一密钥 协商会话密钥

⚠️ 密钥交换不等于加密：ECDHE 本身不加密任何数据，它的作用是让双方在不安全信道上各自独立算出同一个密钥，且私钥不上网。理解这点才看得懂前向保密。

⚠️ 对称加密的性能比非对称快几个数量级。所以 TLS 只用非对称做「握手那几下」，数据全走对称。

二、TLS 1.2 完整握手

消息 作用
ClientHello 客户端随机数、支持的版本 / 套件 / 扩展（SNI、ALPN）
ServerHello 选定版本与套件、服务端随机数
Certificate 服务端证书链
ServerKeyExchange ECDHE 公钥 + 用证书私钥签名（防篡改）
Finished 校验握手完整性（基于所有握手消息的摘要）

⚠️ 会话密钥 = HKDF(R1, R2, 预主密钥)。R1 / R2 是明文传输的，安全性全靠 ECDHE 的预主密钥 —— 这就是为什么随机数不需要保密，但绝不能重复。

⚠️ ServerKeyExchange 的签名必须存在，否则中间人可以替换 ECDHE 参数做降级。早期某些配置漏签是历史漏洞来源。

三、TLS 1.3 的改进（RFC 8446）

维度 TLS 1.2 TLS 1.3
握手往返 2-RTT 1-RTT
会话恢复 2-RTT（或 ticket 1-RTT） 0-RTT（有重放风险）
密钥交换 RSA / DHE / ECDHE 都行 只有 (EC)DHE / PSK
前向保密 可选 强制
密码套件 加密 + 认证 + 密钥交换分开 合并，只保留 AEAD
明文消息 较多 仅 ClientHello / ServerHello

⚠️ TLS 1.3 删掉了静态 RSA 密钥交换（客户端用服务器公钥加密预主密钥），因为它没有前向保密 —— 私钥一旦泄露，历史流量全部可解。所以「配了 RSA 证书」和「用 RSA 密钥交换」是两回事：1.3 下证书可以是 RSA，但密钥交换一定是 ECDHE。

⚠️ 0-RTT 有重放攻击风险：0-RTT 数据不参与完整握手、可被攻击者截获重放。只对幂等的 GET 开 0-RTT，POST / 支付类接口绝不能开。

⚠️ TLS 1.3 下 ssl_ciphers 基本失效（套件由 1.3 自己协商），要限制 1.3 套件得用 ssl_conf_command Ciphersuites。这是升级 1.3 后「配置改了没效果」的原因。

四、证书链与证书字段

字段 说明
Subject 主体（CN 域名已基本被忽略）
subjectAltName (SAN) 真正生效的域名列表，现代客户端只认它
notBefore / notAfter 有效期
keyUsage 证书用途（digitalSignature / keyEncipherment）
extendedKeyUsage 扩展用途（serverAuth / clientAuth）

⚠️ 服务端必须下发中间证书。只下发叶子证书时，浏览器可能因缓存了中间证书而正常，但 curl / Java / Android / 小程序会报 unable to get local issuer certificate。根证书不要下发（客户端本就有）。

⚠️ 顺序错了也会失败：fullchain.pem 必须是叶子证书在前、中间证书在后。反过来拼，部分客户端会验证失败。

⚠️ **现代浏览器只认 SAN，不认 CN**。证书只填 CN=example.com 而 SAN 为空或缺少该域名，会直接报域名不匹配。

⚠️ 证书有效期正在被强制缩短（主流 CA 已推行逐年缩短，最终目标 47 天）。证书过期是「最容易避免又最常发生」的线上事故，必须做到期监控。

⚠️ 一张证书可以同时签多个域名（SAN 多值），但通配符证书 *.example.com 只匹配一级子域：a.example.com ✅，a.b.example.com ❌。

五、SNI、ALPN 与 OCSP

机制 谁去查吊销状态 问题
CRL 客户端下载吊销列表 列表巨大、更新慢
OCSP 客户端实时向 CA 查询 泄露用户访问行为、CA 挂了会拖慢 / 失败
OCSP Stapling 服务器替客户端查好并附在握手里 需配 resolver

⚠️ SNI 是明文的。直接用 IP 访问 HTTPS（不带 SNI）会命中 default_server 的证书，扫 IP 就能扒出站点域名。

⚠️ 老客户端（XP、部分旧 Java）不支持 SNI，只能拿到默认证书。这类客户端如果访问的不是默认域名就会报错。

⚠️ HTTP/2 必须经 ALPN 协商。如果客户端和服务端 ALPN 没谈拢，会静默退回 HTTP/1.1 —— 你以为开了 HTTP/2，实际没开。用 curl -v --http2 https://... 看协商结果。

⚠️ OCSP 会泄露用户正在访问哪个站点（客户端直连 CA 查询）。Stapling 由服务端代查，既省延迟又保护隐私，现代部署应默认开启。

⚠️ 配了 ssl_stapling on 但没配 resolver，nginx 无法解析 OCSP 地址，stapling 静默失效，日志只有 warn，握手照常成功。

六、openssl 排查与常见错误

报错 根因
certificate verify failed 证书链不完整 / 自签名 / 过期
unable to get local issuer certificate 服务端没下发中间证书
certificate has expired notAfter 已过
hostname mismatch / IP address mismatch SAN 里没有该域名
self signed certificate 用了自签证书（内网 / 开发环境）
tlsv1 alert protocol version 客户端与服务端无共同 TLS 版本

⚠️ openssl s_client 必须带 -servername，否则不带 SNI，可能拿到默认证书，看到的是另一个域名的证书 —— 排查时会被误导。

⚠️ Verify return code: 0 (ok) 才代表链完整。21 (unable to verify the first certificate) 说明缺中间证书；20 (unable to get local issuer certificate) 说明本地信任库缺根证书或链不完整。

⚠️ 域名不匹配（mismatch）和链不完整（issuer）是两类完全不同的错误：前者看 SAN，后者看中间证书。修错方向会白忙。

⚠️ 证书「浏览器能开、代码报错」，几乎总是链不完整或信任库老旧（如老 JDK 不认新根证书 / Let’s Encrypt 的交叉签名到期）。这类问题只在特定客户端暴露，最难复现。

七、HSTS、CT、mTLS 与握手延迟优化

机制 作用
HSTS 强制浏览器只走 HTTPS
CT（Certificate Transparency） 所有证书记入公开日志，可审计
SCT 证书里 / 握手里携带的 CT 日志证明
mTLS 客户端与服务端互相验证证书
优化 省下的时间
会话复用（session ticket / cache） 省一次完整握手（1 RTT）
TLS 1.3 比 1.2 少 1 RTT
0-RTT（仅幂等请求） 再省 1 RTT（有重放风险）
CDN 就近终止 TLS 省掉到源站的长途 RTT
OCSP Stapling 省客户端查 OCSP 的往返

⚠️ HSTS 一旦下发无法回退：max-age 内浏览器拒绝任何 HTTP 连接，也拒绝绕过证书错误页。证书出问题时连「点击继续」的机会都没有。且它有首次访问窗口（TOFU），常配合 preload 列表使用。

⚠️ CT 让所有公开签发的证书都能被查到（crt.sh 之类）。这既是审计手段，也意味着你新签的域名 / 子域会立刻公开可见 —— 别拿 CT 日志当保密边界。

⚠️ mTLS 里服务端也要下发 ssl_client_certificate（校验客户端用的 CA 链），否则拿不到客户端证书做校验。这是和普通 HTTPS 配置最大的差别。客户端证书的吊销 / 轮换也容易造成「合法客户端突然连不上」。

⚠️ TLS 握手要 1~2 个 RTT，而每个 RTT 都受物理距离限制（跨洋 ~150ms）。这就是 CDN 在边缘终止 TLS 价值巨大的原因 —— 不只是缓存，而是把握手 RTT 从「用户到源站」缩短到「用户到边缘」。

⚠️ 会话复用依赖同一台服务器 / 同一份 ticket key。多台后端各生成 ticket key 时，用户每次可能命中不同机器，复用率骤降。要共享 ticket key（ssl_session_ticket_key）。

⚠️ 长连接复用（HTTP keep-alive / HTTP2 多路复用）能省掉重复握手。反过来，短连接 + 每次新建 TLS = 每次都吃满握手 RTT，是移动端慢的常见原因。

常见坑清单

  • 服务端只下发叶子证书，没带中间证书
  • fullchain.pem 把顺序拼反（中间证书在前）
  • 证书只填 CN 不填 SAN，现代浏览器不认
  • 通配符证书以为能匹配二级子域
  • 证书过期没有到期监控，直到用户报错
  • 用 IP 访问 HTTPS 命中 default_server，拿到别的域名证书
  • 配了 OCSP stapling 却没配 resolver，静默失效
  • 以为开了 HTTP/2 实际被 ALPN 退回 1.1
  • 对非幂等接口开 TLS 1.3 0-RTT，遭重放
  • 在 TLS 1.3 下用 ssl_ciphers 限制套件（无效）
  • HSTS 一上来 max-age=31536000，出事无法回退
  • 把「域名不匹配」和「链不完整」两类错误混为一谈
  • openssl s_client 不带 -servername，看到别的域名的证书
  • 多后端各生成 session ticket key，会话复用率极低
  • 证书与私钥不配对，nginx reload 才报错
  • mTLS 忘了下发 ssl_client_certificate，客户端证书校验不了
  • 以为中间人抓包（Charles / mitmproxy）是「破解」了 TLS
  • 短连接不复用，每次都吃满握手 RTT
  • 改完证书不 nginx -t 直接 reload，服务起不来
  • 忽略 CT 日志公开性，把新域名当保密信息
