开场：排序快不快，取决于数据分布，不是算法名字

O(n log n) 只是比较排序的下界，不是某个算法的专属标签。实际跑起来：TimSort 在「基本有序」的数据上是 O(n)，pdqsort 在「大量重复元素」上远快于朴素快排，而快排遇到「已排序输入 + 首元素作 pivot」会退化成 O(n²)。选排序前先看数据长什么样。

一、O(n log n) 下界从哪来

n 个元素有 n! 种排列，每次比较只能把候选空间一分为二，所以决策树高度至少是 log₂(n!)。

项 值
排列数 n!
决策树最小高度 log₂(n!)
Stirling 近似 ≈ n·log₂n − 1.44n
结论 任何基于比较的排序，最坏 ≥ Ω(n log n)

⚠️ 这个下界只约束「比较排序」。 只要不靠比较（计数、基数、桶），就能突破 n log n —— 代价是对数据有额外假设（值域有限、可分解成位）。

二、各语言 sort 的真实实现

语言 排序对象 算法 稳定 最坏 备注
Java Arrays.sort(int[]) 基本类型 双轴快排 ❌ O(n²)* Dual-Pivot Quicksort
Java Arrays.sort(Object[]) / List.sort 对象 TimSort ✅ O(n log n) 归并 + 插入，利用已有 run
Python list.sort / sorted 序列 TimSort ✅ O(n log n) 只能排 list
Go sort.Slice / slices.Sort 切片 pdqsort（1.19 起） ❌ O(n log n) 原为快排 + 堆排
C++ std::sort 任意迭代器 introsort ❌ O(n log n) 快排 + 堆排 + 插入
C++ std::stable_sort 任意迭代器 归并 ✅ O(n log n) 额外空间 O(n)
JS Array.prototype.sort 数组 TimSort（V8） ✅ O(n log n) ES2019 起规范要求稳定
Rust sort / sort_unstable 切片 归并 / pdqsort ✅ / ❌ O(n log n) 稳定版需额外空间

* 双轴快排在极端输入上仍可能退化，JDK 内部对小块有插入排序兜底。

⚠️ Java「基本类型用快排、对象用 TimSort」是有意为之。 基本类型没有「相同但不同一」的语义（1 和 1 完全等价），稳定性无意义，所以选更快的快排；对象有身份差异（两个金额相同的订单仍是两个订单），必须稳定，所以用 TimSort。**int[] 排序不稳定不是 bug，是特性。**

⚠️ TimSort 的空间是 O(n)，不是 O(1)。 它是归并类算法，需要临时数组。内存极度受限的场景要留意：std::sort 原地、std::stable_sort 要 O(n) 额外空间，差别就在这。

⚠️ sort.Slice 走反射，比泛型版 slices.SortFunc 慢一个量级。 热路径上的排序（每秒几十万次）应换 slices.SortFunc。Go 1.21 起标准库才有泛型排序。

三、稳定性：多字段排序的命门

稳定 = 相等元素的相对顺序在排序后保持不变。

做法 结果
稳定排序 + 从次要键到主要键依次排 ✅ 正确
稳定排序 + 从主要键到次要键依次排 ❌ 后一次覆盖前一次的次序
不稳定排序 + 多轮排序 ❌ 完全不可控
不稳定排序 + 复合比较器 / 复合 key ✅ 正确

⚠️ TimSort 的稳定性有前提：比较函数必须满足「严格弱序」。 违反传递性（a<b、b<c 却 a>=c）会让 TimSort 直接抛 IllegalArgumentException: Comparison method violates its general contract! —— 线上最常见、也最容易被当成「偶发」的排序事故。常见成因：比较函数里读了会变的字段、浮点 NaN、a - b 在 int 上溢出。

⚠️ (a, b) -> a - b 这种比较器在整数上会溢出。 a = -2e9, b = 2e9 时 a - b 溢出成负数，排序结果直接错乱。Java 用 Integer.compare(a, b)，Go 用 cmp.Compare，Python 的 key 直接返回数值即可（无此问题）。

⚠️ JS 的 sort 默认按字符串比较。 [10, 9, 1].sort() → [1, 10, 9]。数字排序必须传比较器 (a, b) => a - b。另外比较器不能返回布尔值 —— (a, b) => a > b 会被当成 0/1，在 TimSort 下产生错误顺序。

四、非比较排序：什么时候能突破 n log n

算法 时间 空间 前提 稳定
计数排序 O(n + k) O(k) 值域 k 有限且小 ✅
基数排序 LSD O(d·(n + k)) O(n + k) 可拆成 d 位、每轮计数排序 ✅
桶排序 平均 O(n + n²/k) O(n + k) 数据均匀分布 取决于桶内排序
位图排序 O(n) n/8 字节 值域小、无重复 ——

⚠️ 计数排序的空间是 O(值域) 而不是 O(n)。 排 100 万个「取值范围 0~1e9」的数，开 10 亿的计数数组直接 OOM。值域大的时候只能走基数排序（按位分解）或回到比较排序。

⚠️ 基数排序的「稳定」是硬要求。 每一位的排序必须稳定，否则高位排好的顺序会被低位打乱。这就是为什么基数排序必须用计数排序做子过程，不能换成快排。

五、二分查找：边界比算法难

二分本身十行就能写完，翻车几乎全在边界上。

写法 区间 循环条件 收缩 返回
存在性查找 [lo, hi] 闭 lo <= hi lo=mid+1 / hi=mid-1 mid 或 -1
下界 lower_bound [lo, hi) 左闭右开 lo < hi lo=mid+1 / hi=mid lo（插入点）
上界 upper_bound [lo, hi) lo < hi lo=mid+1 / hi=mid lo

⚠️ mid = (lo + hi) / 2 在 C/C++/Java 的 int 上会溢出。 lo = hi = 2³¹−1 时 lo + hi 溢出成负数，mid 变负，直接越界。**统一写 lo + (hi - lo) / 2**（Python 无此问题，但仍推荐统一写法）。这个 bug 在 JDK 的 Arrays.binarySearch 里真实存在了 9 年（直到 2006 年才修）。

⚠️ lo = mid 会导致死循环。 当 hi = lo + 1 时 mid == lo，若分支写 lo = mid，区间不缩小，循环卡死。左闭右开的模板里 lo 必须 mid + 1，只有 hi 可以是 mid。 记住：收缩区间时至少有一侧要排除 mid。

⚠️ 有重复元素时，「找到 target 就返回」返回的下标是不确定的。 想知道第一个或最后一个位置，必须用 lower_bound / upper_bound，不能靠一次 == 判断。

六、各语言二分 API 对照

语言 API 语义 未找到时
Python bisect_left(a, x) 第一个 >= x 返回插入点（0..len）
Python bisect_right(a, x) / bisect 第一个 > x 返回插入点
C++ std::lower_bound 第一个 >= x 返回 end()
C++ std::upper_bound 第一个 > x 返回 end()
Java Arrays.binarySearch 找到即返回（重复时不确定） -(插入点) - 1
Go sort.Search(n, f) 最小 i 使 f(i) == true 返回 n（谓词恒假）
Go 1.21+ slices.BinarySearch 找到返回下标 返回插入点 + false

⚠️ Java 的 binarySearch 返回 -(insertionPoint) - 1 而不是 -insertionPoint，是为了区分「插入点是 0」和「在下标 0 找到了」。取插入点要写 idx = -idx - 1，写成 -idx 会差一位。

⚠️ Go 的 sort.Search 谓词写反了不会报错，只会静默返回错值。 它假设谓词是「false...false, true...true」的单调形式。传一个非单调谓词，结果是未定义的（不 panic，就是答案错）。

七、二分答案：在「答案空间」上二分

当问题形如「最小的 x 使得条件成立」，且条件对 x 单调（x 越大越容易满足），就可以二分答案。

要点 说明
判定函数必须单调 can(x) 为真 ⇒ 所有 > x 也为真
上下界要收紧到可行域 太松不影响正确性，只影响常数
总复杂度 O(n · log(值域))
与普通二分的区别 数组不是给定的，是枚举出来的

⚠️ 二分答案的值域可能是浮点数。 浮点二分不要用 while hi - lo > eps（可能死循环或精度不够），改成固定迭代次数（如 100 次，精度约 值域 / 2¹⁰⁰）。

⚠️ 二分答案前先确认「单调性」成立。 如果 can(x) 不是单调的（中间为真、两边为假），二分会静默给出错误答案 —— 这类 bug 不报错，只算错。

八、第 K 大：排序 vs 堆 vs 快速选择

方案 时间 空间 适用
全量排序 O(n log n) O(n) 或 O(1) 需要完整有序结果
大小为 k 的堆 O(n log k) O(k) 流式数据 / k 很小 / 只要 Top-K
快速选择 quickselect 平均 O(n) O(1) 只要第 k 个，不需要排序
中位数的中位数 最坏 O(n) O(1) 要求最坏界（常数大，少用）
计数 / 桶 O(n) O(k) 值域小

⚠️ 快速选择的最坏是 O(n²)。 面对「已排序输入 + 固定取首元素作 pivot」，每次划分只缩小 1 个元素。解法是随机选 pivot 或三数取中。 生产环境要么随机化，要么直接用 nth_element / heapq.nlargest。

⚠️ nth_element 不保证左侧有序，只保证「左侧都 ≤ 第 k 个 ≤ 右侧」。想拿到有序的前 k 个还要再排左侧 —— 但那是 O(k log k)，比全量排序仍划算。

常见坑清单

  • 用 (lo + hi) / 2 求中点（int 会溢出，应写 lo + (hi - lo) / 2）
  • 二分里写 lo = mid 导致死循环（收缩区间必须排除 mid）
  • 混淆 while (lo <= hi) 和 while (lo < hi) 两套模板
  • 有重复元素时用一次 == 判断，返回的下标不确定
  • Java binarySearch 未找到时写成 -idx 而不是 -idx - 1
  • Go sort.Search 的谓词不单调（静默返回错值）
  • 二分答案前没验证判定函数的单调性
  • 浮点二分用 hi - lo > eps 而非固定迭代次数
  • 比较器写 (a, b) -> a - b，在整数上溢出
  • 比较器不满足严格弱序，TimSort 抛 Comparison method violates its general contract
  • 用 Arrays.sort(int[]) 做多字段排序（基本类型不稳定）
  • JS sort 不传比较器（按字符串比较，[10,9,1] → [1,10,9]）
  • JS 比较器返回布尔值（应返回数字）
  • 稳定排序时按「主要键 → 次要键」顺序多轮排（应从次要键开始）
  • 计数排序的值域远大于 n（空间爆掉）
  • 基数排序的子过程用了不稳定排序
  • 快速选择固定取首元素作 pivot（已排序输入退化成 O(n²)）
  • 用 nth_element 后以为左侧有序
  • 热路径上用 sort.Slice（反射开销，应换 slices.SortFunc）
  • 把 O(n log n) 当成「所有排序一样快」（数据分布决定常数）
