开场：一句话结论

能用结构化输出解决的问题，不要靠提示词解决。 「请你只输出 JSON」的可靠性取决于模型的服从性，而 JSON Schema 约束解码的可靠性取决于解码器 —— 后者是 100%，前者是概率。

一、提示词的四个组成部分

部分 作用 缺了会怎样
角色 / 上下文 界定知识范围与视角 答非所问，跨界编造
任务 明确要做什么 输出散漫，抓不住重点
约束 格式、长度、禁止项 格式不稳，需要反复重试
示例（few-shot） 用样本锚定风格与格式 边界情况处理不一致

⚠️ 约束要写成可判定的。「回答要专业」无法判定，「不超过 150 字」「必须含 [编号]」可以判定，也可以被测试。不可判定的约束等于没有约束。

⚠️ 指令和数据的边界必须显式标记。用 XML 标签（<docs>、<question>）或明确的分隔符，让模型知道哪部分是「要处理的内容」、哪部分是「要遵守的规则」。这也是防提示注入的第一道防线。

二、几个真正有效的技巧

技巧 做法 适用 效果
Few-shot 给 2~5 个输入输出示例 格式敏感、边界多 最稳定，收益最大
分步思考（CoT） 要求先推理再给结论 数学、多跳推理 明显提升，但更慢更贵
分解任务 一个大任务拆成多次调用 复杂流程 稳定性提升最大
自我检查 生成后要求核对约束 格式校验 中等，成本翻倍
预填充（prefill） 让回答以固定前缀开始 强制 JSON / 特定格式 高，且几乎零成本

⚠️ CoT 不是万能的。对简单任务加「让我们一步步思考」反而会让模型把简单问题想复杂，甚至引入错误。只在确实需要多步推理时用，并且优先用「先给结论、再给依据」而不是无约束的长篇推理。

⚠️ few-shot 的示例会「传染」错误。示例里有一个错别字或格式不一致，模型会照样学。示例数量也不必多，3 个高质量示例通常优于 10 个平庸示例。

三、结构化输出：三层可靠性

方案 可靠性 成本 说明
提示里写「输出 JSON」 低（80~95%） 最低 会带 markdown 代码块、会加解释
预填充 + 解析容错 中（95~99%） 低 需要剥离 ```json 包裹
JSON Schema 约束解码 高（100%） 中 解码时按语法树剪枝，不可能输出非法 JSON
函数调用 / 工具模式 高 中 模型直接返回结构化参数
约束类型 Schema 写法 模型行为
必填字段 required: [...] 一定会输出
枚举 enum: ["a","b"] 只在这几个值里选
数值范围 minimum / maximum 越界值被剪掉
数组长度 minItems / maxItems 按约束生成
嵌套对象 $defs / $ref 递归约束

⚠️ 约束解码会略损质量。强制某些 token 不可选，会让模型失去「先解释再作答」的余地，复杂推理任务上可能变差。推理密集的任务用「先自由推理、再结构化输出」两段式，比全程约束更好。

⚠️ 不是所有字段都适合放进 schema。reasoning 这类自由文本字段如果放进严格 schema，会限制模型的表达。常见做法：推理走普通文本，最终结论走 schema。

四、解析容错：生产环境必备

即使有 schema 约束，也要为「不支持该特性的模型」准备降级路径：

⚠️ **永远不要裸调 json.loads**。模型加一句「以下是结果：」就直接炸。生产代码必须有降级解析 + 重试 + 兜底值三层。

⚠️ 重试时要把错误回给模型：「上次输出不符合 schema：price 字段缺失，请重新输出」。直接原样重试，大概率得到同样的错误。

五、温度与其他采样参数

参数 作用 建议
temperature 随机性，0~2 抽取/分类用 0，创意写作用 0.7~1.0
top_p 核采样，累积概率阈值 通常只调一个，别和 temperature 同时大改
max_tokens 输出上限 按任务设，太小会截断
stop 停止序列 用于截断多余内容
seed 尽量可复现 不保证完全一致
presence/frequency_penalty 抑制重复 长文本生成时有用

⚠️ temperature=0 也不保证完全确定性。浮点累加顺序、批处理、GPU 非确定性都会带来差异。需要严格可复现的场景（评估、回归测试），要么固定 seed 并接受偶发差异，要么用容差判定。

⚠️ 同时调 temperature 和 top_p 会让行为难以预测。选一个调，另一个保持默认。

六、提示词的工程化管理

实践 做法
版本化 提示词存文件/数据库，带版本号，不进代码字符串
模板化 变量用占位符，渲染时做转义
回归测试 一组固定输入 + 期望，每次改动跑一遍
灰度 新版本小流量验证，指标达标再全量
可观测 记录 prompt 版本、token 数、延迟、解析失败率
缓存 相同前缀的 prompt 命中缓存（多数厂商支持）

⚠️ str.format 会把用户输入里的 {} 当占位符，直接报错或被注入。用户内容必须最后拼接，或者用 string.Template（$var 语法）避免冲突。

⚠️ 提示词缓存通常按「前缀」命中。把固定的大段说明放最前面、变量放最后，能显著提高缓存命中率，成本和延迟都能降一半以上。

常见坑清单

  • 用「请你只输出 JSON」当唯一保障，没有 schema 约束
  • 裸调 json.loads，模型加一句解释就崩
  • 重试时原样重发，不把错误信息回给模型
  • 约束写成「专业」「简洁」这类不可判定的形容词
  • 对简单任务滥用 CoT，反而引入错误
  • few-shot 示例里有错别字或格式不一致，被模型照学
  • 用 str.format 渲染含用户输入的模板，花括号冲突
  • 强制全流程结构化输出，复杂推理质量下降
  • temperature=0 却期待完全可复现
  • 同时大改 temperature 和 top_p，行为失控
  • 提示词硬编码在代码里，无法灰度与回滚
  • 没有解析失败率监控，线上静默出错
  • 不区分指令与数据，被文档内容里的指令劫持
