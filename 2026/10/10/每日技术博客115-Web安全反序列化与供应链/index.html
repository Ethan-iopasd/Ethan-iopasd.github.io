开场：一句话结论

反序列化漏洞的成因只有一条：数据格式里带上了「类型名 + 构造钩子」，解析器照着指令去实例化对象，攻击者就能把现成的 gadget chain 拼成 RCE。供应链和密钥泄露则是同一个问题的两种表现 —— 你信任了边界之外的东西，而且信任得毫无校验。

问题 本质 修法方向
反序列化 数据能指定「构造什么对象」 换成不带类型信息的格式，或强制白名单
供应链 依赖的内容可能在你看不见的地方被改 锁版本 + 哈希 + 签名验证
密钥泄露 秘密进入了会被复制的介质 不进介质；进去了就立刻轮换

一、格式决定能力：有没有「类型」和「钩子」

判断一个序列化格式能不能被利用，看两点：数据里能不能表达类型、反序列化时会不会自动调用目标代码。两者都具备的，就是 CWE-502。

格式 携带类型信息 反序列化时触发代码 默认水位
JSON ✗（只有 object/array/string/number/bool/null） ✗（除非显式开多态） 安全
Protocol Buffers / MessagePack 部分（schema 固定） ✗ 安全
XML ✓（DTD / 外部实体 / XSLT） ✓（XXE、XSLT 扩展函数） 必须禁 DTD 与外部实体
YAML ✓（!!python/object 等 tag） ✓ 只用 safe_load
Java 原生序列化 ✓（类名 + 字段） ✓（readObject / readResolve） 不可信数据禁用
Python pickle ✓（__reduce__ 可返回任意 callable） ✓ 不可信数据禁用
PHP serialize ✓（类名） ✓（__wakeup / __destruct / __toString） 用 allowed_classes 白名单
Ruby Marshal ✓ ✓（_load / init_with） 不可信数据禁用
.NET BinaryFormatter ✓ ✓（ISerializable） 已从 .NET 9 移除

⚠️ 「内网调用」「消息队列里只有自己人发消息」都不是安全边界。MQ 的 topic 权限配错、上游服务被拿下、或者有人把 payload 存进 Redis 又被另一个服务读出来，链条就通了。

YAML 是更容易踩的那个，因为配置文件天然是「不可信数据」：

场景 用法
读配置、读外部输入 yaml.safe_load
需要自定义对象 用 SafeLoader + add_constructor，只注册自己认可的 tag
只要数据结构 直接用 json.loads，没有类型系统就没有反序列化面

⚠️ PyYAML 5.1 起 yaml.load() 不带 Loader 会发 YAMLLoadWarning，但只是警告，代码照跑；6.0 把它默认成 FullLoader 并去掉警告 —— 于是很多项目「警告消失了，漏洞还在」。FullLoader 不是安全边界，它只是比 UnsafeLoader 少开了几个 tag。

三、Java：ObjectInputStream 与 gadget chain

Java 原生序列化的危险在于反序列化过程中会自动调用目标类的方法：

时机 被自动调用
读对象 readObject / readResolve / readExternal / validateObject
放进集合 hashCode / equals / compareTo（HashMap、TreeMap、PriorityQueue）
类型转换 toString / finalize（部分 gadget 链）

gadget chain 就是把这些串起来：HashMap.readObject → TiedMapEntry.hashCode → LazyMap.get → ChainedTransformer.transform → InvokerTransformer → Runtime.exec。Apache Commons Collections、Spring、Groovy、JDK 自身的类都被用来拼过链（ysoserial 里就是 CommonsCollections1~`7` 这些名字）。

Log4Shell（CVE-2021-44228） 不属于反序列化，但同属「解释器边界被越界」：log4j-core 2.0-beta9 ~ 2.14.1 会解析日志字符串里的 ${jndi:ldap://...} 并主动发起 JNDI 查询，CVSS 10.0。修法：升到 2.17.1+（2.16 起 JNDI 默认关闭）；临时缓解是 -Dlog4j2.formatMsgNoLookups=true 或删掉 JndiLookup class。它是传递依赖 —— 你项目里没直接写 log4j，但某个框架带了它，这才是它影响面那么大的原因。

四、PHP / Node / Ruby / .NET 的同类问题

语言 危险 API 触发钩子 现状
PHP unserialize($data) __wakeup __destruct __toString 用 unserialize($d, ['allowed_classes' => ['A','B']]) 白名单
PHP Phar 反序列化 读取 phar:// 时自动反序列化 metadata 别让用户控制路径
Node node-serialize 的 unserialize _$$ND_FUNC$$_ 直接 eval 函数体 该库已废弃，别用
Node 对象深度合并（_.merge / Object.assign 旧实现） __proto__ / constructor.prototype 原型污染 过滤键名、Object.create(null)
Ruby Marshal.load、YAML.unsafe_load _load / init_with Psych 4（Ruby 3.1+）已把 YAML.load 默认改为安全加载
.NET BinaryFormatter ISerializable / OnDeserialized .NET 8 起 API 抛 NotSupportedException，**.NET 9 起运行时已不再包含实现**
.NET Json.NET 的 TypeNameHandling.All 类型名由输入决定 只用 TypeNameHandling.None + 显式转换

五、依赖供应链：三条攻击路径

路径 手法 真实案例
直接投毒 抢注内部包名，发一个版本号更高的同名公共包 dependency confusion（Alex Birsan，2021）
名称混淆 typosquatting：reqeusts、lodahs、cross-env vs crossenv npm / PyPI 长期存在
上游失陷 攻破维护者账号、或直接改构建产物 Log4Shell（CVE-2021-44228）、xz 后门（CVE-2024-3094）

依赖混淆为什么成立：包管理器从多个源解析时，按版本号最高取胜，而不是按「来源可信度」。

如果内部包 my-lib 是 1.4.2，攻击者在 PyPI 上发一个 my-lib 99.0.0，下一次构建就会装到攻击者的包。npm 侧同理（私有 registry 与公共 registry 混用）。

防御手段 具体做法
内部源做代理 devpi / Artifactory / Nexus 缓存 PyPI，客户端只配 --index-url 指向代理（不要用 --extra-index-url）
锁文件 package-lock.json、poetry.lock、uv.lock、go.sum、Cargo.lock 必须提交
哈希校验 pip install --require-hashes -r requirements.txt（每行带 --hash=sha256:...）
按锁文件安装 npm ci、pnpm i --frozen-lockfile、pip install -r requirements.txt（不加 -U）
作用域隔离 npm 用 @company/* + scoped registry；Python 用私有前缀（company-）并在 PyPI 占位注册
依赖数量治理 引入前先看维护者数量、最近提交、issue 响应；一个 50 行的需求不值得引入 200 个传递依赖

⚠️ npm ci 只保证「按 lockfile 装」，不保证 lockfile 没被改过。攻击者如果同时改了 package.json 和 package-lock.json（一次 PR 就能做到），npm ci 会照单全收。要做的是 registry 侧签名验证（npm audit signatures）或给 lockfile 加 CODEOWNERS 保护。

⚠️ 同理，pip install -r requirements.txt 里的 >= 是供应链的地雷 —— 每次构建装到的版本都可能不同。要可复现就固定 == 并带 hash。

六、SBOM 与 SLSA：把「用了什么、怎么构建的」变成可查的事实

概念 回答什么问题 常见格式 / 工具
SBOM 这个制品里有哪些组件、什么版本、什么许可证 CycloneDX、SPDX；syft、cdxgen 生成
SCA 这些组件有没有已知漏洞 pip-audit、npm audit、govulncheck、cargo audit、OSV-Scanner、Trivy、Grype
provenance 这个制品是谁、在哪、用什么输入构建出来的 in-toto、GitHub Actions artifact attestation
签名 制品和 provenance 有没有被改 sigstore / cosign、GPG

SLSA 的 build track（注意版本差异）：

等级 要求 挡住什么
L0 无 ——
L1 存在 provenance（可未签名） 发布流程搞错（如从错误 commit 构建）
L2 provenance 由托管构建平台生成并签名 构建之后被篡改
L3 构建平台强隔离，签名密钥对构建步骤不可见 构建过程中被篡改（内部人、被拿下的凭据）

⚠️ SLSA 的编号换过。 v0.1 是单轨 SLSA 1~4；v1.0 砍掉了 Source 维度，只保留 Build track（L0~L3）；v1.2 又把 Source track 加回来。网上教程大量混用两套编号 —— 引用前先看 spec 版本号，别照抄「SLSA 4 级」这种说法。

七、密钥泄露：检测、处置、预防

密钥泄露有三条常见链路，覆盖范围依次扩大：

链路 后果
提交进 git 历史 仓库 clone 过的每个人、每个 CI 缓存都有
打进构建产物 / 前端 bundle 任何访问页面的人都能从 JS 里读出来
出现在日志、错误上报、CI 输出 落进第三方平台，你无法确认是否被清理

前端打包是重灾区：

⚠️ VITE_*、NEXT_PUBLIC_*、REACT_APP_*、PUBLIC_*（SvelteKit）全部等价于公开。前端能拿到的只能是「短时效 + 最小权限」的令牌（比如后端签发的临时上传凭证），不能是长期密钥。

场景 工具
提交前拦截 gitleaks protect --staged、detect-secrets、pre-commit hook
扫历史 gitleaks detect、trufflehog git file://.
平台侧 GitHub secret scanning + push protection
容器 / 文件系统 trivy fs --scanners secret .

处置顺序不能反：

  1. 先轮换（revoke 旧密钥 + 签发新的）。泄露发生的那一刻，这个密钥就已经失效了 —— 改 git 历史不能「撤销」已经发生的泄露。
  2. 再清理历史：git filter-repo --invert-paths --path .env（BFG 已停止维护，官方推荐 git filter-repo），然后 force push 并让所有人重新 clone。
  3. 最后评估影响：这个密钥能访问什么？审计日志里有没有异常调用？有没有创建过你不知道的资源？

⚠️ 最常见的错误顺序是「先 force push 清历史，再慢慢想轮换」。攻击者可能早就 clone 了 —— 轮换必须第一步，清历史只是防止后来者再拿到。

常见坑清单

  • 用 pickle / marshal / joblib.load / shelve 处理网络、文件上传、消息队列里的数据
  • yaml.load() 不带 Loader，或显式用了 yaml.Loader / yaml.UnsafeLoader
  • 以为 FullLoader 是安全的 —— 它不是，只是比 UnsafeLoader 少开几个 tag
  • Java 用 ObjectInputStream 读不可信数据，且没有设 ObjectInputFilter 白名单
  • Jackson 开了 enableDefaultTyping() / activateDefaultTyping() 却没配 PolymorphicTypeValidator 白名单
  • 用了 Fastjson autoType，或 .NET Json.NET 的 TypeNameHandling.All
  • PHP unserialize() 未限制 allowed_classes；或让用户控制 phar:// 路径
  • 对象深度合并（merge / extend / Object.assign）未过滤 __proto__ / constructor / prototype 键
  • pip install --extra-index-url 混用内部源与公共源（依赖混淆入口）
  • 没有提交 lockfile，或 CI 里用 npm install / pip install -U 而非 npm ci / --require-hashes
  • 依赖版本用 >= 或 ^ 且不带哈希校验，构建不可复现
  • GitHub Actions 用移动 tag（@v4）而非 commit SHA 固定第三方 action
  • pull_request_target 里 checkout 并执行 PR 代码（外部代码 + secrets 同上下文）
  • 只在直接依赖上跑 SCA，忽略传递依赖（Log4Shell 就是传递依赖）
  • 密钥写进 .env 却提交进仓库；或前端用 VITE_* / NEXT_PUBLIC_* 放真实密钥
  • 发现泄露后先清 git 历史、后轮换密钥（顺序反了）
  • 只在代码库里扫密钥，忘了 CI 日志、错误上报平台、容器镜像层
