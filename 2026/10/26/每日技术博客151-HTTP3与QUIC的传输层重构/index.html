开场：一句话结论

QUIC 把「可靠、有序、拥塞控制」从内核搬到了用户态，跑在 UDP 上。 换来的三件事：流之间不再互相阻塞、连接可以跟着 IP 迁移、握手能压到 0-RTT。代价是 CPU 开销更高、中间设备兼容性更差。

一、HTTP/2 的老问题

问题 根因 QUIC 的解法
TCP 层队头阻塞 单条连接内字节流严格有序 每条流独立重传
握手延迟 TCP 3 次 + TLS 2 次 合并为 1 次（1-RTT）/ 0-RTT
连接迁移 四元组绑定 用 Connection ID 标识
中间设备僵化 内核协议难升级 用户态可快速迭代

⚠️ HTTP/2 的多路复用是「假并行」。在丢包率 2% 的移动网络上，一条 TCP 连接上的所有流都被同一个重传卡住，实际表现常常不如 HTTP/1.1 的 6 条连接。

⚠️ QUIC 不解决带宽瓶颈。它优化的是「延迟与抖动」，在高带宽低延迟的机房内网里收益很小。

二、连接建立：1-RTT 与 0-RTT

模式 往返次数 首次请求延迟 风险
TCP + TLS 1.2 3-RTT 高 ——
TCP + TLS 1.3 2-RTT 中 ——
QUIC 1-RTT 1-RTT 低 ——
QUIC 0-RTT 0-RTT 最低 重放攻击

⚠️ 0-RTT 数据可被重放。攻击者截获后重发，服务端会再执行一次。只对幂等请求（GET）启用 0-RTT，POST 必须等 1-RTT。

⚠️ 0-RTT 需要 PSK 恢复。首次访问没有 PSK，永远是 1-RTT。冷启动用户享受不到这个优化。

三、流与帧：QUIC 的内部结构

概念 作用
Connection 一条 QUIC 连接，由 Connection ID 标识
Stream 双向或单向的字节流，独立流控
Frame 传输单位（STREAM / ACK / CRYPTO / MAX_DATA）
Packet 加密后的 UDP 载荷
帧类型 用途
STREAM 携带应用数据
ACK 确认（含延迟 ACK 信息）
CRYPTO 握手数据
MAX_DATA / MAX_STREAM_DATA 连接级/流级流控
RESET_STREAM 单流取消
CONNECTION_CLOSE 关闭连接
NEW_CONNECTION_ID 下发新连接 ID（用于迁移）

⚠️ 流控是两级的：连接级（所有流总和）+ 流级（单条流）。只调流级，连接级会先卡住。排查吞吐问题时两级都要看。

⚠️ RESET_STREAM 才能真正取消。HTTP/2 里 RST_STREAM 之后对端可能还在发数据，QUIC 的 RESET_STREAM 配合 STOP_SENDING 才彻底停。

四、连接迁移：换网络不断线

机制 说明
Connection ID 不依赖 IP/端口，可自定义长度
Path Validation 新路径要验证可达性（防放大攻击）
迁移限制 通常只允许客户端主动迁移

⚠️ 连接迁移需要服务端支持。负载均衡器要能按 CID 做一致性哈希，否则换了路径就打到别的实例，会话找不到。

⚠️ CID 不能包含可追踪信息。早期草案允许编码主机信息，后来因为隐私问题被限制 —— CID 应该是随机值。

五、与 TCP 的关键差异

维度 TCP QUIC
实现位置 内核 用户态
加密 可选（TLS 在外层） 强制内置
队头阻塞 连接级 流级
拥塞控制 内核算法（CUBIC/BBR） 可插拔（应用层选择）
升级速度 依赖内核与中间设备 随应用发布
CPU 开销 低（内核优化好） 高（用户态 + 加密）
中间设备兼容 好 差（部分防火墙拦 UDP）

⚠️ QUIC 的 CPU 开销明显更高。用户态处理 + 每包加密，实测单核吞吐常低于 TCP。高吞吐场景（大文件分发）不一定划算。

⚠️ 部分企业网络直接封 UDP 443。必须有 TCP 回退机制（Alt-Svc 降级），否则用户直接打不开。

六、部署要点

关注点 做法
端口 UDP 443（与 TCP 443 并存）
发现机制 Alt-Svc: h3=":443" 响应头
回退 浏览器自动降级到 HTTP/2
负载均衡 按 Connection ID 做一致性哈希
证书 同 TLS 1.3，需要支持 ECDSA
监控 按版本统计握手成功率

⚠️ Alt-Svc 有缓存期。ma 设太长，回退后浏览器还会尝试 HTTP/3 一段时间。出问题时要能把 ma 调小或去掉。

⚠️ UDP 缓冲区要调大。默认的 UDP 接收缓冲很容易在突发流量下丢包，表现为「QUIC 连接频繁重建」。

七、什么时候值得上 HTTP/3

场景 收益 建议
移动端、弱网 高 优先上
跨国、高延迟链路 高 优先上
静态资源分发 中 视 CDN 支持情况
机房内网服务间 低 不必
大文件上传下载 低（CPU 成本高） 谨慎
老旧客户端为主 低 缓一缓

⚠️ 先看用户网络分布。如果 90% 用户在企业内网、UDP 被拦，上 HTTP/3 只是增加复杂度。

⚠️ 务必保留 HTTP/2 回退。HTTP/3 失败率虽低但非零，没有回退就是直接不可用。

常见坑清单

  • 以为 QUIC 能提升带宽（它优化的是延迟与抖动）
  • 对 POST 启用 0-RTT，导致请求被重放
  • 只调流级流控，连接级先卡住
  • 负载均衡按 IP 哈希，连接迁移后找不到会话
  • Connection ID 里编码主机信息，泄露隐私
  • 没有 TCP 回退，UDP 被拦的用户直接不可用
  • Alt-Svc 的 ma 设太长，出问题无法快速下线
  • UDP 接收缓冲区太小，突发流量丢包
  • 高吞吐场景上 QUIC，CPU 反而成瓶颈
  • 企业内网用户为主却优先上 HTTP/3
