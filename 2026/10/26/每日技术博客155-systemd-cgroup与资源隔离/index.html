开场：一句话结论

cgroup 管「用多少」，namespace 管「看得见什么」。 容器 = 进程 + 这两层约束。OOMKilled 是 cgroup 内存限制触发，而「容器里 ps 看不到宿主进程」是 PID namespace 的效果。

一、systemd：不只是 init

单元类型 后缀 用途
service .service 常驻服务
timer .timer 定时任务（替代 cron）
socket .socket 按需激活
mount .mount 挂载点
target .target 分组（类似运行级别）
slice .slice cgroup 层级分组
指令 作用 常见误用
Restart=on-failure 异常退出重启 always 会导致正常退出也重启
TimeoutStopSec 停止超时后 SIGKILL 设太短，优雅停机来不及
MemoryMax 内存硬限制 与 MemoryHigh 混淆
CPUQuota CPU 配额（百分比） 200% 表示 2 核
TasksMax 最大进程/线程数 默认可能限制并发

⚠️ MemoryHigh 是软限制，MemoryMax 是硬限制。超过 MemoryHigh 会被限流回收，超过 MemoryMax 直接 OOM kill。想要「尽量不超过」用 High，想「绝不超」用 Max。

⚠️ **Type=notify 需要应用支持 sd_notify**。不支持的用 Type=simple，否则 systemd 会一直等启动信号直到超时。

二、timer 替代 cron

能力 cron systemd timer
错过补跑 ❌ ✅ Persistent
随机延迟 ❌ ✅
日志 需自己重定向 ✅ journald
资源限制 ❌ ✅ cgroup
依赖管理 ❌ ✅
秒级精度 ❌ ✅

⚠️ Persistent=true 依赖时间戳文件。如果机器长时间关机，重启后会补跑一次（不是补跑多次）。

⚠️ OnCalendar 的时区跟随系统时区。容器里常是 UTC，容易算错时间。

三、cgroup v2：资源限制的骨架

控制器 文件 作用
CPU cpu.max 配额（quota/period）
CPU cpu.weight 相对权重（1~10000）
内存 memory.max 硬限制
内存 memory.high 软限制（限流）
内存 memory.current 当前用量
IO io.max 每设备 IOPS/带宽
进程 pids.max 最大进程数

⚠️ memory.current 包含 page cache。看起来「内存用满」其实大部分是缓存，会在压力下自动回收。判断真实内存压力要看 memory.stat 里的 anon。

⚠️ cgroup v1 和 v2 的路径完全不同。排查脚本要能区分，否则在 v2 系统上找不到文件。

四、OOM：为什么被杀了

概念 含义
OOM Killer 内存不足时内核选进程杀掉
oom_score 被杀优先级（越大越先死）
cgroup OOM 容器内存超限，只杀容器内进程
OOMKilled 容器退出码 137 + 该标记
现象 原因
容器反复重启 内存限制太低或泄漏
进程被杀但系统内存充足 cgroup 限制触发
memory.current 接近 max 即将 OOM
oom_kill 计数增长 已经发生过

⚠️ **Java 应用在容器里要设 -XX:MaxRAMPercentage**。老版本 JVM 会按宿主机内存算堆大小，容器限制 1G 却开了 4G 堆，必然 OOM。

⚠️ memory.max 不含 swap 的语义在 v2 有变化。memory.swap.max 单独控制，别以为设了 max 就不会用 swap。

五、namespace：看得见什么

namespace 隔离 表现
PID 进程 ID 容器内 PID 1 是应用
Mount 挂载点 独立的文件系统视图
Network 网卡/端口 独立 IP 与端口空间
UTS 主机名 独立 hostname
IPC 信号量/消息队列 独立 IPC
User UID/GID 映射 root 映射为非 root
Cgroup cgroup 视图 看不到宿主其他 cgroup
Time 时钟偏移 较新，少用

⚠️ docker exec 依赖 namespace。容器没有 shell（distroless 镜像）时，用 nsenter 从宿主机进。

⚠️ User namespace 的 root 不是真 root。容器内 uid 0 映射到宿主机的普通用户，但默认 Docker 没开 user namespace remapping，容器内 root 就是宿主 root。

六、排查实战

现象 排查命令
容器被杀 dmesg、memory.events、docker inspect
CPU 被限流 cpu.stat 里的 nr_throttled
进程数打满 pids.current vs pids.max
启动超时 journalctl -u xxx、TimeoutStartSec
服务不重启 检查 Restart= 与退出码

⚠️ nr_throttled 持续增长说明 CPU 配额不足。表现为「延迟抖动但 CPU 使用率不高」—— 因为被强行限流了。

⚠️ TasksMax 打满会让服务无法创建线程。Java/Go 应用线程多，默认值可能不够，表现为 fork: Resource temporarily unavailable。

七、安全加固基线

指令 作用
NoNewPrivileges=true 禁止提权（setuid 失效）
ProtectSystem=strict 整个 / 只读
ProtectHome=true 隐藏 /home
PrivateTmp=true 独立 /tmp
PrivateDevices=true 隐藏设备节点
RestrictAddressFamilies= 限制 socket 类型
SystemCallFilter= 限制系统调用

⚠️ ProtectSystem=strict 会让应用无法写任何路径。必须配 ReadWritePaths= 白名单，否则服务启动即失败。

⚠️ 加固指令要逐个加并验证。一次性全开，排查起来不知道是哪条导致的失败。

常见坑清单

  • Restart=always 导致正常退出也被重启
  • TimeoutStopSec 太短，优雅停机被打断
  • 混淆 MemoryHigh（软）与 MemoryMax（硬）
  • Type=notify 但应用不支持 sd_notify，启动超时
  • OnCalendar 时区不对，定时任务跑错时间
  • 看 memory.current 以为内存泄漏（其实含 page cache）
  • cgroup v1/v2 路径混用，脚本在 v2 上失效
  • JVM 不设 MaxRAMPercentage，容器内 OOM
  • 以为设了 memory.max 就不会用 swap
  • 容器内 root 当真 root 用（默认没开 userns remap）
  • nr_throttled 增长却以为是性能问题
  • TasksMax 打满，服务无法创建线程
  • ProtectSystem=strict 不配 ReadWritePaths，启动失败
