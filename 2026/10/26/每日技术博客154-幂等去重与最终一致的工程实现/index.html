系统设计系列第五篇。「最终一致」不是一句设计口号，它是一张幂等键 + 一个状态机 + 一个补偿任务。少了任何一样，最终一致就会变成「永久不一致」。

五 幂等、去重与最终一致的工程实现 本篇

开场：一句话结论

所有「至少一次」的投递，都必须靠幂等变成「恰好一次」的效果。 MQ、HTTP 重试、超时重发，全都会重复 —— 与其追求「不重复」，不如让重复无害。

一、幂等键怎么选

来源 幂等键 特点
客户端生成 请求体里的 request_id 最可靠，一次业务一个
业务字段组合 order_id + 操作类型 简单，但需保证唯一
服务端生成 时间戳 + 随机数 不可靠（重试时变了）
消息 ID MQ 自带的 message_id 依赖 MQ 实现
反模式 问题
用时间戳做键 重试时间变了，等于没有
用自增 ID 还没创建哪来自增
每次重试重新生成 最典型的错误
用 hash(请求体) 字段顺序/空格变化导致不一致

⚠️ 幂等键必须在「业务意图」层面生成，而不是「HTTP 请求」层面。用户点两次按钮是两个意图（除非前端防抖），但一次意图的三次重试是一个键。

⚠️ hash(整个请求体) 不可靠。JSON 字段顺序、浮点精度、空格都可能变。用显式的 request_id 字段。

二、去重的实现方式

方案 原理 优点 缺点
唯一索引 DB 唯一约束 最可靠，天然并发安全 只适合有库表
Redis SETNX 键存在即重复 快 重启丢数据
状态机 检查当前状态是否允许 语义清晰 需设计状态
去重表 单独记录已处理 ID 灵活 需清理
布隆过滤器 概率判断 省内存 有假阳性

⚠️ SELECT 再 INSERT 不是幂等。两个并发请求都会通过检查，然后插入两条。必须靠唯一索引或分布式锁。

⚠️ Redis 去重必须配 DB 唯一索引兜底。Redis 主从切换可能丢键，只靠它会出现重复。

三、状态机：让重复变成「无操作」

重复场景 状态机行为
重复支付回调 已 PAID → 直接返回成功
重复发货 已 SHIPPED → 无操作
重复取消 已 CANCELLED → 无操作
乱序（先收到发货再收到支付） 拒绝并告警

⚠️ 「已经是目标状态」要返回成功而不是报错。回调方看到报错会继续重试，形成死循环。

⚠️ 乱序必须能识别。消息队列不保证顺序（尤其多分区），先收到「发货」再收到「支付」时不能直接应用。用版本号或状态机拒绝。

四、事务性 outbox：解决「写库 + 发消息」

方案 一致性 复杂度
直接发消息 可能不一致 低
本地事务 + 重试 仍可能丢 低
事务性 outbox 至少一次，可靠 中
两阶段提交（2PC） 强一致 高、性能差
CDC（Debezium） 至少一次 中

⚠️ outbox 投递是「至少一次」。投递成功后、标记已发前崩溃，会导致重复投递。消费端必须幂等。

⚠️ FOR UPDATE SKIP LOCKED 是多实例安全的关键。没有它，多个投递器会抢同一批记录。

五、补偿：处理「做了一半」

场景 补偿动作
扣库存成功、下单失败 释放库存
支付成功、订单超时取消 退款
发货成功、物流同步失败 重试同步
优惠券已用、订单取消 退还优惠券

⚠️ 补偿要「先做后标记」还是「先标记后做」？ 先做后标记可能重复执行（需幂等）；先标记后做可能漏执行（需超时重试）。选「先做后标记 + 幂等」，配合超时扫描。

⚠️ 补偿任务必须有告警。补偿频繁触发说明主流程有问题，不告警就会掩盖真实故障。

六、对账：最后的兜底

对账类型 频率 作用
内部对账（订单 vs 库存） 分钟级 发现同步延迟/丢失
外部对账（本地 vs 支付渠道） 日终 发现资金差异
总量对账（计数校验） 小时级 快速发现大批量异常

⚠️ 对账不是为了「证明系统正确」，而是为了「发现它不正确」。设计时就假设会有差异，先想好怎么发现。

⚠️ 外部对账要处理「单边账」。本地有、渠道没有（或反之），都要有明确的处理流程，不能只看差异数。

七、端到端的幂等设计

层 幂等手段
客户端 按钮防抖 + 固定 request_id
网关 按 request_id 去重（短窗口）
服务 唯一索引 + 状态机
消息 消费端按 message_id 去重
存储 唯一约束、乐观锁
补偿 幂等动作 + 超时扫描

⚠️ 只在最外层做幂等是不够的。网关去重了，但 MQ 重投仍会重复消费。每一层都要能处理重复。

⚠️ 幂等键要有过期策略。永久保存所有 request_id 会让表无限增长。按业务保留 7~30 天，过期后靠唯一索引兜底。

常见坑清单

  • 用时间戳/自增 ID 做幂等键
  • 每次重试重新生成 request_id
  • 用 hash(请求体) 做键，字段顺序变化即失效
  • SELECT 后 INSERT 做去重，并发下重复插入
  • 只靠 Redis 去重，主从切换丢键
  • 状态已是目标值时返回错误，回调方死循环重试
  • 不处理乱序消息，状态被错误覆盖
  • 先写库再发消息，中间失败导致不一致
  • outbox 投递不幂等，重复投递导致重复处理
  • outbox 查询不用 SKIP LOCKED，多实例抢记录
  • 补偿任务不幂等，重复退款/重复释放库存
  • 补偿无告警，掩盖主流程故障
  • 没有对账，差异长期存在
  • 幂等键永久保存，表无限膨胀
