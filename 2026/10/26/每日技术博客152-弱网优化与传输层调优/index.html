五 弱网优化与传输层调优 本篇

开场：一句话结论

弱网下最致命的不是带宽，是「等待」。 一个 RTT 300ms 的链路，串行 5 次请求就是 1.5 秒 —— 无论带宽多大。所以优化的第一优先级永远是减少往返次数，其次才是压缩体积。

一、先量化：弱网到底差在哪

指标 良好 一般 弱网
RTT < 50ms 50~150ms > 300ms
丢包率 < 0.1% 0.1~1% > 2%
抖动 < 10ms 10~50ms > 100ms
带宽 > 10Mbps 1~10Mbps < 1Mbps

⚠️ 丢包比带宽更影响体验。TCP 在 2% 丢包下，吞吐可能掉到理论值的 1/5（CUBIC 的经典问题）。带宽翻倍不如把丢包从 2% 降到 0.5%。

⚠️ 「4G 满格」不代表网络好。信号强度与丢包、抖动无关。必须实测 RTT 与丢包率。

二、减少往返：收益最大的一类优化

手段 省掉 效果
连接复用（keep-alive） TCP + TLS 握手 省 2~3 RTT
TLS 1.3 / 0-RTT 握手往返 省 1~2 RTT
HTTP/3 队头阻塞 弱网下显著
DNS 预解析 / 预连接 DNS 查询 省 1 RTT
请求合并（BFF / GraphQL） 多次请求 省 N-1 RTT
服务端渲染 / 首屏内联 额外请求 省多轮

⚠️ preconnect 不要滥用。每个预连接都占一个 socket 和一次握手，只对确定会用到的域名用，控制在 2~4 个。

⚠️ HTTP/2 的「多路复用」在弱网下是负优化。丢一个包卡住所有流，反而不如多条连接。弱网场景优先 HTTP/3。

三、压缩与增量：减少字节数

手段 压缩比 CPU 成本 适用
gzip 3~5× 低 通用
brotli（静态） 5~8× 中 静态资源，构建时压
brotli（动态） 4~6× 高 谨慎，动态压缩耗 CPU
zstd 4~7× 低 现代替代方案
图片 WebP/AVIF 2~5× —— 图片
增量更新 视改动量 低 大 JSON / 大文件

⚠️ 小响应压缩是负优化。几百字节的 JSON 压缩后可能更大，还多花 CPU。设 min_length 阈值（1KB 以上）。

⚠️ 动态 brotli 的 CPU 开销被严重低估。高 QPS 下动态 brotli 可能吃掉 30% CPU。静态资源预压缩，动态内容用 gzip 或 zstd。

四、传输层参数调优

参数 作用 弱网建议
TCP 初始拥塞窗口 起步能发多少 10（initcwnd）
tcp_slow_start_after_idle 空闲后是否重置 cwnd 关闭
拥塞控制算法 CUBIC / BBR BBR（弱网优势明显）
tcp_notsent_lowat 减少缓冲膨胀 调小
SO_RCVBUF / SO_SNDBUF 缓冲区 按 BDP 调大
TCP Fast Open 握手时带数据 有中间设备兼容问题
算法 弱网表现 说明
CUBIC 丢包即降速 默认，公平性好
BBR 按带宽时延建模 弱网优势明显，但可能不公平
BBRv2 改进公平性 部署较少

⚠️ BBR 在高丢包链路上优势最大，但也更「霸道」。它会抢走 CUBIC 流量的带宽，共享链路上要评估。

⚠️ tcp_slow_start_after_idle 默认开启。长连接空闲几秒后再发数据，cwnd 被重置到初始值，表现为「间歇性卡顿」。

五、应用层容错设计

策略 做法 注意
超时分级 连接超时短、读超时长 避免一刀切
重试 + 退避 指数退避 + 抖动 只对幂等
请求去重 幂等键 防重复提交
降级 返回缓存/兜底内容 保可用性
断点续传 Range 请求 大文件
本地缓存 先展示旧数据 感知速度

⚠️ 没有抖动的重试会形成「同步风暴」。所有客户端同时失败、同时重试，把刚恢复的服务再次打垮。

⚠️ 超时要逐层递减。网关 5s、服务 3s、下游 2s。都设 5s 等于没有预算分配，最外层先超时，内层还在白跑。

六、弱网下的前端体验

手段 效果
骨架屏 降低「空白等待」的焦虑
乐观更新 立即反馈，后台确认
离线优先 Service Worker 缓存
图片懒加载 + 低清占位 首屏更快
请求优先级 关键接口先发
分页/虚拟列表 减少单次数据量

⚠️ 乐观更新必须能回滚。请求失败时要撤回 UI 状态并提示，否则用户以为成功了。

⚠️ Service Worker 缓存策略要谨慎。缓存了 HTML 却忘了更新，用户会长期看到旧版本。用版本化 + 强制更新机制。

七、弱网测试怎么做

方法 说明
Chrome DevTools Network 面板限速 + 丢包模拟
tc netem Linux 上模拟延迟/丢包/抖动
真机 + 弱网卡 最真实
云真机平台 远程弱网环境

⚠️ **只在开发环境用 tc**。生产机器上误加规则会直接影响线上流量。

⚠️ 只测延迟不测丢包是自欺欺人。真实弱网是三者叠加，必须同时模拟延迟、丢包、抖动。

常见坑清单

  • 只优化带宽，不减少往返次数
  • 忽略丢包影响，2% 丢包下吞吐掉到 1/5
  • preconnect 滥用，占满连接数
  • 弱网下仍用 HTTP/2，队头阻塞更严重
  • 对小响应也开压缩，负优化
  • 动态 brotli 吃满 CPU
  • tcp_slow_start_after_idle 未关闭，间歇性卡顿
  • BBR 用在共享链路上，抢占其他流量
  • 重试无抖动，形成同步风暴
  • 超时层层都是 5s，没有预算分配
  • 乐观更新无回滚，用户误以为成功
  • Service Worker 缓存不更新，用户长期看旧版
  • 弱网测试只模拟延迟不模拟丢包
