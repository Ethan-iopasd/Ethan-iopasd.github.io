开场：一句话结论

async fn 编译出来就是一个实现了 Future 的状态机，只有被 poll 才会推进。 没人 poll 它，它就永远停在第一个 .await 上 —— 这不是 bug，是 Rust 异步的惰性语义。

一、async 到底被编译成了什么

编译器大致生成：

关键点 含义
状态机 每个 .await 是一个状态切换点
惰性 创建 Future 不执行任何代码
poll 驱动 只有 poll 才推进，返回 Pending 表示「还没好」
Pin 状态机可能自引用，所以不能随便移动

⚠️ async fn 调用后什么都没发生。let f = fetch_two(1, 2); 只是构造了一个状态机，step_one 一行都没跑。必须 .await 或者 tokio::spawn(f) 才真正开始。

⚠️ Pin 不是装饰。async 块内部的局部变量可能被后续状态引用（自引用结构），移动会导致悬垂指针。Pin<&mut T> 就是在类型层面保证「这个值不会被移动」。

二、Future trait 与执行器

一个极简执行器长这样：

角色 职责 谁提供
Future 描述「怎么推进」 用户代码 / async
Waker 「好了，来 poll 我」的通知机制 运行时（IO 驱动）
Executor 持有任务队列，反复 poll tokio / async-std / smol
Reactor 监听 epoll/kqueue，就绪时 wake tokio 的 IO driver

⚠️ Rust 标准库没有异步运行时。std::future::Future 只是协议，block_on、定时器、TCP 全在 tokio 这类库里。这也是为什么「Rust 异步」的学习曲线陡 —— 你得同时学语言特性和运行时。

⚠️ Poll::Pending 前必须注册 waker。如果返回 Pending 却没人记住这个 Waker，任务就永远不会被唤醒 —— 表现为「程序挂住，CPU 为 0」。这是手写 Future 最常见的错误。

三、tokio 的运行时结构

组件 作用
多线程调度器 N 个 worker 线程共享一个任务队列（work-stealing）
当前线程调度器 单线程，适合 !Send 任务
IO driver 基于 epoll/kqueue/IOCP，就绪时唤醒对应任务
时间轮 管理 sleep / timeout，避免每个定时器一个线程
阻塞线程池 spawn_blocking 的专用池，默认 512 线程

⚠️ #[tokio::main] 只是 Runtime::new().block_on(...) 的语法糖。在异步上下文里再调 block_on 会 panic（Cannot start a runtime from within a runtime）。需要同步调异步，用 spawn_blocking + Handle::block_on，或者干脆把那段逻辑改成异步。

四、Send 报错：跨 .await 持有了非 Send

这是异步 Rust 最高频的编译错误：

编译器会说 future cannot be sent between threads safely。原因：.await 处状态机的局部变量会被存进 Future 结构体，而 spawn 要求 Future: Send。

修法 做法
缩小作用域 用完立刻 drop(guard)，再 .await
换 tokio::sync::Mutex 它的 guard 是 Send（但锁是异步的）
用 std::sync::Mutex 只做短临界区 别在锁里做 IO
不 spawn，用 join! 同线程内并发，不要求 Send

⚠️ std::sync::Mutex 不是不能用，而是不能跨 .await 持有。它比 tokio::sync::Mutex 快得多，短临界区（几微秒）就该用它。只有在锁内需要 .await 时才换 tokio 版本。

⚠️ **报错位置经常指向 spawn，而不是真正的 await**。看到 future cannot be sent 时，去函数里找所有 .await，逐个检查之前是否有 Rc、RefCell、MutexGuard、&T（非 'static 引用）还活着。

五、阻塞是异步的头号杀手

阻塞操作 后果 正确做法
std::fs::* 卡住一个 worker tokio::fs 或 spawn_blocking
reqwest::blocking 同上，且会 panic reqwest 异步版
CPU 密集计算 卡住 worker 数百毫秒 spawn_blocking 或 rayon
std::thread::sleep 卡住 worker tokio::time::sleep
同步 Mutex 长临界区 其他任务排队 缩短临界区

⚠️ tokio 默认 worker 数 = CPU 核数。8 核机器上只要 8 个任务同时做同步阻塞，整个运行时就会「假死」—— 表现是 QPS 骤降但 CPU 不高，非常难查。

⚠️ **tokio::fs 内部其实就是 spawn_blocking**，不是真正的 IO 多路复用（Linux 上文件 IO 不支持 epoll）。所以大量文件操作时，阻塞池也会被打满，要留意 spawn_blocking 的队列长度。

六、结构化并发：join / select / spawn

API 语义 取消行为
join! 并发等待全部完成 任一 panic 会传播
try_join! 并发，任一失败即返回 其余被 drop（取消）
select! 等第一个完成 其余分支被取消
spawn 独立任务，detached 主任务结束不影响它
JoinSet 管理一组任务 可整体取消、可收集结果

⚠️ select! 的取消是「drop future」。如果被取消的分支里有 spawn 出去的子任务，那些子任务不会被取消，会继续在后台跑。要级联取消，用 JoinSet 或 CancellationToken。

⚠️ select! 默认随机选择就绪分支（公平），但不是所有分支都会被 poll —— 一旦某个分支先完成，其余分支的 future 直接被丢弃。所以分支里不要放「有副作用且必须完成」的操作。

⚠️ spawn 出去的任务不会随主任务结束而终止。main 返回时运行时关闭，这些任务被强制丢弃 —— 如果它们正在写文件，可能留下半个文件。需要优雅退出就用 JoinSet 或 CancellationToken + select!。

七、async trait 与 impl Trait

限制 说明
不是对象安全 Box<dyn Repo> 编译不过
需要 Send 边界时麻烦 用 trait Repo: Send 或 #[async_trait]
返回类型无法命名 只能 impl Future，不能写具体类型

⚠️ #[async_trait] 每个方法都会 Box::pin 一次，在热路径上（每请求调用几十次）会有可测量的开销。能用原生 async fn in trait 就别用它。

八、常见性能陷阱

现象 原因 修法
异步比同步还慢 小任务 spawn 开销超过收益 批量合并，或直接顺序执行
CPU 不高但延迟大 某处同步阻塞 找 std:: 调用，换 tokio 版
内存持续上涨 任务泄漏（spawn 后不回收） JoinSet 管理生命周期
定时器精度差 tokio 时间轮精度约 1ms 别依赖亚毫秒定时
锁竞争严重 全局 Mutex 分片锁 / 无锁结构

⚠️ tokio::spawn 有成本（约几百纳秒 + 一次堆分配）。一个请求里 spawn 上千个小任务，开销可能超过实际工作。判断标准：任务耗时是否显著大于 1 微秒。

⚠️ #[tokio::main] 的 worker 数不要盲目调大。超过 CPU 核数只会增加调度开销。IO 密集场景想提高并发，应该增大「同时在途的任务数」，而不是线程数。

常见坑清单

  • 以为 async fn 调用即执行（实际要 poll）
  • 手写 Future 返回 Pending 却没注册 waker，任务永久挂起
  • 跨 .await 持有 MutexGuard / Rc / RefCell，Send 报错
  • 在异步上下文里调 block_on，直接 panic
  • 用 std::fs / reqwest::blocking 卡死 worker
  • CPU 密集任务不丢 spawn_blocking
  • 以为 tokio::fs 是真异步（内部仍是阻塞池）
  • select! 分支里有必须完成的副作用操作
  • select! 取消后子任务仍在后台跑
  • spawn 的任务无人管理，泄漏
  • main 结束时后台任务正在写文件，留下半成品
  • 用 #[async_trait] 在热路径上，每调用一次装箱一次
  • 每个请求 spawn 上千个小任务，开销超过收益
  • 盲目调大 worker 线程数，调度开销反增
