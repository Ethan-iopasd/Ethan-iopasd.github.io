开场：一句话结论

Python 的性能问题 90% 不在 Python 本身，而在「用错了数据结构」和「在循环里做了本可以不做的事」。 先用 cProfile 找到真正的那 10%，再谈优化 —— 凭直觉优化的结果通常是让代码变难读而快 3%。

一、标准库里的隐藏成本

写法 问题 更快/更安全的写法
if x in list O(n) 线性扫描 set / dict，O(1)
"".join([...]) vs += += 每次重建字符串 一律用 join
for i in range(len(a)): a[i] 索引开销 + 可读性差 for x in a / enumerate
sorted(...) 后再 [0] O(n log n) 取最小值 min(...)，O(n)
list(set(a)) 去重 丢失顺序 dict.fromkeys(a)
os.path.join 拼路径 老 API，返回 str pathlib.Path
re.match 在循环里编译 每次重新编译正则 预编译 re.compile
datetime.now() 带时区 naive datetime 不可比较 datetime.now(timezone.utc)

⚠️ in list 是最高频的性能杀手。一个 1 万次的循环里做 x in big_list（1 万个元素），总比较次数是 1 亿。换成 set 后是 1 万次哈希查找，差三个数量级。

⚠️ re 模块有内部缓存（默认 512 条），所以不预编译通常也不至于太慢 —— 但缓存是按 pattern 字符串做 key 的，动态拼接的正则会撑爆缓存，这时预编译是必须的。

二、可变默认参数：最经典的坑

写法 结果
def f(a=[]) 所有调用共享同一个列表
def f(a=None) + if a is None: a = [] 每次新建
def f(a=()) 元组不可变，安全

⚠️ 不只是 []，{}、set()、以及任何可变对象（包括自定义类的实例）都有这个问题。甚至 datetime.now() 这种「看起来每次不同」的默认值也只在定义时求值一次。

⚠️ 类的属性也有类似陷阱：class A: items = [] 是类属性，所有实例共享；写成 self.items = [] 在 __init__ 里才是实例属性。

三、缓存：functools.lru_cache 的正确用法

参数 含义 建议
maxsize 最多缓存多少条（LRU 淘汰） 按内存预算设，None 表示不淘汰（危险）
typed 1 和 1.0 是否视为不同 key 一般 False 即可
陷阱 说明
参数必须可哈希 传 list / dict 直接报错
返回值是共享的 返回可变对象会被调用方改坏
不感知外部状态 依赖数据库/文件的函数缓存后永远返回旧值
实例方法缓存会泄漏 self 进了 key，实例不被回收
maxsize=None 无上限，长跑服务会 OOM

⚠️ @lru_cache 装饰在实例方法上，self 会进入缓存 key，导致实例无法被 GC 回收。长生命周期对象（如单例 Repo）问题不大，但短生命周期对象（每请求 new 一个）会直接内存泄漏。

⚠️ 缓存不感知外部变化。缓存了「查数据库」的函数，数据更新后仍然返回旧值。要么手动 cache_clear()，要么把版本号/时间戳作为参数传进去。

四、dataclass 与 __slots__：内存与可读性

写法 每实例内存（64 位，粗估） 说明
普通类 ~150+ 字节（含 __dict__） 灵活，可动态加属性
@dataclass 同上，只是省了样板代码 可读性提升
@dataclass(slots=True) ~50 字节 无 __dict__，省 2~3 倍

⚠️ slots=True 之后不能动态加属性，也不能被 pickle 默认处理（需要 __getstate__）。有继承时，父类也要 slots=True 才有效果。

⚠️ field(default_factory=list) 不是可选项。tags: list[str] = [] 会直接报 ValueError: mutable default，dataclass 已经帮你拦住了这个坑。

五、剖析：先测量再优化

工具 用途 开销
cProfile 函数级耗时统计 中等（2~5 倍）
timeit 微基准 低
py-spy 采样分析，可挂到运行中的进程 极低
tracemalloc 内存分配追踪 高
line_profiler 行级耗时 高

⚠️ cProfile 会放大函数调用开销，所以它对「大量小函数调用」的分析结果偏高。判断热点要看 tottime（函数自身耗时）而不是 cumtime（含子调用）。

⚠️ 微基准 timeit 的结果常常骗人。真实代码里有缓存效应、分支预测、GC 压力，单函数快 20% 在整体上可能完全看不出来。优化必须用端到端指标验证。

六、什么时候该换工具

场景 Python 纯实现 替代方案 加速比
数值计算 嵌套循环 NumPy 向量化 50~500×
大批量表格处理 csv + 循环 pandas / Polars 10~100×
字符串批量匹配 re 循环 re 预编译 + findall 3~10×
热点函数 Python 函数 Cython / Rust 扩展（PyO3） 10~100×
IO 密集 同步阻塞 asyncio / 线程池 取决于并发度
CPU 密集 多线程（受 GIL） 多进程 / concurrent.futures 接近核数

⚠️ NumPy 的优势在「大数组一次操作」，不是「把循环换成 NumPy 函数」。如果在 Python 循环里逐个元素调 NumPy，反而比纯 Python 慢（每次调用都有封装开销）。

⚠️ 别过早引入 Cython / Rust 扩展。构建链、跨平台分发、调试成本都会上升。先确认：算法复杂度是否可降？数据结构是否选对？能否向量化？这三步通常能拿到 90% 的收益。

七、几个高频陷阱速查

陷阱 表现 修法
is 比较值 小整数/字符串偶然为 True 值比较用 ==
闭包捕获循环变量 所有 lambda 拿到最后一个值 用默认参数绑定 lambda i=i:
修改正在遍历的列表 元素被跳过 遍历副本 for x in list(a)
except Exception: pass 错误被吞，问题难查 至少 logger.exception
dict 遍历时增删 RuntimeError: changed size 先收集 key 再改
浮点累加 结果有微小误差 math.fsum 或 Decimal
open 不关闭 文件句柄泄漏 with open(...)
大文件 read() 内存爆掉 逐行 / 分块读

⚠️ except Exception: pass 是技术债的头号来源。至少记录堆栈，否则线上问题只能靠猜。要「忽略」也应显式写出预期的异常类型。

⚠️ 浮点累加误差会累积。财务计算用 Decimal，科学计算用 math.fsum，都别用裸 +=。

常见坑清单

  • 循环里 x in list，O(n²) 而不自知
  • 用 += 拼字符串，每次重建
  • 循环内重复编译正则
  • 可变默认参数 def f(a=[])
  • 类属性当实例属性用，所有实例共享
  • lru_cache 装饰实例方法，self 常驻导致泄漏
  • 缓存了依赖外部状态的函数，数据更新后返回旧值
  • lru_cache(maxsize=None) 在长跑服务里 OOM
  • dataclass 用 tags: list = []（已报错，但改成 None 后又忘了初始化）
  • 用 cumtime 判断热点，优化了错误的函数
  • 凭 timeit 微基准下结论，没做端到端验证
  • 在 Python 循环里逐元素调 NumPy，比纯 Python 还慢
  • is 比较值
  • 闭包捕获循环变量
  • except Exception: pass 吞掉错误
  • 遍历 dict 时增删
