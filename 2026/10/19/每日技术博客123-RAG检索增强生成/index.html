开场：一句话结论

RAG 的效果上限由召回决定，不是由模型决定。 检索不到的东西，再强的模型也编不出来；而检索到但塞不进上下文，等于没检索。所以优化顺序永远是：切分 → 召回 → 重排 → 压缩 → 生成，倒过来做是浪费时间。

一、五段流水线

阶段 输入 输出 失败表现
切分（Chunking） 原始文档 语义完整的块 答案被切断，跨块信息拼不起来
索引（Embedding） 块 向量 相似度算不准，语义相近的排不到一起
召回（Retrieval） query Top-K 候选 正确块不在候选里
重排（Rerank） 候选 精排结果 正确块排在第 20 位，被截断
生成（Generation） 上下文 + query 回答 有材料却编造、引用错位

⚠️ 最常见的误判：回答不对就换更大的模型。但 80% 的 RAG 问题在召回阶段 —— 先把「正确块是否出现在 Top-K 里」测出来，再谈别的。

二、切分：RAG 里最被低估的一步

策略 做法 优点 缺点
定长切分 每 N 个 token 切一刀 简单、块大小均匀 语义断裂
按结构切 按标题 / 段落 / 代码块 语义完整 块大小不均
递归切分 先按段落，超长再按句子 平衡 仍可能切断表格
语义切分 按 embedding 相似度找断点 语义最完整 慢，成本高
父子块 子块检索、父块喂给模型 兼顾精度与上下文 实现复杂
参数 建议值 说明
块大小 300~800 token 太小丢上下文，太大稀释相似度
重叠 10%~15% 防止关键句被切断
元数据 来源、标题、时间、权限 过滤和引用都靠它

⚠️ 块太大是隐形的召回杀手。一个 2000 token 的块里只有一句话相关，embedding 会被无关内容稀释，相似度排不上去。而块太小又会丢上下文 —— 折中方案是小块检索、大块生成（父文档检索）。

⚠️ 表格和代码不要按字符切。Markdown 表格切一半就语义全失，代码切一半直接语法错误。这两类要整块保留，或者用专门的解析器转成结构化描述再切。

三、向量化与召回

检索方式 原理 强项 弱项
稠密向量（Dense） 语义相似度 同义改写、跨语言 精确匹配（型号、编号）差
稀疏向量（BM25） 词频统计 关键词、专有名词 不理解同义词
混合检索（Hybrid） 两路结果融合 兼顾 需要调权重
多向量 每块生成多个问题向量 提升召回 索引膨胀

⚠️ Dense 和 BM25 的分数不可直接相加。一个是余弦相似度（0~1），一个是无上界的 BM25 分值，加权求和会被量纲支配。用 RRF（倒数排名融合） 只依赖名次，不需要归一化，是混合检索的默认解。

⚠️ 归一化 embedding 后，余弦相似度等于内积，可以直接用内积索引（更快）。忘了归一化会让长文本天然分数偏高，产生系统性偏差。

四、重排：把对的那条顶上来

粗召回 20 条，真正相关的可能排在第 12 位。Rerank 用交叉编码器逐对打分：

方式 原理 速度 精度
Bi-encoder（召回用） query 和 doc 各自编码 快（可预建索引） 中
Cross-encoder（重排用） query+doc 拼接后一起过模型 慢（不能预建） 高

⚠️ Cross-encoder 不能用来做全库检索，因为每个候选都要跑一次完整前向。它的位置只能是「在 Top-20 里选 Top-5」。这也是为什么召回和重排必须分两段。

⚠️ 重排不是万能的。如果正确块压根没进 Top-20，重排也救不回来 —— 先加大召回 k（比如 50），再靠重排收敛，比调重排模型有效。

五、上下文组装

召回 5 条 800 token 的块 = 4000 token，加上系统提示和对话历史，很容易撑爆上下文，或者把关键信息挤到中间。

问题 对策
总长超限 按分数截断、摘要压缩
无关内容稀释 每块先做相关性过滤
关键信息在中间被忽略（lost in the middle） 把最相关的放开头和结尾
引用错位 每块带编号，要求模型标注 [1]

⚠️ 「lost in the middle」是实测现象，不是玄学：模型对上下文开头和结尾的利用率显著高于中间。所以别简单按分数从高到低排，把最强的放两头。

⚠️ 块之间要加分隔符和编号，否则模型会把相邻块的内容混成一段，引用时也说不清来自哪。

六、评估：不测就是瞎调

指标 衡量什么 怎么算
Recall@K 正确块是否进了 Top-K 人工标注或用 LLM 判定
MRR 正确块排多靠前 倒数名次均值
Faithfulness 回答是否忠于材料 LLM 裁判：有无编造
Answer Relevance 回答是否切题 LLM 裁判
Context Precision 塞进去的块有多少有用 有用块 / 总块数

⚠️ 没有标注就先用 LLM 造测试集：拿每篇文档生成 5 个问题，问题对应的块就是 gold。这套自举标注能覆盖大部分召回问题，比拍脑袋调参靠谱得多。

七、工程落地要点

关注点 做法
增量更新 文档变更时只重建该文档的块，用 doc_id 做删除
权限隔离 元数据带 ACL，检索时先过滤再算相似度
多租户 索引分区或按 tenant_id 过滤
缓存 query → 结果缓存，高频问题直接命中
可观测 记录每次召回的 ids 和分数，出问题能复盘
降级 检索服务挂了要有「无 RAG 直答」的兜底

⚠️ 权限过滤必须在召回前做。先召回再过滤会导致「本来能召回 20 条，过滤后只剩 2 条」，且泄露了无权文档的存在性。用带过滤条件的向量索引（pgvector 的 WHERE、Milvus 的 scalar filter）。

⚠️ 向量库不是必须的。文档少于几千块时，用 numpy 暴力算余弦相似度（几千 × 768 维）只要几毫秒，比维护一套向量库简单得多。

常见坑清单

  • 块切得太大，embedding 被无关内容稀释，召回排不上去
  • 块切得太小，答案跨块拼不起来
  • 按字符切表格和代码，语义直接毁掉
  • embedding 忘了归一化，长文本系统性占优
  • Dense 和 BM25 的分数直接加权相加（量纲不同）
  • 只做稠密检索，型号、编号这类精确匹配召回不到
  • 粗召回 k 设得太小，重排无米下锅
  • 用 cross-encoder 做全库检索，慢到不可用
  • 上下文按分数从高到低排，最强证据落在中间被忽略
  • 塞进去的块没有编号，模型引用错位
  • 先召回再按权限过滤，泄露无权文档的存在性
  • 完全没有评估集，全凭体感调参
  • 回答不对就换更大的模型，其实是召回问题
