开场：一句话结论

requests 决定「能不能调度上去」，limits 决定「跑起来会不会被杀」，HPA 决定「加几个副本」 —— 三者是三套独立机制，任何一个配错都会表现为「Pod 起不来」或「扩容了但没用」。

一、调度器到底怎么选节点

kube-scheduler 对一个 Pending 的 Pod 做两件事：Filter（哪些节点可行）→ Score（哪个最好）→ Bind。

阶段 行为 失败表现
Filter 逐个插件过滤，任一插件否决即淘汰 节点列表为空 → Pod Pending，Event FailedScheduling
Score 各插件给 0~100 分，按权重加权求和 分数相同则随机选一个
Bind 写 pod.spec.nodeName，通知 kubelet 极少数情况 Bind 失败会重试

参与 Filter / Score 的核心插件：

插件 作用 阶段
NodeResourcesFit 判断节点剩余 requests 是否装得下 Filter + Score
NodeAffinity / NodeSelector 匹配 nodeSelector 与 nodeAffinity Filter
TaintToleration 匹配污点与容忍 Filter
InterPodAffinity Pod 亲和 / 反亲和 Filter + Score
PodTopologySpread 拓扑分布约束 Filter + Score
ImageLocality 节点上已有镜像加分 Score

打分默认策略是 LeastAllocated（最小分配）：剩余资源比例越高的节点得分越高，效果是「摊平」，而不是「装箱」。这也是为什么小集群里 Pod 看起来总被均匀撒开。

⚠️ **kubectl top 显示的是真实用量，调度看的是 requests**。节点 CPU 实际只用了 10%，但 requests 已经占满，新 Pod 照样 Insufficient cpu。排查 Pending 先看 kubectl describe node | grep -A8 "Allocated resources"。

⚠️ FailedScheduling 里的 0/6 是可行节点数 / 总节点数，不是错误码。数字对不上时先确认节点是否 Ready、是否有 node.kubernetes.io/unschedulable 污点。

二、requests 与 limits 的真实语义

字段 谁在用 超了会怎样
requests.cpu 调度器记账、HPA 利用率分母 不会「超」，只是影响调度与 HPA
requests.memory 调度器记账、OOM score 参考 同上
limits.cpu kubelet 写 cgroup cpu.max（CFS quota） 被节流，不变慢变卡，不报错
limits.memory kubelet 写 cgroup memory.max OOMKilled，容器退出码 137

CPU 是可压缩资源：limit 到顶就是等 quota，表现为延迟抖动；内存不可压缩：limit 到顶就是杀进程。

CFS 的默认周期是 100ms，limits.cpu: 1 等价于「每 100ms 最多用 100ms CPU 时间」。一个 8 线程的应用在 100ms 窗口里只要并发跑满，就会把 quota 吃光，剩下时间全部被挂起 —— 这就是「CPU 没用满但接口 RT 抖动」的常见来源。

⚠️ CPU limit 不是「保险丝」，是「刹车片」。对延迟敏感的服务，常见做法是只设 requests 不设 CPU limits（Burstable），靠 requests 保证调度份额；内存 limit 则必须设，否则一个泄漏就能拖垮整个节点。

⚠️ requests == limits 得到 Guaranteed QoS，抗驱逐能力最强，但同时意味着 CPU 被硬限。Guaranteed 不等于高性能，Go / Java 这类多线程运行时尤其容易撞 quota。

⚠️ 不写 requests 的 Pod 是 BestEffort，节点压力大时第一批被驱逐；而且 HPA 的 targetAverageUtilization 分母为 0，指标直接失效。

三、把 Pod 放到该放的地方：四层约束

手段 表达能力 代价 典型场景
nodeSelector 等值匹配节点标签 最低 disktype=ssd、gpu=true
nodeAffinity 支持 In / NotIn / Exists / Gt，分 required / preferred 低 指定机型、可用区
podAffinity / podAntiAffinity 按其他 Pod 的标签聚集或分散 高，大集群下 Filter 很慢 同可用区就近、同节点互斥
topologySpreadConstraints 按拓扑域控制数量偏差 中 多可用区 / 多机架均匀分布

硬反亲和是最容易把集群搞挂的写法：

改用拓扑分布，超限时是「尽量均摊」而不是「直接不给调度」：

maxSkew 的语义随 whenUnsatisfiable 变化：

取值 含义 违反时
DoNotSchedule（默认） 目标域 Pod 数 − 全局最小值 ≤ maxSkew 拒绝调度，Pod Pending
ScheduleAnyway 同上，但只作为打分偏好 仍然调度，尽量选偏差小的域

全局最小值 = 各合格域中匹配 Pod 数的最小值；当合格域数量少于 minDomains 时，最小值按 0 计算 —— 这是防止「只有 2 个可用区，却以为摊平了」的关键。

⚠️ 不加 matchLabelKeys: [pod-template-hash]，滚动更新会卡住：新旧两个 ReplicaSet 的 Pod 标签相同，被算进同一个域，旧 Pod 还没退完就判定「该域已满」，新 Pod 全部 Pending。该字段 1.27 进入 Beta，1.34 起改为显式合并进 labelSelector。

⚠️ nodeTaintsPolicy / nodeAffinityPolicy 在 1.26 进入 Beta、1.33 GA；老集群不写这两个字段时，带污点的节点也会被计入分母，导致分布判断失真。

⚠️ podAffinity 的 requiredDuringScheduling 会让调度复杂度随 Pod 数上升，几千 Pod 的集群里能明显拖慢调度吞吐。能用 topologySpreadConstraints 就别用硬亲和。

四、污点、容忍与优先级抢占

effect 含义 已有 Pod 会怎样
NoSchedule 新 Pod 不允许调度 无影响
PreferNoSchedule 尽量不调度（软约束） 无影响
NoExecute 不允许调度 不匹配容忍的 Pod 被驱逐

专用节点池的标准写法：节点打污点，业务加容忍 + 亲和，防止别的负载蹭进来。

优先级与抢占：

内置 PriorityClass value 用途
system-cluster-critical 2000000000 控制面组件
system-node-critical 2000001000 每节点必需组件

⚠️ 容忍只是「允许」，不是「吸引」。只写 toleration 不写 nodeAffinity，Pod 会随机落到普通节点上 —— 专用节点池必须两者都写。

⚠️ 抢占不受 PDB 保护。高优先级 Pod 进来时，调度器会直接驱逐低优先级 Pod，PodDisruptionBudget 只在 eviction 子资源（drain、descheduler）路径上生效。

⚠️ 抢占会先「假装」驱逐受害者来试算可行性，失败则回滚。如果看到 Pod 反复 Pending 且事件里出现 preemption: 0/6 nodes are available，说明连抢占都凑不出资源 —— 该加节点了。

五、HPA：一条公式和四个边界

HPA 的核心就一行：

targetAverageUtilization 模式下，currentMetricValue 是所有目标 Pod 的平均使用量，分母是它们的 requests 之和。

默认行为（不写 behavior 时）：

参数 默认值 说明
容差 --horizontal-pod-autoscaler-tolerance 0.1 比率在 0.9~1.1 之间不动，防抖
同步周期 --horizontal-pod-autoscaler-sync-period 15s 控制循环间隔，不是实时
scaleUp.stabilizationWindowSeconds 0 扩容立即生效
scaleDown.stabilizationWindowSeconds 300 缩容取 5 分钟内最高建议值
--horizontal-pod-autoscaler-cpu-initialization-period 5m 新 Pod 启动期 CPU 不计入
--horizontal-pod-autoscaler-initial-readiness-delay 30s 刚 Ready 的 Pod 视为未就绪

支持的指标类型：

type 来源 典型用法
Resource metrics.k8s.io（metrics-server） CPU / 内存利用率
ContainerResource 同上，按容器维度 多容器 Pod 只看主容器
Pods custom.metrics.k8s.io 每 Pod 平均 QPS
Object 同上 Ingress 的请求数、Service 的连接数
External external.metrics.k8s.io 云监控、队列长度

⚠️ HPA 的分母是 requests，不是 limits，也不是节点容量。requests.cpu: 100m 而实际常驻 800m，利用率会常年 800%，HPA 直接顶到 maxReplicas。requests 配错，HPA 的所有参数都是噪音。

⚠️ 多个指标取最大值，且取不到指标时不缩容。一个指标报错、另一个建议缩容，HPA 会跳过缩容；只要有指标建议扩容，仍然会扩。这是刻意的保守设计，别指望它「指标缺失就自动降级」。

⚠️ HPA 缩不到 0，minReplicas 最小是 1。真需要 0 副本（队列消费、定时任务）只能用 KEDA，或者开 HPAScaleToZero 这个 alpha 特性门控并改用 Object / External 指标。

⚠️ GitOps 会把 HPA 改回的副本数又写回去。清单里保留 replicas: 3，Argo CD 每次同步都会覆盖 HPA 的决策。要么删掉 replicas 字段，要么配 ignoreDifferences。

排查三连：

六、VPA 与 KEDA：纵向与事件驱动

VPA 解决「requests 该写多少」：Recommender 看历史用量出建议，Updater 改 Pod 资源。

updateMode 行为 适用
Off 只出建议，不改 生产首选，人工 review
Initial 只在创建时设值 新建 Pod 生效
Recreate 改资源时重建 Pod 有中断，慎用
InPlaceOrRecreate 优先原地改，不行再重建 依赖 In-Place Pod Resize

原地调整（KEP-1287）在 1.33 进入 Beta、1.35 GA，意味着改 CPU / 内存不再必然重启容器 —— 但内存下调仍然受限，缩容方向不要指望无缝。

⚠️ VPA 与 HPA 不要盯同一个指标。两者同时改 CPU，会互相打架：HPA 加副本降低单 Pod 利用率，VPA 又把 requests 调小，形成震荡。官方建议是 VPA 管内存、HPA 管 CPU，或 VPA 只做 Off 出建议。

KEDA 在 HPA 之上补了「事件源」和「缩到 0」两块：它自己创建并管理 HPA，指标来自 ScaledObject 里声明的触发器。

组件 扩什么 指标来源 能到 0
HPA Pod 副本 metrics-server / 自定义 API 否
VPA 单 Pod 资源 历史用量 —
KEDA Pod 副本（生成 HPA） 队列、Kafka lag、Prometheus 等 是
Cluster Autoscaler / Karpenter 节点 Pending Pod 是（节点）

⚠️ 缩到 0 只适合「有队列兜底」的消费者。HTTP 服务缩到 0 需要 KEDA 的 HTTP Add-on 做请求缓冲，否则冷启动期间请求直接失败。

⚠️ KEDA 的 pollingInterval 决定响应速度上限，cooldownPeriod 决定抖动成本。两个值都调小，等于把队列当缓存用，下游会被反复拉起打爆。

七、PDB 与节点维护

policy/v1 自 1.21 可用，policy/v1beta1 在 1.25 被移除。minAvailable 与 maxUnavailable 只能二选一。

⚠️ PDB 只管「自愿中断」：kubectl drain、eviction API、descheduler 受它约束；节点宕机、OOM、抢占、滚动更新（Deployment 自己删 Pod）都不受它保护。

⚠️ minAvailable 等于副本数，ALLOWED 就是 0，drain 会永久卡住。单副本服务写 PDB 等于给自己上锁。

⚠️ PDB 按 selector 统计 Pod，滚动更新期间新旧 ReplicaSet 都在统计范围内。maxUnavailable 配得太紧，会和 maxSurge 打架，表现为更新卡在 1 old pod terminating。

八、容量规划：从 requests 到节点数

一个可分配的节点，Allocatable 比 Capacity 小：

资源 Capacity 预留 Allocatable
CPU 16 核 1.0 核 15.0 核
内存 64Gi 4Gi 60Gi

按「每 Pod requests 500m / 1Gi，峰值 60 副本」估算：

项 计算 结果
CPU 需求 60 × 0.5 30 核
内存需求 60 × 1Gi 60Gi
单节点可承载 min(15/0.5, 60/1) 15 个 Pod
所需节点 ceil(60 / 15) 4 台
加缓冲（N+1） 4 + 1 5 台

⚠️ **DaemonSet 也占 requests**。日志采集、CNI、监控 agent 每个节点固定吃掉几百 mCPU 和几百 Mi 内存，容量估算里漏掉它们，实际可用副本会少 5%~10%。

⚠️ 扩容是有延迟的链路：HPA 发现指标（≤15s）→ 创建 Pod → 调度（秒级）→ 拉镜像（可能几十秒）→ 就绪探针通过 → 才进 Endpoints。整条链路常见 30s~2min，initialDelaySeconds 设大了会更久。突发流量靠 HPA 兜不住，前面得有队列或限流。

⚠️ 节点扩容比 Pod 扩容慢一个量级：Pod Pending 后 Cluster Autoscaler 才触发，云上开机器通常 1~3 分钟。所以 maxReplicas 要和节点池上限一起算，否则 HPA 扩到 30，节点只够 20。

常见坑清单

  • requests 按「平均值」写，而不是按 P95 / 启动峰值写，导致节点超卖、OOM 频发
  • 只设 limits 不设 requests，Pod 变成 BestEffort，HPA 分母为 0
  • CPU limits 设得和 requests 一样，Guaranteed 了但被 CFS 节流，RT 抖动查不出来
  • 用 requiredDuringScheduling 的 podAntiAffinity 做「一节点一副本」，副本数一超节点数就全 Pending
  • topologySpreadConstraints 忘了 matchLabelKeys: [pod-template-hash]，滚动更新卡死
  • 只写 tolerations 不写 nodeAffinity，专用节点池形同虚设
  • HPA 的 minReplicas 设成 1，滚动更新期间容量直接腰斩
  • HPA 指标长期 <unknown>，没意识到 metrics-server 挂了或证书过期
  • VPA 与 HPA 同时盯 CPU，requests 与副本数互相追着改，指标震荡
  • GitOps 清单里保留 replicas 字段，每次同步把 HPA 的决策覆盖掉
  • PDB 的 minAvailable 等于副本数，kubectl drain 永远卡在 evicting
  • 容量估算漏掉 DaemonSet 与 sidecar 的 requests
  • 以为 maxReplicas 是硬保障，实际节点池上限先到，Pod 全部 Pending
