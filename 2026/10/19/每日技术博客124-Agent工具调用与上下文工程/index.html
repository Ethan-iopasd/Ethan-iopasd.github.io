开场：一句话结论

Agent 的可靠性 ≈ 单步成功率 ^ 步数。 单步 95% 的准确率跑 20 步，端到端只剩 36%。所以工程重点从来不是「让单步更强」，而是减少步数、缩小每步的决策空间、给失败留退路。

一、Agent 的最小构成

组件 作用 缺了会怎样
模型（LLM） 决策中枢 ——
循环（Loop） 反复「思考-行动-观察」 一次性回答，无法多步
工具（Tools） 与外部世界交互 只能空谈，无法查证与执行
状态（State） 记住已做过什么 原地打转，重复调用
终止条件 知道何时停 无限循环或过早放弃

⚠️ 必须硬性限制步数。没有 max_steps 的 Agent 在工具返回空结果时会陷入死循环，一夜烧掉几百美元。生产环境还要加 token 预算和墙钟时间上限。

二、工具设计：Agent 成败的分水岭

工具不是「把 API 包一层」就完事，它其实是给模型看的用户界面。

设计要点 反例 正例
名称自解释 q1、do_it search_orders_by_date
参数少而明确 一个 params: object 三个具名参数，带类型和枚举
描述写清边界 「查询数据」 「按日期查订单，仅支持近 90 天」
返回结构化 一大段 HTML JSON，字段精简
错误可读 500 Internal Error 「未找到订单 123，请确认单号」
幂等性 每次调用都下单 带 idempotency_key

⚠️ 工具数量超过 20 个，模型的选择准确率会明显下降。解法是分层：先给一个 list_capabilities() 或按场景分组，让模型先选「域」再选「工具」，而不是一次性塞 50 个函数定义。

⚠️ 工具返回值也会占上下文。一次返回 5000 行 JSON，下一轮就爆了。在工具内部做截断和摘要，只回必要字段，比在 prompt 里求模型「忽略无关内容」有效得多。

三、上下文工程：Agent 的核心战场

多轮 Agent 的上下文会不断膨胀：每轮的工具结果都堆在 messages 里。

策略 做法 适用
滑动窗口 只保留最近 N 轮 短任务
摘要压缩 旧轮次交给模型总结成一段 长对话
结构化状态 关键事实抽成 JSON 状态机 流程型任务
工具结果截断 只保留前 N 字符 + 摘要 所有场景
子 Agent 隔离 子任务在独立上下文跑完，只回结论 深度探索
外置记忆 写文件 / 数据库，用时再检索 跨会话

⚠️ 摘要会丢细节，而 Agent 恰恰依赖细节（比如某个 ID、某个报错）。所以关键事实要外置成结构化状态（一个 JSON 字典），而不是指望摘要保留。

⚠️ 不要把「已完成的步骤」只放在对话历史里。模型会忘、会被压缩掉。用一个显式的 todo 列表，每轮都重新注入，比任何提示词技巧都管用。

四、规划与反思模式

模式 做法 优点 缺点
ReAct 思考 → 行动 → 观察，交替进行 简单、通用 步数多，易打转
Plan-and-Execute 先出完整计划，再逐步执行 全局视野 计划错则全错
Reflection 执行后自评，不满意则重来 质量高 成本翻倍
多 Agent 协作 规划者 / 执行者 / 评审者分工 分工清晰 通信开销大
图编排 显式状态机，节点是步骤 可控、可观测 不够灵活

⚠️ Reflection 不是免费的。每轮自评都要多一次完整前向，成本翻倍且可能陷入「反复自我否定」。建议只在最终交付前跑一次，而不是每步都跑。

⚠️ Plan-and-Execute 的失败模式是「计划与执行脱节」：计划里说「先查 A 再查 B」，但执行时发现 A 不存在。必须允许重规划（replan），否则一步卡死全程。

五、可靠性的三个杠杆

杠杆 做法 效果
减少步数 把常用多步合并成一个复合工具 指数级提升成功率
缩小决策空间 枚举参数、限定可选值 降低幻觉
加校验与重试 每步输出做 schema 校验 拦截格式错误

⚠️ 参数校验失败要把错误原文回给模型，让它自己改。直接抛异常终止任务，是最浪费的一种处理 —— 模型通常第二次就能改对。

⚠️ 对写操作要格外小心。删数据、发邮件、下单这类不可逆操作，必须有人工确认或dry-run 模式。Agent 幻觉出一个参数就造成了真实损失，这是目前最典型的事故形态。

六、评估与可观测

维度 指标 采集方式
任务成功率 端到端完成比例 有明确判据的任务自动判定
步数 平均 / P95 步数 循环计数
工具错误率 调用失败比例 工具层埋点
成本 token / 单任务 累加 usage
轨迹质量 是否有冗余步骤 人工抽检 + LLM 裁判

⚠️ 没有轨迹日志的 Agent 无法调试。出问题时你要能回答「它在第几步、看到了什么、为什么这么选」。把每步的输入输出摘要落盘，比事后加日志便宜得多。

七、安全边界

风险 场景 对策
提示注入 工具返回的内容里藏指令 工具结果标记为「数据」，不参与指令解析
越权操作 模型调用超出用户权限的工具 工具层做权限校验，不信模型
数据外泄 把敏感信息拼进外部请求 出口过滤、字段脱敏
无限循环 工具持续返回空 步数 / 时间 / 成本三重上限
供应链 加载不可信的工具插件 白名单 + 签名

⚠️ 提示注入无法靠提示词防住。只要工具返回的内容进了上下文，模型就可能把它当指令。可靠做法是在架构上隔离：把不可信内容放在明确的「数据区」，且高危操作永远需要独立授权，不因模型说了什么而放行。

常见坑清单

  • 没有 max_steps，工具返回空时死循环烧钱
  • 一次性给模型 50 个工具，选择准确率崩掉
  • 工具描述含糊，模型反复猜参数
  • 工具返回整页 HTML / 全量 JSON，下一轮上下文爆掉
  • 只靠对话历史记进度，压缩后忘了做到哪
  • 每步都跑 Reflection，成本和延迟翻倍
  • 计划与执行脱节，不允许重规划
  • 参数校验失败直接抛异常终止，而不是回给模型自纠
  • 写操作（删除、支付）没有人工确认或 dry-run
  • 把工具返回内容当可信指令，被提示注入
  • 没有轨迹日志，出问题无法复盘
  • 以为换个更强的模型就能解决可靠性问题（步数才是主因）
