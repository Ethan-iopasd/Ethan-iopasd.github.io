开场：一句话结论

宏不是函数，build.rs 不是运行时，unsafe 不是关闭检查。 前两者是编译流水线的不同阶段，后者是一份「我保证已满足这些不变量」的契约 —— 编译器依然做类型检查，只是不再做那些它无法验证的内存安全证明。

一、四种宏，各在各的阶段

类型 声明方式 使用位置 何时展开
声明宏（macro_rules） macro_rules! name 表达式 / 语句 / item 解析后、类型检查前
过程宏 · derive #[proc_macro_derive(X)] #[derive(X)] 同上，作用于 item
过程宏 · 属性 #[proc_macro_attribute] #[name] 同上，可改写整个 item
过程宏 · 函数式 #[proc_macro] name!(...) 同上，输入输出都是 token

⚠️ macro_rules! 的卫生性（hygiene）只覆盖局部变量，不覆盖类型名和函数名。宏体内引用的 Vec、String 是在调用处解析的 —— 调用方 use 了同名符号就会出问题。过程宏则完全无卫生性，生成的代码必须写全路径（::std::vec::Vec）。

⚠️ 声明宏里 $x:expr 后面的 * 会贪婪匹配，vec![1, 2, 3] 里如果同时有 ($($x:expr),*) 和 ($($x:expr),+ $(,)?) 两个分支，顺序写反会让第一个分支永远匹配不到。宏分支按书写顺序尝试，不会选「更具体」的。

二、过程宏的工程约束

过程宏必须放在独立的 proc-macro = true crate 里，这是 Cargo 的硬性要求：

crate 作用
proc-macro2 提供可脱离编译器运行的 TokenStream（便于单元测试）
syn 把 TokenStream 解析成 AST，derive 用 DeriveInput
quote 用 quote! 模板把 Rust 代码片段拼成 TokenStream

⚠️ split_for_impl() 不能省。手写 impl<#generics> Trait for #name<#generics> 在带生命周期或 where 子句的泛型类型上必然出错，这是 derive 宏最常见的 bug。三个返回值分别对应「impl 侧泛型」「类型侧泛型」「where 子句」。

⚠️ 过程宏出错时 panic! 的报错位置很糟（指向 #[derive] 那一行）。用 syn::Error::to_compile_error() 返回结构化错误，能精确指向字段。

⚠️ 过程宏不能修改输入之外的任何东西。它无法读取文件系统、无法访问调用方的类型信息，derive 只能看到被标注的那个 item 的语法树。想做「跨类型反射」只能靠注册表模式或 build script。

三、build.rs：编译前的那段任意代码

build.rs 在 crate 编译之前运行，产物通过 OUT_DIR 交给主代码：

cargo: 指令 作用
rerun-if-changed=PATH 该文件变更时重跑（不写则任何文件变更都重跑）
rerun-if-env-changed=VAR 环境变量变更时重跑
rustc-env=K=V 注入编译期环境变量，代码里用 env! 读
rustc-link-lib=LIB 链接系统库
rustc-link-search=PATH 链接搜索路径
cargo:warning=MSG 在构建输出里打印警告

⚠️ 不写任何 rerun-if-changed 时，Cargo 的默认行为是「包内任意文件变动都重跑」，看似安全其实很糟：target/ 之外任何文件改动（包括 .git 索引）都会触发全量重编。反过来，写了 rerun-if-changed 之后只监控列出的文件，漏了 proto 或模板文件就会拿到过期产物。

⚠️ build.rs 在宿主机上编译运行，不是目标机。交叉编译时它拿到的 cfg! 和链接的是宿主机环境，判断目标平台要用 CARGO_CFG_TARGET_OS 这类环境变量，不能用 cfg!(target_os = ...)。

⚠️ build.rs 是供应链攻击的常见入口。它拥有完整的文件系统和网络权限，且默认在 cargo build 时静默执行。引入不熟悉的 crate 时值得看一眼它有没有 build.rs。

四、unsafe 到底解锁了什么

unsafe 只开启五件事，其余检查一个不少：

允许的操作 说明
解引用裸指针 *const T / *mut T
调用 unsafe fn 包括外部 C 函数
访问 / 修改 static mut 全局可变状态
实现 unsafe trait 如 Send / Sync
访问 union 字段 union 的读取总是 unsafe

⚠️ unsafe 块的边界要尽量小，并且每个块都要写 // SAFETY: 注释说明「为什么这里满足不变量」。这是社区惯例，也是 review 时唯一能验证的依据。unsafe { } 包住整个函数体等于没写。

⚠️ unsafe fn 的函数体在 Rust 2024 里不再自动是 unsafe 上下文。以前 unsafe fn 内部可以直接做 unsafe 操作，2024 edition 要求显式再写 unsafe {} 块。这是为了强制你标注每处不安全的边界。

五、写对 unsafe 的四条不变量

一个 unsafe 块是否「真的安全」，取决于你是否维持了编译器无法验证的那些条件。最常见的四类：

不变量 破坏后果 典型场景
指针必须指向有效、对齐、已初始化的内存 UB（段错误或静默读脏数据） slice::from_raw_parts
引用必须满足别名规则（&T 可共享 / &mut T 独占） UB，优化器可能重排 把裸指针转引用
长度不能超过分配大小 越界读，可能泄露内存 FFI 缓冲区
类型必须真的符合 trait 契约 逻辑错误或 UB unsafe impl Send

⚠️ from_raw_parts 的 len 为 0 时，指针仍必须是「对齐的非空指针」。std::ptr::null() 配 len = 0 是 UB，虽然实践中常常「看起来没事」。正确做法是 NonNull::dangling()。

⚠️ &mut T 独占性在 unsafe 里依然成立。把同一个裸指针转成两个 &mut T 是 UB，哪怕你不并发访问 —— LLVM 的 noalias 会基于这个假设做优化。

六、Miri 与工具链

写了 unsafe，就得有办法验证它没写错：

工具 检查什么 用法
Miri UB、越界、别名违规、未初始化读 cargo +nightly miri test
-Z sanitizer=address 内存越界、use-after-free 需 nightly
-Z sanitizer=thread 数据竞争 需 nightly
cargo clippy 常见错误模式、unsafe 误用 cargo clippy -- -D warnings
cargo geiger 统计依赖树里的 unsafe 用量 cargo geiger
cargo miri setup 初始化 Miri 环境 首次运行前

⚠️ Miri 只能验证「被执行到的那条路径」。测试覆盖率低的时候，Miri 通过不代表没 UB。而且 Miri 不支持 FFI 调用和部分系统调用，跑 unsafe 封装的 C 库时会被跳过。

⚠️ Miri 慢一到两个数量级，别在 CI 里跑全量集成测试，挑核心 unsafe 模块的单元测试跑即可。

七、什么时候真的该用 unsafe

场景 该用吗 替代方案
调用 C 库 必须 bindgen 生成绑定，自己只写薄封装
高性能数据结构（自写 Vec） 通常该用 先用安全实现 benchmark，确认瓶颈
零拷贝解析 常见 bytes crate 已封装好
消除借用检查器报错 不该 重构数据布局，或 Rc<RefCell> / Arc<Mutex>
访问硬件寄存器 必须 volatile 读写在裸指针上
实现自定义分配器 必须 GlobalAlloc 本身是 unsafe trait

判断标准很朴素：只有当「安全版本已测出性能瓶颈」或「必须跨越 FFI 边界」时才用 unsafe，而不是「编译器不让我过所以加 unsafe」。

⚠️ 用 unsafe 绕过借用检查器是最坏的一种用法。借用检查器的报错通常指向真实的设计问题（共享可变状态），绕过去之后问题从编译期挪到了运行期，而 Rust 的整个安全叙事就失效了。

八、宏、build.rs、unsafe 在发布链路上的影响

环节 影响
编译时间 过程宏 + syn 显著拉长；build.rs 每次依赖变更都重跑
二进制体积 声明宏展开的代码会重复；build.rs 注入的字符串常量很便宜
可复现构建 build.rs 里读时间戳 / 随机数会破坏可复现性
供应链风险 build.rs 与过程宏都在构建期执行任意代码
审计成本 unsafe 块必须有 // SAFETY:，否则 review 无从下手

⚠️ **cargo publish 不会运行 build.rs**，但 cargo install 会。所以 build.rs 里的网络请求在离线环境装包时会失败。

常见坑清单

  • 宏分支顺序写反，更具体的模式永远匹配不到
  • 以为 macro_rules! 有完整卫生性，宏体里裸写 Vec / String
  • 过程宏里手拼泛型参数，没用 split_for_impl()
  • 过程宏 panic! 报错定位到 #[derive] 行，看不出是哪个字段
  • 过程宏试图访问调用方的其他类型信息（拿不到）
  • build.rs 不写 rerun-if-changed，任何文件变动都触发全量重编
  • 写了 rerun-if-changed 但漏了模板 / proto 文件，拿到过期产物
  • 交叉编译时在 build.rs 里用 cfg!(target_os) 判断目标平台
  • unsafe { } 包住整个函数体，边界形同虚设
  • unsafe 块没有 // SAFETY: 注释，review 无法验证
  • slice::from_raw_parts(null, 0) 当合法用法
  • 同一裸指针转出两个 &mut T
  • unsafe impl Send 用来消除编译错误
  • Rust 2024 edition 下 unsafe fn 里没写 unsafe {} 块
  • 以为跑了 Miri 就没 UB（只覆盖被执行到的路径）
  • 为了绕过借用检查器加 unsafe
