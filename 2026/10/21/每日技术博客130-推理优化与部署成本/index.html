AI 系列第八篇。LLM 推理的瓶颈不是算力，是显存带宽：每生成一个 token 都要把全部权重从显存读一遍。理解了这一点，量化、KV cache、批处理、投机解码为什么有效就全都清楚了。

开场：一句话结论

Prefill 是算力密集，Decode 是带宽密集 —— 这是两件完全不同的事。 首 token 延迟看 Prefill（受算力和 prompt 长度支配），生成速度看 Decode（受显存带宽支配），而吞吐看批处理。优化前先确认你被哪个卡住。

一、两阶段：Prefill 与 Decode

阶段 做什么 瓶颈 指标 优化方向
Prefill 一次并行处理整个 prompt 算力（GPU FLOPS） TTFT（首 token 延迟） 减少 prompt、chunked prefill
Decode 逐 token 自回归生成 显存带宽 TPOT（每 token 时间） 量化、批处理、投机解码
模型规模 权重（FP16） Decode 理论下限（单 token） 说明
7B 14 GB ~14 GB / 带宽 单请求必然带宽受限
70B 140 GB ~140 GB / 带宽 必须多卡并行

以 H100（约 3.3 TB/s）为例，7B FP16 单 token 的权重读取理论上限约 4.2 ms，即约 240 token/s。这就是单请求的天花板，任何算法优化都突破不了它 —— 除非批处理把多个请求合在一起摊薄。

⚠️ 单请求的 Decode 速度由「权重字节数 / 带宽」决定，与算力几乎无关。这解释了一个反直觉现象：把 GPU 从 A100 换成算力翻倍的 H100，单请求生成速度提升有限（带宽只提升约 1.6 倍）。

⚠️ 量化能提速，正是因为它减少了要读的字节数。FP16 → INT8 让权重体积减半，Decode 速度理论上翻倍。这也是量化在推理侧比训练侧更立竿见影的原因。

二、批处理：吞吐的唯一来源

批处理方式 机制 吞吐 延迟
无批处理 一次一个请求 最低 最好
静态批处理 攒够 N 个一起跑 高 长请求拖累整批
连续批处理 每个 decode step 重新组批 最高 较好
PagedAttention KV cache 分页管理，避免碎片 高 好

⚠️ KV cache 才是批大小的真正限制。7B 模型权重 14 GB，一张 80 GB 卡看似能跑 5 个副本，但 8K 上下文 + 每请求约 1 GB 的 KV cache，实际能并发的请求数远低于想象。

⚠️ 连续批处理下「吞吐」和「延迟」是权衡关系。批越大，单请求的 TPOT 越慢（要等整批算完），但整体吞吐越高。在线服务要限制最大批大小，别为了吞吐牺牲交互体验。

三、KV cache：显存的大头

以 LLaMA-2 7B（32 层，32 个 KV 头，head_dim 128）为例，8K 上下文、单请求：

优化 做法 效果
GQA 多个 Q 头共享 KV 头（如 32→8） KV cache 降 4 倍
MQA 所有 Q 头共享 1 组 KV 降 32 倍，质量有损
KV 量化 KV cache 存 INT8 降 2 倍
PagedAttention 按块分配，按需增长 消除碎片，利用率可达 95%+
Prefix cache 相同前缀复用 KV 多轮对话省大量重算
滑动窗口 只保留最近 N 个 token 的 KV 长对话内存恒定

⚠️ 前缀缓存对「固定系统提示词 + 多轮对话」收益极大。同一段 2000 token 的系统提示，缓存后每轮省掉整个 Prefill。多数推理框架（vLLM、SGLang）默认开启，但要求前缀完全一致 —— 提示词里带时间戳会直接击穿缓存。

⚠️ KV cache 不能跨请求共享（除前缀外）。每来一个新请求就要新分配，这是并发能力的硬约束。并发数上不去时，先看 KV cache 占了多少显存。

四、量化：精度与速度的权衡

方案 权重精度 显存 质量损失 适用
FP16 / BF16 16 bit 基准 无 训练、高精度推理
INT8（W8A8） 8 bit 1/2 很小 生产默认
INT4（GPTQ / AWQ） 4 bit 1/4 小 单卡跑大模型
FP8 8 bit 1/2 极小 H100 等新卡
1.58 bit（BitNet 类） 三值 1/10 明显 研究阶段

⚠️ INT4 的提速不是 4 倍。权重读取量降到 1/4，但反量化有额外开销，实际 Decode 提速通常 1.5~2.5 倍。宣传的「4 倍加速」多为特定条件下的峰值。

⚠️ 量化对长上下文和推理任务损伤更大。短问答几乎无损，但数学推理、代码生成这类需要精细数值的任务，INT4 会明显掉点。上量化前必须跑自己的评估集。

五、投机解码：用便宜模型带贵模型

变体 思路 适用
Draft model 小模型猜，大模型验 通用，需额外模型
Medusa 多个解码头并行猜 无需额外模型
EAGLE 特征层预测 接受率高
N-gram / 提示查找 从 prompt 里抄候选 摘要、改写类任务
指标 含义 典型值
接受率（acceptance rate） 猜中的比例 60%~85%
加速比 实际提速 1.5~3×

⚠️ 投机解码是带宽受限场景的优化。批很大时 GPU 已经算力饱和，投机解码反而增加开销。低并发、低延迟场景才划算。

⚠️ 接受率决定一切。draft 模型与 target 模型分布差太远时，接受率低到 30%，反而比不投机更慢（多了一次前向）。draft 模型要和 target 同家族、同分词器。

六、部署形态与成本

形态 特点 成本 适用
自建 GPU 一次性投入 + 电费运维 中高（固定） 稳定高负载
按 token 计费 API 零运维，弹性 高（按量） 波动负载、快速验证
按小时租 GPU 弹性，需自己部署 中 中负载、可容忍冷启动
Serverless 推理 自动伸缩，冷启动慢 中 低频、突发
边缘/端侧 无网络依赖，隐私好 低 小模型、隐私敏感
成本项 容易被忽略的部分
显存 KV cache 占用导致并发上不去
冷启动 模型加载 7B 需数十秒，serverless 场景很致命
空闲成本 低峰期 GPU 空转，按小时计费也一样付钱
带宽 多卡张量并行的通信开销
运维 框架升级、模型更新、故障排查

⚠️ 算成本时要把「空闲」算进去。24 小时租一张卡，夜间利用率 5%，实际单 token 成本是满负载的 20 倍。低峰期缩容或切到 API 是更优解。

⚠️ 冷启动对 serverless 是硬伤。7B 模型从磁盘加载 + 初始化 CUDA 上下文通常 20~60 秒。有状态服务要预热池，否则第一个请求必然超时。

七、优化顺序：别做无用功

顺序 优化项 收益 成本
1 减少 prompt 长度（去冗余、压缩 RAG 上下文） 高 低
2 开启前缀缓存 高（多轮场景） 低
3 连续批处理 + PagedAttention 高（吞吐） 低（框架默认）
4 限制 max_tokens 中 低
5 INT8 量化 中 低
6 换 GQA 模型 中（并发） 中（换模型）
7 投机解码 中（低延迟） 中
8 INT4 量化 中 中（需评估）
9 多卡张量并行 高（大模型） 高

⚠️ 先做 1~4 再考虑量化。把 4000 token 的 RAG 上下文压到 1500，比任何量化都直接。很多团队上来就折腾量化，却留着大段冗余 prompt。

⚠️ max_tokens 不设上限是成本失控的头号原因。模型偶尔会输出几千 token 的重复内容，没有上限就一直烧钱。

常见坑清单

  • 把单请求 Decode 慢归因于算力不足，实际是带宽受限
  • 换更强算力的卡，期待生成速度线性提升
  • 只算权重显存，漏算 KV cache 导致 OOM
  • 批大小调到显存上限，忽略 KV cache 随上下文增长
  • 系统提示词里带时间戳，前缀缓存全击穿
  • 以为 INT4 能提速 4 倍
  • 量化后不跑自己的评估集，推理任务掉点没发现
  • draft 模型与 target 不同分词器，接受率极低
  • 高并发场景上投机解码，反而变慢
  • serverless 部署不预热，首请求必然超时
  • 算成本忽略空闲时间，实际单 token 成本远超预期
  • 不设 max_tokens 上限
  • 上来就量化，却留着几千 token 的冗余 prompt
