四 测试数据、Fixture 与不稳定测试治理 本篇

开场：一句话结论

绝大多数 flaky test 都不是「玄学」，而是三个可枚举的来源：状态没隔离、时间/随机不可控、外部依赖不稳定。 按这三类去查，比反复重跑有效得多。

一、Fixture 的作用域与生命周期

作用域 创建次数 适用
function（默认） 每个测试函数一次 首选，隔离最彻底
class 每个测试类一次 类内共享只读资源
module 每个模块一次 启动开销大的只读资源
session 整个会话一次 DB 容器、浏览器实例

⚠️ scope 越大越危险。module 级 fixture 里的可变对象会被多个测试共享，一个测试改了它，后续测试全受影响。默认用 function，只在确实只读时才放大。

⚠️ 用「事务 + 回滚」而不是「每次清表」。清表慢且容易漏（外键、自增 ID 重置）。事务回滚是 O(1)，且天然隔离。

二、测试数据的三种来源

方式 优点 缺点
固定 fixture（JSON/YAML） 可读、可 review 数据漂移后难维护
工厂函数（factory） 灵活、按需生成 需要维护工厂
生产数据脱敏 最真实 隐私与合规风险
原则 说明
每个测试自建数据 不依赖其他测试的产物
时间固定 显式传入，不用 now()
ID 唯一但可预测 uuid4() 或递增，避免冲突
只构造用到的字段 其余走默认值

⚠️ 绝对不要让测试依赖执行顺序。test_a 建的数据被 test_b 使用，一旦并行执行或单独运行就崩。这是 flaky 的第一大来源。

⚠️ 固定 fixture 会「腐烂」。表结构加了非空字段，几十个 JSON fixture 全部失效。用工厂函数，默认值集中一处改。

三、时间、随机与并发：三大不确定性源

不确定性源 症状 治理
时间 月初/月末、闰年、时区失败 freezegun / 注入 clock
随机 偶发断言失败 固定 seed
并发 只在 CI 并行时失败 隔离状态、避免共享文件
网络 偶发超时 用 mock / 本地容器
时区 本地过 CI 挂 统一 UTC

⚠️ time.sleep 在测试里几乎总是错的。它既慢又不稳（CI 机器负载高时不够）。用假时钟推进时间，或用事件/轮询等待条件。

⚠️ random.seed() 是全局副作用。它会污染同进程的其他测试。优先注入 Random 实例，而不是改全局。

四、Flaky Test 的诊断流程

步骤 做什么
1 单独跑 100 次，看失败率
2 加 -p no:randomly 排除顺序影响
3 并行跑，看是否只在并发时失败
4 查共享状态（DB、文件、全局变量、缓存）
5 查时间与随机
6 查外部依赖（网络、端口、临时目录）

⚠️ 「重跑就过」不是解决方案。它只是把问题藏起来。每个 flaky 用例都要么修掉，要么标记隔离并限期处理。

⚠️ CI 上失败、本地通过，先怀疑并发与资源。端口冲突、临时目录共享、数据库连接池耗尽，都是典型原因。

五、并行执行的坑

问题 原因 解法
端口冲突 多个 worker 抢同一端口 用随机端口或端口池
数据库冲突 共用同一个库 每 worker 一个 schema
临时文件冲突 固定路径 tmp_path fixture
全局状态污染 模块级变量 避免全局可变状态
随机顺序失败 测试间有依赖 每个测试自建数据

⚠️ pytest-xdist 默认按文件分发。同一文件的测试在同一 worker 顺序执行，跨文件并行。如果测试依赖跨文件状态，并行必炸。

⚠️ 数据库按 worker 分 schema 是标准做法。--dist loadscope + 每 worker 独立 schema，能解决 90% 的并行冲突。

六、测试可维护性

反模式 问题 改进
一个测试断言 20 件事 失败时不知道哪坏了 一个测试一个关注点
测试名 test_1 失败时看不出意图 test_refund_fails_when_not_paid
大量重复 setup 改一处要改十处 抽 fixture / 工厂
断言整个 JSON 加字段就红 只断言关心的字段
测试私有方法 耦合实现 测公开行为

⚠️ 「一个测试只断言一个概念」不是教条。同一个操作的多条相关断言放一起是合理的，关键是失败时能立刻定位。

⚠️ 测试名要能当文档读。test_refund_fails_when_not_paid 比 test_refund_2 有价值一个量级。

七、CI 上的测试稳定性

措施 效果
失败自动重试 1 次并标记 区分真失败与 flaky
记录 flaky 率 数据驱动治理
超时保护 防止挂死
失败保留日志/截图 事后可查
隔离不稳定用例 不阻塞主流程

⚠️ 自动重试是止痛药，不是解药。它能让 CI 变绿，但会掩盖真实问题。重试必须记录并统计，定期清理。

⚠️ 必须有超时保护。一个死锁的测试会挂住整个 CI，浪费几十分钟。pytest-timeout 是必备插件。

常见坑清单

  • fixture 用 module/session 作用域，测试间共享可变状态
  • 测试依赖执行顺序，单独跑就失败
  • 用「每次清表」而不是事务回滚
  • 测试里 time.sleep 等待
  • 全局 random.seed() 污染其他测试
  • 时间用 now() 而非注入固定时钟
  • 时区不统一，本地过 CI 挂
  • 并行执行端口/临时目录冲突
  • 断言整个 JSON，加字段就红
  • 测试名无意义，失败看不出意图
  • flaky 用例「重跑就过」不了了之
  • CI 没有超时保护，死锁挂住流水线
