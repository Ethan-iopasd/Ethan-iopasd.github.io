开场：一句话结论

UnderReplicatedPartitions > 0 是 Kafka 最重要的一个指标。 它意味着「某份数据正在变少」，此时任何一次 Broker 重启都可能触发数据丢失。其余的监控都围绕它展开。

一、必看的核心指标

指标 JMX 名称 阈值 含义
副本不足分区 UnderReplicatedPartitions > 0 持续 5 分钟 有副本同步落后
离线分区 OfflinePartitionsCount > 0 立即告警 分区不可读写
活跃 Controller ActiveControllerCount 集群总和 == 1 多个说明脑裂
ISR 收缩率 IsrShrinksPerSec 持续 > 0 副本频繁掉队
消息入站速率 MessagesInPerSec 业务基线 突降说明生产端异常
请求处理时间 RequestHandlerAvgIdlePercent < 30% 线程池接近饱和
磁盘使用率 系统指标 > 80% 即将拒写
网络线程空闲 NetworkProcessorAvgIdlePercent < 30% 网络线程饱和

⚠️ ActiveControllerCount 必须全集群求和为 1。如果每个 Broker 都是 1，说明发生了脑裂，可能同时有两个 Controller 在分配副本 —— 后果是数据错乱。

⚠️ RequestHandlerAvgIdlePercent 低于 30% 就要扩容。它反映的是请求处理线程池的空闲比例，掉到 0 意味着所有请求在排队，表现为生产/消费延迟暴涨。

二、消费滞后（Consumer Lag）

LAG 状态 判断 处理
稳定在低位 健康 无
缓慢上升 消费能力不足 扩消费者（≤ 分区数）
突然暴涨 消费端卡住或上游突增 先看消费端日志
持续下降 正在追平 观察
不变化但很高 消费者卡死 检查线程/阻塞
输出列 含义
CURRENT-OFFSET 已提交的 offset
LOG-END-OFFSET 分区最新 offset
LAG 差值
CONSUMER-ID 当前分配的消费者
HOST 消费者地址

⚠️ 消费者数超过分区数时，多出来的会空闲。order-service 有 6 个实例但 Topic 只有 3 个分区，那么 3 个实例完全分不到分区。扩容消费者前先确认分区数够。

⚠️ LAG 不下降但也不涨，通常是消费者线程阻塞（比如同步调用外部接口超时）。看 CONSUMER-ID 是否为空 —— 为空说明这个分区没有活跃消费者。

三、常见故障与定位

故障 现象 定位命令 常见原因
副本不同步 UnderReplicatedPartitions > 0 --describe 看 ISR 网络抖动、磁盘慢、Follower 跟不上
分区不可用 OfflinePartitionsCount > 0 --describe 看 Leader 所有副本都挂了
生产者超时 客户端报 TimeoutException 看 Broker 日志 kafka-request.log acks=all + ISR 不足
消费者反复 rebalance 日志刷 Rebalance 看 session.timeout.ms 消费处理超时
磁盘写满 写入报 NotEnoughReplicas df -h 保留策略配置过大
Controller 频繁切换 元数据操作超时 看 controller.log ZK/KRaft 会话超时

⚠️ --describe 里 Isr: 1,2 而 Replicas: 1,2,3 说明 broker 3 掉队了。持续掉队通常是磁盘 IO 跟不上，或者 replica.lag.time.max.ms 设得太小。

⚠️ rebalance 是「消费抖动」的头号原因。max.poll.interval.ms 默认 5 分钟，如果单批处理超过这个时间，消费者会被踢出组、触发 rebalance，然后无限循环。

四、Rebalance：为什么它这么贵

触发条件 说明
消费者加入/离开 扩容、重启、发布
心跳超时 session.timeout.ms 内没心跳
处理超时 max.poll.interval.ms 内没 poll
分区数变化 增加分区
配置 默认 建议
session.timeout.ms 45s 10~30s（Kafka 3.0+ 默认 45s）
heartbeat.interval.ms 3s session 的 1/3
max.poll.interval.ms 300s 按单批最大处理时间设
max.poll.records 500 处理慢就调小

⚠️ group.instance.id（静态成员）能大幅减少发布时的 rebalance。滚动重启时，消费者在 session.timeout.ms 内重新连上，就不会被踢出组。这是发布期抖动最有效的优化。

⚠️ max.poll.interval.ms 不是越大越好。设得太大，真卡死的消费者要很久才被发现；设得太小，正常的长批处理会被误踢。按 P99 单批处理时间的 2 倍设。

五、扩缩容的正确姿势

操作 影响 建议
加 Broker 不会自动迁移分区 需手动 reassignment
加消费者 触发 rebalance 分区数足够才有效
加分区 破坏 key 顺序 尽量一次性规划好
停 Broker ISR 收缩 先确认无 UnderReplicated

⚠️ 加 Broker 不会自动均衡。Kafka 不会主动把已有分区搬过去，必须手动 reassignment。这是新手最常误以为「加了机器就变快」的地方。

⚠️ 迁移必须限速且分批。一次搬几百个分区会把网络和磁盘打满，导致正常读写超时。按 Broker 逐个搬，每批不超过 10% 分区。

六、KRaft 模式的变化

维度 ZooKeeper 模式 KRaft 模式
元数据存储 外部 ZK 内置 Raft 日志
Controller 选举 ZK 临时节点 Raft 投票
元数据规模 ZK 节点数受限 支持百万级分区
故障恢复 依赖 ZK 会话 Controller quorum 多数派
部署复杂度 需维护 ZK 少一套组件

⚠️ KRaft 的 controller quorum 必须是奇数（3 或 5）。偶数在脑裂时无法形成多数派，会直接不可用。

⚠️ 从 ZK 迁移到 KRaft 不可逆。迁移前务必完整备份，并先在测试环境演练一遍。

七、日常巡检清单

检查项 频率 命令/指标
副本不足分区 每分钟 UnderReplicatedPartitions
离线分区 每分钟 OfflinePartitionsCount
磁盘使用率 每分钟 df -h
消费 LAG 每分钟 kafka-consumer-groups --describe
Controller 唯一性 每 5 分钟 ActiveControllerCount 求和
段文件数量 每天 ls /data/kafka/*/ | wc -l
日志保留是否生效 每周 对比磁盘增长与保留配置

⚠️ 「离线分区」和「副本不足」要分开告警。前者是已经不可用（P0），后者是正在变危险（P1）。混在一起会导致级别判断错误。

常见坑清单

  • 只监控 Broker 存活，不看 UnderReplicatedPartitions
  • ActiveControllerCount 全集群求和不等于 1 却没告警
  • 消费者实例数超过分区数，多余实例空转
  • max.poll.interval.ms 小于实际批处理时间，无限 rebalance
  • 发布时不用静态成员，每次都触发全量 rebalance
  • 加 Broker 后不迁移分区，以为自动均衡
  • 分区迁移不限速，打满集群带宽
  • 磁盘用满前没有告警，写入直接失败
  • KRaft controller 用偶数节点
  • ZK 迁移 KRaft 前没做备份演练
  • 把「离线分区」和「副本不足」混成一个告警
  • 段文件数暴增没发现，inode 被耗尽
