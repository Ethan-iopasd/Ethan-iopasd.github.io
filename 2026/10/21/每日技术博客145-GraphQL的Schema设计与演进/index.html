开场：一句话结论

GraphQL 的 schema 演进是「只增不减」：加字段安全，删字段危险，改类型是破坏性的。 因为客户端只查询它需要的字段，你无法知道谁在用什么 —— 除非靠 @deprecated 和字段使用统计。

一、Schema 设计的基本功

约定 理由
id: ID! 必有 客户端缓存与归一化的锚点
列表用 Connection（游标分页） 可扩展、稳定
输入用 XxxInput 与输出类型解耦
Mutation 返回 XxxPayload 可扩展错误字段
时间用自定义标量 DateTime 明确格式与时区

⚠️ 列表不要直接返回 [User!]!。一旦需要分页就得改类型，属于破坏性变更。从一开始就用 Connection 模式（edges + pageInfo + totalCount）。

⚠️ Mutation 不要只返回实体。updateProfile 返回 User 的话，将来要返回「警告信息」「部分失败字段」就无处可放。返回 Payload 包装类型。

二、空值与错误：最容易被设计错的地方

错误类型 表达方式 适用
业务错误（可预期） Payload.errors 字段 校验失败、状态不合法
系统错误（不可预期） GraphQL errors 数组 服务异常、超时
未找到 null + 明确文档 查询单个资源

⚠️ 业务错误不要抛 GraphQL error。errors 数组是「部分失败」的语义，客户端处理起来很别扭（数据在 data 里、错误在 errors 里，还可能都非空）。可预期的失败用 Payload.errors。

⚠️ String! 与 String 的差别是契约。把必填字段改成可空是「放松」但也可能让客户端少判空而崩；从可空改必填是破坏性变更。

⚠️ null 有三种含义要区分：字段不存在、无权限、真的没有。用不同的类型或错误码表达，别全靠 null。

三、破坏性 vs 非破坏性变更

变更 是否破坏 说明
加字段（可空） ✅ 安全 客户端不查就不影响
加字段（必填，无默认） ❌ 破坏 服务端可能返回 null 给非空字段
加枚举值 ⚠️ 半破坏 客户端 switch 没 default 会崩
加可选参数 ✅ 安全 ——
加必填参数 ❌ 破坏 现有查询会报错
删字段 ❌ 破坏 客户端查询直接失败
改字段类型 ❌ 破坏 兼容性极差
字段从可空改必填 ❌ 破坏 语义变严
字段从必填改可空 ⚠️ 半破坏 客户端可能少判空
@deprecated 标记 ✅ 安全 推荐做法

⚠️ 加枚举值是「半破坏」。客户端用 switch 处理枚举且没有 default 分支时，遇到新值会抛异常。文档里要明确要求客户端必须有 default 分支。

⚠️ @deprecated 不会自动生效。它只是文档标记，客户端仍然能查。必须配合使用统计，确认无人使用后才能真的删。

四、版本策略：GraphQL 通常不需要 v2

方案 做法 适用
无版本（推荐） 持续演进，靠弃用 大多数场景
URL 版本 /graphql/v2 整体切换 大重构
Schema 多版本并存 网关按客户端路由 移动端强制升级困难

⚠️ 移动端是「不能删字段」的主要原因。老版本 App 可能一年后才完全消失。要么长期保留字段，要么做 schema 版本路由。

⚠️ 字段使用统计是删字段的前提。没有统计就删，等于蒙眼拆弹。Apollo Studio / GraphQL Hive 都能做字段级使用分析。

五、分页：游标 vs 偏移

方式 优点 缺点
偏移（offset/limit） 简单、可跳页 数据变动时重复/遗漏
游标（cursor） 稳定、适合无限滚动 不能跳页

⚠️ 游标要包含「排序键 + 唯一 ID」。只用时间戳，同一毫秒的多条数据会重复或遗漏。用 (created_at, id) 复合键。

⚠️ totalCount 在大表上是性能杀手。每次分页都 COUNT(*)，百万行表上要几百毫秒。要么异步算，要么用近似值，要么干脆不提供。

六、Schema 组织与工具

实践 说明
按领域拆文件 user.graphql、order.graphql
共享标量与指令 scalar.graphql、directive.graphql
SDL 优先 先写 schema，再生成代码
Schema 校验 CI 里跑 lint + 破坏性变更检测
文档 每个字段写 description

⚠️ CI 必须做破坏性变更检测。graphql-inspector、rover 都能对比两个 schema 并标出 breaking change。没有这道闸，一次手滑就删了线上字段。

⚠️ description 不是可选的。GraphQL 的自动文档全靠它，写不好等于没有文档。

七、权限与可见性

方案 做法 特点
字段级鉴权 解析器里判断 灵活，易漏
指令（@auth） schema 上声明 集中，需工具链支持
Schema 裁剪 按角色生成不同 schema 最严格，复杂
查询复杂度限制 限制总成本 防滥用

⚠️ 字段级鉴权最容易漏。新增字段忘了加权限判断，就直接泄露。用指令在 schema 层声明，配合 lint 强制「敏感类型必须带指令」。

⚠️ GraphQL 让「越权查询」更容易。客户端可以自己拼嵌套查询，user { orders { items { supplier { contracts } } } } 一条请求拉穿全库。必须有深度限制 + 复杂度预算。

常见坑清单

  • 列表直接返回数组，后来要分页只能破坏性改
  • Mutation 只返回实体，没有错误字段位置
  • 业务错误抛 GraphQL error，客户端处理别扭
  • 加必填字段/参数，现有查询直接失败
  • 加枚举值不考虑客户端 default 分支
  • 删字段前没有使用统计
  • @deprecated 标了但从不清理
  • 移动端老版本还在用，字段已删
  • 游标只用时间戳，同毫秒数据重复
  • 大表上每次都算 totalCount
  • CI 没有破坏性变更检测
  • 字段级鉴权漏加，敏感数据泄露
  • 没有深度/复杂度限制，一条查询打穿全库
