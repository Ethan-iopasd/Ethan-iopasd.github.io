十二 异常链、日志与可观测性 本篇

开场：一句话结论

异常链回答「为什么会这样」，日志回答「当时发生了什么」，指标回答「现在有多糟」。 三者缺一，线上排障就只能靠猜。而这三样里最便宜、最常被省略的，恰恰是 raise ... from ...。

一、异常链：from 与隐式链

写法 效果 __cause__ __context__
raise B from A 显式因果 A A
except ...: raise B 隐式链 None 原异常
raise B from None 切断链 None None（抑制显示）
raise（裸） 重新抛出，保留原栈 不变 不变

⚠️ raise ... from None 会隐藏真实原因。只在「底层异常确实无关且会干扰阅读」时用，比如把 KeyError 转成「配置缺失」时。排查困难时第一件事就是看有没有被 from None 切断。

⚠️ except 块里必须用裸 raise 重新抛出。写 raise e 会重置堆栈起点，丢失原始行号，日志里看到的全是 raise e 那一行。

二、自定义异常体系

设计要点 说明
单一基类 上层可以用 except AppError 统一处理
携带结构化字段 code、http_status、detail
不继承 BaseException 只继承 Exception
消息面向人类，字段面向程序 别让程序去正则解析消息

⚠️ 不要从 BaseException 派生业务异常。BaseException 是给 SystemExit、KeyboardInterrupt、GeneratorExit 这类「必须终止」的异常用的，继承它会导致 except Exception 捕不到你的异常。

⚠️ 业务异常的 message 不要拼接敏感信息。它经常被直接返回给前端或写进日志，把 SQL、内部 URL、堆栈塞进去就是泄露。

三、异常处理的四个层次

层次 该做什么 不该做什么
最内层（库函数） 抛具体异常，带上下文 不吞异常、不打日志
业务层 转换成领域异常，from 保留原因 不吞异常
边界层（API/任务） 统一转成响应/记录日志 不抛裸异常给用户
顶层 兜底日志 + 优雅退出 不静默忽略

⚠️ 库代码里不要 print 也不要 logging。库应该抛异常，让调用方决定怎么记录。库自己打日志会导致同一个错误被记录多次，且格式不可控。

⚠️ 顶层兜底要区分「可重试」和「不可重试」。数据库连接超时可以重试，参数错误重试一万次也没用。

四、日志：结构化才有价值

级别 用途 生产建议
DEBUG 变量值、分支细节 默认关闭，按需开启
INFO 关键业务事件 保留，但控制量
WARNING 可恢复的异常 保留
ERROR 需要人工介入 保留并告警
CRITICAL 服务不可用 立即告警

⚠️ logger.exception() 只能在 except 块里用。它依赖 sys.exc_info()，在块外用会记录 NoneType: None，误导排查。

⚠️ 用 %s 占位符而不是 f-string。logger.info(f"user={uid}") 会在日志级别关闭时仍然执行字符串拼接；logger.info("user=%s", uid) 只在真正输出时才格式化。

五、trace_id：把一次请求串起来

机制 适用 说明
contextvars asyncio 协程安全，推荐
threading.local 多线程 线程安全，但 asyncio 里会串
显式传参 简单脚本 最可靠但最啰嗦

⚠️ asyncio 里用 threading.local 会串号。一个线程上跑多个协程，threading.local 是线程级的，不同请求会共享同一个 trace_id。必须用 contextvars。

⚠️ trace_id 要能被上游传入。如果网关已经生成了 trace_id，服务要复用而不是重新生成，否则跨服务串不起来。

六、指标与健康检查

指标类型 用途 例子
Counter 只增不减的累计量 请求数、错误数
Gauge 可增可减的瞬时值 连接数、队列长度
Histogram 分布统计 延迟分位数
Summary 客户端分位数 少用，聚合困难

⚠️ 别把 user_id、trace_id 做成标签。标签基数爆炸会让 Prometheus 内存直接吃满。标签只用低基数的维度（method、path 模板、status）。

⚠️ 路径要用模板而非真实值。/users/123 和 /users/456 是两个标签，会无限增长。用 /users/{id}。

七、线上排障的固定顺序

步骤 看什么 常见结论
1 错误率 / 延迟曲线 是突增还是缓升
2 最近的变更 90% 的问题来自最近一次发布
3 日志按 trace_id 过滤 定位单次请求的完整链路
4 异常链的根因 看 __cause__ 最底层
5 资源指标 CPU / 内存 / 连接池 / 磁盘

⚠️ 先看变更再看日志。日志量大的时候，从「最近改了什么」倒推比从「错误日志里找规律」快得多。

常见坑清单

  • except Exception: pass 吞掉错误
  • raise e 而不是裸 raise，丢失原始堆栈
  • raise ... from None 切断因果，排障时找不到根因
  • 业务异常继承 BaseException，except Exception 捕不到
  • 在 except 块外调用 logger.exception()
  • 用 f-string 拼日志，级别关闭时仍执行格式化
  • asyncio 里用 threading.local 存 trace_id，跨请求串号
  • 服务自己重新生成 trace_id，不接上游的
  • 把 user_id / trace_id 做成 Prometheus 标签，基数爆炸
  • 指标路径用真实值而非模板
  • 库代码里自己打日志，导致重复记录
  • 异常消息里拼接 SQL / 内部 URL，泄露敏感信息
