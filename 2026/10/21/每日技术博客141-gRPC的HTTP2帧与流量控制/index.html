开场：一句话结论

gRPC 的「多路复用」只解决了应用层队头阻塞，TCP 层的队头阻塞依然存在。 这就是为什么单条长连接在高丢包网络下反而更慢，也是 gRPC 在弱网环境需要特殊配置的根本原因。

一、HTTP/2 的分帧模型

概念 含义 说明
连接（Connection） 一条 TCP 连接 复用给所有 RPC
流（Stream） 一次 RPC 调用 有唯一 stream_id
帧（Frame） 最小传输单位 9 字节头 + payload
消息（Message） 一次序列化后的请求/响应 可跨多个 DATA 帧
帧类型 作用
HEADERS 携带 metadata（含 :path、content-type）
DATA 携带序列化后的 protobuf 字节
RST_STREAM 取消某条流
SETTINGS 协商连接参数（含流控窗口）
WINDOW_UPDATE 增加流控窗口
PING 保活与 RTT 测量
GOAWAY 优雅关闭连接

⚠️ stream_id 由客户端发起且单调递增，奇数给客户端、偶数给服务端（服务端推流用）。流一旦关闭，id 不可复用 —— 这就是为什么长连接跑久了会触发 GOAWAY 重连。

⚠️ 一条 DATA 帧有大小上限（默认 16KB，受 SETTINGS_MAX_FRAME_SIZE 约束）。一个 1MB 的响应会被拆成 64 个帧，帧之间可以穿插其他流的帧，这正是多路复用的实现方式。

二、多路复用解决了什么，没解决什么

问题 HTTP/1.1 HTTP/2
应用层队头阻塞 有（同连接串行） 无（流可交错）
TCP 层队头阻塞 有 仍然有
连接数 需要多条（6~8 条/域名） 一条足够
头部开销 每次全量 HPACK 压缩

⚠️ 弱网环境下不要迷信「单连接多路复用」。丢包率 2% 时，一条连接上的所有流都被同一个重传卡住。移动端 / 跨国链路通常仍需要多条连接或 QUIC。

⚠️ HTTP/3（QUIC）才是真正解决队头阻塞的方案。它把传输层放到 UDP 上，每条流独立重传。gRPC over QUIC 目前生态还不成熟，但方向明确。

三、流量控制：两级窗口

gRPC 有两层流量控制，容易混淆：

层级 控制方 作用范围
HTTP/2 流控 协议层 连接级 + 流级窗口
gRPC 应用层流控 grpc-go / grpc-java 单条流已接收但未处理的消息
配置（Go） 默认 作用
InitialWindowSize 64KB 单流初始窗口
InitialConnWindowSize 64KB 连接初始窗口
ReadBufferSize 32KB 读缓冲
WriteBufferSize 32KB 写缓冲
MaxConcurrentStreams 100（服务端） 单连接并发流上限

⚠️ 默认 64KB 窗口在高延迟链路上是性能杀手。BDP（带宽时延积）= 带宽 × RTT，100ms RTT、100Mbps 链路需要约 1.25MB 窗口才能跑满。窗口不够，吞吐就上不去。

⚠️ 窗口调大是有代价的。每个连接、每条流都按窗口预留缓冲，1000 条流 × 1MB = 1GB 内存。要按并发量和内存预算一起算。

四、Metadata：gRPC 的「Header」

类型 传输方式 大小限制
Metadata（Header） HEADERS 帧 默认 8KB
Message（Body） DATA 帧 默认 4MB（可调）
键名规则 说明
小写 HTTP/2 要求 header 名小写
-bin 后缀 值会被 base64 编码（用于二进制）
保留前缀 grpc- 协议内部使用，不要占用

⚠️ Metadata 有 8KB 上限。想把整个 JWT 或用户权限列表塞进去，很容易超限。大块信息应该放消息体，metadata 只放标识符。

⚠️ -bin 后缀会自动 base64。传二进制时如果自己又编码一次，服务端解出来就是双重编码的乱码。

五、连接管理与 GOAWAY

场景 行为 应对
服务端滚动重启 发 GOAWAY，旧连接不再接新流 客户端自动重连到新实例
MAX_CONCURRENT_STREAMS 打满 新流被拒绝 扩容或调大上限
连接空闲过久 被中间设备断开 配 keepalive
DNS 变更 客户端需重新解析 用 dns:/// resolver

⚠️ 每次请求都 Dial 是性能灾难。建立连接要做 TCP 握手 + TLS 握手 + HTTP/2 SETTINGS 交换，几十毫秒起步。**ClientConn 必须在进程内复用。**

⚠️ PermitWithoutStream: true 会被某些服务端判定为滥用。gRPC 服务端默认 MinTime 是 5 分钟，客户端发得太频繁会收到 GOAWAY 甚至被限流。

六、性能调优清单

维度 调整项 建议
吞吐 InitialWindowSize 按 BDP 设，1~4MB
并发 MaxConcurrentStreams 100~1000
消息大小 MaxRecvMsgSize 按业务设，别无脑调大
压缩 gzip / zstd 大消息开启，小消息别开
连接数 每目标 1~2 条 别一请求一连接
序列化 protobuf 已是最优，别换 JSON

⚠️ 小消息开压缩是负优化。压缩本身有 CPU 开销，几百字节的消息压缩后可能更大。经验阈值：> 1KB 才考虑压缩。

⚠️ MaxRecvMsgSize 调大不等于能传大文件。超过几 MB 的传输应该用流式（stream），一次性大消息会导致内存峰值和超时。

七、与 REST 的性能对比

维度 gRPC REST/JSON
序列化体积 小（二进制） 大（文本，字段名重复）
序列化速度 快 3~10 倍 慢
连接复用 原生多路复用 HTTP/1.1 需多条
浏览器支持 需 grpc-web 代理 原生
调试便利性 需工具（grpcurl） curl 即可
流式支持 四种模式 仅 SSE/WebSocket 模拟

⚠️ 性能优势主要来自序列化和连接复用，不是「协议更先进」。如果你的瓶颈是数据库查询，换 gRPC 不会有任何提升。

⚠️ 对外 API 优先 REST。gRPC 的生态优势在内部服务间，对外暴露要考虑浏览器、网关、第三方集成的兼容性。

常见坑清单

  • 以为 HTTP/2 解决了 TCP 层队头阻塞
  • 弱网环境用单连接多路复用，反而更慢
  • 流控窗口保持默认 64KB，高延迟链路吞吐上不去
  • 窗口调大但不算内存，OOM
  • Metadata 塞大块数据，超过 8KB 上限
  • -bin 后缀自己又 base64 一次
  • 每次请求都 Dial，握手开销吃掉性能
  • keepalive 发太频繁，被服务端 GOAWAY
  • 小消息开压缩，CPU 白耗
  • 用一次性大消息传文件，应该用流式
  • 对外 API 用 gRPC，浏览器和第三方接不了
  • 以为换 gRPC 能解决数据库瓶颈
