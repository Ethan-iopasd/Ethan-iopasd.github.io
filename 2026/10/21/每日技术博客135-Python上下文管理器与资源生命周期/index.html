开场：一句话结论

with 保证的是「退出时一定执行清理」，即使发生了 return、break、continue 或异常。 而 __exit__ 的返回值决定异常是否被吞掉 —— 这是它最容易被误用的一处。

一、协议本身

位置 语义 注意
__enter__ 返回值 绑定到 as 变量 不返回 self 也可以
__exit__ 参数 异常三元组，无异常时全为 None 三个都要接收
__exit__ 返回 True 吞掉异常 慎用，容易掩盖 bug
__exit__ 抛异常 替换原异常 会丢失原始堆栈上下文

⚠️ __exit__ 返回 True 会静默吞掉异常。这是 Python 里最容易写出「bug 消失但问题还在」的地方。除非你在写 contextlib.suppress 这类明确语义的工具，否则一律返回 False / None。

⚠️ __exit__ 里抛出的异常会覆盖原始异常。如果清理逻辑可能失败，用 try/except 包住并记录日志，别让清理失败掩盖真正的错误。

二、contextlib 的四个常用工具

工具 用途 要点
@contextmanager 用生成器写上下文管理器 yield 之前是 enter，之后是 exit
suppress(*exc) 忽略指定异常 比 try/except: pass 语义清晰
ExitStack 动态管理多个资源 后进先出关闭
closing(obj) 退出时调用 obj.close() 适配没有上下文协议的旧对象
nullcontext() 什么都不做的占位 让可选资源写法统一

⚠️ **@contextmanager 里必须用 try/finally 或重新 raise**。如果 yield 之后的代码抛异常却不重新抛出，原异常会被静默吞掉 —— 效果等同于 __exit__ 返回 True。

⚠️ @contextmanager 只能 yield 一次。yield 两次会抛 RuntimeError: generator didn't stop。需要多次进入的场景用类实现，或用 ExitStack。

三、ExitStack：动态资源管理

场景 为什么需要 ExitStack
资源数量运行时才知道 with a, b, c 写不出来
部分资源可能打开失败 已打开的要能正确回滚
需要提前释放某个资源 stack.pop_all() / close()
注册回调而非上下文管理器 stack.callback(fn, *args)

⚠️ ExitStack 的回调是后进先出（LIFO）。注册顺序是 A、B、C，退出时执行 C、B、A。资源之间的依赖顺序要靠注册顺序保证。

⚠️ enter_context 失败时不会注册回调。所以循环里某个资源打不开，之前打开的资源仍然会被正确清理 —— 这正是它比手写 try/finally 嵌套更可靠的地方。

四、异步上下文管理器

类型 方法 使用
同步 __enter__ / __exit__ with
异步 __aenter__ / __aexit__ async with
混合 contextlib.AsyncExitStack 动态异步资源

⚠️ 不能用 with 管理异步资源，反之亦然。async with 内部会 await，在同步函数里会直接语法错误。

⚠️ FastAPI 的 lifespan 本质就是一个异步上下文管理器。把连接池、后台任务的创建与销毁放进去，比 @app.on_event("startup") 更可靠（能保证 finally 执行）。

五、几个实战模式

模式 关键点
状态切换 记录旧值，finally 恢复
环境变量 区分「原本不存在」和「存在但为空」
计时 用 perf_counter 而非 time.time
事务 成功提交、异常回滚、异常要重新抛出

⚠️ 恢复环境变量时要区分 None 和空字符串。os.environ.get(k) 返回 None 说明原本不存在，应该 pop 而不是赋值空串。

⚠️ **计时用 time.perf_counter()**。time.time() 受系统时钟调整影响，可能返回负数间隔。

六、常见反模式

反模式 问题 正确做法
__exit__ 返回 True 吞掉所有异常 返回 False
@contextmanager 不重新抛出 异常被静默丢弃 try/finally 或 raise
try/except: pass 代替 suppress 意图不明确 with suppress(E):
手动 close() 不用 with 异常时泄漏 一律用 with
在 __exit__ 里做耗时操作 拖慢退出路径 只做清理
用 __del__ 代替上下文管理器 回收时机不确定 显式 with

⚠️ __del__ 不能当资源清理的保障。GC 时机不确定，解释器退出时甚至不保证调用。资源清理必须显式，with 是唯一可靠的方式。

⚠️ contextlib.suppress 只抑制指定异常。suppress(Exception) 等价于吞掉一切，和 except Exception: pass 一样危险。要写具体异常类型。

常见坑清单

  • __exit__ 返回 True，把所有异常静默吞掉
  • @contextmanager 里 yield 后不 raise，异常丢失
  • @contextmanager 里 yield 两次，报 RuntimeError
  • __exit__ 里抛异常，覆盖原始错误
  • 恢复环境变量时把 None 写成空字符串
  • 用 time.time() 计时，遇到时钟回拨
  • 用 __del__ 做资源清理，实际不保证执行
  • suppress(Exception) 吞掉一切异常
  • 动态资源数量硬写 with a, b, c，不用 ExitStack
  • 用 with 管理异步资源，或用 async with 管理同步资源
  • 在 __exit__ 里做耗时操作，拖慢退出
