四 鉴权、限流与查询成本控制 本篇

开场：一句话结论

GraphQL 的限流单位不该是「请求数」，而是「查询成本」。 同样是一条 POST，{ me { name } } 和十层嵌套的列表查询，代价差三个数量级。按请求限流等于没限流。

一、为什么传统限流失效

维度 REST GraphQL
请求粒度 一个端点一个资源 一条请求任意组合
代价可预测性 高（端点固定） 低（由客户端决定）
限流单位 QPS 需按查询复杂度
攻击面 大量请求 单条深查询

⚠️ 这条查询不是理论攻击。不加限制的话，1000 × 1000 × 1000 的嵌套足以让任何数据库跪下。深度限制是底线，不是可选项。

⚠️ first: 1000 这种参数必须封顶。客户端传多大就取多大，是最常见的疏忽。服务端强制 max(100)。

二、查询成本计算

成本模型 精度 开销 适用
字段计数 低 极低 快速拦截明显异常
深度加权 中 低 通用方案
列表参数放大 中高 低 有分页参数时
解析器实测 高 高（需执行） 事后审计

⚠️ 成本要在执行前算。执行后再算，攻击已经生效了。静态分析 AST 是唯一能在执行前完成的方式。

⚠️ 成本模型要按业务校准。字段加权系数应该反映真实代价：查缓存 1、查库 10、调外部 API 50。统一按 1 算，限制形同虚设。

三、深度与广度限制

限制 建议值 作用
最大深度 8~12 防嵌套爆炸
单次列表上限 50~100 防 first: 99999
单查询字段数 100~200 防广度攻击
别名重复 限制同名别名 防 a:user(id:1) a:user(id:2)...
总成本 按业务定 综合兜底

⚠️ 深度限制挡不住「别名攻击」。深度只有 2，但字段数上千。必须同时限制总字段数与成本。

⚠️ @skip / @include 指令会被计入静态成本。这没问题（保守估计），但要注意别把合法查询误杀 —— 预算要留余量。

四、鉴权：字段级 vs 全局

方案 优点 缺点
解析器内判断 灵活 易漏、分散
装饰器 / 指令 集中、可读 需工具链
Schema 层裁剪 最严格 实现复杂
数据层过滤 兜底 逻辑重复

⚠️ 鉴权要做两层：字段级 + 数据级。字段级决定「能不能调这个字段」，数据级决定「能看哪些行」。只做字段级，越权 ID 一猜就穿。

⚠️ info.context 里不要放可变状态。GraphQL 可能并行执行多个解析器，共享可变对象会有竞态。

五、限流：按用户、按成本

维度 限什么 说明
用户 每秒成本预算 主限流维度
IP 每秒请求数 防匿名刷
查询 单次成本上限 防单条爆炸
解析器 热点接口单独限 防单点打爆

⚠️ 按成本扣令牌，才能真正限制「重型查询」。按请求数限，攻击者用一条巨型查询就能绕过所有限制。

⚠️ 限流状态要放 Redis 等共享存储。多实例部署时用进程内字典，实际额度是「实例数 × 配额」。

六、持久化查询与白名单

方案 做法 收益
持久化查询（APQ） 客户端只发 hash，服务端查已注册查询 省带宽、防任意查询
查询白名单 只允许注册过的查询 最强防护
查询签名 服务端校验签名 防篡改

⚠️ 白名单是最有效的防护，但牺牲灵活性。适合自有 App（查询由团队控制），不适合开放的第三方 API。

⚠️ APQ 不能防住「首次注册」的攻击。第一次仍然会发送完整查询，仍需配合深度与成本限制。

七、缓存与批处理

手段 作用
DataLoader 批处理 + 请求内缓存，解决 N+1
查询结果缓存 相同查询直接返回
字段级缓存 热门字段单独缓存
HTTP 缓存 仅对 GET 查询生效

⚠️ DataLoader 的缓存只在「单次请求」内有效。跨请求复用会拿到过期数据，而且会造成内存泄漏。每次请求新建实例。

⚠️ GraphQL 默认走 POST，CDN 不缓存。想要 CDN 缓存，需要把只读查询改成 GET + 持久化查询。

常见坑清单

  • 按请求数限流，一条深查询绕过所有限制
  • 没有深度限制，嵌套查询拖垮数据库
  • first 参数不封顶，客户端传多大取多大
  • 只限深度不限字段数，别名攻击畅通
  • 成本模型所有字段权重都是 1，限制形同虚设
  • 执行后才算成本，攻击已生效
  • 只做字段级鉴权，越权 ID 一猜就穿
  • info.context 放可变状态，并行解析器竞态
  • 限流状态存进程内，多实例额度翻倍
  • DataLoader 跨请求复用，数据过期 + 泄漏
  • 没有持久化查询，任意查询都能发
  • 以为 POST 请求能被 CDN 缓存
