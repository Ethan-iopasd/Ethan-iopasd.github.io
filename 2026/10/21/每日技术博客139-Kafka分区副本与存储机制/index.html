每日技术博客 139 · Kafka（三）：分区、副本与存储机制

每日技术博客 · 2026-10-21 · 第 139 篇

Kafka 系列第三篇。Kafka 快的根本原因不是「磁盘顺序写」这么简单，而是分段日志 + 零拷贝 + 批量压缩三者叠加。理解了分段与索引，ISR 和 Leader 选举的代价就清楚了。

开场：一句话结论

Topic 只是逻辑名字，真正落盘的是 Partition；每个 Partition 是一条只追加的分段日志。 副本、ISR、Leader 选举，全都是在维护「这条日志有几份、谁说了算」。

一、Topic / Partition / Replica 三层关系

层级 是什么 数量关系
Topic 逻辑分类 业务决定
Partition 物理分片，并行度单位 每 Topic 几十~几百
Replica 每个 Partition 的副本 通常 3
Segment Partition 内的文件分段 每个 Partition 多个
概念 含义 关键点
Leader 处理读写的副本 每个分区只有一个
Follower 拉取同步的副本 不处理客户端请求
ISR 与 Leader 保持同步的副本集合 包含 Leader 自己
OSR 落后太多的副本 被踢出 ISR
AR 全部分配副本 replication-factor

⚠️ 分区数是「最大并行度」，改小不可能，改大不重平衡。增加分区会让同一个 key 落到不同分区，顺序性被破坏。所以分区数要一次性规划够。

⚠️ ISR 包含 Leader 自身。isr=3 意味着 Leader + 2 个 Follower 都同步。判断「能否写入」的是 min.insync.replicas，不是 replication-factor。

二、分区数怎么定

考虑 说明
吞吐 目标峰值 / 单分区能力，留 2 倍余量
消费者并行度 分区数 ≥ 消费者线程数（否则有线程空闲）
顺序性 需要严格顺序的 key 必须落在同一分区
Broker 数量 分区总数 / Broker 数 建议 < 200
元数据开销 分区越多，Controller 和 ZK/KRaft 压力越大
分区数 单 Broker 分区数 影响
太少 —— 并行度不足，消费者闲置
适中 < 200 健康
过多 > 2000 Leader 选举慢、元数据膨胀、故障恢复久

⚠️ 分区不是越多越好。单 Broker 超过 2000 个分区后，Controller 故障切换可能从秒级变成分钟级。集群总分区数建议控制在几万以内。

⚠️ 改分区数不迁移已有数据。老数据仍按旧分区分布，新数据按新规则 —— 这会让基于 key 的顺序保证失效。能用「新建 Topic + 双写迁移」就别改分区数。

三、分段日志与索引

文件 内容 查找方式
.log 消息批次（RecordBatch） 顺序写，追加
.index offset → 物理位置（稀疏，每 4KB 一条） 二分找到近似位置后顺序扫
.timeindex timestamp → offset 按时间查找
.snapshot 幂等/事务状态 内部使用
参数 默认 作用
log.segment.bytes 1 GB 单个段文件大小
log.roll.hours 168 段滚动时间
log.index.interval.bytes 4096 索引项间隔
log.retention.hours 168 保留时长
log.retention.bytes -1 按大小保留

⚠️ 索引是稀疏的。查 offset 12345 时，先在 .index 里二分找到 ≤12345 的最近一条（比如 12000 的位置），然后从那里顺序扫描。所以索引文件很小（约为日志的 1/1000）。

⚠️ 段文件是删除的最小单位。保留策略只会删整个段，不会删段内部分消息。段太大 = 磁盘释放不及时；段太小 = 文件数爆炸、索引开销上升。

四、为什么快：三个叠加因素

因素 机制 收益
顺序写 只在段末尾追加，不做随机寻道 接近磁盘顺序带宽
页缓存（Page Cache） 写入先进 OS 缓存，异步刷盘 写入延迟极低
零拷贝（sendfile） 数据从页缓存直接到网卡，不经过用户态 省两次内存拷贝
批量 + 压缩 多条消息合成 RecordBatch 压缩 网络与磁盘同时省

⚠️ Kafka 不保证「写入即持久」。默认 acks=1 只写 Leader 的页缓存，此时宕机仍可能丢数据。要真持久必须 acks=all + min.insync.replicas≥2 + unclean.leader.election.enable=false。

⚠️ 零拷贝只对「消费者读取」生效。生产端写入仍是正常的网络接收 + 追加。别把「零拷贝」理解成整体架构特性。

五、Leader 选举与 ISR

场景 行为 风险
ISR 中有存活副本 从中选新 Leader 不丢数据
ISR 全挂但 OSR 有存活 视 unclean.leader.election.enable 可能丢数据
全部副本挂 分区不可用 需等副本恢复
配置组合 数据安全 可用性
acks=all + min.insync=2 + unclean=false 高 中（2 副本挂就不可写）
acks=1 + unclean=true 低 高
acks=all + min.insync=1 中 高

⚠️ unclean.leader.election.enable=true 是「可用性优先」的明确取舍。它允许落后很多的副本当 Leader，代价是丢消息。金融、订单类场景必须设为 false。

⚠️ min.insync.replicas 是 Topic 级配置，不是 Broker 级。写在 Broker 上只是默认值，Topic 覆盖会生效。排查「写入失败」时先看 Topic 的实际配置。

六、存储规划

参数 建议
单盘容量 ≤ 4 TB（太大故障恢复慢）
磁盘类型 普通 SSD 或大容量 HDD，不需要高端 NVMe
RAID JBOD 优于 RAID（Kafka 自带副本）
文件系统 XFS（推荐）
预留空间 ≥ 20%

⚠️ Kafka 用 JBOD 而非 RAID。Kafka 已有副本机制，RAID 是重复冗余且会放大重建时间。一块盘坏了就让 Kafka 用副本恢复。

⚠️ 磁盘用满会导致 Kafka 拒绝写入甚至崩溃。必须监控磁盘使用率，并设置 log.retention.bytes 作为兜底上限。

七、常见运维操作

操作 命令 注意
查看 Topic kafka-topics.sh --describe 看 ISR 是否完整
增加分区 --alter --partitions N 不能减，破坏 key 顺序
增加副本 需生成 reassignment JSON 会触发大量数据复制
查看消费进度 kafka-consumer-groups.sh --describe 看 LAG
迁移分区 kafka-reassign-partitions.sh 限速避免打满带宽
删除 Topic --delete 需 delete.topic.enable=true

⚠️ --throttle 不加会把集群带宽打满，影响正常读写。生产迁移必须限速，完成后记得 --verify 再清除限速。

常见坑清单

  • 分区数规划太小，消费者线程大量空闲
  • 中途增加分区，破坏 key 顺序
  • 单 Broker 分区数超过 2000，故障切换变慢
  • 以为 ISR 不含 Leader
  • 只在 Broker 配 min.insync.replicas，Topic 覆盖后失效
  • unclean.leader.election.enable=true 用在订单场景
  • 以为 acks=1 就持久了
  • 段文件设得太大，磁盘释放不及时
  • 段文件设得太小，文件数爆炸
  • 磁盘预留不足，写满后拒绝写入
  • 分区迁移不限速，打满集群带宽
  • 用 RAID 而非 JBOD，浪费且放大重建
